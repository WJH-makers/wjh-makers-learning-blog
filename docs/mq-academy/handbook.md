## 0. 一句话定位

分布式线只把「装上传送带」讲成了**概念**,这一部把消息中间件从「会发会收」一路讲到「**敢用在钱上**」。

面向的是已经能交付一个后端系统、也听过 MQ 名词、但一被追问「这条消息会不会丢、会不会重、丢了怎么查」就哑火的进阶读者。因此本线的差异化立场只有一句:**任何一步都要说得出它的投递语义,并且被重放打过脸**。

## 1. 衔接与世界观

- 时间线:Java 线上云、分布式线八店连锁、微服务线拆完服务**之后**。咖啡站订单量继续涨,同步链路开始整条整条地拖垮——阿零第一次意识到「把请求收下」和「把活干完」必须分家。
- 舞台:豆豆咖啡站后巷新盖的**消息驿站**。墙上一面回执单墙(每张单据是一次投递记录),角落里堆着「无人认领包裹柜」(死信队列),后院一条越排越长的信巷(积压),楼上一块黑着的大屏——它要到全线最后一话才亮。
- 四卷主线:卷一 为什么要排队(01–07)→ 卷二 Kafka 内核(08–15)→ 卷三 敢用在钱上(16–23)→ 卷四 从消息到流(24–30)。
- 长期项目:**咖啡站订单全面异步化**——削峰、解耦、不丢单。

## 2. 角色表(硬约束,防人设漂移)

### 咕哥(Gu)—— 本线导师,消息驿站信鸽

- **外形**:一只不紧不慢的灰羽信鸽。**脚环上挂着一叠厚得垂到地上的回执单**,再急的信也先盖收件章再上路(先落盘、后确认的具象化);能同时记住一万封信的先后顺序,但只保证「同一条巷子里的信不串序」(分区内有序)。
- **性格**:急件也不慌的慢性子。最烦两种人——**没盖章就飞走的**(不等 ack 就当发成功),和**以为中间件能替你把业务擦干净的**(指望 MQ 自带幂等)。
- **口头禅**:「**先收下,再慢慢送。**」(削峰 / 异步 / 先持久化后处理,三关一语)
- **副口头禅**:「重复不可怕,可怕的是你没准备好被重复。」(每次读者想赖掉幂等设计时出场)
- **能力边界(铁律)**:
  1. 只保证「送到」,**从不承诺「只送一次」**;凡出现「恰好一次」四个字,必须当场拆成「至少一次 + 幂等/事务」,不许留成魔法。
  2. 不替阿零写业务幂等键——给判据、给演练动作,让阿零自己被重复打一次脸。
  3. 不下没有演练证据的可靠性断言;凡说「不会丢」,必须先跑一次 §4 的 🧯 重放演练。
  4. 沿用豆豆的五步排障法,咕哥版第一步永远是「**先看回执,再看业务**」——回执单不会说谎,记忆会。

### 阿零 —— 本线成长弧:从「会用队列」进化到「敢把钱放上去」

## 4. 本线专属深度栏目

### 4.1 📮 投递回执台(每话必有,恰好 1 个)

- **定位**:对标 Java 线的 🔀 多解台、JVM 线的 🔬 炉底显微镜。差异化 = **把这一话新增的每个环节,逐个钉死投递语义**——至多一次 / 至少一次 / 恰好一次,并写清它成立的前提与它先崩在哪。
- **规则**:
  1. 三档语义只能三选一,**不许写「基本不会丢」这种和稀泥的话**。
  2. 「恰好一次」出现时,必须在同一张表里写明它是靠什么换来的(幂等键 / 事务 / 两阶段提交);做不到就老实写「至少一次 + 消费端幂等」。
  3. 每张表必须有「先崩在哪」一列——前提被破坏时,语义会降级成哪一档。
  4. 结尾一句**咕哥判词**,给默认推荐。
- **格式模板**:

  ```text
  > **📮 投递回执台 · 这一步到底算送到没有?**
  >
  > | 环节 | 投递语义 | 成立前提 | 前提没了会怎样 |
  > |---|---|---|---|
  > | 生产者 → Broker | 至少一次 | acks=all + 失败重试 | 退化为至多一次(发完就走) |
  > | Broker 内部 | 至少一次 | 副本数与 min.insync.replicas 匹配 | 少数派存活时可能丢已确认的信 |
  > | Broker → 消费者 | 至少一次 | 先处理后提交位移 | 提前提交则退化为至多一次 |
  > | 端到端 | 至少一次 + 幂等 = 恰好一次(业务口径) | 幂等键覆盖全部写操作 | 漏一处写操作就漏一处重复 |
  >
  > 咕哥判词:我只保证送到,不保证只送一次——剩下那半句,得你自己接。
  ```

### 4.2 🧯 重放演练(按需触发,可靠性话必有)

- **定位**:对标分布式线的 🌩️ 断网演习。**没被重复打过脸的方案不算学会**。
- **规则**:动作、预期现象、判据三件套齐全;动作必须是读者自己能做的(手动重投、杀消费者、回拨位移、拔网线、把消费者停在提交位移之前)。
- **格式模板**:

  ```text
  > **🧯 重放演练 · 把这封信再送一次**
  >
  > 演练动作:消费者处理完业务、提交位移前 kill -9;重启后观察这条消息的去向。
  > 预期现象:同一条消息被重新投递,业务方法被执行第二次。
  > 判据:订单表新增记录数仍为 1,幂等表命中 1 次 —— 通过;新增 2 条 —— 不通过,回 §一 重设幂等键。
  ```

## 7. 写作红线

### 7.1 事实敏感项:发布前必须联网复核

- **铁律**:凡涉及「某中间件哪个版本引入 / 默认值是多少 / 某能力是否 GA」,发布前逐条联网复核(委托 opencode + DeepSeek,或 context7 查官方文档),**不凭记忆、不信旧博客**。核实优先于假设。
- 每话触及即必查的高危清单:Kafka 各参数的**默认值**(acks、位移自动提交、保留时长、副本数);「幂等 Producer / 事务 / Exactly-Once」在目标版本的适用边界;RocketMQ / RabbitMQ / Pulsar 的能力对照(选型话整表都要复核);Flink 的 API 形态与 checkpoint 语义;CDC 工具的版本行为。
- 没把握的版本号一律写**通用表述**(如「Kafka 4.x 起」),**不编具体小版本**;版本号写不实,整话作废重写。
- 涉及 Java / Spring 侧,基线固定为 Java 25 LTS + Spring Boot 4.x + `jakarta.*`;绝不写 `javax.*`。

### 7.2 术语一致性表(全线统一,首现标注英文)

| 统一用词 | 禁用 / 别名 |
|---|---|
| 投递语义(delivery semantics) | 不写「送达保证」 |
| 至多一次 / 至少一次 / 恰好一次 | 不写「exactly once 保证」这类含糊说法 |
| 分区(partition) | 不写「分片」 |
| 位移(offset) | 不写「偏移量」「游标」混用 |
| 消费组(consumer group)/ 再平衡(rebalance) | 首现必标英文 |
| 积压(consumer lag) | 不写「堆积量」混用 |
| 死信队列(DLQ) | 首现全称 |
| 本地消息表 / Outbox | 同一概念,首现写明二者等价 |
| 水位线(watermark) | 不写「水印」 |

### 7.3 其他红线

- **可靠性断言必附演练证据**(🧯 重放演练结果);没证据就让咕哥说「先重投一次再下结论」。
- 报错、回执、监控截图数据一律真实实录,不许编;编不出来就换一个真跑得出的例子。
- **绝不把「恰好一次」当卖点讲**:它永远是「至少一次 + 幂等 / 事务」的组合结果,每次出现都要拆开。
- **绝不把 MQ 讲成万能解药**:每一话都要留一句它换来的代价(延迟、复杂度、一致性窗口、运维成本)。
- 便利贴语法沿用全站规范:`> [!吐槽]`、`> [!彩蛋]`、`> [!警告]` / `> [!坑]`、`> [!强调]`、`> [!答案]`(折叠 details)、`> [!文字版]`;漫画分格 `> **〔n〕**` 格间空行;固定栏目前缀 `> **📮 投递回执台 · …**`、`> **🧯 重放演练 · …**`、`> **📋 投递失败单**`。
- 继承 Java 线 §10 全部「必须坚持 / 绝不做」;本线追加一条不做:**不罗列参数当咒语**——每个参数出场都必须绑一次「改前 / 改后」的可观测差异。
