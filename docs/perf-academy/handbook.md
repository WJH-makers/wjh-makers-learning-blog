## 0. 一句话定位

Java 线教你"会写",JVM 线带你看懂"炉底烧了什么",这一部补上 Java 工程师最硬核的缺口——
**不是背优化技巧,是建立一套可证伪的性能方法论**:任何"变快了"都必须有前后两条曲线撑着,任何"热点"都必须由采样器指出来,而不是由直觉指出来。

面向读完 Java 线与 JVM 线的进阶者。本线的差异化立场只有一句:**先量,再改**。

## 1. 衔接与世界观

- 时间线:JVM 线大结局(后厨全面 Java 25)**之后**。系统干净了,可流量也真的来了——第一次真实午高峰,咖啡站在 200 QPS 上被顶穿,曲线不是"慢",是"忽然全体一起慢"。
- 舞台:咖啡站后巷的**旧风洞计时场**。跑道两侧立着计时门、风速仪与一整墙历史成绩单;墙角堆着上一任店长的"优化秘籍"合订本(全是没有数据的口号,本线的常驻笑料)。
- 主线目标:**把豆豆咖啡站从 200 QPS 扛到 5000 QPS,且 P99 不破 200ms**,同时账单不许翻倍。
- 五卷主线:卷一 先量后改(01–07)→ 卷二 看见热点(08–14)→ 卷三 炉心调优(15–21)→ 卷四 全链路提速(22–28)→ 卷五 扛住与省钱(29–34)。
- 基线声明:Java 25 LTS、Spring Boot 4.x(`jakarta.*` 命名空间);不确定版本行为一律写通用表述并现场实测,不写猜的版本号。

## 2. 角色表(硬约束,防人设漂移)

### 秒秒(Miao)—— 本线导师,风洞猎豹

- **外形**:住在风洞计时场的猎豹。**爪垫里埋着传感器**,起跑前一定先蹲下来测一次风速与地面摩擦——世界上跑得最快的动物,出场动作却永远是"先蹲下"。
- **能力**:能把时间**掰开**给阿零看。她一挥爪,一段执行过程就被摊成一片草地:**每一帧栈都是一层被扑倒的草**,压得越宽说明在那儿待得越久,层叠起来就是一张火焰图。
- **性格**:冷静、极简、不留情面;讨厌形容词("快了不少""感觉流畅多了"一律驳回),只接受数字与区间。对"优化秘籍合订本"零容忍。
- **口头禅**:"**先量,再改。**"
- **副口头禅**:"你猜的那个热点,从来都不是热点。"
- **能力边界(铁律)**:
  1. 不给结论,只给**尺子和方法**:她可以帮阿零架好采样器,但热点必须由阿零自己在图上指出来。
  2. 不做没有观测证据的性能断言;凡是她自己说的数字,当场就得能复现。
  3. 一次只改一个变量,改完必须重跑基线——她自己也遵守 §7 红线。
  4. 沿用豆豆的五步排障法,秒秒版第一步永远是"**先取基线,再谈提速**";没有基线的优化,她直接判为"无效实验"。

### 阿零 —— 本线成长弧:从"能调优"进化到"能证明"

延续前作人设:此时已经能读字节码、看 GC 日志,但仍然习惯"凭经验猜哪里慢"。**每卷一次可见的能力上涨**:

| 卷 | 卷终时阿零能做到 |
|---|---|
| 卷一 | 说清吞吐/延迟/P99 的区别,写出不自欺的压测脚本与 JMH 基准 |
| 卷二 | 独立抓火焰图并按症状选对图种,用证据点名前三热点 |
| 卷三 | 独立完成一次 GC 选型与内存治理,并给出暂停时间的前后对照 |
| 卷四 | 端到端拆解一条请求链路,逐段量化收益,拒绝"银弹式"优化 |
| 卷五 | 设计压测与门禁流程,能在会议上用曲线和账单同时说服工程与老板 |

### 客串规则(豆豆 / 特米 / 焰焰)

- **豆豆**:本线升级为**会造假的甲方 + 流量发生器**——它要的是"平均值好看"和"报告今天就要",秒秒要的是 P99 与可复现;两者的拉扯是本线的固定喜剧张力。毒舌照旧,但**不当导师**。
- **特米**:从风洞通风口探头**递一句命令**(只递 CLI 线教过的:管道、`ss`、`pidstat`、`perf` 之类),台词量级一句;固定梗:"man 一下?你们性能人怕不是要先 measure 一下。"
- **焰焰**:**只在卷三回场**,负责 GC/JIT 的事实校对,与秒秒互怼"先热身,再起飞" vs "先量,再改"——两句其实是同一件事的两面,卷三末点破。
- 秒秒不去别线当导师;跨线联动只走 §8 钩子表。

## 4. 本线专属深度栏目(两个,每话各恰好 1 个)

### 4.1 📊 火焰图台

- **定位**:对标 Java 线的 🔀 多解台、JVM 线的 🔬 炉底显微镜;差异化 = **观测命令 + 读图方法**,让读者在自己机器上重演同一张图。
- **规则**:
  1. 命令照抄可跑,基线 Java 25;Windows(PowerShell 7)与 Linux(服务器)写法有差异时一句注明。
  2. 图必须真跑出来再描述,**逐条读图 2–4 句**:先说"哪条最宽",再说"宽的原因",最后说"这一刀砍在哪一层"。
  3. 不许贴一张图就走人——**必须给出"如果你看到的不是这样,可能是哪里没配对"**(采样频率、符号缺失、没开栈遍历等)。
  4. 按卷推荐工具箱:卷一 压测客户端 + JMH;卷二 async-profiler / JFR;卷三 GC 日志 + heap dump + 编译日志;卷四 慢查询日志 + 链路追踪 + 抓包;卷五 全链路压测平台 + CI 基准报告。
- **格式模板**:

  ```text
  > **📊 火焰图台 · <这一话要看的那张图>**
  >
  > 复现命令(照抄可跑):
  > ```bash
  > <采集命令>
  > ```
  > 怎么读:① 最宽的那条是 …;② 它的上层塌成一片,说明 …;③ 对照 CPU 图与 wall clock 图,差异出在 …。
  > 秒秒结语:<一句把图翻译成人话的结论>。
  ```

### 4.2 ⏱️ 基准红线

- **定位**:本线最重要的反鸡汤装置——**每一个优化都有适用区间**,离开区间它就是负收益。
- **规则**:
  1. 必须写清三件事:**在什么量级下成立**(QPS / 数据规模 / 并发度)、**收益量级**(百分比或绝对毫秒)、**代价**(内存、复杂度、一致性、钱)。
  2. 必须给一条"**什么时候别做**"——没有反例的优化建议一律不许上线。
  3. 数字来自本话实测,不引用没跑过的网帖结论;引用他人数据时注明硬件与负载。
- **格式模板**:

  ```text
  > **⏱️ 基准红线 · <这个优化>什么时候才划算**
  >
  > | 维度 | 结论 |
  > |---|---|
  > | 成立量级 | … QPS / … 数据量以上 |
  > | 收益 | P99 从 … 降到 …(实测) |
  > | 代价 | … |
  > | 什么时候别做 | … |
  ```

## 7. 写作红线

- **一切性能断言必须附观测证据**:前值、后值、判据、环境三件套缺一不可;没数据的话让秒秒原样驳回("先量,再改")。
- **一次只改一个变量**:同一话里同时改 GC 参数和代码,这一话作废——因为读者学不到归因。
- **不把参数当咒语罗列**:每个 JVM/内核/连接池参数出场都必须绑一次观测(改前 vs 改后),并写清它在哪一层生效。
- **拒绝银弹措辞**:禁止"用了 X 性能提升 10 倍"这类无区间断言;所有收益必须写进 ⏱️ 基准红线的适用区间。
- **实录不许编**:命令输出、火焰图描述、GC 日志片段、压测报告一律真实跑出来再节选(≤15 行);编不出来就换一个跑得出的例子。
- **版本敏感事实发布前联网复核**:凡涉及"哪个 JDK/Spring Boot 引入或改变了某行为、某 GC 默认开关",逐条用 opencode+DeepSeek 或 context7 核实,不凭记忆、不信旧攻略。没把握就写通用表述。
- **术语一致性**(首现标注英文):吞吐量(throughput)/ 延迟(latency)/ 尾延迟(tail latency)/ 百分位 P99(不写"99 线")/ 火焰图(flame graph)/ 采样剖析(sampling profiler)/ 虚拟线程(virtual thread,不写"协程")/ 容量水位(不写"负载率")。
- 便利贴语法沿用全站规范(`lib/markdown.ts` STICKY_CLASS):`> [!吐槽]`、`> [!彩蛋]`、`> [!警告]` / `> [!坑]`、`> [!强调]` / `> [!重点]`、`> [!答案]`(折叠 details,放选读硬核推导)、`> [!文字版]`;漫画分格 `> **〔n〕**` 格间空行;固定栏目前缀 `> **📊 火焰图台 · …**`、`> **⏱️ 基准红线 · …**`。
- 继承 Java 线 §10 全部"必须坚持 / 绝不做"。
