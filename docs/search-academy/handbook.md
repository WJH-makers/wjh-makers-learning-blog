## 0. 一句话定位

站内搜索能搜文章,但**咖啡站自己的菜单、订单、评论还在用 `LIKE '%…%'`**。这一部带阿零把"模糊查询"进化成真正的搜索引擎——**从倒排/TF-IDF/BM25 的第一性,到 Elasticsearch 的分片与相关性调优,再到向量检索与 RAG 会师**。

本线的差异化立场是:**每一次检索,都要能还原成"怎么建表、怎么查表"**。搜索不是玄学,是"不是遍历,是查表"这句话的层层展开——先把索引结构讲清,再谈排序为什么这么排。

## 1. 衔接与世界观

- 时间线:咖啡站上云、订单与评论海量沉淀**之后**。午高峰一次"搜拿铁"把数据库拖垮,阿零那句 `LIKE '%咖啡%'` 全表扫描跑瘫,把他逼进二楼档案室。
- 舞台:豆豆咖啡站**二楼·情报室**(堆满菜单卡片、订单存根与顾客评论便签的档案室)。天窗上住着一位老住户——狐狸「寻寻」。
- 四卷主线:卷一 搜索的第一性(01–08)→ 卷二 Elasticsearch 工程(09–16)→ 卷三 相关性调优(17–23)→ 卷四 向量检索与 RAG 会师(24–30)。

## 2. 角色表(硬约束,防人设漂移)

### 寻寻(Xun)—— 本线导师,情报室狐狸

- **外形**:住在档案室天窗、鼻子极灵的狐狸。**能从一整座图书馆里瞬间嗅到你要的那一页**(相关性召回的具象化);**尾巴扫过一排书脊,身后就凭空建好一张倒排索引**(词 → 文档号的糖葫芦串)。爱把问题拆成"建表一半、查表一半"两栏。
- **性格**:优雅、克制、略高冷;厌恶一切"全表扫一遍"的蛮力;被问"怎么搜得更准"时不急着答,先反问需求。
- **口头禅**:"**不是遍历,是查表。**"(倒排 / 索引 / 工程效率三关一语)
- **副口头禅**:"**先想清楚『相关』到底是什么意思。**"(把"搜得更准"这种模糊诉求逼成可打分的目标,引出 🎯 相关性台)
- **能力边界(铁律)**:
  1. 只讲检索的**原理与可复现的建表/查表方法**,不替阿零写业务代码;给结构、给公式、给命令,让阿零自己跑。
  2. 不下没有评测证据的"更相关"断言——她自己也遵守 §7 的红线,任何排序改动都要过评测。
  3. 不吹未落地的"AI 搜索银弹";涉及向量/RAG 只讲"检索环节"能负责的部分,超出的一句"那是生成的事,不归检索"。
  4. 沿用豆豆的五步排障法(观察 → 收集 → 假设 → 改一个变量 → 重跑验证),但寻寻版第一步永远是"**先看它到底建了什么表、查了哪条路**"。

### 阿零 —— 本线成长弧:从"会查库"进化到"会搜索"

延续前作人设:此时已能交付系统,但把"搜索"约等于"SQL 模糊查询"。**每卷一次可见的能力上涨**:

| 卷 | 卷终时阿零能做到 |
|---|---|
| 卷一 | 徒手实现倒排 + BM25,说得清"相关性分"怎么算,搜索好坏能用指标量 |
| 卷二 | 独立用 Elasticsearch 建索引:分片副本、mapping、query/filter、深分页自己拍板 |
| 卷三 | 会先定义"相关"再调排序,function_score、同义词、纠错、个性化 + A/B 一条龙 |
| 卷四 | 把关键词与向量混合检索接进 RAG,并用检索指标证明它真的更好——**能自己判断一个检索方案好不好** |

### 客串规则(豆豆 / 特米 / 焰焰)

- **豆豆**:查询流量发生器——**只在压测/深分页/脑裂等负载话出现**(制造午高峰的搜索风暴与刁钻 query),保持毒舌但**不当导师**(本线导师是寻寻,豆豆只制造麻烦 + 吐槽一句)。
- **特米**(CLI 线):从档案室通风管**递一句命令**(只递 CLI 线已教过的:`curl`、`jq`、管道),用来直接打 ES 的 `_search`;台词量级一句,不抢戏。
- **焰焰**(JVM 线):仅在深分页 OOM 那话探头**递一句 GC / 堆观测**,把"内存爆了"接回 JVM 线,不展开。
- 寻寻不去别线当导师;跨线联动只走 §8 钩子表。

## 4. 本线专属深度栏目(两块)

### 🔍 倒排台(每话必有,恰好 1 个)

- **定位**:对标 JVM 线的 🔬 炉底显微镜;差异化 = **永远把检索还原成"怎么建表、怎么查表"两栏对照**。口号:"不是遍历,是查表。"
- **规则**:
  1. 分**建表(索引侧)**与**查表(查询侧)**两栏,讲清同一个词/文档在两侧各经历什么。
  2. 卷二起命令照抄可跑(`curl` / `_analyze` / `_search` / `explain`),基线 Elasticsearch 8.x/9.x 系;输出真实节选、**≤15 行**,不许手编。
  3. 按卷推荐工具箱:卷一 手写倒排的打印/断点;卷二 `_analyze`(看分词)、`_search` + `explain`(看打分)、`_cat/shards`;卷三 `explain` 拆 function_score、`_termvectors`;卷四 向量 `knn` 查询 + 距离打印。

### 🎯 相关性台(相关性/排序话必有)

- **定位**:排序为什么这么排——**把打分公式摊开、把每个信号逐条称重**。用于卷一 BM25、卷三全卷、卷四混合检索。
- **规则**:表格化列"信号 × 权重 × 为什么";任何"更相关"的结论必须绑一次评测数值(§7 红线);给"默认推荐 + 理由",不许只罗列。

## 7. 写作红线

### 7.1 版本敏感事实:发布前必须联网复核

- **铁律**:凡涉及 Elasticsearch/Lucene 的 API 形态、默认值(分片默认数、`refresh_interval` 默认、`from+size` 上限 `index.max_result_window`)、`knn`/向量检索语法、混合检索(RRF)是否 GA,发布前逐条用 opencode+DeepSeek 或 context7 联网复核,**不凭记忆、不信旧博客**。核实优先于假设。
- 高危清单:ES 版本相关的 query DSL 写法;`search_after` / PIT 的 API;向量字段类型与 `knn` 语法;RRF / 混合检索的可用版本;任何"默认开启/关闭"断言。技术基线:Java 25 LTS / Spring Boot 4.x / jakarta;ES 写"8.x/9.x 系"这类通用表述,不确定的具体小版本号不写死。
- **不吹 AI 银弹**:向量/RAG 只讲检索环节能负责的部分;"大模型幻觉"归生成侧,本线只对"召回对不对"负责。

### 7.2 术语一致性表(全线统一,首现标注英文)

| 统一用词 | 禁用/别名 |
|---|---|
| 倒排索引(inverted index) | 不写"反向索引" |
| posting list(倒排列表) | 首现标英文 |
| 分词(tokenization)/ 分词器(analyzer) | 不写"切词器/分析仪" |
| 相关性(relevance)/ 相关性打分 | 不写"匹配度"当术语 |
| 召回(recall)/ 准确率(precision) | 两者不可混用、不可互换 |
| Elasticsearch(ES)| 首现全称,后文 ES |
| query 上下文 / filter 上下文 | 不写"查询模式/过滤模式" |
| 向量检索(vector search)/ ANN(近似最近邻)| 首现标英文 |
| Embedding(嵌入向量)| 保留英文为主 |
| 混合检索(hybrid search)/ RRF | 首现标英文 |

### 7.3 其他红线

- **"更相关"必附评测证据**(🎯 相关性台的指标数值或 A/B 结果);没证据的相关性话一律让寻寻说"先想清楚『相关』是什么,再去评测台上量一遍"。
- 报错、`_search` 结果、`explain` 输出、向量距离一律真实实录,不许编造;编不出来就换一个真跑得出的例子。
- 便利贴语法沿用全站规范(`lib/markdown.ts`):`> [!吐槽]`、`> [!彩蛋]`、`> [!警告]` / `> [!坑]`、`> [!强调]` / `> [!重点]`、`> [!答案]`(折叠 details,放硬核推导如 BM25 公式)、`> [!文字版]`;漫画分格 `> **〔n〕**` 格间空行;固定栏目前缀 `> **🔍 倒排台 · …**`、`> **🎯 相关性台 · …**`、`> **📋 编译官罚单**` 等,便于一眼识别。
- 继承 Java 线 §10 全部"必须坚持 / 绝不做";本线追加两条不做:**不把 ES 参数当咒语罗列**(每个参数出场必绑一次建表/查表观测);**不把"搜不准"简单归因为"数据不够"**——先看是索引结构、分词还是排序信号的问题。
