## 0. 一句话定位

云原生线教你**把系统送上去**,这一部教你**送上去之后,怎么知道它还活着**。

差异化立场只有一句:**一切结论都必须有一条数据能证明**。所以本线不讲"装个大屏就叫可观测",而是把三件事逐话夯实——
**能发现吗?能定位吗?能证明修好了吗?** 全线的终点是一个可验收的目标:**咖啡站的任何一次异常,三分钟内说得清**。

面向读者:已经能把服务部署上线的人(读完 Java 线 + CLI 线,最好也读过云原生线)。

## 1. 衔接与世界观

- 时间线:云原生线连锁舰队出海、微服务线拆完档口**之后**。咖啡站不再是"能不能跑"的问题,而是"跑着跑着谁也说不清它怎么了"——大屏一片绿,顾客却在群里说下不了单。
- 开场事故:一个深夜,订单成功率悄悄掉了 3%,没有任何告警响;第二天靠顾客投诉才发现。阿零翻了一夜日志,写下那句本线的起点:「日志有一堆,可我一个问题都答不上来。」
- 舞台:咖啡站**楼顶的夜视观测台**——一间只在夜里亮灯的小屋,三面墙分别贴着日志纸带、指标曲线和一整面挂满细线的追踪墙;墙角堆着上一任值班留下的、没人看的 47 块看板。
- 四卷主线:卷一 日志不是打印(01–07)→ 卷二 指标与告警(08–14)→ 卷三 一条线串起来(15–21)→ 卷四 从数据到决策(22–28)。

## 2. 角色表(硬约束,防人设漂移)

### 瞭瞭(Liao)—— 本线导师,夜视猫头鹰

- **外形**:栖在观测台屋檐上的猫头鹰。**脖子能转 270 度**(视角几乎没有盲区,每次转头都是"换一个观测维度"的具象化);**夜里比白天看得清**(别人熄灯下班时她才上班);**左眼看指标、右眼看日志**,两只眼各看一半世界,所以她总说"只用一只眼睛看,你会瞎一半";爪子里始终攥着一根把两边串起来的线——那根线就是 **TraceID**。
- **性格**:安静、慢、爱反问。从不为"直觉"背书,也不嘲笑猜测,只是把猜测立刻翻译成一个可查询的问题。
- **口头禅**:「**看不见的,才最贵。**」(故障时长、误告警成本、看不见的技术债,三关一语)
- **副口头禅**:「先问自己:这个问题,数据答得了吗?」(引导读者先设计观测再动手,对标特米的"man 一下"、焰焰的"JEP 里都写着呢")
- **能力边界(铁律)**:
  1. **不直接说"哪里坏了"**,只给出"用哪条数据能证明它坏了";答案永远由阿零自己查出来。
  2. 不下没有查询语句支撑的结论——她自己也守 §7 的红线。
  3. 不推销工具:任何工具出场都要先说清"它替代了哪一次人肉翻日志"。
  4. 沿用豆豆的五步排障法(观察 → 收集 → 假设 → 改一个变量 → 重跑验证),瞭瞭版把第一步改成"**先确认这个现象在数据里长什么样**"。

### 阿零 —— 本线成长弧:从"翻日志的人"进化到"设计观测的人"

| 卷 | 卷终时阿零能做到 |
|---|---|
| 卷一 | 写出机器能检索、半年后仍是证据的日志,并说得出每个字段为谁而存在 |
| 卷二 | 独立给一个新服务布点、定 SLO、写出一条不会误报的告警 |
| 卷三 | 顺着一条 TraceID 走完全链路,并在异步边界把断掉的线接回去 |
| 卷四 | 主持一次事故:三分钟定位、给出证据、开一场不设被告席的复盘 |

### 客串规则(豆豆 / 特米 / 库舵)

- **豆豆**:本线的**第一报警人**兼**被观测对象**——顾客投诉先到它这儿,同时它自己就是那台被贴满探针的咖啡机。保持毒舌,但**不当导师**(本线导师是瞭瞭);经典位:每次阿零想"再加一块看板",豆豆先问"这块屏谁看?"
- **特米(CLI 线)**:从通风管递一句命令(只递 CLI 线教过的:`journalctl`、`grep`、管道、`ss`),台词量级一句;固定梗:"man 一下?你们这行现在流行的是——查一下。"
- **库舵(云原生线)**:只在追踪与看板话隔空出现一次,交接口径为"**我负责让它跑起来,她负责让你看得见它在跑**";两线共用同一条 TraceID 设定,不得互相改写。
- 瞭瞭不去别线当导师;跨线联动只走 §8 钩子表。

## 4. 本线专属深度栏目

### 4.1 🔭 夜视仪(每话必有,恰好 1 个)

- **定位**:对标 Java 线 🔀 多解台、JVM 线 🔬 炉底显微镜、CLI 线 🪟 双系统对照;差异化 = **每话给出一段可复现的查询语句或看板配置**,读者复制过去就能在自己站上跑出一个数。口号:"看不见的,才最贵。"
- **规则**:
  1. 查询照抄可跑:日志检索(结构化字段过滤)、PromQL、trace 过滤条件、看板面板配置(以 JSON/YAML 片段或面板要素表呈现),按本话主题三选一。
  2. **输出必须真跑出来再节选**(可用脱敏后的自造数据,但形态必须真实),≤15 行,不许手编;逐行解读 2–4 条,每条一句话。
  3. **必给"小水管版"**:教科书方案(全套采集 + 存储 + 看板)之外,永远补一个能在 2C 小服务器上跑起来的最小可用替代;跑不动的方案不算方案。
  4. 按卷推荐工具箱:卷一 结构化日志检索与字段过滤;卷二 PromQL(`rate` / `sum by` / 直方图分位)+ 告警规则片段;卷三 trace 过滤与瀑布图读法、Collector 处理器配置;卷四 看板面板配置、成本核算表、剖析火焰图读法。
  5. 不写产品 UI 的点击路径(界面会变),只写**查询、配置与判读方法**。
- **格式模板**:

  ```text
  > **🔭 夜视仪 · <这一话你该查什么>**
  >
  > 复现查询(照抄可跑):
  > ```promql
  > sum by (route) (rate(http_server_requests_seconds_count{outcome="SERVER_ERROR"}[5m]))
  > ```
  > 真实输出(节选):
  > ```text
  > {route="/orders"}  0.83
  > {route="/menu"}    0.00
  > ```
  > 逐行解读:① 只有下单路由在报错,菜单没事——范围一下缩到一个接口;② 0.83/s 换算成每分钟约 50 次,和顾客投诉量级对得上。
  > 小水管版:没有 Prometheus 的话,先用结构化日志按 `level=ERROR` + `route` 聚合,结论一样,只是慢一点。
  > 瞭瞭结语:你查不出来的部分,才是这次故障真正的成本。
  ```

### 4.2 ❓ 三问自检(每话结尾必有,固定三问)

放在第 11 步,三行答完,**不许留空、不许写"暂无"**:

| 问 | 要回答什么 | 不合格的答法 |
|---|---|---|
| **能发现吗?** | 这类问题发生时,有没有一条信号会主动告诉我们(告警/看板/巡检) | "看日志能看出来"(没人半夜盯日志) |
| **能定位吗?** | 从发现到锁定到"哪个服务、哪一行、哪一单",要走几步、每步查什么 | "再排查一下"(没有路径就等于没有能力) |
| **能证明修好了吗?** | 修完之后用哪条数据、看多久,才能说它真的好了 | "重启后没再复现"(没有观测判据) |

- 三问必须与本话内容咬合:本话解决了哪一问,就在那一问上给出具体查询;还没解决的那问,明确写"下一话解决"并与第 12 步悬念对上。
- 卷终话的三问升级为**整卷验收**:三问全绿才算这一卷的检查点达成。

## 5. 卷结构与检查点版本链(对齐 `series-obs.ts` 的 `projectStage`)

- 版本链(卷终话为里程碑):
  `obs-v1 日志可检索(07)→ obs-v2 告警可信(14)→ obs-v3 一单可追(21)→ obs-v4 全线收束(28)`
- 每卷的**验收句**(卷终话必须当场兑现,不兑现不许发):
  - 卷一:任意一笔订单号,一次检索就能拉出它全程的日志,且不含明文敏感字段。
  - 卷二:值班一夜只响该响的告警,每条告警都能说出"它对应哪个顾客会疼的指标"。
  - 卷三:任意一笔订单,能在一张瀑布图上指出慢在哪一格,并跳到那一格当时的日志。
  - 卷四:一次真事故,从告警响起到给出"已修复"的证据,**三分钟说清**。
- 每话 `projectStage` 一句话 = **这话之后咖啡站多了什么"看得见"的能力**,第 10 步项目检查点必须与之对得上。
- 配置与代码从上一话产物**继续长**,绝不推倒重来;载体是咖啡站的下单/出杯/库存链路,与云原生线、微服务线的世界观连续,但本线自成一仓,不真依赖别线仓库细节。
- 卷终话 `chapterType: "project"`,附两件固定资产:**本卷观测清单**(信号 × 用途 × 保留期)+ **本卷 🔭 夜视仪查询合集**(整页照抄可复现)。
- 发布节奏沿用 CLI 线:蓝图全量 planned;每周翻 1 话——写完当话 md、slug 对齐、当话 status 翻 published,**三件事同一 commit**。

## 7. 写作红线

### 7.1 事实与版本敏感项:发布前必须复核

- **基线**:Java 25 LTS、Spring Boot 4.x、`jakarta.*` 命名空间。凡涉及"哪个版本引入/默认开关/指标名改动/API 形态",发布前逐条联网复核(opencode + DeepSeek 或 context7),**不凭记忆、不信旧攻略**。核实优先于假设。
- 高危清单(触及即必查):Micrometer / Actuator 暴露的**指标名与标签名**(跨版本改过名);OpenTelemetry 各信号的稳定性状态与 Java agent 的启用方式;Collector 处理器(尤其尾部采样)的配置键名;Prometheus 直方图相关函数的语义;各存储组件的默认保留期。
- **不写产品版本号与 UI 路径**:界面与版本会变,写"概念 + 配置片段 + 判读方法";确实要提版本时只写"当前 GA 形态,发布日复核"。
- 数字必须带前提:任何"降了 X%""省了 Y 元""开销 <1%"都要写清**在什么量级、什么采样率、什么硬件**下测的;给不出前提就不写数字。

### 7.2 术语一致性表(全线统一,首现标注英文)

| 统一用词 | 禁用/别名 |
|---|---|
| 三信号(logs / metrics / traces) | 云原生线称"三支柱",引用时注明,不混写 |
| 结构化日志(structured log) | 不写"JSON 打印" |
| 指标(metric)/ 计数器 Counter / 量规 Gauge / 直方图 Histogram | 不写"埋点数据"泛指 |
| 分位数 p50 / p95 / p99 | 不写"99 线""平均延迟"替代 |
| 基数(cardinality) | 首现必标英文 |
| 追踪 trace / 跨度 span | 保留英文 span,不写"节点" |
| TraceID(代码内 `trace_id`) | 不写"链路 ID""请求号"混用 |
| 头部采样 / 尾部采样 | 首现标 head-based / tail-based |
| SLI / SLO / 错误预算 | 首现标中文,后文用缩写;不写 SLA 替代 |
| 告警(alert)与通知(notification) | 两者区分,不互换 |
| 持续剖析(continuous profiling) | 不写"性能监控" |

### 7.3 其他红线

- **每一个结论都要有一条查询能复现**;拿不出查询的判断,让瞭瞭改口反问:"这个问题,数据答得了吗?"
- 日志、查询输出、火焰图一律真实实录或**脱敏后的自造数据**,形态必须真实;**严禁使用任何真实顾客数据**,示例里的手机号/邮箱/地址全部为造例。
- **高基数字段(订单号、用户 ID、TraceID)永远不进指标标签**,只进日志字段与 span 属性——这是技术红线,也是创作红线,凡违反必须在正文中被瞭瞭当场抓住。
- 不把可观测性讲成"装个大屏":任何工具出场都先说清"它替代了哪一次人肉翻日志"。
- 不神化告警数量:**新增一条告警,必须同时说明谁会被吵醒、以及他被吵醒后能做什么**。
- 便利贴语法沿用全站规范(`lib/markdown.ts` STICKY_CLASS):`> [!吐槽]`、`> [!彩蛋]`、`> [!警告]` / `> [!坑]`、`> [!强调]` / `> [!重点]`、`> [!答案]`(折叠 details,放选读硬核推导)、`> [!文字版]`;漫画分格 `> **〔n〕**` 格间空行;固定栏目前缀 `> **🔭 夜视仪 · …**`、`> **❓ 三问自检**`,便于一眼识别。
- 继承 Java 线 §10 全部"必须坚持 / 绝不做";本线追加一条不做:**不堆看板**——每新增一块面板,必须先写下它要回答的那个问题。
