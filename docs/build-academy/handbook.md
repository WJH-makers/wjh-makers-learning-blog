## 0. 一句话定位

豆豆咖啡站要开三家分店了——把"手工冲一杯好咖啡"变成"任何门店、任何时刻都能出品同一杯咖啡"的**中央流水线工程**,正是 Java 构建 / 测试 / 发布 / 供应链的全部秘密。本线的核心冲突只有一句话:**"在我机器上是好的"是工程的头号敌人。**

四条主线沿用 Java 线框架:

| 主线 | 本线内容 | 连贯要求 |
|---|---|---|
| 项目主线 | 中央流水线:口述菜谱 → 图纸化 → 依赖治理 → 提速 → 品控 → 出品 → 防伪 | 检查点版本链 build-v0 → build-v6(§5),构建脚本从上一话的产物继续长,绝不推倒重来 |
| 知识主线 | 构建本质 → 依赖 → 性能 → 测试 → 打包发布 → 供应链安全 | 严格前置依赖,见 §6 铁律与速查 |
| 人物主线 | 阿零从"只会 IDE 绿色三角"到"能给新分店从零搭全套可信流水线" | 每卷至少体现一次能力上涨(§1) |
| 求职主线 | 每话技能 → 招聘瞭望台节点,`jobSkills` 不能空 | Gradle/Maven/CI/测试/供应链安全都是真实 JD 关键词 |

## 1. 角色表

### 阿零 —— 读者代理(延续 Java/CLI 线人设)

已能独立交付系统、玩得转终端(前两线毕业),但对构建的全部认知是"点 IDE 的绿色三角"。本线他第一次为"三家分店三个味"负责。
- 语气不变:好奇、急躁、爱抄近路、"我以为……"然后翻车。翻车对象从代码/终端换成**构建**:漂移的依赖、编不出的缓存、CI 红灯。
- **本线成长弧(每卷一涨,写作时对号)**:
  - B1 末:能看懂一张构建"施工图"(读懂 build.gradle.kts 每一行在干嘛);
  - B2 末:能独立排一次依赖冲突(会看 `dependencies` 树、会精准 exclude);
  - B3 末:能给构建做提速体检(会读 Build Scan,知道慢在哪);
  - B4 末:能设计测试分层策略(什么该天天跑、什么守大门);
  - B5 末:能独立把一个开源库发上 Maven Central;
  - B6 末(毕业):能主导一次供应链安全响应,并给新分店从零搭出全套可信流水线。

### 格叔 —— 本线导师(Gradle 的大象)

大象工头,承包咖啡站中央厨房与分店流水线全部施工。
- **外形**:戴安全帽、挂图纸卷的亚洲象;象鼻能同时抓好几件工具(并行任务);随身一本《施工任务图》,谁依赖谁画得清清楚楚(任务 DAG)。
- **性格**:记性好到可怕——干过的活凭指纹绝不返工(增量构建/缓存哲学);话不多但句句落在图纸上;对"手工作坊式偷懒"零容忍,对新手翻车极有耐心。
- **口头禅**:**「能不干的活,一步都不多干。」**;急眼时:「图纸没锁版本?那是在沙滩上盖楼!」
- **能力边界(硬约束)**:
  - 精通 Gradle 与施工提速;**Maven 细节让位马阿姨**,俩人对照不互相代讲;
  - 不懂咖啡口味与业务需求——那是豆豆的地盘;
  - 终端与服务器操作尊重特米的地盘(「终端的事,问企鹅」);
  - **铁律**:不替阿零改图纸,只圈出错误位置让他自己改;凡讲"快"必先讲"对"(先可复现,再提速)。

### 马阿姨 —— 对照导师(Maven 的信鸽邮差)

老派信鸽邮差,开着一间流程表挂满墙的邮局(validate→compile→test→package…)。
- **外形**:老花镜 + 袖套 + 盖章的手不抖;**性格**:做事按固定流程表一步不差,与格叔斗嘴但互相尊重。
- **口头禅**:「我慢,但我五十年没送错过件。」
- **职责**:🏗️ 双厂对照栏目的 Maven 半边;第 11 话主场;Maven 4 GA 后承接迁移剧情(第 36 话晒新图纸)。
- **术语一致性警告**:Java 线 S3E5 已有角色「Maven 仓库管理员」。本线设定为**两个角色**——马阿姨 = Maven 构建工具本体(邮局与流程表);仓库管理员 = 中央市场(Maven Central)的柜员,是马阿姨的老同事。第 11 话必须用一格漫画交待这层关系,避免读者串戏。

### 客串规则(豆豆 / 特米 / 其他)

- **豆豆**:产品经理 + 质检科长视角,只提需求、验成品、吐槽,**不讲构建知识**(不抢导师戏);卷四(品控)戏份高峰。吐槽走便利贴 `> [!吐槽]`。
- **特米**:只在涉及终端 / CI 脚本时出现(定点第 35 话写 GitHub Actions);保持原线人设——惜字如金、只报命令名不代敲,台词必含「man 一下 gradlew」;出场话交叉链接 `/cli`。
- 每话客串**至多一位**;客串角色语气必须对得上其母线手册;《豆豆咖啡站》线的剧情底牌(MOKA-0 等)**绝不在本线泄露**。
- 技术角色(每个=一种稳定心智模型,逐卷登场):《施工任务图》(任务 DAG,B1E1)、指纹考勤机(up-to-date 检查,第 14 话)、中央成品冷库(build cache,第 15 话)、机器人小 R(Renovate,第 33 话)、扫描员(漏洞门禁,第 32 话)、Bazel 起重机(远景,第 36 话)。

## 2. 每话固定骨架(11 步,继承 Java 线并本线特化)

每话严格遵守;小节用中文数字 `## 一、…` 顺序对齐。字数为量级参考,全话合计见 §7 篇幅约束。

```text
1. 事故或需求(~200 字)   —— 分店/流水线真实事故,一句"承上"接上一话的坑
2. 4~8 格漫画(600–900 字)—— 必含"阿零翻车 + 格叔(或马阿姨)+ ≥1 个技术角色";网页文本分格
3. 本话目标(~100 字)     —— 5 条以内,动词开头
4. 施工图(300–500 字)    —— 原理图:任务 DAG / 仓库解析流程 / 缓存命中判定 / 签名信任链
5. 从上一话继续改图纸(800–1200 字)—— 明确"在上一话哪个文件哪段之上加了什么";Kotlin DSL 为主线基准
6. 故意制造一次构建翻车(200–400 字)—— 版本冲突 / 缓存不命中 / 锁文件漂移 / 签名对不上……选本话最典型的坑
7. 观察真实构建输出(~300 字)—— BUILD FAILED 原文 / 依赖树 / scan 摘录,必须"真跑得出来",不能编
8. 修复并验证(400–600 字)—— 见下方"验证放宽规则"
9. 流水线检查点(~150 字) —— 流水线长成什么样(已具备 / 还没有),对齐 projectStage(§5)
10. 对应招聘技能(~80 字)
11. 下一话悬念(~80 字)   —— 一句"启下",与下一话第 1 步能对上
```

**本线特化**:

- 第 6 步的"Bug"优先选**构建翻车**而非代码 Bug——本线的敌人是不可复现,不是 NPE。
- 第 8 步验证放宽规则(对应 Java 线"至少一个 JUnit"):**卷四起必须真 JUnit**;卷一~卷三可放宽为"构建验证三连"——重跑看 `UP-TO-DATE`/`FROM-CACHE` 标记、`gradlew dependencies` 复查依赖树、对产物 diff 哈希。凡能上测试的仍然上测试。
- **🏗️ 双厂对照是固定段**(每话尽量有,放第 8 步之后、第 9 步之前),不占深度栏目配额;其余深度栏目(§3)按需插入,一话最多 2 个。

## 3. 深度栏目

### 🏗️ 双厂对照(本线专属,对标 CLI 线的 🪟 双系统对照)

同一件事的两种施工法并排:左栏 Gradle(Kotlin DSL)、右栏 Maven(POM),**必须标注语义差异**,不是简单的语法翻译——世界上一半 Java 项目还是 Maven,能读会改是硬技能;Maven 4 GA 后此栏目天然承接迁移内容。

格式模板与示例(取自第 07 话):

```text
> **🏗️ 双厂对照 · 版本冲突,两家怎么收货**
>
> | | 格叔(Gradle · Kotlin DSL) | 马阿姨(Maven · POM) |
> |---|---|---|
> | 声明 | `implementation("com.sugar:syrup:2.0")` | `<dependency>…<version>2.0</version>` |
> | 冲突策略 | 默认**最高版本胜出** | **最近路径优先**(nearest wins) |
> | 查看工具 | `gradlew dependencies` | `mvn dependency:tree` |
> | 坑 | 传递依赖悄悄抬升版本 | 声明顺序都能影响结果 |
>
> 格叔锐评:同一张进货单,两家能收到不同的货——诡异的 NoSuchMethodError,九成从这来。
```

约束:表格化,4–6 行封顶;结尾一句"格叔锐评"或"马阿姨补刀"点破两家哲学差异;严禁展开成散文。

### 沿用栏目(格式规范见 Java 手册 §5,原样继承)

- **🔀 多解台**:确有代表性多解时(如:锁版本的三种姿势 ext 变量 / catalogs / platform;fat jar 的 shadow / bootJar / 分层镜像)。必须给"默认推荐 + 理由"。
- **⏳ 版本时光机**:本线的"版本轴"是**构建工具**而非 JDK(Gradle 4→9→10 / Maven 3→4 / OSSRH→Central Portal / PGP→Sigstore / buildSrc→build-logic)。主线以 Gradle 9 + Kotlin DSL 写法为准,时光机只做知其所以然。
- **🎯 面试直击**:implementation vs api、Gradle 与 Maven 冲突策略差异、增量构建原理、fat jar 的 service 文件合并坑……只放真高频。

固定短栏目前缀(对齐 Java 线 §6):`> **格叔旁白**:…`(捷径/补充)、`> **格叔锐评**:…`(点破本质)、`> **📋 施工罚单**` + 真实 BUILD FAILED 代码块(对应 Java 线"编译官罚单")。

## 5. 检查点版本链与项目主线推进(projectStage 规则)

- 版本链 **build-v0 → build-v6**,与 Java 线 v0→v7 平行编号(首页"工程报纸"可做双时间轴版面):
  - **build-v0**(开场前状态):Java 线 v7 完结时的咖啡站代码——能跑,但构建全靠"口述菜谱"+IDE 绿色三角;
  - **build-v1**(第 06 话):有图纸——Wrapper 锁版本、Kotlin DSL、依赖有坐标有作用域;
  - **build-v2**(第 13 话):三店同款——多模块 + BOM + catalogs + 锁文件,依赖树可复现;
  - **build-v3**(第 20 话):大象从不返工——增量 + 双缓存 + toolchains + convention plugin,且逐字节可复现;
  - **build-v4**(第 26 话):品控上线——JUnit 6 + Testcontainers + 测试分层 + 覆盖率门禁;
  - **build-v5**(第 30 话):三种出品——jar/镜像/native 全打通,拉花算法库上架 Central;
  - **build-v6**(第 36 话):全链路可信——SBOM + 校验 + 自动升级 + 溯源 + 私服海关,完结。
- **规则**:
  1. 每话 `projectStage` 必填,一句话描述"流水线长成什么样"(对齐骨架第 9 步);卷内单调推进,不许回退或原地踏步;
  2. 卷终话(06 / 13 / 20 / 26 / 30 / 36)的 projectStage 必含 `build-vN` 字样,并在正文立"检查点牌"(示例仓库同步打 tag `build-vN`);
  3. 每话构建脚本**从上一话产物继续长**;若某话不推进项目主线(纯知识话),projectStage 也要写出"流水线本话新看清了什么"。

3. **术语一致性**:比喻-术语对照表(§4)是唯一命名源;马阿姨 vs Maven 仓库管理员的角色区分(§1)不许含混。

5. 不做清单(继承 Java 手册 §10 全部,另加):不写"银弹式工具安利"(每个工具必须先展示它解决的事故);不让格叔贬低 Maven(两家哲学对照,不是拉踩);不在卷一~卷三塞 CI(CI 在第 35 话,前面只埋钩子)。
