## 0. 一句话定位

咖啡站要开连锁了——阿零把 Java 线攒出来的单体 v7 拆成一张会呼吸的服务网。**每一话都是一次"拆店手术"+ 一场真实风格的生产事故:这条线教的是"别人流过的血"。**

全线 **6 卷 30 话**(卷码 M1–M6,话号全线连续 01–30):
M1 升级季(Boot 4/Framework 7 迁移,01–05)→ M2 拆店季(拆分与网关,06–11)→ M3 账本季(ORM 与数据,12–16)→ M4 传菜季(消息系统,17–22)→ M5 快取季(缓存与限流,23–27)→ M6 观星季(稳态运营与前沿,28–30)。

## 1. 衔接与世界观

- **时间点**:接 Java 线 56 话完结之后。单体咖啡站 v7 又稳又香,但生意火了:三家分店 + 外卖平台 + 会员体系,一套单体扛不住"三家店同时点单 + 外卖洪峰"。**开连锁 = 拆微服务**。
- **统一比喻体系**:单体咖啡站 → 中央厨房(领域服务)+ 门店(实例)+ 传菜系统(消息)+ 总店大门(网关)。
- **技术基线**(写正文一律以此为准,版本敏感事实的复核规则见 §7):Java 25 LTS · Spring Boot 4.x · Spring Framework 7 · Spring Cloud 2025.1 (Oakwood) · Hibernate ORM 7 (JPA 3.2) · Kafka 4.x(KRaft-only)。
- 主线代码 = Java 线大结局的咖啡站单体仓库,本线第 1 话原样接管为检查点 v8.0,之后**每话从上一话产物继续长,绝不推倒重来**(继承 Java 线项目主线铁律)。

## 2. 角色表(语气表是硬约束,每话对白都要对得上)

### 奥朵(Octo)—— 本线导师 · 章鱼架构师
- **外形**:戴圆框眼镜的章鱼,八条腕足各戴一块不同颜色袖章;曾任"深海连锁餐饮集团"首席架构师,退休后被豆豆的咖啡香引来。
- **活体教科书设定**:她反复强调——章鱼三分之二的神经元长在腕足上,**腕足能自治,大脑只管协调**。这正是微服务本体(服务自治 + 轻量协调),全线比喻的总纲。
- **性格**:与特米的"暴躁 man 一下"相反——慢条斯理,**先问三个"为什么"才肯动手**;最烦"为了拆而拆"的架构表演。
- **口头禅**:**"能不拆就不拆,要拆就拆干净。"** 次口头禅(每次事故复盘时说):**"腕足可以断,大脑不能懵。"**

### 阿零 —— 读者代理(本线成长弧)

## 3. 每话固定骨架 = 12 步(在 Java 线 11 步上特化)

与 Java 线的两点差异:第 4 步"技术原理图"升级为**架构决策图**(拆前/拆后对照);第 11 步固定为本线专属栏目 **🚨 事故复盘室**(Java 线此位是"下一话悬念",本线顺延为第 12 步)。

```text
1.  事故或需求        —— 连锁经营的真实痛点;开头一句"承上"接上一话的坑。150–250 字。
2.  4~8 格漫画        —— 网页文本分格;必含"阿零翻车(架构级)+ 奥朵按手/三问 + ≥1 个技术意象"。每格 40–80 字。
3.  本话目标          —— ≤5 条,动词开头。
4.  架构决策图        —— 拆前 → 拆后两张对照图(文本图),旁附奥朵的三个"为什么"及答案。300–500 字。
5.  从上一话继续改代码 —— 明确"基于检查点 v8.x 的哪段加了什么";主代码块 30–80 行,配置片段单列。
6.  故意制造一个事故   —— 优先选"分布式味道"的坑:超时、双写不一致、重复消费、缓存失效、锁过期。
7.  观察真实报错/日志  —— 报错与日志必须真跑得出来,不能编;含关键配置现场。6–8 三步合计 600–1000 字。
8.  修复并用测试证明   —— 至少一个 JUnit;M3 第 16 话引入 Testcontainers 后,涉及库/消息/缓存的话优先用真容器测。
9.  项目检查点        —— 连锁网长成什么样(已具备 / 还没有);标注当前版本链位置(v8.x,见 §5)。~150 字。
10. 对应招聘技能      —— 3–6 条,不能空(继承求职主线)。
11. 🚨 事故复盘室      —— 本线固定末栏(格式见 §4),300–500 字,表格化。
12. 下一话悬念        —— 一句"启下",与下一话第 1 步的"承上"必须能对上。1–2 句。
```

- 深度栏目沿用 Java 线三件套:**🔀 豆豆的多解台 / ⏳ 版本时光机 / 🎯 面试直击**,按需触发,一话最多 2 个(🚨 事故复盘室是固定栏目,不计入)。本线 ⏳ 时光机的典型题材:Boot 2→3→4、`RestTemplate`→`RestClient`→HTTP Interface、ZooKeeper→KRaft、`@MockBean`→`@MockitoBean`。
- 篇幅硬约束(防臃肿,继承 v2):普通话 **4.2k–5.8k 字符**;卷终话(05/11/16/22/27)5.5k–6.5k;完结话(30)可到 7k。加深度靠密度不靠长度,深度内容一律表格化。
- 小节仍用中文数字 `## 一、…`,标题 `《从零开始拆微服务》0x · 本话名`,H1 唯一;结尾署名行:`*本话属于连载《从零开始拆微服务》。世界观见 handbook.md;卷次地图见系列首页。*`

## 4. 本线专属深度栏目:🚨 事故复盘室(每话固定)

**定位差异**:Java 线有 🎯 面试直击、CLI 线有 🪟 双系统对照,本线的差异点是**用别人流过的血教书**——以"深夜告警群聊天记录"的排版复现一个与本话知识点对应的生产事故,再按 Postmortem 格式收口。

格式模板(两段式:群聊 + 复盘表,群聊 3–6 条,时间戳递进):

```text
> **🚨 事故复盘室 · <事故代号>**
>
> 【23:47】告警机器人:P1|orders-service 5xx 比例 32%,持续 5 分钟
> 【23:49】阿零:我看看……库没挂啊,连接池怎么满了???
> 【23:55】奥朵:先止血,再破案。把 <某开关> 拉下来。

| 阶段 | 记录 |
|---|---|
| 现象 | 用户/监控视角看到了什么 |
| 根因 | 一句话点破(可附一行关键代码/配置) |
| 止血 | 当晚 5 分钟内做的事(可回滚、可降级) |
| 长期修复 | 本话代码里真正落地的那个改动 |

血泪教训:<一句话,点睛台词风格>。
```

约束:
1. 事故原型必须来自**业界真实事故模式**,严禁虚构具体公司名/日期冒充真事;群聊人名只用本宇宙角色。
2. "止血"与"长期修复"必须区分——止血是当晚能做的,长期修复必须就是本话第 8 步落地的代码。
3. 群聊里出现的命令行排障步骤,脚注直链 CLI 线对应话(见 §8 栏目互认)。
4. 表格化,禁止写成大段散文;整栏 300–500 字。

- 固定短栏目前缀沿用:`> **豆豆锐评**:…`(豆豆客串时);本线新增 `> **奥朵三问**:…`(架构决策图旁,列三个为什么及答案)。
