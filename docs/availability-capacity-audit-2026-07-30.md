# 博客容量与可访问性审计（2026-07-30）

本报告结合仓库配置、生产服务器只读指标、外部浏览器审计和 Uptime Kuma 官方发布信息。未修改 DNS、Cloudflare、生产容器、数据库或监控配置。

## 结论

- 当前访问量下，性能余量足够：博客约 200MiB，Uptime Kuma 约 89MiB；主机 3.6GiB 内存中约 2.0GiB 可用。页面布局审计覆盖 21 个路由、63 个视口状态和 547 个站内链接，未发现失败或横向溢出。
- 当前最大风险不是算力，而是单点：博客、Uptime Kuma、反向代理和部署任务位于同一台服务器。同机 Kuma 无法在主机、机房或运营商链路整体故障时发出可靠告警。
- Uptime Kuma 适合作为当前内部监控面板，没必要因性能替换；但线上为 1.23.17，官方稳定版已到 2.4.0。v1 到 v2 是破坏性大版本迁移，必须先备份数据卷并演练恢复。
- 生产发布在 GitHub SSH fetch 阶段出现超过 8 分钟的停顿，旧脚本没有超时，长期占住 systemd 部署锁。本仓库已改为有界 HTTPS fetch 与重试。
- 真正提高可访问性需要“外部探针 + 第二故障域”，而不是在同一台主机多开一个容器。

## 当前容量证据

| 项目 | 实测 | 判断 |
| --- | --- | --- |
| 主机内存 | 3.6GiB，总可用约 2.0GiB | 日常负载充足 |
| 主机磁盘 | 59GB，使用 69%，剩余约 19GB | 构建缓存必须持续限额 |
| 博客容器 | 约 200MiB，低 CPU | 512MiB 上限可用，但发布后需观察峰值 |
| Uptime Kuma | 约 89MiB / 256MiB，CPU 约 0.25%，8 天零重启 | 当前监控规模性能充足 |
| Kuma 数据 | SQLite 主库约 228KiB；`error.log` 约 50MiB | 数据量很小；日志需轮转/归档 |
| Docker | 镜像约 10.6GB；BuildKit 缓存约 23GB | 主要磁盘增长源 |
| 页面构建 | 559/559 静态页 | 内容规模尚未触及构建瓶颈 |

这些数值是一次只读快照，不等于容量上限。扩容前应记录 7–30 天的 CPU、RSS、磁盘增长、源站请求率、Cloudflare 缓存命中率、P95/P99 延迟和错误率。

## Uptime Kuma 评估

保留 Kuma，原因是它已覆盖 HTTP/TCP/DNS/证书/状态页与通知，官方支持最低 20 秒检查间隔；当前资源占用证明它足以承担个人博客和少量配套服务。不要把它横向扩成多个同时写同一数据卷的副本：官方明确要求本地文件系统且不支持 NFS，当前 SQLite/本地卷形态更适合单写实例。

需要补齐：

1. 在异地服务配置一个外部 HTTPS 探针，监控首页与 `/api/version`，告警通道不能只依赖本机。
2. 每日备份 Kuma 数据卷，备份前使用应用导出或 SQLite 一致性快照；每季度在隔离目录恢复一次。
3. 先在副本数据卷上完成 1.23.17 → 2.x 迁移演练，再固定到明确镜像版本，禁止长期跟随浮动 `latest`。
4. 调查并轮转 50MiB `error.log`；保留最近错误和归档，不让监控日志反过来挤满系统盘。
5. 对关键用户路径设置分层探针：首页、首篇 Java 课程、`/api/version`、评论写入依赖、证书到期；低价值页面不必全部用 20 秒频率。

## 可访问性分层方案

### 第一阶段：单机强化

- Cloudflare 继续承担 TLS、静态资源和可缓存公开页面；源站只绑定回环地址。
- 发布采用经过 CI 验证的 commit、容器健康检查和 SHA 对比；网络 fetch 必须有超时。
- 为博客、Kuma、数据库配置独立告警；外部探针与 Kuma 互相监督。
- 建立恢复目标：Git 内容 RPO 为 0；Mongo 写作数据按 Atlas 能力设置备份；Kuma RPO 24 小时以内；单机故障 RTO 以当前手工重建能力为准并实测。

### 第二阶段：双故障域

- 在不同地域或不同云厂商准备第二源站，运行同一不可变镜像；不要把两个副本放在同一宿主机假装高可用。
- 通过 Cloudflare Load Balancing 或等价健康路由在两个源站间故障转移。
- Markdown/静态资源随镜像发布；MongoDB 继续外置。写作台只允许主站或通过统一鉴权入口，避免双主写入。
- 发布改为先部署备用源站、验证 SHA 与核心路径，再切流并更新另一台，实现蓝绿发布。

### 第三阶段：容量扩展

- 公共读取优先提高 CDN 命中率；这比在源站堆 Node 副本更有效。
- 数据库列表查询保持轻量索引和 5 分钟共享缓存；文章正文按 slug 获取。增加实例前核算 Mongo 连接池总预算。
- 当静态生成时间、镜像大小或内存达到门槛时，拆分内容构建和运行镜像，并以压测数据决定副本数。
- 建议目标：公网月可用性 99.9%，P95 HTML 响应低于 500ms，5xx 低于 0.1%，故障检测低于 60 秒；达到第二源站后再收紧 RTO。

## 不建议

- 不建议让同机 Kuma 作为唯一可用性证明。
- 不建议多个 Kuma 副本共享 SQLite/NFS 数据卷。
- 不建议当前直接引入 Kubernetes；单机资源、流量和团队规模下，复杂度会先降低可靠性。
- 不建议只增加博客容器副本而不处理主机、网络、磁盘和反向代理单点。
