# 博客容量与可访问性审计（2026-07-30）

本报告结合仓库配置、生产服务器指标、外部浏览器审计、一次完整生产恢复和 Uptime Kuma 官方发布信息。恢复期间已将博客部署到 `62cc5ae`、清理 Cloudflare 缓存并配置 Java 17 公共 Judge0 后端；未修改 DNS、数据库或防火墙。

## 结论

- 当前访问量下，运行容量足够：博客约 180–200MiB，Uptime Kuma 约 82–89MiB；主机 3.6GiB 内存中约 2.0GiB 可用。页面布局审计覆盖 21 个路由、63 个视口状态和 547 个站内链接，未发现失败或横向溢出。
- 当前最大风险不是算力，而是单点：博客、Uptime Kuma、反向代理和部署任务位于同一台服务器。同机 Kuma 无法在主机、机房或运营商链路整体故障时发出可靠告警。
- Uptime Kuma 性能足够，但当前数据库中 `monitors=0`、`heartbeats=0`、`notifications=0`、`status_pages=0`，因此现状没有监控价值。线上为 1.23.17，官方稳定版已到 2.4.0；v1 到 v2 必须先备份数据卷并演练恢复。
- 生产恢复证明 GitHub SSH 与 HTTPS fetch 都会长时间停顿；HTTPS 连接建立后仍可能 2 分钟没有 pack 数据。首次新镜像构建耗时约 11.5 分钟，其中 `npm ci` 为 493 秒。超时只能防止永久卡死，不能解决出站依赖与构建位置问题。
- 真正提高可访问性需要“外部探针 + 第二故障域”，而不是在同一台主机多开一个容器。

## Uptime Kuma 评估

保留 Kuma，原因是它已覆盖 HTTP/TCP/DNS/证书/状态页与通知，官方支持最低 20 秒检查间隔；当前资源占用证明它足以承担个人博客和少量配套服务。不要把它横向扩成多个同时写同一数据卷的副本：官方明确要求本地文件系统且不支持 NFS，当前 SQLite/本地卷形态更适合单写实例。

当前必须补齐：

1. 在异地服务配置一个外部 HTTPS 探针，监控首页与 `/api/version`，告警通道不能只依赖本机。
2. 每日备份 Kuma 数据卷，备份前使用应用导出或 SQLite 一致性快照；每季度在隔离目录恢复一次。
3. 先在副本数据卷上完成 1.23.17 → 2.x 迁移演练，再固定到明确镜像版本，禁止长期跟随浮动 `latest`。
4. 调查并轮转 50MiB `error.log`；保留最近错误和归档，不让监控日志反过来挤满系统盘。
5. 对关键用户路径设置分层探针：首页、首篇 Java 课程、`/api/version`、评论写入依赖、证书到期；低价值页面不必全部用 20 秒频率。

建议探针矩阵：

| 探针 | 位置 | 周期 | 成功条件 | 告警 |
| --- | --- | --- | --- | --- |
| 首页 HTTPS | 异地外部 | 60 秒 | 200、TLS 有效、正文标记存在 | 连续 3 次失败 |
| 版本证明 | 异地外部 + Kuma | 60 秒 | 200、JSON `healthy=true` | 连续 2 次失败 |
| Java 课程页 | 异地外部 | 5 分钟 | 200、实验区可见 | 连续 2 次失败 |
| Java 沙箱 | 外部合成任务 | 10 分钟 | 编译并输出固定 nonce | 连续 2 次失败；注意配额 |
| 源站回环 | 同机 Kuma | 30 秒 | `127.0.0.1:3001` 200 | 立即告警 |
| TLS 到期 | 异地外部 | 12 小时 | 剩余天数大于 21 天 | 21/14/7 天分级 |

同机 Kuma 只负责“进程/源站是否活着”；主机断电、Cloudflare 路由异常和机房网络故障必须由异地探针发现。至少配置一个不依赖本机的通知渠道，并做一次真实测试告警。

## 可访问性分层方案

### 第一阶段：单机强化

- Cloudflare 继续承担 TLS、静态资源和可缓存公开页面；源站只绑定回环地址。
- 发布采用经过 CI 验证的 commit、容器健康检查和 SHA 对比；网络 fetch 必须有超时。
- 为博客、Kuma、数据库配置独立告警；外部探针与 Kuma 互相监督。
- 建立恢复目标：Git 内容 RPO 为 0；Mongo 写作数据按 Atlas 能力设置备份；Kuma RPO 24 小时以内；单机故障 RTO 以当前手工重建能力为准并实测。
- 发布失败时自动恢复上一个已验证镜像。当前脚本在新容器 unhealthy 时只退出，旧容器已被替换，不能算自动回滚。
- 将镜像构建迁到 CI，并推送按 commit SHA 标记的不可变镜像；服务器只拉取和切换镜像。这样可移除服务器上的 `npm ci`、大部分 BuildKit 缓存及 GitHub pack 下载风险。
- 服务器保留最近两个健康镜像；切换前先启动候选容器，通过 `/api/version` 和核心路径后再改流量，失败则停止候选容器。

### 第二阶段：双故障域

- 在不同地域或不同云厂商准备第二源站，运行同一不可变镜像；不要把两个副本放在同一宿主机假装高可用。
- 通过 Cloudflare Load Balancing 或等价健康路由在两个源站间故障转移。
- Markdown/静态资源随镜像发布；MongoDB 继续外置。写作台只允许主站或通过统一鉴权入口，避免双主写入。
- 发布改为先部署备用源站、验证 SHA 与核心路径，再切流并更新另一台，实现蓝绿发布。

### 第三阶段：容量扩展

- 公共读取优先提高 CDN 命中率；这比在源站堆 Node 副本更有效。
- 数据库列表查询保持轻量索引和 5 分钟共享缓存；文章正文按 slug 获取。增加实例前核算 Mongo 连接池总预算。
- 当前 `getDatabasePosts()` / `getDatabasePostIndex()` 会全量 `toArray()`，公开文章列表还会合并 Markdown 全量扫描。文章达到约 1,000 篇前，应改为投影后的分页索引与按 slug 单查正文，并让共享缓存脱离单进程内存。
- 当静态生成时间、镜像大小或内存达到门槛时，拆分内容构建和运行镜像，并以压测数据决定副本数。
- 建议目标：公网月可用性 99.9%，P95 HTML 响应低于 500ms，5xx 低于 0.1%，故障检测低于 60 秒；达到第二源站后再收紧 RTO。

## Java 编译器可用性边界

当前编译器通过 `ce.judge0.com` 的 JDK 17 执行，生产实测可返回正确输出；应用侧限制源码 20,000 字符、编译 4 秒、运行 2 秒、内存约 128MiB、输出 4,000 字符，并禁用执行网络。它解决了“功能不可用”，但不是高可用终态：

- 公共 Judge0 是站外单点，配额、版本、隐私策略和可用性不受本站控制；UI 应明确代码会提交到隔离的第三方执行服务。
- 至少准备第二个兼容后端，增加健康检查、熔断、短期退避与明确降级文案；不能在故障时无限重试放大流量。
- 长期方案是在独立故障域自建 Judge0 或同级沙箱。编译执行节点不能与博客容器共享权限、Docker socket、文件系统或数据库凭据。
- 沙箱只能接受单文件 Java 17 实验；JUnit、Maven、多文件项目和任意依赖下载应走独立课程环境，不能放宽现有单文件边界。

## 扩容触发阈值

| 信号 | 预警 | 扩容/整改触发 |
| --- | --- | --- |
| 系统盘 | 75% | 85% 或预计 7 天内耗尽 |
| 博客 RSS | 容器上限 70% 持续 15 分钟 | 80% 或出现 OOM/restart |
| 源站延迟 | P95 > 500ms 持续 15 分钟 | P95 > 1s 或 5xx > 0.1% |
| CDN 命中率 | 可缓存流量 < 85% | < 75% 且源站 CPU/带宽受压 |
| 生产发布 | > 10 分钟 | 连续两次 > 15 分钟或一次回滚失败 |
| 静态构建 | > 12 分钟 | > 20 分钟或峰值内存接近构建机上限 |
| Mongo 连接 | 预算使用 > 70% | > 85% 或出现连接等待/拒绝 |

## 推荐执行顺序

1. 立即配置外部探针和通知，填补当前 Kuma 零监控状态。
2. 给部署增加上一镜像自动回滚，并完成一次错误镜像演练。
3. 备份 Kuma 数据卷与 Mongo 数据，记录恢复命令并在隔离环境验证。
4. 把构建迁到 CI/镜像仓库，服务器改为拉取不可变镜像。
5. 部署第二地域源站，再配置 Cloudflare 健康路由；此时才具备主机级高可用。
6. 内容接近 1,000 篇或数据库/构建指标触发阈值后，再做索引分页、共享缓存和应用多副本。

## 不建议

- 不建议让同机 Kuma 作为唯一可用性证明。
- 不建议多个 Kuma 副本共享 SQLite/NFS 数据卷。
- 不建议当前直接引入 Kubernetes；单机资源、流量和团队规模下，复杂度会先降低可靠性。
- 不建议只增加博客容器副本而不处理主机、网络、磁盘和反向代理单点。
