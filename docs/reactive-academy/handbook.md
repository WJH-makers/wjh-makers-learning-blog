## 0. 一句话定位

命令式教你一步步"取了再等",这一部带阿零钻进**数据流**——用 Project Reactor / Spring WebFlux 把咖啡站高并发下单链路改成全异步非阻塞。

本线读者是**读完 Java 线、并跟过 JVM 线并发卷的进阶者**。差异化立场只有一句:**不吹不黑**——讲清响应式到底解决什么(高并发下省线程、削峰、组合异步),更要讲清**什么时候坚决别用它**(简单 CRUD、团队不熟、强事务、虚拟线程已够用)。凡结论,能画成弹珠图、能给出 request(n) 观测就落地,不玩玄学。

## 1. 衔接与世界观

- 时间线:JVM 线大结局(后厨升级 Java 25、扛过百万并发午高峰)**之后**。下单链路虽换了虚拟线程,但仍是一层层"取了再等"的阻塞调用,组合多个外部依赖时回调缠成一团。阿零决定把整条高并发下单链路改造成全异步非阻塞。
- 舞台:豆豆咖啡站**中庭的循环水景池**。池水永不静止,每一次投币的涟漪都会传遍整池——这正是"事件传播"的具象化;池底管路盘成数据流网。
- 四卷主线:卷一 为什么要响应式(01–07)→ 卷二 操作符与组合(08–15)→ 卷三 背压与真相(16–22)→ 卷四 响应式的边界(23–30)。
- 基线:Project Reactor / Spring WebFlux / R2DBC,并全程与 **Java 25 虚拟线程**对照——本线不假装虚拟线程不存在,卷四正面回答"响应式还值不值"。

## 2. 角色表(硬约束,防人设漂移)

### 漾漾(Yang)—— 本线导师,水景池水母

- **外形**:栖息在循环水景池里的水母,通体半透明。**身体随水流的每一次扰动而波动**——一个事件的涟漪能瞬间传遍全身(事件传播 / 信号的具象化);**触手是一条条数据流**,能把下游的 `request(n)` 暗号沿触手逆流传回源头(背压的具象化)。
- **性格**:慢条斯理,从不主动伸手去够食物——她等食物随水流漂来。厌恶一切"忙等、空转、死等"的浪费;但对"耐心等待"极其宽容。
- **口头禅**:"**别去取,等它来。**"(声明式 / 订阅驱动 / 背压三关一语)
- **副口头禅**:"阻塞是一种浪费,等待不是。"(区分 blocking 与 waiting,响应式的第一性原理)
- **能力边界(铁律)**:
  1. 只讲响应式的事实与**可观测的行为**(弹珠图、request(n)、日志),不替阿零写业务代码;给方向、给观测,让阿零自己跑。
  2. 不下没有证据的性能断言——高并发优势必须附压测数据,否则只说"去压一遍再谈"。
  3. **不当鼓吹者**:每逢"要不要上响应式",必须同时给出反面场景;卷四她会亲口劝退。
  4. 沿用豆豆五步排障法(观察→收集→假设→改一个变量→重跑),漾漾版第一步永远是"**先画出这条流的弹珠图**"。

### 阿零 —— 本线成长弧:从"会异步"进化到"会判断该不该异步"

延续前作人设:能交付系统、扛得住并发,但一碰响应式就想"这不就是花式回调吗"。**每卷一次可见的能力上涨**:

| 卷 | 卷终时阿零能做到 |
|---|---|
| 卷一 | 说得清响应式解决什么、能亲手点亮一条 Mono/Flux 管道并解释"装配 vs 执行" |
| 卷二 | 用操作符把整条下单链路串成不阻塞的流,并用 StepVerifier 验证 |
| 卷三 | 自己复现背压、看懂 request(n)、把午高峰洪流削成下游扛得住的细水 |
| 卷四 | **能拿着压测数据和心智成本账,诚实地判断该不该上响应式**——不跟风、不迷信 |

### 客串规则(豆豆 / 特米 / 焰焰)

- **豆豆**:午高峰流量发生器——**只在背压/压测话出现**(制造十万订单洪流),保持毒舌但**不当导师**(本线导师是漾漾)。

## 4. 本线专属深度栏目

### 🌊 数据流台(每话必有,恰好 1 个)

- **定位**:对标 JVM 线的 🔬 炉底显微镜;差异化 = **把当话操作符画成弹珠图(marble diagram)**——时间轴从左到右,每颗弹珠 `─①──②──③─▶` 是一个 `onNext`,`|` 是 `onComplete`,`X` 是 `onError`。
- **规则**:
  1. 至少画"输入流 → 操作符 → 输出流"三行;组合类(zip/merge)画多条输入。
  2. 弹珠图下配 2–4 条逐行解读,每条一句话;能配 `log()` 真实信号日志的,附 ≤10 行实录佐证。
  3. 口号:"**别去取,等它来——你只需描述流,信号自己会走。**"
- **格式模板**(以 flatMap 为例):

  ```text
  > **🌊 数据流台 · flatMap 为什么会打乱顺序?**
  >
  > ```text
  > 源:   ─A────B────C──────────▶
  > flatMap(慢→快):
  >   A→ ────────a| (慢)
  >   B→ ──b|        (快)
  >   C→ ────c|
  > 出:   ───b───c──────a───────▶   ← 顺序被打乱
  > ```
  > 逐行解读:① 每个元素被展开成一条子流并**并发**订阅;② 子流谁先完成谁先并入下游;③ 要保序请换 concatMap(串行订阅子流)。
  > 漾漾结语:并发换来吞吐,顺序是代价——想要哪个,先画一张弹珠图问自己。
  ```

### ⚡ 背压演练(按需触发,卷三每话必有)

- **定位**:专治"生产快、消费慢会怎样"。**必须给可复现的 request(n) 观测**:用 `Flux.range(...).log()` 或自定义 `BaseSubscriber` 手动 `request`,把"下游要多少、上游推多少"打印出来。
- **规则**:改前/改后各一次观测对比;缓冲/丢弃策略必须给出"丢了什么、留了什么"的实录;禁止无证据地说"会 OOM",要么给堆增长曲线,要么老老实实说"取决于速率差"。

## 7. 写作红线

### 7.1 版本敏感事实:发布前必须联网复核

- **铁律**:凡涉及 Project Reactor / Spring WebFlux / R2DBC 的 API 形态、默认行为,以及"虚拟线程在 JDK 25 的状态",发布前逐条用 opencode+DeepSeek 或 context7(`/websites/projectreactor_io`、Spring 官方文档等)联网复核,**不凭记忆、不信旧博客**。核实优先于假设。
- 基线锚点(**发布日仍须复查**):Project Reactor 3.x / Spring Boot 4.x(WebFlux) / R2DBC;Java 25 虚拟线程已转正、结构化并发在 25 仍为预览(与 JVM 线口径一致)。
- 每话触及即必查:所有操作符的确切签名与语义(`flatMap` 并发度默认值、`onBackpressure*` 行为、`publishOn/subscribeOn` 影响范围);一切"默认开启/关闭/并发"断言;WebFlux 默认服务器(Netty)与线程模型;R2DBC 驱动能力边界。

### 7.2 术语一致性表(全线统一,首现标注英文)

| 统一用词 | 禁用/别名 |
|---|---|
| 背压(backpressure) | 首现必标英文;不写"反压"以外别名混用,统一"背压" |
| 弹珠图(marble diagram) | 首现标英文 |
| 冷流 / 热流(cold / hot) | 不写"冷发布者/热发布者" |
| 装配阶段 / 执行阶段(assembly / subscription time) | 不含糊说"定义时/运行时" |

| 非阻塞(non-blocking)/ 阻塞(blocking) | 与"等待(waiting)"严格区分 |

### 7.3 其他红线

- **性能断言必附观测证据**(⚡ 演练输出、压测数据或弹珠图);没证据的性能话一律让漾漾说"别去取——去压一遍再来"。
- 报错、命令输出、`log()` 信号序列一律真实实录,不许编造;编不出来就换真跑得出的例子。
- **绝不把响应式讲成银弹**:每逢"要不要上",必须同时给适用与不适用;卷四是全线的"诚实兑现"。
- 便利贴语法沿用全站规范:`> [!吐槽]`、`> [!彩蛋]`、`> [!警告]` / `> [!坑]`、`> [!强调]` / `> [!重点]`、`> [!答案]`(折叠 details)、`> [!文字版]`;漫画分格 `> **〔n〕**` 格间空行;固定栏目前缀 `> **🌊 数据流台 · …**`、`> **⚡ 背压演练 · …**`、`> **📋 编译官罚单**`,便于一眼识别。
- 追加一条不做:**不把 `block()` 藏进链路当便利**——每次 block() 出场都必须显式标注"这里为什么允许阻塞"(仅测试、`main`、迁移边界三种合法场景)。
