## 一、事故:服务器卡成了幻灯片

上一卷末尾,咖啡站的代码风风光光进了 GitHub。可今天阿零 `ssh` 上服务器,敲个 `ls` 都要等一秒——整台机器像在泥里跑步。

「代码在 Git 里睡得好好的,」豆豆客串飘过,「**是这台机器上正在跑的某个东西疯了**。问题是:你知道这台机器上都跑着什么吗?」

阿零环顾终端:黑屏,光标。什么都看不见。

## 二、漫画 · 看不见的房客

> **〔1〕** 阿零把耳朵贴在屏幕上,像在听墙。
> 阿零:「机器这么卡,总有个东西在疯狂干活吧?可我连它长什么样都看不到!」

> **〔2〕** 特米从光标里探出头,肚皮 `>_` 一闪。
> 特米:「每个正在跑的程序叫**进程**。这台服务器是栋公寓,进程是房客——你是房东,却从没查过房。`ps aux`。」

> **〔3〕** 阿零敲下,屏幕哗啦刷出一整面名单:USER、PID、%CPU……
> 阿零:「这么多?!我只部署了一个咖啡站啊!」特米:「系统本身就是几十个房客。看 **PID**——每个房客唯一的门牌号。」

> **〔4〕** 特米按下 `top`,屏幕变成一块实时跳动的记分牌,最顶上一行红得发烫:`order-watcher.sh  99.7%CPU`。
> 特米:「记分牌按 CPU 排序。**吃得最多的,坐第一排。**」

> **〔5〕** 阿零凑近一看,倒吸一口冷气——那是他上卷写的下单监控脚本,`while true` 里忘了写 sleep,空转了十二天。
> 阿零:「……凶手是我自己。」

> **〔6〕** 特米递给他一把小巧的门铃,又指了指墙上一把落灰的斧头。
> 特米:「请房客走,先按门铃(`kill`),他会收拾行李体面离开。斧头(`kill -9`)砍门——**行李就留在屋里了**。」

## 三、本话目标

- 建立**进程**心智模型:PID、父子关系、状态;
- `ps aux` 拍快照点名,配合管道 `grep` 定位目标;
- `top` 看实时记分牌,揪出吃 CPU 的元凶;
- 分清 `kill`(15,好言相劝)和 `kill -9`(强拆),知道后者的代价;
- 亲手把一台卡死的服务器救回来。

## 四、原理图:进程公寓

```text
公寓管理处(内核)给每个房客发一张房卡:

PID 1  systemd ──── 全楼的大管家,所有房客的老祖宗
 ├── sshd  ──────── 门卫:你每次 ssh 进来都经它手
 │    └── bash ─── 你的翻译官(它也是个进程!)
 │         └── ps  你敲的每条命令 = 一个短命房客
 └── order-watcher.sh  ← 阿零忘掉的疯房客,空转 12 天

STAT 一列 = 房客在干嘛:
R 正在跑 / S 在睡觉等事(大多数)/ Z 僵尸(死了没销户)/ T 被暂停

kill 不是"杀",是"递信号":
kill PID      = 发 15 号信(SIGTERM):请你退场,可以先保存
kill -9 PID   = 发  9 号信(SIGKILL):内核直接拔电,进程连遗言都留不下
```

## 五、上手:点名、直播、请人

先拍快照。`ps aux` 太长,用第 2 卷的管道接 `grep` 过滤:

```bash
$ ps aux | grep order-watcher
ubuntu      4721 99.3  0.1   6208  3456 ?        R    Sep23 17280:11 /bin/bash /home/ubuntu/bin/order-watcher.sh
ubuntu      5133  0.0  0.0   6544  2304 pts/0    S+   14:23   0:00 grep --color=auto order-watcher
```

一行读五个字段:**谁(USER)、门牌(PID)、多能吃(%CPU/%MEM)、什么状态(STAT)、在干嘛(COMMAND)**。第二行是 `grep` 照见了自己,忽略。

> **特米旁白**:嫌快照不过瘾就开直播——`top`,按 `P` 按 CPU 排序、`M` 按内存排序、`q` 退出。第一排常年霸榜的,就是你要找的人。

```text
top - 14:23:05 up 12 days,  3:41,  1 user,  load average: 1.98, 1.72, 0.89
Tasks: 118 total,   2 running, 116 sleeping,   0 stopped,   0 zombie
%Cpu(s): 98.7 us,  1.0 sy,  0.0 ni,  0.3 id,  0.0 wa,  0.0 hi,  0.0 si,  0.0 st
MiB Mem :   3915.8 total,    213.4 free,   1024.7 used,   2894.2 buff/cache

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   4721 ubuntu    20   0    6208   3456   3072 R  99.7   0.1  17280:11 order-watcher.s
```

`load average: 1.98` ——1 核的机器背着近 2 倍的活。元凶确认:PID 4721。按门铃:

```bash
$ kill 4721          # 默认发 15 号信 SIGTERM,没有输出 = 信送到了
$ ps -p 4721
    PID TTY          TIME CMD
```

名单空了,房客走了。`top` 里 load average 一分钟内开始回落,`ls` 又快了。

## 七、读懂真实翻车

咖啡站死得悄无声息。可重启后,阿零查当天的订单流水,最后一行是这样的:

```bash
$ tail -2 ~/coffee-shop/orders.log
2026-10-05 14:40:57,ORD-1041,americano,12.0,PAID
2026-10-05 14:41:02,ORD-1042,latte,
```

**最后一笔订单只写了半行,再后面的三笔直接消失了。**

根因:程序写文件通常先写进内存缓冲区,攒够了才落盘。`kill`(15)是可以被程序接住的——咖啡站的关闭钩子会把缓冲区刷进磁盘、断开连接、道别退场;而 `kill -9` **程序根本收不到**,是内核直接把进程抹掉,缓冲区里没落盘的数据当场蒸发。这就是半行订单的来历。

> **特米锐评**:`-9` 是最后的枪。顺序永远是:先 `kill`,等几秒,`ps -p` 复查;它装死不走,才 `-9`。上来就 `-9`,等于用「会丢数据」换「省三秒」。

对照修复:对 2216 该做的是——

```bash
$ kill 2216 && sleep 3 && ps -p 2216   # 好言相劝 → 等 → 复查
```

日志尾部干干净净:`... Flushing 3 pending orders... Coffee shop closed. Bye.`

> **🪟 双系统对照 · 查进程与请人走路**

| 干什么 | Linux | PowerShell | 备注 |
|---|---|---|---|
| 点名快照 | `ps aux` | `Get-Process`(别名 `ps`) | PS 返回**对象**,列可再加工 |
| 找吃 CPU 的 | `top` 按 `P` | `Get-Process | Sort-Object CPU -Descending | Select-Object -First 5` | Windows 的 CPU 列是累计秒数 |
| 按名字找 | `ps aux \| grep coffee` | `Get-Process java` | PS 直接按名筛,不用 grep |
| 好言相劝 | `kill PID`(15 号信) | `Stop-Process -Id PID` | 注意:`Stop-Process` **更接近 -9**,是硬杀 |
| 体面关闭 | 程序接 SIGTERM 清场 | 先试 `$p.CloseMainWindow()` 或服务用 `Stop-Service` | Windows 没有信号机制,这是最大差异 |

> **🎯 面试直击**:`kill -9` 和 `kill -15` 的区别?
> 15(SIGTERM)是**请求**,进程可捕获、做清理再退出;9(SIGKILL)由内核直接终结,进程无法捕获,来不及刷缓冲、关连接、删临时文件。追问点:哪个信号杀不掉僵尸进程?都杀不掉——僵尸已经死了,只等父进程收尸(`wait`),要么等父进程处理,要么父进程退出后由 PID 1 领养回收。
