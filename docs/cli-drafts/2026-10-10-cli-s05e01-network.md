# 《从零开始玩命令行》22 · 网络三板斧:ping、curl 与 ss

> 连载特刊 · 第二部《从零开始玩命令行》第 5 卷「网络与部署」第 1 话(**最终卷开幕**)
> 长期项目:**把豆豆咖啡站部署上真实服务器**。前作《从零开始学 Java》全 56 话见 [/java](/java)。

## 一、需求:包裹到了,店却开不了门

上一卷末尾,阿零用 `rsync` 把 `coffee-api.jar` 稳稳送上了服务器,还顺手装好了 MySQL。今天他 `ssh` 进去,`java -jar coffee-api.jar`,Spring 的启动横幅刷过,一切正常。

他得意地把地址甩给豆豆:`http://203.0.113.10:8080`。三秒后豆豆幽幽回话:「**转圈圈,打不开。** 你确定我的新家不是海市蜃楼?」

阿零盯着屏幕:服务明明起了啊。是网断了?地址错了?端口没开?还是服务其实死了?——**他连该先怀疑哪一层都不知道。**

---

## 二、漫画 · 三板斧登场

> **〔1〕** 服务器窗口里 Spring 横幅还热着,阿零在本机敲 `curl` 一切正常;画面另一侧,豆豆举着手机,加载圈转得像拉花。
> 豆豆:「Java 线你交付过整套 API,现在店门口连**门都摸不到**?」

> **〔2〕** 特米滑进画面,肚皮 `>_` 一亮,甩出三把小斧头,斧柄上分别刻着 `ping`、`curl`、`ss`。
> 特米:「连不上,不许猜。三句话:**路通吗、店开吗、门牌谁在听。**」

> **〔3〕** 特米画了一条送咖啡的路线:马路(网络)→ 地址簿(DNS)→ 门牌号(端口)→ 柜台店员(服务)。
> 特米:「豆豆那杯咖啡送不到,只可能断在这四层之一。**一层一层问,别跳。**」

> **〔4〕** 阿零 `ping` 通了,立刻拍桌:「网没问题!那就是玄学!」
> 特米(面无表情):「`ping` 只证明**马路通**,不证明**店开门**。下一板斧。不会用?**man 一下**。」

> **〔5〕** `ss -tlnp` 的输出亮出来,`8080` 那行的地址赫然是 `127.0.0.1`。
> 特米:「找到了。你的店员只对**店内**喊单——门牌根本没挂到街面上。」

## 三、本话目标

- 把「连不上」拆成四层分诊:**网络 → DNS → 端口 → 服务**;
- `ping`:探网络层通不通;`curl -I`:探服务活没活;`ss -tlnp`:查端口谁在听、听在哪个地址;
- 学会读 `curl` 的三种典型死法:**拒绝、超时、解析失败**,各指向不同一层;
- 踩一次「服务只绑 `127.0.0.1`」的经典坑。

---

## 四、原理图:四层分诊流程

```text
「连不上」四层分诊(从下往上问)

① 路通吗?      ping <IP>            不通 → 网络层:机器没开机/路由不通
② 名字对吗?    curl http://域名     curl: (6) Could not resolve host → DNS 层
③ 门牌有人听吗? (服务器上) ss -tlnp  没有那行 → 服务没起;地址是 127.0.0.1 → 只听本机
④ 店员活着吗?  curl -I localhost:端口   200 → 服务本身是好的

curl 三种死法 → 各指向一层:
  (6) Could not resolve host   名字查不到       → DNS
  (7) Connection refused       到了,被明确拒绝 → 端口没人听(服务/绑定)
  (28) Connection timed out    包石沉大海       → 网络不通,或防火墙悄悄丢包
```

> **特米旁白**:老教程里的 `netstat -tlnp` 已经退休,Ubuntu 24.04 的正统是 `ss`(参数几乎同款:`-t` TCP、`-l` 监听、`-n` 数字、`-p` 进程)。

## 五、上手:三板斧连招

在你自己的电脑上问路,在服务器上查门牌:

```bash
# ① 本机 → 服务器:路通吗
$ ping -c 3 203.0.113.10
PING 203.0.113.10 (203.0.113.10) 56(84) bytes of data.
64 bytes from 203.0.113.10: icmp_seq=1 ttl=52 time=8.42 ms
64 bytes from 203.0.113.10: icmp_seq=2 ttl=52 time=8.37 ms
64 bytes from 203.0.113.10: icmp_seq=3 ttl=52 time=8.51 ms

--- 203.0.113.10 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms

# ② 服务器上:店员活着吗(HEAD 请求只看响应头)
$ curl -I http://127.0.0.1:8080/api/menu
HTTP/1.1 200
Content-Type: application/json
Date: Sat, 10 Oct 2026 09:30:12 GMT

# ③ 服务器上:门牌谁在听
$ sudo ss -tlnp
State   Recv-Q  Send-Q   Local Address:Port    Peer Address:Port  Process
LISTEN  0       100          127.0.0.1:8080         0.0.0.0:*      users:(("java",pid=1873,fd=9))
LISTEN  0       4096           0.0.0.0:22           0.0.0.0:*      users:(("sshd",pid=712,fd=3))
```

路通、店员活着——但第三板斧露了馅:`8080` 挂在 `127.0.0.1` 上,而 `sshd` 的 `0.0.0.0` 才是「对所有网卡开门」。

## 六、故意制造一个 Bug:抄来的配置

这个坑是阿零自己埋的:他把本地调试用的 `application.properties` 原样 rsync 了上来,里面躺着当年图安全加的一行:

```properties
server.address=127.0.0.1
```

于是在服务器上模拟外部访问(对着公网 IP 而不是 localhost):

```bash
$ curl -I http://203.0.113.10:8080/api/menu
```

## 七、读懂真实报错

```text
curl: (7) Failed to connect to 203.0.113.10 port 8080 after 0 ms: Connection refused
```

同一台机器,`127.0.0.1` 是 200,公网 IP 却被**拒绝**。对照四层分诊:refused 意味着包**到了机器**,但那个地址上**没人听**——`ss` 早就告诉过你答案:`127.0.0.1:8080`,店员只听店内广播。

修法:`vim` 删掉那行(或改成 `server.address=0.0.0.0`),`Ctrl+C` 停掉重新 `java -jar`。再看 `ss`,地址变成了 `*:8080`——所有网卡,街面开门。

> **🪟 双系统对照 · 三板斧在 Windows 上怎么抡**

| 干什么 | Linux (bash) | PowerShell 7 | 备注 |
|---|---|---|---|
| 路通吗 | `ping -c 3 主机` | `ping 主机` / `Test-Connection 主机` | Windows 默认 4 次,`-c` 写作 `-n` |
| 店开吗 | `curl -I http://…` | `Invoke-WebRequest -Method Head http://…`(别名 `iwr`) | Win10+ 自带真 `curl.exe`,手感可直接迁移 |
| 谁在听 | `ss -tlnp` | `Get-NetTCPConnection -State Listen` | 配 `-LocalPort 8080`,再拿 `OwningProcess` 去 `Get-Process` |
| 名字解析 | `dig` / `resolvectl query` | `Resolve-DnsName 域名` | 两边都比 `ping` 更适合单查 DNS |

> **🎯 面试直击**:Connection refused 和 Connection timed out 有什么区别?
> refused = 对端**明确回了 RST**:机器可达,但端口没人听(服务没起/绑错地址);timed out = 包**石沉大海**:路由不通、机器不在线,或防火墙 DROP 静默丢包。追问:防火墙 REJECT 会表现成 refused,DROP 才是超时——所以「超时」永远要多怀疑一层防火墙。

## 八、用命令验证:一层一层重新问

```bash
$ sudo ss -tlnp | grep 8080
LISTEN  0  100  *:8080  *:*  users:(("java",pid=1954,fd=9))    # 地址已是 *

$ curl -I http://203.0.113.10:8080/api/menu    # 服务器上,对公网 IP
HTTP/1.1 200
```

服务器内部,四层全绿。可豆豆那边刷新——**还是转圈圈**,本机 `curl` 对着服务器公网 IP 也从 refused 变成了:

```text
curl: (28) Failed to connect to 203.0.113.10 port 8080 after 133281 ms: Connection timed out
```

refused 变 **timed out**——按今天学的,这不是服务的问题了,是**有人在半路悄悄丢包**。
