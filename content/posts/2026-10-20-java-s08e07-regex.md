## 一、事故:第十一个 if

冬歇期第七天,技术债账本第一页翻到「文本校验」这一笔。会员注册表单里的手机号五花八门:带 `+86` 的、中间塞空格的、还有人干脆填了十一个 8。阿零的校验函数已经写到第十一个 `if`:第一位是不是 `'1'`、第二位在不在 3~9、后面九位挨个 `Character.isDigit`……

## 二、漫画 · 刻章人与巡逻员

> **〔1〕** 注册申请堆成山,阿零的屏幕上 if 叠 if,像一面歪歪扭扭的砖墙。
> 阿零:「第一位 `'1'`,第二位 3 到 9,后面九位是数字……这是第十一个 if 了。」
> 豆豆(翻账本):「技术债第一页第七笔:文本校验,一直拿 if 蛮干。今天请正牌军。」

> **〔2〕** 豆豆推出一台刻章机,把 `^1[3-9]\d{9}$` 刻成一枚铜章(Pattern);旁边一个小巡逻员(Matcher)举着章,在字符串大街上逐格比对。
> 豆豆:「`Pattern.compile` 把规则**编译**成章——刻一次,盖一辈子。Matcher 是拿章巡逻的人,有状态,一人只巡一条串,别共用。」

> **〔3〕** 阿零得意地在循环里写 `s.matches(regex)`,身后刻章机疯狂冒烟——每循环一圈就重刻一枚一模一样的铜章,废章堆成小山。
> 豆豆:「`String.matches` 每调一次就重新编译一次。一万条会员数据 = 重刻一万枚章。章要 `static final`,供起来。」

> **〔4〕** 【特写格】巡逻员走进备注街「少糖少糖……」,在街尾撞上一个非法的「!」,开始一步步**倒着走回头路**,每个岔口都要把没走过的路全试一遍;身后 Timeout 迷雾 Bug 怪缓缓漫上来,收银台的秒针停摆。
> 豆豆:「回头路本身不可怕,可怕的是你给它修了**嵌套量词**的迷宫——岔口乘岔口,指数爆炸。」

> **〔5〕** 阿零抄起听诊器 jstack 往 JVM 城主的线程调度中心一贴,吐出一摞 `Pattern$Curly.match` 栈帧。
> 阿零:「凶手把名字印在栈上了!」
> 豆豆(叼着豆子叉腰):「正则崩起来**不出声**——不抛异常,只烧 CPU。这才是它最阴的地方。」

## 三、本话目标

- 用 `Pattern`/`Matcher` 预编译正则,戒掉循环里的 `String.matches`;
- 认全字符类、量词、锚点、分组四大件,分清 `matches` 与 `find`;
- 用命名分组解析订单行,用 `replaceAll` + `$1` 给日志打码;
- 分清贪婪 / 懒惰 / 占有三种量词的回溯脾气;
- 亲手引爆一次灾难性回溯(ReDoS),再彻底拆掉它。

## 四、原理图:Pattern 是章,Matcher 是巡逻员

```text
"^1[3-9]\d{9}$" ──Pattern.compile()──▶ Pattern(编译产物:不可变、线程安全,刻一次用一辈子)
                                          │ pattern.matcher(input)
                                          ▼
                                       Matcher(带状态的巡逻员:记着走到哪,一人一串,不可共享)

matches() —— 整串从头到尾必须吻合(自带 ^…$ 整串锚定)
find()    —— 在串里往前扫,找到一段算一段,可连续调用
String.matches(regex) —— 语法糖:每调一次 = 现场重新 compile 一次
```

四大件速查:

| 家族 | 记号 | 一句话 |
|---|---|---|
| 字符类 | `[3-9]` `\d` `\w` `\s` `[^…]` | 这一格允许哪些字符 |
| 量词 | `*` `+` `?` `{n,m}` | 上一格重复几次(默认贪婪) |
| 锚点 | `^` `$` `\b` | 不吃字符,只钉位置 |
| 分组 | `(…)` `(?<name>…)` | 抓内容,供 `group(...)` / `$1` 引用 |

三种量词的脾气(对「x2 加浓 x2」用 `x(.*)2` 抓 `$1`):

| 写法 | 策略 | 结果 |
|---|---|---|
| 贪婪 `.*` | 先吞到底,再一步步回吐 | `$1` = `2 加浓 x`(最大匹配) |
| 懒惰 `.*?` | 能少吃就少吃 | `$1` = 空串(x 后立刻遇 2) |
| 占有 `.*+` | 吞到底且**绝不回吐** | 整体匹配失败(2 被吞走,不回头) |

## 五、代码:给注册表单和订单日志上正则

上一话订单的时间字段已全面换成 `java.time`;本话在同一套注册与下单流程上,给**手机号**和**日志**加正则守门员:

```java
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class SignupValidator {
    // 章刻一次,供起来:Pattern 不可变、线程安全
    private static final Pattern PHONE = Pattern.compile("^1[3-9]\\d{9}$");
    private static final Pattern ORDER_LINE =
            Pattern.compile("(?<name>\\S+)\\s*x(?<count>\\d+)");   // 命名分组

    static boolean isPhone(String s) {
        return PHONE.matcher(s).matches();          // matches:整串必须吻合
    }

    public static void main(String[] args) {
        IO.println(isPhone("13812345678"));         // true
        IO.println(isPhone("2381234567"));          // false:锚点 ^ 卡死第一位

        Matcher m = ORDER_LINE.matcher("拿铁 x2,美式 x1");
        while (m.find()) {                          // find:扫到一段算一段
            IO.println(m.group("name") + " → " + m.group("count") + " 杯");
        }

        // replaceAll + $1/$2:日志里给手机号打码,捕获组按序号反向引用
        String log = "会员 13812345678 注册成功";
        IO.println(log.replaceAll("(1[3-9]\\d)\\d{4}(\\d{4})", "$1****$2"));
        // 输出:会员 138****5678 注册成功
    }
}
```

## 六、故意制造一个 Bug:嵌套量词

轮到订单**备注**字段,阿零照猫画虎:「备注 = 若干个词(汉字或字母数字),词间可以有个空格。」

```java
// 阿零的第一版:内层 […]+ 外面再套 (…)+ —— 看着无懈可击
static boolean remarkOk(String remark) {
    return remark.matches("([\\u4e00-\\u9fa5\\w]+ ?)+");   // matches 自带整串锚定
}
```

上线十分钟,一位顾客粘贴了一条 40 字符的备注,结尾多了个全角感叹号:

```java
String hostile = "少糖".repeat(19) + "糖!";   // 40 字符,最后的「!」不在字符类里
remarkOk(hostile);                            // ← 这一行,再也没有返回
```

## 七、观察真实现象:CPU 100%,jstack 抓现行

没有异常,没有日志。收银台整个假死,java 进程把一颗核焊死在 100%。阿零抄起 jstack(回看第 43 话)一贴:

   java.lang.Thread.State: RUNNABLE
	at java.util.regex.Pattern$Curly.match0(java.base@25/Pattern.java:4529)

	...(同样几个帧反复堆叠了几十层)

状态 `RUNNABLE`、cpu 一路疯涨、栈里全是 `Pattern$Curly` / `Pattern$Loop`——凶手名字直接印在栈上。

**根因**:Java 正则是**回溯式引擎**。那 39 个合法字符,既能被内层 `[…]+` 一整口吞下,也能拆成「少 + 糖少 + 糖……」让外层 `(…)+` 多转几圈——**每个字符缝都可以切一刀,也可以不切**。匹配成功时引擎走运只试一条路;而结尾那个「!」注定整串失败,引擎便老老实实把 2³⁸ 量级的切法**全部试完**才认输——按每秒一亿步,也得跑上个把小时。这叫**灾难性回溯**;被人拿去当武器,就叫 **ReDoS**。

> **🎯 面试直击**:什么是 ReDoS?为什么一条正则能打挂服务?
> Java 正则引擎靠**回溯**:失败就退回岔口换路重试。嵌套量词(如 `(a+)+b`)让同一段文本有指数级种拆法,一条构造过的**不匹配**长串就能让一次 `matches` 烧掉一颗核几小时;请求线程被逐个钉死,线程池抽干,服务就挂了。追问点:怎么防?① 用户输入先设长度上限;② 消除嵌套量词或改占有量词;③ `static final Pattern` 预编译并 review 模式;④ 必须跑不可信正则时,丢独立线程加超时。

## 八、修复,并用测试证明

豆豆的手术,三刀:

```java
import java.util.regex.Pattern;

public final class RemarkValidator {
    private static final int MAX_LEN = 40;
    // 第一刀:压平——单层字符类 + 有界量词,同一串只剩一种走法,回溯无路可退
    private static final Pattern REMARK = Pattern.compile("[\\u4e00-\\u9fa5\\w ]{1,40}");

    public static boolean isValid(String remark) {
        if (remark == null || remark.length() > MAX_LEN) return false; // 第二刀:长度上限先行
        return REMARK.matcher(remark).matches(); // 第三刀:static final Pattern,顺手戒掉重复编译
    }
}
```

真需要「词 + 分隔符」结构时,给内层换**占有量词**:`([一-龥\w]++ ?)+`——`++` 吃了不吐,内外量词之间不再有第二种拆法,失败即秒败。

JUnit 质检员踱过来:「证据呢?」

```java
import org.junit.jupiter.api.Test;
import java.time.Duration;
import static org.junit.jupiter.api.Assertions.*;

class RemarkValidatorTest {
    @Test
    void normal_remark_passes_and_illegal_chars_fail() {
        assertTrue(RemarkValidator.isValid("少糖 去冰 双份浓缩"));
        assertFalse(RemarkValidator.isValid("少糖<script>"));
    }

    @Test
    void hostile_40_char_remark_fails_within_100ms() {
        String hostile = "少糖".repeat(19) + "糖!";   // 打挂旧版的那条,原样回放
        assertTimeoutPreemptively(Duration.ofMillis(100),
                () -> assertFalse(RemarkValidator.isValid(hostile)));
    }
}
```

绿灯。同一条毒备注,旧版正则一小时出不来,新版一毫秒内利落拒绝。

> **豆豆锐评**:**所有用户输入都要先设长度上限,再进正则**。回溯的代价 = 模式的歧义 × 输入的长度;模式将来会不会被谁改出歧义,你管不住,但输入多长,你今天就能管——一行 O(1) 的长度检查,把指数炸弹的引信剪到最短。

1. `String.matches(regex)` 每调一次实际做了什么?
   - A) 只是字符串比较　B) 内部重新 `Pattern.compile(regex)` 一次　C) 复用全局缓存　D) 直接返回 boolean

   - A) 继续用 matches　B) 把 Pattern 提成 static final,用 `PATTERN.matcher(s).matches()`　C) 换 String 其他方法　D) 不用正则

   - A) 都是相同的　B) Pattern 是编译好的印章(线程安全可复用),Matcher 是巡逻员(带状态不可共享)　C) Pattern 是单例　D) 都可以复用

6. 灾难性回溯(ReDoS)的根因是?
   - A) 正则引擎太慢　B) 嵌套量词让同一段文本有指数级拆法,引擎逐一回溯尝试　C) Pattern 没有预编译　D) CPU 不够
7. 防御 ReDoS 的第一条铁律是?

8. 贪婪 `.*`、懒惰 `.*?`、占有 `.*+` 的区别是?
   - A) 只是性能不同　B) 贪婪吃到底再吐,懒惰吃一点算一点,占有吃到底绝不回吐　C) 都是同一种　D) 占有没有意义
9. `replaceAll("(1[3-9]\\d)\\d{4}(\\d{4})", "$1****$2")` 中 `$1` 指?
   - A) 第一个字符　B) 第一个捕获组匹配到的内容　C) 1 元　D) 转义
10. `static final Pattern` 为什么线程安全?
    - A) Pattern 是不可变对象——编译后没有可变状态　B) 加了锁　C) 编译器保护　D) 默认单例

> [!答案]
> **1-B**　`String.matches` 是语法糖,内部每次调用都会 `Pattern.compile(regex).matcher(input).matches()`,重复编译一模一样的东西。**举一反三**:循环里调 matches 就是 O(n) 次编译——文章里的「一万条会员=一万枚废章」是真实故事;任何循环里的正则调用都要把 Pattern 提到外面。
> **2-B**　`static final Pattern P = Pattern.compile(...)`,编译一次用一辈子。**举一反三**:这就是「预编译」——不仅快,还让正则的可读性提升;同事看代码一眼就知道这里用的是什么模式。
> **3-B**　Pattern 是不可变的编译产物,`Pattern.compile` 一次就够,多线程共享安全。Matcher 持有当前匹配位置等状态,是一个串一个 Matcher,不能跨线程共享。**举一反三**:`"Pattern 是模板,Matcher 是拿着模板逐格比对的工人"`,Worker 手上有状态(走到哪了),不能两个人共用一个。
> **4-B**　`find()` 像「扫一遍找到第一个匹配」,可以连续调找下一个;`matches()` 要整串从第一个字符到最后一个字符都符合。**举一反三**:`matches` 等同于 `^...$` 的效果;如果只是想检查字符串里是否包含某段,用 `find()`;手机号校验通常用 `matches`,日志解析用 `find`。
> **5-B**　命名分组让正则和 Java 代码解耦——正则里调整分组顺序,Java 代码不需要跟着改 `group(1)` 的序号。**举一反三**:`(?<name>\S+)\s*x(?<count>\d+)`——6 个月后回来维护,`group("count")` 比 `group(2)` 可读得多。
> **6-B**　`([一-龥\w]+ ?)+`——内层的 `+` 和外层的 `+` 重叠扫描同一个区间,每一个字符缝能切也能不切,引擎把 2^N 种切法全试了才认输(输入有 N 个字符缝)。**举一反三**:Java 的正则引擎是**回溯式**的,NFA;Go 和 Rust 的正则用 DFA 引擎,对同一模式天然 O(n),没有这个问题——但不代表 Java 里就不要写了,消嵌套量词即可。
> **7-B**　长度上线 = 剪掉炸弹引信:不管正则被谁写成多歧义,输入短了回溯步数就有限。**举一反三**:生产上在 Controller/网关层对所有输入做长度校验是基础安全实践,不仅防 ReDoS,还防内存占满(超大输入)。
> **8-B**　贪婪 `.*` 先吞到底再回吐一点点匹配后续模式;懒惰 `.*?` 吃最少的;占有 `.*+` 吞到底且不回吐,后续模式若失败就直接整体失败(不回溯)。**举一反三**:占有量词就是 ReDoS 的直接解药——`[一-龥\w]++` 让内层吃了不吐,把指数回溯从源头掐死。
> **9-B**　捕获组按左括号顺序编号,`$1` 引用第一个组捕获的内容。**举一反三**:`replaceAll` + 捕获组引用可以一行代码给日志/手机号脱敏——这就是为什么读日志的正则同时写了 `$1****$2`。
> **10-A**　Pattern 编译后是一个不可变的状态机(内部是节点图,immutable),所有匹配操作都由 Matcher 承担(持有跑到了哪的状态),Pattern 本身无状态可改。**举一反三**:String 也遵循同样原理——不可变 = 线程安全;所有不可变对象天生可以 static final 共用。

### 解答题(5 道)

1. 用一张表总结正则四大件(字符类、量词、锚点、分组),各给 2 个例子并解释。
2. 为什么 `String.matches` 在循环里是大忌?写出正确做法。
3. ReDoS 的典型模式长什么样?为什么「先限长」是第一防线?
4. 一个日志行格式 `"2026-10-19 下单 拿铁 x2"`,用命名分组解析出日期、操作和数量。
5. 三种量词(贪婪/懒惰/占有)各给一个场景,说明为什么这种场景适合它。

> [!答案]
> **1**　| 家族 | 例子 | 解释 ||---|---|---|| 字符类 | `[3-9]` | 允许 3~9 任一数字 || 字符类 | `\d` | 等价 [0-9] || 量词 | `{9}` | 正好 9 次 || 量词 | `+` | 1~N 次 || 锚点 | `^` | 字符串开头 || 锚点 | `\b` | 单词边界 || 分组 | `(...)` | 捕获,按左括号顺序编号 || 分组 | `(?<n>...)` | 命名捕获,`group("n")` 取值 |　**举一反三**:四大件不用死背——每次写正则就扫一遍这张表,写多了自然记住;忘掉的用例翻文档比硬回忆快。
> **2**　循环里的 `s.matches(regex)` 每圈调一次 Pattern.compile——一万圈就是一万次编译。正确做法:`static final Pattern P = Pattern.compile(regex)`,循环里 `P.matcher(s).matches()`。**举一反三**:IDEA 的 Inspection 能自动检测这种 Pattern——`'String.matches()' used in loop` 警告,见到就修。
> **3**　典型模式:嵌套量词如 `(a+)+b`、`([一-龥\w]+ ?)+`,内外两层量词对同一段文本都有「吃多少」的决定权,每处都能抉择,组合爆炸。先限长:正则前加一行 `if (input.length() > MAX) return false`,无论正则本身多歧义,输入短了试探步数就可控。**举一反三**:三层防线:① 长度上限先行,② 消除嵌套量词(压平为单层 `[...]{1,N}`),③ 必须保留嵌套时换占有量词 `++`。
> **4**　```java
Pattern ORDER = Pattern.compile("(?<date>\\d{4}-\\d{2}-\\d{2}) (?<op>下单) (?<name>\\S+) x(?<count>\\d+)");
Matcher m = ORDER.matcher(line);
if (m.find()) {
    String date = m.group("date"), op = m.group("op");
    String name = m.group("name"), count = m.group("count");
}
```　**举一反三**:命名分组让正则和 Java 代码彻底解耦——以后正则里加一个分组 ?<channel>,Java 侧加一行 m.group("channel") 即可,不碰 group(n) 的序号。
> **5**　贪婪 `.*`:日志行 `[2026-10-19] 下单 拿铁x2`,用 `\[(.*)\]` 抓方括号内容——它能自动找到最后一个 `]`,不回退吃不全是吧?但贪婪就是先吞到尾再回退到最后一个 `]`,恰好符合需求。懒惰 `.*?`:同一行 `\[(.*?)\]` 也能找到,而且从左往右最早出现的 `]`,和贪婪一样结果但策略不同。占有 `.*+`:扫描安全场景——防范恶意输入时,用 `[a-zA-Z0-9]++@[a-zA-Z0-9]++\.[a-zA-Z]+` 让邮箱各部分绝不回退重试。**举一反三**:默认写贪婪,如果发现正则性能差(输入长时卡死)再换成占有;懒惰最慢(每吃一步就要试探后续能否匹配),只在确实需要「最少匹配」时才用。
