## 🎬 开场：深夜卡顿复盘

> **〔1〕**
> 凌晨 2 点，告警响了：咖啡站下单接口 P99 突然飙到 800ms，持续 3 分钟，然后恢复正常。早上阿零看监控，只有 QPS 和错误率，没有卡顿期间的 JVM 内部状态。「如果当时开着 JFR，就能看到卡顿那 3 分钟里，GC 停顿了多少次，哪个方法突然变慢，线程在等什么锁。」

> **〔2〕**
> JFR（Java Flight Recorder）是 JDK 内置的诊断框架，JDK 11 起完全免费。它持续录制 JVM 内部事件（GC、JIT、线程、IO、锁等），存入固定大小的环形 buffer，写满后覆盖最旧的数据（默认 128MB）。平均开销 <1%，适合生产常态开启。事件触发后 dump 到文件，用 JDK Mission Control（JMC）或 `jfr print` 分析。

> **〔3〕**
> 内置事件覆盖 GC（停顿、堆摘要）、JIT（编译事件、去优化）、线程（park/unpark、sleep、监控等待）、IO（socket/file 读写超过阈值）、CPU（采样 profiling，每 10ms 采一次热点方法）、异常（堆栈记录）。事件类型超过 160 个，configuration 分 default（低开销）和 profile（更多细节，稍高开销）。

> **〔4〕**
> 自定义事件：继承 `jdk.jfr.Event`，加字段注解，在业务代码里 `commit()`。出杯耗时、订单金额、用户等级这些业务指标就和 JVM 内部事件写进同一时间轴。复盘时直接对照：「下单慢的那 50ms，JFR 里对应了什么？」——是 GC 停顿、锁竞争，还是 IO 等待，一目了然。

## 🔑 核心 API

```
启动方式：
  命令行：java -XX:StartFlightRecording=duration=60s,filename=app.jfr MyApp
          java -XX:StartFlightRecording=maxage=5m,maxsize=100m MyApp  # 连续录制
  jcmd：  jcmd <pid> JFR.start name=prod settings=default maxage=5m
          jcmd <pid> JFR.dump name=prod filename=/tmp/dump.jfr
          jcmd <pid> JFR.stop name=prod
  API：   new Recording(config); recording.start(); ... recording.dump(path);

分析工具：
  jfr print --events EventType file.jfr    命令行文本分析
  jfr summary file.jfr                     事件类型统计概览
  JDK Mission Control (JMC)                GUI 可视化，火焰图/时间轴

自定义事件：
  @Name("com.example.OrderProcessed")      事件名（唯一标识）
  @Label("订单处理完成")                    JMC 显示名
  @Category({"业务", "订单"})              分类（JMC 树形导航）
  @StackTrace(false)                        不采集堆栈（降低开销）
  @Threshold("10 ms")                       只记录超过 10ms 的事件
  @Period("1 s")                           周期性事件（每秒触发一次）

  用法：
    var e = new OrderEvent();
    e.begin();      // 开始计时
    // ... 业务逻辑 ...
    e.orderId = "xxx";
    e.commit();     // 结束并提交（自动计算 duration）
    // 或：e.end(); if (e.shouldCommit()) e.commit();  // 尊重 Threshold
```

## ⚙️ 代码实录：自定义 JFR 事件 + 编程式录制

```java
// javac -encoding UTF-8 --release 25 JfrDemo.java
// java -XX:StartFlightRecording=duration=30s,filename=demo.jfr JfrDemo
// 或直接运行（内部编程式录制）：java JfrDemo
import jdk.jfr.*;
import jdk.jfr.consumer.*;
import java.nio.file.*;
import java.util.*;
import java.util.concurrent.*;

// ── 自定义事件：订单处理 ─────────────────────────────────────
@Name("com.coffee.OrderProcessed")
@Label("订单处理完成")
@Category({"业务", "咖啡站", "订单"})
@Description("记录每笔订单的处理时长和关键属性")
@StackTrace(false)               // 业务事件不需要堆栈，节约开销
class OrderEvent extends Event {
    @Label("订单ID")
    String orderId;

    @Label("商品")
    String item;

    @Label("金额(分)")
    int amountCents;

    @Label("用户等级")
    String memberTier;

    @Label("是否走缓存")
    boolean fromCache;
}

// ── 自定义事件：周期性指标（每秒上报出杯统计）──────────────────
@Name("com.coffee.BrewStats")
@Label("出杯速率统计")
@Category({"业务", "咖啡站", "监控"})
@Period("1 s")                   // 周期性事件，JFR 每秒触发 commit
class BrewStatsEvent extends Event {
    @Label("累计出杯数")
    int totalBrewed;

    @Label("平均出杯耗时(ms)")
    long avgBrewMs;
}

// ── 主体 ────────────────────────────────────────────────────
class JfrDemo {

    static final Random RNG = new Random(42);
    static int totalBrewed = 0;
    static long totalBrewMs = 0;

    static void processOrder(String orderId, String item) throws Exception {
        var event = new OrderEvent();
        event.begin();   // ← 开始计时

        // 模拟订单处理（含随机延迟）
        int brewMs = 150 + RNG.nextInt(100);
        Thread.sleep(brewMs);
        int amount = 3200 + RNG.nextInt(2000);
        String tier = RNG.nextInt(3) == 0 ? "GOLD" : "NORMAL";
        boolean cache = RNG.nextBoolean();

        // 填充事件字段
        event.orderId    = orderId;
        event.item       = item;
        event.amountCents = amount;
        event.memberTier  = tier;
        event.fromCache   = cache;

        // 更新全局统计（供 BrewStats 周期事件读取）
        totalBrewed++;
        totalBrewMs += brewMs;

        event.commit();  // ← 结束计时并提交事件
    }

    public static void main(String[] args) throws Exception {
        // 编程式录制
        var config = Configuration.getConfiguration("default");
        try (var recording = new Recording(config)) {
            // 启用内置事件
            recording.enable("jdk.GarbageCollection").withoutStackTrace();
            recording.enable("jdk.ThreadSleep").withThreshold(
                java.time.Duration.ofMillis(50));
            // 启用自定义事件
            recording.enable("com.coffee.OrderProcessed");
            recording.enable("com.coffee.BrewStats");

            recording.start();
            System.out.println("JFR 录制启动，处理 20 笔订单...");

            // 模拟订单流
            String[] items = {"拿铁", "美式", "卡布奇诺", "馥芮白"};
            for (int i = 1; i <= 20; i++) {
                processOrder("ORD-" + String.format("%04d", i),
                    items[i % items.length]);
            }

            recording.stop();
            Path jfrFile = Files.createTempFile("jfr-demo-", ".jfr");
            recording.dump(jfrFile);
            System.out.println("JFR 文件: " + jfrFile);

            // ── 读取并分析 JFR 文件 ─────────────────────────
            System.out.println("\n=== 订单处理事件分析 ===");
            long totalDuration = 0;
            int count = 0;
            long maxDuration = 0;

            try (var stream = EventStream.openFile(jfrFile)) {
                stream.onEvent("com.coffee.OrderProcessed", e -> {
                    long dur = e.getDuration().toMillis();
                    System.out.printf("  %s %-8s %4d分 %-6s 缓存:%-5s  耗时:%dms%n",
                        e.getString("orderId"),
                        e.getString("item"),
                        e.getInt("amountCents"),
                        e.getString("memberTier"),
                        e.getBoolean("fromCache"),
                        dur);
                });
                stream.onEvent("jdk.GarbageCollection", e -> {
                    System.out.printf("  [GC] %s  停顿:%dms%n",
                        e.getString("cause"),
                        e.getDuration().toMillis());
                });
                stream.start();
            }

            // 统计
            System.out.println("\n=== 性能摘要 ===");
            try (var stream = EventStream.openFile(jfrFile)) {
                List<Long> durations = new ArrayList<>();
                stream.onEvent("com.coffee.OrderProcessed",
                    e -> durations.add(e.getDuration().toMillis()));
                stream.start();
                if (!durations.isEmpty()) {
                    Collections.sort(durations);
                    System.out.printf("订单数: %d | 均值: %dms | P99: %dms | 最慢: %dms%n",
                        durations.size(),
                        (long) durations.stream().mapToLong(x->x).average().orElse(0),
                        durations.get((int)(durations.size()*0.99)),
                        durations.get(durations.size()-1));
                }
            }

            Files.delete(jfrFile);
        }
    }
}
```

## ⚠️ 常见陷阱

```java
// ❌ 陷阱 1：event.commit() 忘了调 begin()
var e = new OrderEvent();
// e.begin() 没调！
e.orderId = "X";
e.commit();  // duration = 0，事件 startTime 等于 endTime，分析时无法区分

// ✅ 用 try-with-resources 风格（JDK 17+ Event 支持 AutoCommit 模式）：
var e2 = new OrderEvent();
e2.begin();
try {
    // 业务逻辑
} finally {
    e2.orderId = result;
    e2.commit();  // 确保即使异常也 commit
}

// ❌ 陷阱 2：高频事件不加 @Threshold，每次都 commit 导致 buffer 溢出
// 每笔请求 10µs 的操作，QPS 10万 → 每秒100万条事件 → buffer 秒级溢出
@Name("com.coffee.CacheHit")
class CacheHitEvent extends Event { ... }
// ✅ 加 @Threshold("1 ms") — 只记录超过 1ms 的缓存命中（异常情况才值得关注）

// ❌ 陷阱 3：用 EventStream.openFile 后没调 stream.start()
try (var stream = EventStream.openFile(path)) {
    stream.onEvent("xxx", e -> ...);
    // ❌ 忘了 stream.start()！回调永远不会触发
    stream.start(); // ✅ 必须调用，会阻塞直到文件读完
}

// ❌ 陷阱 4：在高并发路径上读 e.getClass() 等重操作（在 onEvent 回调里）
// onEvent 回调在 EventStream 的后台线程里串行执行，重操作会导致消费跟不上
// ✅ 在回调里只做轻量聚合（计数/累加），最后统一输出

// ❌ 陷阱 5：自定义事件字段类型用复杂对象
class BadEvent extends Event {
    List<String> tags;  // ❌ JFR 不支持 List 字段，会被忽略
    // ✅ 支持的类型：String, int, long, double, float, boolean, byte, short, char
    String tagsJson;    // ✅ 序列化成字符串
}
```

## 🔬 炉底显微镜

```bash
# 查看 JFR 文件中所有事件类型及数量
jfr summary demo.jfr

# 输出指定事件（文本格式）
jfr print --events jdk.GarbageCollection demo.jfr
jfr print --events com.coffee.OrderProcessed demo.jfr

# 只看超过 100ms 的线程 sleep 事件（耗时过滤）
jfr print --events jdk.ThreadSleep \
  --stack-depth 5 demo.jfr | grep -A3 "duration.*[1-9][0-9][0-9]ms"

# CPU 热点方法（采样 profiling，最重要的性能分析工具）
jfr print --events jdk.ExecutionSample demo.jfr \
  | grep "stackTrace" | sort | uniq -c | sort -rn | head -20
# 等价于火焰图的文本版；频率最高的方法栈 = CPU 热点

# 用 jcmd 在运行中的进程上实时操作
jcmd <pid> JFR.start name=prod settings=profile maxage=10m maxsize=500m
# 10 分钟内覆盖的环形 buffer，出问题时：
jcmd <pid> JFR.dump name=prod filename=/tmp/incident.jfr

# jcmd 查看正在录制的会话
jcmd <pid> JFR.check

# 生产推荐：容器启动参数（开销<1%，持续录制）
java -XX:StartFlightRecording=maxage=30m,maxsize=500m,\
settings=default,dumponexit=true,filename=/logs/app.jfr \
-XX:FlightRecorderOptions=samplethreads=true \
MyApp
```

**JFR 事件分层**（按开销由低到高）：

```
瞬时事件（Timed）    begin()+commit() 自动记录 duration，最常用
周期事件（Periodic）  @Period 注解，JFR 调度器定期触发，适合心跳/统计
请求事件（Requestable）手动触发，通常在特定条件下
```

## 🎯 随堂练习

**Q1.** JFR 录制的默认存储机制是什么？为什么适合生产常态开启？

**Q2.** 自定义事件必须继承什么类？`begin()` 和 `commit()` 分别做什么？

**Q3.** `@Threshold("10 ms")` 注解的作用是什么？

**Q4.** `@Period("1 s")` 注解适合哪类事件？

**Q5.** `EventStream.openFile()` 后必须调用什么方法才能触发 `onEvent` 回调？

**Q6.** JFR 自定义事件字段支持 `List<String>` 类型吗？

**Q7.** `jfr print --events jdk.ExecutionSample` 可以用来做什么分析？

**Q8.** `jcmd <pid> JFR.dump` 和 `recording.dump(path)` 的区别是什么？

**Q9.** 如何在不重启 JVM 的情况下，对已经在运行的进程开启 JFR 录制？

**Q10.** Configuration 有哪两种预设，区别是什么？

---

> [!答案]
>
> **Q1. JFR 使用固定大小的环形 buffer（默认 128MB），持续写入，写满后覆盖最旧的数据。**这意味着内存占用有界，不会无限增长；问题发生时 dump 当前 buffer，保留问题前后一段时间的完整数据。开销 <1% 来自于：二进制格式（不做文本序列化）、环形 buffer 无锁写入、采样事件而非全量记录——适合生产常态开启，不需要「出了问题再去开」。
>
> **Q2. 自定义事件必须继承 `jdk.jfr.Event`（最终继承自 `jdk.jfr.internal.event.EventConfiguration`）。`begin()` 记录事件开始时间（startTime）；`commit()` 记录结束时间、计算 duration，并把事件写入 JFR buffer。**两者之间执行业务逻辑。`shouldCommit()` 可在 commit 前检查（基于 Threshold）——超阈值才实际写入，节约 buffer 空间。
>
> **Q3. `@Threshold("10 ms")`：只有事件 duration（`begin()` 到 `commit()` 的时间间隔）超过 10ms 时，事件才被实际写入 buffer。**低于阈值的事件调用 `shouldCommit()` 返回 false，commit 调用是空操作。适合高频操作（如每次数据库查询）——只记录慢查询，忽略快查询，极大降低 buffer 写入量。
>
> **Q4. `@Period("1 s")` 适合周期性心跳/统计类事件：不是由单次操作触发，而是 JFR 调度器每隔指定时间自动触发一次 commit。**例如：每秒采集一次当前连接池大小、出杯计数、内存使用量等指标——不需要在每次操作里手动触发，类似 Prometheus 的 scrape 机制，但数据直接进 JFR 时间轴。
>
> **Q5. 必须调用 `stream.start()`。**`start()` 会阻塞当前线程，直到文件中所有事件都被处理完（`onEvent` 回调全部触发）。忘记调用 `start()` 是最常见的错误——回调注册了但永远不执行，没有任何报错，只是静默地什么都不发生。
>
> **Q6. 不支持。JFR 事件字段只支持 Java 原始类型（int/long/double/float/boolean/byte/short/char）和 String。**不支持 List/Map/数组/自定义对象。需要记录复杂数据时，序列化为 JSON String，或拆分成多个字段（如 `tag1`, `tag2`），或在 commit 前转成逗号分隔字符串。
>
> **Q7. `jdk.ExecutionSample` 是 JFR 的 CPU 采样 profiling 事件（每 ~10ms 采一次热点线程的调用栈）。**对这些事件按调用栈聚合计数，频率最高的栈 = CPU 热点方法——等价于火焰图的文本版（火焰图是这些数据的可视化）。这是定位 CPU 性能瓶颈最直接的工具，无需代码插桩，生产可用。
>
> **Q8. `jcmd <pid> JFR.dump`：对正在运行的进程（通过 jcmd 连接）做 dump，进程继续运行，录制不停止；`recording.dump(path)`：在代码内部（通过 Recording API）做 dump，同样不停止录制（dump 是拷贝当前 buffer 到文件）。**两者效果相同，区别在于操作方式：`jcmd` 是外部工具触发（运维 / 告警脚本），API 是代码内自动触发（如检测到异常时自动 dump）。
>
> **Q9. 使用 `jcmd <pid> JFR.start`（不重启 JVM）：**`jcmd <pid> JFR.start name=incident settings=default maxage=5m maxsize=200m`。JFR 支持动态 attach，不需要重启。这是事后补救方案；更好的实践是提前用 `dumponexit=true` 配置常态录制，出问题时直接 dump 而不是临时开启（临时开启会丢失问题发生前的数据）。
>
> **Q10. `default`：低开销配置，适合生产常态运行，开销 <1%；启用约 80 个高价值低开销事件（GC/JIT/线程/IO/锁超阈值）。`profile`：更全面的诊断配置，开销约 2%；额外启用 CPU 采样（ExecutionSample）、对象分配采样、更细的 GC 阶段事件等——适合诊断性能问题时短时间开启，不建议常态运行。**
