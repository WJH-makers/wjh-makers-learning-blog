## 四、原理图:三种 Bug 怪的弱点

```text
类型         什么时候发作     谁来抓             致命弱点
─────────────────────────────────────────────────────────
Syntax Bug   编译就过不去     编译官(error:…)   报错带行号,顺藤摸瓜最好抓
Logic  Bug   能跑,结果错     没人报!靠测试+脑   最阴险:无栈无报错,只能想清边界
Null 幽灵    运行到一半崩     JVM(NPE)          现代 JDK 会点名 "xxx" is null
```

五步排障法(阿零这次全程照着念的):

```text
① 观察现象 —— 它到底表现成什么样?崩了?算错了?还是编译不过?
② 收集报错 —— 有报错就读全,行号、异常名、"because…"一个都别漏
③ 提出假设 —— 「我怀疑是 X」
④ 只改一处 —— 一次只动一个变量,否则治好了也不知道是谁的功劳
⑤ 重跑验证 —— 好了?进行下一个。没好?回到 ③ 换假设
```

## 五、代码:一段带三处伤的下单逻辑

```java
public class Cafe {
    static double priceOf(int choice) {
        return switch (choice) {
            case 1 -> 15.0;
            case 2 -> 18.0;
            default -> 20.0;
        };
    }

    public static void main(String[] args) {
        int qty = 3;
        double total = priceOf(1) * qty      // ① 语法:少了分号
        double paid = 40.0;

        if (paid > total) {                  // ② 逻辑:钱刚好等于时也该出杯,应为 >=
            System.out.println("出杯");
        }

        String note = null;
        System.out.println("备注长度:" + note.length());   // ③ Null:对 null 调 length()
    }
}
```

## 六、阿零独立排障

**① 语法 Bug**——阿零:「先编译,连门都没进就被拦。观察现象:编译官甩报错;收集报错:」

```text
Cafe.java:13: error: ';' expected
        double total = priceOf(1) * qty
                                      ^
```

「`';' expected`,箭头顶在第 13 行末尾——假设:漏了分号。**只改这一处**,补上 `;`,重跑。过了。下一个。」

**② 逻辑 Bug**——阿零:「这只灰怪不报错,程序跑得好好的,可我付 40、总价 40,它偏不出杯。没有报错能读,那就**自己想边界**:`paid > total`,当 `paid == total`(刚好付够)时是 `false`——顾客付了整钱却被拒。假设:该用 `>=`。改这一处。」这类 Bug **编译和运行都不吭声**,只能靠想清楚边界、或写测试逼它现形。

**③ Null 幽灵**——阿零:「跑到第三步才崩。收集报错:」

```text
Exception in thread "main" java.lang.NullPointerException:
        Cannot invoke "String.length()" because "note" is null
        at Cafe.main(Cafe.java:20)
```

「现代 JDK 太贴心了,它**直接点名**:`because "note" is null`。`note` 是 `null`,对 `null` 调 `.length()` 必崩。假设成立。给它一个有意义的默认值:`String note = "";`」

## 七、修复后

```java
double total = priceOf(1) * qty;      // ① 补分号
if (paid >= total) { ... }            // ② 改 >=
String note = "";                     // ③ 不再是 null
```

三处修好,程序正常出杯、打印「备注长度:0」。阿零全程**只改了三处、每处只改一个变量**——这正是五步法第 4 步的纪律。

## 八、用测试守住那只最阴险的

语法和 Null 会「吵着」暴露:一个编译不过、一个当场崩,想漏都难。真正阴险的是 **Logic Bug**——它无栈、无报错、不崩溃,只是安安静静地算错账,可能上线三个月才被财务发现对不上。

> **豆豆锐评**:记死这句——**逻辑 Bug 没有栈、没有报错,你唯一的防线是「测试 + 边界思考」**。报错会自己跳出来找你;逻辑错要你主动出击去逼它。所以「刚好付够」这种边界,必须钉一个测试守住:

```java
static boolean shouldServe(double paid, double total) {
    return paid >= total;   // 关键边界:相等也要出杯
}

@Test
void serve_when_exactly_paid() {
    assertTrue(Cafe.shouldServe(45.0, 45.0));   // 若手滑写成 >,这行立刻变红
}
```

这个测试就是那只灰怪的「防复发疫苗」:哪天有人手滑把 `>=` 改回 `>`,红灯当场亮起——比等财务对账早三个月。JUnit 质检员的口头禅又对上了:「**证据呢?**」

> **🎯 面试直击**:NullPointerException 是怎么来的,怎么防?
> **对一个 `null` 引用调用方法或访问字段**就抛 NPE。防线:① 变量给合理默认值(如空串、空集合)而非 null;② 用 `Objects.requireNonNull` 在入口尽早拦;③ 用 `equals` 时把已知非 null 的常量写前面。追问点:`Optional` 是更系统的「可能没有值」的表达(第二季讲)。现代 JDK 的**详细 NPE 报错**会点名是哪个变量为 null,排查快很多。

### 一、选择题（10 道）

1. [基础] 以下哪种 Bug 编译器**无法**发现？
   - A) 缺少分号　B) 变量名拼写错误　C) 数组越界访问　D) 方法参数类型不匹配

2. [基础] `NullPointerException` 属于哪种异常类型？
   - A) 编译期错误　B) 检查型异常（Checked Exception）　C) 非检查型异常（Unchecked Exception）　D) 不是异常，是 JVM 警告

3. [基础] 以下哪种调试方法最简单直接、零工具依赖？
   - A) 用 IDE 断点调试　B) 用 `System.out.println` 打印变量　C) 用 JProfiler 性能分析　D) 用 `jstack` 查看线程

4. [理解] 程序崩溃时打印了一大堆红色错误信息（stack trace），你应该从哪里开始读？
   - A) 从最下面最后一行读起　B) 从最上面第一条异常类型和消息开始　C) 随机挑选一行　D) 从中间 `Caused by` 行开始

5. [理解] 以下哪种 Bug 编译和运行都不报错，但结果完全错误？
   - A) 缺少 `return` 语句　B) `for` 循环中把 `sum += i` 误写成 `sum = i`　C) 数组越界　D) null 引用调用方法

6. [应用] 下面代码的输出是？`int sum = 0; for(int i = 1; i <= 10; i++) { sum = i; } System.out.println(sum);`
   - A) 55　B) 10　C) 0　D) 编译报错

7. [分析] Stack trace 中，哪一行最能帮你定位 Bug？
   - A) 第一行（异常类型和消息）　B) 指向你自己代码的第一行（`at com.xxx.YourClass.method(YourClass.java:XX)`）　C) 最后一行　D) JDK 内部调用行

8. [分析] `try-catch` 捕获异常后只打印了 `e.printStackTrace()`，这属于什么级别的 Bug 处理？
   - A) 完美处理　B) 可接受的处理　C) 吞掉了异常（bad practice）　D) 会让程序更快

9. [判断] 以下关于调试的说法正确的是？
   - A) 只有在代码写完后才能开始调试　B) 先猜 Bug 原因再改代码比先打日志看变量值更高效　C) 二分法排查（注释掉一半代码缩小范围）是有效的定位策略　D) 调试只在新手阶段需要

10. [综合] 以下代码有三个 Bug（编译/运行/逻辑各一），能正确识别全部三个的是？`public int calc(int[] arr) { int total = 0; for(int i=0; i<=arr.length; i++) { totel += arr[i]; } return total }`
    - A) 缺少分号、变量拼写、数组越界　B) 缺少返回类型、死循环、空指针　C) 缺少分号、语法错误、逻辑错误　D) 变量未初始化、非法字符、类型不匹配

> [!答案]
> **1-C**：数组越界（`ArrayIndexOutOfBoundsException`）是**运行时异常**，编译器不检查索引值是否在有效范围内。A、B、D 都是语法/类型层面的问题，编译器会直接拦截。**举一反三**：编译期能拦住语法和类型错误，但逻辑错误（如判断条件写反）编译和运行都不报错——这才是最隐蔽的 Bug。
> **2-C**：`NullPointerException` 继承自 `RuntimeException`，属于非检查型异常（Unchecked Exception）。非检查型异常不需要在方法签名中声明 `throws`，编译器也不会强制要求 `try-catch`。**举一反三**：检查型异常（如 `IOException`）必须在编译时处理，否则代码编译不通过——这是 Java 争议最大的设计之一。
> **3-B**：`System.out.println` 俗称"打桩"（printf debugging），不需要 IDE、不需要配置、任何环境都能用。缺点是临时性强，查完 Bug 后需要清理。**举一反三**：打桩法虽然原始，但在生产环境中（不能断点调试时）几乎是唯一可用的手段——学会打桩是程序员的必修课。
> **4-B**：Stack trace 应该从**最上面**开始读：先看异常类型名称（告诉你是什么错误），再看**第一条指向你自己代码的 `at` 行**（告诉你错误发生在哪个文件的哪一行）。JDK 内部的调用链（`java.base/...`）通常不是你的问题。**举一反三**：`Caused by` 链要逐层往下追——最底层的才是真正的根因。
> **5-B**：`sum = i` 是覆盖赋值而非累加，属于**逻辑 Bug**——语法正确、运行不崩溃、但结果错误。这是最难发现的 Bug 类型，因为没有红字提示。A 会编译报错，C 会抛异常，D 会抛异常。**举一反三**：逻辑 Bug 的排查黄金方法：在循环里加 `println` 打印每轮变量值，一眼就能看出"为什么 sum 没累加"。
> **6-B**：期望 1 到 10 累加得 55，但 `sum = i` 是覆盖赋值（不是累加），每轮用当前 i 的值覆盖 sum。循环结束 i=10 退出条件不满足前，最后一次赋值 `sum = 10`。输出 10。**举一反三**：这是经典笔试题——肉眼很难一眼看出，但执行一遍就明白。
> **7-B**：Stack trace 中指向你自己代码的第一行（包名 + 类名 + 行号）是定位 Bug 的黄金线索。例如 `at com.coffee.Main.order(Main.java:42)` 告诉你 `Main.java` 第 42 行的 `order` 方法出问题了。**举一反三**：在 IDE 中点击 Stack trace 的蓝色链接可以直接跳转到对应行——这是 IDE 对排 Bug 效率的杀手级提升。
> **8-C**：只打印堆栈而不做任何处理（恢复默认值、提示用户、记录日志到文件）属于"吞异常"（swallow exception）——程序可能继续运行但状态已经不正确，后续的 Bug 更难排查。**举一反三**：至少应该：①记录完整日志，②给用户友好提示，③重启或回滚事务。沉默的异常是"定时炸弹"。
> **9-C**：二分法排查是经典调试策略——每次注释掉（或 skip）一半可疑代码，看 Bug 是否消失，快速缩小范围。A 错：写一段测一段是更高效的 TDD 方法。B 错：猜而不看数据是"盲修"，浪费时间。D 错：调试能力是区分初级和高级工程师的核心指标之一。**举一反三**：二分法 = 代码界的"折半查找"——把 O(n) 的排查成本降到 O(log n)。
> **10-A**：三个 Bug——①`return total` 行末缺少分号（编译错误）；②循环内 `totel` 拼写错误，正确变量名是 `total`（编译错误）；③循环条件 `i<=arr.length` 应改为 `i<arr.length`，否则当 i=arr.length 时 `arr[i]` 越界（运行时异常）。**举一反三**：一道代码里的多 Bug 排查是面试常见题——先修编译错再修运行错，顺序不能乱。

### 二、解答题（3 道）

1. [概念阐述] 请清晰定义"编译期错误""运行时异常""逻辑 Bug"三类问题，各举一个具体的代码例子。为什么说逻辑 Bug 是最危险的？

2. [场景解释] 咖啡机系统上线后，用户投诉"买 3 杯美式价格显示不对"。作为开发者，请描述你的排查流程：①如何复现问题（输入什么）；②在哪里加 print 打桩（打印哪些变量）；③如何用二分法缩小范围；④修复后如何验证不再复发。

3. [综合分析] 阅读以下 Stack trace，用文字描述发生了什么错误，并指出应该修复的代码行号和修复方向。
```
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 5 out of bounds for length 5
    at com.cafe.OrderSystem.calcTotal(OrderSystem.java:24)
    at com.cafe.OrderSystem.main(OrderSystem.java:12)
```
请说明：①异常类型和含义；②哪一行是触发点（自己的代码）；③为什么会有这个异常；④如何修复。

> [!答案]
> **1**　①**编译期错误**：语法/类型不匹配，代码无法编译成 `.class` 文件。例如 `int x = "hello";`——类型不兼容，IDE 红线，javac 直接拒绝。②**运行时异常**：编译通过但运行到某条语句时崩溃，抛出异常。例如 `String s = null; s.length();`——`NullPointerException`，控制台打印红色 Stack trace。③**逻辑 Bug**：编译通过、运行不崩溃，但计算结果错误。例如把 `sum += i` 写成 `sum = i`——没有异常信息，只有最终结果不对。逻辑 Bug 最危险：没有报错指引，全靠人工推理，可能在生产环境潜伏数月。**举一反三**：防止逻辑 Bug 最有效的手段是**单元测试**——用机器替你验证每种情况的结果，而非肉眼比较。
> **2**　排查流程：①复现——输入饮品 1（美式），数量 3，观察输出总价。预期 15×3=45，实际如果显示 15，说明只算了单价没乘数量；如果显示 15+15+15=45但打印过程对不上，可能是循环内变量覆盖。②打桩——在 `calcTotal` 方法中每一步后打印：`System.out.println("单价=" + price + " 数量=" + qty + " 小计=" + price*qty);`，观察每轮小计和累加过程。③二分法——如果怀疑是乘法错了，先固定 price 和 qty 为常数测试；再逐步释放变量，看哪个变量引入错误值。④修复后验证——用多组数据测试：单杯×1、多杯×多、边界（单价 0、数量 0、数量最大），全部通过后才算修复。**举一反三**：专业的做法是把这些测试用例写成 JUnit 单元测试——每次改代码后自动跑一遍，防止回归。
> **3**　①异常类型：`ArrayIndexOutOfBoundsException`——数组下标越界异常。消息 `Index 5 out of bounds for length 5` 表示试图访问索引 5，但数组长度只有 5（有效索引 0~4）。②触发点：`OrderSystem.java` 第 24 行，在 `calcTotal` 方法中。③原因：很可能是循环条件写成了 `i <= arr.length`（第 5 次循环 `i=5` 时越界），应改为 `i < arr.length`。或者是手动访问了 `arr[5]`。④修复：将循环条件从 `<=` 改为 `<`，或将直接索引访问 `arr[5]` 改为 `arr[arr.length - 1]`（取最后一个）。**举一反三**：Stack trace 中消息部分（"Index 5 out of bounds for length 5"）有时比异常类型更有价值——它直接告诉你是"什么值"越界、"上限是多少"。

### 三、代码题（2 道）

1. [基础实现] 下面这段代码有 4 个 Bug（编译错误 + 运行时异常 + 逻辑 Bug + 代码规范问题），请找出全部并逐一修复。修复后的代码应能正确计算并打印 1+2+3+4+5 的累加结果（15）。
```
public class BugFix {
    public static void main(string[] args) {
        int total = 0
        for(int i = 1; i <= 5; i++) {
            totla = i;
        }
        System.Out.println("结果是: " + total);
    }
}
```

2. [综合设计] 写一个"温度转换器 + 自测"程序：用 `assert` 或自己写验证逻辑，对温度转换方法进行边界条件测试。需求：①实现 `c2f(double c)` 和 `f2c(double f)` 方法；②设计一个 `test()` 方法，测试绝对值零度（-273.15°C）、冰点（0°C=32°F）、沸点（100°C=212°F）、相同值（-40°C=-40°F），如果任何一项失败则打印失败位置并计数；③在 `main` 中先调 `test()` 再演示正常转换，体现"测完再用"的安全流程。

> [!答案]
> **1 验收**：
> ```java
> public class BugFix {
>     public static void main(String[] args) {   // 修复1: string → String
>         int total = 0;                         // 修复2: 缺少分号
>         for (int i = 1; i <= 5; i++) {
>             total += i;                        // 修复3: totla → total (拼写)
>                                                // 修复4: = → += (逻辑Bug: 覆盖→累加)
>         }
>         System.out.println("结果是: " + total); // 修复5: Out → out (输出错误)
>     }
> }
> // 输出: 结果是: 15
> ```
> Bug 分类：修复1是编译错误（`string` 小写），修复2是编译错误（缺少分号），修复3是编译错误（变量名 `totla` 拼写错误），修复4是逻辑 Bug（`=`应为`+=`），修复5是编译错误（`System.Out` 应为 `System.out`）。**举一反三**：编译错误优先修——修完一个试着编译一次，有时一个语法错误会掩盖后面多个错误，分批修反而更快。
>
> **2 验收**：
> ```java
> public static double c2f(double c) { return c * 9.0 / 5.0 + 32; }
> public static double f2c(double f) { return (f - 32) * 5.0 / 9.0; }
>
> static int test() {
>     int failures = 0;
>     double tolerance = 0.001;
>
>     // 绝对零度
>     double absC = -273.15;
>     if (Math.abs(c2f(absC) - (-459.67)) > tolerance) {
>         System.out.println("FAIL: 绝对零度转换");
>         failures++;
>     }
>     // 冰点
>     if (Math.abs(c2f(0) - 32) > tolerance) {
>         System.out.println("FAIL: 冰点 C→F");
>         failures++;
>     }
>     if (Math.abs(f2c(32) - 0) > tolerance) {
>         System.out.println("FAIL: 冰点 F→C");
>         failures++;
>     }
>     // 沸点
>     if (Math.abs(c2f(100) - 212) > tolerance) {
>         System.out.println("FAIL: 沸点 C→F");
>         failures++;
>     }
>     if (Math.abs(f2c(212) - 100) > tolerance) {
>         System.out.println("FAIL: 沸点 F→C");
>         failures++;
>     }
>     // -40 相等点
>     if (Math.abs(c2f(-40) - (-40)) > tolerance) {
>         System.out.println("FAIL: -40度 C→F");
>         failures++;
>     }
>     if (Math.abs(f2c(-40) - (-40)) > tolerance) {
>         System.out.println("FAIL: -40度 F→C");
>         failures++;
>     }
>
>     if (failures == 0) {
>         System.out.println("全部测试通过 (7/7)");
>     } else {
>         System.out.println("失败: " + failures + " / 7");
>     }
>     return failures;
> }
>
> public static void main(String[] args) {
>     // 先测
>     int fails = test();
>     if (fails > 0) {
>         System.out.println("测试未通过，请修复！");
>         return; // 不继续执行正常逻辑
>     }
>     // 再用
>     System.out.println("\n正常演示:");
>     System.out.printf("25°C = %.1f°F\n", c2f(25));  // 77.0
>     System.out.printf("98.6°F = %.1f°C\n", f2c(98.6)); // 37.0
> }
> ```
> 运行验证：`test()` 输出"全部测试通过 (7/7)"，然后正常转换演示正确。**举一反三**：注意浮点数比较不能直接用 `==`，要用 `Math.abs(a-b) < epsilon` 容忍微小误差。这本身就是浮点精度 Bug 的预防措施——测试代码也得防 Bug！
