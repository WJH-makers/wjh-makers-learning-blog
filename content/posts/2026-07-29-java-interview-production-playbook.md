# Java 后端面试与生产排障题库：从八股边界到真实事故

![Java 面试与生产排障漫画：从结论到证据](/comics/java/java-interview-production-playbook.png)
> 适用边界：生产项目常见基线是 JDK 17 或 21；本文以 JDK 25 API/语言规范校验新特性。JDK 25 是 LTS，但 Java 26 已是更新的功能版本。回答任何版本题时，先说清「目标 JDK、JVM 实现、框架版本、部署模型」。

> 面试不是背诵比赛。一个合格答案至少包含：**结论、适用边界、失败例子、验证证据、修复取舍**。只报名词或只背阈值，都经不起线上事故。

## 一、五分钟回答模板

面对任何高频题，按这个顺序答：

1. **先给结论**：例如「Java 只有值传递，引用变量传递的是引用值的副本」。
2. **说边界**：例如 `Integer` 缓存、代理类型、隔离级别、JDK 版本会改变细节。
3. **给反例**：用一段最小代码或一次真实故障证明「错误直觉」为什么错。
4. **给证据**：日志、线程栈、JFR、执行计划、指标或并发测试，而不是“我觉得”。
5. **说取舍**：吞吐、延迟、一致性、复杂度与可运维性不能同时最大化。

## 二、Java 核心：中厂重基础、大厂追边界

### 1. Java 是值传递还是引用传递？

**标准答法**：Java 只有值传递。对象变量里的“值”是对象引用；传参时复制这个引用值，因此可以通过副本修改对象状态，却不能让调用方变量改指向另一个对象。

```java
static void rename(StringBuilder x) { x.append("!"); }
static void rebind(StringBuilder x) { x = new StringBuilder("new"); }
```

`rename` 会影响原对象，`rebind` 不会。追问时不要说“传地址”——Java 语言规范并没有 C++ 式引用传参。

**坑**：把可变对象当 `HashMap` key 后再修改参与 `equals/hashCode` 的字段，条目可能仍在表中却再也取不出来。修复是让 key 不可变，或修改前删除、修改后重新放入。

### 2. `==`、`equals`、`hashCode` 怎么答才完整？

- `==` 比较基本类型的值、比较引用时比较对象身份；
- `equals` 是逻辑相等约定；没有重写时继承 `Object` 的身份比较；
- 相等对象必须有相同 `hashCode`，反方向不成立；
- 重写 `equals` 必须同时重写 `hashCode`，否则 `HashMap`/`HashSet` 会出现“明明相等却找不到”的故障。

**上机追问**：写一个 `User(id, name)` 放进 `HashSet`，要求按 `id` 去重；再演示为什么修改 `id` 会破坏集合语义。答出不可变性和业务主键，比背 `Objects.hash` 更重要。

### 3. `BigDecimal` 为什么不能随手 `new BigDecimal(double)`？

二进制浮点数通常不能精确表示十进制 `0.1`。金额优先使用最小货币单位 `long`，或使用 `BigDecimal.valueOf(0.1)` / 字符串构造；金额比较使用 `compareTo`，不要用 `equals` 忽略 scale 差异。

**事故题**：优惠金额经 `double` 计算后出现 `0.30000000000000004`，如何定位？先打印原始值与 scale，再检查构造入口和舍入点；不要只在最终展示时 `format` 掩盖账务误差。

### 4. `HashMap` 为什么不是线程安全的？树化阈值到底是什么？

JDK 8+ 中，碰撞桶在链表节点达到树化阈值时**可能**转为红黑树；还需表容量至少为 64，否则优先扩容。树节点减少到 6 以下时可能退化。阈值不是业务容量规划公式，更不是“超过 8 必然树化”。

**高分追问**：为什么不用 AVL？HashMap 更重视更新和实现代价，红黑树在最坏碰撞下提供对数级查找的折中；但正常设计应先避免低质量 hash、可变 key 和恶意输入碰撞。

### 5. `ArrayList` 与 `LinkedList` 如何按业务选？

不要背“插入 LinkedList 快”。在真实 JVM 中，`ArrayList` 连续内存、缓存局部性好；按下标遍历通常很快。`LinkedList` 的“已拿到节点后 O(1) 插入”很少是业务热路径优势，且对象分配与指针追踪有成本。按访问模式、数据规模和测量结果选择。

## 三、并发：答案必须能写出竞态与验证

### 6. `volatile` 保证什么？为什么 `count++` 仍会丢失？

`volatile` 提供可见性，并约束相关读写的重排序；`count++` 是读、加、写三步，不是原子操作。计数用 `AtomicInteger`/`LongAdder`，复合状态转换用 CAS 循环或锁。

```java
if (stock.get() > 0) stock.decrementAndGet(); // 仍可能扣成负数
```

**正确修复**：CAS 循环中同时判断和更新，或在清晰的临界区内加锁。验证不能只跑一次：用 `CountDownLatch` 对齐大量任务，断言成功数不超过库存。

### 7. `synchronized`、`ReentrantLock`、CAS 怎么选？

| 场景 | 首选 | 原因与边界 |
| --- | --- | --- |
| 简单共享状态 | `synchronized` | 语义清晰，异常自动释放锁 |
| 可中断/可超时/多个条件队列 | `ReentrantLock` | `lockInterruptibly`、`tryLock`、`Condition` 可表达需求 |
| 极短的单变量状态转换 | CAS/原子类 | 避免阻塞；高冲突时会自旋，未必更快 |
| 热点统计 | `LongAdder` | 分段累加吞吐高；求和不是瞬时强一致快照 |

**坑**：不要把“无锁”说成“没有竞争”。CAS 有 ABA、饥饿和高冲突退化问题；需要版本语义时用 `AtomicStampedReference`，或回到锁/数据库条件更新。

### 8. `ConcurrentHashMap` 安全，为什么仍会超卖？

它保证容器单次操作的线程安全，不自动把你的 `get → 判断 → put` 变成一个业务原子操作。使用 `compute`、`merge`、`replace`，或用原子变量/锁把检查与更新合并。多实例时还要把原子性落到数据库条件更新、唯一约束或可靠的分布式协调上。

### 9. 线程池的参数不是面试口诀

`ThreadPoolExecutor` 的决策顺序是：创建核心线程 → 入队 → 创建非核心线程 → 拒绝。无界队列常使 `maximumPoolSize` 形同虚设，并把压力转成 OOM/高延迟；无界请求也不该交给无限虚拟线程。

**生产题**：下游慢 10 倍，如何避免本服务被拖死？给每类任务隔离执行器/并发额度、有限队列、超时和拒绝策略；暴露活跃线程、队列长度、拒绝数、下游延迟；按压测数据定容量，而不是套 CPU 核数公式。

### 10. 虚拟线程什么时候不该用？

虚拟线程适合大量阻塞式 I/O 任务，常见用法是一任务一虚拟线程；它不让 CPU 密集型任务更快，也不能消除数据库连接、HTTP 下游、内存等资源上限。排查 pinning、外部连接池和背压后再扩大并发。JDK 21 起虚拟线程是正式特性；结构化并发/Scoped Values 的可用状态必须按目标 JDK 单独说明。

## 四、JVM：从“会背区”进入证据链

### 11. 线上 CPU 100% 的第一小时怎么做？

1. 确认是进程、容器还是宿主机饱和；记录时间窗和请求特征。
2. 用 `top -H`/容器指标定位热点线程；将线程 ID 转十六进制，与两次 `jstack` 或 `jcmd Thread.print` 对照。
3. 对持续热点采集 JFR；区分死循环、锁竞争、正则灾难性回溯、GC 抖动与下游重试风暴。
4. 先限流/降级止血，后用最小复现和回归测试根治。

**反例**：看到 CPU 高就先 `kill -9`，会丢掉线程栈、JFR、GC 日志和关键现场。

### 12. OOM 不是一个错误，而是一组错误

| 现象 | 优先证据 | 常见根因 |
| --- | --- | --- |
| `Java heap space` | heap dump、对象保留路径 | 缓存无上限、集合累积、重复加载 |
| `Metaspace` | 类加载器与类数 | 热部署/插件 classloader 泄漏 |
| `Direct buffer memory` | NMT/JFR/Netty 指标 | 直接内存未释放、上限过小 |
| `unable to create native thread` | 线程数、cgroup PID/内存限制 | 无界线程、阻塞堆积、容器限制 |

启动前就配置可控的 heap dump 路径与磁盘告警；复盘时用保留路径解释“谁持有谁”，不要只看对象大小排名。

### 13. 类加载的三个阶段与双亲委派的边界

加载、链接（验证/准备/解析）、初始化是不同阶段。常见的 parent-first 委派避免核心类被覆盖；SPI、容器、插件框架会通过线程上下文类加载器或 child-first 策略解决服务发现/隔离，不是“把双亲委派推翻”。

**面试追问**：为什么 `Class.forName` 与 `ClassLoader.loadClass` 表现可能不同？回答要落到是否触发初始化、是否执行静态初始化块，并标明具体 API 重载。

### 14. GC 选型应从 SLO 开始

吞吐优先和低延迟优先不是口号。先收集分配速率、存活集、暂停分位数、CPU/内存预算，再评估 G1、ZGC、Shenandoah 等。GC 参数是实验结果，不是复制线上“神参数”；JDK、堆大小、容器限制和工作负载变化都可能使旧参数失效。

## 五、Spring：代理、事务和启动失败是高频真实题

### 15. `@Transactional` 为什么会“没生效”？

默认代理模式只拦截**经代理进入的外部调用**。同类自调用会绕过代理；`final` 方法不能被 CGLIB 子类覆盖；受检异常默认不回滚。事务方法优先作为 `public` Service 边界，出现问题时打印事务状态、检查代理类型和调用路径，再决定拆分 Service、调整 rollback 规则或使用其他架构。

**重要边界**：`NESTED` 依赖具体 `PlatformTransactionManager` 对保存点的支持；不要把它当跨数据库、跨消息队列的分布式事务方案。

### 16. `REQUIRED`、`REQUIRES_NEW` 的事故题

`REQUIRED` 加入已有事务或新建事务；`REQUIRES_NEW` 挂起外层并新开独立事务。后者可能在连接池很小、外层并发很高时制造连接饥饿。审计日志若必须保存，先明确“日志成功”是否可以掩盖主业务失败；更稳的跨服务方案通常是本地事务写 outbox，再可靠投递。

### 17. Spring Boot 自动配置失败怎么排？

它不是“扫描所有类”。自动配置由 imports 清单导入，再由条件注解决定是否生效。排查顺序：启动条件报告 → 实际 classpath → 配置属性绑定 → 用户自定义 Bean 是否让默认配置退让。不要先删依赖或到处加 `@ComponentScan`。

## 六、数据与分布式：中厂常问落地，大厂继续追一致性

### 18. MySQL 索引与 MVCC 的回答边界

B+ 树索引不是“加了就快”。联合索引按最左前缀、过滤性、排序与回表成本设计；用 `EXPLAIN ANALYZE`（在支持的版本）验证行数估计与真实执行。MVCC 为一致性读提供版本视图；锁定读、隔离级别、索引条件决定锁范围。谈“RR 防幻读”时要区分快照读与当前读/间隙或临键锁，避免绝对化。

### 19. 缓存一致性如何回答？

先选一致性目标。典型 cache-aside：读未命中查库再回填；写库后删缓存，失败重试并配合过期兜底。必须补齐：穿透（空值/布隆过滤器）、击穿（互斥/逻辑过期）、雪崩（TTL 打散/限流）、热 key 和重建放大。分布式锁不是缓存一致性的万能解。

### 20. MQ 至少一次投递，消费者怎样不重复扣款？

以业务唯一键/消息 ID 建幂等记录或唯一约束；处理与状态落库放在本地事务中；失败可重试、超过阈值进死信队列并告警；顺序只在明确分区键内讨论。不要承诺“全链路恰好一次”而没有说明 broker、数据库和外部副作用的边界。

### 四道必须会写的现场题

1. 写一个库存扣减，200 并发下绝不超卖，并解释单机和多实例方案的差别。
2. 给出 CPU 100% 的线程栈和 GC 日志片段，提出证据收集顺序，禁止直接重启。
3. 设计订单创建 + 消息投递，允许最终一致但不得重复扣款。
4. 修复同类自调用导致的事务失效，并说明为什么“换成 `REQUIRES_NEW`”不是自动修复。
