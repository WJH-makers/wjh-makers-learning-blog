# 《从零开始玩命令行》20 · 定时任务与环境变量

> 连载特刊 · 第二部《从零开始玩命令行》第 4 卷「进程与系统」第 4 话
> 长期项目:**把豆豆咖啡站部署上真实服务器**。前作《从零开始学 Java》全 56 话见 [/java](/java)。

## 一、需求:凌晨三点,谁来备份

咖啡站常驻了,豆豆的心思立刻转到数据上:「订单表就是账本。**每天凌晨三点备份一次**,备份文件按日期留档。你要是打算每天定闹钟起来敲命令,我现在就换人。」

阿零连夜写了个 `backup.sh`:`mysqldump` 导出订单库,`tar` 压成带日期的包。手动一跑,`/coffee-lab/srv/backup/` 里整整齐齐躺着 `coffee_2026-10-07.tar.gz`。剩下的问题只有一个:**怎么让服务器自己在三点准时干这件事**——他还不知道,真正的坑不在"定时",而在定时之后。

## 二、漫画 · 按时打卡,颗粒无收

> **〔1〕** 豆豆客串,咖啡豆脑袋敲着桌面:「凌晨的订单数据无价。每天 3 点备份,连跑七天给我看。」
> 阿零拍胸脯,当场手动跑通 `backup.sh`,备份包闪闪发光。阿零:「稳了。」

> **〔2〕** 特米教他 `crontab -e`,阿零抄下五颗星:`30 3 * * * /coffee-lab/srv/coffee/scripts/backup.sh`。
> 阿零(关灯):「服务器,三点半见。」特米(欲言又止):「……嗯,明早见。」

> **〔3〕** 第二天早上,`/coffee-lab/srv/backup/` 空空如也。阿零跳起来:「cron 根本没跑!」
> 特米:「先别喊冤,取证。`grep CRON /coffee-lab/var/log/syslog`——看,03:30:01,**它按时打卡了**。」

> **〔4〕** 阿零当场手动再跑一遍脚本——好好的!备份包唰地出现。
> 阿零:「同一个脚本、同一台机器、同一个用户,凭什么?!」特米肚皮打出两个字:**环境**。

> **〔5〕** 特米展开两张背包:「你的 shell 出门背着 `.bashrc` 塞满的大包,PATH 里什么路都认;cron 叫脚本干活时只发一个小挎包——`PATH=/coffee-lab/usr/bin:/bin`,**不读 .bashrc**。你的 mysqldump 住在 `/coffee-lab/usr/local/mysql/bin`,cron 根本不认识路。」
> 阿零:「所以它不是没跑,是跑了……然后迷路了,还没留遗书?」

> **〔6〕** 特米:「所以无人值守的任务,**先安黑匣子再上天**:输出重定向进日志,一行都别放跑。」
> 特米(冷冷):「记住这案子:手动跑得动 ≠ cron 跑得动。人证(syslog)、物证(日志),缺一个都破不了案。」

## 三、本话目标

- 会用 `crontab -e / -l` 装卸定时任务,读写**五星位**:分 时 日 月 周,`*/5` 每 5 分钟;
- 亲手翻一次本话大车:**手动能跑、cron 不跑**,根因是 cron 的环境 ≠ 登录 shell;
- 掌握两件修法:脚本内**自设 PATH(或全用绝对路径)** + 输出重定向 `>> 日志 2>&1` 留证据;
- 讲透第一性原理:**shell 按 PATH 里目录的顺序找可执行文件**,`export` 是把变量放进子进程的行囊;
- 一句话分清 `.bashrc` 和 `.profile`,并记住:cron 谁都不读。

## 四、原理图:五颗星与两个世界

```text
crontab 一行 = 闹钟(何时)+ 命令(干什么):

 ┌────────── 分 (0-59)
 │  ┌─────── 时 (0-23)
 │  │  ┌──── 日 (1-31)
 │  │  │  ┌─ 月 (1-12)
 │  │  │  │  ┌ 周 (0-7,0 和 7 都是周日)
 30 3  *  *  *   /coffee-lab/srv/coffee/scripts/backup.sh

两个世界的环境(第一性原理:shell 沿 PATH 目录顺序找可执行文件,找不到即报错):

 你的登录 shell                        cron 的世界
 ─────────────────                     ─────────────────
 读 .profile,再读 .bashrc             谁都不读(SHELL=/bin/sh)
 PATH=…:/coffee-lab/usr/bin:/coffee-lab/usr/local/mysql/bin  PATH=/coffee-lab/usr/bin:/bin
 mysqldump → 找得到                    mysqldump → command not found
 输出打在你脸上(终端)                输出试图寄邮件,没装 MTA 就石沉大海
```

一句话:**cron 不是"替你敲命令的你",它是个不读你任何配置、两手空空的陌生人。**

## 五、上手:先把闹钟上好

备份脚本(手动版,先跑通):

```bash
$ cat /coffee-lab/srv/coffee/scripts/backup.sh
#!/bin/bash
mysqldump -u coffee -p"$DB_PASS" coffee_shop > /coffee-lab/srv/backup/coffee_$(date +%F).sql
tar -czf /coffee-lab/srv/backup/coffee_$(date +%F).tar.gz -C /coffee-lab/srv/backup coffee_$(date +%F).sql

$ /coffee-lab/srv/coffee/scripts/backup.sh && ls /coffee-lab/srv/backup/
coffee_2026-10-07.sql  coffee_2026-10-07.tar.gz
```

装进 crontab:

```bash
$ crontab -e                     # 编辑当前用户的任务表(第一次会让你选编辑器)
$ crontab -l                     # 列出确认
30 3 * * * /coffee-lab/srv/coffee/scripts/backup.sh
*/5 * * * * /coffee-lab/srv/coffee/scripts/healthcheck.sh    # */5 = 每 5 分钟一次
```

顺手摸一下环境变量这条线:

```bash
$ echo $PATH
/coffee-lab/usr/local/sbin:/coffee-lab/usr/local/bin:/coffee-lab/usr/sbin:/coffee-lab/usr/bin:/sbin:/bin:/coffee-lab/usr/local/mysql/bin
$ which mysqldump                # which 就是"沿 PATH 找一遍给你看"
/coffee-lab/usr/local/mysql/bin/mysqldump
$ export CAFE_ENV=prod           # export = 放进行囊,子进程才带得走
$ bash -c 'echo $CAFE_ENV'
prod
```

> **特米旁白**:最后那截 `/coffee-lab/usr/local/mysql/bin` 是当年豆豆装官方版 MySQL 时写进 `.bashrc` 的——`export PATH=/coffee-lab/usr/local/mysql/bin:$PATH`。记住这个伏笔,凶手已经登场了。

## 七、读懂真实报错:先让案发现场开口

**第一步,人证**——cron 到底触发了没有?查 syslog:

```bash
$ sudo grep CRON /coffee-lab/var/log/syslog | tail -1
Oct  8 03:30:01 coffee-server CRON[5123]: (azero) CMD (/coffee-lab/srv/coffee/scripts/backup.sh)
```

打卡记录在案:cron **准时跑了**。那输出去哪了?cron 会把任务输出寄给本地邮箱,而这台机器没装邮件服务——证据当场蒸发。所以修的第一刀不是修 Bug,是**装黑匣子**:

```bash
$ sudo touch /coffee-lab/var/log/backup.log && sudo chown azero /coffee-lab/var/log/backup.log
$ crontab -l
30 3 * * * /coffee-lab/srv/coffee/scripts/backup.sh >> /coffee-lab/var/log/backup.log 2>&1
```

排查期还可以临时把五星位改成 `* * * * *`(每分钟),别真等到凌晨。一分钟后,**物证**到手:

```text
/coffee-lab/srv/coffee/scripts/backup.sh: line 2: mysqldump: command not found
tar: coffee_2026-10-08.sql: Cannot stat: No such file or directory
tar: Exiting with failure status due to previous errors
```

根因水落石出:`mysqldump` 装在 `/coffee-lab/usr/local/mysql/bin`,这条路是 `.bashrc` 里 export 进 PATH 的;而 **cron 的环境不是登录 shell**——它不读 `.bashrc`,PATH 只有 `/coffee-lab/usr/bin:/bin`,自然 `command not found`;第一步倒下,后面的 `tar` 跟着连环撞。修法在脚本顶部自设 PATH(或全部写绝对路径):

```bash
#!/bin/bash
export PATH=/coffee-lab/usr/local/mysql/bin:/coffee-lab/usr/bin:/bin
```

顺带立两条规矩:`.profile` 是**登录时读一次**(放环境变量),`.bashrc` 是**每开一个交互式 shell 读一次**(放别名、提示符)——而 cron 两个都不读,别指望。另外,若把 `date +%F` 直接写在 crontab 行里,`%` 必须转义成 `\%`——cron 把裸 `%` 当换行符,这是它的又一个冷门脾气(写进脚本里则不受影响)。

> **🪟 双系统对照 · Windows 的闹钟叫计划任务**

| 干什么 | Linux (bash) | PowerShell 7 / Windows | 关键差异 |
|---|---|---|---|
| 定时任务 | `crontab -e` 写五星位一行文本 | `Register-ScheduledTask` + `New-ScheduledTaskTrigger -Daily -At 3:30am` | cron 是**一行文本**;计划任务是**对象三件套**(触发器/动作/主体)拼装 |
| 列出任务 | `crontab -l` | `Get-ScheduledTask \| Where State -eq Ready` | PS 返回对象,可按属性继续筛 |
| 看变量 | `echo $PATH` | `$env:PATH` | 分隔符 Linux 用 `:`,Windows 用 `;` |
| 永久设变量 | 写进 `~/.profile` | `[Environment]::SetEnvironmentVariable('X','y','User')` | Windows 存注册表,**新开的**终端才生效 |
| 同款大坑 | cron 环境 ≠ 登录 shell | 计划任务默认以 SYSTEM/服务环境跑 ≠ 你的终端 | 两边都会"手动能跑、定时不跑",破案思路完全通用 |

对象 vs 文本的老对比,这回站在 cron 一边说句公道话:一行 `30 3 * * *` 十秒写完;PowerShell 的触发器对象啰嗦,但类型明确、不会把 `%` 当换行——各有各的道理。

> **🎯 面试直击**:脚本手动能跑,放进 cron 就不跑,怎么排查?
> 标准四步:① `grep CRON /coffee-lab/var/log/syslog` 确认到底触发没有;② 给任务加 `>> 日志 2>&1`,让报错落地;③ 想环境差异——cron 不读 `.bashrc`,`PATH=/coffee-lab/usr/bin:/bin`,`HOME`/`SHELL` 也可能不同;④ 修法:脚本自设 PATH 或全用绝对路径。这题是 Linux 面试的保留曲目,答出「cron 环境 ≠ 登录 shell」这句就及格,答出四步就是加分。

### 解答题(5 道)

**Q1 概念:** cron 的五星位(分 时 日 月 周)语义是什么?每列的合法取值范围和特殊符号(`* / - ,`)各代表什么?

**Q4 排障:** 菜菜写了一个 Python 脚本,手动 `python3 /coffee-lab/home/user/backup.py` 运行正常,但 cron 里配置 `0 3 * * * python3 /coffee-lab/home/user/backup.py` 就是不执行。请给出排查清单和解决方案。

**Q5 综合设计:** 设计咖啡站的全套定时任务策略:①数据库备份(每天,保留 30 天) ②日志归档清理(每周) ③SSL 证书过期检查(每天) ④健康检查与告警(每 5 分钟)。要求:每个任务有独立的日志文件、错误告警机制、环境变量管理、以及任务依赖处理(备份完成后才清理旧备份)。

> [!答案]
> **1-B** `crontab -e`=编辑(首次会让你选择编辑器,推荐选 1=nano 或 3=vim.basic),`crontab -l`=列出。**举一反三:**`crontab -r` 删除所有定时任务(危险!);`crontab -u username -e` 编辑指定用户的 crontab(root 用)。🪟 Windows 中用 Task Scheduler(任务计划程序)替代 cron。
>
> **2-B** 五星位:分(0-59) 时(0-23) 日(1-31) 月(1-12) 周(0-7,0 和 7=周日)。`0 2 * * *` = 在分钟=0、小时=2、日/月/周任意(*)时执行 → 每天凌晨 2:00。**举一反三:**记忆:从左到右粒度递减(分→时→日→月→周)。
>
> **3-B** `*/N` 表示"每隔 N"。`*/15 * * * *`=每隔 15 分钟执行(即 0,15,30,45 分时)。**举一反三:**`*/15` 在分钟位=每 15 分钟;在小时位=每 15 小时;在日位=每 15 天。`*/` 语法是 step 写法,等价于 `0,15,30,45`。
>
> **4-B** cron 的环境只包含 `HOME`、`LOGNAME`、`SHELL=/bin/sh`、极简 `PATH`(通常只有 `/coffee-lab/usr/bin:/bin`),没有登录 shell 加载的 `.bashrc`、`.profile`、用户自定义 PATH、JAVA_HOME 等。**举一反三:**这就是 cron 最大的坑——它不是跑你的 shell 环境,是跑一个"空壳"环境。
>
> **5-A** 在脚本开头显式设置 PATH 是最佳实践。**举一反三:**也可以在 crontab 文件顶部加 `PATH=/coffee-lab/usr/local/bin:/coffee-lab/usr/bin:/bin:/coffee-lab/usr/local/sbin:/coffee-lab/usr/sbin` 设置该 crontab 级别的环境变量。同样可以设置 `MAILTO=admin@example.com` 把 cron 输出邮件发到指定地址。
>
> **6-B** `-u username` 指定目标用户(需要 root 或 sudo 权限),`crontab -e` 编辑自己的。**举一反三:**`sudo crontab -u www-data -e` 编辑 www-data 用户的 crontab(Web 应用的定时任务通常应该用服务用户的 crontab)。
>
> **7-B** `0 0 1 1 *` = 分=0,时=0,日=1,月=1,周=* → 1 月 1 日 00:00(元旦)。**举一反三:**日和周同时指定时为"或"关系(不是"且"),如果写 `0 0 1 * 1` 表示"每月 1 号**或**每个周一"都执行——这可能不是你想要的。
>
> **8-B** cron 会将任务的 stdout 和 stderr 通过本地邮件系统发送给 crontab 所有者(`/coffee-lab/var/mail/username`)。**举一反三:**如果不希望收到邮件,在 cron 命令后加 `> /dev/null 2>&1` 或 `&> /dev/null`;更好的做法:把输出重定向到日志文件 `>> /coffee-lab/var/log/backup.log 2>&1`。`mail` 命令查看本地邮件;`sudo apt install postfix` 安装邮件系统。
>
> **9-A** `export` 将变量提升为环境变量,使子进程可以继承。`VAR=value`(无 export)只在当前 shell 脚本中可见,调用的其他程序看不到。**举一反三:**在 cron 脚本中一定要 export 关键变量:`export PATH=...`, `export JAVA_HOME=...`, `export PYTHONPATH=...`。所有被调用的外部程序都需要通过 PATH 找到。
>
> **10-C** 完全不记录日志是最糟糕的做法——问题排查时无法知道 cron 是否执行了、执行结果如何。**举一反三:**最佳实践:将 cron 任务的输出重定向到日志文件(`>> /coffee-lab/var/log/task.log 2>&1`),并设置 logrotate 防止日志无限膨胀。出现异常时,日志是唯一的线索。
>
> **Q1** 五星位格式:分钟(0-59) 小时(0-23) 日(1-31) 月(1-12) 星期(0-7,0 和 7=周日)。特殊符号:`*`=匹配所有值;`,`=列表(如 `1,15,30`);`-`=范围(如 `1-5`=1到5);`/`=步进(如 `*/10`=每10个单位)。**示例:**`0 9-17 * * 1-5`=工作日(周一到周五)每天 9 点到 17 点整点执行;`30 4 * * 0`=每周日凌晨 4:30 执行;`*/5 * * * *`=每 5 分钟执行。**注意:**日和周同时设置非 `*` 时是"或"关系而非"与"。
>
> **Q2** cron 环境差异:①PATH:登录 shell 有完整 PATH(含 `/coffee-lab/usr/local/bin`、用户自定义路径),cron 的 PATH 极简(`/coffee-lab/usr/bin:/bin`) ②shell:登录 shell 通常是 `/bin/bash`,cron 默认用 `/bin/sh`(语法差异、缺少某些功能) ③环境变量:登录 shell 会 source `.bashrc`/`.profile`/`.bash_profile`,cron 不加载任何用户配置,`JAVA_HOME`/`PYTHONPATH` 等变量不存在 ④locale/时区:登录 shell 使用用户设置的 locale 和时区,cron 可能使用系统默认(通常是 `C`/`POSIX` locale,可能导致中文/emoji 处理异常) ⑤当前工作目录:登录后 `pwd`=home,cron 的工作目录可能是 `/` 或用户的 home(取决于实现)。**故障原因:**命令找不到(PATH 问题)→脚本中调用 `java`/`python3`/`node` 等命令失败,且错误信息被邮件吞掉→"看起来没运行"。
>
> **Q3** 命令序列:①`crontab -e` 打开编辑器 ②添加:`0 3 * * * /coffee-lab/home/deploy/scripts/backup-db.sh >> /coffee-lab/var/log/backup-db.log 2>&1`(每天 3:00) ③添加:`0 2 * * * find /coffee-lab/var/log -name "*.log" -mtime +7 -delete >> /coffee-lab/var/log/cleanup.log 2>&1`(每天 2:00,清除 7 天前) ④在备份脚本 `backup-db.sh` 开头写:`#!/bin/bash`、`export PATH=/coffee-lab/usr/local/bin:/coffee-lab/usr/bin:/bin`、`export JAVA_HOME=/coffee-lab/usr/lib/jvm/java-17`、`set -e`(遇错退出) ⑤保存退出 ⑥`crontab -l` 确认 ⑦第二天检查日志文件确认执行成功。**举一反三:**首次配置后等几分钟,检查 `/coffee-lab/var/log/syslog`(grep CRON)确认 cron 守护进程已经调度了任务。
>
> **Q4** 排查清单:①`grep CRON /coffee-lab/var/log/syslog | grep backup` 确认 cron 是否执行了命令(有调度记录才算开始) ②如果调度了,在脚本开头加 `exec &> /tmp/cron_debug.log; set -x` 捕获所有输出和调试信息 ③`which python3`(手动)和脚本输出对比,很可能 cron 找不到 `python3` ④解决:脚本第一行写 `#!/coffee-lab/usr/bin/env python3` 或使用 Python 的绝对路径(如 `which python3` 得到 `/coffee-lab/usr/bin/python3`) ⑤cron 命令改为:使用绝对路径:`0 3 * * * /coffee-lab/usr/bin/python3 /coffee-lab/home/user/backup.py >> /tmp/backup.log 2>&1`。**举一反三:**终极方案——把所有脚本都写成自包含的(绝对路径、export 所有需要的变量、#!/bin/bash 加 set -euxo pipefail),并在 crontab 中用脚本路径而非内联命令。cron 只负责"到点调脚本",脚本内部保证自己能在任何环境下运行。
>
> **Q5** 策略:①数据库备份:`0 3 * * * /coffee-lab/opt/scripts/backup-db.sh >> /coffee-lab/var/log/backup.log 2>&1 && /coffee-lab/opt/scripts/cleanup-old-backups.sh`,备份脚本内设 `find /backups -mtime +30 -delete`(只保留 30 天) ②日志归档:`0 2 * * 0 /coffee-lab/opt/scripts/log-rotate.sh`(每周日凌晨 2 点) ③SSL 检查:`0 9 * * * /coffee-lab/opt/scripts/check-ssl.sh`,脚本用 `openssl s_client` 检查证书剩余天数,<30 天发送告警(邮件/webhook) ④健康检查:`*/5 * * * * /coffee-lab/opt/scripts/health-check.sh`,脚本 curl 各服务 `/health` 端点,失败发送告警并写入日志 ⑤环境变量管理:创建 `/coffee-lab/opt/scripts/env.sh` 集中定义所有环境变量,每个脚本开头 `source /coffee-lab/opt/scripts/env.sh` ⑥日志策略:每个任务独立日志文件,配置 logrotate(`/coffee-lab/etc/logrotate.d/coffee-tasks`)每周轮转、保留 4 周 ⑦告警:关键任务失败时用 `|| /coffee-lab/opt/scripts/alert.sh "备份失败"` 发送通知。**举一反三:**生产环境推荐用 systemd timer 替代 cron(更精确、支持随机延迟避免"惊群效应"、失败后的重试机制、与 systemd 生态统一)。用 `OnCalendar=daily` 等语义化时间描述替代五星位数字。

## 运行前边界、回滚与验证

- **运行前**：示例以 GNU/Linux 的 Bash 为主；先用 `command --help`、`man command` 或发行版文档确认本机版本和参数。不要把教程中的 IP、域名、用户、路径直接复制到生产机器。
- **先确认作用域**：涉及文件、仓库、容器或远端主机时，先运行 `pwd`、`whoami`、`git status`、`docker context show` 或 `ssh -G 主机别名`，确认当前目标；对重要数据先做可恢复备份。
- **完成后验证**：用只读命令确认结果，例如 `ls -la`、`git status`、`systemctl status 服务名`、`docker ps` 或 `curl -fS URL`；失败时停止扩大操作范围，先读报错。
- **权限边界**：先用 `stat`/`ls -ld` 查所有者和现有权限；按最小权限原则修改，避免 `chmod -R 777`。`sudo` 仅用于明确的单条命令，不在不理解的脚本前盲加。
- **远端边界**：首次连接核验主机指纹；传输前先确认目标路径和账号，`rsync` 删除模式必须先加 `--dry-run`。远程改网络或防火墙时保留一个已登录会话和云控制台回退路径。
- **定时任务边界**：cron 环境最小且非交互。先用绝对路径、显式环境变量和可写日志路径；手动执行同一命令并检查日志后再安装任务。
