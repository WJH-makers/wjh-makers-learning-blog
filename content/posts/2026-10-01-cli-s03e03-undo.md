## 一、事故:一句命令,半天工作蒸发

阿零合并完随手 `git reset --hard`,想撤掉刚才一步。回车。工作区瞬间干干净净——连**还没提交的半天改动**都没了。他反复 `ls`、反复 `git status`,只剩一句冰冷的 `working tree clean`。

守卫叹气:「后悔药有三种,你灌错了最猛的一种。今天我把三兄弟摆齐,再教你一根救命稻草——但先说清:**没提交过的东西,连我也未必救得回。**」

## 二、漫画 · 三瓶药与一根稻草

> **〔1〕** 守卫掏出三只药瓶,标签分别是 `checkout`、`reset`、`revert`,颜色从黄到红。
> 守卫:「治的病不同,毒性也不同。灌之前先问:我要动的,是**工作区**、是**分支指针**、还是**已上线的历史**?」

> **〔2〕** 黄瓶 `checkout/restore`:阿零把一个文件改花了,守卫一滴药下去,文件回到上次提交的样子。
> 特米:「它只丢**工作区**里没提交的改动。恢复单个文件的悔棋,轻。」

> **〔3〕** 红瓶 `reset`:守卫演示三档——`--soft` 改动退回暂存区、`--mixed` 退回工作区、`--hard` **连工作区一起抹掉**。
> 守卫:「同一味药,三种剂量。`--hard` 是唯一会**真删你没提交的改动**的档位——你刚才灌的就是它。」

> **〔4〕** 阿零指着 `revert`:「这瓶呢?」守卫:「最温和。它不删历史,而是**再盖一个反向存档点**,把上一次的改动抵消——**已经推给别人的提交,只能用它**。」

> **〔5〕** 阿零想起被清空的工作:「那我那半天……」守卫摇头:「没 `commit` 过,`reflog` 也救不了。」阿零瘫了。
> 守卫:「但如果你 `--hard` 掉的是**提交过的**存档点,那还有救——」

> **〔6〕** 守卫亮出稻草 `git reflog`,一串 `HEAD@{n}` 像脚印一样浮现:每一次 HEAD 移动都留了痕。
> 守卫:「reflog 记着你 HEAD 走过的每一步。找到那颗被丢下的钉子,`reset` 回去,提交就回来了。」

## 三、本话目标

- 分清三种后悔药各**动哪个区**、危险等级如何排序;
- `git checkout -- <file>` / `git restore <file>`:丢工作区改动;
- `git reset --soft / --mixed / --hard`:移动分支指针的三档剂量;
- `git revert`:造反向提交,不改历史,专治"已推送"的提交;
- 用 `git reflog` 从 `reset --hard` 掉的**提交**里救回历史(顺带认清:没提交的救不回)。

---

## 四、原理图:三兄弟各动一个区

```text
                        动工作区   动暂存区   动分支指针   改历史?  危险
git checkout -- f          ✔          ·          ·         否      中(丢未提交改动)
git restore f      (同上,新命令)
git reset --soft H~1       ·          ·          ✔         是      低(改动留暂存区)
git reset --mixed H~1      ·          ✔          ✔         是      中(改动退工作区)
git reset --hard H~1       ✔          ✔          ✔         是      高(未提交改动永久没)
git revert H              (新增一个反向提交,以上都不动)          否      最低(最安全)

一句话:越往下越猛。--hard 是唯一"真删没提交的改动"的档位;
        revert 是唯一"不改历史"的后悔药,公共分支专用。
```

## 五、上手:三兄弟逐个试

先备一段历史:A、B、C 三个提交,C 有 bug。

```bash
$ git log --oneline
dbfd5ce feat: C 改样式(有bug)
356cab4 feat: B 加功能
862241f feat: A 初始
```

**① checkout / restore —— 丢工作区改动**(把某个文件改花了,想还原):

```bash
$ printf 'v3-改坏了\n' > app.txt      # 手滑改花
$ git status -s
 M app.txt
$ git checkout -- app.txt             # 老写法:丢弃工作区改动
# 或等价新写法:
$ git restore app.txt                 # Git 2.23+ 推荐
```

文件回到上次提交的样子。注意:**这一步丢掉的改动没提交过,找不回来**——所以 checkout/restore 也不是完全无害,别对着改了一小时还没提交的文件乱敲。

**② reset 三档 —— 移动分支指针**:

```bash
$ git reset --soft HEAD~1     # 撤销上一次 commit,改动留在暂存区(想改提交信息/重新合并时用)
Unstaged changes after reset: (无,改动在暂存区)

$ git reset HEAD~1            # = --mixed(默认):撤销 commit,改动退回工作区
Unstaged changes after reset:
M	app.txt
```

**③ revert —— 造反向提交,不改历史**(C 已经上线,别人也拉走了,只能这样):

```bash
$ git revert --no-edit HEAD
[main 6f30341] Revert "feat: C 改价格(有bug已上线)"
 1 file changed, 1 insertion(+), 1 deletion(-)

$ git log --oneline
6f30341 Revert "feat: C 改价格(有bug已上线)"   # ← 多了一条反向提交
2b671a5 feat: C 改价格(有bug已上线)            # ← 原提交仍在,历史没被抹
f2a0633 feat: B 加折扣(线上已用)
587ab68 feat: A 初始
```

看清 revert 的哲学:它**不删 C**,而是新盖一个"把 C 的改动倒过来"的存档点。历史完整、可追溯——这正是它能安全用在公共分支的原因。

## 六、故意制造一个 Bug:reset --hard 抹掉未提交的工作

阿零写了个重要新功能,**还没 commit**,顺手 `reset --hard` 想"清爽一下":

```bash
$ printf '重要的新功能-还没提交\n' >> app.txt
$ git status -s
 M app.txt
$ git reset --hard HEAD          # 手滑
HEAD is now at 0c7bf58 feat: C 改样式(有bug)
```

## 七、读懂现象:reflog 能救提交,救不了没提交的

```bash
$ cat app.txt
v3                               # "重要的新功能"那行,没了

$ git status -s                  # 干干净净——也就是说,那半天改动蒸发了
```

**残酷真相**:`reset --hard` 会把工作区强行对齐到目标提交,**没提交过的改动直接丢弃,`reflog` 也救不回**——因为它从没进过 Git 的对象库。这就是漫画里阿零那半天工作回不来的原因。

但如果你 `--hard` 掉的是**提交过的**存档点,reflog 就是救命稻草:

```bash
$ git reflog
0c7bf58 HEAD@{0}: reset: moving to HEAD
0c7bf58 HEAD@{1}: commit: feat: C 改样式(有bug)
356cab4 HEAD@{2}: reset: moving to HEAD~1
ae0c29d HEAD@{3}: commit: feat: C 改样式(有bug)
356cab4 HEAD@{4}: reset: moving to HEAD~1
dbfd5ce HEAD@{5}: commit: feat: C 改样式(有bug)
356cab4 HEAD@{6}: commit: feat: B 加功能
862241f HEAD@{7}: commit (initial): feat: A 初始
```

reflog 记录了 HEAD **走过的每一步**。假如你 `--hard` 掉了 `ae0c29d` 那个提交,只要它在 reflog 里,一句就能捞回来:

```bash
$ git reset --hard ae0c29d       # 或 git reset --hard HEAD@{3}
```

一句护身符:**`reset --hard` 前,先 `git stash` 或先 `commit`**——把没提交的东西存一下,`--hard` 就永远伤不到它。

> **豆豆锐评**:三兄弟里,`revert` 是唯一"对外可用"的后悔药。铁律:**只要提交已经 push 出去、别人可能拉过,就用 `revert`,别用 `reset`**——`reset` 改历史,会把协作者的时间线搅成一团。

## 八、用命令验证:确认停在了对的存档点

```bash
$ git log --oneline -3           # 现在 HEAD 停哪
$ git status                     # 工作区/暂存区是否如预期
$ git reflog | head -5           # 万一撤错,退路还在不在
```

三条都对得上——撤销才算落地。养成习惯:**任何 reset 之后,先 `git log` + `git status` 复查再继续干活。**

> **🪟 双系统对照 · "撤销"在两个世界**

| 想撤的东西 | Git 里(跨系统一致) | 别跟系统的"撤销"搞混 |
|---|---|---|
| 工作区某文件改动 | `git restore f` / `git checkout -- f` | ≠ 编辑器 Ctrl+Z(那是编辑器缓冲,没落盘就没了) |
| 上一次提交 | `git reset --soft/--mixed/--hard HEAD~1` | ≠ PowerShell `rm` 删文件——那要去回收站找 |
| 已推送的提交 | `git revert` | 回收站/Ctrl+Z 都够不着远程 |

Git 的后悔药只管 **Git 跟踪的内容**;文件系统层面的误删(PowerShell `Remove-Item`、Linux `rm`)不归 Git 管,得靠回收站或备份。两码事,别指望 `git` 救 `rm`。

> **🎯 面试直击**:`git reset --soft`、`--mixed`、`--hard` 分别退到哪个区?
> 三档都移动分支指针,区别在**对暂存区和工作区动不动手**:`--soft` 都不动,原改动留在**暂存区**(适合改提交信息、重新组织提交);`--mixed`(默认)清暂存区,改动退回**工作区**;`--hard` 连工作区一起对齐目标提交,**未提交改动永久丢失**。追问点:`reset` 与 `revert` 何时用哪个——本地私有分支用 `reset` 改历史无妨,已 push 的公共提交必须用 `revert`(反向提交、不改历史)。

### 解答题(5 道)

**Q1 概念:** 对比 `checkout --` / `restore`、`reset`(三档)、`revert` 三种后悔方式,分析各自的作用域和"后悔的后悔"可行性。

**Q2 解释:** 用"打草稿纸"比喻解释 `reset --soft`、`--mixed`(默认)、`--hard` 三档的区别。哪种最危险?

**Q3 操作:** 菜菜刚刚 commit 了一个包含 API 密钥的文件 `secret.env`,但还没 push。请写出安全的撤销操作序列:取消 commit、从暂存区移除、加入 `.gitignore`、重新 commit。

**Q4 排障:** 菜菜执行 `git reset --hard HEAD~3`,发现把重要的代码改丢了啊。但他隐约听说过 `git reflog` 能救命。请写出恢复操作的完整步骤。

**Q5 综合设计:** 设计一套"安全后悔操作矩阵":针对①工作区的误改 ②暂存区的误 add ③本地误 commit(未 push) ④已 push 的误 commit ⑤"误 reset --hard 后想再后悔"。列出每种场景的最佳恢复方案和注意事项。

> [!答案]
> **1-B** `--mixed`(reset 默认):①移动 HEAD 指针到目标 ②清空暂存区 ③工作目录中的修改**保留**(但变为 unstaged 状态)。**举一反三:**`git reset HEAD~1` 后,修改仍在你的文件中,只是从"已提交"变回"已修改未暂存"。
>
> **2-B** `--hard` 不仅回退 HEAD,还会**直接覆盖工作目录**,所有未提交的修改将永久消失。**举一反三:**`--hard` 前务必确认工作目录是干净的(`git status`显示干净),或者先用 `git stash` 暂存。但即使误操作,也可以靠 `git reflog` 在一定时间内恢复(30-90天,取决于提交是否"可达")。
>
> **3-B** `revert` 创建新的"反向提交":历史线变为 `A→B→C→revert-C`(完整保留了 C 的存在和撤销事实)。`reset` 回退指针:历史线可能变成 `A→B`(C 消失了)。**选哪个:**已推送的用 revert(不改写公共历史);未推送的可以用 reset(保持历史简洁)。
>
> **4-B** reflog(Reference Log)记录 HEAD 的每次变更:`commit`、`reset`、`checkout`、`merge` 等操作都会留下记录。**举一反三:**reflog 是许多人眼中的 Git 最伟大的安全网——只要操作发生在 30 天内(reflog 保留期),几乎总能通过 `git reflog` 找到并恢复"消失"的提交。
>
> **5-B** `git checkout -- file.txt`(旧命令)或 `git restore file.txt`(新命令):用暂存区或上次 commit 中的版本覆盖工作目录中的文件。**举一反三:**这操作不可逆!如果你改了一个文件但没 commit,执行此命令后修改永久消失。`git restore` 是 Git 2.23+ 推荐的新命令。
>
> **6-B** `--soft`:只移动 HEAD,不动暂存区和工作目录(修改完好)。`--mixed`:移动 HEAD + 清空暂存区,工作目录中有修改。`--hard`:移动 HEAD + 清空暂存区 + 覆盖工作目录(修改全丢)。**举一反三:**记忆:soft 最软(保护最多),hard 最硬(破坏最大)。
>
> **7-C** reflog 记录了 reset 前的 HEAD 位置。`git reflog` 找到被 "reset away" 的提交,然后 `git reset --hard <hash>` 回到那个位置。**举一反三:**`git reflog` 不仅能看到 commit hash,还能看到操作描述(如 `reset: moving to HEAD~2`),方便定位。恢复后如果想保存,立即创建一个分支:`git branch save-point <hash>`。
>
> **8-B** 已经共享到远程的提交,坚决不能用 `reset --force`(会改写历史,其他同事拉取时会出问题)。`revert` 是不改写历史的"撤销"方式,创建新提交来记录"我决定撤销那个错误的提交"——所有人都能安全 pull。**举一反三:**铁律:私有本地未推送→reset 随便用;已推送到公共分支→只能用 revert。🪟 使用 TFS/Azure DevOps 的团队也有类似概念:Rollback changeset。
>
> **9-B** `git restore --staged file.txt` 将文件从暂存区移回工作目录(保留修改),相当于 "取消 git add"。**举一反三:**旧命令:`git reset HEAD file.txt`;新命令:`git restore --staged file.txt`。这是 Git 2.23+ 拆分 checkout 职责的结果,语义更清晰。
>
> **10-D** `git reset --hard` 后的提交确实可达(reachable 通过 reflog),在 reflog 中默认保留 30 天。D 选项说法错误。**举一反三:**reflog 是本地绝密——它存储在 `.git/logs/` 中,`git clone` 或 `git push` 都不会传输 reflog。多台电脑之间的"后悔"需要依赖远程仓库。
>
> **Q1** ①`checkout -- file` / `restore file`:丢弃工作目录中某个文件的未暂存修改→恢复到暂存区/commit 状态。不可恢复,因为没有历史记录。②`reset`:回退 HEAD 指针到过去的某个提交。三档:soft(修改在暂存区)、mixed(修改在工作目录)、hard(修改全丢但可通过 reflog 恢复 30 天内)。③`revert`:创建反向新提交,安全(不改写历史,保留完整记录)。**后悔的后悔:**checkout -- 不可逆;reset 可通过 reflog 逆;revert 是追加提交,天然可逆(再 revert 回来即可)。
>
> **Q2** 比喻:commit 相当于"把草稿纸(暂存区)上的内容誊写到正式本子上"。—— `--soft`:把正式本翻回前几页,但草稿纸上的内容还在(暂存区和 worktree 都不变),可以基于当前修改重写。`--mixed`(默认):翻回正式本,同时清空草稿纸(暂存区),但修改还在桌上(worktree),需要重新 add。`--hard`:翻回正式本,清空草稿纸,桌面的笔墨全部擦掉——回到那个时间点的**完全状态**。**最危险:**`--hard` 会丢失 worktree 修改,但 reflog 仍然可能急救。
>
> **Q3** 操作序列:①`git reset HEAD~1`(撤销 commit,保留修改) ②`git restore --staged secret.env`(从暂存区移除) ③`echo "secret.env" >> .gitignore && git add .gitignore` ④`git commit -m "重新提交(已排除 secret.env)"`。**举一反三:**如果不慎已经 push 含密钥的文件,即使删除后重新提交,密钥仍在历史中!需要:①立即更换密钥 ②用 `git filter-branch` 或 `BFG Repo-Cleaner` 从历史中彻底清除 ③或者将仓库设为 private 并重新评估风险。
>
> **Q4** 恢复步骤:①`git reflog` 查看 HEAD 移动历史,找到 reset 前的条目(看起来像 `abc1234 HEAD@{1}: commit: 完成了核心功能`) ②记下那个 commit hash(如 `abc1234`) ③`git reset --hard abc1234` 回到那个提交 ④`git log --oneline -3` 确认提交回来了 ⑤强烈建议立即创建保护分支:`git branch recovery-point abc1234`。**举一反三:**reflog 的目标是按操作描述找到"reset 前我在哪"。如果 reflog 显示太多条目,用 `git reflog | grep -v "checkout"` 过滤掉切换操作。
>
> **Q5** 安全后悔矩阵:①工作区误改:`git restore file` 恢复单文件;`git checkout .` 恢复所有文件(危险,需确认) ②暂存区误 add:`git restore --staged file` 取消暂存 ③本地误 commit(未 push):`git reset --soft HEAD~1`(保留修改重新提交)或 `git commit --amend`(修改最近提交) ④已 push 误 commit:`git revert HEAD` 创建反向提交推送;绝不能用 reset+force ⑤reset --hard 后悔:`git reflog`→找到目标 hash→`git reset --hard <hash>`。**总原则:**未 push=随便玩;已 push=只用 revert;reflog 是最后的救命稻草。

## 运行前边界、回滚与验证

- **运行前**：示例以 GNU/Linux 的 Bash 为主；先用 `command --help`、`man command` 或发行版文档确认本机版本和参数。不要把教程中的 IP、域名、用户、路径直接复制到生产机器。
- **先确认作用域**：涉及文件、仓库、容器或远端主机时，先运行 `pwd`、`whoami`、`git status`、`docker context show` 或 `ssh -G 主机别名`，确认当前目标；对重要数据先做可恢复备份。
- **完成后验证**：用只读命令确认结果，例如 `ls -la`、`git status`、`systemctl status 服务名`、`docker ps` 或 `curl -fS URL`；失败时停止扩大操作范围，先读报错。
- **删除边界**：`rm`/`Remove-Item` 不会进入回收站。先用 `ls -- 路径` 或 PowerShell 的 `-WhatIf` 预演；避免对变量、通配符或当前目录直接使用递归强制删除。
- **Git 回滚边界**：`reset --hard`、rebase 和强推会改写本地或共享历史。先保存 `git status`/`git log --oneline`，共享分支优先 `git revert`；必须强推时使用 `--force-with-lease` 并与协作者确认。
- **远端边界**：首次连接核验主机指纹；传输前先确认目标路径和账号，`rsync` 删除模式必须先加 `--dry-run`。远程改网络或防火墙时保留一个已登录会话和云控制台回退路径。
