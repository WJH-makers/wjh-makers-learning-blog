# 《从零开始学 Java》42 · 锁与并发:最后一杯,却卖出了三杯

> 连载特刊 · 第五季「服务器战争」第 3 话 · 基线 Java 25(最新 LTS)
> 承接:上一话线程池让几十个工人**同时**出杯。可当他们同时去扣"同一款豆子"的库存,账就乱了。

---

## 一、需求:守住那最后一杯的账

早高峰,招牌款"耶加雪菲"只剩 1 杯。三个顾客几乎同时点单,三个工人线程几乎同时执行 `stock--`。结果:三杯都显示"下单成功",库存变成了 `-2`。豆豆:「这叫**超卖**。不是网络的锅,不是数据库的锅——是你那句看着人畜无害的 `stock--`,在多线程下**根本不是一步完成的**。今天我们把并发最经典的坑挖到底:**竞态条件**和**内存可见性**。」

---

## 二、漫画 · Race 双胞胎抢最后一杯

> **〔1〕** 货架上只剩 1 包耶加雪菲豆。三个工人线程几乎同时探头看货架,**都**看到了那个"1"。
> 三个工人(异口同声):「还有 1 包,够我这单!」

> **〔2〕** 一对穿着相同、跑得飞快的双胞胎"哧溜"钻进画面——**Race 双胞胎**(竞态兄弟)。他们专挑"读一下、算一下、写回去"这种三步动作下手,趁你还没写回,就抢先改掉了值。
> Race 双胞胎(坏笑):「你读的那个『1』,已经是**过期快照**啦~」

> **〔3〕** 三个工人各自默默执行 `1 - 1 = 0`,再各自把 `0` 写回货架。货架显示 `0`,可**三杯都卖出去了**。账面少扣了两次。
> 阿零(冷汗):「每一步单看都对啊……怎么合起来就错了?」

> **〔4〕** 豆豆掏出一把**唯一的钥匙**(锁),往货架上一锁:「想动库存?先抢到这把钥匙。**同一时刻只准一个工人进来**,读—改—写做完、开锁,下一个才准进。」Race 双胞胎被挡在门外,气得跺脚。
> 豆豆(叼豆子):「这就叫**互斥**。`synchronized` 就是这把钥匙。」

> **〔5〕** 阿零又发现个怪事:他改了一个"停业"开关,另一个工人线程却**半天没看见**,还在傻乎乎接单。
> 豆豆:「那是**可见性**问题——每个线程手里都有一份『本地缓存』,你改的是主内存,他读的是他自己的旧副本。这得靠 `volatile` 或锁来同步。JMM 的水,比你想的深。」

## 三、本话目标

- 看懂**竞态条件**:为什么 `stock--` 在多线程下会丢更新;
- 用 `synchronized` / `ReentrantLock` 给临界区上锁,堵住超卖;
- 理解 **JMM 内存模型**:主内存 vs 工作内存、可见性、`happens-before`;
- 分清 `volatile` 能做什么(可见性、禁重排)、不能做什么(不保证原子);
- 知道并发计数还有更轻的解法:`AtomicInteger`。

---

## 四、原理图:一次 `stock--` 其实是三步

```text
stock-- 的真面目(读—改—写,三步,不是一步):
   1. read   把主内存里的 stock 读进本地
   2. modify 本地算 stock - 1
   3. write  把结果写回主内存

单线程:  read1 → modify → write   ✔ 一气呵成
并发无锁: 线程A read(1)          线程B read(1)      ← 两个都读到 1!
          线程A write(0)         线程B write(0)     ← B 覆盖了 A,少扣一次
          结果:卖了 2 杯,库存只减 1  → 超卖

JMM 内存视图:
  ┌── 主内存(所有线程共享)── stock ──┐
  │                                    │
  线程A 工作内存(stock 副本)   线程B 工作内存(stock 副本)
  ← 各改各的副本,不同步就互相看不见对方的修改(可见性问题)
```

两个独立的坑,常被搅在一起:
- **原子性**:`read-modify-write` 三步中途被打断 → 丢更新 → 超卖。`volatile` **管不了**这个,得用锁或原子类。
- **可见性**:一个线程改了共享变量,别的线程用的还是旧副本。`volatile` 和锁**都能**解决。

## 五、代码:超卖的下单逻辑(承接 v4 的 CoffeeService)

第四季的 `CoffeeService.order` 在单线程下一直很正常,搬到并发下就露馅了:

```java
public class CoffeeService {
    // 库存:商品名 -> 剩余杯数(承接第四季,这里简化成内存 Map)
    private final Map<String, Integer> stock = new ConcurrentHashMap<>();

    public boolean order(String name, int qty) {
        int left = stock.get(name);          // 1 read
        if (left >= qty) {                   // 2 check
            stock.put(name, left - qty);     // 3 write  ← 读-判-写,三步不原子!
            System.out.println(Thread.currentThread().getName() + " 卖出 " + qty + ",剩 " + (left - qty));
            return true;
        }
        return false;
    }
}
```

> **豆豆锐评**:很多人以为把 `HashMap` 换成 `ConcurrentHashMap` 就"线程安全"了。**大错**。`ConcurrentHashMap` 只保证**单个** `get`/`put` 各自线程安全;你这里是 `get`→判断→`put` **三个操作的组合**,组合起来照样有竞态。线程安全的容器 ≠ 线程安全的业务逻辑。

## 六、故意制造一个 Bug:100 个工人抢 50 杯

用线程池(上一话的成果)让 100 个线程并发下单,库存只有 50:

```java
var service = new CoffeeService();
service.setStock("耶加雪菲", 50);
var pool = Executors.newFixedThreadPool(16);
var success = new java.util.concurrent.atomic.AtomicInteger();
for (int i = 0; i < 100; i++) {
    pool.execute(() -> { if (service.order("耶加雪菲", 1)) success.incrementAndGet(); });
}
// ... 等待全部结束,打印 success 和最终库存
```

理论上最多成功 50 单、库存刚好 0。跑跑看。

## 七、读懂现象:成功了 50 多单,库存变负数

多跑几次,每次结果还不一样(并发 Bug 的典型特征——**不确定、难复现**):

```text
成功下单:57
最终库存:-7
```

卖超了 7 杯。原因就是第四节那张图:多个线程同时 `read` 到同一个 `left`,各自判断"够",各自写回,**中间的修改互相覆盖**,还有线程在库存已被别人扣光后仍读到旧的正数。这就是**竞态条件(Race Condition)**:结果依赖于线程调度的偶然顺序。

修复——给"读-判-写"这段**临界区**上锁,保证同一时刻只有一个线程能进:

```java
public class CoffeeService {
    private final Map<String, Integer> stock = new ConcurrentHashMap<>();
    private final Object lock = new Object();

    public boolean order(String name, int qty) {
        synchronized (lock) {                // 🔒 整段读-判-写变成不可分割的原子操作
            int left = stock.get(name);
            if (left >= qty) {
                stock.put(name, left - qty);
                return true;
            }
            return false;
        }
    }
}
```

加锁后再跑:**成功恰好 50 单,库存恰好 0**,重复一百遍都一样。

> **豆豆锐评 · 锁要锁在"数据"上,别锁在"方法"上乱锁**
> 三个提醒:① 锁对象要**共享且不变**(用 `final Object lock`,别用会变的 `Integer`、别用 `this` 图省事导致锁粒度过大);② 临界区**越小越好**——只圈住真正竞争的那几行,别把查数据库、发网络请求也锁进去,否则并发直接退化成串行;③ 这只是**单机锁**,一旦部署多个实例,`synchronized` 就管不住跨进程的超卖了——那要靠数据库锁或分布式锁(第六季)。

> **🔀 豆豆的多解台 · 堵住超卖,有几种锁法?**

| 方案 | 写法要点 | 适合什么时候 | 坑 |
|---|---|---|---|
| `synchronized` | `synchronized(lock){…}`,JVM 内置 | 简单临界区,首选 | 不可中断、不能设超时、锁粒度粗 |
| `ReentrantLock` | `lock.lock()` / `finally unlock()` | 要超时(`tryLock`)、可中断、公平锁 | **忘了 `unlock` 会死锁**,必须写 `finally` |
| `AtomicInteger` | `decrementAndGet()` CAS 无锁 | **纯计数**(如扣库存)最轻最快 | 只能护一个变量,复合业务护不住 |
| 数据库乐观锁 | `UPDATE … SET stock=stock-1 WHERE stock>=1` | **多实例部署**、库存在 DB | 靠 DB 行锁,受数据库压力 |

豆豆锐评:**单机纯扣库存 → `AtomicInteger` 最优**(无锁、最快);**含多步业务判断 → `synchronized` 起步,要超时/公平再上 `ReentrantLock`**;**上了多台机器 → 只能靠数据库或分布式锁**,`synchronized` 立刻失效。

> **🎯 面试直击**:`volatile` 能保证线程安全吗?它和 `synchronized`什么区别?
> **不能保证原子性**。`volatile` 只做两件事:①**可见性**——改了立刻刷回主内存、读时强制从主内存拿,别的线程马上看得见;②**禁止指令重排序**(常用于双检锁单例)。但 `i++` 这种复合操作它护不住,照样超卖。所以"停业开关"这种**一写多读的状态位**用 `volatile` 正合适;而**扣库存**这种读-改-写,必须上 `synchronized`/锁/`Atomic`。一句话:`volatile` 管**可见性**,`synchronized` 既管**可见性**又管**原子性(互斥)**。

## 八、用测试钉死:并发下绝不超卖

并发 Bug 最阴险的是"偶尔才复现",所以测试要**高并发反复压**:

```java
import org.junit.jupiter.api.RepeatedTest;
import java.util.concurrent.*;
import static org.junit.jupiter.api.Assertions.*;

class OversellTest {
    @RepeatedTest(20)   // 并发 Bug 靠概率,重复压 20 次逼它现形
    void never_oversell() throws Exception {
        var service = new CoffeeService();
        service.setStock("耶加雪菲", 50);
        var pool = Executors.newFixedThreadPool(16);
        var latch = new CountDownLatch(100);
        var success = new java.util.concurrent.atomic.AtomicInteger();
        for (int i = 0; i < 100; i++) {
            pool.execute(() -> {
                try { if (service.order("耶加雪菲", 1)) success.incrementAndGet(); }
                finally { latch.countDown(); }
            });
        }
        latch.await(3, TimeUnit.SECONDS);
        pool.shutdown();
        assertEquals(50, success.get(), "成功下单数必须恰好等于库存");
        assertEquals(0, service.stockOf("耶加雪菲"), "库存不能为负");
    }
}
```

`@RepeatedTest(20)` 是并发测试的关键姿势:跑一次通过不代表安全,**多跑几十次都稳定通过**,才敢说竞态被真正堵住了。没加锁的版本,这个测试几乎每轮都挂在"成功 57 单"上。

### 一、选择题(10 道)
1. [基础]`synchronized` 修饰实例方法和修饰静态方法的锁对象分别是什么?
- A) 都是 this　B) 实例方法锁 `this`,静态方法锁 `类名.class`(Class 对象)　C) 都是类对象　D) 没有固定锁对象
> [!答案] **1-B**　实例方法=`this`(当前实例),静态方法=`ClassName.class`(JVM 中只有一个)。**举一反三**:两个线程用**不同实例**调用同一个 `synchronized` 实例方法,拿的是不同的 `this` 锁,互斥失效——这是"以为加了锁其实没加"的经典 Bug。

2. [进阶]`volatile` 能做什么,不能做什么?
- A) 能保证原子性,不能保证可见性　B) 能保证**可见性**和**禁止指令重排**,但**不能保证原子性**(如 `i++` 照样有竞态)　C) 能替代 `synchronized`　D) 只用于修饰方法
> [!答案] **2-B**　`volatile` 的作用:①写后立即刷回主内存,读时从主内存拿(可见性);②禁止 JVM/CPU 指令重排序。但 `i++`(读-改-写三步)它护不住——必须用 `synchronized`/`Lock`/`AtomicInteger`。**举一反三**:`volatile` 最适合"一写多读"的状态位,如 `volatile boolean running = true`——一个线程改,其他线程立刻看到。

3. [深入]死锁的四个必要条件中,破坏哪个成本最低?
- A) 互斥(资源不可共享)　B) 持有并等待——一次性申请所有资源,或用 `tryLock` 超时放弃　C) 不可剥夺　D) 循环等待
> [!答案] **3-B**　①互斥是资源本身属性难以改;②持有并等待:程序控制,最容易——一次性获取所有锁,或用 `ReentrantLock.tryLock(timeout)` 拿不到就释放已有的;③不可剥夺:抢占其他线程的锁很危险;④循环等待:按固定顺序加锁成本也不高,但持有并等待最灵活。**举一反三**:`synchronized` 没有 `tryLock` 能力,这也是 `ReentrantLock` 比它灵活的核心原因。

4. [基础]`ConcurrentHashMap` 的"线程安全"范围是什么?
- A) 所有操作组合都线程安全　B) 单个 `get`/`put`/`remove` 操作各自线程安全,但 "get→判断→put" 这种复合操作不保证原子性　C) 只保证读安全　D) 完全等同 `synchronized` 版本的 HashMap
> [!答案] **4-B**　`ConcurrentHashMap` 只保证单个方法(单次 KV 操作)线程安全;复合操作如 `if(map.get(key)==null) map.put(key,value)` 照样有竞态——两个线程可能都读到 null 然后都 put。**举一反三**:需要复合原子操作用 `computeIfAbsent()` 或 `merge()` 等内置原子方法,或外加 `synchronized`。

5. [进阶]`ReentrantLock` 相比 `synchronized` 的三个独有功能?
- A) 没有独有功能　B) `tryLock`(尝试拿锁不阻塞)、可中断(`lockInterruptibly`)、公平锁(`new ReentrantLock(true)`)　C) 性能更好　D) 自动释放锁
> [!答案] **5-B**　①`tryLock()`:拿不到立即返回 false,不阻塞;②`lockInterruptibly()`:等待期间可被中断;③公平锁:按等待时间排队。**举一反三**:代价是必须 `finally {lock.unlock();}`——忘了就是死锁,`synchronized` 自动释放相对更安全。

6. [深入]`AtomicInteger.incrementAndGet()` 底层用什么实现无锁线程安全?
- A) `synchronized`　B) CAS(Compare-And-Swap,比较并交换)——CPU 指令级原子操作,不断重试直到成功　C) `volatile`　D) 数据库锁
> [!答案] **6-B**　CAS 思路:读出当前值→计算新值→用 `compareAndSet(old,new)` 原子地"如果值仍是 old 则替换为 new"→失败则重试。纯 CPU 指令,无上下文切换,轻量高效。**举一反三**:CAS 的 ABA 问题(值从 A→B→A,看似没变)——`AtomicStampedReference` 加版本号解决。

7. [基础]`wait()` 和 `sleep()` 的核心区别?
- A) 完全相同　B) `wait()` 释放锁,需在 `synchronized` 块内调用,由 `notify()`/`notifyAll()` 唤醒;`sleep()` 不释放锁,时间到自动醒　C) `sleep()` 释放锁　D) `wait()` 不释放锁
> [!答案] **7-B**　`wait()`:Object 方法,必须在 `synchronized` 块内调用,调用后**释放锁**进入 WAITING,等待 `notify()` 唤醒;`sleep()`:Thread 静态方法,**不释放锁**,到时间自动苏醒。**举一反三**:`wait()` 常用在"条件不满足时等待"的场景——如生产者消费者中队列满时生产者 wait,消费者消费后 notify 唤醒。

8. [进阶]JMM(Java 内存模型)的 `happens-before` 规则用来解决什么问题?
- A) 代码执行顺序的约定　B) 定义"一个操作的结果对另一个操作**可见**"的保证——有了 happens-before,后一个操作才能看到前一个操作的结果　C) 垃圾回收时机　D) 类加载顺序
> [!答案] **8-B**　`happens-before` 是 JMM 的核心:如果操作 A happens-before 操作 B,则 A 的结果对 B 可见,且 A 在 B 之前执行。常见的 happens-before:①同一个线程内,前面的操作 happens-before 后面;②`unlock` happens-before 后续的 `lock`;③`volatile` 写 happens-before 后续的 volatile 读。**举一反三**:这就是为什么加了 `synchronized` 之后,临界区内的修改对其他拿到同一把锁的线程可见。

9. [深入]`synchronized` 在 JDK 6 之后的锁升级过程是?
- A) 直接重量级锁　B) 偏向锁→轻量级锁(CAS)→重量级锁(OS 互斥量),逐步升级不降级　C) 轻量级→偏向→重量级　D) 没有锁升级
> [!答案] **9-B**　JDK 6 优化:①无竞争→偏向锁(记录线程 ID,同一线程重入不 CAS);②轻度竞争→轻量级锁(CAS 自旋);③重度竞争→重量级锁(系统调用,线程阻塞)。**举一反三**:这就是为什么 `synchronized` 在低竞争下性能已和 `ReentrantLock` 接近——大多数场景直接用 `synchronized` 就够,不需要为"性能"盲目上 Lock。

10. [综合]`synchronized` + `ConcurrentHashMap` 能否保证"扣库存"操作在多线程下不超卖?为什么?
- A) 能,B) 不能——`ConcurrentHashMap` 只保证单次 get/put 安全,"get→判断→put" 的组合操作不原子,必须另加 `synchronized` 锁住整段读-判-写　C) 取决于 JDK 版本　D) 只与数据库有关
> [!答案] **10-B**　线程安全容器 ≠ 线程安全业务。`ConcurrentHashMap` 的单次 `get` 和 `put` 各自线程安全,但它们之间的"判断"步骤不在保护范围内——线程 A 和 B 都 `get` 到 5,都判断够,都 `put` 4,结果扣了两次却只减了 1。必须把整段 `synchronized(lock){get→判→put}` 包起来。**举一反三**:同理,`AtomicInteger` 只保护单个变量,多个 `AtomicInteger` 的组合操作(如"扣 A 余额的同时加 B 余额")也必须加锁。

### 二、解答题(3 道)
1. [概念]用"货架上的最后一杯咖啡"场景,解释:竞态条件是什么?为什么 `stock--` 在多线程下会出错?为什么 `volatile` 救不了它?
> [!答案] **1**　①竞态条件(Race Condition):多个线程同时访问共享数据,最终结果依赖于线程调度的偶然顺序——不确定、难复现。②`stock--` 实际是三步:读主内存→CPU 减 1→写回。线程 A 读完 1 还没写回,线程 B 也读到 1,各自减成 0 写回——卖了两杯库存只减了 1。③`volatile` 能保证"读完写回后别的线程能看见新值"(可见性),但三个线程同时读到旧值 1 这件事它管不了——原子性需要锁或 `AtomicInteger`。**举一反三**:`volatile` 管**看到**,`synchronized` 管**不被插队**——两者解决不同层面的并发问题。

2. [场景]写一个"转账"方法 `transfer(Account from, Account to, int amount)`,要求不发生死锁。描述你的锁策略和为什么不会死锁。
> [!答案] **2**　策略:按锁的固定顺序(`System.identityHashCode` 小的先锁)——`Account first = hashCode(from) < hashCode(to) ? from : to; Account second = first == from ? to : from; synchronized(first){ synchronized(second){ from.debit(amount); to.credit(amount); }}`。**为什么不会死锁**:所有线程都用同一规则决定先后顺序,不会出现"A 持有 from 等 to,B 持有 to 等 from"的交叉等待。**举一反三**:`identityHashCode` 极少数情况会碰撞(对象不同但 hashCode 相同),生产代码用 `ReentrantLock.tryLock(timeout)` 更可靠——拿不到就放弃重试。

3. [综合]从原子性、可见性、有序性三个维度,分析 `synchronized` 和 `volatile + AtomicInteger` 两种方案各自保证什么,分别适用于什么场景。
> [!答案] **3**　①原子性:`synchronized` 全能;`volatile` 不能;`AtomicInteger` 只能保证单个变量操作。②可见性:两者都能——`synchronized` unlock 前刷主存、`volatile` 写即刷。③有序性:`synchronized` 块内可重排但不能逸出;`volatile` 禁止重排。适用场景:纯计数用 `AtomicInteger`(最轻);简单状态标志用 `volatile`;含多步判断/多变量协调用 `synchronized` 或 `ReentrantLock`。**举一反三**:没有万能方案——选择取决于"你保护的是单个变量还是多个变量","是纯数值还是判断逻辑"。多数场景从 `synchronized` 起步,发现性能瓶颈再考虑细化。

### 三、代码题(2 道)
1. [基础]写一个线程安全的计数器:三个线程各加 1000 次,最终结果为 3000。用 `synchronized` 实现。
> [!答案] **1 验收**:
> ```java
> class SafeCounter {
>     private int count = 0;
>     synchronized void increment() { count++; }
>     synchronized int get() { return count; }
> }
> 
> @Test void threeThreads_sumTo3000() throws Exception {
>     var counter = new SafeCounter();
>     var pool = Executors.newFixedThreadPool(3);
>     var latch = new CountDownLatch(3);
>     for (int t = 0; t < 3; t++)
>         pool.execute(() -> { for (int i=0;i<1000;i++) counter.increment(); latch.countDown(); });
>     latch.await(5, TimeUnit.SECONDS);
>     assertEquals(3000, counter.get());
> }
> ```
> **举一反三**:`AtomicInteger` 版本更轻:`incrementAndGet()` 一行替代 `synchronized increment()`——单变量纯计数场景原子类是最优选择。

2. [综合]实现一个死锁场景(线程 A 先锁 account1 再等 account2,线程 B 先锁 account2 再等 account1),然后写出**修复版**(按固定顺序加锁),并用测试验证:修复后 20 次并发转账,A 和 B 的余额总和始终为 200。
> [!答案] **2 验收**:
> ```java
> @Test @RepeatedTest(20)
> void transfer_noDeadlock_sumUnchanged() throws Exception {
>     var a = new Account(100); var b = new Account(100);
>     var pool = Executors.newFixedThreadPool(2);
>     var latch = new CountDownLatch(2);
>     // 按固定顺序: hashCode 小的先锁
>     Runnable transfer = () -> {
>         Account first = System.identityHashCode(a) < System.identityHashCode(b) ? a : b;
>         Account second = first == a ? b : a;
>         synchronized (first) {
>             synchronized (second) {
>                 a.balance -= 10; b.balance += 10;
>             }
>         }
>         latch.countDown();
>     };
>     pool.execute(transfer); pool.execute(transfer);
>     latch.await(2, TimeUnit.SECONDS);
>     assertEquals(200, a.balance + b.balance, "总和始终 200");
> }
> ```
> **举一反三**:`@RepeatedTest(20)` 是并发测试的安全网——跑一次通过不代表无死锁,多跑几十次所有时序都覆盖到才放心。
