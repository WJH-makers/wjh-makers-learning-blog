# 《从零开始玩命令行》14 · 连接云端:remote / push / pull

> 连载特刊 · 第二部《从零开始玩命令行》第 3 卷「Git 时间机」第 4 话(实验话)
> 长期项目:**把豆豆咖啡站部署上真实服务器**。承接上一话:代码只在本机一台机器上,硬盘一坏全没。这一话把咖啡站推上 GitHub。全卷地图见 [/cli](/cli)。

## 一、需求:代码得有个云上的家

上一话阿零明白了:只在本机 `commit` 再多,硬盘一坏就全没,更别提和同学协作。他要把咖啡站推到 **GitHub**——一个所有人都能同步的"约定的中央仓库"。可他 `git push` 第一下就被拒:`Permission denied (publickey)`。

守卫:「上云要过两关。**第一关握手**:证明你是你(ssh key);**第二关礼让**:别人也在推,你得先接住他们的改动,再推自己的。」

## 二、漫画 · 云端的门与桥

> **〔1〕** 天上垂下一座写着 `GitHub` 的云端城堡,吊桥紧闭。阿零 `push`,桥一动不动,门吐出 `Permission denied (publickey)`。
> 守卫:「它不认识你。先造一把**钥匙**。」

> **〔2〕** 阿零 `ssh-keygen`,手里凭空多出一对钥匙:一把**私钥**(揣兜里,谁都不给)、一把**公钥**(挂门上)。
> 特米:「私钥留本机,公钥贴到 GitHub。以后握手,它拿公钥验你的私钥——不用每次输密码。」

> **〔3〕** `git remote add origin` 一声,本机和城堡之间架起一座桥,桥头挂牌 `origin`。
> 守卫:「`origin` 只是这座远程桥的**默认名字**,不是什么魔法。`push` 走这座桥往城堡送,`pull` 走它往回取。」

> **〔4〕** 阿零 `push -u origin main`,代码顺桥而上,城堡亮起 `[new branch]`。他刚要庆祝——
> 特米:「先别乐。你同学刚也往城堡推了一版。」

> **〔5〕** 阿零再推自己的新提交,桥头红灯 `! [rejected]`。他一愣:「刚还好好的!」
> 守卫:「城堡里已经有了你**本地没有**的东西。你硬推会盖掉同学的活——所以门先拦住你。」

> **〔6〕** 守卫指路:先 `git pull` 把同学的改动接回来、和自己的合到一起,再 `push`。红灯转绿,两人的活都在。
> 守卫:「记住这四个字:**push 被拒,先 pull**。这是协作的第一条礼仪。」

## 三、本话目标

- 用 `ssh-keygen` 生成密钥对,配置 GitHub 免密握手;
- `git remote add` / `git clone` 连接远程仓库,认清 `origin` 只是默认名;
- `git push -u` 首推并建立跟踪,`git pull` 取回远程改动;
- 踩一次 `push` 被拒(`rejected` / `non-fast-forward`),用"先 pull 再 push"化解;
- 分清 SSH 与 HTTPS 两种连法,及各自的凭据管理。

## 四、原理图:本地与远程之间

```text
你的电脑(本地仓库)                        GitHub(远程仓库 origin)
─────────────────────────────────        ─────────────────────────
main          你正在提交的分支
origin/main   远程跟踪分支                main
              = 上次 fetch 时             = 远端真正的分支
                远端 main 的快照

  git fetch              ──▶ 只更新本地那份 origin/main,不碰你的 main
  git merge origin/main  ──▶ 把快照合进当前分支
  git pull               ──▶ 上面两步一起做(合的方式是 merge 还是 rebase,看配置)
  git push               ──▶ 把本地 main 推到远端 main

⚠ origin/main 在**你的电脑里**,不在 GitHub 上。
   它的全名是 refs/remotes/origin/main,存在你的 .git/ 里;
   GitHub 上那条分支的全名是 refs/heads/main。
   名字里带 origin,说的是「这是 origin 的镜像」,不是「它住在 origin」。
   所以你能在断网时 git log origin/main —— 看的是上次同步留下的快照。

push 被拒的根因:远端 main 有你本地没有的提交(fast-forward 不成立)。
解法:先 git fetch 看清远端到底多了什么,再 merge 或 rebase,然后再 push。
```

## 五、实验:配钥匙、连远程、推上云

**① 生成 ssh key**(有了就跳过):

```bash
$ ssh-keygen -t ed25519 -C "azero@example.com"
Generating public/private ed25519 key pair.
Your identification has been saved in /coffee-lab/home/ubuntu/.ssh/id_ed25519
Your public key has been saved in /coffee-lab/home/ubuntu/.ssh/id_ed25519.pub
The key fingerprint is:
SHA256:+478qxpWtOD9yLXO5CzXe4xHkwOfQ43/c7tTpVO6b60 azero@example.com

$ cat ~/.ssh/id_ed25519.pub          # 复制这一整行,贴到 GitHub → Settings → SSH keys
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIAtjplUTSOc3O2njCRg7w+K7uZtf4GHnQOHazJlP/Zkb azero@example.com

$ ssh -T git@github.com              # 验握手
Hi example-user! You've successfully authenticated, but GitHub does not provide shell access.
```

> **特米旁白**:`-t ed25519` 是现在推荐的密钥类型(比老的 RSA 短、快、安全)。私钥 `id_ed25519` **永远不外传**,贴到 GitHub 的只有 `.pub` 那把公钥。

**② 连远程 + 首推**:

```bash
$ git remote add origin git@github.com:example-org/coffee-shop.git
$ git remote -v
origin	git@github.com:example-org/coffee-shop.git (fetch)
origin	git@github.com:example-org/coffee-shop.git (push)

$ git push -u origin main            # -u:首推并建立 main→origin/main 跟踪
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

`-u` 建立跟踪后,以后在这条分支上 `git push` / `git pull` 都不用再写 `origin main`。别人已有的项目则用 `git clone git@github.com:...` 一步克隆(自带 origin 和全部历史)。

## 七、读懂现象:rejected,因为你落后了

```text
To github.com:example-org/coffee-shop.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:example-org/coffee-shop.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
```

读懂它:`remote contains work that you do not have locally`——**远程有你本地没有的提交**(同学那条)。Git 拦住你,是怕你的 push 盖掉同学的活。**千万别用 `git push -f` 硬推**——那会真的覆盖掉同学的提交。正解就是 hint 最后那句:**先 pull**。

```bash
$ git pull --no-ff origin main       # 取回远程改动并合并(生成一个合并提交)
From github.com:example-org/coffee-shop
 * branch            main       -> FETCH_HEAD
Merge made by the 'ort' strategy.
 readme.md | 1 +
 1 file changed, 1 insertion(+)

$ git push origin main               # 再推,这次两人的活都在
   85d0ed2..e93f3f1  main -> main
```

> **豆豆锐评**:`git pull` = `git fetch`(把远程改动**取到本地**)+ `git merge`(**合进当前分支**)。新版 Git 遇到分叉会让你**明确选**合并方式(`--no-ff` 合并 / `--rebase` 变基),别嫌它啰嗦——它在逼你想清楚"我要的历史长什么样",而不是稀里糊涂搅一团。

## 八、用命令验证:本地和远程对齐了吗

```bash
$ git log --oneline --graph
*   e93f3f1 Merge branch 'main' of github.com:example-org/coffee-shop
|\
| * 85d0ed2 docs: 同事写了说明
* | 3e9ba35 feat: 我加了菜单
|/
* c9a4308 feat: 初始

$ git status
On branch main
Your branch is up to date with 'origin/main'.
nothing to commit, working tree clean
```

`up to date with 'origin/main'` + push 那行显示 `main -> main` 成功——本地和云端对齐,协作闭环成立。

> **🪟 双系统对照 · 凭据管理(本卷唯一的真差异)**

| 环节 | Linux / Git Bash | Windows / PowerShell 7 |
|---|---|---|
| ssh key 存哪 | `~/.ssh/id_ed25519` | `~\.ssh\id_ed25519`(`~` 同样指向它) |
| ssh-agent 记私钥 | `eval $(ssh-agent); ssh-add ~/.ssh/id_ed25519` | 用系统服务:`Start-Service ssh-agent; ssh-add` |
| HTTPS 方式记密码 | `git config --global credential.helper cache`(内存缓存) | **Git Credential Manager**——首次弹窗登录,之后存进 Windows 凭据管理器 |
| 命令本身 | `git push` / `git pull` | **完全一样** |

`git push/pull/clone/remote` 命令跨系统零差异;**唯一分岔在"密钥/密码存在哪、谁来记"**。SSH 走 `~/.ssh` 密钥(两系统同构),HTTPS 走凭据助手(Windows 上是图形化的 Credential Manager,Linux 上多用 `cache`/`store`)。推荐统一用 SSH,一次配置,两端一致。

> **🎯 面试直击**:`git fetch` 和 `git pull` 有什么区别?
> `git fetch` 只把远程的提交**下载到本地**(更新 `origin/main` 这类远程跟踪分支),**不动你的工作区和当前分支**,你可以先 `git log origin/main` 审一眼再决定合不合;`git pull` = `fetch` + `merge`(或 `rebase`),**下载并立刻合进当前分支**。追问点:push 被拒(non-fast-forward)为什么发生、为什么不能 `push -f`——远程有你没有的提交,强推会覆盖他人工作,正解是先 `pull` 纳入再 `push`。

### 解答题(5 道)

**Q1 概念:** `remote`、`fetch`、`pull`、`push` 四个概念如何配合实现"本地↔远程"的同步协作?

**Q2 解释:** 为什么 `git push` 被拒时应"先 pull 再 push",而不是 `push --force`?说明 force push 的风险。

**Q3 操作:** 写出将本地已有仓库关联到 GitHub 并完成首次推送的完整命令序列(含 SSH key 配置前的准备步骤)。

**Q4 排障:** 菜菜 `git push` 时报 `fatal: No configured push destination`,诊断原因并给出两种解决方案。

**Q5 综合设计:** 为咖啡站团队设计一套日常 Git 协作工作流:早上开始工作前的同步步骤、开发过程中的 commit 习惯、push 前的安全检查、冲突处理协议。确保不会覆盖同事的代码。

> [!答案]
> **1-B** `git clone` 下载远程仓库的**完整副本**(含所有分支、提交历史)到本地。**举一反三:**`git clone --depth 1` 浅克隆(只拿最近一次提交),适用于只需最新代码不用完整历史的场景。🪟 `git clone` 在 Windows 上同样工作,无需额外配置。
>
> **2-B** `origin` 是远程仓库 URL 的本地别名/简称,约定俗成命名为 `origin`(可以改成其他名字,如 `upstream`、`github`)。**举一反三:**一个本地仓库可以有多个 remote:`git remote add upstream https://...`(原始仓库)、`git remote add origin https://...`(自己 fork 的仓库)。`git remote -v` 查看所有 remote。
>
> **3-B** `-u` = `--set-upstream`,关联本地分支与远程分支,之后直接 `git push` 或 `git pull` 即可,不再需要指定 remote 和分支名。**举一反三:**`git branch -vv` 可以看到每个本地分支跟踪的远程分支。`-u` 只需要在第一次 push 时使用。
>
> **4-C** `git pull` = `git fetch`(从远程下载最新数据) + `git merge`(合并到当前本地分支)。**举一反三:**`git pull --rebase` = fetch + rebase(而非 merge),可以得到更线性的历史。当你想看远程有什么更新但先不合并时,分开用 `git fetch` 再看 `git log origin/main`。
>
> **5-B** push 被拒的典型错误:`Updates were rejected because the remote contains work that you do not have locally.` 意思是"你不在最新代码上,你 push 会覆盖别人的更新"。**举一反三:**这是 Git 的**安全机制**——它在保护你不会不小心覆盖团队成员的提交。
>
> **6-B** `fetch`=下载远程数据到 `origin/main`(本地远程跟踪分支),不影响你当前的工作分支。`pull`=fetch + merge/rebase,直接更新你当前的工作分支。**举一反三:**安全做法:想看看远程更新了什么用 fetch;准备好合并了再用 pull。`git fetch` 永远不会破坏你的本地修改。
>
> **7-B** 标准流程:①`git pull` 拉取并合并远程最新提交 ②如果自动合并成功,直接 `git push` ③如果有冲突,解决冲突→`git add`→`git commit`→`git push`。**举一反三:**也可以用 `git pull --rebase` 然后 `git push`,这样历史更线性。无论哪种,核心都是"先拿到最新的,再提交你的"。
>
> **8-B** 设置 upstream 后,在对应分支上 `git push` 即可自动推到关联的远程分支。**举一反三:**`git push` 默认只推送"有上游跟踪"的分支;`git push --all origin` 推送所有分支。
>
> **9-B** HTTPS:每次操作需认证(用户名+密码/Personal Access Token)。SSH:一次性配置密钥对(ssh-keygen),之后免密操作。**举一反三:**GitHub 已经从 2021 年起不再支持 HTTPS 密码认证,必须用 Personal Access Token(PAT)。推荐使用 SSH——`ssh-keygen -t ed25519 -C "email"` 并把公钥添加到 GitHub Settings。
>
> **10-C** `--force` 直接用本地历史**覆盖**远程分支,如果有其他人在远程推了新提交,那些提交会被**永久删除**。**举一反三:**`--force-with-lease`(Git 2.22+)是 force push 的安全版本——如果远程在你上次 fetch 后有新提交,它会拒绝 force push。永远用 `--force-with-lease` 替代裸 `--force`。
>
> **Q1** ①`remote`(远程仓库 URL 的本地别名):定义"远方在哪"。用 `git remote add origin URL` 建立连接。②`fetch`(只下载不合并):把远程的新数据拉到本地远程跟踪分支(`origin/main`),让你看到"别人做了什么"但不影响当前工作。③`pull`(下载+合并):fetch+merge,把远程更新直接合并到当前分支。④`push`(推送):把本地提交上传到远程,分享给团队。**协作循环:**pull(拿最新)→commit(本地改)→pull again(合并别人改)→push(分享)。
>
> **Q2** `push --force` 的危险:假设你本地有提交(A→B→C),远程已经有同事的提交(A→D→E)。force push 会用你的(A→B→C)覆盖远程,同事的(D→E)从历史上消失,这就是"抹掉别人的代码"——团队管理员的噩梦。**正确做法:**`git pull` 拉取远程(A→D→E),合并成本地(A→D→E→B→C),然后 `git push`(A→D→E→B→C),所有历史完整保留。**例外:**只有你知道自己在做什么且确认远程分支只属于你一个人时,才偶尔用 `--force-with-lease`。
>
> **Q3** 命令序列:①`ssh-keygen -t ed25519 -C "your_email@example.com"` 生成 SSH 密钥 ②`cat ~/.ssh/id_ed25519.pub` 复制公钥→添加到 GitHub Settings→SSH Keys ③在 GitHub 创建空仓库(不勾选 README) ④本地:`git init && git add . && git commit -m "初始提交"` ⑤`git remote add origin git@github.com:user/repo.git` ⑥`git push -u origin main`(初次推送)。**举一反三:**`git remote -v` 验证 remote 配置正确;如果远程仓库已有 README/LICENSE,先用 `git pull origin main --allow-unrelated-histories`。
>
> **Q4** 原因:当前仓库没有配置远程仓库(remote)。**解决方案一:**添加远程仓库:`git remote add origin <URL>` 然后 `git push -u origin main`。**解决方案二:**如果是从远程 clone 的仓库不会有此问题;如果是新初始化的本地仓库,必须手动添加 remote。**检查:**`git remote -v` 查看当前配置的远程列表;如果输出为空,说明没有任何 remote 配置。
>
> **Q5** 日常工作流:①**早上同步:**`git switch main`→`git pull origin main`(获取最新代码)→`git switch -c feature/today-task`(创建今日分支) ②**开发中:**小步 commit(每完成一个小功能点就 commit,commit 信息写清楚改了什么)→不要一个 commit 改所有文件 ③**push 前安全检查:**`git status`→`git diff`→`git switch main`→`git pull origin main`(再次同步)→`git switch feature/xxx`→`git merge main`(把最新 main 合并到功能分支)→解决冲突→跑测试→`git push -u origin feature/xxx`→创建 Pull Request ④**冲突协议:**发现冲突不要慌→理解为什么冲突(同一行被两人改了)→沟通:与冲突作者讨论谁该保留→本地解决→测试→push。**核心原则:**永远先 pull 再 push;永远不用 force push 到 main。

## 运行前边界、回滚与验证

- **运行前**：示例以 GNU/Linux 的 Bash 为主；先用 `command --help`、`man command` 或发行版文档确认本机版本和参数。不要把教程中的 IP、域名、用户、路径直接复制到生产机器。
- **先确认作用域**：涉及文件、仓库、容器或远端主机时，先运行 `pwd`、`whoami`、`git status`、`docker context show` 或 `ssh -G 主机别名`，确认当前目标；对重要数据先做可恢复备份。
- **完成后验证**：用只读命令确认结果，例如 `ls -la`、`git status`、`systemctl status 服务名`、`docker ps` 或 `curl -fS URL`；失败时停止扩大操作范围，先读报错。
- **Git 回滚边界**：`reset --hard`、rebase 和强推会改写本地或共享历史。先保存 `git status`/`git log --oneline`，共享分支优先 `git revert`；必须强推时使用 `--force-with-lease` 并与协作者确认。
- **远端边界**：首次连接核验主机指纹；传输前先确认目标路径和账号，`rsync` 删除模式必须先加 `--dry-run`。远程改网络或防火墙时保留一个已登录会话和云控制台回退路径。
