# 《从零开始玩命令行》15 · rebase 与整洁历史

> 连载特刊 · 第二部《从零开始玩命令行》第 3 卷「Git 时间机」第 5 话
> 长期项目:**把豆豆咖啡站部署上真实服务器**。承接上一话:历史里满是自动合并提交,像一团麻花。这一话学会把它捋直。全卷地图见 [/cli](/cli)。

## 一、需求:让历史排成一条干净的直线

阿零 review 自己的 `git log --graph`,一堆 `|\ |/` 菱形和 `Merge branch` 提交,根本看不出功能是怎么长出来的。他还有个坏习惯:一个功能拆成 `wip: 写一半`、`wip: 又写一点`、`fix: 打错字` 三个凌乱提交,推上去被同学吐槽"日志像流水账"。

守卫:「`merge` 忠实记录'何时分叉、何时汇合';`rebase` 换个思路——**把你的提交搬到目标分支最新处,假装从没分叉过**,历史变一条直线。但它有代价,也有一条不能碰的红线。」

---

## 二、漫画 · 重排钉子的沙漏

> **〔1〕** 守卫指着阿零那团菱形历史:「这是 `merge` 的诚实——它把'两条线合过'如实钉下。」
> 阿零:「可我只想要一条直线。」

> **〔2〕** 守卫沙漏一转,把支线上的钉子**逐颗拔起、挪到主线尖端之后**重钉,菱形塌成一条直线。
> 守卫:「这就是 `rebase`。你的提交没消失,只是**换了'父亲'、重排了顺序**——注意,哈希全变了,是**新的钉子**。」

> **〔3〕** 阿零又想收拾那三个 `wip`。守卫展开一张 `todo` 清单:每行一个 `pick`。
> 特米:「交互式 rebase。把后两个 `pick` 改成 `squash`,三个提交就揉成一个,提交信息你重写。」

> **〔4〕** 三个 wip "啪"地并成一颗干净的钉子 `feat: 报表功能`。阿零:「清爽多了!」
> 守卫:「本地这么收拾,随便。但——」沙漏突然变红。

> **〔5〕** 阿零手一快,对**已经 push 出去的分支**也 rebase 了,再推——`! [rejected]`。他 `push -f` 硬怼上去。
> 守卫脸色骤变:「你把公共历史**换成了新钉子**!同学基于旧钉子的活,全对不上了。」

> **〔6〕** 云端另一头,同学的仓库一片混乱,提交重复、冲突四起。守卫钉下最后一条铁律。
> 守卫:「**公共分支,永不 rebase。** 只在没推出去、只有你自己的本地分支上变基。」

## 三、本话目标

- 讲清 `merge` 与 `rebase` 的本质区别与各自适用场景;
- `git rebase <base>`:把当前分支的提交搬到目标分支之后,得直线历史;
- `git rebase -i`:交互式变基,用 `squash` 把凌乱提交揉成一个;
- 理解 rebase **重写哈希**的代价;
- 踩一次"rebase 已推送的公共分支"大坑,立下"公共分支不 rebase"铁律。

## 四、原理图:merge 保形,rebase 改形

```text
分叉现状:
  * 主线加了登录        (main)
  | * 报表导出          (feature,基于旧的"基础")
  | * 报表骨架
  |/
  * 基础

── merge main → feature:保留分叉,多一个合并提交(菱形)
── rebase main:把 feature 的两个提交"搬"到 main 尖端之后,变直线 ↓

  * 报表导出            ← 新哈希(内容同,父亲变了)
  * 报表骨架            ← 新哈希
  * 主线加了登录
  * 基础

代价:rebase 后的提交是"重写"出来的新对象,旧哈希作废。
      → 若这些旧提交已被别人拉走,灾难。
```

## 五、上手:rebase 捋直 + 交互式收拾

**① 普通 rebase,把分叉捋成直线**:

```bash
$ git log --oneline --graph --all      # 分叉现状
* 41378c7 feat: 主线加了登录
| * d78ea2f feat: 报表导出
| * 2b0e934 feat: 报表骨架
|/
* 17dbf6e feat: 基础

$ git switch feature/report
$ git rebase main                      # 把 feature 的提交搬到 main 之后
Successfully rebased and updated refs/heads/feature/report.

$ git log --oneline --graph --all      # 变直线了
* 16021d9 feat: 报表导出              ← 注意哈希变了(原 d78ea2f)
* da8e2be feat: 报表骨架              ← 原 2b0e934
* 41378c7 feat: 主线加了登录
* 17dbf6e feat: 基础
```

**② 交互式 rebase,把三个 wip 揉成一个**:

```bash
$ git log --oneline
0912187 fix: 打错字
4a7e2b7 wip: 又写一点
e74953a wip: 写一半
5dc8577 feat: 基础

$ git rebase -i HEAD~3                  # 收拾最近 3 个提交
```

弹出的 `todo` 清单长这样(改它来指挥变基):

```text
pick e74953a wip: 写一半
pick 4a7e2b7 wip: 又写一点
pick 0912187 fix: 打错字

# Commands:
# p, pick   = 保留该提交
# s, squash = 合并进上一个提交(保留两者信息,让你编辑)
# f, fixup  = 像 squash 但丢弃本提交信息
# r, reword = 只改提交信息
# d, drop   = 删掉该提交
```

把后两行的 `pick` 改成 `squash`,保存退出,Git 让你重写合并后的信息:

```text
pick   e74953a wip: 写一半
squash 4a7e2b7 wip: 又写一点
squash 0912187 fix: 打错字
```

结果:

```bash
Successfully rebased and updated refs/heads/main.
$ git log --oneline
122a12c feat: 报表功能(合并3个wip)     ← 三个 wip 揉成一个干净提交
5dc8577 feat: 基础
```

> **🔀 特米的多解台 · 想合并两条分支,merge 还是 rebase?**

| 方式 | 历史长相 | 适合什么时候 | 坑 |
|---|---|---|---|
| `git merge` | 保留分叉,多一个合并提交 | 公共/长期分支、想留下"何时合过"的真相 | 图谱有菱形,`log` 略乱 |
| `git rebase` | 一条直线,像没分叉过 | **自己的本地私有分支**、提交推送前的整理 | **重写哈希**,推过的绝不能 rebase |

特米锐评:**默认原则——"本地未推送就 rebase 整理,已推送/公共就 merge。"** 想要直线历史又要安全,团队里常用 `git pull --rebase` 拉取自己分支,合入主线时用 merge(或平台的 squash merge)。

## 六、故意制造一个 Bug:rebase 了已经推送的分支

阿零把已经 `push` 出去、同学也拉过的 `feature/report` 又 rebase 了一遍(哈希全变),再推:

```bash
$ git rebase main                       # 分支早已 push,同学也基于旧提交在干活
$ git push origin feature/report
```

## 七、读懂现象:rejected,而 force push 是毒药

```text
 ! [rejected]        feature/report -> feature/report (non-fast-forward)
error: failed to push some refs to '...'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart.
```

它被拒是因为你本地这条分支的提交**和远程对不上了**(你 rebase 重写了哈希,远程还是旧的)。**新手此刻最容易犯的致命错**是 `git push --force` 强推上去——

```bash
$ git push --force origin feature/report   # 【危险!别学】
```

后果:远程的旧提交被你的新提交**覆盖**。同学本地还基于**旧哈希**在干活,他一 `pull`,历史对不上、提交重复、冲突四起——你把整条公共时间线搅烂了。补救只能是全组停工、对齐历史,代价极高。

**铁律(背下来)**:**只在"没推出去、只有你一个人"的本地分支上 rebase。任何别人可能已经拉过的分支,永远用 merge/revert,绝不 rebase + force。** 万一真必须改已推送的分支(极少数情况),也要用 `--force-with-lease`(它会先检查远程没被别人动过)而非裸 `--force`,并提前通知全组。

> **守卫锐评**:`git push --force` 是新手杀伤力最大的一条命令。判断口诀:**push 前问一句"这分支别人拉过吗?"——只要答案不是斩钉截铁的'没有',就别 force。**

## 八、用命令验证:直线历史 + 分支状态

```bash
$ git log --oneline --graph          # 确认是不是一条直线,没有意外菱形
$ git status                         # 分支和远程是否一致
$ git rebase --abort                 # 万一 rebase 中途冲突搞乱了,一键回到 rebase 前
```

rebase 中途若遇冲突,流程和 merge 冲突一样:改文件 → `git add` → `git rebase --continue`;想放弃就 `git rebase --abort`,毫发无损回到起点。

> **🪟 双系统对照 · CRLF/LF 换行:rebase 假冲突的元凶**

| 现象 | 根因 | 处理(跨系统一致) |
|---|---|---|
| Windows 上 `git add` 报 `warning: LF will be replaced by CRLF` | Windows 换行是 `CRLF`,Linux 是 `LF`,`core.autocrlf` 在转换 | 团队统一:仓库根放 `.gitattributes` 写 `* text=auto eol=lf` |
| rebase/合并时整个文件"全变了、满屏冲突" | 两端换行不一致,Git 以为每行都改了 | 根治靠 `.gitattributes` 锁死换行,而非各改各的 `autocrlf` |
| 查看当前设置 | — | `git config core.autocrlf`(Windows 常为 `true`,Linux 常为 `false`) |

`git rebase` 命令本身跨系统零差异;真正会在 rebase/merge 时坑到跨平台协作的,是**换行符**——Windows 存 `CRLF`、Linux 存 `LF`,不统一就会冒出"整文件假冲突"。**最佳实践:仓库根提交一个 `.gitattributes`,用 `* text=auto eol=lf` 让 Git 统一按 LF 存,谁的机器都不再犯这毛病。**

> **🎯 面试直击**:`git merge` 和 `git rebase` 到底怎么选?
> `merge` 合并两条历史、生成一个有两个父亲的**合并提交**,保留真实分叉形状、不改哈希;`rebase` 把你的提交**搬到目标分支最新提交之后重放**,历史成一条直线、更干净,但**改写了提交哈希**。选择铁律:**公共分支(别人也在用的)只 merge 不 rebase**,以免打乱他人历史;自己没推送的本地分支可以 rebase 让历史整洁。追问点:交互式 rebase 的 `squash`/`fixup`/`reword` 各干嘛,以及 `--force` 与 `--force-with-lease` 的安全差别。

### 选择题(10 道)

1. `git rebase main`(在 feature 分支上执行)做了什么?
   - A) 删除 main 分支　B) 将 feature 分支的提交"搬"到 main 分支的最新提交之后(变基)　C) 合并 main 到 feature　D) 回退到 main 的状态

2. merge 和 rebase 的区别,以下哪种描述最准确?
   - A) merge 一定比 rebase 好　B) rebase 一定比 merge 好　C) merge 产生合并提交保留分支历史,rebase 重写历史使提交线更线性　D) 两者结果完全相同,只是命令不同

3. "公共分支,绝不 rebase"这条铁律的原因是什么?
   - A) rebase 太慢　B) rebase 会改变提交 ID(哈希),其他人基于旧 ID 在工作的会出问题　C) rebase 有 bug　D) rebase 只能用于 main 分支

4. 交互式 rebase(`git rebase -i`)可以做什么?
   - A) 只改变提交顺序　B) 合并(squash)、重排、重写多个提交信息、删除提交等　C) 只删除提交　D) 只修改最近一个提交

5. 在交互式 rebase 中,`squash` 指令的作用是什么?
   - A) 删除这个提交　B) 将这个提交与前一个提交合并,并保留两个提交信息　C) 跳过这个提交　D) 重新排列提交顺序

6. 为什么 `rebase` 后通常需要 `push --force`?
   - A) 这是 bug,不应该 force push　B) rebase 重写了本地提交的 ID,与远程历史不一致,必须 force push 覆盖　C) rebase 需要更多权限　D) 不需要,正常 push 即可

7. `squash` 和 `fixup` 的区别是什么?
   - A) 完全一样　B) squash 保留被合并提交的提交信息(让你编辑),fixup 丢弃被合并提交的信息(只保留前一个)　C) fixup 会删除文件　D) squash 只能用于远程分支

8. 你正在 feature 分支上开发,突然发现 main 更新了不少内容。以下哪种同步操作最**不可能**引起问题?
   - A) `git merge main`(在 feature 上合并 main)　B) `git rebase main`(在 feature 上变基到 main)　C) `git rebase feature`(在 main 上变基到 feature)　D) A 和 B 都可以,取决于团队偏好

9. 下面关于 merge vs rebase 的"使用场景选择",**不合理**的是?
   - A) 个人 feature 分支同步 main 最新代码用 rebase(保持历史整洁)　B) 将 feature 最终合并回 main 用 merge --no-ff(保留合并节点)　C) 公共分支 main 用 rebase 来同步别的分支　D) 把多个零散的 "WIP" 小提交整理成清晰提交用 `rebase -i`

10. `git pull --rebase` 的效果是什么?
   - A) 与 `git pull` 完全相同　B) `git fetch` + `git rebase`(而非 merge),让你的本地提交"跑"到远程最新提交之后　C) 只 fetch 不 merge　D) 重新克隆仓库

### 解答题(5 道)

**Q1 概念:** 画出 merge 和 rebase 在提交历史 DAG 图上的效果差异,并解释"线性历史"和"有向无环图"两种世界观。

**Q2 解释:** 为什么说 rebase 是在"重写历史"?为什么重写历史能带来好处但同时很危险?

**Q3 操作:** 写出用交互式 rebase 将最近 4 个零散的 commit 合并(squash)为一个有意义的 commit 的完整步骤。

**Q4 排障:** 菜菜在 feature 分支上 `git rebase main`,遇到冲突解决了无数次(同一个文件反复冲突),怀疑操作方式有误。分析可能的原因并给出高效解决策略。

**Q5 综合设计:** 咖啡站项目当前提交历史混乱:有十几个 "WIP"、"fix typo"、"test" 提交。请设计一套整理方案:①用 rebase 合并零散提交 ②用 `--no-ff` merge 到 main 保留功能边界 ③整理后的 push 策略和团队通知。

> [!答案]
> **1-B** `git rebase main` 将当前分支(feature)的所有提交"摘下来",临时放到一旁,然后把 feature 的根部移到 main 的最新提交,再将之前的提交一个个"接回去"。**举一反三:**也可以理解为"把我分支的变更,在 main 的**最新**版本上重新播放一遍"。
>
> **2-C** merge 保留每条分支的存在和汇合点(DAG 拓扑图保留分叉和合并),rebase 将分叉历史"拉直"为一条线(提交 ID 改变)。**举一反三:**merge:真实历史(什么时间在哪条分支上做了什么)。rebase:整理后的叙事(故事按逻辑顺序排列)。
>
> **3-B** rebase 会重新生成提交(新的哈希),旧的提交对象变成"孤儿"。如果其他人基于你旧提交做了工作,你的 rebase+force push 会让他们陷入混乱。**举一反三:**一旦 commit 被 push 到共享仓库且有别人可能拉取了,就永远不要 rebase 那个 commit。
>
> **4-B** 交互式 rebase(`-i`)是一个强大的提交编辑器:可以 squash(合并)、reword(改信息)、drop(删除)、reorder(重排)、edit(停下来修改)。**举一反三:**`git rebase -i HEAD~5` 编辑最近 5 个提交;`git rebase -i <commit-hash>` 编辑指定提交之后的所有提交。
>
> **5-B** squash(南瓜/挤压):将当前提交合并到前一个提交中,保留两个提交的信息供你编辑。**举一反三:**`fixup` 类似 squash 但丢弃被合并提交的信息(不让你编辑),适合 "fix typo" 这类无意义的提交。交互式 rebase 中标记为 `s`(squash)或 `f`(fixup)。
>
> **6-B** rebase 后本地提交 ID 全变了,和远程分支上的旧 ID 完全不同,Git 认为两条历史没有前后关系,拒绝普通 push。必须用 force push 告诉 Git"我知道我在改写历史,接受我的版本"。**举一反三:**这也是为什么"公共分支不 rebase"——你的 force push 会把团队成员基于旧 ID 的工作扔进垃圾堆。
>
> **7-B** squash:合并提交 + 保留两个提交信息 → 让你编辑最终信息。fixup:合并提交 + 只保留前一个提交的信息 → 自动丢弃 fixup 的提交信息。**举一反三:**fixup 适用场景:`修个typo` `补充注释` `修复lint错误`——这些提交信息没有保留价值,直接融入上一个提交即可。多数人更喜欢用 fixup 快速清理。
>
> **8-C** 在 main 上 rebase 到 feature 等于"改写 main 的历史"——这正是禁止的操作!main 是公共分支,rebase main 会让所有同事崩溃。**举一反三:**A 和 B 都可以,看团队偏好。同步 feature 的两种方式:merge main into feature(产生一个合并提交)或 rebase feature onto main(改写 feature 的提交基准)。两者各有优劣,但都比"rebase main onto feature"安全一万倍。
>
> **9-C** `git rebase` 改写到公共分支 main 是**绝对禁止**的,不应推荐。A(个人分支同步)、B(最终合并用 merge --no-ff 保留功能边界)、D(整理 WIP 提交)都是合理使用场景。**举一反三:**核心原则:rebase 只用于你的私有分支;merge 用于公共分支。
>
> **10-B** `git pull --rebase` = fetch + rebase(而非 fetch + merge)。**举一反三:**在活跃的 main 分支上,如果不确认本地是否有"待合并的奇怪提交",用 `--rebase` 可以让历史保持整洁。可以全局设置:`git config --global pull.rebase true`。
>
> **Q1** Merge:历史图有分叉(两条线并行)和一个汇合点(merge commit),看起来像河流分岔又汇合。Rebase:历史图是一条直线,所有提交"凭空"出现在在目标分支之后,看起来像所有开发是在最新代码上线性进行的。**两种世界观:**merge 派认为"历史就应该是真实的,分叉代表并行开发的事实";rebase 派认为"历史是讲给后来人听的故事,应该是干净的线性叙事"。现代团队常用混合策略:个人分支用 rebase 保持整洁,合并到公共分支用 merge 保留功能边界。
>
> **Q2** rebase "重写历史"指:原来的提交(A→B→C,基于旧 main)被替换为新的提交(A'→B'→C',基于最新 main)。原提交和新提交的**哈希值完全不同**,虽然源码内容相似。**好处:**①提交历史线性易读(像一条直线的故事) ②bisect 调试更方便(每个节点都是可工作状态) ③code review 友好(系列提交逻辑清晰)。**危险:**①如果别人基于你的旧提交做了工作,force push 后会让他们迷失 ②rebase 过程中可能引入新的 bugs(因为每个提交在"新基底"上重放时可能产生不同的合并结果) ③一旦 force push 后,reflog 在别人机器上无法找到你(他们的 reflog 没有你的操作记录)。
>
> **Q3** 完整步骤:①`git log --oneline -6` 确认最近 4 个提交的起始位置 ②`git rebase -i HEAD~4`(注意 `~4` 是相对于 HEAD 的倒数 4 个) ③在打开的编辑器中,保留第一个提交为 `pick`,后面 3 个改为 `squash`(或简写 `s`) ④保存关闭,编辑器再次打开让你编辑合并后的提交信息 ⑤删除零散信息,写一条清晰的新提交信息,保存关闭 ⑥`git log --oneline -3` 确认 4 个提交已合并为 1 个 ⑦如果是远程私有分支:`git push --force-with-lease`。**举一反三:**不想进入交互编辑器也可以用 `git rebase -i --autosquash` + 提前用 `git commit --fixup=<hash>` 标记需要合并的提交。
>
> **Q4** 反复冲突的可能原因:①feature 和 main 之间的差异太大(功能分支开发太久没同步) ②同一个文件的同一区域在多个提交中都做了修改,每个提交在"重放"时都要重新解决一遍冲突 ③包含了一些不该 rebase 的内容(如 merge commit)。**高效策略:**①先 `git merge main` 解决一次冲突,把冲突解决结果作为一个提交,然后再用 rebase 整理历史(或直接不 rebase 了,merge 就够) ②当冲突太多时,选择 merge 而不是 rebase 更明智 ③或者用 `squash merge`(在 GitHub 上)把整个 feature 当成一个提交合并,避免多次冲突解决。**核心判断:**如果 rebase 过程中不断出现同类冲突,说明这个分支不适合 rebase——直接用 merge。
>
> **Q5** 整理方案:①先确认本地 feature 分支未 push 到公共仓库(或只有你一个人用) ②`git rebase -i HEAD~15` 15 个待整理的提交 ③编辑器中将第 2-15 个提交标记为 `squash`(或 `fixup` 给无意义的 WIP) ④编写一个清晰的总提交信息:"实现订单超时自动关闭功能(含单元测试)" ⑤检查:`git log --oneline -3` ⑥现在 feature 分支有 1-3 个干净提交 ⑦`git switch main && git pull origin main` ⑧`git merge --no-ff feature`(强制创建合并节点,保留"function 分支存在过的痕迹") ⑨`git push origin main`(注意这次不是 force push,因为 main 没有改写) ⑩`git push origin feature --force-with-lease`(feature 个人分支需要 force) ⑪通知团队:告知 force push 的分支范围。**举一反三:**GitHub/GitLab 的 "Squash and Merge" 按钮本质上就是帮你完成了 rebase squash + merge 的流程。但自己手动做可以更精细地控制中间过程。

## 运行前边界、回滚与验证

- **运行前**：示例以 GNU/Linux 的 Bash 为主；先用 `command --help`、`man command` 或发行版文档确认本机版本和参数。不要把教程中的 IP、域名、用户、路径直接复制到生产机器。
- **先确认作用域**：涉及文件、仓库、容器或远端主机时，先运行 `pwd`、`whoami`、`git status`、`docker context show` 或 `ssh -G 主机别名`，确认当前目标；对重要数据先做可恢复备份。
- **完成后验证**：用只读命令确认结果，例如 `ls -la`、`git status`、`systemctl status 服务名`、`docker ps` 或 `curl -fS URL`；失败时停止扩大操作范围，先读报错。
- **Git 回滚边界**：`reset --hard`、rebase 和强推会改写本地或共享历史。先保存 `git status`/`git log --oneline`，共享分支优先 `git revert`；必须强推时使用 `--force-with-lease` 并与协作者确认。
