# 《从零开始当工程师》02 · 秒杀系统：让不超卖成为测试

> 先把“绝不超卖”写成能失败的测试，再讨论 Redis、消息队列和分布式系统。

## 一、面试够用的 V0–V2 边界

| 版本 | 目标 | 必须能证明 | 暂不承诺 |
|---|---|---|---|
| V0 | 单机正确扣减 | 并发下库存不为负 | 高吞吐、分布式 |
| V1 | 数据库原子扣减 | 受影响行数决定抢购结果 | 缓存一致性万能解 |
| V2 | 一人一单幂等 | 唯一约束或幂等记录拒绝重复 | 全链路“恰好一次” |

这已经覆盖 Java 并发、事务、索引、异常处理和压测方法。只有目标岗位确实要求，才把 MQ、分库分表、异步削峰放进后续版本。

## 二、V1 的核心不是“先查再扣”

错误写法是先查询库存、判断大于零、再更新。两个请求可能读到同一个旧值，检查与扣减之间已经出现竞态。

数据库层应把判断与更新合成一次条件写入：

```sql
UPDATE sku
SET stock = stock - 1
WHERE id = ? AND stock > 0;
```

`affected rows = 1` 才表示扣减成功，`0` 表示卖完或商品不存在。这里依赖的是目标数据库的事务与行级并发控制；它不自动解决“一个用户重复请求”或多个服务实例之外的业务问题。

## 三、V2：重复请求必须有业务答案

库存正确不等于订单正确。给订单表一个业务唯一约束，例如 `(user_id, sku_id)`，并在同一事务边界内处理“创建订单”和“扣减库存”的失败路径。

```text
请求 → 校验用户/商品 → 条件扣减 → 创建订单 → 提交
                         └→ 失败：回滚并返回可解释结果
```

唯一约束冲突不是“系统炸了”，而是“该用户已经成功参与过”的业务结果。接口要返回一致的状态，日志要能用请求 ID 或订单号定位一次尝试。

## 四、验收脚本应回答什么

压测数字必须附带口径：机器、JDK、数据库版本、连接池、并发数、请求参数和观测时间。没有这些，只有一个 QPS 没有意义。

最小验收至少断言：

```text
初始库存 = N
并发请求数 >= N
成功订单数 <= N
数据库库存 >= 0
成功订单数 + 剩余库存 = N
同一用户重复请求后，订单数仍为 1
```

失败时先保留 SQL、异常、请求标识和最终数据；不要为了让演示绿灯而吞掉异常或手工改库存。

## 五、面试时如何说取舍

“当前版本用数据库条件更新保证库存不为负，并用唯一约束保证一人一单。它优先正确性和可解释性，瓶颈会集中在热点行与数据库连接上。若压测证据显示数据库成为瓶颈，我会先做限流、库存分段或异步化评估，并重新证明不超卖与幂等，而不是直接声称上 Redis 锁就解决了。”

这段回答比“我做了高并发秒杀，Redis + Kafka + 分布式锁”可靠得多。

## 六、下一步

把你的真实环境、启动命令、表结构、一次成功和一次失败的验证记录填入项目证据卡。没有实测前，本文的 SQL 与断言只是验收设计，不是你的项目成果。
