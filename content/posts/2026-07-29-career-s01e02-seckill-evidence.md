# 《从零开始当工程师》02 · 秒杀系统：让不超卖成为测试

> 连载特刊 · 第四部《从零开始当工程师》第一卷「把能力变成证据」第 2 话
> 长期项目：阿零从只会写代码，到带着咖啡站团队把事做成。

> 先把“绝不超卖”写成能失败的测试，再讨论 Redis、消息队列和分布式系统。

## 一、限量豆卖出了三十七份

上一话阿零把"不超卖"写进了项目证据卡的第一栏。领姐当时只问了一句：你怎么证明？

这周咖啡站搞活动：限量手冲豆，三十份，秒杀。

> **〔1〕** 活动结束。豆豆的屏幕上滚出一行订单统计，然后卡住了。
> 豆豆（声音发直）：「阿零。库存三十。订单三十七。」
> 阿零：「不可能，我写了判断的！库存大于零才扣！」
> 豆豆：「你写了。写了七遍都不管用。」

> **〔2〕** 阿零把代码翻出来，指着屏幕理直气壮。
> ```java
> if (sku.getStock() > 0) {          // 查一下
>     sku.setStock(sku.getStock()-1); // 减一下
>     save(sku);                      // 存一下
> }
> ```
> 阿零：「这不挺清楚的吗？大于零才减啊。」
> 领姐（落在窗台，翅膀收好）：「清楚。但它有三步。你以为是一个动作，机器眼里是三个。」

> **〔3〕**（镜头钻进豆豆屏幕——两个小豆子同时冲到货架前。）
> 豆子甲：「还有 1 份！」
> 豆子乙：「还有 1 份！」
> 两个同时拿走了那最后一份。货架变成 **-1**。
> 豆豆（在旁边看着）：「他们俩都没说谎。他们看的都是'拿之前'的那一眼。」

> **〔4〕** 阿零脸涨红了：「那我加锁！`synchronized` 上去！」
> 领姐：「你有几台机器？」
> 阿零：「……上线要开两个实例。」
> 领姐：「那你这把锁，锁的是其中一台的门。另一台照样进。」
> 阿零（张嘴，没说出话）。

> **〔5〕** 领姐翅膀上那张路线图翻了一页。
> 领姐：「别急着找更大的锁。先回答我一个问题——**你怎么知道你现在没修好？**」
> 阿零：「……我看订单数比库存多，就知道了。」
> 领姐：「那就把这句话写成代码。写成一条**每次都会自动去数一遍、数不对就红灯**的测试。」
> 领姐：「你现在的问题不是不会用锁。是你的'不超卖'活在你嘴里，不在你仓库里。」

> [!重点] 领姐：「能被自动验证的，才叫做到了。剩下的都叫'我记得当时是好的'。」

## 二、本话目标

- 看清"先查再扣"为什么在并发下必然出错。
- 用一次条件写入把判断与扣减合成原子操作。
- 用业务唯一约束解决"一人多单"。
- 把"绝不超卖"写成一条会失败的自动化断言。
- 划清 V0–V2 的承诺边界，不虚构分布式能力。

## 三、面试够用的 V0–V2 边界

| 版本 | 目标 | 必须能证明 | 暂不承诺 |
|---|---|---|---|
| V0 | 单机正确扣减 | 并发下库存不为负 | 高吞吐、分布式 |
| V1 | 数据库原子扣减 | 受影响行数决定抢购结果 | 缓存一致性万能解 |
| V2 | 一人一单幂等 | 唯一约束或幂等记录拒绝重复 | 全链路“恰好一次” |

这已经覆盖 Java 并发、事务、索引、异常处理和压测方法。只有目标岗位确实要求，才把 MQ、分库分表、异步削峰放进后续版本。

## 四、V1 的核心不是“先查再扣”

错误写法是先查询库存、判断大于零、再更新。两个请求可能读到同一个旧值，检查与扣减之间已经出现竞态。

数据库层应把判断与更新合成一次条件写入：

```sql
UPDATE sku
SET stock = stock - 1
WHERE id = ? AND stock > 0;
```

`affected rows = 1` 才表示扣减成功，`0` 表示卖完或商品不存在。这里依赖的是目标数据库的事务与行级并发控制；它不自动解决“一个用户重复请求”或多个服务实例之外的业务问题。

## 五、V2：重复请求必须有业务答案

库存正确不等于订单正确。给订单表一个业务唯一约束，例如 `(user_id, sku_id)`，并在同一事务边界内处理“创建订单”和“扣减库存”的失败路径。

```text
请求 → 校验用户/商品 → 条件扣减 → 创建订单 → 提交
                         └→ 失败：回滚并返回可解释结果
```

唯一约束冲突不是“系统炸了”，而是“该用户已经成功参与过”的业务结果。接口要返回一致的状态，日志要能用请求 ID 或订单号定位一次尝试。

## 六、验收脚本应回答什么

压测数字必须附带口径：机器、JDK、数据库版本、连接池、并发数、请求参数和观测时间。没有这些，只有一个 QPS 没有意义。

最小验收至少断言：

```text
初始库存 = N
并发请求数 >= N
成功订单数 <= N
数据库库存 >= 0
成功订单数 + 剩余库存 = N
同一用户重复请求后，订单数仍为 1
```

失败时先保留 SQL、异常、请求标识和最终数据；不要为了让演示绿灯而吞掉异常或手工改库存。

## 七、一次真实翻车：绿灯是自己给的

阿零照着上面的断言写了测试。跑，绿。他截了张图发给领姐。

领姐回了一句：「把库存改成 1，并发调到 50，再跑一次。」

阿零跑了。还是绿。他有点得意。

领姐：「你的测试里，成功订单数是从哪读的？」

阿零去看自己的代码——他读的是**接口返回成功的次数**，而不是数据库里真实的订单行数。而他的接口在唯一约束冲突时，`catch` 完打了条日志，返回的是 `success: true`。

也就是说：数据库里只有 1 单，接口说成功了 1 次，两个数一对，绿灯。**但这两个数都是同一个谎的两面。**

阿零把断言改成直接 `SELECT count(*)` 查库，重跑。红了。

> [!坑] 断言读的数据如果和被测逻辑走同一条通路，那测的就不是正确性，是自我一致性。**验证要从外部拿证据。**

## 八、复盘出根因

| 层次 | 内容 |
|---|---|
| 表象 | 测试全绿，但线上超卖 |
| 直接原因 | 断言读接口返回值，而不是数据库真实状态 |
| 根因 | 把"程序说它成功了"当成了"它真的成功了" |
| 本可以怎样 | 断言只从最终事实源取数：查库、查文件、查外部系统 |

这条根因不只属于秒杀。它属于所有测试：**如果被测代码能影响断言的取数，那这个测试保护不了你。**

> **💬 沟通拆解 · 面试被追问并发时怎么说**
>
> | 场景 | 常见说法（反面） | 问题出在哪 | 改写后 |
> |---|---|---|---|
> | 讲方案 | 「我用 Redis 分布式锁解决了超卖。」 | 跳过了为什么需要锁，也没说锁本身的代价 | 「我先用数据库条件更新保证不超卖，因为它一次写入就完成判断和扣减。分布式锁我没上——单点数据库还没成为瓶颈，先加锁只会多一个可用性风险。」 |
> | 讲验证 | 「我压测过，没问题。」 | 无口径、无断言内容 | 「我有一条并发断言：初始库存 N、并发 ≥N，跑完直接查库校验'成功订单数 + 剩余库存 = N'且库存 ≥0。脚本在仓库里，可以现在跑。」 |
> | 被问到边界 | 「后面加 MQ 就能扛住了。」 | 承诺没验证过的东西 | 「瓶颈会先出现在热点行和连接池。真到那一步，我会先压测定位，再在限流、库存分段、异步化里选一个——并重新证明不超卖和幂等还成立。」 |
>
> 一句套路小结：**先说你保证了什么并给出可跑的证据，再说你没保证什么和下一步怎么判断。**

## 九、面试时如何说取舍

“当前版本用数据库条件更新保证库存不为负，并用唯一约束保证一人一单。它优先正确性和可解释性，瓶颈会集中在热点行与数据库连接上。若压测证据显示数据库成为瓶颈，我会先做限流、库存分段或异步化评估，并重新证明不超卖与幂等，而不是直接声称上 Redis 锁就解决了。”

这段回答比“我做了高并发秒杀，Redis + Kafka + 分布式锁”可靠得多。

## 十、下一步

把你的真实环境、启动命令、表结构、一次成功和一次失败的验证记录填入项目证据卡。没有实测前，本文的 SQL 与断言只是验收设计，不是你的项目成果。

> **🧭 路线台 · 这周你可以做的三件事**
>
> 1. 给你现在的项目写一条并发断言：库存设成 1，并发调到 50，跑完**直接查库**校验总数守恒。断言里不许出现任何来自被测接口的返回值。
> 2. 把你项目里所有 `catch` 块过一遍，找出"吞掉异常还返回成功"的地方。这一条改完，你就有了一个能讲的真实翻车故事。
> 3. 下周自检一句：如果我故意把扣减那行删掉，我的测试会红吗？不会红的测试等于没写。
>
> 领姐结语：技术是船，方向是舵——先校准方向，再谈速度。

## 十一、项目检查点

秒杀这块此刻的状态：

- **已具备**：一次条件写入的原子扣减；业务唯一约束保证一人一单；一条从数据库取证的并发断言；明确的 V0–V2 承诺边界。
- **还没有**：热点行的压测数据；限流与库存分段；任何可声称的分布式一致性。

阿零的变化：他从"我加了判断所以应该没问题"，变成"我有一条会红的测试，所以我知道它现在是对的"。

## 十二、对应招聘技能

并发控制、数据库事务与唯一约束、幂等设计、可复现的验收脚本、边界表达能力。
