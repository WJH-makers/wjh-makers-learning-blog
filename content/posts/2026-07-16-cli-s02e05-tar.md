## 一、需求:几十个文件,得先捆成一个

配置改利索了,豆豆下最后一道令:「把整个 `coffee-shop/` 目录**打成一个包**,传上服务器一次解开。你总不能几十个文件一个个 `scp` 吧?」

阿零懂这个痛点:文件一多,一个个传又慢又容易漏。他需要把整棵目录树**捆成一个文件**,还顺手压小体积。Linux 上干这活的祖师爷,就是 `tar`——一个几乎每台服务器都在用、参数却最容易记混的命令。本卷就用它给咖啡站打出**第一个部署包**收尾。

## 二、漫画 · tar 的暗号

> **〔1〕** 阿零面前摊着一目录零散文件,他准备一个个往服务器传。
> 阿零:「几十个文件……传到手抽筋。」

> **〔2〕** 管道工扛着一卷打包带走来:「捆成一个包,再压扁。一条命令的事——`tar`。」他敲下 `tar -czf coffee.tar.gz coffee-shop`。
> 阿零:「`czf`?这三个字母什么暗号?」

> **〔3〕** 管道工拆解:「**c**reate 造包、**z** 用 gzip 压、**f**ile 指定包名。**造·压·名**,连起来 `czf`。」特米补一句:「解开就把 c 换成 **x**(e**x**tract)——`xzf`,**解·压·名**。」

> **〔4〕** 阿零想验货,`tar -tzf coffee.tar.gz` 一敲,包里的文件清单唰唰列出,一个没漏。
> 阿零:「不解开也能看里面有啥?!」特米:「**t** = list,先验货再解包,是好习惯。」

> **〔5〕** 阿零想在服务器解开,手一快漏了个 `f`,敲成 `tar -czf`(后面啥都没跟),终端「咔」地卡住不动,像死机。
> 阿零(慌):「它、它不动了!」特米(淡定):「没死。`f` 后面等着你给包名呢,你没给,它在**等输入**。按 `Ctrl+C` 中止。」

> **〔6〕** 阿零改对 `tar -xzf coffee.tar.gz -C /coffee-lab/srv/`,包在服务器上原样铺开。
> 管道工收起打包带:「打包 `czf`、解包 `xzf`、验货 `tzf`——三句暗号,咖啡站的部署包成了。」

## 三、本话目标

- 用 `tar -czf` 把目录打成 `.tar.gz` 压缩包(create + gzip + file);
- 用 `tar -xzf` 解包,`-C` 指定解到哪个目录;
- 用 `tar -tzf` **不解开就列出**包内清单(验货);
- 认识备胎 `zip` / `unzip`(跨平台交换更友好);
- 踩一个真实坑:`f` 后面没跟包名,终端「假死」在等输入。

## 四、原理图:tar 与 gzip 是两件事

```text
tar 只"捆",gzip 才"压" —— .tar.gz 是两步合一:

  多个文件/目录 ──tar 归档──▶ coffee.tar(捆成一个,没变小)
                                 │
                                 └──gzip 压缩──▶ coffee.tar.gz(变小了)

一条命令里的字母 = 一步操作,按顺序读:
  c  create   造一个新包         x  extract  解开一个包
  z  gzip     顺带压缩/解压       t  list     只列清单,不解开
  f  file     下一个词是"包名"    v  verbose  过程中打印每个文件名
  -C dir      解包时:切到 dir 再展开(不加就解在当前目录)

暗号记忆:  打包 czf = 造·压·名    解包 xzf = 解·压·名    验货 tzf = 列·压·名
```

**关键认知:`f` 永远紧挨着包名,是「file 名跟在后面」的意思——漏了它,tar 就不知道包叫什么,只能干等。**

## 五、上手:给咖啡站打一个部署包

**① 打包 + 压缩**(在 `coffee-shop` 的上一级目录):

```bash
$ tar -czf coffee-deploy.tar.gz coffee-shop
$ ls -la coffee-deploy.tar.gz
-rw-r--r-- 1 ubuntu ubuntu 689 Sep 28 10:14 coffee-deploy.tar.gz
```

一个 689 字节的包,装下了整棵目录树。

**② 验货**(不解开,先看里面对不对):

```bash
$ tar -tzf coffee-deploy.tar.gz
coffee-shop/
coffee-shop/config/
coffee-shop/config/app.conf
coffee-shop/logs/
coffee-shop/logs/access.log
coffee-shop/src/
coffee-shop/src/menu.js
coffee-shop/src/order.js
```

**③ 解包到指定目录**(模拟传上服务器后展开):

```bash
$ mkdir -p /coffee-lab/srv/coffee && tar -xzf coffee-deploy.tar.gz -C /coffee-lab/srv/coffee
$ ls /coffee-lab/srv/coffee/coffee-shop
config  logs  src
```

想看解包过程,给它加个 `v`(verbose):`tar -xzvf ...` 会把每个铺开的文件名逐行打印出来。

> **特米旁白**:`.tar.gz` 也常写成 `.tgz`,一回事。见到 `.tar.bz2` / `.tar.xz` 只是换了压缩算法——把命令里的 `z` 换成 `j`(bzip2)/`J`(xz)即可,`czf`/`xzf` 的骨架不变。

## 七、读懂真实报错

先看漏包名的「假死」:`tar -czf` 后面 `f` 声明了「要给包名」,你却没给,又没给要打包的源——**tar 在标准输入上等你继续喂内容**,不是死机。按 `Ctrl+C` 中止即可。而如果 `f` 后面直接跟了别的选项、把包名挤没了,tar 会明确报错:

```text
tar: option requires an argument -- 'f'
Try 'tar --help' or 'tar --usage' for more information.
```

翻译:**`f` 这个选项需要一个参数(包名),你没给。** 根因都指向同一件事——`f` 和包名是绑定的一对,中间不能断。修法就是把包名紧跟在 `czf` 后面:

```bash
$ tar -czf coffee-deploy.tar.gz coffee-shop   # f→包名→源,顺序别断
$ echo $?                                       # 成功返回 0
0
```

> **多解台记法**:很多人把 `-czf` 写成 `czf`(不带横杠)也能跑——tar 对老式选项容忍无横杠。但**新手一律带 `-` 更安全**,和别的命令习惯统一,不容易和后面的包名粘连出歧义。

> **🪟 双系统对照 · tar ↔ Compress-Archive**

| 干什么 | Linux (bash) | PowerShell 7 | 备注 |
|---|---|---|---|
| 打包压缩 | `tar -czf app.tar.gz app/` | `Compress-Archive -Path app\ -DestinationPath app.zip` | PS 原生产出的是 **.zip**,不是 .tar.gz |
| 解包 | `tar -xzf app.tar.gz` | `Expand-Archive app.zip -DestinationPath .\out` | — |
| 列清单不解开 | `tar -tzf app.tar.gz` | 需 `[IO.Compression.ZipFile]` 或先 Expand | tar 的 `-t` 更顺手 |
| 覆盖已存在 | 默认覆盖 | 加 `-Force` | PS 不加会报「已存在」 |

**好消息:Windows 10/11 和 Ubuntu 24.04 都自带了 `tar` 命令**——所以跨机传部署包,`.tar.gz` 是最稳的通用格式,两边都认:

```powershell
# PowerShell 7 里直接用 tar,和服务器一模一样
tar -czf coffee-deploy.tar.gz coffee-shop
tar -tzf coffee-deploy.tar.gz     # 列清单,验货
```

要给同事发个 Windows 双击就能开的包,才用 `zip`;传服务器部署,`tar -czf` 一路通到底。

> **🎯 面试直击**:`.tar` 和 `.tar.gz` 有什么区别?
> `.tar` 只是把多个文件**归档**成一个(打包,不压缩);`.tar.gz` 是在 tar 归档之上再用 **gzip 压缩**,体积更小。tar 负责「捆」、gzip 负责「压」,是两件独立的事,命令里的 `z` 就是那步压缩。追问:为什么 Linux 世界偏爱 tar+gzip 而非 zip?tar 完整保留 Unix 的文件权限、符号链接、属主等元信息,zip 对这些支持弱——部署场景权限不能丢。

## 八、用命令验证:包完整、解开一致

打包后不能只看「命令成功」,要验证**解开的内容和原始一致**:

```bash
$ tar -tzf coffee-deploy.tar.gz | wc -l          # 包里有几个条目
8
$ find coffee-shop | wc -l                        # 原始目录有几个条目(含目录本身)
8
$ echo $?
0
```

8 = 8,说明打包没漏东西。更严谨可以解到临时目录再逐文件比对,但「条目数对上 + 退出码 0 + tzf 清单肉眼扫一遍」在部署前已经足够可信。

### 解答题(5 道)

**Q1 概念:** 解释"压缩"和"归档(打包)"的区别。tar 和 gzip 各负责什么?

**Q2 解释:** 为什么 `tar -czf` 中 `-f` 必须紧跟包名(放最后),而不能写成 `tar -cfz` 或 `tar -f backup.tar.gz -cz`?

**Q3 操作:** 写出将 `~/project/` 打包压缩为 `project-backup.tar.gz`(排除 `.git/` 和 `node_modules/` 目录),然后解压到 `/tmp/restore/` 的完整命令。

**Q4 排障:** 菜菜执行 `tar -xzf backup.tar.gz`,报错 `gzip: stdin: not in gzip format`。分析可能原因并给出排查/解决步骤。

**Q5 综合设计:** 为咖啡站设计一套备份策略(含压缩),要求:①将 `~/coffee-app/` 打包,文件名含日期(如 `coffee-20260928.tar.gz`) ②打包前列出要备份的文件 ③验证压缩包完整性 ④自动清理 30 天前的旧备份。写出脚本逻辑。

> [!答案]
> **1-B** `c`=create 创建,`z`=gzip 压缩,`f`=file 指定文件名。**举一反三:**记忆口诀"造(c)压(z)名(f)"——先说要 create,再说用什么压缩,最后告诉它叫什么名字。解压: `xzf`="解(x)压(z)名(f)"。🪟 PowerShell 中 `Compress-Archive` 等价于 zip 打包,不直接对应 tar.gz。
>
> **2-B** `-xzf` = extract + gzip + file:解压(extract)gzip 压缩的归档文件。**举一反三:**`tar -xvf` 解压 tar 包(不压缩),`tar -xvjf` 解压 bzip2 压缩的 tar.bz2 包。记忆:`x`=解,`z`=gzip,`j`=bzip2,`J`=xz。
>
> **3-B** `-f` 后跟归档文件名(如 `backup.tar.gz`),它是不可省略的参数——没有文件名 tar 不知道读写哪个文件。**举一反三:**这是 `tar` 最常犯的错误:忘记 `-f` 参数或把它放错位置。永远把 `-f` 和它的参数(文件名)放在选项组的最后。
>
> **4-C** `-tzf` = list + gzip + file:列出(t=list)归档内容而不解压。**举一反三:**解压前先用 `-tzf` 看一眼里面有什么,避免解压出一堆文件污染当前目录。相当于"先看菜单再下单"。
>
> **5-A** 在有/无尾部 `/` 时,`tar -czf` 打包整个目录的行为实际相同:都会创建包含 `project/` 目录的归档,解压后得到一个 `project/` 目录。**举一反三:**这与 `rsync` 和 `cp` 中源路径尾部 `/` 的行为差异不同;但依然建议统一风格,加上尾部 `/` 更清晰表明"打包目录"的意图。
>
> **6-B** `-C`(大写 C)= Change directory,先切换到指定目录再执行解压。**举一反三:**`tar -xzf file.tar.gz -C /tmp/` 等价于 `cd /tmp && tar -xzf file.tar.gz` 但不需要手动切换。`-C` 在创建归档时也可以使用,指定"从哪个目录打包"。
>
> **7-B** 解压:`xzf`(eXtract gZip File);列:`tzf`(lisT gZip File)。记忆公式:"造(c)压(z)名(f)"→"解(x)压(z)名(f)"→"列(t)压(z)名(f)",只需替换第一个字母。
>
> **8-A** `tar -czf file.tar.gz /data` 是正确写法。B 错误:选项组中 `-f` 后没有参数(文件名被 `z` 占位了);C 正确但 `-zcf` 中 `-f` 同样需要一个参数在它之后;D 参数顺序错误(文件名和打包目标互换了)。**举一反三:**`-f` 的参数(文件名)必须**紧跟在 `-f`** 后面,所以 `-f` 通常放在选项组的最后:`-czf file.tar.gz` 是标准写法。
>
> **9-B** tar 负责打包(把多个文件和目录合并为一个 .tar 文件,不压缩),gzip 负责压缩(把 .tar 文件变小)。.tar.gz 是"先打包再压缩"的结果。**举一反三:**gzip 只能压缩单个文件,不能压缩目录——这也是为什么需要 tar 先打包。其他压缩算法:bzip2(-j)压缩率更高但更慢,xz(-J)压缩率最高但极慢。
>
> **10-C** `-O`(大写 O,=to stdout)将解压内容输出到标准输出而不是写入磁盘。`tar -xzf backup.tar.gz -O file.txt | less` 实现不解压查看。**举一反三:**这是查看压缩包内容的神技——不用解压到磁盘,直接管道查看。`tar -xzf backup.tar.gz --to-stdout file.txt` 是 GNU tar 的长选项写法。
>
> **Q1** 归档(Archiving/打包):将多个文件和目录合并为单个文件(如 .tar),保留目录结构和文件元数据(权限、时间戳),但**不减少体积**。压缩(Compression):对单个文件或数据流进行编码以减小体积(如 .gz、.bz2、.xz)。**tar 负责打包,gzip/bzip2/xz 负责压缩。**`.tar.gz`=tar 打包 + gzip 压缩,两步合一。🪟 Windows 中 .zip 同时打包和压缩(两步合一),所以不需要 tar+zlib 分离。
>
> **Q2** `-f` 需要一个参数(文件名),这个参数必须**紧跟在 `-f` 后面**。`tar -cfz archive.tar.gz data` 中,`-f` 的下一个字符是 `z`,所以 `z` 被当作文件名而非选项,导致混乱。正确写法:`tar -czf archive.tar.gz data`——`-f` 在选项组最后,后面紧跟文件名。**记忆:**选项组中 `-f` 和它的文件名不能分开,所以总是 `-czf name` 或 `-xzf name`,不能写成 `-cfz` 或 `-fxz`。
>
> **Q3** 打包:`tar -czf project-backup.tar.gz --exclude='.git' --exclude='node_modules' ~/project/`。解压:`mkdir -p /tmp/restore && tar -xzf project-backup.tar.gz -C /tmp/restore/`。**举一反三:**`--exclude` 支持 glob 模式,如 `--exclude='*.log'` 排除所有日志文件。排除列表较长时可用 `--exclude-from=exclude-list.txt` 外部文件控制。
>
> **Q4** 可能原因:①文件根本不是 gzip 压缩的——可能是普通 tar(无压缩)、zip、bzip2 等其他格式 ②文件名是 `.tar.gz` 但实际是未压缩的 `.tar` 文件(重命名错误) ③文件下载不完整或损坏 ④文件被错误地当成 gzip 数据。**排查步骤:**①`file backup.tar.gz` 检查真实文件类型:`file` 能识别出实际压缩/归档格式而不管扩展名 ②如果是 tar,用 `tar -xf`(不用 z);如果是 zip,用 `unzip` ③检查文件大小:`ls -lh`,太小可能是空文件或损坏。
>
> **Q5** 脚本逻辑:①`tar -czf ~/backups/coffee-$(date +%Y%m%d).tar.gz ~/coffee-app/`(日期嵌入文件名) ②备份前预览:`tar -tzf coffee-*.tar.gz | head` ③验证完整性:`tar -tzf coffee-$(date +%Y%m%d).tar.gz > /dev/null && echo "OK" || echo "CORRUPT"`(列出内容,正确返回 0 则通过) ④清理旧备份:`find ~/backups/ -name "coffee-*.tar.gz" -mtime +30 -delete`。**举一反三:**生产级备份还应考虑加密(`openssl` + tar)、远程存储(`rsync`/`scp` 传输压缩包)、增量备份(`tar -g` 增量模式)等。

## 运行前边界、回滚与验证

- **运行前**：示例以 GNU/Linux 的 Bash 为主；先用 `command --help`、`man command` 或发行版文档确认本机版本和参数。不要把教程中的 IP、域名、用户、路径直接复制到生产机器。
- **先确认作用域**：涉及文件、仓库、容器或远端主机时，先运行 `pwd`、`whoami`、`git status`、`docker context show` 或 `ssh -G 主机别名`，确认当前目标；对重要数据先做可恢复备份。
- **完成后验证**：用只读命令确认结果，例如 `ls -la`、`git status`、`systemctl status 服务名`、`docker ps` 或 `curl -fS URL`；失败时停止扩大操作范围，先读报错。
- **远端边界**：首次连接核验主机指纹；传输前先确认目标路径和账号，`rsync` 删除模式必须先加 `--dry-run`。远程改网络或防火墙时保留一个已登录会话和云控制台回退路径。
