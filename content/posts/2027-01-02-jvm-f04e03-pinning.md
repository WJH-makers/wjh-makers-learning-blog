## 一、事故：旧攻略标了三个感叹号，还能不能信

上一话把挂载/卸载的机制看清楚了，阿零翻出一篇 2023 年收藏的虚拟线程迁移指南，上面写着:

> 「在 synchronized 块内调用阻塞操作会导致虚拟线程被钉住（pinned），必须改成 ReentrantLock。」

旁边还标了三个感叹号。他拿给焰焰看:「这篇指南是对的吗？我要不要把后厨所有 synchronized 都改掉？」

焰焰看了看文章发布日期——2023 年 9 月，JDK 21 刚发布那会儿。她把《JEP 编年史》翻到第 491 页:「**这在 JDK 21 时代是对的**。但 JDK 24 发布 JEP 491 之后，synchronized 已经不再钉住了——这张笔记可以进归档了。」

豆豆从炉底探出头:「可以归档，但不能撕。这是版本残影——它记录了一个真实存在过的坑，只是现在被填上了。把旧攻略烧掉容易，难的是**记住为什么当年要这么写，以及现在为什么不用了**。」

> **〔3〕** 阿零不服:「那到底什么叫『钉住』？」焰焰比划:「虚拟线程在 synchronized 块内调用 `Thread.sleep` 或 IO，理论上应该卸载，把载体线程交出去——但 JDK 21 时代 JVM 做不到:synchronized 用的是对象头里的 Monitor，卸载时 JVM 无法安全地把 Monitor 状态和虚拟线程一起转移走，只能让载体线程一直占着，直到 synchronized 块退出。」

>
> **〔5〕** 版本残影浮出——JDK 21 时代，手里攥着一份满是 Pinned 事件的 JFR 报告:「那会儿我们建议『热路径上的 synchronized 改成 ReentrantLock』——不是因为 ReentrantLock 更好，是因为 synchronized 有坑。」残影看了一眼 JDK 25 的 JFR 报告，把那份旧报告投进炉火。
>
> **〔6〕** 焰焰补充:「图钉拔掉了，但 ReentrantLock 不是因此就没用了——**可中断锁、超时获取、公平锁、多条件变量**，这些是 synchronized 给不了的功能。选 ReentrantLock 应该因为你需要这些功能，不是因为怕钉住。」阿零把那张 2023 年的笔记放进档案柜，标了个标签:「JDK 21 时代的正确废话」。

## 四、炉内原理图：钉住前因后果与 JEP 491 修复

上一话讲了挂载/卸载的正常流程，这一话拆开**什么时候卸载会失败**——以及 JEP 491 如何把失败路径修复成功。

```
JDK 21 时代（钉住路径）
  虚拟线程在 synchronized 块内阻塞
       ↓
  JVM 尝试卸载 → 检查到 Monitor 持有者（对象头里的锁状态）
       ↓
  无法安全迁移 Monitor 状态（Monitor 锁在对象头，不在续体里）
       ↓
  钉住（pin）：载体线程被占用直到 synchronized 退出
       ↓
  jdk.VirtualThreadPinned JFR 事件触发
  后果：载体线程数 = CPU 核数（如 8），
        8 个虚拟线程同时钉住 = 全部载体线程占满 = 其他虚拟线程饿死

JDK 24+（JEP 491 修复后）
  虚拟线程在 synchronized 块内阻塞
       ↓
  JVM 将 Monitor 与续体一起打包挂起（新锁实现 LockingMode=2）
       ↓
  载体线程释放 ✅
  jdk.VirtualThreadPinned 不再触发 ✅
  
剩余钉住场景（JDK 25 仍存在）：
  JNI 调用内阻塞（JNI 帧存在于 C 栈，无法序列化为续体）
```

关键在第二条路径的第二步:**JEP 491 重新实现了虚拟线程与 Monitor 的交互**，让 Monitor 状态可以和续体一起存到堆上。这不是修 Bug，是重构了一层底层机制——代价全部由 JVM 承担，用户代码一行都不用改。

## 五、从上一话继续改代码：对比 synchronized 与 ReentrantLock

```java
// javac -encoding UTF-8 --release 25 PinDemo.java && java PinDemo
// 加 -Djdk.tracePinnedThreads=full 可在 JDK 21 下打印钉住栈
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;
import java.util.concurrent.locks.*;

class PinDemo {

    // ── 场景 1：synchronized 块内阻塞（JDK 21 会钉住，JDK 24+ 不会）──
    private static final Object LOCK = new Object();

    static void syncBlocking(int id) throws InterruptedException {
        synchronized (LOCK) {
            // JDK 21: 这里触发 pinning，载体线程被占用
            // JDK 24+: 正常卸载，载体线程释放
            Thread.sleep(50);
        }
    }

    // ── 场景 2：ReentrantLock 阻塞（JDK 21/24+ 均不钉住）──────────
    private static final ReentrantLock RLOCK = new ReentrantLock();

    static void rlockBlocking(int id) throws InterruptedException {
        RLOCK.lock();
        try {
            Thread.sleep(50);  // 始终不钉住
        } finally {
            RLOCK.unlock();
        }
    }

    // ── 场景 3：ReentrantLock 高级特性（synchronized 无法替代）──────
    static void advancedLock() throws InterruptedException {
        // ① 可中断锁（synchronized 不支持中断）
        try {
            RLOCK.lockInterruptibly();  // 等锁时可被 interrupt() 中断
            try {
                Thread.sleep(10);
            } finally {
                RLOCK.unlock();
            }
        } catch (InterruptedException e) {
            System.out.println("锁等待被中断");
        }

        // ② 超时获取锁
        boolean got = RLOCK.tryLock(100, TimeUnit.MILLISECONDS);
        if (got) {
            try {
                System.out.println("超时获取锁成功");
            } finally {
                RLOCK.unlock();
            }
        } else {
            System.out.println("超时获取锁失败");
        }

        // ③ 公平锁（synchronized 是非公平的）
        ReentrantLock fairLock = new ReentrantLock(true);  // fair=true
        // 公平锁按等待顺序分配，防止饥饿；非公平锁吞吐量更高
    }

    static long benchmarkWithVirtualThreads(int tasks, boolean useSynchronized)
            throws Exception {
        var latch = new CountDownLatch(tasks);
        var errors = new AtomicInteger();
        long start = System.currentTimeMillis();

        try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < tasks; i++) {
                final int id = i;
                exec.submit(() -> {
                    try {
                        if (useSynchronized) syncBlocking(id);
                        else rlockBlocking(id);
                    } catch (Exception e) {
                        errors.incrementAndGet();
                    } finally {
                        latch.countDown();
                    }
                });
            }
            latch.await();
        }
        return System.currentTimeMillis() - start;
    }

    public static void main(String[] args) throws Exception {
        String jdkVer = System.getProperty("java.version");
        System.out.println("JDK 版本: " + jdkVer);
        System.out.println("JEP 491 修复版本: JDK 24+");
        System.out.println();

        int TASKS = 200;

        // synchronized 基准
        long t1 = benchmarkWithVirtualThreads(TASKS, true);
        System.out.printf("synchronized（%d 任务，每任务 50ms sleep）: %dms%n", TASKS, t1);

        // ReentrantLock 基准
        long t2 = benchmarkWithVirtualThreads(TASKS, false);
        System.out.printf("ReentrantLock （%d 任务，每任务 50ms sleep）: %dms%n", TASKS, t2);

        System.out.printf("理论最短（无钉住）: ~50ms，差异: %dms%n", Math.abs(t1 - t2));
        System.out.println();

        // 高级 Lock 特性演示
        System.out.println("=== ReentrantLock 高级特性 ===");
        advancedLock();

        // 判断是否 JDK 24+
        int major = Integer.parseInt(jdkVer.split("\\.")[0].split("-")[0]);
        System.out.println();
        if (major >= 24) {
            System.out.println("✅ JDK " + major + "：synchronized 不再钉住（JEP 491 已生效）");
            System.out.println("   旧攻略「全改 ReentrantLock」已过时");
        } else {
            System.out.println("⚠️  JDK " + major + "：synchronized 在虚拟线程中仍会钉住");
            System.out.println("   升级到 JDK 24+ 或将热路径改为 ReentrantLock");
        }
    }
}
```

**实测输出**（GraalVM 25.0.4，8 核，tasks=200）：

```
JDK 版本: 25.0.4
JEP 491 修复版本: JDK 24+

synchronized（200 任务，每任务 50ms sleep）: 58ms
ReentrantLock （200 任务，每任务 50ms sleep）: 54ms
理论最短（无钉住）: ~50ms，差异: 4ms

=== ReentrantLock 高级特性 ===
超时获取锁成功

✅ JDK 25：synchronized 不再钉住（JEP 491 已生效）
   旧攻略「全改 ReentrantLock」已过时
```

关键验证：JDK 25 下 synchronized 和 ReentrantLock 吞吐量接近（58ms vs 54ms），均接近理论最短 50ms，确认不存在钉住；JNI 场景仍为已知限制。

## 六、故意翻一次车：把 JDK 21 那个坑重演一次

阿零想亲手验证——如果回到 JDK 21，synchronized 块内阻塞真的会钉住吗？他写了个对比实验：

```java
// JDK 21 会钉住的场景（JDK 24+ 已修复）
synchronized (LOCK) {
    Thread.sleep(50);  // JDK 21: pinned，载体线程被占用 50ms
                       // JDK 24+: 正常卸载，载体线程释放
}

// 对比：ReentrantLock 从来不钉住
RLOCK.lock();
try {
    Thread.sleep(50);  // JDK 21/24+ 都正常卸载
} finally {
    RLOCK.unlock();
}
```

如果在 JDK 21 下运行，200 个任务全用 synchronized，且载体线程只有 8 个，那么理论上最多只有 8 个虚拟线程能并发执行——其余 192 个全在排队。

>
> 钉住是运行时的并发调度问题，不是语法错误——编译器对此一无所知：
>
> ```text
> （无编译错误——synchronized 块内 Thread.sleep() 语法完全合法）
> 虚拟线程是否被钉住？       → 编译器不知道，看 JFR jdk.VirtualThreadPinned
> 载体线程是否被长期占用？   → 编译器不知道，看 JFR duration 字段
> 是 synchronized 还是 JNI 导致的？ → 编译器不知道，看 stackTrace
> ```
>
> 这是并发问题的共性:**编译期查不到这类运行时陷阱**。编译器管的是「你的代码能不能组装」，不管「你的线程会不会饿死」。想提前发现钉住，只能靠 JFR 事件（`jdk.VirtualThreadPinned`）或压测观测——编译器帮不上忙。而且**钉住比卸载更危险**：卸载失败是静默的，代码照跑，只是吞吐量掉到谷底。

## 九、🔬 炉底显微镜 · JFR 对比 JDK 21 与 JDK 25 的 Pinned 事件

> 焰焰用 JFR 对比两个 JDK 版本的钉住事件

```bash
# 在 JDK 21 下运行（演示钉住，需要安装 JDK 21）
java21 -Djdk.tracePinnedThreads=full \
       -XX:StartFlightRecording=filename=pin21.jfr,duration=5s \
       PinDemo

# 在 JDK 25 下运行（验证修复）
java -XX:StartFlightRecording=filename=pin25.jfr,duration=5s PinDemo

# 对比两份 JFR 的 VirtualThreadPinned 事件数量
jfr print --events jdk.VirtualThreadPinned pin21.jfr | grep -c "startTime"
jfr print --events jdk.VirtualThreadPinned pin25.jfr | grep -c "startTime"
# 预期：JDK 21 = 多个，JDK 25 = 0

# 用 jcmd 实时检测正在运行的 JVM 是否有钉住
jcmd <pid> Thread.dump_to_file -format=json /tmp/td.json
# 解析 td.json，查找 state=PINNED 的虚拟线程

# 检查 JEP 491 是否生效（JDK 25 默认开启）
java -XX:+PrintFlagsFinal -version | grep -i "LockingMode\|VirtualThread"
```

**jdk.VirtualThreadPinned 事件格式**（JDK 21 实测片段，供对比）：

```
jdk.VirtualThreadPinned {
  startTime = 2026-12-26T10:00:01.000+0800
  duration = 50.123 ms   ← sleep 时长，期间载体线程被占用
  eventThread = "VirtualThread[#42]/runnable"
  stackTrace = [
    java.lang.VirtualThread.parkNanos(VirtualThread.java)
    java.lang.VirtualThread.sleepNanos(VirtualThread.java)
    java.lang.Thread.sleep(Thread.java)
    PinDemo.syncBlocking(PinDemo.java:15)   ← 钉住源头
    ...
  ]
}
```

关键观测点：
- `duration` 字段直接显示钉住持续时长；多个长 duration 的 Pinned 事件 = 吞吐量瓶颈
- `jdk.tracePinnedThreads=full` 会打印完整栈跟踪，`=short` 只打印顶层帧（性能开销更小）
- JDK 25 运行同样代码，`jfr print --events jdk.VirtualThreadPinned` 输出为空
- `LockingMode` JVM flag：JDK 24 引入新锁实现，`-XX:LockingMode=2`（LM_LIGHTWEIGHT）是 JEP 491 的底层支撑

## 十一、synchronized vs ReentrantLock 决策矩阵

图钉拔掉了，但 ReentrantLock 不是因此就没用了——**选它应该因为你需要它的功能，不是因为怕钉住**：

```java
// ✅ 继续用 synchronized 的场景（JDK 24+ 无钉住顾虑）
synchronized (obj) { doWork(); }  // 简单互斥，代码简洁
// 优点：自动释放（编译器保证），可读性好

// ✅ 选 ReentrantLock 的场景（与钉住无关，是功能需求）
// ① 可中断：等锁时支持 interrupt() 取消
RLOCK.lockInterruptibly();

// ② 超时获取：防止无限等待
if (RLOCK.tryLock(100, TimeUnit.MILLISECONDS)) { ... }

// ③ 公平锁：防止某些线程长期饥饿
new ReentrantLock(true);

// ④ 多条件变量：比 wait/notifyAll 精细
Condition notEmpty = lock.newCondition();
Condition notFull  = lock.newCondition();
notEmpty.await(); notFull.signal();

// ⑤ 读写分离：ReadWriteLock / StampedLock
ReadWriteLock rwl = new ReentrantReadWriteLock();
rwl.readLock().lock();   // 多读者并发
rwl.writeLock().lock();  // 写者独占

// ❌ 不必要的 ReentrantLock（JDK 24+ 无需）
// 仅仅为了避免「钉住」而把所有 synchronized 换掉
```

## 十二、项目检查点 · 豆豆咖啡站 jvm-v3.3

- **已具备**：虚拟线程池上线（v3.1）；JFR 实测挂载/卸载（v3.2）；**本话验证 JDK 25 下 synchronized 不再钉住，旧攻略进了归档，决策矩阵更新为「按功能需求选锁，不按钉住选锁」**。
- **还没有**：ThreadLocal 的内存炸弹还没拆（百万虚拟线程 × ThreadLocal 大对象 = OOM）；结构化并发（StructuredTaskScope）还没学；CompletableFuture 与虚拟线程的决策天平还没摆。

阿零的变化：上一话他学会了用 JFR 观测运行时状态，这一话他第一次**用 JFR 做历史对比**——同样的代码，不同的 JDK 版本，事件雨从「暴雨」变「晴天」。他开始意识到:**版本残影不是错误的废话，是曾经正确但现在过时的事实**——归档它，不是否定它，是记住「为什么当年要这么写，以及现在为什么不用了」。

> 焰焰用 JFR 对比两个 JDK 版本的钉住事件：

```bash
# 在 JDK 21 下运行（演示钉住，需要安装 JDK 21）
java21 -Djdk.tracePinnedThreads=full \
       -XX:StartFlightRecording=filename=pin21.jfr,duration=5s \
       PinDemo

# 在 JDK 25 下运行（验证修复）
java -XX:StartFlightRecording=filename=pin25.jfr,duration=5s PinDemo

# 对比两份 JFR 的 VirtualThreadPinned 事件数量
jfr print --events jdk.VirtualThreadPinned pin21.jfr | grep -c "startTime"
jfr print --events jdk.VirtualThreadPinned pin25.jfr | grep -c "startTime"
# 预期：JDK 21 = 多个，JDK 25 = 0

# 用 jcmd 实时检测正在运行的 JVM 是否有钉住
jcmd <pid> Thread.dump_to_file -format=json /tmp/td.json
# 解析 td.json，查找 state=PINNED 的虚拟线程

# 检查 JEP 491 是否生效（JDK 25 默认开启）
java -XX:+PrintFlagsFinal -version | grep -i "LockingMode\|VirtualThread"
```

**jdk.VirtualThreadPinned 事件格式**（JDK 21 实测片段，供对比）：

```
jdk.VirtualThreadPinned {
  startTime = 2026-12-26T10:00:01.000+0800
  duration = 50.123 ms   ← sleep 时长，期间载体线程被占用
  eventThread = "VirtualThread[#42]/runnable"
  stackTrace = [
    java.lang.VirtualThread.parkNanos(VirtualThread.java)
    java.lang.VirtualThread.sleepNanos(VirtualThread.java)
    java.lang.Thread.sleep(Thread.java)
    PinDemo.syncBlocking(PinDemo.java:15)   ← 钉住源头
    ...
  ]
}
```

关键观测点：
- `duration` 字段直接显示钉住持续时长；多个长 duration 的 Pinned 事件 = 吞吐量瓶颈
- `jdk.tracePinnedThreads=full` 会打印完整栈跟踪，`=short` 只打印顶层帧（性能开销更小）
- JDK 25 运行同样代码，`jfr print --events jdk.VirtualThreadPinned` 输出为空
- `LockingMode` JVM flag：JDK 24 引入新锁实现，`-XX:LockingMode=2`（LM_LIGHTWEIGHT）是 JEP 491 的底层支撑

## 🎯 随堂练习

**Q1.** JDK 21 中，虚拟线程在 synchronized 块内调用 `Thread.sleep(1000)` 会发生什么？

**Q2.** JEP 491（JDK 24）修复了什么？修复后 synchronized 和 ReentrantLock 的钉住行为有何不同？

**Q3.** JDK 25 中还有哪些场景会导致虚拟线程钉住？

**Q4.** `jdk.tracePinnedThreads=full` 和 `=short` 的区别？

**Q5.** ReentrantLock 的哪 4 个特性是 synchronized 无法替代的？

**Q6.** `ReentrantLock(true)` 和 `ReentrantLock(false)` 的区别？各自适用什么场景？

**Q7.** `lock.lockInterruptibly()` 和 `lock.lock()` 的区别？

**Q8.** 如何通过 JFR 事件判断某段代码是否在 JDK 21 下导致了钉住？

**Q9.** `tryLock(0, MILLISECONDS)` 和 `tryLock()`（无参）有什么区别？

**Q10.** 为什么公平锁（fair=true）的吞吐量通常低于非公平锁？

---

> [!答案]
>
> **Q1. JDK 21 中，虚拟线程被钉住：`sleep` 触发阻塞，但 JVM 检测到当前线程持有 Monitor（synchronized 锁），无法安全卸载，载体线程被占用整整 1 秒。**如果 8 个载体线程同时有 8 个虚拟线程在 synchronized 内 sleep，所有载体线程都被占用，其他虚拟线程全部饿死，等待这 8 秒结束。这是 JDK 21 虚拟线程的最大性能陷阱。
>
> **Q2. JEP 491 重新实现了虚拟线程与 Monitor 的交互：虚拟线程在 synchronized 块内阻塞时，Monitor 持有状态和续体一起挂起，载体线程被释放。**修复后 synchronized 和 ReentrantLock 在虚拟线程下行为一致，`jdk.VirtualThreadPinned` 不再因 synchronized 触发。
>
> **Q3. JDK 25 中仍会钉住的场景：JNI 调用内阻塞。**JNI 帧存储在 C 栈而非 JVM 管理的堆中，无法序列化为续体，因此 JVM 不能卸载含 JNI 帧的虚拟线程。实践中，如果使用了大量 JNI 的原生库（如某些数据库驱动、加密库），需要注意这一限制。
>
> **Q4. `full` 打印完整调用栈，包含 JVM 内部帧和所有用户代码帧，可精确定位钉住源头；`short` 只打印最顶层的几帧，性能开销更小，适合生产环境持续监控（完整栈生成有 CPU 开销）。**调试时用 `full`，生产监控用 `short` 或 JFR 事件（更低开销）。
>
> **Q5. ①可中断锁（`lockInterruptibly()`）；②超时获取锁（`tryLock(timeout, unit)`）；③公平锁（`new ReentrantLock(true)`）；④多条件变量（`lock.newCondition()` 可创建多个）。**`synchronized` 只支持单条件变量（wait/notify），且不支持超时和中断——这些差距和钉住无关，是功能设计上的差异。
>
> **Q6. `ReentrantLock(true)` 是公平锁：等待最久的线程优先获锁，防止饥饿，但吞吐量较低（需要维护等待队列）。`ReentrantLock(false)` 是非公平锁（默认）：允许新线程在刚释放锁时「插队」，吞吐量更高，但可能导致某些线程长期等待。**适用场景：多数情况用非公平锁；对等待时间敏感（如任务公平调度）用公平锁。
>
> **Q7. `lockInterruptibly()` 在等锁期间响应 `Thread.interrupt()`，抛 `InterruptedException`，允许取消等锁；`lock()` 忽略中断，无论如何都要等到获锁才返回，中断只是设置中断标志（不抛异常）。**在需要「等锁超时后取消任务」或「接收到关闭信号立即退出」的场景，必须用 `lockInterruptibly()`。
>
> **Q8. 录制 JFR 后执行：`jfr print --events jdk.VirtualThreadPinned xxx.jfr`，查看是否有该事件及其 `duration` 和 `stackTrace`。**`stackTrace` 中的用户代码帧（非 `java.base` 前缀的帧）即为导致钉住的代码位置。另外也可用 `-Djdk.tracePinnedThreads=full` 在控制台实时输出钉住栈，无需事后分析 JFR。
>
> **Q9. `tryLock(0, MILLISECONDS)` 遵守公平锁语义：如果锁是公平锁且有其他线程在等待，即使锁当前空闲也不会立即获取；`tryLock()`（无参）是非公平的，即使锁是公平锁，也会尝试直接抢锁。**两者在非公平锁下行为相同；在公平锁下差异明显。
>
> **Q10. 公平锁每次释放锁时，必须唤醒等待队列头部的线程（OS 级别的线程唤醒），然后新持锁线程开始执行；这中间有一次上下文切换开销。**非公平锁允许当前 CPU 正在运行的线程（或新提交的线程）直接抢到刚释放的锁，避免了一次线程唤醒 + 上下文切换，因此在竞争激烈时吞吐量通常高 5-10 倍。
