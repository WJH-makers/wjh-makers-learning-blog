# 《从零开始玩命令行》20 · 定时任务与环境变量

> 连载特刊 · 第二部《从零开始玩命令行》第 4 卷「进程与系统」第 4 话
> 长期项目:**把豆豆咖啡站部署上真实服务器**。前作《从零开始学 Java》全 56 话见 [/java](/java)。

---

## 一、需求:凌晨三点,谁来备份

咖啡站常驻了,豆豆的心思立刻转到数据上:「订单表就是账本。**每天凌晨三点备份一次**,备份文件按日期留档。你要是打算每天定闹钟起来敲命令,我现在就换人。」

阿零连夜写了个 `backup.sh`:`mysqldump` 导出订单库,`tar` 压成带日期的包。手动一跑,`/srv/backup/` 里整整齐齐躺着 `coffee_2026-10-07.tar.gz`。剩下的问题只有一个:**怎么让服务器自己在三点准时干这件事**——他还不知道,真正的坑不在"定时",而在定时之后。

---

## 二、漫画 · 按时打卡,颗粒无收

> **〔1〕** 豆豆客串,咖啡豆脑袋敲着桌面:「凌晨的订单数据无价。每天 3 点备份,连跑七天给我看。」
> 阿零拍胸脯,当场手动跑通 `backup.sh`,备份包闪闪发光。阿零:「稳了。」

> **〔2〕** 特米教他 `crontab -e`,阿零抄下五颗星:`30 3 * * * /srv/coffee/scripts/backup.sh`。
> 阿零(关灯):「服务器,三点半见。」特米(欲言又止):「……嗯,明早见。」

> **〔3〕** 第二天早上,`/srv/backup/` 空空如也。阿零跳起来:「cron 根本没跑!」
> 特米:「先别喊冤,取证。`grep CRON /var/log/syslog`——看,03:30:01,**它按时打卡了**。」

> **〔4〕** 阿零当场手动再跑一遍脚本——好好的!备份包唰地出现。
> 阿零:「同一个脚本、同一台机器、同一个用户,凭什么?!」特米肚皮打出两个字:**环境**。

> **〔5〕** 特米展开两张背包:「你的 shell 出门背着 `.bashrc` 塞满的大包,PATH 里什么路都认;cron 叫脚本干活时只发一个小挎包——`PATH=/usr/bin:/bin`,**不读 .bashrc**。你的 mysqldump 住在 `/usr/local/mysql/bin`,cron 根本不认识路。」
> 阿零:「所以它不是没跑,是跑了……然后迷路了,还没留遗书?」

> **〔6〕** 特米:「所以无人值守的任务,**先安黑匣子再上天**:输出重定向进日志,一行都别放跑。」
> 特米(冷冷):「记住这案子:手动跑得动 ≠ cron 跑得动。人证(syslog)、物证(日志),缺一个都破不了案。」

## 三、本话目标

- 会用 `crontab -e / -l` 装卸定时任务,读写**五星位**:分 时 日 月 周,`*/5` 每 5 分钟;
- 亲手翻一次本话大车:**手动能跑、cron 不跑**,根因是 cron 的环境 ≠ 登录 shell;
- 掌握两件修法:脚本内**自设 PATH(或全用绝对路径)** + 输出重定向 `>> 日志 2>&1` 留证据;
- 讲透第一性原理:**shell 按 PATH 里目录的顺序找可执行文件**,`export` 是把变量放进子进程的行囊;
- 一句话分清 `.bashrc` 和 `.profile`,并记住:cron 谁都不读。

## 四、原理图:五颗星与两个世界

```text
crontab 一行 = 闹钟(何时)+ 命令(干什么):

 ┌────────── 分 (0-59)
 │  ┌─────── 时 (0-23)
 │  │  ┌──── 日 (1-31)
 │  │  │  ┌─ 月 (1-12)
 │  │  │  │  ┌ 周 (0-7,0 和 7 都是周日)
 30 3  *  *  *   /srv/coffee/scripts/backup.sh

两个世界的环境(第一性原理:shell 沿 PATH 目录顺序找可执行文件,找不到即报错):

 你的登录 shell                        cron 的世界
 ─────────────────                     ─────────────────
 读 .profile,再读 .bashrc             谁都不读(SHELL=/bin/sh)
 PATH=…:/usr/bin:/usr/local/mysql/bin  PATH=/usr/bin:/bin
 mysqldump → 找得到                    mysqldump → command not found
 输出打在你脸上(终端)                输出试图寄邮件,没装 MTA 就石沉大海
```

一句话:**cron 不是"替你敲命令的你",它是个不读你任何配置、两手空空的陌生人。**

## 五、上手:先把闹钟上好

备份脚本(手动版,先跑通):

```bash
$ cat /srv/coffee/scripts/backup.sh
#!/bin/bash
mysqldump -u coffee -p"$DB_PASS" coffee_shop > /srv/backup/coffee_$(date +%F).sql
tar -czf /srv/backup/coffee_$(date +%F).tar.gz -C /srv/backup coffee_$(date +%F).sql

$ /srv/coffee/scripts/backup.sh && ls /srv/backup/
coffee_2026-10-07.sql  coffee_2026-10-07.tar.gz
```

装进 crontab:

```bash
$ crontab -e                     # 编辑当前用户的任务表(第一次会让你选编辑器)
$ crontab -l                     # 列出确认
30 3 * * * /srv/coffee/scripts/backup.sh
*/5 * * * * /srv/coffee/scripts/healthcheck.sh    # */5 = 每 5 分钟一次
```

顺手摸一下环境变量这条线:

```bash
$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/local/mysql/bin
$ which mysqldump                # which 就是"沿 PATH 找一遍给你看"
/usr/local/mysql/bin/mysqldump
$ export CAFE_ENV=prod           # export = 放进行囊,子进程才带得走
$ bash -c 'echo $CAFE_ENV'
prod
```

> **特米旁白**:最后那截 `/usr/local/mysql/bin` 是当年豆豆装官方版 MySQL 时写进 `.bashrc` 的——`export PATH=/usr/local/mysql/bin:$PATH`。记住这个伏笔,凶手已经登场了。

## 六、故意制造一个 Bug:把闹钟上好,然后去睡觉

阿零什么都没多做——这正是事故的全部配方。`30 3 * * *` 上好,手动验证过,睡觉。第二天:

```bash
$ ls /srv/backup/ | grep 2026-10-08
$                                  # 什么都没有
```

没有备份,没有报错,没有任何输出。**无声,是无人值守任务最可怕的翻车姿势。**

## 七、读懂真实报错:先让案发现场开口

**第一步,人证**——cron 到底触发了没有?查 syslog:

```bash
$ sudo grep CRON /var/log/syslog | tail -1
Oct  8 03:30:01 coffee-server CRON[5123]: (azero) CMD (/srv/coffee/scripts/backup.sh)
```

打卡记录在案:cron **准时跑了**。那输出去哪了?cron 会把任务输出寄给本地邮箱,而这台机器没装邮件服务——证据当场蒸发。所以修的第一刀不是修 Bug,是**装黑匣子**:

```bash
$ sudo touch /var/log/backup.log && sudo chown azero /var/log/backup.log
$ crontab -l
30 3 * * * /srv/coffee/scripts/backup.sh >> /var/log/backup.log 2>&1
```

排查期还可以临时把五星位改成 `* * * * *`(每分钟),别真等到凌晨。一分钟后,**物证**到手:

```text
/srv/coffee/scripts/backup.sh: line 2: mysqldump: command not found
tar: coffee_2026-10-08.sql: Cannot stat: No such file or directory
tar: Exiting with failure status due to previous errors
```

根因水落石出:`mysqldump` 装在 `/usr/local/mysql/bin`,这条路是 `.bashrc` 里 export 进 PATH 的;而 **cron 的环境不是登录 shell**——它不读 `.bashrc`,PATH 只有 `/usr/bin:/bin`,自然 `command not found`;第一步倒下,后面的 `tar` 跟着连环撞。修法在脚本顶部自设 PATH(或全部写绝对路径):

```bash
#!/bin/bash
export PATH=/usr/local/mysql/bin:/usr/bin:/bin
```

顺带立两条规矩:`.profile` 是**登录时读一次**(放环境变量),`.bashrc` 是**每开一个交互式 shell 读一次**(放别名、提示符)——而 cron 两个都不读,别指望。另外,若把 `date +%F` 直接写在 crontab 行里,`%` 必须转义成 `\%`——cron 把裸 `%` 当换行符,这是它的又一个冷门脾气(写进脚本里则不受影响)。

> **🪟 双系统对照 · Windows 的闹钟叫计划任务**

| 干什么 | Linux (bash) | PowerShell 7 / Windows | 关键差异 |
|---|---|---|---|
| 定时任务 | `crontab -e` 写五星位一行文本 | `Register-ScheduledTask` + `New-ScheduledTaskTrigger -Daily -At 3:30am` | cron 是**一行文本**;计划任务是**对象三件套**(触发器/动作/主体)拼装 |
| 列出任务 | `crontab -l` | `Get-ScheduledTask \| Where State -eq Ready` | PS 返回对象,可按属性继续筛 |
| 看变量 | `echo $PATH` | `$env:PATH` | 分隔符 Linux 用 `:`,Windows 用 `;` |
| 永久设变量 | 写进 `~/.profile` | `[Environment]::SetEnvironmentVariable('X','y','User')` | Windows 存注册表,**新开的**终端才生效 |
| 同款大坑 | cron 环境 ≠ 登录 shell | 计划任务默认以 SYSTEM/服务环境跑 ≠ 你的终端 | 两边都会"手动能跑、定时不跑",破案思路完全通用 |

对象 vs 文本的老对比,这回站在 cron 一边说句公道话:一行 `30 3 * * *` 十秒写完;PowerShell 的触发器对象啰嗦,但类型明确、不会把 `%` 当换行——各有各的道理。

> **🎯 面试直击**:脚本手动能跑,放进 cron 就不跑,怎么排查?
> 标准四步:① `grep CRON /var/log/syslog` 确认到底触发没有;② 给任务加 `>> 日志 2>&1`,让报错落地;③ 想环境差异——cron 不读 `.bashrc`,`PATH=/usr/bin:/bin`,`HOME`/`SHELL` 也可能不同;④ 修法:脚本自设 PATH 或全用绝对路径。这题是 Linux 面试的保留曲目,答出「cron 环境 ≠ 登录 shell」这句就及格,答出四步就是加分。

## 八、用命令验证:黑匣子里要有好消息

```bash
$ sudo grep CRON /var/log/syslog | tail -1        # 人证:仍在按时打卡
Oct  9 03:30:01 coffee-server CRON[6420]: (azero) CMD (/srv/coffee/scripts/backup.sh >> /var/log/backup.log 2>&1)
$ tail -2 /var/log/backup.log                     # 物证:没有报错即最好的消息
$ ls -lh /srv/backup/ | tail -1
-rw-r--r-- 1 azero azero 1.2M Oct  9 03:30 coffee_2026-10-09.tar.gz
$ tar -tzf /srv/backup/coffee_2026-10-09.tar.gz   # 能列出内容,包没坏
coffee_2026-10-09.sql
```

特米补一刀:**备份的终点不是"文件存在",是"能恢复"**。`tar -tzf` 起码验个完整性;真讲究的话,定期挑一份拉到测试库导入一遍。
