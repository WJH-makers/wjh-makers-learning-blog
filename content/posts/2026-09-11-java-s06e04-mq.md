# 《从零开始学 Java》49 · MQ 派单站(异步解耦削峰,与丢/重/乱三坑)

> 连载特刊 · 第六季「分布式时代」第 4 话 · 基线 Java 25 · Spring Boot 4.x · 项目检查点:分布式扣减 → 异步制作。
> 承接:上一话分布式锁保住了库存,但下单接口里塞着一长串同步动作,高峰期照样慢。

---

## 一、需求:下单别再干等一整条流水线

现在点一杯拿铁,接口要**同步**做完这些才返回:扣库存 → 通知后厨制作 → 发优惠券 → 加积分 → 推送短信。制作慢一点、短信网关抖一下,整个下单就被拖住。豆豆:「顾客只关心'单下成功了'。制作、发券、加积分这些**不必当场做完**。给你架一个**派单站**——下单只把一张'派单'条子丢进队列就立刻返回;后厨、营销、积分各自在队列另一头**慢慢领活干**。这就是**消息队列(MQ)**。」

## 二、漫画 · 把长流水线剪断

> **〔1〕** 老流程:顾客站在收银台前,眼睁睁看着店员扣库存、写制作单、盖优惠券、敲积分、发短信……全干完才说"好了"。队伍排到街上。
> 阿零:「他就下个单,凭什么陪我把后面全看完?」豆豆:「问得好。**把它剪断。**」

> **〔2〕** 豆豆架起一条传送带——**MQ 派单站**。收银台只把"派单条"往传送带上一放(生产者 produce),"叮"一声就对顾客说"下单成功"。
> 豆豆:「后厨、营销、积分是三个**消费者**,各自从传送带取自己的条子干活。收银台再不用等他们。」

> **〔3〕** 三个好处的招牌亮起:**解耦**(收银台不认识后厨是谁)、**异步**(下单秒返回)、**削峰**(洪峰堆在传送带上,消费者按自己节奏慢慢领,不被冲垮)。
> 阿零:「完美!以后加个'集卡活动'消费者,收银台代码一行都不用改!」豆豆(叼豆子):「先别乐——传送带上的条子会**掉、会被领两遍、会乱序**。」

> **〔4〕** 一张"制作拿铁"的条子被后厨领了两次,做出两杯;积分消费者也把 10 分加成了 20。
> 阿零:「啊?!」豆豆:「**丢失、重复、乱序**——MQ 的三座大山。今天翻过去。」

## 三、本话目标

- 理解 MQ 的三大作用:**解耦 / 异步 / 削峰**;
- 用 Spring Kafka 发送并消费一条"派单"消息;
- 保证消息**不丢**(生产确认 + 消费手动提交);
- 保证**不重**——用**幂等**扛住重复消费;
- 理解消息**顺序**为何靠"同 key 同分区"。

## 四、原理图:生产者 → Broker → 消费者

```text
【同步 · 旧】 下单 ─扣库存─发券─加积分─通知制作─▶ 返回(全串行,慢)

【异步 · 新】
  下单接口 ──produce──▶ ┌──────────────────┐
   (扣库存后)           │  Kafka Broker      │
   立刻返回"成功"        │  topic: coffee-order│
                        │  ├ partition-0 ─┐  │
                        │  └ partition-1  │  │
                        └────────┬────────┘  │
                消费者组各取所需 ▼   ▼   ▼
                          [后厨] [营销] [积分]  ← 各自按节奏消费

关键词:  offset=每条消息的位置   consumer group=一组分摊消费的实例
         同一个 key(如订单号)→ 落同一 partition → 保证该订单内有序
```

## 五、代码:下单发消息,后厨来消费

加依赖并配置 broker 地址(依赖铁律):

```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      acks: all               # ← 所有副本确认才算发成功(防丢,详见第八节)
    consumer:
      group-id: coffee-maker
      enable-auto-commit: false   # ← 关掉自动提交,改手动(防丢)
```

下单:扣完库存,只发一条消息就返回:

```java
@Service
public class OrderService {
    private final KafkaTemplate<String, String> kafka;

    public Long placeOrder(OrderRequest req) {
        Long orderId = saveOrderAndDeductStock(req);        // 落库 + 扣库存(上一话的锁)
        // key 用 orderId:同一订单永远进同一分区,保证该订单的消息有序
        kafka.send("coffee-order", String.valueOf(orderId), toJson(orderId, req));
        return orderId;                                     // 立刻返回,不等制作
    }
}

@Component
public class MakerConsumer {
    @KafkaListener(topics = "coffee-order", groupId = "coffee-maker")
    public void onOrder(String message, Acknowledgment ack) {
        Order order = fromJson(message);
        makeCoffee(order);        // 后厨制作(慢活)
        ack.acknowledge();        // ← 处理成功后,手动提交 offset
    }
}
```

## 六、故意制造一个 Bug:一条派单被做了两遍

后厨制作偶尔慢,超过了消费者的 `max.poll.interval`,Kafka 认为这个消费者"卡死了",触发 **rebalance**(重新分配分区),这条还没提交 offset 的消息被**另一个消费者又拉了一遍**——同一张"制作拿铁"派单,做了两次;积分也加了两次。

```java
@KafkaListener(topics = "coffee-order", groupId = "coffee-maker")
public void onOrder(String message, Acknowledgment ack) {
    makeCoffee(fromJson(message));   // ← 不做任何去重,来一条做一条
    ack.acknowledge();
}
```

## 七、读懂现象:重复消费是常态,不是意外

日志里同一个 `orderId` 被处理了两次:

```text
[maker-1] consume orderId=1001, 开始制作拿铁... (耗时过长)
[kafka] consumer group rebalance: partition-0 reassigned to maker-2
[maker-2] consume orderId=1001, 开始制作拿铁...   ← 同一单,第二次!
[积分] orderId=1001 加 10 分  ×2  → 用户凭空多 10 分
```

**关键认知:MQ 默认给的是"至少一次(at-least-once)"投递**——为了不丢,它宁可重发。重复消费**几乎无法从根上杜绝**(网络重试、rebalance、生产者重发都会造成重复)。所以正确姿势不是"消灭重复",而是**让消费逻辑对重复免疫**——这就是**幂等**:同一条消息处理一次和处理十次,结果一样。

> **豆豆锐评 · "不丢"和"不重"是天平的两端**
> 想**绝不丢**,就得重发 + 确认,代价是**可能重复**(at-least-once);想**绝不重**,严格 exactly-once 成本极高。工程界的主流选择:**用 at-least-once 保证不丢,再用业务幂等消化重复**。记住这条,MQ 一致性的面试就答对了大半。

> **🔀 豆豆的多解台 · 消息不丢 / 不重 / 有序,分别怎么保?**

| 难题 | 在哪一环出问题 | 解法 | 代价 / 坑 |
|---|---|---|---|
| **丢失** | 生产发丢 / Broker 没落盘 / 消费未处理就提交 | 生产 `acks=all`+重试、Broker 多副本持久化、消费**处理成功再手动提交 offset** | 吞吐略降;提交与处理顺序千万别反 |
| **重复** | 网络重试、消费者 rebalance、生产重发 | 消费端**幂等**:唯一业务键 + 去重(DB 唯一索引 / Redis / 状态机) | 重复无法根除,只能消化;去重表要清理 |
| **乱序** | 多分区并行消费,顺序被打乱 | 同一业务键用相同 key → 落**同一分区**,单分区内有序 | 别为全局有序退回单分区,会自废吞吐 |

豆豆锐评:**不丢 + 幂等消化重复 + 局部有序**是性价比最高的一套;绝对全局有序和严格 exactly-once 成本极高,没需求别硬追。

## 八、修复:三坑各个击破,并测试幂等

照上表落地,核心就三招:**不丢**——生产 `acks=all`,消费**处理成功后再手动提交 offset**;**有序**——同一订单用 `orderId` 当 key(第五节已这么发)。最关键的**不重(幂等)**,最稳的做法是**数据库唯一约束**——制作记录表对 `order_id` 建唯一索引,重复消息插入时直接被拦:

```java
@KafkaListener(topics = "coffee-order", groupId = "coffee-maker")
public void onOrder(String message, Acknowledgment ack) {
    Order order = fromJson(message);
    try {
        makerLogMapper.insert(order.id());   // order_id 唯一索引:重复消息在这一步被 DB 拒绝
    } catch (DuplicateKeyException e) {
        ack.acknowledge();                   // 已处理过,直接确认丢弃,幂等
        return;
    }
    makeCoffee(order);
    ack.acknowledge();
}
```

**③ 有序**:Kafka 只保证**单分区内有序**,靠 `orderId` 当 key 让同一订单的消息始终落同一分区即可,不必强求全局有序而自废吞吐。

幂等测试:同一条消息投递两次,断言只制作一次:

```java
@Test
void duplicate_message_makes_coffee_once() {
    String msg = toJson(1001L, req);
    consumer.onOrder(msg, ack);
    consumer.onOrder(msg, ack);              // 重复投递
    verify(makerService, times(1)).makeCoffee(any());  // 只做了一杯 —— 幂等成立
}
```

> **🎯 面试直击**:如何保证消息不丢、不重复消费?
> **不丢**三段都要保:生产者 `acks=all`+重试、Broker 持久化+多副本、消费者**手动提交 offset(处理成功后再提交)**。**不重**靠**消费端幂等**——唯一业务键 + 去重(数据库唯一索引 / Redis 记录 / 状态机),因为 MQ 默认 at-least-once,重复不可避免。追问 exactly-once:成本高,常用"at-least-once + 幂等"等价达成。

### 一、选择题（10 道）

**1.** 消息队列（MQ）的三大核心作用不包括以下哪项？
- A) 解耦（服务间不直接调用）　B) 异步（发送方不等接收方处理完）　C) 削峰（洪峰暂存队列，消费者按节奏消费）　D) 数据持久化存储，替代数据库

**2.** Kafka 中用订单 ID 作为 key（`kafka.send(topic, orderId, message)`）的主要作用是什么？
- A) 加速消息发送　B) 对消息进行加密　C) 保证同一订单的消息始终路由到同一分区，保证该订单内消息顺序　D) 作为消息去重的唯一标识

**3.** Kafka 消费端为什么要关闭自动提交（`enable-auto-commit: false`），改用手动提交 offset？
- A) 自动提交会导致消费者组名冲突　B) 防止"消息还没处理完就提交 offset"，若消费者崩溃则消息丢失　C) 手动提交能提升消费速度　D) 手动提交是 Kafka 新版本强制要求

**4.** 消息"幂等性"的正确理解是什么？
- A) 每条消息只被发送一次　B) 同一消息被消费一次和消费十次，最终业务结果完全相同　C) 消息不会丢失　D) 消息严格按照发送顺序被消费

**5.** Kafka producer 配置 `acks=all` 的作用是什么？
- A) 消息立即发送不等待确认　B) 消息到 leader 后即认为成功　C) 消息必须被所有 ISR 确认后才算成功　D) 开启消息压缩

**6.** Kafka 消费者 rebalance 可能导致的典型问题是什么？
- A) 消息永远丢失　B) 消息被重复消费（rebalance 时未提交 offset 的消息被新消费者重拉）　C) 消费者组名被覆盖　D) Kafka Broker 崩溃

**7.** MQ 默认的投递语义是什么？
- A) exactly-once（恰好一次）　B) at-most-once（至多一次）　C) at-least-once（至少一次）　D) 取决于配置，默认为 exactly-once

**8.** 保证消息不丢，需要在哪三个环节分别采取措施？
- A) 生产者、Broker、消费者　B) 网络层、应用层、数据库层　C) 发送端、接收端、监控端　D) 进程、线程、协程

**9.** Kafka"单分区内有序"意味着什么？
- A) 所有分区之间的消息自然有序　B) 同一分区内的消息按生产者发送顺序存储和消费　C) 消费者可跨分区按顺序消费所有消息　D) 消息顺序由消费速度决定

**10.** 以下关于消息队列的说法，哪个是**错误**的？
- A) MQ 可实现生产者和消费者的解耦　B) MQ 能完全消除消息重复消费的可能性　C) MQ 的削峰通过队列暂存消息实现　D) Kafka 和 RabbitMQ 都是常用消息队列中间件

> [!答案]
> **1-D**　MQ 三大作用：解耦、异步、削峰。MQ 不替代数据库——消息是临时的，不适用于长期数据存储和复杂查询。　举一反三：MQ 和数据持久化是互补关系——核心业务数据仍要落库，MQ 只传递事件通知。
> 
> **2-C**　Kafka 只保证单分区内有序。用 orderId 做 key 哈希，同一订单的"创建→支付→发货"始终落在同一分区，消费者按 offset 顺序拉取保证有序。　举一反三：不要为全局有序把所有消息塞进同一个分区——那等于自废并行吞吐。局部有序够用就行。
> 
> **3-B**　自动提交是定时提交，不管消息是否处理成功。若消费者拉到消息后自动提交了 offset，然后处理逻辑时崩溃——重启后 Kafka 认为已消费，消息丢失。手动提交在业务成功后才 `ack.acknowledge()`，保证 at-least-once。　举一反三：手动提交也不能保证 exactly-once——业务成功但提交前崩溃，消息仍会重发。at-least-once + 业务幂等是最务实的组合。
> 
> **4-B**　幂等 = 重复执行产生相同结果。本话通过制作记录表 `order_id` 唯一索引——重复消息 `INSERT` 被 `DuplicateKeyException` 拒绝，结果与消费一次一样。　举一反三：MQ 默认 at-least-once，重复几乎无法根除（网络重试、rebalance、producer 重发）。"消灭重复"是错的，"对重复免疫"才是对的。
> 
> **5-C**　`acks=all`（`acks=-1`）要求 leader 等待所有 ISR 副本确认收到后才返回成功——生产端不丢消息的核心配置。`acks=1` 只等 leader（leader 崩可能丢），`acks=0` 发完不管（最快但最不可靠）。　举一反三：`acks=all` 配合 `min.insync.replicas` 才发挥最大作用——确保至少有几个 ISR 副本存在，防止只有一个副本的风险。
> 
> **6-B**　消费者 A 处理慢，超过 `max.poll.interval` 被判定"卡死"→触发 rebalance→分区重新分配给 B→B 从上次提交的 offset 重拉→A 未提交的消息被重复消费。　举一反三：防 rebalance 重复的三招：① 合理设 `max.poll.interval`；② 业务做幂等；③ 减小单次拉取消息数（`max.poll.records`）让处理时间可控。
> 
> **7-C**　大多数 MQ 默认保证 at-least-once——为了不丢消息宁可重发。at-most-once 可能丢；exactly-once 成本极高。　举一反三：豆豆锐评——"不丢"和"不重"是天平两端。工程界务实选择："at-least-once 保不丢 + 幂等消化重复"。
> 
> **8-A**　生产端：`acks=all`+重试；Broker 端：多副本持久化+`min.insync.replicas`；消费端：手动提交 offset（处理成功后再提交）。三段任一疏漏都可能丢消息。　举一反三：面试被问"怎么保证消息不丢"，按这三段逐一展开说明具体配置和原理 = 真正落地过消息可靠性。
> 
> **9-B**　Kafka 只保证单分区内消息按生产者追加顺序存储和消费，不保证跨分区全局顺序。需要某个业务实体有序就用相同 key。　举一反三：强行全局有序把所有消息塞进一个分区 = 把 Kafka 降级成单线程队列，浪费多分区并行吞吐能力。
> 
> **10-B**　MQ 默认 at-least-once 投递，重复消费几乎无法根除。正确做法不是"消灭重复"而是"让消费逻辑对重复免疫"（幂等）。　举一反三：严格 exactly-once 需事务支持（如 Kafka 事务 API），成本高性能差，绝大多数场景用"at-least-once + 幂等"更务实。

### 二、解答题（3 道）

**1.** 用自己的话解释 MQ 的"削峰填谷"和为什么它不能无限削峰。

**2.** 为什么说"重复消费是常态，不是意外"？幂等性如何具体实现？

**3.** MQ 中消息"不丢"和"不重"为什么是天平的两端？如何权衡？

> [!答案]
> **1**　削峰填谷：请求洪峰到来时消息暂存队列（削峰），后端消费者按自身处理能力匀速消费（填谷），避免突发流量压垮下游。相当于"缓冲蓄水池"。不能无限削峰：若消费速率长期低于生产速率，队列会持续堆积直到磁盘满或触发流控，最终还是需限流或扩容。　举一反三：削峰健壮性取决于消费速率 > 平均生产速率，队列只平滑瞬时抖动而非解决根本容量不足。大促场景下还需前端限流+服务降级组合拳。
> 
> **2**　MQ 遵循 at-least-once 语义，重复来自多种必然场景：① 网络超时后生产重发；② rebalance 时未提交 offset 被新消费者重拉；③ 消费成功但提交 offset 前崩溃。这些不是 Bug 而是分布式系统的正常情况。幂等实现方案：① 数据库唯一约束——最稳定（如 `order_id` 唯一索引）；② Redis 去重——`SETNX` 标记已处理的消息 ID；③ 状态机——消息带版本号，状态不匹配则忽略。　举一反三：方案①最稳、方案②适合高频、方案③适合有明确状态流转。幂等逻辑必须是消费处理的第一步。
> 
> **3**　要"绝不丢"必须重发+确认——生产端重试、Broker 多副本、消费端处理成功才提交。但重试和 rebalance 天然导致重复投递，所以"不丢"的代价是"可能重复"（at-least-once）。要"绝不重"需要严格 exactly-once——生产+消费+Broker 端事务，成本极高。工程界权衡：选"at-least-once 保证不丢 + 业务幂等消化重复"，在成本可控前提下达到"逻辑上的 exactly-once"。　举一反三：记住这个天平 = MQ 一致性面试题答对大半。

### 三、代码题（2 道）

**1.** 写一个 Spring Kafka 消费者方法，消费 `coffee-order` topic 的消息，实现幂等消费——通过制作记录表的 `order_id` 唯一索引去重，包含手动提交 offset。

**2.** 用 Java 的 `BlockingQueue` 模拟生产者和消费者模型：生产者每秒生产一条"订单"消息放入容量为 5 的队列，消费者以 0.5 秒/条处理。队列满时生产者阻塞等待，队列空时消费者阻塞等待。

> [!答案]
> **1 验收**　```java
> @KafkaListener(topics = "coffee-order", groupId = "coffee-maker")
> public void onOrder(String message, Acknowledgment ack) {
>     Order order = fromJson(message);
>     try {
>         makerLogMapper.insert(order.id());  // order_id唯一索引，重复则抛异常
>     } catch (DuplicateKeyException e) {
>         ack.acknowledge();  // 已处理过，直接确认丢弃→幂等
>         return;
>     }
>     makeCoffee(order);
>     ack.acknowledge();  // 处理成功后才提交，防丢
> }
> ```　举一反三：如果业务操作不止一步，幂等判断和后续操作要在同一事务内——先插去重记录，违反唯一约束说明已处理，跳过整个事务。
> 
> **2 验收**　```java
> BlockingQueue<String> queue = new LinkedBlockingQueue<>(5);
> new Thread(() -> {
>     for (int i = 1; i <= 10; i++) {
>         try { queue.put("订单-" + i); Thread.sleep(1000); } // put:满则阻塞（反压）
>         catch (InterruptedException e) { break; }
>     }
> }, "producer").start();
> new Thread(() -> { while (true) {
>     try { String msg = queue.take(); System.out.println("消费: " + msg); Thread.sleep(500); }
>     catch (InterruptedException e) { break; }
> }}, "consumer").start();
> ```　举一反三：`put()` 满时阻塞（反压）、`take()` 空时阻塞。真实 MQ 中 `max.poll.records`、`linger.ms`、`buffer.memory` 等参数共同构成流控体系。
