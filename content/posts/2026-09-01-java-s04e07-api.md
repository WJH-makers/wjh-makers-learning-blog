## 四、API 全景:接口契约

```text
方法   路径                权限        说明
POST   /api/register       公开        注册(密码 BCrypt 加密存储)
GET    /api/menu           公开        浏览菜单
POST   /api/orders         登录        下单(@Valid 校验、扣库存、缺货 409)
POST   /api/admin/coffees  ADMIN       店长上新/改库存

一次下单请求穿过的全链路:
  HTTP → Security 认证授权 → Controller(@Valid 校验)
       → Service(业务规则) → Repository/MyBatis → MySQL
  出错 → @RestControllerAdvice 统一 { code, message } + 状态码
```

这张表就是交给前端的**契约**——他们照着它对接,不用看你的源码。

## 五、代码:补齐 CORS,让前端连得上

前几话已经建好了各层,结局这一步是打通前后端。全局 CORS 配置:

```java
import org.springframework.context.annotation.*;
import org.springframework.web.servlet.config.annotation.*;

@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:5173")   // 允许前端域(生产换成真实域名)
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("*");
    }
}
```

下单接口(整合校验 + 业务 + 安全的最终形态):

```java
@RestController
@RequestMapping("/api")
public class CoffeeController {
    private final CoffeeService service;
    public CoffeeController(CoffeeService service) { this.service = service; }

    @GetMapping("/menu")
    public List<Coffee> menu() { return service.menu(); }

    @PostMapping("/orders")                              // 需登录(Security 拦截)
    public Coffee order(@Valid @RequestBody OrderRequest req) {   // 校验 + 统一异常兜底
        return service.order(req.name(), req.qty());
    }
}
```

## 六、故意制造一个 Bug:忘了 CORS

前端(`http://localhost:5173`)用 `fetch` 调 `http://localhost:8080/api/menu`,后端没配 CORS。

---

## 七、读懂现象:跨域被浏览器拦下

浏览器控制台:

```text
Access to fetch at 'http://localhost:8080/api/menu' from origin
'http://localhost:5173' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

注意:**这不是后端报错**——用 `curl`/Postman 直接调接口是通的。是**浏览器**的**同源策略**在拦:前端域(:5173)和 API 域(:8080)不同源,浏览器要求后端明确回一个 `Access-Control-Allow-Origin` 头表示"我允许它访问"。补上第五节的 CORS 配置即解决。这是几乎每个全栈新手联调时都会撞的墙。

> **豆豆锐评 · CORS 是浏览器的规矩,不是后端的 Bug**
> 记住三点:① 拦截发生在**浏览器**,服务端其实收到了请求;② 它只约束**浏览器发起的跨源请求**,`curl`/服务间调用不受限;③ 生产环境 `allowedOrigins` 要写**具体域名**,别图省事写 `*`(尤其带凭证时,`*` 会被拒)。

> **🎯 面试直击**:什么是单体架构?它的优缺点?
> 咖啡站 v4 就是**单体(Monolith)**:所有功能(用户、菜单、订单)打包成一个应用、一个进程、一个库。优点:**开发简单、部署一个包、调用是本地方法调用、事务好处理**——绝大多数项目该从单体起步。缺点:代码膨胀后**编译慢、一处故障可能拖垮整体、只能整体扩容**。追问:什么时候才拆微服务?当团队/流量大到单体成为瓶颈时——**别一上来就拆**(这正是第六季的主题)。

## 八、端到端测试:核心链路通

```java
@Test
void full_order_flow() throws Exception {
    // 未登录下单 → 401
    mvc.perform(post("/api/orders").contentType("application/json")
            .content("{\"name\":\"美式\",\"qty\":1}"))
       .andExpect(status().isUnauthorized());

    // 带认证下单 → 200,库存扣减
    mvc.perform(post("/api/orders").with(httpBasic("alice", "123456"))
            .contentType("application/json")
            .content("{\"name\":\"拿铁\",\"qty\":2}"))
       .andExpect(status().isOk())
       .andExpect(jsonPath("$.stock").value(3));
}
```

## 🎯 随堂练习

先自己做,再对答案。每道答案都带一句「举一反三」,帮你把这一个点连成一片。

### 选择题(10 道)

1. CORS 报错时,真正拦下请求的是?
   - A) 后端返回了错误　B) **浏览器**的同源策略 —— 服务端其实收到了请求　C) 防火墙　D) Nginx
2. 同一个接口,用 `curl` / Postman 调却是通的,原因是?
   - A) 它们绕过了后端校验　B) CORS 只约束**浏览器发起的跨源请求**,命令行和服务间调用不受限　C) 它们自带跨域权限　D) 缓存命中
3. 浏览器要求后端返回哪个响应头才放行?
   - A) `Content-Type`　B) `Access-Control-Allow-Origin`　C) `Authorization`　D) `Origin`
4. 生产环境 `allowedOrigins` 应该?
   - A) 写 `*` 最省事　B) 写**具体域名** —— 尤其带凭证时 `*` 会被拒　C) 留空　D) 写 IP 段
5. 单体架构(Monolith)的定义是?
   - A) 只有一个类　B) 所有功能打包成一个应用、一个进程、一个库　C) 只能部署一台机器　D) 不能用数据库
6. 单体架构的优点**不包括**?
   - A) 开发简单、部署一个包　B) 调用是本地方法调用,事务好处理　C) 可以按模块独立扩容　D) 排查链路短
7. 关于什么时候拆微服务,本话的建议是?
   - A) 项目一开始就拆　B) 当团队/流量大到单体成为瓶颈时再拆,**别一上来就拆**　C) 只要用了 Spring Boot 就该拆　D) 由框架决定
8. 「接口契约」(路径、方法、权限、响应)的价值是?
   - A) 归档用　B) 前端照着它对接,不用看你的源码　C) 生成代码　D) 满足合规要求
9. 下单时库存不足,这套 API 返回?
   - A) `200` 带错误信息　B) `400`　C) `409` + `{ code: "OUT_OF_STOCK", message: ... }`　D) `500`
10. 一次下单请求穿过的全链路顺序是?
    - A) Controller → Security → Service → Repository　B) **Security 认证授权 → Controller(校验)→ Service(业务)→ Repository → MySQL**　C) Service → Controller → Repository　D) Repository → Service → Controller

> [!答案]
> **1-B**　CORS 是浏览器的规矩,不是后端的 Bug。**举一反三**:所以看日志会发现请求确实到了后端并正常返回,只是响应被浏览器丢弃了。
> **2-B**　同源策略只活在浏览器里。**举一反三**:这也是排查 CORS 的最快手段 —— 先 curl 一下,通了就说明是跨域而非接口问题。
> **3-B**　这个头是浏览器的放行凭证。**举一反三**:复杂请求(自定义头、非简单方法)还会先发一个 `OPTIONS` 预检请求,后端也得正确响应它。
> **4-B**　`*` 与凭证不能共存。**举一反三**:通配放行等于把接口暴露给任意站点的前端,是常见的安全疏漏。
> **5-B**　一个应用、一个进程、一个库。**举一反三**:绝大多数项目该从单体起步 —— 它不是落后方案,而是默认的正确起点。
> **6-C**　按模块独立扩容恰恰是单体做不到的。**举一反三**:只能整体扩容,正是流量压力上来后拆分的核心动机之一。
> **7-B**　别一上来就拆。**举一反三**:过早微服务化会把「本地方法调用」变成「网络调用 + 分布式事务」,复杂度暴涨而收益为零。
> **8-B**　契约是前后端的共同语言。**举一反三**:用 OpenAPI/Swagger 把契约变成可执行文档,联调效率会再上一个台阶。
> **9-C**　409 表示状态冲突,配统一错误体。**举一反三**:这是第 37 话统一异常处理的成果 —— 每种错误都有稳定的 code,前端能可靠地分支处理。
> **10-B**　安全在最外层,数据在最里层。**举一反三**:记住这条链路,线上排障时就能快速判断「问题出在哪一层」。
