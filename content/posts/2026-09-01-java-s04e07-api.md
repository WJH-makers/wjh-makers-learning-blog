## 四、API 全景:接口契约

```text
方法   路径                权限        说明
POST   /api/register       公开        注册(密码 BCrypt 加密存储)

```

这张表就是交给前端的**契约**——他们照着它对接,不用看你的源码。

## 五、代码:补齐 CORS,让前端连得上

前几话已经建好了各层,结局这一步是打通前后端。全局 CORS 配置:

```java
import org.springframework.context.annotation.*;
import org.springframework.web.servlet.config.annotation.*;

@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:5173")   // 允许前端域(生产换成真实域名)
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("*");
    }
}
```

下单接口(整合校验 + 业务 + 安全的最终形态):

```java
@RestController
@RequestMapping("/api")
public class CoffeeController {
    private final CoffeeService service;
    public CoffeeController(CoffeeService service) { this.service = service; }

    @GetMapping("/menu")
    public List<Coffee> menu() { return service.menu(); }

    @PostMapping("/orders")                              // 需登录(Security 拦截)
    public Coffee order(@Valid @RequestBody OrderRequest req) {   // 校验 + 统一异常兜底
        return service.order(req.name(), req.qty());
    }
}
```

## 六、故意制造一个 Bug:忘了 CORS

前端(`http://localhost:5173`)用 `fetch` 调 `http://localhost:8080/api/menu`,后端没配 CORS。

---

## 七、读懂现象:跨域被浏览器拦下

浏览器控制台:

```text
Access to fetch at 'http://localhost:8080/api/menu' from origin
'http://localhost:5173' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

注意:**这不是后端报错**——用 `curl`/Postman 直接调接口是通的。是**浏览器**的**同源策略**在拦:前端域(:5173)和 API 域(:8080)不同源,浏览器要求后端明确回一个 `Access-Control-Allow-Origin` 头表示"我允许它访问"。补上第五节的 CORS 配置即解决。这是几乎每个全栈新手联调时都会撞的墙。

> **豆豆锐评 · CORS 是浏览器的规矩,不是后端的 Bug**
> 记住三点:① 拦截发生在**浏览器**,服务端其实收到了请求;② 它只约束**浏览器发起的跨源请求**,`curl`/服务间调用不受限;③ 生产环境 `allowedOrigins` 要写**具体域名**,别图省事写 `*`(尤其带凭证时,`*` 会被拒)。

> **🎯 面试直击**:什么是单体架构?它的优缺点?
> 咖啡站 v4 就是**单体(Monolith)**:所有功能(用户、菜单、订单)打包成一个应用、一个进程、一个库。优点:**开发简单、部署一个包、调用是本地方法调用、事务好处理**——绝大多数项目该从单体起步。缺点:代码膨胀后**编译慢、一处故障可能拖垮整体、只能整体扩容**。追问:什么时候才拆微服务?当团队/流量大到单体成为瓶颈时——**别一上来就拆**(这正是第六季的主题)。

### 一、选择题(10 道)
1. [基础]RESTful API 的 URL 设计原则,以下哪个是正确的?
- A) `GET /getOrders`(动词)　B) `GET /orders`(名词复数)　C) `POST /createOrder`(动词)　D) `GET /api?action=getOrders`(参数)
> [!答案] **1-B**　RESTful 核心:URL 代表资源(名词,通常复数),HTTP 方法代表操作——`GET /orders` 查订单,`POST /orders` 创建。**举一反三**:层级关系用 URL 路径表达:`/orders/{id}/items` 表示某订单的行项目;避免在 URL 中放动词。

2. [进阶]CORS 跨域问题的根本原因是什么?
- A) 后端接口报错　B) 浏览器的**同源策略**阻止了不同域名/端口的请求,必须由后端明确返回 `Access-Control-Allow-Origin` 头表示允许　C) 网络断了　D) 前端代码写错了
> [!答案] **2-B**　同源策略要求协议、域名、端口三者一致才叫"同源"。前端(:5173)调后端(:8080)端口不同→浏览器拦截。注意:**不是后端报错**——用 curl 直接调是通的,拦截发生在浏览器。**举一反三**:CORS 只约束**浏览器发起的跨源请求**,服务间调用、curl 不受限;生产环境 `allowedOrigins` 要写具体域名,别图省事写 `*`。

3. [深入]Spring Boot 中配置全局 CORS 的正确方式是?
- A) 在每个 Controller 方法里写 `response.addHeader`　B) 实现 `WebMvcConfigurer`,重写 `addCorsMappings(CorsRegistry registry)`　C) 修改 `application.yml` 里的 `server.cors` 配置　D) 不需要配置,自动支持
> [!答案] **3-B**　`@Configuration` 类 `implements WebMvcConfigurer`,重写 `addCorsMappings()`,全局设置允许的源、方法、头。**举一反三**:`@CrossOrigin` 注解可作用于单个 Controller 或方法——适合临时或差异化的跨域策略;全局 CORS 配置更适合统一管理。

4. [基础]非简单请求(如 Content-Type:application/json)跨域时,浏览器会先发什么请求?
- A) 直接发真实请求　B) 先发 `OPTIONS` 预检请求(Preflight),验证服务器是否允许跨域,通过后才发真实请求　C) 发两次 POST　D) 不检查,直接跨域
> [!答案] **4-B**　非简单请求(含 JSON、自定义 Header 等)浏览器先发 `OPTIONS` 预检,服务器返回允许的源/方法/头,通过后才发真实请求。简单的 GET/POST(form) 不触发预检。**举一反三**:如果后端没配 CORS,OPTIONS 请求会返回 403——前端看到的报错是"No Access-Control-Allow-Origin header"。

5. [进阶]什么是单体架构(Monolith)?它的核心优缺点是什么?
- A) 越复杂越好　B) 所有功能(用户、菜单、订单)打包成一个应用、一个进程、一个库——开发简单、调用是本地方法、事务好处理;但代码膨胀后编译慢、一处故障可能拖垮整体、只能整体扩容　C) 和微服务完全相同　D) 已经过时的架构
> [!答案] **5-B**　咖啡站 v4 就是单体:"一个 jar 包跑起来就是全部功能"。优点:开发部署简单、本地方法调用不经过网络、事务天然支持。缺点:团队大了代码耦合严重,一处 OOM 全站挂,只能整包扩容。**举一反三**:绝大多数项目该从单体起步——在规模真的成为瓶颈之前,单体的简单是一种巨大的优势。第六季才会讨论什么时候拆微服务。

### 二、解答题(3 道)
1. [概念]用自己的话解释 CORS 跨域问题:它发生在哪一层(浏览器还是服务器),为什么会出现,Spring Boot 如何解决。
> [!答案] **1**　CORS 是**浏览器的安全策略**(同源策略),不在服务器端。浏览器禁止一个域(A)的 JavaScript 直接访问另一个域(B)的 API——即便 B 的接口是通的(curl 可以调通)。解决:后端在响应头中加 `Access-Control-Allow-Origin: http://A-host`,告知浏览器"我允许 A 来访问"。Spring Boot 通过实现 `WebMvcConfigurer.addCorsMappings()` 全局配置,或 `@CrossOrigin` 注解单接口配置,自动给响应加上这些头。**举一反三**:跨域只影响**浏览器→后端**的场景;两个后端服务之间互调(服务间调用)不受同源策略限制——它只约束运行在浏览器里的代码。

2. [场景]前后端联调时,前端(`localhost:3000`)调后端(`localhost:8080/api/menu`)报 CORS 错,而 Postman 调通。请解释为什么 Postman 能通,并写出完整的 CORS 配置修复代码。
> [!答案] **2**　为什么 Postman 能通:Postman 不是浏览器,不运行在网页的 JavaScript 环境里,不受浏览器同源策略约束——它直接发 HTTP 请求,没有"跨源"的概念。修复配置:`@Configuration class CorsConfig implements WebMvcConfigurer { @Override public void addCorsMappings(CorsRegistry registry) { registry.addMapping("/api/**").allowedOrigins("http://localhost:3000").allowedMethods("GET","POST","PUT","DELETE").allowedHeaders("*"); }}`。**举一反三**:这个问题的翻版在生产中就是"Nginx 后面能通,浏览器里不行"——排查的顺序:先用 curl 确认后端确实通→再查 CORS 头有没有正确返回→最后看浏览器的 OPTIONS 预检是否被 Nginx/防火墙拦截。

3. [综合]第四季大结局交付的是"Spring Boot 单体 v4"。从系统演进的视角,解释"单体"为什么是合理的第四季终点,以及它在什么情况下会成为瓶颈(为什么需要第五季的并发和第六季的分布式)。
> [!答案] **3**　①单体是合理的终点:第四季的目标是"从零交付一个完整后端",而非"上分布式"。单体的简单性——一个 jar 包、一个进程、本地方法调用、单库事务——让阿零能专注学"业务应该怎么分层、数据应该怎么持久化、安全应该怎么控权",而不是被分布式复杂度(网络分区、数据一致性、服务发现)淹没。②何时成为瓶颈:**并发量**上来后,一个进程的 CPU/内存/连接池有上限(第五季学线程池和 GC 调优就是在单体内部极限优化);**流量**再翻十倍,一台机器再也扛不住(第六季拆微服务、多实例负载均衡);**单点故障**——这台机器一挂,全站宕机,没有容错。③这就是连载的脉络:第四季=从零到有,第五季=从有到稳,第六季=从稳到无限扩容——每一步都解决上一步的真实瓶颈。**举一反三**:面试中"为什么选单体而不是微服务"的标准答案:起步阶段团队小、流量低、业务在快速试错,单体的简单本身就是最大的资产——别为解决"假设中的未来瓶颈"而牺牲当前的开发效率。

### 三、代码题(2 道)
1. [基础]写一个 `CorsConfig` 类:允许 `http://localhost:3000` 跨域访问所有 `/api/**` 路径,支持 GET/POST/PUT/DELETE,允许所有头。实现 `WebMvcConfigurer` 接口。
> [!答案] **1 验收**:
> ```java
> @Configuration
> class CorsConfig implements WebMvcConfigurer {
>     @Override
>     public void addCorsMappings(CorsRegistry registry) {
>         registry.addMapping("/api/**")
>                 .allowedOrigins("http://localhost:3000")
>                 .allowedMethods("GET", "POST", "PUT", "DELETE")
>                 .allowedHeaders("*");
>     }
> }
> ```
> **举一反三**:`addMapping` 支持通配符(`/api/**` 匹配 `/api/menu`、`/api/orders/1` 等);如果需要凭证(cookie/Authorization 头),设置 `.allowCredentials(true)` 且 `allowedOrigins` 必须写具体域名,不能用 `*`。

2. [综合]写一个端到端测试,验证第四季完整的"下单链路":①未登录下单→401;②带错误参数(负数 qty)下单→400;③合法参数下单→200,响应体包含 `stock` 字段且值正确减少。使用 `@SpringBootTest` + `@AutoConfigureMockMvc` + `@WithMockUser`。
> [!答案] **2 验收**:
> ```java
> @SpringBootTest
> @AutoConfigureMockMvc
> class FullOrderFlowTest {
>     @Autowired MockMvc mvc;
> 
>     @Test
>     void order_without_auth_returns_401() throws Exception {
>         mvc.perform(post("/api/orders").contentType("application/json")
>                 .content("{\"name\":\"美式\",\"qty\":1}"))
>            .andExpect(status().isUnauthorized());
>     }
> 
>     @Test
>     @WithMockUser(username = "alice", roles = "USER")
>     void order_negative_qty_returns_400() throws Exception {
>         mvc.perform(post("/api/orders").contentType("application/json")
>                 .content("{\"name\":\"美式\",\"qty\":-1}"))
>            .andExpect(status().isBadRequest());
>     }
> 
>     @Test
>     @WithMockUser(username = "alice", roles = "USER")
>     void valid_order_returns_200_and_reduces_stock() throws Exception {
>         mvc.perform(post("/api/orders").contentType("application/json")
>                 .content("{\"name\":\"拿铁\",\"qty\":2}"))
>            .andExpect(status().isOk())
>            .andExpect(jsonPath("$.stock").exists());
>     }
> }
> ```
> **举一反三**:这三个测试覆盖了第四季的三层防线——认证门(401)、校验门(400)、业务层(200)——正好验证"安全→校验→业务"的完整链路通畅;`@WithMockUser` 让你无需真实登录就能测试权限,专注测各层逻辑。
