## 一、事故：CPU 没满，P99 却每隔十几秒跳一次

## 三、本话目标

- 分清 STW 停顿与并发阶段，别把 collection 总时长当停顿；
- 读懂 `-Xlog:gc*` 日志里 Young / Mixed / Full 的区别；
- 说清分代 ZGC 与非分代 ZGC 的差别与版本边界；
- 用 JFR 与 `jstat` 拿到自己服务的停顿分布；
- 按延迟、吞吐、内存三个约束做 GC 选型，不照抄别人的参数。

---

接上一话：JIT 管的是**每条指令跑多快**，GC 管的是**会不会突然全停下来**。上一话预热之后短跑数字很漂亮，正是因为跑得短——短到 GC 还没来得及插手。压测一拉长，第二个变量就露头了。

两者的观测方式也不同：JIT 看 `PrintCompilation` 的编译事件，GC 看日志里的 `Pause` 行。**混在一起看就会把 GC 停顿误判成代码变慢。**

## 五、从上一话继续改代码：GC 日志与 JFR 观察

```java
// javac -encoding UTF-8 --release 25 GcDemo.java
// 运行：java -Xmx256m -Xms64m -Xlog:gc*:file=gc.log:time,level,tags \
//            -XX:+UseZGC GcDemo
// 或：   java -Xmx256m -Xms64m -Xlog:gc* -XX:+UseG1GC GcDemo
import java.util.*;
import java.util.concurrent.*;

class GcDemo {

    // 模拟高分配速率（咖啡站订单处理）
    static void simulateHighAllocation(int rounds) throws Exception {
        List<byte[]> survivor = new ArrayList<>();
        Random rng = new Random(42);

        for (int i = 0; i < rounds; i++) {
            // 模拟短生命周期对象（每次请求的临时 DTO）
            for (int j = 0; j < 1000; j++) {
                byte[] tmp = new byte[1024]; // 1KB 短暂对象
                // 随机让少量对象晋升老年代
                if (rng.nextInt(100) < 2) {
                    survivor.add(tmp);
                }
            }
            if (i % 100 == 0) {
                System.out.printf("round %d, survivor=%d KB%n",
                    i, survivor.size());
            }
            // 偶尔释放老年代对象
            if (survivor.size() > 500) {
                survivor.subList(0, 200).clear();
            }
            Thread.sleep(1); // 1ms 间隔，模拟请求流
        }
    }

    // 用 JFR API 录制 GC 事件
    static void jfrGcRecord() throws Exception {
        var config = jdk.jfr.Configuration.getConfiguration("default");
        try (var recording = new jdk.jfr.Recording(config)) {
            recording.enable("jdk.GarbageCollection");
            recording.enable("jdk.YoungGarbageCollection");
            recording.enable("jdk.OldGarbageCollection");
            recording.enable("jdk.GCHeapSummary");
            recording.start();

            simulateHighAllocation(500);

            recording.stop();
            var tmp = java.nio.file.Files.createTempFile("gc-", ".jfr");
            recording.dump(tmp);

            // 统计 GC 事件
            long gcCount = 0, totalPause = 0, maxPause = 0;
            try (var stream = jdk.jfr.consumer.EventStream.openFile(tmp)) {
                stream.onEvent("jdk.GarbageCollection", e -> {
                    // duration 单位 ms（JFR 时间字段）
                });
                stream.onEvent("jdk.YoungGarbageCollection", e -> {
                    System.out.printf("  YoungGC: %s pause=%dµs%n",
                        e.getString("cause"),
                        e.getDuration("pause").toMicros());
                });
                stream.start();
            }
            java.nio.file.Files.delete(tmp);
        }
    }

    // 演示显式堆分析（不同 GC 配置下的对比）
    static void heapStats() {
        Runtime rt = Runtime.getRuntime();
        long usedBefore = rt.totalMemory() - rt.freeMemory();
        System.out.printf("堆使用: %,d KB / %,d KB (max %,d KB)%n",
            usedBefore / 1024,
            rt.totalMemory() / 1024,
            rt.maxMemory() / 1024);
    }

    public static void main(String[] args) throws Exception {
        System.out.println("=== GC Demo（-XX:+UseZGC 分代）===");
        heapStats();

        long t = System.currentTimeMillis();
        simulateHighAllocation(300);
        System.out.printf("300轮分配完成，耗时 %dms%n",
            System.currentTimeMillis() - t);

        heapStats();
        System.out.println("查看 gc.log 获取 GC 详情");
    }
}
```

```

# 分代 ZGC Young GC：
[1.234s][info][gc] GC(3) Minor Collection   45M->18M(256M)  0.234ms   ← <1ms

# 分代 ZGC Old GC（并发，不停炉）：
[3.456s][info][gc,phases] GC(7) Major Collection (Concurrent)
```

## 六、故意翻一次车：四种误读，阿零中了两种

阿零看完日志的第一反应是"换 ZGC 就完事了"。焰焰让他先把下面四条对照一遍——他中了第 1 和第 4 条。

```bash
# ❌ 陷阱 1：ZGC 下堆太小，触发 Allocation Stall
# ZGC 需要并发清理，堆必须足够大以容纳并发分配和并发 GC 共存
# 日志出现：[GC] Allocation Stall  → 调大堆或降低分配速率
-Xmx4g -Xms4g   # ✅ 生产建议：Xmx=Xms，避免堆动态扩展停顿

# ❌ 陷阱 2：G1 Full GC 退化（频繁出现 "Pause Full"）
# 原因：Mixed GC 速度跟不上老年代增长；或堆太小
# ✅ 调优方向：
-XX:G1HeapRegionSize=16m     # 增大 Region，减少碎片
-XX:G1NewSizePercent=30      # 调大新生代比例，减少晋升频率
-XX:MaxGCPauseMillis=50      # G1 目标停顿 50ms（软目标，不是硬保证）

# ❌ 陷阱 3：在 ZGC 下用 System.gc() 强制 Full GC
# 不要假设 ZGC 会忽略 System.gc()；先查启动参数与日志。
# 若业务确认不允许显式 GC,可显式禁用：
-XX:+DisableExplicitGC

# ❌ 陷阱 4：误读 GC 停顿——把并发时间算进去
# ZGC 日志中大部分时间是「并发阶段」（不停世界），只有极短的 STW
# 停顿时间 = 只看 "Pause" 字样的事件，不是 collection 总时长

# ✅ 选型速决：
# 延迟 P99 < 10ms 硬要求？    → 把 ZGC 列为候选并压测
# 吞吐量优先，停顿可到 100ms？ → G1（默认配置即可）
# 容器/低内存（<1GB 堆）？     → Serial GC（-XX:+UseSerialGC）
# 批处理/数据管道？            → Parallel GC（-XX:+UseParallelGC）
```

阿零的两个错：一是他的堆只给了 256m 就想上 ZGC（陷阱 1）；二是他把日志里 collection 的总时长当成了停顿（陷阱 4）——那 280ms 里真正 STW 的只有一小段。

## 八、修复并验证

修的是两件事：**先把堆给够，再决定要不要换收集器**。顺序反了会得到错误结论——堆不够的 ZGC 可能比堆够的 G1 更差。

验证判据四条：

1. **停顿口径正确**：只统计日志里带 `Pause` 的行，不把 `Concurrent` 阶段算进去。
2. **Full GC 归零**：`jstat -gcutil` 的 `FGC` 列在整轮压测中不再增长。
3. **P99 与 GC 事件解耦**：JFR 里的 `jdk.GarbageCollection` 时间点不再对应 P99 尖峰。
4. **换收集器要有对照**：同一份负载、同一个堆大小，G1 与 ZGC 各压一轮，比的是自己的两组数据，不是别人博客里的数字。

第 4 条是这一话最该记住的：**GC 选型没有标准答案，只有你自己压出来的答案。**

## 九、🔬 炉底显微镜 · 停顿分布从哪里读

```bash
# 开启 GC 日志（生产级别配置）
java -Xmx4g -Xms4g \
     -XX:+UseZGC \
     -Xlog:gc*:file=/var/log/app-gc.log:time,level,tags:filecount=5,filesize=20m \
     MyApp

# 实时查看 GC 频率和停顿
jcmd <pid> GC.heap_info
jcmd <pid> VM.flags | grep -E "GC|Heap"

# JFR 录制 GC 事件（生产安全，开销<1%）
jcmd <pid> JFR.start name=GCProfile settings=profile filename=/tmp/gc.jfr duration=60s
jcmd <pid> JFR.stop name=GCProfile

# JFR 报告：GC 停顿分布
jfr print --events jdk.GarbageCollection,jdk.YoungGarbageCollection /tmp/gc.jfr \
  | grep -E "duration|cause|pause"

# 查看当前 GC 统计（不重启）
jstat -gcutil <pid> 1000 10
# 输出：S0  S1  E    O    M     CCS  YGC  YGCT  FGC  FGCT  CGC  CGCT  GCT
# E=Eden占用%, O=老年代占用%, YGC=Young GC次数, FGC=Full GC次数（越少越好）

# 验证 ZGC 是否真的 <1ms：
jfr print --events jdk.YoungGarbageCollection /tmp/gc.jfr \
  | awk -F'duration = ' '{print $2}' | sort -n | tail -10
```

**分代 ZGC 内部机制要点**：
- 染色指针（Colored Pointers）：在 64 位指针的高位编码对象 GC 状态（Marked0/Marked1/Remapped），读屏障（Load Barrier）在每次对象引用读取时检查并修复指针——这是 ZGC 并发不停炉的核心机制
- 分代化后：Young Region 独立维护 remembered set，Old→Young 的跨代引用通过写屏障记录；Young GC 只扫描 Young Region + remembered set，大幅减少扫描范围，提升吞吐量

## 十、⏳ 版本时光机 · ZGC 从实验到唯一实现

**版本边界**

| 特性 | JDK | 说明 |
|---|---|---|
| G1 GC 正式 | **JDK 7u4** | |
| G1 成为默认 GC | **JDK 9** | 替代 Parallel GC |
| ZGC（实验）| **JDK 11** | JEP 333 |
| ZGC 正式 | **JDK 15** | JEP 377 |
| 分代 ZGC 引入 | **JDK 21** | JEP 439,可与非分代模式切换 |
| 分代模式成为 ZGC 默认 | **JDK 23** | JEP 474；不是把 ZGC 设为 JDK 默认收集器 |
| 非分代 ZGC 移除 | **JDK 24** | JEP 490；`-XX:+UseZGC` 只剩分代实现 |
| Shenandoah 正式 | **JDK 15** | JEP 379，非 Oracle JDK |
| 本话代码运行环境 | JDK 25 | ✅ |

> [!坑] 这张表最容易记错的是最后两行的关系。**「分代成为 ZGC 的默认模式」不等于「ZGC 成为 JDK 的默认收集器」**——JDK 25 的默认收集器仍是 G1，`-XX:+UseZGC` 必须你自己写上。

---

> [!答案]
>
> **Q1. 分代 ZGC 把对象按年龄组织,通过 remembered set 追踪跨代引用,让常见回收不必处理整个堆。**这通常改善回收效率,但不存在对所有工作负载都成立的“吞吐固定提升 30%”或“每次必低于 1ms”保证；必须以 GC 日志与压测数据为准。
>
> **Q2. 只看日志中带 "Pause" 关键字的行——那才是 Stop-The-World 停顿时间（单位 ms）。**ZGC 的大部分工作（标记、重定位、引用处理）是并发执行的，日志中显示为 "Concurrent" 阶段，这段时间 JVM 正常运行，不是停顿。误把 collection 总时长当停顿时间是常见错误——ZGC 一次 collection 可能花 100ms，但其中 STW 只有 0.3ms。
>
> **Q3. 常见原因：①分配速率过高，Mixed GC 回收老年代速度跟不上晋升速度（Concurrent Mode Failure）；②堆碎片化严重，大对象无法分配到连续 Region；③堆太小。**避免方法：调大堆（`-Xmx`）、增大 G1 Region（`-XX:G1HeapRegionSize`）、降低 Mixed GC 触发阈值（`-XX:InitiatingHeapOccupancyPercent`，默认 45，可降到 25~35）、控制晋升速率（调大新生代比例）。
>
> **Q4. 染色指针在 64 位地址的高位编码 GC 元数据（Marked0/Marked1/Remapped 等状态位），让 GC 线程和应用线程并发工作时，通过读屏障（Load Barrier）在每次读取对象引用时自动检查并修正陈旧指针。**传统 GC（如 G1）需要 STW 才能安全移动对象（否则应用线程读到旧地址）；ZGC 通过染色指针 + 读屏障实现并发重定位——应用线程读到旧地址时，读屏障自动把它修正为新地址，无需停世界。
>
> **Q5. `FGC` 列表示 Full GC 次数。理想值：0（或极少，如每天 0~1 次）。**`FGC > 0` 且频繁出现是严重性能问题信号，意味着老年代 GC 无法并发处理，退化为 STW Full GC。ZGC 下正常运行不应出现 FGC；G1 下偶尔 1 次可接受，频繁出现需调优。
>
> **Q6. 堆动态扩展本身需要向 OS 申请内存，触发 `mmap/brk` 系统调用，有延迟；扩展过程中可能触发额外 GC（G1 需要扩展 Region 池）。**`-Xmx = -Xms` 让 JVM 启动时直接预留最大堆内存，避免运行时扩展带来的停顿抖动——对延迟敏感服务尤其重要。代价是启动就占用全部堆内存，容器环境需确保预留足够内存。
>
> **Q7. 软目标（Soft Goal）。**G1 会尽力满足 `MaxGCPauseMillis`，但不保证。若回收压力过大（老年代增长过快、Region 碎片严重），G1 可能超过目标停顿时间甚至触发 Full GC。设置过小（如 10ms）反而可能导致 G1 每次只回收少量 Region，回收速度跟不上分配，反而增加 Full GC 风险。建议：根据实测 P99 停顿设置，通常 50~200ms 是合理范围。
>
> **Q8. Allocation Stall（分配停滞）：应用线程尝试分配对象时，堆空间不足（GC 并发回收速度跟不上分配速率），应用线程被迫等待 GC 释放空间，表现为请求延迟突增。**ZGC 下出现 Allocation Stall 的原因通常是：堆太小（GC 与分配竞争空间）、分配速率过高（每秒产生 GB 级短暂对象）、GC 线程数不足。解决：调大堆、增加 GC 并发线程数（`-XX:ConcGCThreads`）、降低分配速率。
>
> **Q9. Remembered Set 记录老年代对象指向年轻代对象的引用（跨代引用）。**Young GC 只扫描年轻代时，必须知道有哪些老年代对象引用了年轻代对象（否则可能错误回收仍被老年代引用的年轻代对象）。没有 remembered set，Young GC 就必须扫描全堆才安全。分代 ZGC 通过写屏障（Write Barrier）在每次写入老年代引用时更新 remembered set，使 Young GC 只需扫描年轻代 + remembered set，大幅减少扫描范围。
>
> **Q10. P99 < 5ms 硬要求时,把 ZGC（`-XX:+UseZGC`）列为优先候选,但仍要用真实堆大小、分配速率和容器 CPU 配额压测。**批处理数据管道可比较 Parallel GC 与 G1 的总吞吐；选择来自数据,不是收集器名称。JDK 25 的默认收集器仍是 G1。
