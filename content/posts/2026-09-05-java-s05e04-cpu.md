## 一、事故:CPU 100%,却没有一行报错

> **事故报告 · INC-0925**
> 时间:14:07 · 现象:coffee-api 单节点 CPU 持续 100%,风扇狂转,`/api/menu` 平均响应从 20ms 涨到 2s。
> 反常点:**日志里没有任何 Exception**,服务没崩、还在跑,就是慢得要死。

阿零第一反应是翻日志,翻了十分钟一无所获。豆豆:「别翻了。**没有报错的故障,才最考验人**。程序没抛异常,说明它不是『出错了』,而是『在拼命干一件蠢事』——比如某个线程陷进了**死循环**,把一整颗 CPU 核吃满了。日志帮不了你,得靠**排障命令**去 JVM 内部抓现行。」

## 二、漫画 · 抓那个偷偷空转的线程

> **〔1〕** 咖啡站后厨,一个工人线程站在原地**疯狂空转**——手上没活,却一秒挥手一万次,满头大汗,把整个后厨的电(CPU)全耗光了。其他工人想干活却抢不到电。
> 阿零:「这家伙……在干嘛?活儿早没了他还在挥手!」

> **〔2〕** 豆豆掏出**听诊器**(`top`),往服务器胸口一贴:「先别猜。CPU 是哪个**进程**在吃?」屏幕上 `java` 那一行 `%CPU` 高达 `398%`——四个核快占满了。
> 豆豆:「进程锁定。可一个进程里几百个线程,是**哪个线程**在空转?」

> **〔3〕** 豆豆把听诊器往里探一层(`top -Hp`),精确到**线程**级:一个 tid 单独占了 `99.9%`,其余都很闲。
> 豆豆(叼豆子):「凶手线程找到了。可 `top` 给的是十进制线程号,`jstack` 里认的是**十六进制**,得先换算。」

> **〔4〕** `printf '%x'` 一转,`jstack` 一抓,那条线程的调用栈"哗"地摊开在阿零面前,状态 `RUNNABLE`,死死卡在一段 `while` 循环里。
> 阿零(瞪大眼):「是我上一话为了『重试扣库存』写的那个 `while`!条件永远不满足,它就一直转!」豆豆:「破案了。**报错不会告诉你的事,线程栈会。**」

## 三、本话目标

- 建立"无报错故障"的排障心智:CPU 高 = 有线程在空转/热点计算;
- 掌握定位热点线程的**真实五步**:`top` → `top -Hp` → `printf` 换算 → `jstack` → 读栈;
- 读懂 `jstack` 里的线程状态(`RUNNABLE`/`BLOCKED`)和调用栈;
- 分清"死循环吃 CPU"和"锁竞争 BLOCKED"两类高 CPU 病因;
- 修复那个偷偷空转的重试循环。

## 四、排障五步:从一台机器到一行代码

```text
第 1 步  top                     哪个进程在吃 CPU?→ 记下 java 的 PID(如 12345)
第 2 步  top -Hp 12345           这个进程里哪个线程在吃?→ 记下线程 PID(十进制,如 12362)
第 3 步  printf '%x\n' 12362     十进制 → 十六进制(得到 304a)→ jstack 里的 nid
第 4 步  jstack 12345 | ...      抓全部线程栈,搜 nid=0x304a 那一段
第 5 步  读栈                    看它 RUNNABLE 卡在哪个方法的哪一行 → 定位源码

一句话:先锁进程,再锁线程,再把线程号翻译成 jstack 认识的十六进制,最后读栈。
```

为什么要换算十六进制?因为 `top` 显示的线程 ID 是**十进制**,而 `jstack` 输出里每条线程的 `nid`(native id)是**十六进制**。这一步换算是新手最容易卡住的地方——记住 `printf '%x\n'` 就行。

## 五、命令:一步步把凶手线程逼出来

**第 1 步** —— 哪个进程在烧 CPU:

```text
$ top
  PID USER   %CPU  %MEM   TIME+   COMMAND
12345 app   398.7  12.3  88:41.20 java     ← 就是它,快占满 4 个核
  901 app     0.3   0.1   0:12.01 sshd
```

**第 2 步** —— 进程里哪个线程在烧(`-H` 展开线程,`-p` 指定进程):

```text
$ top -Hp 12345
  PID USER   %CPU  %MEM   TIME+   COMMAND
12362 app    99.9   0.0  42:15.77 java     ← 单个线程独占一个核,凶手
12363 app     0.1   0.0   0:00.03 java
12345 app     0.0   0.0   0:00.10 java
```

**第 3 步** —— 十进制线程号转十六进制:

```text
$ printf '%x\n' 12362
304a
```

**第 4 步** —— `jstack` 抓线程快照,只看 `nid=0x304a` 那一段(`-A 15` 顺带打印后 15 行栈):

```text
$ jstack 12345 | grep -A 15 'nid=0x304a'
"coffee-worker-7" #38 prio=5 os_prio=0 cpu=2535912.44ms tid=0x00007f... nid=0x304a runnable [0x00007f2b3c1fe000]
   java.lang.Thread.State: RUNNABLE
	at com.coffee.CoffeeService.retryDeduct(CoffeeService.java:57)
	at com.coffee.CoffeeService.order(CoffeeService.java:41)
	at com.coffee.OrderController.lambda$submit$0(OrderController.java:29)
	at java.base/java.util.concurrent.ThreadPoolExecutor.runWorker(ThreadPoolExecutor.java:1144)
	at java.base/java.lang.Thread.run(Thread.java:1583)
```

三个关键信号:① 线程名 `coffee-worker-7`——上一话坚持给线程起名,此刻回报了,一眼知道是咖啡站出杯工人;② 状态 `RUNNABLE`——它在**真跑**(不是等锁),典型的死循环/热点计算特征;③ 栈顶 `CoffeeService.java:57`——凶手就在这一行。

**第 5 步** —— 翻到 `CoffeeService.java:57`,真相大白。

## 六、故意制造一个 Bug:一个永远转不出去的重试循环

阿零上一话为了"库存不足时重试几次",随手写的:

```java
// CoffeeService.java —— 看似人畜无害的"自旋重试"
private boolean retryDeduct(String name, int qty) {
    while (true) {                          // 57 行:无条件死循环
        if (tryDeduct(name, qty)) {
            return true;
        }
        // ← 忘了两件致命的事:没有重试次数上限、没有任何等待/让出 CPU
    }                                       // 库存长期不足时,这里就是纯烧 CPU 的空转
}
```

平时库存充足,`tryDeduct` 一次就成功,你根本发现不了。可一旦某款豆子**售罄**,`tryDeduct` 永远返回 `false`,这个 `while(true)` 就以最高速度空转,一个线程独吞一整颗 CPU 核。

---

## 七、读懂现象 + 修复:给重试装上"刹车"

现象已由第五节的 `jstack` 坐实:`RUNNABLE` + 卡在 `while` 行 = **CPU 密集型死循环**。(对照:如果状态是 `BLOCKED`,那是**锁竞争**,得去看它 `waiting to lock` 哪个锁、谁持有——那是另一类高 CPU,病因在锁不在循环。)

修复:重试必须有**次数上限**和**退避等待**,别让它裸奔:

```java
private boolean retryDeduct(String name, int qty) {
    for (int attempt = 0; attempt < 3; attempt++) {   // ① 最多重试 3 次,有终点
        if (tryDeduct(name, qty)) {
            return true;
        }
        try {
            Thread.sleep(20L * (attempt + 1));        // ② 退避等待:让出 CPU,不空转
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();        // ③ 正确响应中断,不吞掉信号
            return false;
        }
    }
    return false;   // 3 次仍失败 → 老实返回"缺货",交给上层提示顾客
}
```

改完重新抓一次 `top -Hp`,那个 99.9% 的线程消失了,CPU 回落到个位数。

> **豆豆锐评 · 高 CPU 的两张面孔,jstack 里长得不一样**
> ① **死循环/热点计算**:目标线程 `RUNNABLE`,栈顶稳定停在某个业务方法——像本话。② **锁竞争**:大量线程 `BLOCKED`,栈里写着 `waiting to monitor entry` / `waiting to lock <0x...>`,而某一条线程 `RUNNABLE` 持有那把锁——CPU 也会高(疯狂上下文切换)。**排障口诀:CPU 高先看热点线程是 RUNNABLE 还是 BLOCKED,方向立刻分岔。** 另外抓 `jstack` 要**连抓两三次**,间隔一两秒——每次都停在同一行的,才是真凶。

> **🎯 面试直击**:线上 CPU 100% 你怎么排查?
> 标准答法就是本话五步:**`top` 定位进程 → `top -Hp <pid>` 定位线程 → `printf '%x'` 把线程号转十六进制 → `jstack <pid>` 抓栈、按 `nid` 找到那条线程 → 读栈定位到具体代码行**。追问会问"怎么区分死循环还是锁竞争":看目标线程状态——`RUNNABLE` 卡在业务代码是死循环/热点,大片 `BLOCKED` 是锁竞争。再追问"生产不让装工具怎么办":`top`/`jstack` 都是 JDK 自带、零依赖,这正是它们的价值(进阶可提 Arthas / async-profiler 出火焰图,但基本功是这五步)。

## 八、用测试证明:重试有界、会正常放弃

CPU 死循环本身难写单元测试,但它的**根因——"重试没有上限"**完全可测:给一个永远缺货的场景,断言方法能在有限时间内返回 `false`,而不是转到天荒地老:

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.Timeout;
import java.util.concurrent.TimeUnit;
import static org.junit.jupiter.api.Assertions.*;

class RetryTest {
    @Test
    @Timeout(value = 1, unit = TimeUnit.SECONDS)   // 超过 1 秒仍没返回 = 又死循环了,测试失败
    void retry_gives_up_when_sold_out() {
        var service = new CoffeeService();
        service.setStock("耶加雪菲", 0);            // 永远缺货
        assertFalse(service.order("耶加雪菲", 1),   // 必须优雅返回 false
                "售罄时应在重试上限内放弃,而不是空转");
    }
}
```

`@Timeout` 是给"可能死循环"的代码上的保险丝:改回 `while(true)`,这个测试会直接超时红掉——**用测试把死循环挡在上线之前**。

### 一、选择题(10 道)
1. [基础]CPU 100% 排障的第一步是什么?
- A) 直接 jstack 看所有线程　B) 先 `top` 确定是哪个**进程**在吃 CPU(记下 PID)　C) 重启服务　D) 先查数据库
> [!答案] **1-B**　经典五步:①`top` 找进程 PID;②`top -Hp <pid>` 找到高 CPU 的线程 TID;③`printf '%x\n' <tid>` 转十六进制;④`jstack <pid>` 按 nid 搜;⑤读栈定位代码行。**举一反三**:`top -Hp`(Linux) 或 `ps -L -p <pid>`;别一上来就猜,先看数据。

2. [进阶]`jstack` 输出中线程的 `nid` 是什么?
- A) 线程名　B) Native Thread ID(操作系统级线程 ID),用**十六进制**表示　C) Java 线程 ID　D) 进程 ID
> [!答案] **2-B**　`nid` = Native ID,对应操作系统的线程号;而 `top -Hp` 显示的是**十进制**线程号——两者同一 ID 但进制不同,必须先用 `printf '%x'` 换算才能对齐。**举一反三**:`tid`(javaThreadId)是 JVM 内的线程 ID(十进制),和 nid 不是同一个数——搜栈用 nid,不要混淆。

3. [深入]`RUNNABLE` 状态 + 栈顶稳定停在同一个方法的同一行,最可能是什么问题?
- A) 线程在等锁　B) 线程在等 IO　C) 死循环或热点计算(CPU 密集型)——线程一直在跑,没有等待　D) 线程已结束
> [!答案] **3-C**　`RUNNABLE`+栈顶稳定 = 线程在"真跑"而非等待。如果连续两次 `jstack` 都卡在同一行,几乎肯定是死循环或极耗 CPU 的计算(如正则回溯、JSON 大对象循环)。**举一反三**:大量线程 `BLOCKED` 且 `waiting to lock <0x...>`——这是锁竞争导致的 CPU 高(上下文切换),病因与解法完全不同。

4. [基础]`jps` 命令的作用是?
- A) 查看 Java 进程的 PID 和主类名　B) 查看线程栈　C) 导出堆转储　D) 分析内存使用
> [!答案] **4-A**　`jps`(Java Process Status)=列出当前用户的所有 Java 进程 PID + 主类名,比 `ps aux | grep java` 更快更准。**举一反三**:`jps -l` 显示完整包名;`jps -v` 显示 JVM 启动参数——排障时先 `jps` 确认 PID,再做后续操作。

5. [进阶]`top -Hp 12345` 中 `-H` 和 `-p` 参数各自含义?
- A) `-H` 显示帮助,`-p` 显示端口　B) `-H` 把进程的线程展开成独立行,`-p` 指定进程 PID　C) `-H` 显示历史,`-p` 指定路径　D) 不需要参数
> [!答案] **5-B**　`-H`:Threads toggle,将进程的每个线程独立显示;`-p`:指定监控的进程。组合后逐行显示每个线程的 CPU 占有率,一眼找到"99.9%" 那个线程。**举一反三**:`top -H -p <pid> -n 1 -b` 可输出文本结果(非交互),方便脚本化采集。

6. [深入]为什么抓 `jstack` 要连续抓 2~3 次(间隔 1~2 秒)?
- A) 提高成功率　B) 一次快照只是"瞬间状态"——连抓几次,每次都卡在同一行的线程才是真凶;只卡一次的可能是恰好路过　C) 为了收集更多线程　D) 不需要多次
> [!答案] **6-B**　`jstack` 是瞬间快照,某线程可能刚好"路过"某行(比如在 `System.out.println` 上)。连抓 2~3 次,每次都停在 `CoffeeService.java:57` 的才证明是长期热点。**举一反三**:每次 `jstack` 改文件名或重定向到不同文件(`jstack pid > stack1.txt`),事后对比。

7. [基础]`printf '%x\n' 12362` 输出什么?
- A) 12362　B) 304a(十六进制)　C) 0x304a　D) 报错
> [!答案] **7-B**　`printf '%x'` 将十进制 12362 转为十六进制 304a(小写,不带 0x 前缀)。**举一反三**:`jstack` 里 nid 是 `nid=0x304a`——搜 `0x304a` 才能匹配,只搜 `304a` 可能漏。

8. [进阶]线程状态 `BLOCKED`,栈里有 `waiting to lock <0x...>`,被另一个线程 `locked <0x...>` 持有——这是什么问题?
- A) 死循环　B) 锁竞争——大量线程在抢同一把锁,持有锁的线程是瓶颈　C) 网络超时　D) 数据库慢查询
> [!答案] **8-B**　`BLOCKED`+`waiting to lock`=锁竞争。持有锁的那个线程(显示 `locked`)是瓶颈——它可能本身慢(持锁时间长),也可能是高并发下锁粒度太粗。**举一反三**:解法:减小锁粒度、用 `ConcurrentHashMap` 替代 `synchronized`、或将大锁拆成多个小锁(分段锁思想)。

9. [深入]如果生产环境无法安装额外工具,排障能用什么?
- A) 只能重启　B) JDK 自带工具:`jps`/`jstack`/`jmap`/`jstat`/`jcmd`,零依赖无需安装　C) 必须安装 Arthas　D) 必须装 Prometheus
> [!答案] **9-B**　JDK 的 `bin/` 目录自带全部排障工具:`jps`(进程)、`jstack`(线程栈)、`jmap`(堆)、`jstat`(GC统计)、`jcmd`(综合命令)——生产环境无需额外安装,关键时要能信手拈来。**举一反三**:Arthas 等工具提供更友好的交互,但基本功是 JDK 自带命令——面试和严控环境下的排障都靠它们。

10. [综合]CPU 100% 时,先看监控发现 GC 次数也在飙升——这提示什么问题?
- A) 只是 CPU 问题　B) 可能是内存不足导致频繁 GC——对象大量创建→堆满→频繁 GC→GC 线程吃掉 CPU。此时 `jstack` 看到的可能是 GC 线程而非业务线程　C) 网络问题　D) 不需要关心
> [!答案] **10-B**　CPU 高 + GC 频繁 = "内存压力转嫁 CPU"。根因不是 CPU 不够,是**堆内存吃紧**→频繁 GC→GC 线程拼命回收→CPU 被 GC 线程吃掉。治本:先查哪里疯狂造对象(分配热点),或调大堆/换 GC 器。**举一反三**:`jstat -gc <pid> 1000` 可实时看 GC 频率和耗时,验证"CPU 是否被 GC 吃掉"。

### 二、解答题(3 道)
1. [概念]用自己的话描述 CPU 100% 排障五步,并解释每一步的目的和信息流向。
> [!答案] **1**　①`top`:锁定哪个进程在吃 CPU(如 java PID=12345)。②`top -Hp 12345`:精确到线程,找到 CPU 99.9% 的 TID。③`printf '%x'`:十进制 TID→十六进制 nid(jstack 的语言)。④`jstack 12345 | grep 0xnid -A20`:抓该线程的调用栈,定位代码行。⑤读栈:看它在做什么——RUNNABLE+死循环 vs BLOCKED+等锁,方向分岔。**举一反三**:信息流是"CPU→进程→线程→代码行",每一步都在缩小嫌疑范围,而不是一开始就猜代码。

2. [场景]线上 CPU 突然从 30% 飙到 100%,但看了 `jstack` 发现大量线程都是 `BLOCKED` 在等一把锁。这锁可能是哪个线程持有的?如何找到"锁的持有者"?
> [!答案] **2**　在 `jstack` 输出中搜索 `waiting to lock <0x...>` 锁地址,再搜 `locked <0x...>`——那个显示 `locked` 的就是持有者。观察持有者在做什么:如果它在等数据库,锁就变成 IO 瓶颈;如果它自己也在等另一把锁,可能形成锁链。**举一反三**:`jstack` 结尾有"Deadlock Detection"段——如果 JVM 检测到死锁,会直接打印死锁线程信息和锁的持有链。另外,`BLOCKED` 本身不耗 CPU——CPU 高是因为大量线程在 CAS 自旋或频繁上下文切换。

3. [综合]比较"死循环"和"频繁 Full GC"两类 CPU 100% 场景:监控数据(JVM指标、GC曲线)、`jstack` 表现(线程栈特征)、修复方向有何不同?
> [!答案] **3**　①死循环:CPU 集中在**单个业务线程**(top -Hp 看到某线程 99.9%);GC 曲线正常;`jstack` 看到该线程 RUNNABLE 卡在业务代码;修复=改循环逻辑/加退出条件。②频繁 Full GC:CPU 被**GC 线程群**吃(多个 GC 线程各占一些);堆内存曲线锯齿状,GC 频率飙升;`jstack` 看到 GC 线程在 `VMThread` 或其他 GC 任务上;修复=查内存泄漏(调大堆是临时方案)、减少对象创建(治本)。**举一反三**:两种场景的**排障入口**不同——死循环从线程栈入手,频繁 GC 从堆和 GC 日志入手——方向错了浪费大量时间。

### 三、代码题(2 道)
1. [基础]写一段能导致 CPU 单核 100% 的代码(一个线程死循环),并给出用 jstack 定位它的完整命令(假设程序正在运行)。
> [!答案] **1 验收**:
> ```java
> public class CpuSpinner {
>     public static void main(String[] args) {
>         new Thread(() -> { while (true) { /* 空转 */ } }, "cpu-burner").start();
>     }
> }
> // 排障命令:
> // jps -l                    → 找到 CpuSpinner 的 PID
> // top -Hp <pid>             → 找到 CPU 最高的 TID
> // printf '%x\n' <tid>       → 转十六进制
> // jstack <pid> | grep 0x<nid> -A 15  → 看到 cpu-burner 线程卡在 while 行
> ```
> **举一反三**:生产环境的 CPU 100% 极少是直接 `while(true)`——常见元凶:正则表达式回溯、Jackson 解析超长 JSON、循环里的字符串 `+=` 拼接、hashCode 冲突时的退化链表。

2. [综合]写一个 `@RepeatedTest(10)` 测试,验证某个可能死循环的方法在**有限时间内一定返回**(用 `@Timeout` 断言)。同时模拟一个"重试有上限、有退避"的正确写法,对比死循环版。
> [!答案] **2 验收**:
> ```java
> @RepeatedTest(10)
> @Timeout(value=2, unit=TimeUnit.SECONDS)
> void retryMustReturnWithinTimeout() {
>     assertFalse(retryWithLimit("售罄咖啡", 1, 3),
>             "3 次重试后应返回 false 而非死循环");
> }
> 
> boolean retryWithLimit(String name, int qty, int maxRetries) {
>     for (int i = 0; i < maxRetries; i++) {
>         if (tryDeduct(name, qty)) return true;
>         try { Thread.sleep(20L * (i + 1)); } // 退避等待
>         catch (InterruptedException e) { Thread.currentThread().interrupt(); return false; }
>     }
>     return false; // 有终点!
> }
> // 对比——死循环版(永远不会返回):
> // while (true) { if (tryDeduct(name,qty)) return true; } // ← 库存售罄时 CPU 100%
> ```
> **举一反三**:`@Timeout` 是"可能死循环"代码的保险丝——进了 CI 门禁后,谁写出 `while(true)` 无退出条件的代码,测试直接超时红掉。退避(backoff)不要恒定 20ms——递增退避(20→40→60)或指数退避(100→200→400)更稳健。
