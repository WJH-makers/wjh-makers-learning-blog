## 二、漫画 · 两个张三擦肩而过

> **〔1〕** 一道门写着 `HashSet`。会员进门要过两关:先按 `hashCode` 被指到某个**桶**,再在桶里用 `equals` 和老住户比对。
> 豆豆:「先按哈希**找桶**,再在桶里用 equals **确认**——两步都对上,才算『已经有你了』,才拦下不让重复。」

> **〔2〕** 第一个「张三」进门,`hashCode` 把他分到 3 号桶,住下。
> 第二个「张三」进门,因为 Member **没写 hashCode**、走的是默认按地址算的哈希,被分到了 **17 号桶**。

> **〔3〕** 两个「张三」隔着十几个桶,谁也看不见谁,`equals` 那一关**根本没机会触发**。俩人擦肩而过,双双在名单上留下。
> 阿零瞪大眼:「明明是同一个人,怎么两个都留下了?!」

> **〔4〕** 豆豆(叼着豆子叉腰,把第 19 话那颗雷的画面调出来):「记得吗?两话前我拽着你、不让你只写 equals 不写 hashCode?**这就是那颗雷。**它跨过 List 一路潜伏到今天,专等你进 Set 的这一刻炸。」

> **〔5〕** 豆豆顺手把门牌翻过来,背面小字:`HashSet ≈ HashMap<E, PRESENT>`。
> 豆豆:「顺便剧透——`HashSet` 根本没自己的身体,它内部就是揣了个 `HashMap`,把你的元素当**键**、拿一个固定的占位对象当**值**。所以它的脾气和下一话的 Map 一模一样。」

## 三、本话目标

- 用 `Set<T>` / `HashSet` 自动去重;
- 讲清 HashSet 去重「先 hashCode 找桶、再 equals 确认」两步走;
- 认识 `TreeSet`(按大小有序)与 `LinkedHashSet`(保持插入顺序);
- **亲眼看第 19 话埋的 hashCode 雷在此引爆**:元素没正确实现 hashCode,去重失效。

## 四、原理图:Set 判重复的两步

```text
Set 不允许重复。HashSet 判「是不是已经有了」:
  ① 算元素的 hashCode → 定位到某个桶(数组下标)
  ② 在这个桶里逐个 equals 比对 → 相等则视为已存在,拒绝加入

hashCode 不一致 → 分到不同桶 → 两个对象永远碰不到一起做 equals → 去重失效！

关键内幕:HashSet 内部就是一个 HashMap<E, Object>,
         你 add 的元素当【键】,值是一个共享的占位常量 PRESENT。
         → 所以 HashSet 的一切脾气,都是下一话 HashMap 的脾气

TreeSet     元素按大小排序(需可比较)   LinkedHashSet  保持插入顺序
```

## 五、代码:会员去重(用 record 保证契约)

```java
import java.util.HashSet;
import java.util.Set;

record Member(String id, String name) {}   // record 自动给出正确、成对的 equals/hashCode

public class Members {
    public static void main(String[] args) {
        Set<Member> members = new HashSet<>();
        members.add(new Member("m01", "张三"));
        members.add(new Member("m01", "张三"));   // 内容相同,自动被丢弃
        members.add(new Member("m02", "李四"));

        System.out.println("去重后 " + members.size() + " 人");   // 2 —— 契约齐全,去重成立
    }
}
```

> **豆豆旁白**:用 `record` 当 Set 元素,是防这类 bug 最省心的姿势——它保证 `equals` 和 `hashCode` 都按字段自动生成、天生成对,你想漏都漏不掉。这也是第 19 话把 Coffee 升级成 record 的深意:**为进集合做准备**。

## 六、故意制造一个 Bug:重演第 19 话的雷

把 `record` 换回那个「只写了 equals、没写 hashCode」的普通类——正是第 19 话阿零偷懒的版本:

```java
class Member {
    final String id;
    Member(String id) { this.id = id; }
    @Override public boolean equals(Object o) {
        return o instanceof Member m && id.equals(m.id);
    }
    // 缺 hashCode —— 编译过、不报错,但去重会失灵
}
```

再往 HashSet 里放两个相同 id 的 Member。

## 七、读懂现象:去重失效(不报错,但雷炸了)

```java
var set = new HashSet<Member>();
set.add(new Member("m01"));
set.add(new Member("m01"));
System.out.println(set.size());   // 输出 2,而不是期望的 1
```

`size()` 是 `2` 不是 `1`——**不报任何错,但去重彻底没生效**。两个 `equals` 相等的对象,因为 `hashCode` 走默认、按对象地址算,各不相同,被分进不同的桶,永远碰不到一起做 `equals`。**这就是第 19 话埋下、跨过第 20 话、在这一话准点引爆的雷。**

修法两条,和第 19 话一模一样:补上 `hashCode`,或者干脆用 `record`。

> **🎯 面试直击**:HashSet 是怎么实现的?它和 HashMap 什么关系?
> HashSet **内部就是一个 HashMap**:你 `add` 的元素作为 HashMap 的**键**,值是一个所有元素共享的占位常量(源码里叫 `PRESENT`)。所以 HashSet 的去重、扩容、树化行为全部继承自 HashMap;「元素必须正确实现 equals/hashCode」的要求,本质就是「HashMap 的键必须正确实现 equals/hashCode」。追问点:那 HashSet 有序吗?无序——想有序用 `LinkedHashSet`(插入序)或 `TreeSet`(排序)。

> **🔀 豆豆的多解台 · 三种 Set,该挑哪个?**

| Set 实现 | 底层 | 顺序 | 适合什么时候 | 代价 |
|---|---|---|---|---|
| `HashSet` | HashMap | **无序** | 只要去重、不在乎顺序(绝大多数场景) | 元素必须正确实现 equals/hashCode |
| `LinkedHashSet` | HashMap + 双向链表 | **插入顺序** | 去重且要「先来后到」(如去重后按录入序展示) | 比 HashSet 多一点内存记链表 |
| `TreeSet` | 红黑树 | **按大小排序** | 去重且要有序输出(如会员按 id 排) | 元素要可比较(Comparable/Comparator),操作 O(log n) |

豆豆锐评:**默认用 `HashSet`**——最快、最省。只有明确需要「保留插入顺序」才上 `LinkedHashSet`,明确需要「排序」才上 `TreeSet`。别一上来就 TreeSet,你多半并不需要排序,白付 O(log n)。

### 一、选择题（10 道）

1. [基础] `HashSet` 的核心特性是什么？- A) 元素有序　B) 元素唯一（不重复）　C) 元素可重复　D) 键值对存储
2. [基础] `HashSet` 的去重依赖哪两个方法？- A) `toString()` + `compareTo()`　B) `hashCode()` + `equals()`　C) `hashCode()` + `toString()`　D) 只用 `equals()`
3. [基础] `HashSet` 允许存入 `null` 吗？- A) 不允许　B) 允许一个 `null`　C) 允许多个 `null`　D) 编译错误
4. [进阶] 只覆写 `equals` 不覆写 `hashCode` 的对象放入 `HashSet`，会发生什么？- A) 去重正常　B) 两个 `equals` 相等的对象可能同时存在　C) 编译错误　D) 自动去重
5. [进阶] `TreeSet` 按什么顺序排列元素？- A) 插入顺序　B) 随机顺序　C) 自然顺序或 `Comparator` 指定顺序　D) 哈希码顺序
6. [进阶] `LinkedHashSet` 与 `HashSet` 的主要区别是什么？- A) 更快　B) 保持插入顺序　C) 允许重复　D) 线程安全
7. [进阶] `TreeSet` 对元素有什么要求？- A) 必须覆写 `hashCode`　B) 必须实现 `Comparable` 或提供 `Comparator`　C) 必须是字符串　D) 无要求
8. [综合] 下面代码输出什么？```java Set<Member> set = new HashSet<>(); set.add(new Member("张三")); set.add(new Member("张三")); System.out.println(set.size());```（Member 只覆写 equals，未覆写 hashCode）- A) 1　B) 2　C) 编译错误　D) 运行时异常
9. [综合] `HashSet` 内部是用什么实现的？- A) `ArrayList`　B) `LinkedList`　C) `HashMap`（元素作为 key，value 是一个占位 Object）　D) 红黑树
10. [综合] 三个 Set 实现的使用场景匹配：- A) 去重无所谓顺序→HashSet，保插入顺序→LinkedHashSet，需要排序→TreeSet　B) 全部用 HashSet　C) 全部用 TreeSet　D) 全部用 LinkedHashSet

> [!答案] **1-B**　`Set` 接口的核心特性就是元素不重复。**2-B**　`hashCode()` 定位桶 + `equals()` 同一桶内判等——缺一不可。**3-B**　`HashSet` 允许一个 `null` 元素。**4-B**　两个逻辑相等的对象可能分到不同桶——去重失效。这就是 S02E07 埋的雷在 S02E09 引爆的原因。**5-C**　`TreeSet` 基于红黑树，按 `Comparable.compareTo()` 或 `Comparator.compare()` 排序。**6-B**　`LinkedHashSet` = `HashSet` + 双向链表维护插入顺序，遍历时按插入顺序输出。**7-B**　`TreeSet` 需要比较元素，所以元素必须实现 `Comparable` 或构造时传 `Comparator`，否则 `ClassCastException`。**8-B**　只覆写 equals → Object 默认 hashCode（内存地址相关）→ 两个 "张三" hashCode 不同 → 分到不同桶 → 各存各的，size=2。**9-C**　`HashSet` 内部持有一个 `HashMap`，`add(e)` 实际是 `map.put(e, PRESENT)`——PRESENT 是一个 dummy Object。**10-A**　三句话背下来：要快用 HashSet、要顺序用 LinkedHashSet、要排序用 TreeSet。
**举一反三**：第 8、9 题连在一起是个经典面试闭环——"为什么 HashSet 去重失败？→ 因为漏了 hashCode → HashSet 底层是 HashMap → HashMap 依赖 hashCode 分桶"。一环扣一环。

### 二、解答题（3 道）

1. [概念] 解释 `HashSet` 的 "先 hashCode 后 equals" 去重流程——为什么两个步骤缺一不可？如果遇到哈希冲突（不同元素的 hashCode 相同），Set 会怎么处理？
2. [场景] 会员系统需要两个列表：①"今日新增会员"（按注册先后展示，自动去重）；②"会员排行榜"（按消费金额从高到低排，自动去重）。分别用哪个 Set 实现？为什么？
3. [综合] `TreeSet` 要求元素实现 `Comparable`，但 `Member` 类既要按姓名排序（管理员视图），又要按注册时间排序（统计视图）。一个类只能实现一个 `compareTo`，怎么办？写出两种方案的代码框架。

> [!答案] **1**　流程：①调用 `hashCode()` 定位到桶（bucket）；②在桶内的链表/红黑树上用 `equals()` 逐一比较。缺一不可：没 hashCode → 无法定位桶（跟 HashMap 分桶机制脱节）；没 equals → 桶内冲突时无法分辨是否同一元素。哈希冲突时（A.hashCode() == B.hashCode() 但 !A.equals(B)），两个元素会被挂在同一个桶的链表上——Set 既不会漏掉也不会去重，遍历效率轻微下降（从 O(1) 退化到 O(log n) 或 O(n)，视桶内结构）。**举一反三**：这就是为什么 HashMap 在桶内元素 ≥8 时会树化（链表→红黑树）——解决极端冲突的性能退化。**2**　"今日新增"需要保持插入顺序 + 去重 → `LinkedHashSet`。`LinkedHashSet` 在 `HashSet` 的哈希表基础上加了双向链表，记录插入顺序，`iterator()` 按插入顺序返回。"排行榜"需要按消费金额排序 + 去重 → `TreeSet`，构造时传入 `Comparator.comparingDouble(Member::getSpending).reversed()`。**举一反三**：哪个 Set 都不会"重复"——去重是 Set 接口的基石。区分点全在顺序上：无序（HashSet）、插入序（LinkedHashSet）、排序序（TreeSet）。**3**　方案一（多 TreeSet + 不同 Comparator）：
> ```java
> Set<Member> byName = new TreeSet<>(Comparator.comparing(Member::getName));
> Set<Member> byRegTime = new TreeSet<>(Comparator.comparing(Member::getRegTime));
> ```
> `Member` 类本身不需要实现 `Comparable`——每个 `TreeSet` 带自己的 `Comparator`。方案二（单 TreeSet + 视图切换）：如果确实需要"同一个 Set 切换排序"，做不到——`TreeSet` 的排序在构造时固定。可以用 `List` + `sort` 临时排序，或维护两个 `TreeSet` 做双索引。**举一反三**：`TreeSet` 的 `Comparator` 构造参数比强制实现 `Comparable` 更灵活——它把"如何排序"从类定义里抽离出来。

### 三、代码题（2 道）

1. [基础] 用 `HashSet`、`LinkedHashSet`、`TreeSet` 分别创建设置、存入三个 String："摩卡"、"美式"、"拿铁"。遍历打印，对比三者的输出顺序有何不同。
2. [综合] 设计 `Coffee` 类（`String name, double price`），使 `equals` 和 `hashCode` 仅基于 `name`（同名为同一杯咖啡，忽略价格）。用 `HashSet` 验证：添加两个 name 相同但 price 不同的 Coffee，Set 应只保留一个。再创建一个 `TreeSet<Coffee>`，按 price 从低到高排序——验证 `TreeSet` 的排序和 `HashSet` 的去重是独立工作的。

> [!答案] **1 验收**：
> ```java
> Set<String> hashSet = new HashSet<>();
> hashSet.add("摩卡"); hashSet.add("美式"); hashSet.add("拿铁");
> System.out.println("HashSet: " + hashSet);  // 无序，如 [美式, 拿铁, 摩卡]
> 
> Set<String> linkedSet = new LinkedHashSet<>();
> linkedSet.add("摩卡"); linkedSet.add("美式"); linkedSet.add("拿铁");
> System.out.println("LinkedHashSet: " + linkedSet); // [摩卡, 美式, 拿铁] 插入序
> 
> Set<String> treeSet = new TreeSet<>();
> treeSet.add("摩卡"); treeSet.add("美式"); treeSet.add("拿铁");
> System.out.println("TreeSet: " + treeSet); // [拿铁, 摩卡, 美式] Unicode 序
> ```
> **举一反三**：`foreach` 遍历 `HashSet` 的顺序不保证每次都一样（取决于哈希桶分布和元素插入顺序），不能依赖。**2 验收**：
> ```java
> import java.util.*;
> class Coffee {
>     String name;
>     double price;
>     Coffee(String name, double price) { this.name = name; this.price = price; }
>     @Override public boolean equals(Object o) {
>         if (this == o) return true;
>         if (!(o instanceof Coffee c)) return false;
>         return Objects.equals(name, c.name);  // 只比 name
>     }
>     @Override public int hashCode() { return Objects.hash(name); }
>     @Override public String toString() { return name + " ¥" + price; }
> }
> // HashSet 去重: 同名不同价 → 只保留一个
> Set<Coffee> hashSet = new HashSet<>();
> hashSet.add(new Coffee("美式", 15.0));
> hashSet.add(new Coffee("美式", 18.0));  // name 相同 → 判重
> System.out.println(hashSet.size()); // 1
> 
> // TreeSet 排序: 按 price 排序，但去重仍按 compareTo（或 Comparator）
> // 注意: TreeSet 用 compareTo 判重，不是 equals!
> Set<Coffee> treeSet = new TreeSet<>(Comparator.comparingDouble(c -> c.price));
> treeSet.add(new Coffee("美式", 15.0));
> treeSet.add(new Coffee("拿铁", 22.0));
> treeSet.add(new Coffee("摩卡", 18.0));
> treeSet.forEach(System.out::println); // 美式 ¥15.0 / 摩卡 ¥18.0 / 拿铁 ¥22.0
> ```
> **举一反三**：这里有一个关键点——`TreeSet` 的去重用的是 `compareTo`（或 `Comparator.compare()` 返回 0），**不是 `equals`**。如果 `Comparator` 说两元素"相等"（compare=0），即使 `equals` 返回 false，`TreeSet` 也会拒绝第二个。这是 Set 接口的一个细微不一致，知道就行。
