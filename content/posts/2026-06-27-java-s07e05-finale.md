阿零盯着那张海报,手心冒汗。他现在敢一把把新版本全量上线吗?流量真上来了,哪个服务会先崩?崩了有预案吗?——这三个问题,他一个都答不上来。

## 四、原理图:一次安全的大促发布

```text
                        新版本 v7 镜像(CI 已验证)
                              │
   ┌──────────────── 灰度发布(金丝雀) ─────────────────────┐
   │  Ingress 按权重分流:                                  │
   │     95% ─▶ 稳定版 v6 Pod 组                           │
   │      5% ─▶ 金丝雀 v7 Pod 组   ← 盯它的错误率/延迟     │
   │  没问题 → 20% → 50% → 100%(逐步放量)                  │
   │  出问题 → 权重打回 0 / rollout undo(秒级回滚)         │
   └───────────────────────────────────────────────────────┘
                              │ 上线前
   ┌──────────────── 压测演练(预发环境) ─────────────────────┐
   │  流量重放 40× ──▶ 观察三支柱 ──▶ 找到瓶颈(连接池/慢查询)│
   └─────────────────────────────────────────────────────────┘
                              │ 上线中,三张预案牌随时能打
   ┌───────────┬───────────┬──────────────┐
   │  限流降级  │   扩容     │   回滚     │
   │ Sentinel  │ scale/HPA │ rollout undo │
   └───────────┴───────────┴──────────────┘
```

核心思想一句话:**把「上线」从一个不可逆的赌博,变成一个可控、可观测、可回退的过程。** 灰度控制「炸的范围」,压测控制「意外的概率」,预案控制「炸了之后的损失」。

## 五、代码:金丝雀灰度 + 压测 + 预案

**① 金丝雀发布**——用 Nginx Ingress 的 canary 注解,把 5% 流量切给 v7。稳定版 Ingress 不动,另建一个金丝雀 Ingress:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: coffee-order-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "5"    # ← 只放 5% 流量给金丝雀
spec:
  rules:
    - host: order.coffee.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: coffee-order-canary-svc          # 指向 v7 那组 Pod
                port: { number: 80 }
```

盯着上一话的 Grafana,给金丝雀单独看板:v7 那组 Pod 的错误率、P99 延迟。没问题就把 `canary-weight` 逐步调到 20、50、100;不对劲就打回 0。

**② 压测**——上线前在预发环境,用 k6 把大促流量提前打一遍:

```javascript
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 2000 },   // 2 分钟爬到 2000 并发(≈平日 40 倍)
    { duration: '5m', target: 2000 },   // 维持 5 分钟,看系统稳不稳
    { duration: '2m', target: 0 },      // 收尾
  ],
  thresholds: { http_req_duration: ['p(99)<800'] },   // P99 必须 < 800ms,否则判定不达标
};

export default function () {
  const res = http.post('https://pre.coffee.example.com/api/orders',
                        JSON.stringify({ name: '拿铁', qty: 1 }),
                        { headers: { 'Content-Type': 'application/json' } });
  check(res, { '下单成功': (r) => r.status === 200 });
}
```

**③ 预案**——三条命令背下来,大促当天闭眼能打:

```bash
# 扩容:一键把订单服务加到 12 个实例
kubectl scale deployment/coffee-order --replicas=12

# 回滚:新版本出事,10 秒退回上一版(K8s 记着历史 ReplicaSet)
kubectl rollout undo deployment/coffee-order

# 限流:降级开关(第六季 Sentinel 规则),超阈值请求走排队/兜底
kubectl apply -f sentinel-flow-rule-blackfriday.yaml
```

## 六、故意制造一个 Bug:灰度权重配反

大促前夜,阿零改金丝雀权重,想从 5% 提到 50%,结果手滑把 `canary-weight` 敲成了 **100**——**全站流量瞬间涌向还没充分验证的 v7**:

```yaml
    nginx.ingress.kubernetes.io/canary-weight: "100"   # ← 本想写 50,手滑成 100
```

`kubectl apply` 照常成功。几秒后,Grafana 上 v7 那组的错误率开始爬。

## 七、读懂现象:30 秒定位 + 秒级止血

告警先响了(上一话配的 Prometheus 规则):

```text
[FIRING] CoffeeOrderErrorRateHigh
  service = coffee-order (v7 canary)
  error_rate = 6.2%   (阈值 1%)
  描述:金丝雀版本 5xx 错误率突破阈值
```

阿零打开 Grafana,一眼看清:**稳定版 v6 的流量掉到了 0,全部涌进 v7**;点进上一话的链路追踪,慢的那几笔 TraceId 指向 v7 一个还没压测过的优惠券查询——它扛不住全量。根因不是代码 bug,是**发布动作错了:未验证的版本吃了 100% 流量**。

这时候**不折腾根因,先止血**——把金丝雀权重秒级打回 0,流量全退回稳定版 v6:

```bash
kubectl patch ingress coffee-order-canary --type=merge \
  -p '{"metadata":{"annotations":{"nginx.ingress.kubernetes.io/canary-weight":"0"}}}'
# 若 v7 已全量替换了 Deployment,则改用 kubectl rollout undo 回滚
```

3 秒后 Grafana 上 v6 流量回升、错误率归零。从告警到平息 **不到 30 秒**。事后再慢慢查 v7 优惠券为什么扛不住,补压测、修好、重新灰度。

> **豆豆锐评 · 线上止血优先于查根因**
> 新手出事第一反应是「让我看看为什么」,一头扎进日志——顾客的订单正在一笔笔失败。**老手第一反应是「先让它别再错」**:回滚 / 限流 / 摘流量,把损失止住,再从容查根因。记住这个顺序:**止血 → 定位 → 修复 → 复盘**。这也是为什么预案要提前备、要演练——真出事时,你没有时间现学 `rollout undo` 的用法。今天阿零 30 秒扑灭,靠的不是聪明,是**提前把牌准备好了**。

> **🔀 豆豆的多解台 · 三种发布策略,大促选哪个?**
>
> | 策略 | 怎么做 | 优点 | 代价 / 适用 |
> |---|---|---|---|
> | 滚动更新(Rolling) | Pod 一批批换新版(K8s 默认) | 不停机、不额外占资源 | 新旧版本短暂并存;出问题回滚较慢。**日常小改动** |
> | 蓝绿(Blue-Green) | 备一套完整新环境,一次性切流量 | 切换瞬间、回滚瞬间(切回旧环境) | 要双倍资源;切换是「全量」有风险。**要求秒级回滚** |
> | 金丝雀 / 灰度(Canary) | 先放一小撮流量,逐步放量 | **爆炸半径最小**,能用真实流量验证 | 流程长、需配套监控。**大促、高风险变更(本话)** |
>
> 豆豆锐评:**大促这种「错了就是事故」的场景,首选金丝雀**——它把风险切成小份,让你在只影响 5% 顾客时就发现问题。日常改个文案走滚动更新就够了,别为一行改动上金丝雀,那是杀鸡用牛刀。三者可组合:金丝雀验证通过后,底层用滚动更新全量铺开。

## 八、验证:压测达标 + 预案演练

大促前的验收不是「祈祷」,是**跑一遍、看数据**。压测在预发环境跑 k6:

```text
     ✓ 下单成功
     http_req_duration..............: p(99)=612ms   (阈值 800ms ✓)
     http_reqs......................: 892431  2038.6/s
     ✓ thresholds on http_req_duration
running (09m00.0s), 0000/2000 VUs, 892431 complete
```

P99 = 612ms,压在 800ms 红线内,40 倍流量下核心链路稳住。同时,把「回滚真的能退回上一版」也写成一条自动化验收(灾备演练脚本),确认 `rollout undo` 后服务版本号确实回退、健康检查转绿:

```java
@Test
void rollback_restores_previous_healthy_version() {
    deploy("coffee-order:v7-broken");        // 故意上一个坏版本
    assertFalse(healthOk());                 // 健康检查失败
    kubectl("rollout undo deployment/coffee-order");
    await().atMost(30, SECONDS).until(this::healthOk);   // 30 秒内回滚并恢复健康
    assertEquals("v6", runningImageTag());   // 版本确实退回稳定版
}
```

绿了——这意味着大促当天,**预案不是纸上谈兵,是验证过、真能救命的**。

4. 把 `canary-weight` 从 5 手滑写成 100,后果是?
   - A) 灰度停止　B) **全量流量涌向还没充分验证的新版**,稳定版流量掉到 0　C) 部署失败　D) 触发自动回滚
5. `kubectl rollout undo deployment/...` 能秒级回滚,是因为?
   - A) 缓存了镜像　B) K8s 记着历史 ReplicaSet,切回上一版即可　C) 重新构建了旧版本　D) 从备份恢复
6. k6 压测里 `thresholds: { http_req_duration: ['p(99)<800'] }` 的作用是?
   - A) 限制并发数　B) 设定验收红线:P99 超过 800ms 就判定不达标　C) 控制压测时长　D) 设置超时
7. 大促当天要提前备好的三套预案是?
   - A) 备份、监控、告警　B) **限流(Sentinel)、扩容(scale/HPA)、回滚(rollout undo)**　C) 降配、迁移、重启　D) 加机器、加缓存、加索引
8. 蓝绿发布相比金丝雀的代价是?
   - A) 回滚更慢　B) **需要双倍资源**,且切换是「全量」有风险　C) 不能回滚　D) 必须停机
9. 日常改一行文案,合适的发布策略是?
   - A) 金丝雀,越谨慎越好　B) 蓝绿　C) 滚动更新就够了 —— 别为一行改动杀鸡用牛刀　D) 停机发布
10. 全系列反复强调、从读懂第一个 `cannot find symbol` 用到定位跨五服务慢请求的方法是?
    - A) 背 API　B) **五步排障法**:观察现象 → 收集报错 → 提出假设 → 只改一处 → 重跑验证　C) 加日志　D) 重启服务

> [!答案]
> **1-B**　把风险切成小份。**举一反三**:它让你在只影响 5% 顾客时就发现问题,而不是全量翻车后才知道。
> **2-B**　三件事各管一段。**举一反三**:把「上线」从不可逆的赌博,变成可控、可观测、可回退的过程。
> **3-B**　先让它别再错。**举一反三**:新手一头扎进日志时,顾客的订单正在一笔笔失败 —— 止血永远优先。
> **4-B**　未验证版本吃了全量。**举一反三**:根因不是代码 bug 而是发布动作错了 —— 发布本身也是需要被评审的变更。
> **5-B**　历史版本还留着。**举一反三**:所以镜像标签要唯一(第 53 话的 commit SHA),否则「上一版」到底是哪一版都说不清。
> **6-B**　它是自动化的验收标准。**举一反三**:压测没有阈值就只是「跑了一下」,有阈值才叫验收。
> **7-B**　三张牌,大促当天闭眼能打。**举一反三**:预案必须演练过 —— 真出事时你没有时间现学命令用法。
> **8-B**　双倍资源换瞬间切换。**举一反三**:三种策略可以组合 —— 金丝雀验证通过后,底层用滚动更新全量铺开。
> **9-C**　按风险选策略。**举一反三**:流程的成本也是成本,对低风险变更上重流程,只会让团队绕开流程。
> **10-B**　方法论比工具更持久。**举一反三**:K8s 会有下一代,但「怎么把一个搞不懂的问题拆开」的能力会跟你一辈子。
