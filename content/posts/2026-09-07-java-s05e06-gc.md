## 一、事故:没人报错,延迟却周期性抖动

> **事故报告 · INC-0938**
> 现象:coffee-api 平均延迟很稳(20ms),但 **P99 每隔一阵就窜到 400ms**,曲线像心电图上的尖刺。无异常、无泄漏(上一话已治)、CPU 也不高。
> 线索:抖动的**周期**和监控里 GC 次数的曲线**对得上**。

豆豆:「这是 GC 的**停顿(Stop-The-World, STW)**。清洁队认真收垃圾时,为了不让你一边改一边收乱套,会把**所有业务线程暂停**一小会儿——毫秒级你感觉不到,可一旦某次 GC 停了几百毫秒,那一刻所有请求全卡住,P99 就窜上去了。想治它,先得**看见它**:读 GC 日志。看不够,就上 JVM 的黑匣子 **JFR**,给整个运行过程录像。这是第五季最后一块拼图——**可观测性**。」

## 二、漫画 · 清洁队喊的那声"全体暂停"

> **〔1〕** 咖啡站正热火朝天出杯,GC 清洁队长突然吹哨:「全体暂停!收垃圾!」所有工人线程瞬间定格,顾客的订单全悬在半空。几毫秒后哨声再响,大家继续——顾客几乎没察觉。
> 阿零:「原来每次 GC,大家都被按了一下暂停键?」

> **〔2〕** 可某一次,清洁队要做一次**大扫除(Full GC)**,哨声响了整整 400 毫秒。这一下顾客全愣住了,门口瞬间积压一片"怎么这么慢"。
> 豆豆(叼豆子):「短暂停没事,**长停顿才是刺客**。你得知道:多久一次、每次停多久、为啥这次停这么久。」

> 豆豆:「出事后回放这盒磁带,啥都瞒不住。飞机靠它查事故,你的服务也该有一台。」

> **〔4〕** 阿零把 GC 日志和 JFR 报告并排贴在墙上,咖啡站第一次有了"体检报告"。
> 阿零:「从第一季那行 `Hello`,到现在能看懂它心跳、抓它的病……我好像真的会做系统了。」豆豆:「是啊。第五季,你从『会写』长成了『能守』。」

## 四、原理图:GC、STW 与可观测性三件套

```text
对象的一生(分代 + STW):
  new 对象 → Eden 区
     │ Eden 满 → Young GC(STW,很短,毫秒级)→ 活的挪到 Survivor
     │ 熬过多轮 → 晋升 Old 区
     │ Old 快满 → Mixed/Full GC(可能 STW 较长)← P99 毛刺的常见来源

为什么必须 STW:回收时若业务线程还在乱改引用,收集器会数错、误删存活对象。
现代收集器(G1/ZGC)拼命把 STW 压短:能并发做的都挪到业务线程"旁边"并行做。

线上可观测性三件套(这一话补齐):
  ① GC 日志  -Xlog:gc*        —— 每次 GC 停多久、回收多少(便宜,长期开)
  ② JFR      飞行记录仪        —— GC/分配/锁/热点线程全程低开销录像(黑匣子)
  ③ 指标     Micrometer→监控   —— P99、GC 次数上大盘告警(第六季展开)
```

一句话:**看不见,就治不了。** 前几话是"出事后抓现行",这一话是给服务装上"日志 + 黑匣子",让问题**在录像里自己现形**。

## 五、命令:让 GC 日志和 JFR 都开起来

**开 GC 日志**(生产建议长期开,开销极低,滚动切分防撑爆磁盘):

```text
java -Xlog:gc*:file=/data/log/gc.log:time,uptime,level,tags:filecount=5,filesize=20M \
     -XX:+HeapDumpOnOutOfMemoryError \
     -jar coffee-api.jar
```

一次正常的 Young GC,日志长这样(Java 9+ 的**统一日志**格式):

```text
[2026-09-07T14:03:11.204+0800][12.450s][info][gc] GC(42) Pause Young (Normal) (G1 Evacuation Pause) 512M->48M(1024M) 6.803ms
[2026-09-07T14:03:15.870+0800][17.116s][info][gc] GC(43) Pause Young (Normal) (G1 Evacuation Pause) 520M->51M(1024M) 7.114ms
```

怎么读第一行:`GC(42)` 第 42 次 GC;`Pause Young` 年轻代停顿;`512M->48M(1024M)` 回收前 512M、回收后 48M、堆总共 1024M;`6.803ms` 这次 **STW 停了 6.8 毫秒**——很健康。

而 P99 毛刺那一刻,日志里能抓到一次异类:

```text
[2026-09-07T14:07:29.551+0800][275.9s][info][gc] GC(88) Pause Full (G1 Compaction Pause) 1002M->640M(1024M) 412.771ms
```

`Pause Full` + `412ms`——凶手现形:一次 Full GC 停了 412 毫秒,正好对上那根 400ms 的尖刺。根因:堆偏小、老年代频繁被填满触发 Full GC。

**开 JFR**(启动即录,或对运行中的进程随时 `jcmd` 开录):

```text
# 方式一:启动时挂上黑匣子,持续录制
java -XX:StartFlightRecording=maxsize=200m,maxage=6h,filename=coffee.jfr -jar coffee-api.jar

# 方式二:线上进程正在跑,临时抓 120 秒
jcmd 12345 JFR.start name=diag duration=120s filename=/data/coffee.jfr
jcmd 12345 JFR.dump  name=diag filename=/data/coffee-snap.jfr    # 随时导出当前录像
```

导出的 `.jfr` 用 JDK Mission Control(JMC)打开,GC 停顿分布、对象分配热点、锁竞争、热点方法一目了然——上一话要 `jstack`+`jmap` 分头抓的东西,JFR **一盒磁带全录下来了**,而且开销通常在百分之一量级,**敢在生产常开**。

## 六、故意制造一个 Bug:堆太小,把自己逼进 Full GC

阿零图省内存,把堆设得很小,又在下单路径里每次都 `new` 一大坨临时对象:

```text
# 启动参数:堆只给 256M(对高峰期的咖啡站来说太挤)
java -Xms256m -Xmx256m -Xlog:gc -jar coffee-api.jar
```

```java
// 下单时拼一份"超详细日志字符串",每单都造一大串临时对象
public void order(OrderRequest req) {
    String audit = "";
    for (int i = 0; i < 10_000; i++) {
        audit += "[" + i + ":" + req + "]";   // ← 循环里字符串 += 疯狂造垃圾(还记得 StringBuilder 吗)
    }
    log.info(audit);
    // ...真正的下单逻辑
}
```

高峰一来,Eden 被临时对象瞬间填满、疯狂 Young GC,对象来不及回收就晋升老年代,老年代也很快满 → **触发昂贵的 Full GC**。

## 七、读懂现象 + 调优:先看日志,再动参数

GC 日志现象(短时间内 Young GC 极密集,还夹着 Full GC):

```text
[..][info][gc] GC(120) Pause Young (Normal) 248M->240M(256M) 5.1ms   ← 回收后还剩 240M,几乎没收掉
[..][info][gc] GC(121) Pause Young (Normal) 252M->245M(256M) 5.4ms   ← 堆一直贴着上限
[..][info][gc] GC(122) Pause Full (G1 Compaction Pause) 255M->198M(256M) 402.9ms  ← 被逼出 Full GC
```

信号:**每次 GC 后剩余内存居高不下、堆长期贴顶、Young GC 极频繁并诱发 Full GC**。这是"堆压力过大 + 疯狂造垃圾"的典型画像。两步治理(**先治代码,再调参数**):

**① 治代码**——消灭下单路径的垃圾制造机(回到第一季学的 `StringBuilder`):

```java
public void order(OrderRequest req) {
    var audit = new StringBuilder();      // 不再每次循环 new 一个新 String
    for (int i = 0; i < 10_000; i++) {
        audit.append('[').append(i).append(':').append(req).append(']');
    }
    log.info(audit.toString());
    // ...真正的下单逻辑
}
```

**② 调参数**——给足合理的堆(容量问题该调就调,和上一话"泄漏别乱调 `-Xmx`"不冲突):

```text
java -Xms1g -Xmx1g -Xlog:gc -jar coffee-api.jar
```

改完再看日志:Young GC 回落到"回收后剩几十 M"的健康态,Full GC 消失,P99 那根 400ms 的尖刺被抹平。

> **豆豆锐评 · 调优铁律:先测量,再动手;先治因,再调参**
> 新手一遇 GC 问题就疯狂加 `-XX` 参数、换收集器,**方向全反**。正确顺序:① 开 GC 日志/JFR **测量**——到底停多久、多久一次、卡在哪;② 优先**治代码**——绝大多数 GC 压力来自"造了太多垃圾"(循环里拼字符串、批量查全表、对象没复用),这一步收益最大;③ 才是**调堆大小/选收集器**。别把"频繁 GC"直接等同于"要换 GC 器"——十有八九是代码在狂造垃圾。

> **⏳ 版本时光机 · Java 垃圾收集器这些年**

| JDK 版本 | 默认/代表收集器 | 关键变化 |
|---|---|---|
| Java 8 | Parallel GC(默认)· CMS(低延迟选项) | 吞吐优先;CMS 追求短停顿但有碎片问题 |
| Java 9~14 | **G1 成为默认** · CMS 于 14 被移除(JEP 363) | 分区(Region)+ 可设停顿目标,兼顾吞吐与延迟 |
| Java 21 | 分代 ZGC 登场(JEP 439) | 停顿控制在**亚毫秒级**,适合超大堆、低延迟 |
| Java 25 | 默认仍 G1;ZGC 已全面分代;新增分代 Shenandoah、Compact Object Headers | 低延迟三选一(G1/ZGC/Shenandoah);对象头压缩省堆 |

一句演进小结:主流从"吞吐优先(Parallel)"一路演进到"低停顿优先(G1/ZGC)"。**默认 G1 适合绝大多数服务**;只有当你有**超大堆 + 严格低延迟**要求(如交易、广告竞价)时,才上 ZGC(`-XX:+UseZGC`)。本话主线基线 Java 25 用默认 G1。

> **🎯 面试直击**:一次 GC 会 STW 吗?G1 和 ZGC 怎么选?
> **会,但看阶段**。现代收集器把大量工作做成**并发**(和业务线程并行),但仍有短暂 STW 阶段(如根扫描、最终标记)——G1 的 Young/Mixed GC 有毫秒级 STW,极端下 Full GC 才会长停顿;ZGC 把 STW 压到**亚毫秒**且几乎不随堆增大而变长。选型:**默认 G1**(通用、成熟、能设 `-XX:MaxGCPauseMillis` 目标);**堆特别大(几十上百 G)或延迟要求极严** → ZGC。切忌"听说 ZGC 快就无脑换"——中小堆上 G1 的吞吐往往更划算。

## 八、用验证证明:垃圾造得少了,Full GC 没了

GC/停顿难写纯单元测试,但它的**根因——"下单路径疯狂造垃圾"**可以用分配量间接验证。用 JFR 事件或简单的分配对比即可,这里给一个"行为不变、垃圾骤减"的守门测试:

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class AllocationTest {
    // 保证重构成 StringBuilder 后,业务输出和原来一字不差(重构不能改行为)
    @Test
    void audit_string_unchanged_after_refactor() {
        var req = new OrderRequest("拿铁", 2);
        assertEquals(OrderService.buildAuditOld(req), OrderService.buildAuditNew(req),
                "StringBuilder 版必须和 += 版输出完全一致");
    }

    // 用 JFR 编程式录制,断言下单路径的分配字节数被压下来(回归守门)
    @Test
    void order_allocates_less_after_fix() throws Exception {
        long before = com.coffee.bench.AllocProbe.measure(() -> OrderService.orderNew());
        assertTrue(before < 2_000_000, "优化后单次下单分配应远小于 += 版的量级");
    }
}
```

第一个测试守住"重构不改行为"(把 `+=` 换成 `StringBuilder`,输出必须一致);第二个用分配探针守住"垃圾确实变少"。**性能优化也要有测试兜底**,否则下次有人改回 `+=`,毛刺会悄悄回来。

> **豆豆旁白 · 可观测性不只有 JFR**
> JFR 是"事后回放黑匣子";日常还需要**实时指标**——Spring Boot 用 Micrometer 把 GC 停顿、P99、线程池活跃数暴露成 metrics,接到监控大盘并设告警,问题**发生前**就预警。这套"指标 + 告警 + 链路追踪"的完整可观测性,是第六季分布式的重头戏。这一话你先把单机的"日志 + 黑匣子"打通,已经能独立守住一台服务器了。

### 一、选择题(10 道)
1. [基础]JVM 堆内存中,新生代 Eden 区和两个 Survivor 区(S0/S1)的默认比例是?
- A) 1:1:1　B) 8:1:1　C) 6:2:2　D) 4:3:3
> [!答案] **1-B**　HotSpot 默认 Eden:S0:S1 = 8:1:1,可通过 `-XX:SurvivorRatio=8` 调整(8 代表 Eden 与一个 Survivor 的比值)。**举一反三**:每次 Minor GC 后存活对象从 Eden+S0 复制到 S1,年龄+1;年龄超过 `-XX:MaxTenuringThreshold`(默认 15)晋升老年代——这就是"分代 GC"的物理基础。

2. [进阶]Minor GC 和 Full GC 的核心区别是?
- A) Minor GC 更慢　B) Minor GC 只回收新生代(Eden+S0/S1),速度快、频次高、STW 毫秒级;Full GC 回收整个堆(含老年代+元空间),STW 长(百毫秒到秒级)　C) 两者完全相同　D) Full GC 只在程序结束时触发
> [!答案] **2-B**　Minor GC:新生代满触发,通常几毫秒;Full GC:老年代/元空间满触发,STW 显著长。**举一反三**:Minor GC 频繁(每秒几次)是正常的;Full GC 频繁(每分钟几次)则是严重警告——要么堆太小,要么内存泄漏被迫频繁回收老年代。

3. [基础]Java 9+ 启用统一 GC 日志的正确 JVM 参数是?
- A) `-XX:+PrintGCDetails`　B) `-Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=20M`　C) `-verbose:gc`　D) `-XX:+PrintGC`
> [!答案] **3-B**　Java 9+ 使用统一日志框架(`-Xlog`);`gc*` 表示所有 GC 相关 tag,`:file=` 指定输出文件,`filecount=5,filesize=20M` 做滚动切分。Java 8 以前的 `-XX:+PrintGCDetails` 已废弃。**举一反三**:**生产长期开 GC 日志**——开销几乎为零,关键时刻是诊断 Full GC 的唯一证据。

4. [深入]GC 日志行 `[gc] GC(42) Pause Young (Normal) 512M->48M(1024M) 6.803ms` 的含义是?
- A) 程序运行了 42 秒　B) 第 42 次 GC,年轻代停顿,回收前堆用 512M→回收后 48M,堆总 1024M,STW 停了 6.803ms　C) 内存泄漏 42MB　D) 线程数 42
> [!答案] **4-B**　`GC(42)`:第 42 次 GC 事件;`Pause Young`:年轻代停顿;`512M->48M(1024M)`:回收前→回收后→堆总大小;`6.803ms`:这次 STW 的耗时。**举一反三**:关注两个数字——"回收后"残留量和 STW 耗时。残留量居高不下→对象大多活着→可能晋升太快;耗时超 100ms→开始影响延迟。

5. [进阶]STW(Stop-The-World)为什么不可避免?
- A) JVM 设计缺陷　B) GC 回收引用时,若业务线程仍在修改对象图,收集器会数错或误删存活对象——必须暂停一致性的"快照时刻"　C) 为了降低 CPU 使用　D) 只有 Full GC 才会 STW
> [!答案] **5-B**　STW 是"安全点"(Safepoint):所有线程停在安全点上,对象引用关系不再变化,GC 才能准确标记存活对象。**举一反三**:现代收集器(G1/ZGC)把大部分工作做成并发(与业务线程并行),把 STW 压到最短——G1 毫秒级,ZGC 亚毫秒级——但完全消灭 STW 在理论上是不可行的。

6. [深入]G1 收集器的核心设计思想是?
- A) 和 Parallel GC 完全相同　B) 分区(Region) + 可设停顿目标(`-XX:MaxGCPauseMillis`)——堆被切分成多个 Region,每次选择"回收收益最高的几个 Region"做 Mixed GC,把 STW 控制在用户设定的目标内　C) 只做 Full GC　D) 不用 STW
> [!答案] **6-B**　G1 把堆分成大小相等的 Region(默认约 2048 个),每次 Mixed GC 挑选"垃圾最多的几个 Region"回收,而非全堆扫描,由此兼顾吞吐和可控停顿。**举一反三**:`-XX:MaxGCPauseMillis`(默认 200ms)是软目标——G1 会尽量在此范围内完成,但不做硬保证;若老年代实在回收不过来,仍会退化到 Full GC。

7. [基础]对象从新生代晋升到老年代的条件是?
- A) 对象大小超过 1MB　B) 经历多次 Minor GC 后"年龄"超过 `MaxTenuringThreshold`(默认 15),或 Survivor 区中同龄对象超过一半(动态年龄计算)　C) 程序运行超过 10 秒　D) 对象被 finalize 过
> [!答案] **7-B**　晋升条件:①年龄达阈值;②动态晋升——Survivor 中某年龄的对象大小总和超过 Survivor 一半,大于等于该年龄的对象全部晋升;③大对象直接进老年代(超过 `-XX:PretenureSizeThreshold`)。**举一反三**:Survivor 区"留不住"对象→过早晋升→老年代快速膨胀→Full GC——这是堆配置不合理(新生代太小)的典型症状。

8. [进阶]ZGC 相比 G1 的最大优势是什么?G1 仍然是默认收集器的原因?
- A) ZGC 更快更省内存,应取代 G1　B) ZGC 将 STW 控制在**亚毫秒级**且几乎不随堆增大而变长(适合 TB 级堆、极低延迟);G1 吞吐在中小堆上更优,生态更成熟,是通用场景的最稳妥选择　C) ZGC 不需要内存　D) G1 已过时
> [!答案] **8-B**　ZGC 基于染色指针(Colored Pointers)和读屏障,大部分工作并发完成;G1 在中低延迟场景下吞吐更优。选型:默认 G1(8~64G 堆,99%场景);ZGC 用于超大堆(64G+)或严格低延迟(P99<1ms)场景。**举一反三**:别盲目追新——ZGC 的"亚毫秒"令人向往,但如果你的 P99 瓶颈在数据库查询而非 GC,换 ZGC 毫无意义。先量,再选。

9. [深入]GC 日志中连续出现 `Pause Full (G1 Compaction Pause)` 且耗时 400ms+,堆使用量回收后仍接近上限(如 1002M→960M/1024M),这提示什么?
- A) 系统很健康　B) **堆压力过大 + 可能内存泄漏**——Full GC 回收量极小(只腾出 42M),说明老年代对象几乎全活着、回收不掉,很快又满又触发 Full GC,恶性循环　C) CPU 不够　D) 网络问题
> [!答案] **9-B**　Full GC 回收量极小 = 老年代里的对象大部分"不该死"(被引用),而非"刚死的垃圾"。要么是真正的内存泄漏(GC Root 拴住);要么堆太小,负载撑到了上限。**举一反三**:先 `jmap -histo` 看哪类对象最多→有异常膨胀则 `jmap -dump` 进 MAT 找 GC Root;若对象量合理但堆偏小,扩容 `-Xmx`。始终先排查代码泄漏,再调堆参数。

10. [综合]GC 调优的正确步骤顺序是?
- A) 直接换 GC 收集器→调大堆→写代码　B) ①开 GC 日志/JFR **测量**停顿、频率和回收量→②**先治代码**(减垃圾制造:循环拼字符串、全表查询、对象不复用)→③调堆大小/选收集器　C) 先调小堆→再调大堆　D) 重启服务
> [!答案] **10-B**　铁律三句话:①**先量后治**——没数据不动手;②**代码优先**——绝大多 GC 压力来自"造垃圾太猛",改一行代码比调一百个 JVM 参数收益大;③**参数兜底**——代码治本后再配合理的堆和收集器。**举一反三**:JFR 是"测量"的极致——低开销全程录像,事后回放看每次 GC 停顿、分配热点、锁竞争,一盒磁带装下整个运行时真相。

### 二、解答题(3 道)
1. [概念]用自己的话解释 GC 的"分代假设"和分代收集流程:对象从诞生到被回收或被晋升的完整生命线。
> [!答案] **1**　①分代假设(Weak Generational Hypothesis):绝大多数对象"朝生夕死"(很快变垃圾),少数"老不死"(长期存活)。基于此,堆分为新生代和老年代——新生代频繁回收"短命对象",老年代偶尔回收"长命对象"。②对象生命线:`new`→分配在 Eden→Eden 满触发 Minor GC→存活对象复制到 Survivor(S0/S1),年龄+1→每熬过一次 Minor GC 年龄递增→年龄超阈值(默认 15)或动态判定→晋升老年代→老年代满触发 Full GC→真正死亡被回收。**举一反三**:优化方向——如果绝大多数对象熬不过第一次 Minor GC(健康的"朝生夕死"),说明代码分配合理;如果大量对象快速晋升老年代,说明新生代太小或对象生命周期意外长,需查代码或调大新生代。

2. [场景]线上 P99 延迟每 30 秒出现一次 400ms 尖刺。GC 日志显示:Young GC 正常(5ms),但每隔 30 秒出现一次 `Pause Full (G1 Compaction Pause) 1010M→980M(1024M) 412ms`。请分析根因并给出治理方案(先代码后参数)。
> [!答案] **2**　①根因:Full GC 是元凶——STW 412ms 恰好对应 P99 尖刺。每次 Full GC 回收量极小(1010M→980M,只腾出 30M),说明老年代对象大量存活着,回收不掉,很快又满又触发下一轮 Full GC,形成"30 秒一轮"的周期。②代码层面:`jmap -histo` 看哪类对象数量异常→若有缓存 Map 或 ThreadLocal 未清理→按上一话方式修复泄漏;同时检查下单路径是否有"循环拼字符串"等大对象分配热点,用 `StringBuilder` 替代 `+=`。③参数层面:代码治完后,若确认是容量问题(业务真实需要),适当增大堆 `-Xms2g -Xmx2g`,并设 `-XX:MaxGCPauseMillis=100` 引导 G1 控制停顿。**举一反三**:30 秒周期提示"某对象的生存周期约等于到达老年代的时间"——结合业务逻辑(如 session 过期时间、缓存 TTL、定时任务周期)交叉定位,往往能一击命中。

3. [综合]从"默认 G1"和"低延迟 ZGC"两个维度,分析 GC 选型的决策框架:什么场景用 G1、什么场景考虑 ZGC、什么指标决定切换时机。同时说明 JFR 在选型决策中的作用。
> [!答案] **3**　①G1 适合:堆 4~64G,延迟目标 P99<100ms,绝大多数 Web 服务——生态成熟、吞吐优、可设 `MaxGCPauseMillis` 引导停顿。②ZGC 适合:堆超大(64G~TB 级),或延迟要求极严(P99<1ms),如交易引擎、广告竞价、实时风控——停顿亚毫秒且几乎不随堆/存活集增大而变长。③切换时机:不是"感觉 GC 慢"就换,而是开 GC 日志/JFR 拿到数据——若 G1 的 Mixed GC 已触发 `MaxGCPauseMillis` 目标但 P99 仍超标,且优化代码和扩容均无效,再评估 ZGC。④JFR 作用:提供 GC 停顿分布图、分配热点、对象晋升速率等全维度数据,回答"STW 到底停多少、卡在哪"——有数据,选型才不是拍脑袋。**举一反三**:G1 和 ZGC 不是"谁更好"而是"谁更匹配业务特征"——中小堆、通用场景下 G1 的吞吐往往比 ZGC 高;ZGC 的价值在"大堆 + 低延迟"场景才真正发挥。

### 三、代码题(2 道)
1. [基础]写一段模拟 Minor GC 的代码并配置 GC 日志参数:持续分配 512KB 的 `byte[]`,用 `-Xlog:gc*` 开启统一日志,打印 3 次 Minor GC 并解读日志行。给出完整 JVM 启动命令。
> [!答案] **1 验收**:
> ```java
> // 启动参数: java -Xms64m -Xmx64m -Xlog:gc*:file=gc.log:time,uptime,level,tags -jar demo.jar
> public class MinorGcDemo {
>     public static void main(String[] args) {
>         for (int i = 0; i < 200; i++) {
>             byte[] tmp = new byte[512 * 1024]; // 512KB,配合 64M 堆触发 Minor GC
>             if (i % 50 == 0) System.out.println("分配第 " + i + " 次");
>         }
>     }
> }
> // 日志解读(取一条):
> // [2026-09-07T14:03:11.204+0800][12.450s][info][gc] GC(3) Pause Young (Normal) 45M->12M(64M) 4.203ms
> // ↑ GC(3):第 3 次 GC | Pause Young:年轻代回收 | 45M->12M:堆从 45M 降到 12M | (64M):堆总 64M | 4.203ms:停顿 4.2ms
> ```
> **举一反三**:关注日志中 `->` 后的数值——若每次 Minor GC 后残留逐渐升高(如 12M→18M→25M),说明有对象在"攒"着不回收,可能是逐步晋升老年代的信号。

2. [综合]写一个 `@RepeatedTest(10)` 测试,验证"下单日志拼接从 `+=` 重构为 `StringBuilder` 后,输出文本完全一致且内存分配显著降低"。用 JFR 编程式 API(`jdk.jfr.Recording`)或简单的 `Runtime.totalMemory()` 对比来拦截"垃圾制造回归"。
> [!答案] **2 验收**:
> ```java
> @RepeatedTest(10)
> void stringBuilder_sameResult_lessAllocation() {
>     var req = new OrderRequest("美式", 2);
> 
>     // 1. 验证行为一致
>     String oldResult = buildAuditWithConcat(req);     // += 旧版
>     String newResult = buildAuditWithBuilder(req);    // StringBuilder 新版
>     assertEquals(oldResult, newResult, "重构后输出必须一字不差");
> 
>     // 2. 验证分配减少
>     System.gc(); // 尽力清理,缩小噪音
>     long before = Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory();
>     for (int i = 0; i < 1000; i++) buildAuditWithBuilder(req);
>     long after = Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory();
>     long allocated = after - before;
> 
>     System.gc();
>     long beforeOld = Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory();
>     for (int i = 0; i < 1000; i++) buildAuditWithConcat(req);
>     long afterOld = Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory();
>     long allocatedOld = afterOld - beforeOld;
> 
>     assertTrue(allocated < allocatedOld,
>             "StringBuilder 版分配量应显著小于 += 版("+allocated+" vs "+allocatedOld+")");
> }
> 
> // 旧版:循环里 +=,每次创建新 String 对象
> String buildAuditWithConcat(OrderRequest req) {
>     String result = "";
>     for (int i = 0; i < 1000; i++) result += "[" + i + ":" + req + "]";
>     return result;
> }
> 
> // 新版:StringBuilder 内部分配,只产生一个最终 String
> String buildAuditWithBuilder(OrderRequest req) {
>     var sb = new StringBuilder();
>     for (int i = 0; i < 1000; i++) sb.append('[').append(i).append(':').append(req).append(']');
>     return sb.toString();
> }
> ```
> **举一反三**:`System.gc()` 在生产代码中是禁忌(强制触发 Full GC 不可控),但在测试中用它可以更干净地测量内存基线;生产环境用 JFR 的 `ObjectAllocationInNewTLAB` 和 `ObjectAllocationOutsideTLAB` 事件做无侵入的分配采样,开销在百分之一量级,一线可常开。
