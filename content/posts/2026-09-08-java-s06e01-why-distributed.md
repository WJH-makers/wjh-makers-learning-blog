# 《从零开始学 Java》46 · 单体为什么开始吃力(先讲问题,别急着拆)

> 连载特刊 · 第六季「分布式时代」第 1 话 · 基线 Java 25(最新 LTS)· Spring Boot 4.x · 项目检查点:单体 v5。
> 承接:第五季把咖啡站送上线、也学会了用 `jstack`/`jmap` 查线上事故——但那始终是**一台机器**。这一话看它什么时候会撑不住。

---

## 一、需求:流量翻十倍,一台机器还够吗

第五季结束时,咖啡站是个"上线并可排障的 Spring Boot 单体"(v5):单机并发扛住了、JVM 出问题也能诊断。可运营部一条消息进来——下周做联名活动,预估流量**翻十倍**。

阿零第一反应:「简单,微服务拆了不就行?我看大厂都这么干。」

豆豆一巴掌把他按住:「**打住。你连它卡在哪都不知道,拆什么?** 拆微服务是最后一步,不是第一步。今天只干一件事——**压测,把瓶颈量出来**。看清是 CPU 不够、内存不够,还是数据库连接不够,再谈拆。」

---

## 二、漫画 · 三堵看不见的墙

> **〔1〕** 阿零信心满满地把服务器换成一台更贵的:32 核、128G。「加钱加配置,总行了吧!」
> 豆豆(叼着豆子):「垂直扩展(scale up)。能顶一阵,但你钱包有底、机器也有天花板。而且——瓶颈可能根本不在这台机器上。」

> **〔2〕** 压测工具把 QPS 一路往上拉:1000、2000……到 3000 时曲线突然拍平,响应时间飙红。
> 阿零:「CPU 才 40%,内存也没满,它凭什么不动了?!」

> **〔3〕** JVM 城主翻开监控:线程全卡在同一处——等一个叫「数据库连接」的东西。远处 MySQL 仓库门口排着长队,只放行十个人。
> 豆豆:「看到没?**不是机器慢,是数据库连接池就那么大。** 你 32 核,可去数据库的门只有 10 扇。」

> **〔4〕** Timeout 迷雾从连接池里冒出来,一个个请求等到超时倒下。
> 阿零:「所以加机器没用?」豆豆:「加**应用**机器,大家还是挤这一个数据库这一个池。这就是单体到顶的真相——**先量,再拆**。」

---

## 三、本话目标

- 分清**垂直扩展**(加配置)与**水平扩展**(加机器)的边界;
- 认识单机三堵墙:**CPU、内存、数据库连接数**;
- 用压测把瓶颈**量化**出来,而不是靠猜;
- 读懂连接池打满的真实报错;
- 建立铁律:**先定位问题,再谈拆分**。

---

## 四、原理图:单体到顶的三堵墙

```text
                     早高峰:成千请求同时涌入
                              │
                   ┌──────────▼──────────┐
                   │   一台机器上的单体 v5   │
                   │  ┌───────────────┐   │
   墙①  CPU 打满 ──┼─▶│ Tomcat 线程池   │   │
                   │  └──────┬────────┘   │
   墙②  堆内存爆 ──┼────────▶│(对象堆积)    │
                   │  ┌──────▼────────┐   │
   墙③ DB连接耗尽 ─┼─▶│ HikariCP 连接池 │← 只有 N 个连接
                   │  └──────┬────────┘   │
                   └─────────┼────────────┘
                             ▼
                       一个 MySQL(全站共用)  ← 加应用机器也救不了它
```

三堵墙,先撞上哪堵取决于你的业务:

- **墙① CPU**:计算密集(加密、序列化、复杂运算)先顶到 CPU 100%,`jstack` 能抓到热点线程(第五季学过)。
- **墙② 内存**:对象堆积、缓存无上限,堆撑爆触发频繁 GC 甚至 OOM,`jmap` 能看堆(第五季学过)。
- **墙③ 数据库连接**:这是最阴的一堵。应用可以水平加机器,但它们**共用一个数据库**,连接池一满,再多机器也在门口排队。

## 五、代码:把瓶颈压出来

沿用 v5 的下单接口,先看它的连接池配置(`application.yml`)。第五季默认没细调,Spring Boot 用的是 HikariCP:

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/coffee
    hikari:
      maximum-pool-size: 10        # ← 连接池上限:同时只有 10 个连接能查库
      connection-timeout: 30000    # ← 拿不到连接,最多等 30 秒就报错
```

下单要查库存 + 扣库存,每个请求都要占一个连接。写个最小压测,用虚拟线程(Java 21+)轻松并发打 200 个请求:

```java
var client = HttpClient.newHttpClient();
long start = System.currentTimeMillis();
try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {   // 200 并发,毫无压力
    var reqs = new java.util.ArrayList<Future<?>>();
    for (int i = 0; i < 200; i++) reqs.add(pool.submit(() -> {
        var req = HttpRequest.newBuilder()
            .uri(URI.create("http://localhost:8080/api/menu")).GET().build();
        return client.send(req, HttpResponse.BodyHandlers.ofString()).statusCode();
    }));
    for (var r : reqs) r.get();   // 等全部返回
}
System.out.println("200 请求耗时:" + (System.currentTimeMillis() - start) + "ms");
```

## 六、故意制造一个 Bug:池太小,门太窄

保持 `maximum-pool-size: 10`,再把下单接口里查库存的方法故意加一句慢查询(模拟没建索引的全表扫描):

```java
// CoffeeService.java —— 故意让每次查库存慢 500ms(占着连接不放)
Thread.sleep(500);   // 别在真代码里这么写,这里只为放大连接占用时间
```

200 个请求抢 10 个连接,每个还占着 500ms 不放——门口必然堵死。跑压测。

## 七、读懂真实报错:连接池被榨干

日志里 Timeout 迷雾成片刷屏:

```text
org.springframework.jdbc.CannotGetJdbcConnectionException:
  Failed to obtain JDBC Connection
Caused by: java.sql.SQLTransientConnectionException:
  HikariPool-1 - Connection is not available, request timed out after 30000ms
    (total=10, active=10, idle=0, waiting=190)
```

一句话读懂:`total=10, active=10, idle=0, waiting=190`——**池子一共 10 个连接,全在用,190 个请求在排队**,排到 30 秒还没轮到,直接抛超时。

这时如果你去 MySQL 那头看,再把池子调大到几百,又会撞上数据库自己的墙:

```text
com.mysql.cj.jdbc.exceptions.CJException:
  Data source rejected establishment of connection,
  message from server: "Too many connections"   -- MySQL 默认 max_connections=151
```

**根因不是机器慢,是"通往数据库的门"就那么宽。** 加应用机器,只会让更多请求来抢同一个数据库的连接——这就是单体的天花板。

> **豆豆锐评 · 加机器不是万能药**
> 无脑水平扩展应用节点,在无状态计算上有效;但只要大家共享**同一个数据库**,DB 就是那个"分母"。真正的解法有三步递进:① 别让请求都打到 DB(**加缓存**,下一话);② 削峰、异步(**MQ**,E4);③ 数据库本身分库分表/读写分离。**先看清瓶颈在哪一层,再动手。**

> **🔀 豆豆的多解台 · 单机扛不住了,怎么扩?**

| 方式 | 做法 | 适合 | 天花板 / 坑 |
|---|---|---|---|
| **垂直扩展**(scale up) | 换更强的机器(加 CPU/内存) | 起步快、临时救急 | 单机有物理上限,越往上越贵;救不了 DB 连接瓶颈 |
| **水平扩展**(scale out) | 加应用实例 + 负载均衡分摊 | 无状态的计算/接口层 | **共享的 DB 不会因此变快**,反而更多实例来抢连接 |
| **架构拆分** | 加缓存、异步 MQ、读写分离、分库分表 | 前两招到顶后的根治 | 复杂度陡增,别在没瓶颈时提前上(本季主题) |

豆豆锐评:**先垂直顶一阵、再水平扩计算层,最后才动数据层与架构**——顺序反了就是过度设计。这一季就沿这条路,一步一步拆。

> **🎯 面试直击**:如何定位一个接口的性能瓶颈?
> 分层排查、逐层量化:先看**监控**(CPU/内存/GC/RT/QPS 曲线在哪拍平),再看**线程栈**(`jstack` 抓热点或阻塞点),看它卡在 CPU 计算、锁等待、还是 I/O(DB/网络)。数据库瓶颈的典型信号就是"CPU 不高但线程全在 `waiting`,连接池 active 打满"。**能说出'先量化再优化、不靠猜'就赢了一半**。

## 八、修复,并用测试证明连接不再溢出

修法两步:给库存查询**建索引**去掉慢查询,把连接池调到**匹配数据库承受力**的合理值(不是越大越好——连接是数据库的稀缺资源)。改完再压,`waiting` 归零。

用一个并发测试守住"连接池不被打爆"的底线:

```java
@Test
void concurrent_requests_should_not_exhaust_pool() throws Exception {
    var ok = new AtomicInteger();
    try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
        var tasks = new java.util.ArrayList<Future<?>>();
        for (int i = 0; i < 50; i++)
            tasks.add(pool.submit(() -> { if (menuService.list() != null) ok.incrementAndGet(); }));
        for (var t : tasks) t.get(10, TimeUnit.SECONDS);   // 10 秒内必须全部拿到连接返回
    }
    assertEquals(50, ok.get());   // 没有一个因拿不到连接而超时
}
```

绿了,说明在合理并发下连接不再溢出。但这只是"止血"——真正的减负,是别让菜单查询每次都去打数据库。

## 十一、下一话悬念

压测数据指得清清楚楚:菜单几乎不变,却被**每个请求反复查库**,连接池一大半耗在这上面。

> 下一话《Redis 高速取餐柜》:阿零给咖啡站装一个"高速取餐柜"——把热门菜单缓存在内存里,DB 压力肉眼可见地降下来。可他很快撞上缓存的三连暴击:**穿透、击穿、雪崩**,一个比一个能把数据库瞬间打崩。

## 🎯 随堂练习

先自己做,再对答案。每道答案都带一句「举一反三」,帮你把这一个点连成一片。

### 选择题(10 道)

1. 单体到顶的「三堵墙」是?
   - A) 带宽、磁盘、网络　B) **CPU、内存、数据库连接数**　C) 线程、进程、协程　D) 前端、后端、数据库
2. 垂直扩展和水平扩展的区别是?
   - A) 垂直 = 加机器,水平 = 换更强的机器　B) **垂直 = 换更强的机器(scale up),水平 = 加实例 + 负载均衡(scale out)**　C) 两者等价　D) 垂直只用于数据库
3. 水平扩展应用实例,救不了哪一堵墙?
   - A) CPU　B) 内存　C) **共享的数据库** —— 更多实例只会来抢同一批连接　D) 网络带宽
4. `total=10, active=10, idle=0, waiting=190` 这行 HikariCP 日志说明?
   - A) 连接池有 190 个连接　B) 池子共 10 个连接全在用,190 个请求在排队等　C) 有 190 个空闲连接　D) 数据库宕机了
5. MySQL 默认的 `max_connections` 大约是?
   - A) 51　B) 151　C) 1000　D) 无上限
6. 连接池 `maximum-pool-size` 该怎么定?
   - A) 越大越好　B) 匹配数据库的承受力 —— 连接是数据库的**稀缺资源**,盲目调大会拖垮 DB　C) 等于线程池大小　D) 固定 100
7. 数据库瓶颈的典型信号是?
   - A) CPU 100%　B) **CPU 不高,但线程大量 `waiting`、连接池 active 打满**　C) 频繁 Full GC　D) 内存持续上涨
8. 定位性能瓶颈的正确方法论是?
   - A) 凭经验猜最可能的点　B) 分层排查、逐层量化:先看监控曲线,再看线程栈,判断卡在 CPU / 锁 / IO　C) 直接加机器观察　D) 先重构代码
9. 本话建议的扩展顺序是?
   - A) 先拆微服务 → 再加缓存 → 最后加机器　B) **先垂直顶一阵 → 再水平扩计算层 → 最后才动数据层与架构**　C) 一步到位上分库分表　D) 只做垂直扩展
10. 「先定位问题,再谈拆分」这条铁律针对的是?
    - A) 代码规范　B) 在没有量化出瓶颈前就急着上微服务的过度设计　C) 测试策略　D) 部署流程

> [!答案]
> **1-B**　三堵墙先撞哪堵取决于业务类型。**举一反三**:CPU 墙用 `jstack`、内存墙用 `jmap`,这都是第五季的成果;第三堵墙才是本季新课题。
> **2-B**　一个往上长,一个往外长。**举一反三**:垂直扩展起步快但有物理上限且越往上越贵,水平扩展理论无上限但要求服务无状态。
> **3-C**　DB 是那个「分母」。**举一反三**:所以真正的解法是「别让请求都打到 DB」(缓存)、「削峰异步」(MQ)、「拆数据层」三步递进。
> **4-B**　四个数字讲完了整个故事。**举一反三**:看到 `waiting` 数远大于 `total`,基本可以确定是连接池配置或慢查询问题。
> **5-B**　默认 151。**举一反三**:所以把应用侧连接池调到几百是自欺欺人 —— 会直接撞上 `Too many connections`。
> **6-B**　连接是稀缺资源。**举一反三**:经验上连接池不必很大,把慢查询治好比调大池子有效得多。
> **7-B**　线程都在等 IO,CPU 反而闲着。**举一反三**:这正是「CPU 高就是忙、CPU 低就是闲」这种直觉最容易骗人的地方。
> **8-B**　先量化再优化,不靠猜。**举一反三**:面试里能说出这条方法论,比背出十个调优参数更能拿分。
> **9-B**　顺序反了就是过度设计。**举一反三**:每一步都比上一步复杂度高一个量级,不该跳级。
> **10-B**　没瓶颈就别拆。**举一反三**:过早微服务化会把本地方法调用变成网络调用 + 分布式事务,复杂度暴涨而收益为零。
