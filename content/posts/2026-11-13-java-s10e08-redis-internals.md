## 四、原理图:三支柱与特制家具

```text
Redis 为什么快 —— 三支柱
① 纯内存         数据全在内存,读写不碰磁盘寻道
② IO 多路复用    epoll:一个线程盯上万连接,谁就绪处理谁,不傻等
③ 单线程执行命令  免锁、免上下文切换、命令天然原子
   边界:6.0 起的多线程只做网络 IO 收发与协议解析,执行命令的仍是那一根
```

| 类型 | 底层 | 快在哪 |
|---|---|---|
| String | SDS:长度头 + 预分配 | 取长度 O(1);C 字符串要数到 `\0`,还存不了二进制 |
| List | quicklist:双向链表串起压缩块 | 两端进出 O(1),中段省内存 |
| Hash / Set | 元素少走紧凑编码,变大升级哈希表 | 小数据省内存,大数据 O(1) |
| ZSet | 跳表 + 字典 | 范围查 O(log n),单点查 O(1) |

7.0 起「紧凑编码」由 **listpack** 取代 ziplist。ZSet 选跳表不选红黑树:**范围查询顺着底层链表平走**、**实现简单得多**。

```text
持久化两条腿 + 一个合体
  RDB —— fork 子进程拍全量快照,COW 让主进程照常营业;恢复快,丢得多
  AOF —— 追加命令日志,everysec 刷盘:最多丢约 1 秒
  混合 —— 4.0 起 RDB 打底 + 增量 AOF:恢复快、丢得少

高可用三级跳
  主从(异步复制,主挂可能丢最后几笔)
   → 哨兵(投票判死 + 自动故障转移)
    → Cluster(固定 16384 槽,CRC16(key) % 16384 定位节点)
```

> **豆豆旁白**:缓存穿透/击穿/雪崩三问,回看第 47 话。再记两句:**大 key** 会卡住那根单线程,人人陪等;**热 key** 会打爆单节点——都得拆。

> **🎯 面试直击**:Redis 单线程为什么还这么快?
> 纯内存 + epoll 多路复用 + 单线程免锁免切换,瓶颈在网络不在 CPU。必被追问:**6.0 的多线程只管网络 IO 与协议解析,命令执行仍单线程**,单条命令的原子性没变。

## 五、代码:给商品状态加缓存读路径

给「商品上下架」接上缓存。本地可跑可测:用 `ConcurrentHashMap` 模拟 Redis 的 GET/SET/DEL 语义,真实项目换成 Redis 客户端,**读写顺序的逻辑一字不改**:

```java
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public class MenuStatusCache {

    final Map<String, String> redis = new ConcurrentHashMap<>(); // 模拟 Redis
    final Map<String, String> db    = new ConcurrentHashMap<>(); // 模拟 MySQL

    public MenuStatusCache() { db.put("香草拿铁", "在售"); }

    /** 读路径:缓存 → 未命中查库 → 回填 */
    public String status(String name) {
        var v = redis.get(name);
        if (v != null) return v;
        v = db.getOrDefault(name, "无此商品");
        redis.put(name, v);  // 回填
        return v;
    }

    /** 写路径(先删为敬):先删缓存,再写库 */
    public void offline(String name) {
        redis.remove(name);  // ① 先删缓存
        // ← 中间隔着网络往返,足够一个并发读挤进来
        db.put(name, "已下架");  // ② 后写库
    }
}
```

## 六、故意制造一个 Bug:先删缓存,再写库

香草拿铁告急下架。Race 双胞胎照第 5 格剧本,把一个并发读插进 ①② 的缝里——按真实时序重放:

```java
void main() {
    var s = new MenuStatusCache();
    s.redis.remove("香草拿铁");  // 运维:① 先删缓存
    IO.println("顾客A读到:" + s.status("香草拿铁"));  // 并发读挤进缝隙
    s.db.put("香草拿铁", "已下架");  // 运维:② 才写库
    IO.println("库里此刻:" + s.db.get("香草拿铁"));
    IO.println("顾客B读到:" + s.status("香草拿铁"));
}
```

## 七、观察真实现象

```text
顾客A读到:在售
库里此刻:已下架
顾客B读到:在售
```

库里明明「已下架」,顾客却一直看到「在售」——**旧值复活**。复盘:删缓存后、写库前,顾客 A 未命中,从库里读到**旧值**并回填;写库完成时,缓存里已躺着旧数据,之后所有读全命中它,**不设 TTL 就永远错下去**。不报错不打日志——比崩溃更阴。

## 八、修复,并用测试证明

阿零想打补丁:睡几百毫秒**再删一次**(延迟双删)。豆豆摇头:「睡多久靠拍脑袋,第二删失败照样旧值。**换顺序才是正解**。」

```java
/** 写路径(修复):先更库,再删缓存 */
public void offlineFixed(String name) {
    db.put(name, "已下架");  // ① 先更库
    redis.remove(name);  // ② 再删缓存
}
```

并发读插在 ① 前,回填的旧值随后被 ② 删掉;插在 ①② 之间,回填的已是**新值**。JUnit 把两种顺序的最坏时序各重放一遍:

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class MenuStatusCacheTest {

    @Test
    void delete_cache_first_lets_stale_value_resurrect() {
        var s = new MenuStatusCache();
        s.redis.remove("香草拿铁");  // ① 先删缓存
        s.status("香草拿铁");  // 并发读插队,回填旧值
        s.db.put("香草拿铁", "已下架");  // ② 后写库
        assertEquals("在售", s.status("香草拿铁"));  // 旧值复活:坏顺序的罪证
    }

    @Test
    void update_db_first_then_evict_stays_fresh() {
        var s = new MenuStatusCache();
        s.status("香草拿铁");  // 缓存先有旧值
        s.db.put("香草拿铁", "已下架");  // ① 先更库
        s.redis.remove("香草拿铁");  // ② 再删缓存
        assertEquals("已下架", s.status("香草拿铁")); // 回填的已是新值
    }
}
```

> **🔀 豆豆的多解台 · 缓存一致性怎么保?**

| 方案 | 做法 | 适合什么时候 | 坑 |
|---|---|---|---|
| 先更库,再删缓存 | Cache-Aside 标准写序 | **绝大多数业务的默认解** | 残余竞态概率极小(读旧库值、删后才回填) |
| 延迟双删 | 删 → 更库 → 睡 → 再删 | 被迫「先删后更」的旧代码救急 | 睡多久拍脑袋;第二删失败仍旧值 |
| 订阅 binlog 兜底 | 监听库变更,异步删缓存 | 一致性要求高的核心数据 | 多一套组件;最终一致而非强一致 |

豆豆锐评:**默认「先更库再删缓存」,核心数据加 binlog 兜底**;延迟双删只是给欠账续命,别当首选。

**Q5(设计)** 你需要为咖啡站的商品菜单设计「三级缓存一致性方案」:核心商品要求强一致,普通商品容忍短时不一致,静态数据缓存永不过期。请为三个级别分别设计缓存更新策略,并说明每种策略的并发安全保证。

> [!答案]
> **选择题**
> 1-B。纯内存(数据在内存,读写不碰磁盘)→epoll(一个线程盯上万连接)→单线程执行命令(免锁免切换)。★举一反三:前两点决定「快」,第三点决定了「为什么单线程还快」——瓶颈在 IO 和内存,不在 CPU。
>
> 2-B。6.0 IO 多线程只处理网络数据收发与 RESP 协议解析,命令执行依然是那根单线程。★举一反三:这样设计的好处是「单条命令的原子性」完全不变——多线程引入线程安全风险但只做外围杂活。
>
> 3-A。SDS 结构中有一个 len 字段记录当前长度,O(1) 获取;预分配策略减少频繁 realloc;不依赖 `\0` 终止符,能存任意二进制(如图片缩略图)。★举一反三:C 字符串取长度要数到 `\0`——O(n)。
>
> 4-A。跳表实现比红黑树简单得多(核心代码几十行),而 ZSet 的范围查询(ZRANGE/ZREVRANGE)直接顺着跳表最底层的链表平移即可(红黑树需要中序遍历)。★举一反三:选择数据结构不一定只看大 O——实现复杂度、范围查询便利性也是真实考量。
>
> 5-B。混合持久化:先 RDB 打底(快照到某个时间点),之后的写命令记录为 AOF 增量。恢复时先读 RDB,再重放增量——兼具 RDB 的恢复速度和 AOF 的少量丢失。★举一反三:这是 Redis 4.0 开始默认推荐的方式。
>
> 6-B。CRC16 哈希 + 16384 槽位,slot = CRC16(key) % 16384,每个节点负责一部分槽。★举一反三:16384 个槽被设计为在集群节点间传递心跳信息时压缩性好(bitmap 2KB),而不是像一致性哈希的虚拟节点。
>
> 7-B。时序:删缓存→并发读从 DB 读到旧值并回填→写库→缓存里躺着旧值且永远有效。★举一反三:这个问题的隐蔽性在于:不报错、不打日志,看起来一切正常——直到对账发现货不对板。
>
> 8-B。极端情况下:①读找到缓存 miss;②读去 DB 查到旧值;③写更新了 DB 并删了缓存;④读把旧值回填——概率极低(需要读写时序精确重叠),且只在写操作的瞬间有窗口。相比「先删后更」的「只要一次并发读就必复活」,安全得多。★举一反三:绝大多数场景下「先更库再删缓存」已足够安全,核心数据可以加 binlog 异步兜底。
>
> 9-B。延迟 = 睡多久?太小可能没删到,太大增加不一致窗口;而且第二次删除调用是异步的,可能失败(网络超时等)。★举一反三:延迟双删是「欠了债的先删后更代码」的续命稻草,不是首选。
>
> 10-A。主从(异步复制,读扩展+备份)→哨兵(自动 failover,高可用)→Cluster(16384 槽,数据分片,水平扩展)。★举一反三:三者不是替代关系,是演进——Cluster 里面每个分片内部仍然是主从 + 哨兵那套。
>
> **解答题**
>
> **Q1** RDB:fork 子进程拍全量快照,COW 让主进程照常营业;触发:配置 `save`(如 900s 内 1 个 key 变化)或手动 `BGSAVE`;优:恢复快、文件小;缺:丢得多(两次快照间的数据)。AOF:追加写命令日志;触发:everysec 刷盘(每秒);优:丢得少(最多 1 秒);缺:文件大、恢复慢(需重放)。混合(4.0+):RDB 打底 + 增量 AOF;优:恢复快且丢得少;缺:文件可读性不如纯 AOF。★举一反三:生产推荐混合持久化,两者优点兼得。
>
> **Q2** 不受影响。6.0 的多线程只在网络层:客户端连接的数据读取(RECV)和响应写入(SEND)可以由多个 IO 线程并行处理,但命令的解析和实际执行(如 SET/GET/INCR)仍然在**主线程**中串行完成。这是一个「外围多线程 + 核心单线程」的架构,命令执行路径不变——单条命令的原子性、事务(MULTI/EXEC)的隔离性、Lua 脚本的原子性全部完好。★举一反三:这种设计模式类似 Netty 的主从 Reactor 模型——accept 和 IO 多线程,业务逻辑单线程。
>
> **Q3** 可能原因:先删缓存后改库的乱序——①运营操作触发「删缓存」→②顾客查询「香草拿铁」未命中,从 DB 读到旧值「在售」并回填缓存→③运营的「改库」完成。结果:缓存里躺着旧值,TTL 无限(或很长),此后所有顾客都命中旧缓存。修复:把顺序改为「先更库,再删缓存」——①先改 DB 为「已下架」→②再删缓存;若有并发读插在①②中间,读到的是「已下架」再回填缓存,正确。兜底:订阅 binlog,监听 DB 变更,延迟再删一次缓存。★举一反三:缓存一致性是分布式系统的经典难题——没有完美解,只有「概率足够低」和「排查手段够快」。
>
> **Q4** 实现复杂度:跳表核心代码几十行(随机层级 + 插入/查找/删除),红黑树需要处理五种旋转情况,实现和维护复杂度都明显更高。范围查询效率:跳表底层有一条完整的有序链表,范围查询(如 ZRANGE key 0 100)直接顺链平走,复杂度 O(log n + m)(m 是返回数量);红黑树需要中序遍历,虽然也是 O(log n + m)但需要遍历指针和递归/栈维护,不如链表简单直接。维护成本:跳表的随机层级策略在概率上保证了平衡(类似 skiplist 的期望高度 log n),不需要像红黑树那样在每次插入/删除后做旋转重新平衡。★举一反三:选型不是只看大 O——跳表在「足够快 + 实现简单」之间的 trade-off 做得刚刚好,Redis 的品味在此。
>
> **Q5** 三级设计:①**强一致**(核心商品——价格/库存):「先更库,再删缓存」+ binlog 异步兜底(监听 DB 变更,延迟 500ms 再删一次缓存,覆盖残余竞态)。并发窗口概率已极低,binlog 兜底相当于「保险」。②**容忍短时不一致**(普通商品——描述/图片):「先更库,再删缓存」+ 合理 TTL(如 10 分钟)——即使极端情况下读到了旧值,TTL 到期后自然纠正。③**静态数据**(菜单分类、固定文案):永不过期 + 应用启动时预加载到本地缓存(Caffeine/Guava,或 Redis 不设 TTL)——数据不变,不需要失效策略;修改时手动刷新或发版刷新。★举一反三:分级策略的核心思想:不是所有数据都需要同一级别的一致性保证——区分「库存数字」(错一秒赔钱)和「商品描述」(错五分钟没人发现),把精力花在刀刃上。
