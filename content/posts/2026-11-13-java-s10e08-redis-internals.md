## 二、漫画 · 取餐柜的引擎室

> **〔1〕** 取餐柜侧门打开,里面只有**一个**戴耳麦的店员,面前一整面墙的呼叫灯。
> 阿零:「就……一个人?!」豆豆:「一个人,快过一屋子。看他干活。」

> **〔2〕** 【特写格】店员不挨个窗口问,只盯灯板——哪盏亮(数据就绪)处理哪个。阿零:「多雇几个不是更快?」店员头也不回:「多人就得抢柜子——锁、排队、换班全是开销。我一个人,**免锁免切换,每条命令天然原子**。」
> 豆豆:「盯灯板,就是 **epoll 多路复用**:一个线程看住上万条连接,绝不为慢客户傻等。」

> **〔3〕** 【剖面格】柜体内部:带长度刻度的 **SDS 尺子**、小车厢串成的 **quicklist 火车**、斜搭楼层的**跳表电梯**。
> 豆豆:「快不止靠线程模型,家具全是特制的。」

> **〔4〕** 角落里,一个「影子店员」被 fork 出来,抱着相机拍全店快照,真店员照常营业。
> 豆豆:「**写时复制(COW)**,谁也不碍谁;断电了,靠这张照片复活。」

> **〔5〕** 阿零撸起袖子:「懂了!下架商品我顺手清缓存——**先删为敬**!」暗处,**Race 双胞胎**交换眼神,窜进「删缓存」与「写库」的缝隙。
> 豆豆(叼着豆子):「'先删为敬'……这四个字,明天会让你社死。」

## 三、本话目标

- 讲清快的三支柱:纯内存、epoll 多路复用、单线程执行(含 6.0 IO 线程的边界);
- 掀开数据类型底层:SDS、quicklist、小编码升级、跳表;
- 分清 RDB / AOF / 混合持久化,与主从 → 哨兵 → Cluster 三级高可用;
- 踩一次「先删缓存再写库」的旧值复活,并给缓存一致性方案排序。

## 四、原理图:三支柱与特制家具

```text
Redis 为什么快 —— 三支柱
① 纯内存         数据全在内存,读写不碰磁盘寻道
② IO 多路复用    epoll:一个线程盯上万连接,谁就绪处理谁,不傻等
③ 单线程执行命令  免锁、免上下文切换、命令天然原子
   边界:6.0 起的多线程只做网络 IO 收发与协议解析,执行命令的仍是那一根
```

| 类型 | 底层 | 快在哪 |
|---|---|---|
| String | SDS:长度头 + 预分配 | 取长度 O(1);C 字符串要数到 `\0`,还存不了二进制 |
| List | quicklist:双向链表串起压缩块 | 两端进出 O(1),中段省内存 |
| Hash / Set | 元素少走紧凑编码,变大升级哈希表 | 小数据省内存,大数据 O(1) |
| ZSet | 跳表 + 字典 | 范围查 O(log n),单点查 O(1) |

7.0 起「紧凑编码」由 **listpack** 取代 ziplist。ZSet 选跳表不选红黑树:**范围查询顺着底层链表平走**、**实现简单得多**。

```text
持久化两条腿 + 一个合体
  RDB —— fork 子进程拍全量快照,COW 让主进程照常营业;恢复快,丢得多
  AOF —— 追加命令日志,everysec 刷盘:最多丢约 1 秒
  混合 —— 4.0 起 RDB 打底 + 增量 AOF:恢复快、丢得少

高可用三级跳
  主从(异步复制,主挂可能丢最后几笔)
   → 哨兵(投票判死 + 自动故障转移)
    → Cluster(固定 16384 槽,CRC16(key) % 16384 定位节点)
```

> **豆豆旁白**:缓存穿透/击穿/雪崩三问,回看第 47 话。再记两句:**大 key** 会卡住那根单线程,人人陪等;**热 key** 会打爆单节点——都得拆。

> **🎯 面试直击**:Redis 单线程为什么还这么快?
> 纯内存 + epoll 多路复用 + 单线程免锁免切换,瓶颈在网络不在 CPU。必被追问:**6.0 的多线程只管网络 IO 与协议解析,命令执行仍单线程**,单条命令的原子性没变。

## 五、代码:给商品状态加缓存读路径

给「商品上下架」接上缓存。本地可跑可测:用 `ConcurrentHashMap` 模拟 Redis 的 GET/SET/DEL 语义,真实项目换成 Redis 客户端,**读写顺序的逻辑一字不改**:

```java
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public class MenuStatusCache {

    final Map<String, String> redis = new ConcurrentHashMap<>(); // 模拟 Redis
    final Map<String, String> db    = new ConcurrentHashMap<>(); // 模拟 MySQL

    public MenuStatusCache() { db.put("香草拿铁", "在售"); }

    /** 读路径:缓存 → 未命中查库 → 回填 */
    public String status(String name) {
        var v = redis.get(name);
        if (v != null) return v;
        v = db.getOrDefault(name, "无此商品");
        redis.put(name, v);  // 回填
        return v;
    }

    /** 写路径(先删为敬):先删缓存,再写库 */
    public void offline(String name) {
        redis.remove(name);  // ① 先删缓存
        // ← 中间隔着网络往返,足够一个并发读挤进来
        db.put(name, "已下架");  // ② 后写库
    }
}
```

## 六、故意制造一个 Bug:先删缓存,再写库

香草拿铁告急下架。Race 双胞胎照第 5 格剧本,把一个并发读插进 ①② 的缝里——按真实时序重放:

```java
void main() {
    var s = new MenuStatusCache();
    s.redis.remove("香草拿铁");  // 运维:① 先删缓存
    IO.println("顾客A读到:" + s.status("香草拿铁"));  // 并发读挤进缝隙
    s.db.put("香草拿铁", "已下架");  // 运维:② 才写库
    IO.println("库里此刻:" + s.db.get("香草拿铁"));
    IO.println("顾客B读到:" + s.status("香草拿铁"));
}
```

## 七、观察真实现象

```text
顾客A读到:在售
库里此刻:已下架
顾客B读到:在售
```

库里明明「已下架」,顾客却一直看到「在售」——**旧值复活**。复盘:删缓存后、写库前,顾客 A 未命中,从库里读到**旧值**并回填;写库完成时,缓存里已躺着旧数据,之后所有读全命中它,**不设 TTL 就永远错下去**。不报错不打日志——比崩溃更阴。

## 八、修复,并用测试证明

阿零想打补丁:睡几百毫秒**再删一次**(延迟双删)。豆豆摇头:「睡多久靠拍脑袋,第二删失败照样旧值。**换顺序才是正解**。」

```java
/** 写路径(修复):先更库,再删缓存 */
public void offlineFixed(String name) {
    db.put(name, "已下架");  // ① 先更库
    redis.remove(name);  // ② 再删缓存
}
```

并发读插在 ① 前,回填的旧值随后被 ② 删掉;插在 ①② 之间,回填的已是**新值**。JUnit 把两种顺序的最坏时序各重放一遍:

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class MenuStatusCacheTest {

    @Test
    void delete_cache_first_lets_stale_value_resurrect() {
        var s = new MenuStatusCache();
        s.redis.remove("香草拿铁");  // ① 先删缓存
        s.status("香草拿铁");  // 并发读插队,回填旧值
        s.db.put("香草拿铁", "已下架");  // ② 后写库
        assertEquals("在售", s.status("香草拿铁"));  // 旧值复活:坏顺序的罪证
    }

    @Test
    void update_db_first_then_evict_stays_fresh() {
        var s = new MenuStatusCache();
        s.status("香草拿铁");  // 缓存先有旧值
        s.db.put("香草拿铁", "已下架");  // ① 先更库
        s.redis.remove("香草拿铁");  // ② 再删缓存
        assertEquals("已下架", s.status("香草拿铁")); // 回填的已是新值
    }
}
```

> **🔀 豆豆的多解台 · 缓存一致性怎么保?**

| 方案 | 做法 | 适合什么时候 | 坑 |
|---|---|---|---|
| 先更库,再删缓存 | Cache-Aside 标准写序 | **绝大多数业务的默认解** | 残余竞态概率极小(读旧库值、删后才回填) |
| 延迟双删 | 删 → 更库 → 睡 → 再删 | 被迫「先删后更」的旧代码救急 | 睡多久拍脑袋;第二删失败仍旧值 |
| 订阅 binlog 兜底 | 监听库变更,异步删缓存 | 一致性要求高的核心数据 | 多一套组件;最终一致而非强一致 |

豆豆锐评:**默认「先更库再删缓存」,核心数据加 binlog 兜底**;延迟双删只是给欠账续命,别当首选。
