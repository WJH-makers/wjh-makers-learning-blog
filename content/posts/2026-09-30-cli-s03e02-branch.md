# 《从零开始玩命令行》12 · 平行时间线:branch 与 merge

> 连载特刊 · 第二部《从零开始玩命令行》第 3 卷「Git 时间机」第 2 话
> 长期项目:**把豆豆咖啡站部署上真实服务器**。承接上一话:咖啡站进了 Git,但所有存档挤在一条 main 上,不敢做实验。全卷地图见 [/cli](/cli)。

## 一、需求:想做实验,又怕炸了主线

阿零要给咖啡站加"会员折扣",这功能一时半会调不好。他不敢直接在 `main` 上改——万一改到一半豆豆要上线,拿到的就是个半成品。他问守卫:「能不能另开一条时间线,在那边随便折腾,成了再合回来?」

守卫:「这正是 `branch` 的用处。**分支是平行时间线**——你在支线炸得再惨,主线毫发无伤;调好了,`merge` 一句汇回主线。」

---

## 二、漫画 · 岔开的沙流

> **〔1〕** 守卫的沙漏一晃,单股沙流"啵"地裂成两条并行的光带。
> 守卫:「上面这条是 `main`,你的正式时间线。下面这条,归你实验。」

> **〔2〕** 阿零 `git switch -c feature/discount`,身影一分为二,一个站主线、一个跳上支线。
> 特米:「`-c` = create + switch,开一条新分支并跳过去。你现在站在支线上,改什么都不惊动 main。」

> **〔3〕** 阿零在支线把拿铁改成会员价 16,提交。守卫钉下一颗只属于支线的钉子。
> 阿零:「主线那边还是 20?」守卫:「一字没动。两条时间线,各活各的。」

> **〔4〕** 剧情突变:豆豆在主线上也把拿铁**涨到 22**(旺季调价),提交。两条时间线都动了`同一行`。
> 特米(眯眼):「要出事了——待会儿合并,Git 会发现两边对同一行给了**不同答案**。」

> **〔5〕** 阿零回主线 `git merge feature/discount`,屏幕炸出红字 `CONFLICT`。他一慌:「Git 坏了?!」
> 守卫:「没坏。它诚实地说:**这一行我不敢替你做主**——16 还是 22,你定。」

> **〔6〕** 阿零打开文件,看见 `<<<<<<<` `=======` `>>>>>>>` 三道分割线,把两个版本并排摆着。
> 特米:「这不是乱码,是 Git 给你的**选择题**。删掉标记、留下你要的那版,再 `add`+`commit`,冲突就化解了。」

## 三、本话目标

- `git branch` / `git switch` 开分支、切分支,`switch -c` 一步到位;
- 理解分支的本质:**一个指向某个提交的可移动指针**,不是"文件的副本";
- `git merge` 汇流,看懂 fast-forward 与"真合并提交"的区别;
- 读懂冲突标记 `<<<<<<< ======= >>>>>>>`,手动解决冲突;
- 踩一次两边改同一行的冲突,并用 `git log --graph` 验证合并形状。

## 四、原理图:分支只是一个指针

```text
分支 = 一个贴在某次提交上的可移动标签,切换几乎零成本

      feature/discount
             │
             ▼
初始 ●────────● (会员价 16)
      \
       ●  (涨价 22)
       ▲
       │
      main   ← 你现在站这里(HEAD 指向 main)

merge 的两种结局:
  fast-forward:main 没动过,直接把标签快进到支线尖端(不产生新提交)
  真合并      :两边都动过 → 生成一个"合并提交",有两个父亲,
               若动了同一行 → 冲突,需你手动裁决
```

一句心法:**分支切换改的只是 HEAD 这个指针指向谁**,所以开一百条分支也不占多少空间——它不是复制文件,是贴标签。

## 五、上手:开支线、做实验、汇回主线

```bash
$ git switch -c feature/discount     # 开"会员折扣"支线并跳过去
Switched to a new branch 'feature/discount'

# 在支线把拿铁改成会员价 16,提交
$ printf '拿铁 = 16\n美式 = 18\n' > menu.txt
$ git commit -am "feat: 拿铁会员价 16"

$ git switch main                    # 回主线
Switched to branch 'main'
```

> **特米旁白**:`git commit -am` 里的 `-a` 会自动把**已跟踪文件**的改动一起 `add`(新建的未跟踪文件不管用,那种还得手动 `git add`)。省一步,但别养成不看 `status` 就 `-am` 的习惯。

这时豆豆在主线上把拿铁涨到了 22(旺季调价):

```bash
$ printf '拿铁 = 22\n美式 = 18\n' > menu.txt
$ git commit -am "feat: 拿铁涨价 22"
```

现在两条时间线都改了拿铁那一行。合并:

```bash
$ git merge feature/discount
Auto-merging menu.txt
CONFLICT (content): Merge conflict in menu.txt
Automatic merge failed; fix conflicts and then commit the result.
```

第一次冲突,如约而至。注意 `Auto-merging`——Git **先尽力自动合并**,只有它拿不准的行才丢给你。

## 六、故意制造一个 Bug:冲突了却硬 commit

阿零被红字吓到,想绕过去,直接 `git commit`,结果什么也提交不了;他又想"是不是没 add",于是 `git add` 后再 commit——**把带 `<<<<<<<` 标记的半成品文件提交了进去**。这是新手最常见的两种翻车。先看正确姿势:冲突态下 `git status` 会明确告诉你该干嘛。

## 七、读懂现象:冲突标记是一道选择题

```bash
$ git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   menu.txt
```

`both modified` = 两边都改了这文件。打开它:

```text
<<<<<<< HEAD
拿铁 = 22
=======
拿铁 = 16
>>>>>>> feature/discount
美式 = 18
```

三道线的读法,记死它:

- `<<<<<<< HEAD` 到 `=======`:**当前分支(main)** 的版本 → 拿铁 22;
- `=======` 到 `>>>>>>> feature/discount`:**被合并进来那条分支** 的版本 → 拿铁 16;
- `美式 = 18` 没被包起来:两边一致,Git 已自动合好,不用管。

解决 = **把三道标记全删掉,只留你要的最终内容**。假设决定用会员价 16:

```bash
# 手动编辑 menu.txt,改成最终想要的样子:
#   拿铁 = 16
#   美式 = 18
$ git add menu.txt               # 用 add 告诉 Git"这行我裁决完了"
$ git status
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)
Changes to be committed:
	modified:   menu.txt

$ git commit --no-edit           # 收尾,生成合并提交(--no-edit 用默认信息)
[main cdd145b] Merge branch 'feature/discount'
```

> **豆豆锐评**:冲突不是 Git 出 bug,是它**拒绝替你瞎猜**——两个人对同一行给了不同答案,只有你知道该听谁的。真慌了就 `git merge --abort`,一键回到合并前,重新来过,零损失。

## 八、用命令验证:合并的形状对不对

```bash
$ git log --oneline --graph
*   cdd145b Merge branch 'feature/discount'
|\
| * 40295f7 feat: 拿铁会员价 16
* | 7cbdf87 feat: 拿铁涨价 22
|/
* 6aceab4 feat: 初始菜单

$ git branch                     # 支线还在,合完可删
* main
  feature/discount
$ git branch -d feature/discount # 合并过的分支,-d 安全删除
```

`git log --graph` 里那个 `|\ ... |/` 菱形,就是"两条时间线分叉又汇合"的真实形状——一眼看出这里发生过一次合并。

> **🪟 双系统对照 · 冲突处理跨系统一致**

| 环节 | Git Bash | PowerShell 7 | 备注 |
|---|---|---|---|
| 开/切分支 | `git switch -c x` | `git switch -c x` | **完全一样** |
| 冲突标记长相 | `<<<<<<< ======= >>>>>>>` | 同左 | 是文件内容,与系统无关 |
| 编辑冲突文件 | `vim` / `nano` | VS Code、记事本均可 | 用什么编辑器随意,删掉三道线即可 |
| 中止合并 | `git merge --abort` | `git merge --abort` | 一致 |

冲突解决是纯 git + 编辑文本,**两系统零差异**。唯一要留神的是换行符——那是下一卷 rebase 那话的坑,这里先不碰。

> **🎯 面试直击**:`git switch`、`git checkout`、`git branch` 都能碰分支,有啥区别?
> `git branch` 只**管理**分支(列出/新建/删除),自己不切换;`git switch` 是新版**专职切分支**的命令(`-c` 新建并切);`git checkout` 是老命令,又能切分支又能恢复文件,职责太杂容易误伤,所以 Git 2.23 后拆成了 `switch`(切分支)+ `restore`(恢复文件)。追问点:fast-forward merge 和普通 merge 的区别——前者目标分支没有新提交,直接快进指针、不产生合并提交;后者两边都有新提交,才生成有两个父亲的合并提交。

### 解答题(5 道)

**Q1 概念:** 什么是 Git 分支?用"时间线的平行宇宙"比喻解释分支的用途。

**Q2 解释:** 用图示和文字解释 fast-forward 合并和"真合并"的区别。为什么 `--no-ff` 有时是更好的选择?

**Q3 操作:** 写出从创建 `fix-login-bug` 分支到修复 bug 后合并回 `main` 的完整操作序列。

**Q4 排障:** 菜菜在 `feature` 分支上执行 `git merge main`,遇到合并冲突。请给出从检查冲突→解决冲突→标记已解决→完成合并的完整步骤。

**Q5 综合设计:** 咖啡站的团队有 3 个人同时开发:菜菜做登录功能,豆豆改支付模块,阿零修 bug。请设计一套分支策略(含命名规则、合并顺序、冲突处理流程)。

> [!答案]
> **1-C** `git branch` 列出所有本地分支,当前分支前有 `*`。**举一反三:**`git branch -a` 同时列出远程分支;`git branch -r` 只列远程分支。🪟 Git GUI 工具(如 GitKraken、Sourcetree)用图形化方式展示分支。
>
> **2-C** `git switch -c feature-login`(Git 2.23+)创建并切换。旧命令:`git checkout -b feature-login`。**举一反三:**`git switch` 和 `git restore` 是 Git 2.23 引入的新命令,专门负责分支切换和文件恢复,语义比 `checkout` 更清晰。建议新用户用 `switch`/`restore` 替代 `checkout`。
>
> **3-B** 当目标分支(main)在 branch 创建后没有新提交时,合并就是简单的"快进指针"(把 main 的指针直接移到 feature 的最新提交),不产生新的合并提交。**举一反三:**`--ff-only` 只在可以快进时才合并,否则拒绝——适合"要么干净,要么别做"的场景。
>
> **4-B** Git 使用 `<<<<<<<`(当前分支)、`=======`(分界线)、`>>>>>>>`(被合并分支)标记冲突区域。**举一反三:**冲突区域可以有多个;删除标记符号并确认正确的代码版本即可解决冲突。许多 IDE(VS Code、IntelliJ)提供"接受当前/接受传入/两者都保留"的可视化冲突解决按钮。
>
> **5-B** `--graph` 在左侧绘制 ASCII 分支线,`--oneline` 每提交一行。**举一反三:**`git log --graph --oneline --all --decorate` 是查看仓库全貌的最佳命令组合。可以在 `.gitconfig` 中设置为别名:`git lg`。
>
> **6-B** `--no-ff`(no fast-forward)强制创建一个 merge commit,即使原本可以 fast-forward 快进。**举一反三:**`--no-ff` 的好处:保留"feature 分支存在过"的历史痕迹,方便追溯"这些提交是为了 login 功能"。关于 ff vs no-ff 的偏好因团队而异,没有绝对的对错。
>
> **7-B** 反向合并(将 main 的更新合并到 feature)是常见的同步操作,保证 feature 分支包含 main 的最新更改后再继续开发。**举一反三:**也可以用 `git rebase main`(在 feature 上)实现同步,rebase 会让历史更线性但会重写提交 ID。
>
> **8-B** 冲突标记告诉你是谁和谁在冲突(`HEAD`=当前分支,`feature`=被合入的分支),但 Git **不会**自动决定保留哪个——必须由你手动编辑文件、删除标记符号、确定最终内容,然后 `git add` 标记为已解决。**举一反三:**冲突不是 Bug,而是正常现象——当两个分支修改了同一文件的同一行时,Git 无法自动判定谁是对的,把决定权交给人。
>
> **9-B** `-d`(小写)安全删除:如分支的修改未合并到当前分支或上游,会拒绝删除并提示。`-D`(大写)强制删除:不检查,直接删。**举一反三:**`-D` 删除的是分支指针,不是提交对象(提交仍在 reflog 的 30 天内可恢复)。但养成习惯:不确定时用 `-d`。
>
> **10-B** Feature Branch Workflow 是业界标准:每个功能/修复一个分支,独立开发,完成后合并。**举一反三:**这是 Git Flow、GitHub Flow 的基础。分支命名建议:`feature/xxx`、`bugfix/xxx`、`hotfix/xxx`。
>
> **Q1** Git 分支是"指向某个提交的指针/标签"。**比喻:**时间线是主宇宙(main 分支),每个分支是平行宇宙——你可以开一条"如果加个登录功能会怎样"的平行线,在里面随便折腾;实验成功就合并回主宇宙(merge),失败就抛弃这条线(delete),主宇宙毫发无伤。**用途:**①并行开发:多人同时做不同功能 ②风险隔离:在分支上试验,不破坏稳定代码 ③版本管理:release 分支做发布,hotfix 分支修补紧急 bug。
>
> **Q2** Fast-forward:main 在创建 feature 后没有新提交,合并只是让 main 指针"快进"到 feature 的位置,不产生新的合并提交。**真合并:**双方都有独立的新提交,合并时 Git 创建一个新的 merge commit 作为"汇合点",有两个 parent(来自双方的最近提交)。**为什么选 `--no-ff`:**强制创建 merge commit 可以保留"这个功能是作为整体被合并的"历史记录,方便追溯和回滚(比如 `git revert -m 1 <merge-commit>`)。缺点:提交历史更"胖"。**选择:**团队决策,没有绝对对错。
>
> **Q3** 操作序列:`git switch main` → `git switch -c fix-login-bug`(创建并切换到 fix 分支) → 修改代码修复 bug → `git add .` → `git commit -m "修复登录密码验证空字符串 bug"` → `git switch main` → `git merge fix-login-bug` → `git branch -d fix-login-bug`(清理已合并的分支)。**举一反三:**合并前先 `git pull origin main` 确保本地 main 是最新的。
>
> **Q4** 完整流程:①冲突出现时 `git status` 查看哪些文件冲突(标记为 `both modified`) ②打开冲突文件,搜索 `<<<<<<<` 定位冲突区域 ③手动编辑:删除标记符号,确认正确的代码内容(可能保留一方的、或合并两方、或重写) ④解决所有冲突后,`git add <resolved-file>`(对每个已解决文件标记) ⑤所有文件解决后 `git status` 确认无未解决冲突 ⑥`git commit`(不指定 -m,让 Git 使用默认合并信息;或 `git commit -m "合并 main 到 feature"`)。**举一反三:**如果冲突太复杂想放弃合并:`git merge --abort` 回到合并前的状态。使用 `git mergetool` 可调用可视化合并工具。
>
> **Q5** 分支策略:①主分支:`main`(生产就绪代码,只通过 PR/merge 进入) ②功能分支:`feature/login`(菜菜)、`feature/payment`(豆豆) ③修复分支:`bugfix/order-timeout`(阿零) ④合并顺序:各人 feature→自测→git pull origin main(同步最新)→解决冲突→push→创建 PR→code review→merge 到 main ⑤冲突处理:先 pull 最新 main,在本地 feature 分支上解决冲突,测试通过后再 push。**命名规则:**`feature/功能描述`、`bugfix/问题简述`、`hotfix/紧急修复描述`。**举一反三:**这就是简化版的 GitHub Flow,适合小型团队。大型项目可能需要 Git Flow(main + develop + feature + release + hotfix)。

## 运行前边界、回滚与验证

- **运行前**：示例以 GNU/Linux 的 Bash 为主；先用 `command --help`、`man command` 或发行版文档确认本机版本和参数。不要把教程中的 IP、域名、用户、路径直接复制到生产机器。
- **先确认作用域**：涉及文件、仓库、容器或远端主机时，先运行 `pwd`、`whoami`、`git status`、`docker context show` 或 `ssh -G 主机别名`，确认当前目标；对重要数据先做可恢复备份。
- **完成后验证**：用只读命令确认结果，例如 `ls -la`、`git status`、`systemctl status 服务名`、`docker ps` 或 `curl -fS URL`；失败时停止扩大操作范围，先读报错。
- **Git 回滚边界**：`reset --hard`、rebase 和强推会改写本地或共享历史。先保存 `git status`/`git log --oneline`，共享分支优先 `git revert`；必须强推时使用 `--force-with-lease` 并与协作者确认。
