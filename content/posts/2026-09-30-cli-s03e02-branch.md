# 《从零开始玩命令行》12 · 平行时间线:branch 与 merge

> 连载特刊 · 第二部《从零开始玩命令行》第 3 卷「Git 时间机」第 2 话
> 长期项目:**把豆豆咖啡站部署上真实服务器**。承接上一话:咖啡站进了 Git,但所有存档挤在一条 main 上,不敢做实验。全卷地图见 [/cli](/cli)。

---

## 一、需求:想做实验,又怕炸了主线

阿零要给咖啡站加"会员折扣",这功能一时半会调不好。他不敢直接在 `main` 上改——万一改到一半豆豆要上线,拿到的就是个半成品。他问守卫:「能不能另开一条时间线,在那边随便折腾,成了再合回来?」

守卫:「这正是 `branch` 的用处。**分支是平行时间线**——你在支线炸得再惨,主线毫发无伤;调好了,`merge` 一句汇回主线。」

---

## 二、漫画 · 岔开的沙流

> **〔1〕** 守卫的沙漏一晃,单股沙流"啵"地裂成两条并行的光带。
> 守卫:「上面这条是 `main`,你的正式时间线。下面这条,归你实验。」

> **〔2〕** 阿零 `git switch -c feature/discount`,身影一分为二,一个站主线、一个跳上支线。
> 特米:「`-c` = create + switch,开一条新分支并跳过去。你现在站在支线上,改什么都不惊动 main。」

> **〔3〕** 阿零在支线把拿铁改成会员价 16,提交。守卫钉下一颗只属于支线的钉子。
> 阿零:「主线那边还是 20?」守卫:「一字没动。两条时间线,各活各的。」

> **〔4〕** 剧情突变:豆豆在主线上也把拿铁**涨到 22**(旺季调价),提交。两条时间线都动了`同一行`。
> 特米(眯眼):「要出事了——待会儿合并,Git 会发现两边对同一行给了**不同答案**。」

> **〔5〕** 阿零回主线 `git merge feature/discount`,屏幕炸出红字 `CONFLICT`。他一慌:「Git 坏了?!」
> 守卫:「没坏。它诚实地说:**这一行我不敢替你做主**——16 还是 22,你定。」

> **〔6〕** 阿零打开文件,看见 `<<<<<<<` `=======` `>>>>>>>` 三道分割线,把两个版本并排摆着。
> 特米:「这不是乱码,是 Git 给你的**选择题**。删掉标记、留下你要的那版,再 `add`+`commit`,冲突就化解了。」

---

## 三、本话目标

- `git branch` / `git switch` 开分支、切分支,`switch -c` 一步到位;
- 理解分支的本质:**一个指向某个提交的可移动指针**,不是"文件的副本";
- `git merge` 汇流,看懂 fast-forward 与"真合并提交"的区别;
- 读懂冲突标记 `<<<<<<< ======= >>>>>>>`,手动解决冲突;
- 踩一次两边改同一行的冲突,并用 `git log --graph` 验证合并形状。

---

## 四、原理图:分支只是一个指针

```text
分支 = 一个贴在某次提交上的可移动标签,切换几乎零成本

      feature/discount
             │
             ▼
初始 ●────────● (会员价 16)
      \
       ●  (涨价 22)
       ▲
       │
      main   ← 你现在站这里(HEAD 指向 main)

merge 的两种结局:
  fast-forward:main 没动过,直接把标签快进到支线尖端(不产生新提交)
  真合并      :两边都动过 → 生成一个"合并提交",有两个父亲,
               若动了同一行 → 冲突,需你手动裁决
```

一句心法:**分支切换改的只是 HEAD 这个指针指向谁**,所以开一百条分支也不占多少空间——它不是复制文件,是贴标签。

## 五、上手:开支线、做实验、汇回主线

```bash
$ git switch -c feature/discount     # 开"会员折扣"支线并跳过去
Switched to a new branch 'feature/discount'

# 在支线把拿铁改成会员价 16,提交
$ printf '拿铁 = 16\n美式 = 18\n' > menu.txt
$ git commit -am "feat: 拿铁会员价 16"

$ git switch main                    # 回主线
Switched to branch 'main'
```

> **特米旁白**:`git commit -am` 里的 `-a` 会自动把**已跟踪文件**的改动一起 `add`(新建的未跟踪文件不管用,那种还得手动 `git add`)。省一步,但别养成不看 `status` 就 `-am` 的习惯。

这时豆豆在主线上把拿铁涨到了 22(旺季调价):

```bash
$ printf '拿铁 = 22\n美式 = 18\n' > menu.txt
$ git commit -am "feat: 拿铁涨价 22"
```

现在两条时间线都改了拿铁那一行。合并:

```bash
$ git merge feature/discount
Auto-merging menu.txt
CONFLICT (content): Merge conflict in menu.txt
Automatic merge failed; fix conflicts and then commit the result.
```

第一次冲突,如约而至。注意 `Auto-merging`——Git **先尽力自动合并**,只有它拿不准的行才丢给你。

## 六、故意制造一个 Bug:冲突了却硬 commit

阿零被红字吓到,想绕过去,直接 `git commit`,结果什么也提交不了;他又想"是不是没 add",于是 `git add` 后再 commit——**把带 `<<<<<<<` 标记的半成品文件提交了进去**。这是新手最常见的两种翻车。先看正确姿势:冲突态下 `git status` 会明确告诉你该干嘛。

---

## 七、读懂现象:冲突标记是一道选择题

```bash
$ git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   menu.txt
```

`both modified` = 两边都改了这文件。打开它:

```text
<<<<<<< HEAD
拿铁 = 22
=======
拿铁 = 16
>>>>>>> feature/discount
美式 = 18
```

三道线的读法,记死它:

- `<<<<<<< HEAD` 到 `=======`:**当前分支(main)** 的版本 → 拿铁 22;
- `=======` 到 `>>>>>>> feature/discount`:**被合并进来那条分支** 的版本 → 拿铁 16;
- `美式 = 18` 没被包起来:两边一致,Git 已自动合好,不用管。

解决 = **把三道标记全删掉,只留你要的最终内容**。假设决定用会员价 16:

```bash
# 手动编辑 menu.txt,改成最终想要的样子:
#   拿铁 = 16
#   美式 = 18
$ git add menu.txt               # 用 add 告诉 Git"这行我裁决完了"
$ git status
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)
Changes to be committed:
	modified:   menu.txt

$ git commit --no-edit           # 收尾,生成合并提交(--no-edit 用默认信息)
[main cdd145b] Merge branch 'feature/discount'
```

> **豆豆锐评**:冲突不是 Git 出 bug,是它**拒绝替你瞎猜**——两个人对同一行给了不同答案,只有你知道该听谁的。真慌了就 `git merge --abort`,一键回到合并前,重新来过,零损失。

## 八、用命令验证:合并的形状对不对

```bash
$ git log --oneline --graph
*   cdd145b Merge branch 'feature/discount'
|\
| * 40295f7 feat: 拿铁会员价 16
* | 7cbdf87 feat: 拿铁涨价 22
|/
* 6aceab4 feat: 初始菜单

$ git branch                     # 支线还在,合完可删
* main
  feature/discount
$ git branch -d feature/discount # 合并过的分支,-d 安全删除
```

`git log --graph` 里那个 `|\ ... |/` 菱形,就是"两条时间线分叉又汇合"的真实形状——一眼看出这里发生过一次合并。

> **🪟 双系统对照 · 冲突处理跨系统一致**

| 环节 | Git Bash | PowerShell 7 | 备注 |
|---|---|---|---|
| 开/切分支 | `git switch -c x` | `git switch -c x` | **完全一样** |
| 冲突标记长相 | `<<<<<<< ======= >>>>>>>` | 同左 | 是文件内容,与系统无关 |
| 编辑冲突文件 | `vim` / `nano` | VS Code、记事本均可 | 用什么编辑器随意,删掉三道线即可 |
| 中止合并 | `git merge --abort` | `git merge --abort` | 一致 |

冲突解决是纯 git + 编辑文本,**两系统零差异**。唯一要留神的是换行符——那是下一卷 rebase 那话的坑,这里先不碰。

> **🎯 面试直击**:`git switch`、`git checkout`、`git branch` 都能碰分支,有啥区别?
> `git branch` 只**管理**分支(列出/新建/删除),自己不切换;`git switch` 是新版**专职切分支**的命令(`-c` 新建并切);`git checkout` 是老命令,又能切分支又能恢复文件,职责太杂容易误伤,所以 Git 2.23 后拆成了 `switch`(切分支)+ `restore`(恢复文件)。追问点:fast-forward merge 和普通 merge 的区别——前者目标分支没有新提交,直接快进指针、不产生合并提交;后者两边都有新提交,才生成有两个父亲的合并提交。
