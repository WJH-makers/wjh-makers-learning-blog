## 一、事故:半夜那台机器重启了

凌晨三点,阿零被电话吵醒:咖啡站全站 502。他 SSH 上服务器一看——那台跑着所有容器的机器,被云厂商**计划内维护重启**了。`docker compose up` 手动敲回来,已经黑了十七分钟。

豆豆隔着屏幕吐槽:「你把六个微服务、Redis、MQ **全塞进一台机器**,这不叫分布式,这叫『把鸡蛋换了个更花哨的篮子』。今天我们把镜像交给一支**舰队指挥官**——它盯着你要的状态,谁掉队它自己补,机器没了它换一台重开。它叫 **Kubernetes**。」

本话只干一件事:让咖啡站的订单服务,**在集群里跑 3 个实例、挂了自动拉起、一条命令就能扩容**。

## 二、漫画 · 舰队指挥官上任

> **〔1〕** docker-compose 的老巢:一座孤岛,六个集装箱摞在一起,底下就一台发电机。发电机"啪"地熄火,整座岛陷入黑暗。
> 阿零(举着手电筒):「就……全没了?我一个个手动搬回来?」

> **〔2〕** 天上降下一艘航母,舰桥上站着 **K8s 调度官**,手里攥着一张纸条:`replicas: 3`。
> K8s 调度官:「我不关心『你现在有几个』,我只认『你**想要**几个』。你写下 3,我就永远保证甲板上有 3 架在飞。少一架,我立刻补。」

> **〔3〕** 三个一模一样的 **Pod**(每个舱里裹着咖啡站的订单容器)在甲板上排开。一个 Pod 突然冒烟坠海——调度官眼皮都没抬,手一挥,一个崭新的 Pod 补上空位。
> 阿零:「它……它自己长回来了?!」豆豆:「这叫**自愈**。你声明期望,它负责兜底。」

> **〔4〕** 阿零想直接把订单打给某个 Pod,却发现 Pod 的 IP 一重启就变。
> K8s 调度官:「别记它们的脸,它们随时会换。记这块**不变的门牌**——`Service`。你敲门牌,我负责把请求分给活着的那几个。」

> **〔5〕** 早高峰流量猛涨,阿零手忙脚乱。豆豆(叼着豆子叉腰)敲下一行 `kubectl scale --replicas=6`,甲板上"唰"地又起飞三架。
> 豆豆:「从 3 到 6,一行命令,八秒钟。这就是你昨晚缺的东西。」

## 四、原理图:声明式的三层

Docker 时代你说的是「**跑起来这个容器**」(命令式);K8s 时代你说的是「**我要长这样**」(声明式),剩下的它自己维持。

```text
                 你写下 YAML(期望状态)
                        │  kubectl apply
                        ▼
        ┌──────────── Kubernetes 控制面 ────────────┐
        │  控制器不停对比:期望 3 个 vs 实际几个?     │
        │  少了就创建,多了就删除 —— reconcile 循环   │
        └───────────────────────────────────────────┘
                        │ 维持
   ┌────────────────────┼────────────────────┐
   ▼                    ▼                    ▼
 Deployment ──管理──▶ ReplicaSet ──管理──▶ Pod × 3
                                          (每个 Pod 裹着订单容器)
                        ▲
                        │  按标签 app=coffee-order 选中
                 Service(不变的门牌 + 负载均衡)
                        ▲
                    顾客请求
```

三个必须分清的概念:

- **Pod**:最小调度单位,里面裹着一个(或一组紧密协作的)容器。**Pod 是「牲口不是宠物」**——随时可被销毁重建,IP 会变,别去记它。
- **Deployment**:声明「我要几个副本、用哪个镜像」。它通过 ReplicaSet 保证副本数,还负责滚动升级(第 5 话灰度会用到)。
- **Service**:给一组 Pod 一个**稳定的虚拟 IP + DNS 名**,按标签把它们兜在一起,自动负载均衡。Pod 换了,门牌不变。

## 五、代码:把订单服务交给 Deployment

第六季已经把订单服务打成了镜像 `coffee-order:v6`。现在不改一行 Java,只写一份**部署清单** `order-deploy.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: coffee-order
spec:
  replicas: 3                      # ← 期望 3 个实例,K8s 负责维持
  selector:
    matchLabels:
      app: coffee-order            # Deployment 靠这个标签认领自己的 Pod
  template:
    metadata:
      labels:
        app: coffee-order          # Pod 身上贴的标签
    spec:
      containers:
        - name: order
          image: coffee-order:v6
          ports:
            - containerPort: 8080
          readinessProbe:          # 就绪探针:没通过前,Service 不给它导流量
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 10
          livenessProbe:           # 存活探针:探测失败,K8s 重启这个容器
            httpGet:
              path: /actuator/health/liveness
              port: 8080
```

这里用到第五季就配好的 Spring Boot Actuator——它天生暴露 `/actuator/health/readiness` 和 `/liveness` 两个端点,正好喂给 K8s 的探针。**探针是 K8s 判断「这个 Java 进程到底活没活、能不能接客」的唯一依据**,不配的话 K8s 只能看容器进程在不在,进程没死但接口卡死它是不知道的。

再来一份 `order-svc.yaml` 给它们一块不变的门牌:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: coffee-order-svc
spec:
  selector:
    app: coffee-order              # ← 门牌靠这个标签,把请求分给匹配的 Pod
  ports:
    - port: 80                     # Service 对外的端口
      targetPort: 8080             # 转发到 Pod 容器的端口
```

一键部署并观察:

```bash
kubectl apply -f order-deploy.yaml -f order-svc.yaml
kubectl rollout status deployment/coffee-order
```

```text
deployment "coffee-order" successfully rolled out
```

```bash
kubectl get pods -l app=coffee-order
```

```text
NAME                            READY   STATUS    RESTARTS   AGE
coffee-order-7d9c5b8f4d-4hx2p   1/1     Running   0          38s
coffee-order-7d9c5b8f4d-9wq7z   1/1     Running   0          38s
coffee-order-7d9c5b8f4d-tk5vn   1/1     Running   0          38s
```

三架都上天了。**验证自愈**——手动删掉一个 Pod,看它自己长回来:

```bash
kubectl delete pod coffee-order-7d9c5b8f4d-4hx2p
kubectl get pods -l app=coffee-order
```

```text
NAME                            READY   STATUS              RESTARTS   AGE
coffee-order-7d9c5b8f4d-9wq7z   1/1     Running             0          2m
coffee-order-7d9c5b8f4d-tk5vn   1/1     Running             0          2m
coffee-order-7d9c5b8f4d-x6rpc   0/1     ContainerCreating   0          2s   ← 新的自己补上了
```

阿零昨晚手动干了十七分钟的活,K8s 两秒钟自动做完了。

## 七、读懂现象:Pod 明明活着,门后却没人

Pod 全 `Running`,日志干干净净,可请求就是进不去。豆豆的五步排障法上场——**Service 和 Pod 之间靠标签牵线,那就去看这根线断没断**:

```bash
kubectl get endpoints coffee-order-svc
```

```text
NAME               ENDPOINTS   AGE
coffee-order-svc   <none>      1m
```

`ENDPOINTS` 是 `<none>`——**门牌后面一个 Pod 都没挂上**。Service 拿着 `app=coffee-oder` 这个标签满集群找,没找到任何匹配的 Pod(它们贴的是 `coffee-order`),于是把请求转发给了「空气」,前端只能超时。

这是 K8s 头号高频坑:**Pod 健康 ≠ Service 通**。中间隔着一层「标签选择器」,一个字母不匹配,流量就凭空蒸发,而且**两边都不报错**。改回 `app: coffee-order` 重新 apply:

```bash
kubectl get endpoints coffee-order-svc
```

```text
NAME               ENDPOINTS                                        AGE
coffee-order-svc   10.244.1.7:8080,10.244.1.8:8080,10.244.2.4:8080  3m
```

三个 Pod IP 全挂上来了,流量恢复。

> **豆豆锐评 · 出了问题,顺着「期望 vs 实际」往下看**
> K8s 排障有个万能起手式:`kubectl get`(看状态)→ `kubectl describe`(看事件 Events)→ `kubectl logs`(看容器日志)。这次卡在 Service 层,`get endpoints` 一眼看穿;如果是 Pod 起不来,`describe pod` 底部的 `Events` 会明说是拉镜像失败还是探针不过。**别一上来就重启,先问它「你现在到底是什么状态」。**

> **🎯 面试直击**:Kubernetes 是怎么实现「自愈」和「扩容」的?
> 核心是**控制器的调谐循环(reconcile loop)**:你在 etcd 里存了「期望状态」(replicas=3),控制器不停地拿**期望**和**实际**做差——少了就创建 Pod,多了就删,Pod 所在节点没了就在别处重建。所以自愈和扩容本质是**同一件事**:改变期望值(删 Pod=实际变少、`scale`=期望变大),控制器负责把实际拉回期望。追问点:它是**声明式**而非命令式——你描述目标,不描述步骤,这也是它和 `docker run` 最根本的区别。

## 八、扩缩容 + 冒烟测试:证明门后真有人

早高峰来了,一条命令从 3 扩到 6:

```bash
kubectl scale deployment/coffee-order --replicas=6
```

```text
deployment.apps/coffee-order scaled
```

光看 Pod 数不够,得证明**通过 Service 真能下单**。用第四季学的 `HttpClient` 写个冒烟测试,打到 Service 暴露的地址(本地用 `kubectl port-forward svc/coffee-order-svc 8080:80` 转出来):

```java
@Test
void service_routes_to_a_live_pod() throws Exception {
    var client = java.net.http.HttpClient.newHttpClient();
    var req = java.net.http.HttpRequest.newBuilder()
        .uri(java.net.URI.create("http://localhost:8080/actuator/health"))
        .GET().build();
    var resp = client.send(req, java.net.http.HttpResponse.BodyHandlers.ofString());

    assertEquals(200, resp.statusCode());          // 门牌后面确实有人应答
    assertTrue(resp.body().contains("\"status\":\"UP\""));
}
```

绿了——不管请求落到 6 个 Pod 中的哪一个,Service 都能把它导到一个**健康**的实例上。这正是探针的价值:没通过 readiness 的 Pod,Service 根本不会把它挂进 endpoints。

### 一、选择题（10 道）

**1.** Kubernetes 中最小调度单位是什么？
- A) Container　B) Pod　C) Deployment　D) Service

**2.** Deployment 通过哪个组件保证 Pod 副本数始终等于期望值？
- A) Service　B) ConfigMap　C) ReplicaSet　D) Ingress

**3.** Service 在 K8s 中的核心作用是什么？
- A) 存储敏感配置　B) 管理 Pod 生命周期　C) 提供稳定的虚拟 IP 和负载均衡　D) 限制容器资源使用

**4.** ConfigMap 在 K8s 中的正确用途是？
- A) 存储数据库密码等敏感信息　B) 挂载为容器内的配置文件或环境变量　C) 替代 Service 做服务发现　D) 管理 Pod 的自动扩缩容

**5.** Ingress 在 K8s 中的主要功能是？
- A) 集群内部服务发现　B) 管理外部 HTTP/HTTPS 流量的路由规则　C) 自动扩缩 Pod 数量　D) 存储容器镜像

**6.** 查看所有命名空间中所有 Pod 的正确 kubectl 命令是？
- A) `kubectl get pods`　B) `kubectl get pods --all`　C) `kubectl get pods -A`　D) `kubectl describe pods`

**7.** HPA（Horizontal Pod Autoscaler）根据什么指标自动调整 Pod 副本数？
- A) 仅根据内存使用量　B) 仅根据集群节点数　C) 根据 CPU/内存等资源指标或自定义指标　D) 根据代码提交次数

**8.** `kubectl apply` 与 `kubectl create` 的核心区别是？
- A) 两者功能完全相同　B) apply 是声明式（增量+幂等），create 是命令式（重复执行会报错）　C) apply 只能用于 Deployment　D) create 比 apply 快

**9.** 手动 `kubectl delete pod` 后系统自动重建了一个新 Pod，这体现了 K8s 的什么能力？
- A) 负载均衡　B) 滚动更新　C) 自愈（控制器调谐循环）　D) 服务发现

**10.** Service 的 `selector` 中标签写错一个字母，会发生什么？
- A) `kubectl apply` 报错　B) Pod 启动失败　C) Service 创建成功但流量到不了任何 Pod（ENDPOINTS 为空）　D) K8s 自动纠正标签

> [!答案]
> **1-B**　Pod 是 K8s 最小调度和部署单元，可包含一个或多个紧密协作的容器。Deployment 管理 Pod 副本数，Service 提供网络发现。　举一反三：一个 Pod 内容器共享网络命名空间（localhost 互通）和存储卷，适合放 Sidecar（日志采集、代理等）。
> 
> **2-C**　Deployment 内部创建并管理 ReplicaSet，ReplicaSet 持续监控实际与期望副本数的差值，少则创建、多则删除。　举一反三：直接删 ReplicaSet 的 Pod 不影响 Deployment——ReplicaSet 立即重建；但用 `kubectl scale` 改 Deployment 的 replicas，ReplicaSet 才跟着调。
> 
> **3-C**　Pod IP 随重建改变，Service 通过标签选择器将一组 Pod 聚合并提供不变的 ClusterIP + DNS 名，自动负载均衡到健康 Pod。　举一反三：Service 有 ClusterIP、NodePort、LoadBalancer 三种类型——集群内通信用 ClusterIP 就够了，暴露外部才需后两者。
> 
> **4-B**　ConfigMap 用于存储非敏感配置（如 application.yml），可挂载为文件或注入为环境变量。敏感信息（密码、Token）应使用 Secret。　举一反三：ConfigMap 更新后挂载为文件的 Pod 约 60s 延迟自动同步；注入为环境变量则需重启 Pod 才生效。
> 
> **5-B**　Ingress 是七层负载均衡器，定义域名、路径等路由规则，将外部请求转发到集群内 Service。实际流量处理依赖 Ingress Controller（如 Nginx Ingress）。　举一反三：Ingress 只是规则定义——不同 Controller 支持的注解不同（如 `canary` 灰度注解）。
> 
> **6-C**　`kubectl get pods -A`（`--all-namespaces`）列出全部命名空间 Pod。不加 `-A` 只看当前 namespace。　举一反三：日常排障三部曲：`kubectl get`（看状态）→ `kubectl describe`（看 Events）→ `kubectl logs`（看日志）。
> 
> **7-C**　HPA 根据 Metrics Server 的 CPU/内存利用率或 Prometheus 等外部自定义指标，自动调整 replicas。如 CPU 超 80% 就扩容。　举一反三：HPA + Cluster Autoscaler 双层自动扩缩——HPA 加 Pod、节点不够时 CA 自动加节点。
> 
> **8-B**　`apply` 声明式——资源不存在则创建、已存在增量更新，可重复执行；`create` 命令式创建，重复执行报 `AlreadyExists`。日常运维建议用 `apply`。　举一反三：`apply` 增量更新依赖 last-applied-configuration 注解（K8s 自动维护），对比差异只更新变化部分。
> 
> **9-C**　Deployment 的 ReplicaSet 持续对比期望（replicas=3）与实际差值，发现减少立即创建新 Pod 补上——这叫 reconcile loop（调谐循环），是 K8s 自愈能力核心。　举一反三：新 Pod IP 与旧不同——因此不能依赖 Pod IP，必须通过 Service 访问，这也是 Service 存在的根本原因。
> 
> **10-C**　YAML 语法没错 apply 照常成功，但 Service 拿错误标签匹配不到 Pod，ENDPOINTS 显示 `<none>`，流量凭空蒸发。　举一反三：排障口诀：`kubectl get endpoints <svc-name>` 看门后有没有人——ENDPOINTS 为空说明标签选择器没匹配到 Pod。

### 二、解答题（3 道）

**11.** 用自己的话解释 Deployment 和 Service 的分工——它们各自解决什么问题，为什么需要两者配合？

**12.** HPA 的工作流程是怎样的？它和手动 `kubectl scale` 的本质区别在哪里？

**13.** Kubernetes 的「声明式 API」与传统运维脚本的「命令式」思想有什么根本不同？这对可靠性有何影响？

> [!答案]
> **11**　Deployment 解决「运行什么、多少个」——声明镜像、副本数、资源限制、更新策略，通过 ReplicaSet 维持 Pod 数量，负责应用生命周期管理。Service 解决「怎么找到它们」——提供稳定的 ClusterIP + DNS 名，负载均衡到健康 Pod，负责网络发现与流量分发。配合原因：Pod IP 不固定（扩缩、重启都会变），Service 用标签选择器动态绑定，屏蔽了 Pod 的短暂性。　举一反三：两者完全解耦——可单独创建，但生产总是配合使用，且 selector 必须一致，这是 K8s 排障最高频检查点。
> 
> **12**　HPA 每隔 15s 通过 Metrics Server 获取 Pod 资源利用率，计算期望副本数（`ceil(当前 × 当前利用率 / 目标利用率)`），自动调整 replicas。与手动 scale 本质区别：HPA 是自动的、基于规则的、动态的——高峰自动扩、低谷自动缩，无需人工介入；手动 scale 是一次性的、凭经验的。　举一反三：HPA 缩容有冷却期（默认 5 分钟）防止频繁扩缩（flapping）。生产中常同时配 HPA 和 PodDisruptionBudget 保证最少可用副本数。
> 
> **13**　声明式：告诉 K8s「我期望的状态」（YAML 中 replicas: 3），K8s 持续对比期望与实际，自动执行差异动作。命令式：你写步骤（拉镜像→起容器→配网络），执行到哪算哪，中间断了就停。根本区别：声明式把「维护状态」的责任从人转移给系统——控制器不停做 reconcile loop，即使节点宕机也能在其他节点补上 Pod；声明式天然幂等（重复 apply 不会出错），系统能自动从偏离中恢复；命令式脚本脆弱（执行一半宕机状态不可知）。　举一反三：这也是 K8s 和 docker-compose 的根本差异——compose 命令式，不监控运行中是否偏离预期；K8s 控制器一直在后台盯着。

### 三、代码题（2 道）

**14.** 写一份完整的 K8s YAML，包含：(1) Deployment：部署 `coffee-shop:v2` 镜像，3 副本，端口 8080，配置 readinessProbe 和 livenessProbe；(2) Service：ClusterIP 类型，端口 80 转发到 8080；(3) HPA：CPU 目标 70%，最小 3 副本、最大 10 副本。

**15.** 你的 Pod 全部 `Running`，但通过 Service 访问返回超时。写出从现象到定位的一条完整排障命令链（至少 4 步），并解释每步目的。

> [!答案]
> **14 验收**　```yaml
> apiVersion: apps/v1
> kind: Deployment
> metadata:
>   name: coffee-shop
> spec:
>   replicas: 3
>   selector:
>     matchLabels: { app: coffee-shop }
>   template:
>     metadata:
>       labels: { app: coffee-shop }
>     spec:
>       containers:
>         - name: coffee
>           image: coffee-shop:v2
>           ports: [{ containerPort: 8080 }]
>           readinessProbe:
>             httpGet: { path: /actuator/health/readiness, port: 8080 }
>             initialDelaySeconds: 15
>           livenessProbe:
>             httpGet: { path: /actuator/health/liveness, port: 8080 }
>             initialDelaySeconds: 30
>           resources:
>             requests: { cpu: "200m", memory: "256Mi" }
>             limits: { cpu: "500m", memory: "512Mi" }
> ---
> apiVersion: v1
> kind: Service
> metadata:
>   name: coffee-shop-svc
> spec:
>   selector: { app: coffee-shop }
>   ports: [{ port: 80, targetPort: 8080 }]
> ---
> apiVersion: autoscaling/v2
> kind: HorizontalPodAutoscaler
> metadata:
>   name: coffee-shop-hpa
> spec:
>   scaleTargetRef:
>     apiVersion: apps/v1
>     kind: Deployment
>     name: coffee-shop
>   minReplicas: 3
>   maxReplicas: 10
>   metrics:
>     - type: Resource
>       resource:
>         name: cpu
>         target: { type: Utilization, averageUtilization: 70 }
> ```　举一反三：HPA 的 CPU 目标需 Pod 的 `resources.requests.cpu` 有值才能计算利用率；livenessProbe 失败会重启容器，readinessProbe 失败只从 Service 摘掉——混淆两者可能导致服务反复重启。
> 
> **15 验收**　```bash
> # 1. 确认 Pod 是 Running
> kubectl get pods -l app=coffee-shop
> 
> # 2. 看 Service Endpoints——门后面挂没挂上 Pod IP（为空则标签没匹配）
> kubectl get endpoints coffee-shop-svc
> 
> # 3. 在 Pod 内 curl 验证端口是否真的在监听
> kubectl exec -it <pod-name> -- curl -s localhost:8080/actuator/health
> 
> # 4. port-forward 绕过 Service 直打 Pod，判断问题在 Service 层还是 Pod 层
> kubectl port-forward pod/<pod-name> 8081:8080
> curl http://localhost:8081/actuator/health
> # 若通→问题在 Service 层（标签/端口映射）；若不通→Pod 层
> ```　举一反三：排障黄金顺序——`get`（全貌）→ `describe`（Events）→ `logs`（内部）。不要一上来就重启，先问清楚「你到底什么状态」。
