## 三、本话目标

- 分清 Comparable(自然序)与 Comparator(外部序),用 `comparing/thenComparing/reversed` 组装规则;
- 用 TreeSet/TreeMap 维护恒有序排行榜,吃透 O(log n) 代价与 **compare==0 即判重**;
- 用 LinkedHashMap 的 `accessOrder` + `removeEldestEntry` 三行写出 LRU 热点榜;
- 用 Sequenced Collections(JDK 21)统一取首尾与倒序。

## 四、原理图:两把尺子与一棵树

```text
把「怎么比」告诉容器,只有两条路:
  Comparable<T>  自然序 —— 类自己实现 compareTo,写死在类里,一个类只有一种
                 (String、Integer、LocalDate 自带,所以 TreeSet<String> 裸奔也行)
  Comparator<T>  外部序 —— 尺子在类外,想要几把造几把,流水线组装:
                 comparing(主键) → thenComparing(平局补维) → reversed(翻转)

TreeSet / TreeMap(同一棵红黑树;TreeSet 就是 TreeMap 的马甲:add = put(e, 占位符))
  · 增删查全是 O(log n) —— 「永远有序」的价签(HashMap O(1) 但无序)
  · 判重铁律:compare(a, b) == 0 ⇒ 视为同一个元素,与 equals 无关
  · TreeMap 键有序还能切片:headMap / tailMap / subMap(「30 杯以上的」一刀切出)

LinkedHashMap(哈希表 + 一条双向链表)
  · 默认记「插入序」;构造传 accessOrder=true 改记「访问序」——每 get 一次挪到队尾
  · 访问序 + removeEldestEntry ⇒ 三行手写 LRU 缓存
```

> **豆豆锐评**:选容器先问一句「要不要顺序、要哪种」:插入序 → LinkedHashMap,比较序 → TreeMap/TreeSet,不要序 → HashMap/HashSet。有序从来不免费,O(log n) 就是价签。

## 五、代码:排行榜与热点榜

叫号系统(上一话的 PriorityQueue)照常跑,本话在它旁边新立一个 `Leaderboard`。

**第一脚:没递尺子。**`record` 又没实现 Comparable,无参 TreeSet 默认赌你有自然序——第一杯进门就要 `compare(自己, 自己)` 验明正身,当场炸:

```java
record SalesEntry(String name, int cups) {}

var board = new TreeSet<SalesEntry>();   // 没递尺子
board.add(new SalesEntry("拿铁", 41));   // ← 第一杯就炸
```

**递上尺子(Comparator 外部序),排行榜上线:**

```java
import java.util.Comparator;
import java.util.TreeSet;

record SalesEntry(String name, int cups) {}

public class Leaderboard {
    // 尺子:按销量降序(暂时只有这一维——伏笔)
    static final Comparator<SalesEntry> BY_SALES =
            Comparator.comparingInt(SalesEntry::cups).reversed();

    public static void main(String[] args) {
        var board = new TreeSet<>(BY_SALES);
        board.add(new SalesEntry("拿铁", 41));
        board.add(new SalesEntry("美式", 27));
        board.add(new SalesEntry("燕麦拿铁", 33));

        System.out.println("销冠:" + board.getFirst().name());   // JDK 21 起,统一入口
        System.out.println("垫底:" + board.reversed().getFirst().name());  // 倒序视图,不复制
        for (var e : board) {                                     // 中序一走,就是榜单
            System.out.println(e.name() + " " + e.cups() + " 杯");
        }
    }
}
```

> **⏳ 版本时光机 · 「取首尾元素」怎么变的**

| JDK 版本 | 写法 | 关键变化 |
|---|---|---|
| Java 8 | 首:`set.iterator().next()` / `list.get(0)`;尾:`list.get(list.size() - 1)`,SortedSet 另有 `first()/last()`,Deque 又是 `peekFirst()` | 每种容器一套方言,取个尾巴要么绕要么先数长度 |
| Java 21 | `getFirst()` / `getLast()` / `reversed()`(JEP 431,Sequenced Collections) | List、Deque、LinkedHashSet、TreeSet 统一入口;`reversed()` 是视图,倒着看不复制 |

一句演进小结:从「每个容器背一套 API」到「有顺序的容器共用一套」。

**热点榜:三行 LRU。**老板还要「最近被点过的 3 款」。LinkedHashMap 构造第三参 `accessOrder=true` 开访问序,再覆写一个钩子:

```java
var hot = new LinkedHashMap<String, Integer>(16, 0.75f, true) {
    @Override protected boolean removeEldestEntry(Map.Entry<String, Integer> eldest) {
        return size() > 3;   // 第 4 款进门,最久没人点的出局
    }
};
hot.put("拿铁", 1); hot.put("美式", 1); hot.put("摩卡", 1);
hot.get("拿铁");                    // 拿铁被翻牌,挪到队尾最新位
hot.put("可可", 1);                 // 第 4 款 → 踢掉最久未访问的「美式」
System.out.println(hot.keySet());   // [摩卡, 拿铁, 可可]
```

## 七、观察现象:后来者凭空消失

```text
3
拿铁 41 杯
燕麦拿铁 33 杯
美式 27 杯
```

没有异常、没有日志,摩卡**无声蒸发**。真凶就是漫画〔4〕那个门卫:`BY_SALES` 只量销量,27 对 27 量出 **0**——TreeSet 判定「你就是美式」,保留旧的、丢掉新的,`add` 默默返回 `false`,而阿零根本没看返回值。**在排序容器里,相等由 compare 说了算,equals 说了不算**;比较维度不全 = 判重规则漏水。

> **🎯 面试直击**:Comparable 与 Comparator 什么区别?TreeSet 判重靠什么?
> Comparable 是自然序:类自己实现 `compareTo`,写死类里、一类一种;Comparator 是外部序:规则在类外,可造多把、可 `thenComparing` 组装。TreeSet 判重**只看 compare 是否为 0,与 equals/hashCode 无关**。追问点:同一批对象放 HashSet(看 hashCode+equals)和 TreeSet(看 compare),size 可能不同——不是 Bug,是两套判重规则。

## 八、修复,并用测试证明

给尺子补上第二维:平局再按名字比,谁也不吞谁。

```java
static final Comparator<SalesEntry> BY_SALES =
        Comparator.comparingInt(SalesEntry::cups).reversed()
                  .thenComparing(SalesEntry::name);   // 平局补维
```

> **豆豆旁白**:`thenComparing` 要接在 `reversed()` **之后**——主维降序、平局升序。写成 `comparing(...).thenComparing(...).reversed()` 是整串一起翻转,名字也跟着倒。另:String 自然序按字符码位,中文不是拼音序,「摩」码位就排在「美」前;真要拼音序得换 `Collator`,今天不展开。

JUnit 质检员:「证据呢?」

```java
import org.junit.jupiter.api.Test;
import java.util.TreeSet;
import static org.junit.jupiter.api.Assertions.assertEquals;

class LeaderboardTest {
    @Test
    void tied_sales_both_stay_on_board() {
        var board = new TreeSet<>(Leaderboard.BY_SALES);
        board.add(new SalesEntry("拿铁", 41));
        board.add(new SalesEntry("美式", 27));
        board.add(new SalesEntry("摩卡", 27));   // 同销量,一杯都不许吞

        assertEquals(3, board.size());
        assertEquals("拿铁", board.getFirst().name());
        assertEquals("美式", board.getLast().name());   // 同 27 杯按名字升序,「摩」在「美」前
    }
}
```

绿灯。排行榜四款齐全,黑板恢复诚实。

7. TreeSet 增删查的时间复杂度是?

8. `Comparator.comparingInt(SalesEntry::cups).reversed()` 的含义是?
   - A) 销量升序　B) 销量降序　C) 按名字排序　D) 先销量后名字
9. `.reversed().thenComparing(...)` 与 `.thenComparing(...).reversed()` 的区别?
   - A) 完全一样　B) 前者主维降序、平局补维升序;后者整串全反,平局也跟着降序　C) 语法错误　D) 取决于 JDK 版本
10. HashMap 和 TreeMap 的第一取舍标准是什么?
    - A) 都行　B) 要不要有序:不要序→HashMap,要序→TreeMap(代价是 O(log n))　C) TreeMap 更快　D) HashMap 更强

> [!答案]
> **1-B**　Comparable 是「我天生就知道怎么比」(String/Integer/LocalDate 都实现了),Comparator 是「我给你一把尺子,你按它比」——可以在外部随时换。**举一反三**:TreeSet 无参构造只用 Comparable,传 Comparator 就用外部尺子——两者不能同时缺,否则第一杯就 ClassCastException。
> **2-C**　TreeSet/TreeMap 底层判重只走 `compareTo` 或 `Comparator.compare`——compare 返回 0,就认定「有这个元素了」,不看 equals 也不看 hashCode。**举一反三**:这一点和 HashSet(HashMap 判重先看 hashCode 后比 equals)完全不同——同一批对象放 HashSet 和 TreeSet,size 可能不一样!
> **3-B**　add 内部走 `TreeMap.put`,compare 返回 0 就认为是已有 key,保留旧的、丢弃新的,add 返回 false(但不会抛异常)。**举一反三**:`Set.add` 的返回值是有用的——返回 false 说明这个元素没加进去(判重规则不认它);但多数人习惯忽略返回值,这是 Bug 的温床。
> **4-B**　thenComparing 是 Comparator 的「平局补维」方法:主维相等时用它做次级排序,同时也修复了判重漏水。**举一反三**:规则链越长判重越准,生产上任何按业务 ID 判重的 Comparator 都应该把 ID 作为最后一个维度,保证每个元素唯一。
> **5-B**　accessOrder=true 让每次 get 把它挪到队尾(最新访问),removeEldestEntry 返回 size()>3 时自动踢掉最久未访问的元素——正好三行代码实现一个简单的 LRU 缓存。**举一反三**:这是最简单版的 LRU——没有并发安全、没有过期时间;生产上的 Caffeine 缓存在此基础上加了时间窗口和并发优化,但核心思路就是「双向链表 + 哈希表」。
> **6-B**　JEP 431(JDK 21)定义了 SequencedCollection 接口,让 List/Deque/SortedSet/LinkedHashSet 的都共用 `getFirst/getLast/addFirst/addLast/reversed`——之前每种容器一套方言的历史终结。**举一反三**:面试被问到 JDK 21 新特性时,Sequenced Collections 是最好讲的一个——先画旧API的「碎片化」,再画新 API 的「统一」。
> **7-B**　TreeSet 底层是 TreeMap(红黑树),增删查都是 O(log n);有序但比 HashMap O(1) 慢。**举一反三**:O(log n) 这个代价换来的是全树有序——中序遍历一遍就是排序后的结果;所以 **TreeSet 是「插入时付 O(log n) 的排序费,遍历时不费吹灰之力」**。
> **8-B**　`comparingInt(cups)` 升序,`.reversed()` 翻转成降序。**举一反三**:链式写法的可读性远胜于手写 `(a,b) -> b.cups()-a.cups()`——后者不仅难读,还有整数溢出风险(大减负会产生正数)。
> **9-B**　`comparing().reversed().thenComparing()` = 主维降序然后平局升序; `comparing().thenComparing().reversed()` = 整串全翻转,平局也降序。**举一反三**:这是个容易踩的坑——读 Comparator 的链式调用要从左到右理解,reversed 只翻转它左边所有的规则,不影响右边的 thenComparing。
> **10-B**　HashMap 无序,O(1) 的快速查询;TreeMap 全程有序,O(log n) 的增删代价换取永远有序。**举一反三**:面试官问「用哪个」时先说「要不要顺序」——这是前进一步,再列出其他考量(要不要 null key,要不要线程安全,要不要 LRU)。

### 解答题(5 道)

1. 同一批对象放进 HashSet 和 TreeSet,得到的大小可能不同——为什么?举例说明。
2. 用 `Comparator.comparing(...).thenComparing(...).reversed()` 写一个「先按销量降序,同销量按名称升序」的排行榜排序规则。
3. 写出三行代码实现「最近被点过的 3 款饮品」的 LRU 缓存,解释 `accessOrder` 和 `removeEldestEntry` 各自的作用。
4. Comparable 和 Comparator 都在手,什么场景用 Comparable(自然序),什么场景用 Comparator(外部序)?
5. String 自然序按字符的 Unicode 码位排列,中文不按拼音——这对排行榜有什么影响?怎么解决?

> [!答案]
> **1**　假设 record Item(String name, int value),HashSet 判重看 hashCode+equals;TreeSet 判重看 compare 的返回值。如果 Comparator 只按 value 排序,同 value 不同 name 的两个对象在 TreeSet 里就只留下先加的那个,而 HashSet 里两个都在。**举一反三**:这就是「判重漏水」的完整原因——compare 维度不全,相等就不准;解决是用 thenComparing 把唯一标识符也纳入比较链。
> **2**　```java
Comparator<SalesEntry> BY_SALES = Comparator
    .comparingInt(SalesEntry::cups).reversed()
    .thenComparing(SalesEntry::name); // 只在主维平局时生效
```　**举一反三**:注意 `.thenComparing` 在 `.reversed()` 之后——这样名字维度仍是默认的升序;如果整串 reversed 全反,名字也降序,可能不是你要的。
> **3**　```java
var hot = new LinkedHashMap<String, Integer>(16, 0.75f, true) {
    protected boolean removeEldestEntry(Map.Entry<String, Integer> eldest) {
        return size() > 3;
    }
};
hot.put("拿铁", 1); hot.put("美式", 1); hot.put("摩卡", 1);
hot.get("拿铁"); // 拿铁被摸过一次,变成最新访问
hot.put("可可", 1); // 第4款,踢掉最久没人摸的「美式」
```　accessOrder=true 让每次 get 将元素挪到队尾;removeEldestEntry 在每次 put 后调用,返回 true 就踢掉最老元素。**举一反三**:LinkedHashMap 的 `eldest` 参数是有序链表的 head(最老),它就是被淘汰的候选;生产上更常用 Guava Cache 或 Caffeine——它们有 TTL(时间过期)和最大重量限制。
> **4**　Comparable: 类自身有唯一的、公认的排序规则时用(String 按字典序、Instant 按时间线)。Comparator: 同一批对象需要多种排序口径(按销量、按时间、先 VIP 后普通),或你控制不了类的源码时(给 String 按长度排序)。**举一反三**:`Comparator.comparing(...)` 链式 API 让大部分外部排序不用手写匿名类——这是函数式风格在集合领域的最大胜利。
> **5**　String 自然序按 UTF-16 码位,中文汉字码位顺序和拼音无关(「摩」在「美」前),排行榜看到的是码位序而不是拼音序。解决:用 `Collator.getInstance(Locale.CHINESE)` 创建按拼音排序的比较器。**举一反三**:Collator 是 ICU(International Components for Unicode)的轻量封装,支持中文按笔画、拼音等排序规则,但它性能不如码位比较——量小时直接用,量大时可以在外层先按码位排再精排。
