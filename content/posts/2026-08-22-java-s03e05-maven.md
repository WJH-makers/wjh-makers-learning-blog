## 一、需求:别再手工搬砖

咖啡站的代码涨到十几个类,阿零每次都手动 `javac *.java`,想跑测试还得上网下 JUnit 的 jar、手动塞进 classpath。换台电脑,整套依赖重下一遍。豆豆:「你缺的不是勤快,是一个**标准化车间**——声明你要什么,剩下的交给工具。」

这一话不写业务代码,而是给项目装上**构建系统**。它是"能运行"迈向"团队能协作、能持续交付"的分水岭。

## 三、本话目标

- 看懂 Maven **坐标**(groupId / artifactId / version)如何唯一定位一个依赖;
- 用一份 `pom.xml` 声明 JUnit 依赖,让 Maven 自动下载;
- 理解**生命周期**(compile → test → package)与目录约定;
- 理解依赖 **scope**,踩一次"scope 贴错"的坑;
- 用 `mvn test` 让上一话的测试自动跑起来。

## 四、原理图:坐标、目录、生命周期

```text
坐标(唯一定位一个 jar):
    groupId : artifactId : version
    org.junit.jupiter : junit-jupiter : 5.11.3

目录约定(Maven 认死理,放对位置就不用配):
    coffee-shop/
    ├── pom.xml
    └── src/
        ├── main/java/   ← 业务代码(CoffeeShop、MenuStore…)
        └── test/java/   ← 测试代码(…Test)

生命周期(后一步自动带跑前面所有步):
    validate → compile → test → package → verify → install → deploy
    `mvn test` 会先 compile;`mvn package` 会先 compile + test
```

## 五、配置:一份能用的 pom.xml

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             http://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>cafe.doudou</groupId>
    <artifactId>coffee-shop</artifactId>
    <version>1.0.0</version>

    <properties>
        <!-- 用 release 一次锁定源码/字节码/API 到 Java 25,比 source+target 更稳 -->
        <maven.compiler.release>25</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>5.11.3</version>
            <scope>test</scope>   <!-- ★ 只在测试期用,不打进成品 jar -->
        </dependency>
    </dependencies>
</project>
```

把上一话的 `CoffeeShop.java` 放进 `src/main/java/`,`CoffeeShopTest.java` 放进 `src/test/java/`,然后:

```bash
mvn compile     # 编译 src/main/java
mvn test        # 自动先编译,再跑 src/test/java 里的测试
mvn package     # 自动先 compile + test,全过了才打成 target/coffee-shop-1.0.0.jar
```

## 六、故意制造一个 Bug:scope 贴错

把 JUnit 的 `<scope>test</scope>` 删掉(等于默认 `compile`),再在**业务代码** `CoffeeShop.java` 里手滑写了句测试注解 `@Test`——因为 scope=compile,编译期它居然"看得见":

```java
// src/main/java/CoffeeShop.java  ← 业务代码里混进了测试 API
import org.junit.jupiter.api.Test;   // scope=test 时这里应当编译不过
```

## 七、读懂真实报错:主代码碰不到测试依赖

```text
[ERROR] .../src/main/java/CoffeeShop.java:[3,32] package org.junit.jupiter.api does not exist
```

`scope=test` 的依赖**只在 `src/test/java` 的编译期与运行期可见**,主代码 `src/main/java` 够不着它。这句报错正是 scope 在起保护作用:它把测试框架挡在成品之外。删掉 scope(变 compile)反而"能编译过"——但那意味着 JUnit 被打进了你的发布包,是**反模式**。

> **豆豆锐评 · scope 就是"这依赖在哪些阶段可见"**
> `compile`(默认,全程可见)、`test`(只测试期)、`provided`(编译期要、运行期由容器提供,如 Servlet API)、`runtime`(运行期才要,如 JDBC 驱动)。贴错 scope 的后果很实在:该进包的没进(运行期 `ClassNotFound`)、不该进的进了(包臃肿、甚至冲突)。

> **⏳ 版本时光机 · 指定 Java 版本的写法**

| 时期 | 写法 | 问题 |
|---|---|---|
| 早期 | `<source>25</source>` + `<target>25</target>` | 只管源码级别和字节码级别,**不校验你是否误用了新版 API** |
| Java 9+ 推荐 | `<release>25</release>`(或 `maven.compiler.release`) | 一步锁定源码/字节码/**平台 API**,防止"编译过了但用到了旧版没有的 API" |

现代项目一律用 `release`。

> **🎯 面试直击**:`mvn package` 和 `mvn install` 有什么区别?
> `package` 把项目打成 jar/war 放到 `target/`;`install` 在此基础上,再把这个 jar **装进本地仓库 `~/.m2`**,供本机其它项目当依赖引用。追问:两者都会**自动先跑 compile + test**(生命周期的前置阶段),测试不过就中断——所以"构建失败"常常其实是"测试没过"。

## 八、验证:让上一话的测试自动跑

```bash
$ mvn test
...
[INFO] Tests run: 2, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

不用再手动指定 classpath、手动 `java -jar junit...`——Maven 的 surefire 插件自动发现 `*Test.java` 并运行。上一话写的销量统计测试,现在一条命令就跑起来了。

## 🎯 随堂练习

先自己做,再对答案。每道答案都带一句「举一反三」,帮你把这一个点连成一片。

### 选择题(10 道)

1. Maven **坐标**由哪三段唯一确定一个依赖?
   - A) name : version : scope　B) groupId : artifactId : version　C) package : class : version　D) repo : jar : hash
2. Maven 约定的源码与测试目录是?
   - A) `src/` 和 `test/`　B) `src/main/java` 和 `src/test/java`　C) `main/` 和 `spec/`　D) 任意,由 pom 指定
3. 执行 `mvn test` 时会发生什么?
   - A) 只跑测试　B) 先自动 compile,再跑 `src/test/java` 里的测试　C) 先 package 再测试　D) 只校验 pom
4. `<scope>test</scope>` 的含义是?
   - A) 测试优先下载　B) 该依赖只在测试的编译期与运行期可见,不打进成品　C) 只在 CI 里生效　D) 版本由测试框架决定
5. 把 JUnit 的 `<scope>test</scope>` 删掉(变默认 compile),后果是?
   - A) 编译更快　B) 主代码也能 import 测试 API,且 JUnit 被打进发布包 —— 反模式　C) 测试跑不起来　D) 无影响
6. 现代项目指定 Java 版本应该用?
   - A) `<source>` + `<target>`　B) `<release>`(或 `maven.compiler.release`),一步锁定源码/字节码/**平台 API**　C) 环境变量 JAVA_HOME　D) 命令行参数
7. `mvn package` 和 `mvn install` 的区别是?
   - A) 没区别　B) `package` 打包到 `target/`;`install` 还会把 jar 装进本地仓库 `~/.m2` 供本机其它项目依赖　C) `install` 会发布到远程仓库　D) `package` 不编译
8. 「构建失败」在 Maven 里最常见的真实原因是?
   - A) 网络问题　B) **测试没过** —— package/install 会自动先跑 compile + test　C) 磁盘满　D) JDK 版本不对
9. 是谁在 `mvn test` 时自动发现并运行 `*Test.java`?
   - A) JUnit 自己　B) surefire 插件　C) 编译器　D) Maven 核心
10. JDBC 驱动这类「编译期不需要、运行期才要」的依赖,scope 应该是?
    - A) `compile`　B) `test`　C) `provided`　D) `runtime`

> [!答案]
> **1-B**　三段坐标唯一定位一个 jar。**举一反三**:同一个 artifactId 不同 groupId 是完全不同的库,包冲突排查时先看全坐标。
> **2-B**　Maven 认死理,放对位置就不用配。**举一反三**:「约定优于配置」是 Maven 的核心哲学,也是它比 Ant 省事的根本原因。
> **3-B**　后一步自动带跑前面所有步。**举一反三**:所以生命周期是**线性**的 —— `mvn package` 不可能跳过 test,除非显式 `-DskipTests`。
> **4-B**　scope 决定「这依赖在哪些阶段可见」。**举一反三**:贴错 scope 的后果很实在 —— 该进包的没进(运行期 `ClassNotFound`)、不该进的进了(包臃肿甚至冲突)。
> **5-B**　测试框架混进成品包。**举一反三**:「能编译过」不等于「配置对」,这一题正是反例。
> **6-B**　`release` 还会校验你有没有误用新版 API。**举一反三**:只写 source+target 时,用 JDK 25 编译「target 17」的代码,仍可能引用到 17 没有的 API,上线才炸。
> **7-B**　`install` 多了「装进本地仓库」这一步。**举一反三**:多模块项目里,子模块互相依赖就靠 install(或 Maven 的反应堆一次构建)。
> **8-B**　构建失败常常其实是测试没过。**举一反三**:这正说明测试是构建的一部分 —— 测试红了就不该产出制品。
> **9-B**　surefire 负责跑单元测试。**举一反三**:与之对应的是 failsafe 插件,负责集成测试(`*IT.java`),两者分工不同。
> **10-D**　`runtime` 正是为它设计的。**举一反三**:`provided` 则是「编译期要、运行期由容器给」,Servlet API 是典型。
