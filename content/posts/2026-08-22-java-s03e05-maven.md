## 一、需求:别再手工搬砖

咖啡站的代码涨到十几个类,阿零每次都手动 `javac *.java`,想跑测试还得上网下 JUnit 的 jar、手动塞进 classpath。换台电脑,整套依赖重下一遍。豆豆:「你缺的不是勤快,是一个**标准化车间**——声明你要什么,剩下的交给工具。」

这一话不写业务代码,而是给项目装上**构建系统**。它是"能运行"迈向"团队能协作、能持续交付"的分水岭。

## 三、本话目标

- 看懂 Maven **坐标**(groupId / artifactId / version)如何唯一定位一个依赖;
- 用一份 `pom.xml` 声明 JUnit 依赖,让 Maven 自动下载;
- 理解**生命周期**(compile → test → package)与目录约定;
- 理解依赖 **scope**,踩一次"scope 贴错"的坑;
- 用 `mvn test` 让上一话的测试自动跑起来。

## 四、原理图:坐标、目录、生命周期

```text
坐标(唯一定位一个 jar):
    groupId : artifactId : version
    org.junit.jupiter : junit-jupiter : 5.11.3

目录约定(Maven 认死理,放对位置就不用配):
    coffee-shop/
    ├── pom.xml
    └── src/
        ├── main/java/   ← 业务代码(CoffeeShop、MenuStore…)
        └── test/java/   ← 测试代码(…Test)

生命周期(后一步自动带跑前面所有步):
    validate → compile → test → package → verify → install → deploy
    `mvn test` 会先 compile;`mvn package` 会先 compile + test
```

## 五、配置:一份能用的 pom.xml

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             http://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>cafe.doudou</groupId>
    <artifactId>coffee-shop</artifactId>
    <version>1.0.0</version>

    <properties>
        <!-- 用 release 一次锁定源码/字节码/API 到 Java 25,比 source+target 更稳 -->
        <maven.compiler.release>25</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>5.11.3</version>
            <scope>test</scope>   <!-- ★ 只在测试期用,不打进成品 jar -->
        </dependency>
    </dependencies>
</project>
```

把上一话的 `CoffeeShop.java` 放进 `src/main/java/`,`CoffeeShopTest.java` 放进 `src/test/java/`,然后:

```bash
mvn compile     # 编译 src/main/java
mvn test        # 自动先编译,再跑 src/test/java 里的测试
mvn package     # 自动先 compile + test,全过了才打成 target/coffee-shop-1.0.0.jar
```

## 六、故意制造一个 Bug:scope 贴错

把 JUnit 的 `<scope>test</scope>` 删掉(等于默认 `compile`),再在**业务代码** `CoffeeShop.java` 里手滑写了句测试注解 `@Test`——因为 scope=compile,编译期它居然"看得见":

```java
// src/main/java/CoffeeShop.java  ← 业务代码里混进了测试 API
import org.junit.jupiter.api.Test;   // scope=test 时这里应当编译不过
```

## 七、读懂真实报错:主代码碰不到测试依赖

```text
[ERROR] .../src/main/java/CoffeeShop.java:[3,32] package org.junit.jupiter.api does not exist
```

`scope=test` 的依赖**只在 `src/test/java` 的编译期与运行期可见**,主代码 `src/main/java` 够不着它。这句报错正是 scope 在起保护作用:它把测试框架挡在成品之外。删掉 scope(变 compile)反而"能编译过"——但那意味着 JUnit 被打进了你的发布包,是**反模式**。

> **豆豆锐评 · scope 就是"这依赖在哪些阶段可见"**
> `compile`(默认,全程可见)、`test`(只测试期)、`provided`(编译期要、运行期由容器提供,如 Servlet API)、`runtime`(运行期才要,如 JDBC 驱动)。贴错 scope 的后果很实在:该进包的没进(运行期 `ClassNotFound`)、不该进的进了(包臃肿、甚至冲突)。

> **⏳ 版本时光机 · 指定 Java 版本的写法**

| 时期 | 写法 | 问题 |
|---|---|---|
| 早期 | `<source>25</source>` + `<target>25</target>` | 只管源码级别和字节码级别,**不校验你是否误用了新版 API** |
| Java 9+ 推荐 | `<release>25</release>`(或 `maven.compiler.release`) | 一步锁定源码/字节码/**平台 API**,防止"编译过了但用到了旧版没有的 API" |

现代项目一律用 `release`。

> **🎯 面试直击**:`mvn package` 和 `mvn install` 有什么区别?
> `package` 把项目打成 jar/war 放到 `target/`;`install` 在此基础上,再把这个 jar **装进本地仓库 `~/.m2`**,供本机其它项目当依赖引用。追问:两者都会**自动先跑 compile + test**(生命周期的前置阶段),测试不过就中断——所以"构建失败"常常其实是"测试没过"。

### 一、选择题（10 道）

1. [基础] Maven 项目的核心配置文件是？
- A) `build.gradle`　B) `package.json`　C) `pom.xml`　D) `settings.xml`

2. [基础] Maven 坐标由哪三个要素唯一定位一个依赖？
- A) name, version, scope　B) groupId, artifactId, version　C) package, class, method　D) src, target, output

3. [基础] Maven 的标准目录约定中，业务代码放在哪里？
- A) `src/main/java/`　B) `src/java/`　C) `src/main/source/`　D) `src/`

4. [进阶] `mvn package` 会自动执行哪些阶段？
- A) 仅 package　B) validate → compile → test → package　C) clean → compile → package　D) 仅 test → package

5. [进阶] JUnit 依赖的 `scope` 应该设置为？
- A) `compile`　B) `provided`　C) `test`　D) `runtime`

6. [进阶] `<maven.compiler.release>25</maven.compiler.release>` 相比分别设置 `source` 和 `target` 的优势是？
- A) 编译更快　B) 一并锁定源码级别 + 字节码 + **平台 API**，防止误用新版 API　C) 不需要指定 JDK 版本　D) 只影响运行时

7. [进阶] `mvn package` 测试失败时会怎样？
- A) 跳过测试直接打包　B) **构建中断**，不生成 jar　C) 仍然生成 jar 但标记警告　D) 自动重跑测试 3 次

8. [综合] 依赖 `scope=provided` 的意思是？
- A) 只在运行时可用　B) 编译和测试期可用，但**不打包进成品**（由容器提供）　C) 永远不可用　D) 等价于 test

9. [综合] `mvn install` 和 `mvn package` 的区别是？
- A) 完全相同　B) install 多一步：将 jar **安装到本地仓库 `~/.m2`**　C) install 跳过测试　D) package 多一步部署

10. [综合] Maven 的**生命周期**设计意味着什么？
- A) 每个阶段独立运行　B) 后一阶段**自动触发所有前置阶段**　C) 必须从 compile 开始手动依次执行　D) 只适用于简单项目

> [!答案] **1-C** `pom.xml`（Project Object Model）是 Maven 的项目描述文件。`settings.xml` 是全局/用户级配置。**举一反三**：Gradle 的对应物是 `build.gradle`。
> [!答案] **2-B** GAV 坐标：groupId（组织/公司域名反写）、artifactId（模块名）、version（版本号）。**举一反三**：`org.junit.jupiter:junit-jupiter:5.11.3` 中，groupId 是 `org.junit.jupiter`，artifactId 是 `junit-jupiter`。
> [!答案] **3-A** Maven 认 `src/main/java/`（业务代码）和 `src/test/java/`（测试代码）。放对位置，零配置即可编译和测试。**举一反三**：这种"约定优于配置"的思想贯穿 Maven 设计——遵守约定就省掉大量配置。
> [!答案] **4-B** 生命周期是链式的：`package` 之前会按顺序跑完 validate、compile、test。测试不过则在此中断。**举一反三**：`mvn test` 也会先 compile；所有阶段自动带跑前置阶段。
> [!答案] **5-C** `scope=test` 表示只在测试编译和运行期可用，不打包进成品 jar。**举一反三**：scope=compile（默认）→ 全程可见；test → 只测试期；provided → 编译期要但由容器提供（如 Servlet API）；runtime → 运行期才要（如 JDBC 驱动）。
> [!答案] **6-B** `release` 是 Java 9+ 推荐的统一开关，锁定三样：源码语言级别、字节码版本、以及平台 API——防止用 `--release 11` 编译却误用了 Java 17 才有方法。**举一反三**：现代项目一律用 `release`，不再单独设置 `source`/`target`。
> [!答案] **7-B** 测试不过则构建失败，不产出 jar。这是**质量门禁**——"能编译"不等于"能交付"，测试是打包的前置条件。**举一反三**：`mvn package -DskipTests` 可以跳过测试（紧急修复时用，但不应成为习惯）。
> [!答案] **8-B** `provided` 表示"编译期需要，但运行时由 JDK 或容器提供"。典型例子：Servlet API（Tomcat 自带）、Lombok（编译期注解处理）。**举一反三**：如果 scope 贴错——需要 provided 的标了 compile，会导致 jar 冲突；需要 compile 的标了 provided，运行期 ClassNotFound。
> [!答案] **9-B** `install` = `package` + 将 jar 装到 `~/.m2/repository/`，供本机其他项目当依赖引用。`deploy` 则进一步上传到远程仓库。**举一反三**：多模块项目中，先 `mvn install` core 模块，app 模块才能引用到它。
> [!答案] **10-B** Maven 生命周期是链式的——你只需说"我要 package"，它自动把前面的 validate/compile/test 全跑完。**举一反三**：这是标准化车间的核心——不会出现"编译了但忘了测试"的情况。

### 二、解答题（3 道）

1. [概念] Maven 的三种经典 dependency scope 是什么（compile / test / provided），各自的可见范围和适用场景各举一例。

2. [场景] 咖啡站项目的 `pom.xml` 现在只依赖 JUnit。如果要引入一个 JSON 解析库（如 Gson），应该怎么写 `<dependency>`？如果这个 JSON 库**只在测试时用**，scope 应该设什么？写出完整的 `<dependency>` 片段。

3. [综合] "构建失败常常其实是测试没过"——请解释这句话背后的 Maven 生命周期机制。如果你的 `mvn package` 失败了，你会如何快速判断是**编译错误**还是**测试失败**？从 Maven 输出中给出判断依据。

> [!答案] **1** compile（默认）：全程可见，如 `gson`（业务代码和测试都要用）；test：只测试期可见，如 `junit-jupiter`、`assertj`；provided：编译测试期可见但不打包，如 `lombok`、`servlet-api`。**举一反三**：还有 runtime（运行期才要，如 JDBC 驱动——编译只需接口）和 system（已废弃，用本地 jar 路径）。
> [!答案] **2** `<dependency><groupId>com.google.code.gson</groupId><artifactId>gson</artifactId><version>2.11.0</version></dependency>`（scope 默认 compile）。如果只测试时用：添加 `<scope>test</scope>`。**举一反三**：不确定 artifactId 时，去 [mvnrepository.com](https://mvnrepository.com) 搜 GAV 坐标。
> [!答案] **3** Maven 生命周期中 `test` 是 `package` 的前置阶段——测试不通过，`package` 不会执行。判断依据：Maven 输出中 `Tests run: X, Failures: Y`——如果 Y > 0，是测试失败；如果出现 `[ERROR] cannot find symbol` 或 `Compilation failure`，是编译错误。输出末尾的 `BUILD FAILURE` 上面的最后几行错误信息就是根因。**举一反三**：`mvn test` 可以单独跑测试，帮助快速定位是编译问题还是测试问题。

### 三、代码题（2 道）

1. [基础] 为一个 Maven 项目写出完整的 `pom.xml`：groupId 为 `cafe.doudou`，artifactId 为 `coffee-shop`，version 为 `2.0.0`，Java 版本设为 25，编码 UTF-8，并添加 JUnit Jupiter 5.11.3 测试依赖。要求正确设置 scope。

2. [综合] 在一个 `pom.xml` 中添加两个依赖：①`org.slf4j:slf4j-api:2.0.16`（编译期）；②`com.h2database:h2:2.3.232`（仅运行时）。同时，这个项目依赖一个第三方 jar 已经装在本机 `~/.m2`——请用 Maven 概念说明如何让项目引用这个已安装的 jar（不需要写具体 jar 的坐标，只需说明机制）。写出完整 `pom.xml` 的 `<dependencies>` 部分。

> [!答案] **1 验收**：
> ```xml
> <project xmlns="http://maven.apache.org/POM/4.0.0"
>          xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
>          xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
>                              http://maven.apache.org/xsd/maven-4.0.0.xsd">
>     <modelVersion>4.0.0</modelVersion>
>     <groupId>cafe.doudou</groupId>
>     <artifactId>coffee-shop</artifactId>
>     <version>2.0.0</version>
>     <properties>
>         <maven.compiler.release>25</maven.compiler.release>
>         <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
>     </properties>
>     <dependencies>
>         <dependency>
>             <groupId>org.junit.jupiter</groupId>
>             <artifactId>junit-jupiter</artifactId>
>             <version>5.11.3</version>
>             <scope>test</scope>
>         </dependency>
>     </dependencies>
> </project>
> ```
> **举一反三**：`properties` 中定义的变量可在别处用 `${property.name}` 引用，比如 `${junit.version}` 统一管理版本。
> [!答案] **2 验收**：
> ```xml
> <dependencies>
>     <!-- 日志门面：编译和运行都需要 -->
>     <dependency>
>         <groupId>org.slf4j</groupId>
>         <artifactId>slf4j-api</artifactId>
>         <version>2.0.16</version>
>     </dependency>
>     <!-- H2 内存数据库：只在运行时需要（JDBC 驱动） -->
>     <dependency>
>         <groupId>com.h2database</groupId>
>         <artifactId>h2</artifactId>
>         <version>2.3.232</version>
>         <scope>runtime</scope>
>     </dependency>
> </dependencies>
> ```
> 引用已安装到 `~/.m2` 的第三方 jar：只要知道该 jar 的 GAV 坐标（groupId:artifactId:version），直接写 `<dependency>` 即可——Maven 会先从本地仓库查找，找到即用。**机制**：`mvn install` 会把 jar 装进 `~/.m2/repository/{groupId路径}/{artifactId}/{version}/`，任何本机项目都能通过坐标引用。**举一反三**：`scope=runtime` 的依赖在编译时不需要（只靠接口编译），运行时才需要具体实现类——JDBC 驱动是典型场景。
