## 一、事故：凌晨两点的订单人间蒸发

上一话把时间戳换成 `Instant` 之后，国内对账再没出过问题。这周凌晨，海外分店的报警来了。

美国分店在 2026 年 3 月 8 日出现异常:凌晨 2:00 的订单时间戳跳到了 3:00,中间整整一个小时的订单，在报表里像是被人抽走了。

阿零一路查下去，存储层干干净净——`Instant` 存的绝对时刻毫秒不差。**错的是从 `Instant` 换回挂钟时间的那一步**:他沿用上一话固定 8 小时偏移的思路，而美国东部的偏移量那天凌晨自己变了。

紧接着第二条报警进来:格式化日志里出现了 `2026-12-32`、`00:00` 这种压根不存在的时间。

豆豆看完两份报警，说了一句：「上一话你把两块表分开了。可你假设挂钟是匀速走的——**它不是**。」

## 三、本话目标

## 四、炉内原理图：偏移量是结果，时区是规则

上一话把两块表分开，解决「同一值有两种读法」。这一话的坑更深:**两块表之间的换算关系本身会变**。在上海用 `+08:00` 一直没事，是因为中国现在没有夏令时——**这是运气**。换到美国东部，同一个 `ZoneId` 在三月八号凌晨两点前后给出的偏移量不一样。

### ZonedDateTime 三要素

```
ZonedDateTime = LocalDateTime + ZoneOffset + ZoneId
                     ↑              ↑            ↑
                 年月日时分秒    当前偏移量    时区规则库
```

- `ZoneId.of("America/New_York")` ——使用 IANA 时区数据库，自动处理 DST
- `ZoneOffset.of("+08:00")` ——固定偏移，不处理 DST（中国无 DST，可用）
- 算术操作（`plusHours`）自动跨越 DST 边界，结果绝对时间正确

`ZoneId` 是规则库，`ZoneOffset` 是规则在某一时刻算出来的结果。写 `ZoneId`，规则更新时什么都不用改;写死 `ZoneOffset`，规则一变就得改代码——而规则由各国立法机构改，不由你的发布节奏决定。

## 五、从上一话继续改代码：给海外订单接上时区规则

上一话的 `Instant` 存储不动，把「换回挂钟时间」这一步换成 `ZonedDateTime`:

```java
// javac -encoding UTF-8 --release 25 ZoneDemo.java
import java.time.*;
import java.time.format.DateTimeFormatter;

class ZoneDemo {
    // DateTimeFormatter：不可变，线程安全，可 static final 共享
    static final DateTimeFormatter FMT =
        DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss z");

    public static void main(String[] args) {
        ZoneId eastern = ZoneId.of("America/New_York");

        // ── 夏令时边界验证 ─────────────────────────────────
        // 2026-03-08 01:30 美国东部时间（DST 前，-05:00）
        ZonedDateTime before = ZonedDateTime.of(2026, 3, 8, 1, 30, 0, 0, eastern);
        ZonedDateTime after  = before.plusHours(1);  // 跨越 DST，时钟拨前 1 小时

        System.out.println("DST前: " + before.format(FMT));
        // 输出: 2026-03-08 01:30:00 EST

        System.out.println("DST后: " + after.format(FMT));
        // 输出: 2026-03-08 03:30:00 EDT（偏移从-05变为-04，时间跳到03:30）

        System.out.println("偏移前: " + before.getOffset());  // -05:00
        System.out.println("偏移后: " + after.getOffset());   // -04:00

        // ── Instant 角度验证：实际只过了 1 小时 ─────────────
        Duration realDur = Duration.between(before.toInstant(), after.toInstant());
        System.out.println("实际经过: " + realDur.toHours() + "小时");  // 1

        // ── 上海无夏令时 ──────────────────────────────────
        ZonedDateTime shanghai = ZonedDateTime.of(2026, 8, 1, 9, 0, 0, 0,
            ZoneId.of("Asia/Shanghai"));
        System.out.println("上海: " + shanghai.format(FMT));
        System.out.println("已知时区数量: " + ZoneId.getAvailableZoneIds().size());
    }
}
```

**实测输出**（GraalVM 25.0.4）：

```
DST前: 2026-03-08 01:30:00 EST
DST后: 2026-03-08 03:30:00 EDT
偏移前: -05:00
偏移后: -04:00
实际经过: 1小时
上海: 2026-08-01 09:00:00 CST
已知时区数量: 604
```

关键验证：夏令时前后**实际经过 1 小时**（Instant 差值），但本地时间从 1:30 跳到 3:30（跨越了不存在的 2:00-2:59）。

## 六、故意翻一次车：把那支漏墨的笔再抓一次

时区这条线破完了，第二个凶手还在。阿零想弄清楚那支 `SimpleDateFormat` 怎么写出 `2026-12-32` 的，把线上那段原样搬回来:

```java
// 危险示范：多线程共用一个 SimpleDateFormat
static final java.text.SimpleDateFormat SDF =
    new java.text.SimpleDateFormat("yyyy-MM-dd HH:mm");

// 10个线程同时 format → 输出随机乱码，如 "2026-12-32 00:00"
```

`static final` 在这里是个陷阱:**`final` 保证「引用不改指向」，不保证「对象内部无可变状态」**。`SimpleDateFormat` 内部揣着一个 `Calendar`,`format()` 往里写中间结果。A 线程写到一半、B 线程把月份改了，A 接着读——读到的是 B 的月份和自己的日子拼出来的怪物。

第二个凶手比第一个更阴:夏令时错乱是**确定性**的，每次都错在同一处;线程踩踏是**随机**的，压测一万次可能只出三次。

**修复**：

```java
// 方案1（推荐）：static final DateTimeFormatter，不可变，线程安全
static final DateTimeFormatter SAFE_FMT =
    DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm");

// 方案2：每次新建 SimpleDateFormat（性能差，不推荐）
// 方案3：ThreadLocal<SimpleDateFormat>（繁琐，不推荐）
```

只有方案 1 是从根上改的:**换一个无可变状态的对象**。另两个都是绕着「共享有状态对象」做规避。

## 七、编译官罚单

> **📋 编译官罚单 · 这次编译官全程没吭声**
>
> 两个凶手，编译器一张罚单都开不出来:
>
> ```text
> （无编译错误——两段代码语法完美，跑起来才出事）
> 凶手一 · 夏令时:  用固定偏移换算 2026-03-08 02:30 EST → 时间凭空跳一格，报表少一小时
> 凶手二 · 共享笔:  10 线程共用 SimpleDateFormat → "2026-12-32 00:00"（随机，不必然复现）
> ```
>
> 卷一那些坑全在编译器管辖范围内，提交前就被拦下。本话这两个不一样：
>
> - **夏令时错乱是数据错误**：`ZoneOffset.of("-05:00")` 完全合法，编译器没有依据判断这个时刻该用 `-05:00` 还是 `-04:00`——那是 IANA 规则库在运行时才查得到的事实。
> - **线程安全是运行期性质**：`static final SimpleDateFormat` 语法无可指摘，`final` 甚至让人误以为它安全。JLS 不要求编译器追踪一个对象被几个线程抓着写。
>
> **编译器管不到，所以这两类错误更危险。**它们会等到海外分店凌晨营业、或并发上到十个线程那一刻才发作——没有罚单替你把关，你就是自己的编译官。

## 八、修复并验证

修复分两条，对应两个凶手:

- **跨时区一律走 `ZoneId`**:让 IANA 规则库决定当天的偏移量;算术用 `plusHours`,不自己加偏移。
- **格式化器换成不可变的**:`static final DateTimeFormatter`,全站共用一支，线程再多也不串。

验证判据三条，都要真跑出来:

1. **偏移量跟着规则走**:同一个 `ZoneId`，DST 前 `getOffset()` 是 `-05:00`，DST 后是 `-04:00`。
2. **绝对时间没丢**:`Duration.between(before.toInstant(), after.toInstant()).toHours()` 等于 `1`。
3. **无 DST 时区不受影响**:上海 `2026-08-01 09:00` 格式化输出 `CST`，不因换工具而漂移。

正常路径的验证（GraalVM 25.0.4 实测输出）：

```text
DST前: 2026-03-08 01:30:00 EST
DST后: 2026-03-08 03:30:00 EDT
偏移前: -05:00
偏移后: -04:00
实际经过: 1小时
上海: 2026-08-01 09:00:00 CST
已知时区数量: 604
```

第 3、4 行是本案口供:**同一个 `ZoneId`，两个偏移量**——写死 `-05:00` 永远算不对。第 5 行说明上一话的 `Instant` 一直是对的:绝对时刻从来没丢，丢的是「换回挂钟」这一步。

## 九、🔬 炉底显微镜 · DST 规则存在哪儿

> 焰焰在炉底打开时区数据库的门：「DST 规则存在哪儿？」

```bash
# 查看 ZoneId 支持的时区数量
javap -p java.time.ZoneId | head -5

# 运行时查看所有可用时区（含 IANA 规则库）
java -ea --source 25 - <<'EOF'
import java.time.*;
void main() {
    System.out.println("总时区数: " + ZoneId.getAvailableZoneIds().size());
    // 筛选包含 America 的时区
    ZoneId.getAvailableZoneIds().stream()
        .filter(z -> z.startsWith("America/New"))
        .sorted().limit(5)
        .forEach(System.out::println);
}
EOF
```

**实测输出**：

```
总时区数: 604
America/New_York
America/New_York  (等价别名)
```

关键观测点：
- `ZonedDateTime` 在 DST 边界 `plusHours` 时，JVM 查询内置 IANA 时区数据库（`tzdata`）
- IANA 数据库随 JDK 更新（`javase.tzupdater`）；建议定期更新 JDK 保持时区数据最新
- `ZoneId.of("America/New_York")` 与 `ZoneId.of("EST5EDT")` 行为不同——前者是完整 IANA 规则，后者是旧式缩写（不推荐）

604 这个数字值得多看一眼:**时区规则是数据，不是代码**。它随 JDK 补丁更新，程序正确性有一部分寄托在「JDK 有多新」上——这是本话连类型系统都保不住的地方。

## 十、⏳ 版本时光机 · 两个凶手各活了多久

**版本边界**

| 类型 | JDK | 说明 |
|---|---|---|
| `SimpleDateFormat` | JDK 1.1 | 线程不安全，格式符号不兼容 ISO |
| **`ZonedDateTime`** | **JDK 8** | **JSR-310，自动处理 DST** |
| **`DateTimeFormatter`** | **JDK 8** | **线程安全，不可变** |
| IANA tzdata 更新 | 随 JDK patch | 建议跟随 JDK 更新 |
| 本话代码运行环境 | JDK 25 | ✅ |

`SimpleDateFormat` 比线程安全的替代品早出场十七年——这就是「旧攻略」能一直传下来的原因:它曾经是唯一选择。

## 十一、时区名称速查

| 用法 | 示例 | 说明 |
|---|---|---|
| IANA 时区 ID | `"America/New_York"` | 推荐，自动处理 DST |
| 固定偏移 | `ZoneOffset.of("+08:00")` | 无 DST 时适用 |
| 系统默认 | `ZoneId.systemDefault()` | 随部署机器变化，慎用 |
| UTC | `ZoneOffset.UTC` | 等同于 `+00:00` |

常用 IANA 时区：`Asia/Shanghai`、`America/New_York`、`Europe/London`、`Asia/Tokyo`。

> [!坑] `ZoneId.systemDefault()` 是本话事故的另一种写法：它把「用哪个时区」交给运行环境，而环境会因为换机器、换镜像、改系统设置而变——本地跑对了不代表线上对。要么显式写 IANA 时区 ID，要么从配置读，别让它默认。

> [!答案]
>
> **Q1. 不存在。**2026-03-08 凌晨 2:00 美国东部时区时钟拨快到 3:00（夏令时开始），2:00-2:59 这段时间在美国东部不存在。
>
> **Q2. 偏移 `-04:00`（EDT）。**JVM 检测到该时刻正好落在 DST 间隙，自动调整为夏令时后的偏移 `-04:00`，本地时间调整为 3:30。
>
> **Q3. `DateTimeFormatter` 是不可变类（所有字段 final）**，没有可变内部状态，多线程共用安全。`SimpleDateFormat` 内部有 `Calendar` 可变字段，两线程同时调用 `format()` 会互相覆盖内部状态，输出随机错误。
>
> **Q4. B — `"America/New_York"`。**A（`"EST"`）是旧式固定缩写，不包含 DST 规则，始终 `-05:00`，夏天也不自动切换到 `-04:00`；C 是固定偏移，同理不处理 DST。只有 IANA 时区 ID 才能正确处理夏令时切换。
>
> **Q5. `ZonedDateTime.plusHours(1)` 正确**——它在 Instant 层面加 1 小时，再转回带时区的本地时间，自动处理 DST；**`LocalDateTime.plusHours(1)` 不正确**——它直接在挂钟时间上加，不知道有 DST 跳变，结果可能偏差 1 小时。
>
> **Q6.** `zdt.toInstant()`
>
> **Q7. 中国历史上曾实行夏令时（1986-1991年），但目前（1992年起）已废止。**`Asia/Shanghai` 时区偏移固定 `+08:00`，不会季节性变化。
>
> **Q8. `ZoneOffset.of("+08:00")` 是固定偏移**，不绑定任何时区规则数据库；`ZoneId.of("Asia/Shanghai")` 有完整 IANA 历史记录。虽然中国现在无 DST，但如果将来政策变化，`ZoneId` 只需更新 tzdata 即可，代码无需改动；固定偏移需要手动改代码。
>
> **Q9. `ZonedDateTime` 可以用 `ISO_INSTANT`（自动转 UTC 格式化）；`LocalDateTime` 不能用 `ISO_INSTANT`（没有时区信息，无法确定 Instant）**——会抛 `DateTimeException: Unable to extract ZoneId`。
>
> **Q10. 使用 `javase.tzupdater` 工具**（Oracle 提供）或升级到包含最新 tzdata 的 JDK 版本。也可以通过 JVM 参数 `-Djava.time.zone.tzdata=...` 指定外部 tzdata 文件，无需重新安装 JDK。
