## 一、需求:服务器卡了,可屏幕上什么都看不见

还记得上一卷收尾那晚服务器毫无征兆卡的那三秒吗?阿零当时没当回事——毕竟那晚他刚随手跑起一个压测脚本 `stress.sh`,想赶在咖啡站上线前掂掂这台小服务器的斤两,结果忘了关就下了线。今早 ssh 上去,敲个 `ls` 都要顿两秒,`vim` 打开文件卡出残影。

问题是——屏幕上**什么都看不见**。没有任务管理器,没有弹窗,没有风扇狂转的动静(服务器在千里之外的机房)。阿零第一次意识到:这台机器上此刻正同时跑着一堆东西,而他连「都有谁在跑」都答不上来。他需要一双眼睛:**列出所有正在运行的进程,找出吃 CPU 的那个,然后让它停下。**

## 二、漫画 · 黑箱里的住户名册

> **〔1〕** 阿零敲 `ls`,光标冻了两秒才动。旁边的豆豆急得咕嘟咕嘟冒泡。
> 阿零:「服务器……在梦游?」特米(肚皮闪出心电图):「不,是有住户在里面开派对。」

> **〔2〕** 特米一挥手,黑屏掀开一角:里面密密麻麻全是小人,每人胸口一个编号。
> 特米:「每个正在运行的程序叫**进程**,编号叫 **PID**。`ps aux`——住户名册,全楼拉一遍。」

> **〔3〕** 名册里一行红得发亮:`%CPU 99.3`。阿零:「抓到了!是我的 `stress.sh`!」
> 特米:「`ps` 是**快照**,拍完就完;想盯着实时刷新,用 `top`——名册变监控大屏。」

> **〔4〕** 阿零撸袖子:「杀!」特米按住:「`kill` 不是杀,是**寄信**。默认寄 15 号信 TERM:『请你体面退出』。」
> 阿零:「进程还能拒收?」特米:「能。所以才有 9 号信 KILL——内核直接掀桌,**没人能拒收**。」

> **〔5〕** 阿零 `kill 4721`,等了两秒进程纹丝不动;再寄一封,还是不动。
> 特米(眯眼):「这脚本把 TERM 信号**捕获了**,装死。对付装死的,寄 9 号。」

> **〔6〕** `kill -9 4721`,红色小人当场消失,`ls` 唰地回来了,整栋楼瞬间恢复呼吸。
> 特米:「记住顺序:**先 15 商量,不听再 9。** 一上来就掀桌的,不配管服务器。」

## 三、本话目标

- 用 `ps aux` 拉出全部进程,逐列读懂 PID / %CPU / %MEM / STAT / COMMAND;
- 用 `ps aux | grep` 定位目标进程,顺手破掉「grep 自己也在名册里」的经典梗;
- 用 `top` 实时盯梢:`P` 按 CPU 排、`M` 按内存排、`q` 退出;
- 从第一性原理理解 `kill`:它是**发信号**,TERM(15)商量 vs KILL(9)掀桌,以及 `-9` 的代价;
- 用 `pgrep`/`pkill` 按名字直接找人/寄信;
- 踩两个真实坑:对已死 PID 寄信、进程捕获 TERM 装死。

## 四、原理图:进程是住户,kill 是邮差

```text
一台运行中的 Linux = 一栋公寓楼

  ┌─────────────────────── coffee-server ───────────────────────┐
  │  PID 1    init/systemd   ← 楼长,所有住户的老祖宗            │
  │  PID 812  sshd           ← 门卫(你就是从它这儿进来的)       │
  │  PID 4721 stress.sh      ← 失控住户,CPU 99%  ◀── 今天的目标 │
  │  ...几百个住户,各有编号(PID)、房态(STAT)、饭量(%CPU/%MEM)│
  └──────────────────────────────────────────────────────────────┘

  ps   = 给全楼拍一张"快照"名册(拍完即止)
  top  = 监控大屏,几秒刷新一次,谁吃得多谁排前面
  kill = 邮差,给指定 PID 送"信号":
         ── SIGTERM(15,默认):请体面退出——进程可收尾、可拒收
         ── SIGKILL(9):内核直接清房——进程根本收不到,谈不上拒收,
                         但也没机会保存数据、删临时文件(后患自负)
```

一句话:**ps 看快照,top 看直播,kill 寄信——信分「商量」和「掀桌」两种。**

## 五、上手:拉名册,抓元凶

**① `ps aux` 全楼快照,逐列认字**:

```bash
$ ps aux | head -4
USER   PID %CPU %MEM    VSZ   RSS TTY   STAT START  TIME COMMAND
root     1  0.0  0.5 167404 11808 ?     Ss   09:00  0:02 /sbin/init
root   812  0.0  0.3  15420  6900 ?     Ss   09:00  0:00 sshd: /usr/sbin/sshd
ubuntu 4721 99.3  0.1   7368  3200 pts/0 R   23:47 412:10 /bin/bash ./stress.sh
```

- **PID**:进程唯一编号,寄信全靠它;
- **%CPU / %MEM**:CPU 和内存占比——`99.3` 就是今天的元凶;
- **STAT**:房态。`R` 正在跑、`S` 睡觉(等事件)、`D` 等磁盘(杀不动)、`Z` 僵尸(已死没收尸)、`T` 被暂停;
- **COMMAND**:住户的真名和启动命令;
- **TIME**:累计吃掉的 CPU 时间——`412:10`,跑了一整夜的铁证。

**② 配 grep 精准点名(注意经典梗)**:

```bash
$ ps aux | grep stress
ubuntu 4721 99.3  0.1  7368 3200 pts/0 R  23:47 412:10 /bin/bash ./stress.sh
ubuntu 5103  0.0  0.0  6480 2200 pts/1 S+ 10:22   0:00 grep --color=auto stress
```

第二行是谁?**grep 自己**——它的命令行里也含 `stress`,把自己照了出来。破法两选一:`grep [s]tress`(正则 `[s]tress` 匹配 stress,但 grep 自己的命令行里是 `[s]tress`,匹配不上自己),或者干脆用专业工具 `pgrep`:

```bash
$ pgrep -a stress          # -a 连命令一起显示,只报真住户
4721 /bin/bash ./stress.sh
```

**③ `top` 开直播**(进去后按 `P` 按 CPU 排、`M` 按内存排、`q` 退出):

```bash
$ top
top - 10:24:01 up  1 day, 1:24,  2 users,  load average: 1.98, 1.95, 1.90
Tasks: 108 total,   2 running, 106 sleeping,   0 stopped,   0 zombie
%Cpu(s): 99.0 us,  0.7 sy,  0.0 ni,  0.3 id
    PID USER    PR  NI    VIRT    RES  %CPU  %MEM     TIME+ COMMAND
   4721 ubuntu  20   0    7368   3200  99.3   0.1  412:10.33 stress.sh
    812 root    20   0   15420   6900   0.0   0.3    0:00.12 sshd
```

`load average: 1.98` ≈ 这台单核小机常年背着两倍的活——难怪 `ls` 都卡。

## 六、故意制造一个 Bug:寄信给死人 + 进程装死

阿零先手抄错了 PID,给一个早就退出的进程寄信:

```bash
$ kill 4712                # 手滑,真身是 4721
```

改对之后按规矩先寄 15 号信,结果这脚本开头写了 `trap '' TERM`(捕获并无视 TERM——测试脚本防误杀的土办法),两封信都石沉大海:

```bash
$ kill 4721
$ kill 4721                # 再寄一封,依然 99.3% 稳如老狗
```

---

## 七、读懂真实报错

**坑一**,给不存在的 PID 寄信:

```text
bash: kill: (4712) - No such process
```

根因:这栋楼里**没有 4712 这个住户**——要么抄错号,要么它早就退出了。PID 还会被系统回收复用,所以「杀进程」永远要先 `ps`/`pgrep` **现查现杀**,别用十分钟前抄在纸上的旧号,否则轻则报错,重则误杀一个刚好复用了该 PID 的无辜进程。

**坑二**,TERM 寄了两封都被无视——这个坑**没有任何报错**,`kill` 静默返回 0,进程照跑。根因:TERM 是「可拒收的商量信」,进程可以用 `trap`(shell)或信号处理器(C/Java 里的 shutdown hook 同理)捕获它、置之不理。验证它是否还活着,再升级手段:

```bash
$ kill -9 4721             # SIGKILL:内核直接清房,进程无法捕获
$ pgrep stress ; echo $?   # 没输出、退出码 1 = 真死了
1
```

代价也要记住:`-9` 让进程**没有任何收尾机会**——临时文件不删、缓冲不落盘、锁不释放。所以铁律是**先 15 等几秒,确认不退再 9**,而不是反过来。

> **🪟 双系统对照 · 看进程:文本名册 vs 对象花名册**

| 干什么 | Linux (bash) | PowerShell 7 | 关键差异 |
|---|---|---|---|
| 列进程 | `ps aux` | `Get-Process` | ps 吐**文本列**,靠肉眼对齐;PS 吐 **Process 对象**(.Id/.CPU/.WS 是真属性) |
| 找某个进程 | `ps aux \| grep nginx` | `Get-Process nginx` | PS 按名字直接取对象,没有「grep 抓到自己」这回事 |
| 按 CPU 排前 5 | `ps aux --sort=-%cpu \| head -6` | `Get-Process \| Sort-Object CPU -Descending \| Select-Object -First 5` | 一个在排**文本行**,一个在排**对象属性** |
| 结束进程 | `kill 4721`(TERM)/ `kill -9` | `Stop-Process -Id 4721` | PS 里 `kill` 是 Stop-Process 的**别名**;Windows 没有 POSIX 信号,没有「15 商量 / 9 掀桌」的分级,Stop-Process 一律硬停 |
| 按名字批量结束 | `pkill stress` | `Stop-Process -Name stress` | — |

最值得咂摸的是最后一行:Linux 的 kill 体系建立在**信号**这套通信机制上,「结束进程」只是信号的用途之一;Windows 上没有这套邮政系统,所以 PS 的 `kill` 只有掀桌一种寄法。

> **🎯 面试直击**:`kill -15` 和 `kill -9` 有什么区别?为什么不该一上来就 `-9`?
> `-15`(SIGTERM,kill 默认)是**请求**:进程可捕获它,做完保存数据、释放锁、删临时文件等清理后体面退出,也可以选择忽略;`-9`(SIGKILL)由内核直接终止进程,**不可捕获、不可忽略**,进程没有任何清理机会。一上来就 `-9` 可能留下脏数据、残留锁文件、孤儿子进程。标准姿势:先 TERM,等几秒确认没退,再 KILL。追问点:`kill -9` 也杀不掉的进程是什么(`D` 状态,不可中断的磁盘等待)、僵尸进程 `Z` 为什么 kill 无效(它已经死了,等的是父进程收尸)。

### 解答题(5 道)

**Q1 概念:** `ps`、`top`、`kill` 三者在进程管理中各完成什么任务?用一个比喻说明它们的协作关系。

**Q2 解释:** 为什么推荐先 `kill -15`(SIGTERM),再用 `kill -9`(SIGKILL)?两个信号的技术区别是什么?直接 kill -9 有什么风险?

**Q3 操作:** 写出一套完整的"进程排查与终止"命令序列:发现系统变慢→找出占用 CPU 最高的进程→查看它的详细信息→尝试优雅终止→如果不响应就强制终止。

**Q4 排障:** 菜菜用 `kill -9` 杀死了 nginx,重启后发现部分日志文件损坏。分析为什么 `kill -9` 会导致数据损坏,以及正确的操作应该是什么。

**Q5 综合设计:** 为咖啡站的生产服务器设计一套进程健康监控方案:①用 `ps`/`top` 定期采集关键进程(nginx、java、postgres)的状态 ②设置告警阈值(CPU>80%、内存>2GB) ③异常时的排查步骤和终止/重启规范 ④确保在任何情况下不丢数据(数据优先于服务可用性)。

> [!答案]
> **1-B** `ps aux`(BSD 风格,无前导 `-`)和 `ps -ef`(Unix 风格,有 `-`)显示内容相似但列名/顺序不同。`a`=所有用户进程(含终端),`u`=用户友好格式,`x`=含无终端进程。**举一反三:**`ps aux --sort=-%mem` 按内存降序排列;`ps -ef --forest` 显示进程树。🪟 PowerShell 中 `Get-Process` 等价于 `ps`。
>
> **2-B** 在 `top` 界面中:按 `P`(大写)=按 CPU 排序,按 `M`=按内存排序,按 `T`=按运行时间排序。**举一反三:**`top -o %CPU` 启动时直接按 CPU 排序;`htop` 是 `top` 的增强版(彩色、鼠标支持、可滚动列表)。
>
> **3-B** 信号 9 = SIGKILL,由内核直接终止进程,进程无法捕获、忽略或拒绝。**举一反三:**常用信号:1=SIGHUP(重新加载配置),2=SIGINT(Ctrl+C 中断),9=SIGKILL(强制杀死),15=SIGTERM(优雅终止,默认),19=SIGSTOP(暂停),18=SIGCONT(继续)。`kill -l` 列出所有信号。
>
> **4-B** SIGTERM 是**请求**进程退出(如"咖啡站要关门了,请收拾一下关灯撤离");SIGKILL 是内核**直接**终止进程(如"强制清场,不管你在做什么")。**举一反三:**数据库、文件服务器等进程收到 SIGTERM 后会冲刷缓冲区、关闭连接、释放锁;收到 SIGKILL 则立即死亡,可能导致数据丢失。
>
> **5-B** Load Average(负载均衡)表示**正在运行+等待运行的进程**的平均数量。**举一反三:**单核 CPU 的负载=1 表示 CPU 满负荷;负载 < CPU 核心数一般正常;负载持续 > CPU 核心数 x 2 需要关注。三个数字的趋势也很重要:1min 远大于 15min 说明负载在上升。🪟 Windows 任务管理器中"CPU 使用率"概念不同,是百分比而非进程队列长度。
>
> **6-A** VSZ(Virtual Size)=虚拟内存空间(含共享库、malloc 未使用的区域),RSS(Resident Set Size)=实际占用的物理内存。**举一反三:**RSS 比 VSZ 更准确地反映进程"真正吃了多少内存",但多个进程共享的库会被重复计入各进程的 RSS。
>
> **7-B** 正确做法:先 `kill -15 PID`(或默认 `kill PID`),给进程清理的机会。如果进程在几秒后仍不退出,再用 `kill -9 PID`。**举一反三:**`kill -9` 是"最后的武器",平时应该用 `kill PID`(默认 SIGTERM=15)。`Ctrl+C` 发送 SIGINT(2),也是温和终止。步骤:`kill PID`→等待 3 秒→`kill -9 PID`。
>
> **8-B** 在 `top` 中按 `k`,然后输入进程 PID,再输入信号编号(默认 15=SIGTERM),确认后杀掉进程。**举一反三:**`top` 的快捷键:按 `1` 展开/折叠每个 CPU 核心;按 `c` 切换完整命令行;按 `u` 按用户过滤;按 `q` 退出。
>
> **9-A** `kill -0` 发送空信号(signal 0),信号不会被送达,但发送者可以从返回值判断进程是否存在:返回 0=存在,非 0=不存在。**举一反三:**常用于脚本中检查进程是否存活:`if kill -0 $PID 2>/dev/null; then echo "运行中"; else echo "已停止"; fi`。
>
> **10-B** 这是 grep 的经典"自匹配"问题——`grep nginx` 进程的命令行包含 "nginx",所以出现在 `ps` 输出中,然后被 grep 自己匹配到。**举一反三:**排除自身:`ps aux | grep nginx | grep -v grep`;或使用巧技:`ps aux | grep [n]ginx`(方括号让 grep 自身的命令行变成 `grep [n]ginx`,不匹配模式 `[n]ginx` 的字面值)。
>
> **Q1** 比喻:①`ps`=人事部的员工花名册(静态查询:当前所有在岗员工的基本信息——PID、状态、CPU/内存占用) ②`top`=实时监控大厅大屏(动态:持续刷新显示资源占用排名、负载趋势) ③`kill`=人事任免通知(发送信号:决定员工是自行收拾后下班,还是被保安强制拖走)。**协作关系:**`top` 发现异常→`ps` 查看详情→`kill` 执行终止。
>
> **Q2** SIGTERM(15):进程会收到信号,可以设置信号处理函数来执行清理工作(关闭文件句柄、冲刷缓冲区、释放锁、写日志),然后自行退出。SIGKILL(9):内核直接终止进程,不给任何执行代码的机会,清理工作不会完成。**风险:**①数据库未关闭连接,下次启动需要恢复 ②文件缓冲区未冲刷,数据丢失 ③锁残留,死锁 ④临时文件未清理。**底线:**默认 `kill PID` 就是 SIGTERM;只有进程卡死不响应时才 escalate 到 SIGKILL。
>
> **Q3** 命令序列:①`top` 或 `htop` 发现高 CPU 进程(PID=12345) ②`ps -fp 12345` 查看该进程详细信息(命令行、启动时间、父进程) ③读进程名和参数判断是否可以安全终止 ④`kill 12345`(SIGTERM) ⑤等待 3-5 秒,`ps -p 12345 > /dev/null 2>&1 && echo "仍在运行"` ⑥如果不退出:`kill -9 12345`(SIGKILL) ⑦再次检查:`ps -p 12345 || echo "已终止"`。**举一反三:**对于服务进程,优先用 systemd/supervisor 的管理命令(`systemctl stop`)而非直接 kill;`killall -15 nginx` 可以按名称杀进程。
>
> **Q4** nginx 收到 SIGKILL 是瞬间死亡:①访问日志缓冲区未写入磁盘→最后几秒的访问日志丢失 ②正在处理的 HTTP 请求被粗暴断开,客户端收到连接重置 ③worker 进程的共享内存未释放→可能损坏。**正确操作:**`nginx -s quit`(优雅关闭:完成当前请求后退出)或 `systemctl stop nginx`(使用 nginx 的 systemd 单元,默认发送 SIGQUIT 优雅退出)。如果必须 kill:用 `kill -QUIT PID`(信号 3,nginx 推荐的优雅退出信号),而非 `-9`。
>
> **Q5** 监控方案:①定期采集:`while true; do ps aux | grep -E "nginx|java|postgres" >> /tmp/process_health.log; sleep 60; done`(每分钟快照) ②CPU/内存告警:`ps -p PID -o %cpu,%mem | tail -1 | awk '{if($1>80||$2>2) print "ALERT"}'` ③异常排查:先 `top` 宏观看→`ps -fp PID` 看进程详情→`lsof -p PID` 看打开的文件/连接→`strace -p PID` 跟踪系统调用 ④终止规范:服务进程优先 `systemctl stop`,应用进程先 SIGTERM→10 秒超时→SIGKILL,数据库进程**绝不用 SIGKILL**(用数据库自身的 shutdown 命令) ⑤数据保护:终止前确认是否有未完成的事务或写入(`/proc/PID/io` 查看 IO 状态),配置适当的超时时间和优雅关闭脚本。
