## 一、事故:CPU 100%,却没有一行报错

> **事故报告 · INC-0925**
> 时间:14:07 · 现象:coffee-api 单节点 CPU 持续 100%,风扇狂转,`/api/menu` 平均响应从 20ms 涨到 2s。
> 反常点:**日志里没有任何 Exception**,服务没崩、还在跑,就是慢得要死。

阿零第一反应是翻日志,翻了十分钟一无所获。豆豆:「别翻了。**没有报错的故障,才最考验人**。程序没抛异常,说明它不是『出错了』,而是『在拼命干一件蠢事』——比如某个线程陷进了**死循环**,把一整颗 CPU 核吃满了。日志帮不了你,得靠**排障命令**去 JVM 内部抓现行。」

## 三、本话目标

- 建立"无报错故障"的排障心智:CPU 高 = 有线程在空转/热点计算;
- 掌握定位热点线程的**真实五步**:`top` → `top -Hp` → `printf` 换算 → `jstack` → 读栈;
- 读懂 `jstack` 里的线程状态(`RUNNABLE`/`BLOCKED`)和调用栈;
- 分清"死循环吃 CPU"和"锁竞争 BLOCKED"两类高 CPU 病因;
- 修复那个偷偷空转的重试循环。

## 四、排障五步:从一台机器到一行代码

```text
第 1 步  top                     哪个进程在吃 CPU?→ 记下 java 的 PID(如 12345)
第 2 步  top -Hp 12345           这个进程里哪个线程在吃?→ 记下线程 PID(十进制,如 12362)
第 3 步  printf '%x\n' 12362     十进制 → 十六进制(得到 304a)→ jstack 里的 nid
第 4 步  jstack 12345 | ...      抓全部线程栈,搜 nid=0x304a 那一段
第 5 步  读栈                    看它 RUNNABLE 卡在哪个方法的哪一行 → 定位源码

一句话:先锁进程,再锁线程,再把线程号翻译成 jstack 认识的十六进制,最后读栈。
```

为什么要换算十六进制?因为 `top` 显示的线程 ID 是**十进制**,而 `jstack` 输出里每条线程的 `nid`(native id)是**十六进制**。这一步换算是新手最容易卡住的地方——记住 `printf '%x\n'` 就行。

## 五、命令:一步步把凶手线程逼出来

**第 1 步** —— 哪个进程在烧 CPU:

```text
$ top
  PID USER   %CPU  %MEM   TIME+   COMMAND
12345 app   398.7  12.3  88:41.20 java     ← 就是它,快占满 4 个核
  901 app     0.3   0.1   0:12.01 sshd
```

**第 2 步** —— 进程里哪个线程在烧(`-H` 展开线程,`-p` 指定进程):

```text
$ top -Hp 12345
  PID USER   %CPU  %MEM   TIME+   COMMAND
12362 app    99.9   0.0  42:15.77 java     ← 单个线程独占一个核,凶手
12363 app     0.1   0.0   0:00.03 java
12345 app     0.0   0.0   0:00.10 java
```

**第 3 步** —— 十进制线程号转十六进制:

```text
$ printf '%x\n' 12362
304a
```

**第 4 步** —— `jstack` 抓线程快照,只看 `nid=0x304a` 那一段(`-A 15` 顺带打印后 15 行栈):

```text
$ jstack 12345 | grep -A 15 'nid=0x304a'
"coffee-worker-7" #38 prio=5 os_prio=0 cpu=2535912.44ms tid=0x00007f... nid=0x304a runnable [0x00007f2b3c1fe000]
   java.lang.Thread.State: RUNNABLE
	at com.coffee.CoffeeService.retryDeduct(CoffeeService.java:57)
	at com.coffee.CoffeeService.order(CoffeeService.java:41)
	at com.coffee.OrderController.lambda$submit$0(OrderController.java:29)
	at java.base/java.util.concurrent.ThreadPoolExecutor.runWorker(ThreadPoolExecutor.java:1144)
	at java.base/java.lang.Thread.run(Thread.java:1583)
```

三个关键信号:① 线程名 `coffee-worker-7`——上一话坚持给线程起名,此刻回报了,一眼知道是咖啡站出杯工人;② 状态 `RUNNABLE`——它在**真跑**(不是等锁),典型的死循环/热点计算特征;③ 栈顶 `CoffeeService.java:57`——凶手就在这一行。

**第 5 步** —— 翻到 `CoffeeService.java:57`,真相大白。

## 六、故意制造一个 Bug:一个永远转不出去的重试循环

阿零上一话为了"库存不足时重试几次",随手写的:

```java
// CoffeeService.java —— 看似人畜无害的"自旋重试"
private boolean retryDeduct(String name, int qty) {
    while (true) {                          // 57 行:无条件死循环
        if (tryDeduct(name, qty)) {
            return true;
        }
        // ← 忘了两件致命的事:没有重试次数上限、没有任何等待/让出 CPU
    }                                       // 库存长期不足时,这里就是纯烧 CPU 的空转
}
```

平时库存充足,`tryDeduct` 一次就成功,你根本发现不了。可一旦某款豆子**售罄**,`tryDeduct` 永远返回 `false`,这个 `while(true)` 就以最高速度空转,一个线程独吞一整颗 CPU 核。

---

## 七、读懂现象 + 修复:给重试装上"刹车"

现象已由第五节的 `jstack` 坐实:`RUNNABLE` + 卡在 `while` 行 = **CPU 密集型死循环**。(对照:如果状态是 `BLOCKED`,那是**锁竞争**,得去看它 `waiting to lock` 哪个锁、谁持有——那是另一类高 CPU,病因在锁不在循环。)

修复:重试必须有**次数上限**和**退避等待**,别让它裸奔:

```java
private boolean retryDeduct(String name, int qty) {
    for (int attempt = 0; attempt < 3; attempt++) {   // ① 最多重试 3 次,有终点
        if (tryDeduct(name, qty)) {
            return true;
        }
        try {
            Thread.sleep(20L * (attempt + 1));        // ② 退避等待:让出 CPU,不空转
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();        // ③ 正确响应中断,不吞掉信号
            return false;
        }
    }
    return false;   // 3 次仍失败 → 老实返回"缺货",交给上层提示顾客
}
```

改完重新抓一次 `top -Hp`,那个 99.9% 的线程消失了,CPU 回落到个位数。

> **豆豆锐评 · 高 CPU 的两张面孔,jstack 里长得不一样**
> ① **死循环/热点计算**:目标线程 `RUNNABLE`,栈顶稳定停在某个业务方法——像本话。② **锁竞争**:大量线程 `BLOCKED`,栈里写着 `waiting to monitor entry` / `waiting to lock <0x...>`,而某一条线程 `RUNNABLE` 持有那把锁——CPU 也会高(疯狂上下文切换)。**排障口诀:CPU 高先看热点线程是 RUNNABLE 还是 BLOCKED,方向立刻分岔。** 另外抓 `jstack` 要**连抓两三次**,间隔一两秒——每次都停在同一行的,才是真凶。

> **🎯 面试直击**:线上 CPU 100% 你怎么排查?
> 标准答法就是本话五步:**`top` 定位进程 → `top -Hp <pid>` 定位线程 → `printf '%x'` 把线程号转十六进制 → `jstack <pid>` 抓栈、按 `nid` 找到那条线程 → 读栈定位到具体代码行**。追问会问"怎么区分死循环还是锁竞争":看目标线程状态——`RUNNABLE` 卡在业务代码是死循环/热点,大片 `BLOCKED` 是锁竞争。再追问"生产不让装工具怎么办":`top`/`jstack` 都是 JDK 自带、零依赖,这正是它们的价值(进阶可提 Arthas / async-profiler 出火焰图,但基本功是这五步)。

## 八、用测试证明:重试有界、会正常放弃

CPU 死循环本身难写单元测试,但它的**根因——"重试没有上限"**完全可测:给一个永远缺货的场景,断言方法能在有限时间内返回 `false`,而不是转到天荒地老:

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.Timeout;
import java.util.concurrent.TimeUnit;
import static org.junit.jupiter.api.Assertions.*;

class RetryTest {
    @Test
    @Timeout(value = 1, unit = TimeUnit.SECONDS)   // 超过 1 秒仍没返回 = 又死循环了,测试失败
    void retry_gives_up_when_sold_out() {
        var service = new CoffeeService();
        service.setStock("耶加雪菲", 0);            // 永远缺货
        assertFalse(service.order("耶加雪菲", 1),   // 必须优雅返回 false
                "售罄时应在重试上限内放弃,而不是空转");
    }
}
```

`@Timeout` 是给"可能死循环"的代码上的保险丝:改回 `while(true)`,这个测试会直接超时红掉——**用测试把死循环挡在上线之前**。

> **1-B**　先锁进程,再锁线程,再翻译,最后读栈。**举一反三**:这五步全用 JDK 自带工具,零依赖 —— 这正是它在生产环境的价值。

> **6-B**　有终点、会让步、不吞中断。**举一反三**:退避等待还常配合指数退避与随机抖动,避免大量线程同时重试形成新的洪峰。

> **8-B**　单次快照可能撞巧。**举一反三**:同理排查慢接口也要多次采样,或直接上 async-profiler 出火焰图。
> **9-B**　用测试把死循环挡在上线之前。**举一反三**:CPU 死循环本身难测,但它的根因「重试没有上限」完全可测 —— 找到可测的那一面是测试设计的关键。
