## 一、技术债第一页:状态列的裸字符串

冬歇期清账继续。`BigDecimal` 刚保住钱的尊严,豆豆的笔尖就停在订单表的状态列上:`"PAID"`、`"paid"`,还有一条 `"PAIDD"`——那笔订单卡了三天,打错一个字母,没有任何一行代码拦它。

阿零先亮方案:「上常量,`static final String PAID`。」豆豆摇头:「常量只是给字符串**起名**,方法参数还是 `String`,天下所有字符串都能混进来。你缺的不是名字,是**类型**——一个实例天生只有五个的类型。」

## 四、原理图:enum 的真身

```text
enum OrderStatus { CREATED, PAID, MAKING, DONE, CANCELLED }
        │ 编译官脱糖后,约等于 ↓
final class OrderStatus extends java.lang.Enum<OrderStatus> {
    public static final OrderStatus CREATED = new OrderStatus("CREATED", 0);
    public static final OrderStatus PAID    = new OrderStatus("PAID", 1);
    …(五枚徽章,类初始化时一次铸齐)
    private OrderStatus(String name, int ordinal) { super(name, ordinal); }
    public static OrderStatus[] values() { return $VALUES.clone(); } // 每次给克隆,防篡改
    public static OrderStatus valueOf(String n) { … } // 查无此名 → IllegalArgumentException
}

final 类  → 没人能继承它偷造「第六种状态」
私有构造  → 实例即常量:世上有且只有这五枚
name()   → 常量名,身份证;ordinal() → 声明位置,座位号——座位会变,身份证不会
```

> **豆豆锐评**:枚举比较直接用 `==`——实例唯一,语义就是「同一枚徽章」,而且左边是 `null` 也不崩;`equals` 遇上 null 调用者,当场 NPE。

> **🔀 豆豆的多解台 · 单例有四种写法,选哪个?**

| 写法 | 代码要点 | 适合什么时候 | 坑 |
|---|---|---|---|
| 饿汉 | `static final X I = new X();` | 实例轻、早晚要用 | 类一加载就建;反射能再造一个 |
| 懒汉 + 双检锁(DCL) | `volatile` 字段 + 两层 `if` + `synchronized` | 想延迟初始化又要线程安全 | 极易写错;那个 `volatile` 一个字都不能省——为什么?账记在第二页,第 70 话清算 |
| 静态内部类 | `Holder.I`,首次访问才触发类加载 | 要延迟又不想上锁 | 反射、反序列化仍能打出第二个实例 |
| 枚举 | `enum X { INSTANCE }` | 绝大多数单例的默认答案 | 不能再继承别的类;做不到「用到字段才建」那种极致延迟 |

豆豆锐评:**默认写枚举**——初始化由 JVM 的类加载保证,只此一次;真要懒加载,再上静态内部类。

> **🎯 面试直击**:枚举为什么是最安全的单例?
> 三重保险:① 常量由 JVM 在类初始化时创建,天然线程安全、只此一次;② 反射被判死刑——`Constructor.newInstance` 见到枚举直接抛 `IllegalArgumentException: Cannot reflectively create enum objects`;③ 序列化只写 `name`,反序列化按名找回**原实例**,造不出分身。追问点:普通单例怎么防分身?`readResolve`——但那是补丁,枚举是天生的。

## 五、代码:给订单装上状态机

订单状态铸成徽章,每枚自带显式 `code`(为持久化准备)与文案;状态机用 EnumMap + EnumSet 写死合法去向:

```java
import java.util.*;

public enum OrderStatus {
    CREATED(10, "已下单"), PAID(20, "已支付"), MAKING(30, "制作中"),
    DONE(40, "已完成"), CANCELLED(90, "已取消");

    private final int code;        // 身份证:与常量名、声明顺序都解耦
    private final String label;

    OrderStatus(int code, String label) { this.code = code; this.label = label; }
    public int code()     { return code; }
    public String label() { return label; }

    /** 状态机:每个状态只认自己的合法去向 */
    private static final Map<OrderStatus, Set<OrderStatus>> NEXT = new EnumMap<>(Map.of(
            CREATED, EnumSet.of(PAID, CANCELLED),  PAID, EnumSet.of(MAKING, CANCELLED),
            MAKING,  EnumSet.of(DONE),             DONE, EnumSet.noneOf(OrderStatus.class),
            CANCELLED, EnumSet.noneOf(OrderStatus.class)));

    public boolean canGoTo(OrderStatus next) { return NEXT.get(this).contains(next); }

    public static OrderStatus ofCode(int code) {
        for (var s : values()) if (s.code == code) return s;
        throw new IllegalArgumentException("未知状态码: " + code);
    }
}
```

取餐屏用 switch 表达式写文案,阿零漏了 `CANCELLED`:

> **📋 编译官罚单**
>
> ```text
> OrderBoard.java:5: error: the switch expression does not cover all possible input values
>         return switch (s) {
>                ^
> 1 error
> ```

补上分支即放行。豆豆:「注意,**别写 `default`**——穷尽列出五个分支,以后新增状态,编译器会替你吼;写了 `default`,它就永远沉默了。」

EnumSet/EnumMap 是枚举专用容器,便宜得离谱:

```java
var inShop = EnumSet.of(OrderStatus.PAID, OrderStatus.MAKING); // 一个 long 的位向量(回看第 58 话)
var stats  = new EnumMap<OrderStatus, Integer>(OrderStatus.class); // 数组,ordinal 当下标
stats.merge(OrderStatus.DONE, 1, Integer::sum);                // 完成一单,计数 +1
```

> **豆豆旁白**:EnumMap 在**进程内**拿 ordinal 当数组下标,天经地义——同一次运行里座位号不变。ordinal 的罪,只在**离开 JVM**(存库、写文件、发消息)那一刻成立。

最后一件宝库藏品——**每枚常量自带行为**(枚举策略),会员折扣不再散落在各处 switch 里:

```java
import java.math.BigDecimal;

public enum MemberLevel {
    SILVER { BigDecimal discount(BigDecimal p) { return p; } },
    GOLD   { BigDecimal discount(BigDecimal p) { return p.multiply(new BigDecimal("0.9")); } },
    BLACK  { BigDecimal discount(BigDecimal p) { return p.multiply(new BigDecimal("0.8")); } };

    abstract BigDecimal discount(BigDecimal price); // 新增等级?编译器逼你当场实现
}
```

## 六、故意制造一个 Bug:把 ordinal 写进归档

冬歇归档,阿零嫌 `"CANCELLED"` 九个字母太占地方,存了数字:

```java
int stored = OrderStatus.DONE.ordinal();             // 归档:DONE → 存下 3
// —— 冬歇升级:在 PAID 与 MAKING 之间插入新状态 QUEUED(排队中)——
OrderStatus restored = OrderStatus.values()[stored]; // 读档:values()[3] 现在是谁?
IO.println("1024 号订单:" + restored.label());
```

## 七、读懂真实现场:没有异常的事故

```text
OrderStatusTest > archived_done_stays_done() FAILED
    org.opentest4j.AssertionFailedError: expected: <DONE> but was: <MAKING>
        at OrderStatusTest.archived_done_stays_done(OrderStatusTest.java:11)
```

这是本卷最阴的 Bug:**不抛任何异常**,数据静悄悄集体错位——

```text
归档时(升级前)          读档时(插入 QUEUED 后)
2 MAKING          →      2 QUEUED     制作中的单,回去重新排队
3 DONE            →      3 MAKING     已完成的单,全部「回炉重做」
4 CANCELLED       →      4 DONE       已退款的单,变成「已完成」!
```

根因一句话:`ordinal` 是**座位号**,不是身份证。中间插一枚徽章,后面所有座位整体后移,而归档文件里的数字纹丝不动。

## 八、修复,并用测试证明

持久化只认两样:`name()`(可读,但常量**改名**即翻车)或显式 `code`(与名字、顺序双解耦)。咖啡站定案:存 code。

```java
int stored = OrderStatus.DONE.code();            // 40:QUEUED 插到哪都不影响
OrderStatus restored = OrderStatus.ofCode(stored);
```

> **豆豆旁白**:走 name 路线就用 `valueOf` 读回,查无此名会抛 `java.lang.IllegalArgumentException: No enum constant OrderStatus.PAIDD`——脏数据当场炸响,也好过静悄悄错位。

JUnit 质检员:「证据呢?」

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class OrderStatusTest {
    @Test
    void code_round_trip_survives_new_states() {
        for (var s : OrderStatus.values())
            assertEquals(s, OrderStatus.ofCode(s.code())); // code ↔ 徽章,与座位无关
    }

    @Test
    void unknown_code_fails_fast() {
        assertThrows(IllegalArgumentException.class, () -> OrderStatus.ofCode(999));
    }

    @Test
    void state_machine_blocks_backflow() {
        assertTrue(OrderStatus.PAID.canGoTo(OrderStatus.MAKING));
        assertFalse(OrderStatus.DONE.canGoTo(OrderStatus.MAKING)); // 完成的单不许回炉
    }
}
```

三条全绿。状态列从「任何字符串都能混进来」变成「五枚徽章 + 编译期穷尽 + 运行期状态机」三层闸门。

### 选择题(10 道)

1. 编译后 `enum` 的真身是?
   - A) 一个接口　B) **一个继承 `java.lang.Enum` 的 final 类,常量是它的 public static final 实例**　C) 一个注解　D) 一组 int 常量
2. `final` 类 + 私有构造器带来的保证是?
   - A) 性能更好　B) **没人能继承它偷造「第六种状态」,实例即常量、世上有且只有这几枚**　C) 支持序列化　D) 便于反射
3. 枚举之间比较推荐用?
   - A) `equals`　B) **`==`** —— 实例唯一,左边是 null 也不崩　C) `compareTo`　D) `Objects.equals`
4. 枚举被称为「最安全的单例」,三重保险是?
   - A) 加锁、缓存、校验　B) **JVM 类初始化保证只创建一次 + 反射被禁止创建枚举 + 序列化按 name 找回原实例**　C) final、static、private　D) 双检锁、volatile、synchronized
5. 用现代 switch 处理枚举时,为什么建议**不写** `default`?
   - A) 性能更好　B) **写了 `default` 编译器就永远沉默;不写才能在新增常量时报「未覆盖所有值」**　C) 语法不允许　D) 会产生警告
6. `ordinal()` 的正确定位是?
   - A) 身份证　B) **座位号** —— 声明位置,中间插入新常量就会整体后移　C) 唯一标识　D) 哈希值

8. 枚举持久化的正确做法是?
   - A) 存 `ordinal()`　B) 存 `name()` 或**显式 `code`**(与名字、顺序双解耦)　C) 存 `hashCode()`　D) 存 `toString()`
9. `EnumSet` 和 `EnumMap` 的底层分别是?
   - A) HashSet 和 HashMap　B) **位向量(一个 long)和数组(ordinal 当下标)**　C) 链表和红黑树　D) 都是数组
10. 在进程内用 `EnumMap`(内部用 ordinal 当下标)有问题吗?
    - A) 有,应该避免　B) **没有** —— 同一次运行里座位号不变;ordinal 的罪只在离开 JVM(存库/写文件)时成立　C) 只在多线程下有问题　D) 取决于枚举大小

> [!答案]
> **1-B**　脱糖后就是一个普通 final 类。**举一反三**:知道它是类,就明白为什么枚举能有构造器、字段和方法。
> **2-B**　实例即常量。**举一反三**:这也是枚举适合做状态机的根本原因 —— 合法值的集合在编译期就被钉死了。
> **3-B**　`==` 语义清晰且 null 安全。**举一反三**:`enumValue.equals(null)` 返回 false,但 `null.equals(enumValue)` 会 NPE —— `==` 两边都不怕。
> **4-B**　三层都堵死了。**举一反三**:普通单例要靠 `readResolve` 打补丁防反序列化分身,枚举天生免疫。
> **5-B**　让编译器替你把关。**举一反三**:这跟第 5 话「箭头 switch 强制穷尽」是同一条思路 —— 把「记得改」变成「不改就编译不过」。
> **6-B**　座位会变,身份证不会。**举一反三**:同理别依赖 `values()` 的顺序写业务逻辑。
> **7-B**　静默错位是本卷最阴的 Bug。**举一反三**:已完成的订单变成「制作中」、已退款变成「已完成」—— 没有异常,只有错账。
> **8-B**　code 与名字、顺序都解耦。**举一反三**:走 name 路线也可以,但常量**改名**就翻车,而且 `valueOf` 查无此名会抛异常 —— 至少是当场炸而不是静默错。
> **9-B**　枚举专用容器,便宜得离谱。**举一反三**:`EnumSet` 底层就是第 58 话的位图,只是套了个类型安全的壳。
> **10-B**　进程内用 ordinal 天经地义。**举一反三**:判断一个「坏实践」是否真的坏,要看它的边界条件 —— 而不是一刀切地禁用。
