# 《从零开始学 Java》44 · OOM 内存事故(线上事故报告)

> 连载特刊 · 第五季「服务器战争」第 5 话 · 线上事故报告 · 基线 Java 25(最新 LTS)
> 承接:上一话扑灭了 CPU 100% 的死循环。可同一台机器又出事——这次不是 CPU 烧,是内存慢慢涨到爆。

---

## 一、事故:内存只涨不落,最后 OOM

> **事故报告 · INC-0931**
> 时间:连续三天 · 现象:coffee-api 堆内存**锯齿逐日抬高**——每次 Full GC 后的最低点也在往上爬,GC 越来越频繁,第三天 02:14 抛出 `OutOfMemoryError: Java heap space`,进程僵死。
> 反常点:重启后一切正常,**跑几天又复现**。典型的"慢性病"。

豆豆:「CPU 那种是急性病,一个 `jstack` 抓现行。内存泄漏是**慢性病**——它不是一次分配了超大对象,而是**有些对象本该被回收,却被人死死攥着不放**,一天天攒,攒到堆装不下。Java 有 GC,可 GC 只回收『没人引用』的对象;**只要还有一根引用链拴着它,GC 就不敢动**。查这种病,靠 `jmap` 把堆『拍张 X 光片』,再用 MAT 看谁在攥着不放。」

## 二、漫画 · 揪住攥着东西不放的手

> **〔1〕** 咖啡站仓库,GC 清洁队推着车来收垃圾。大部分空杯子一收就走,可角落有一堆杯子被一根根**看不见的绳子**拴在墙上,清洁队拽了半天拽不动,只能绕开。
> GC 清洁队长:「这些……还有绳子连着,按规矩我不能收。」

> **〔2〕** 顺着绳子往上看,墙上钉着两颗钉子:一颗是**静态缓存 Map**(`static` 藤蔓),越长越粗,把所有进来的订单全缠住不放;另一颗是 **ThreadLeak 藤蔓**——线程池里的工人干完活走了,却把随身的 `ThreadLocal` 小背包忘在了椅子上,下一个工人坐上来又挂一个。
> 阿零:「工人明明下班了,背包怎么还在?!」

> **〔3〕** 豆豆掏出一台**X 光机**(`jmap`),对着仓库"咔嚓"一拍,导出一张堆快照 `.hprof`。
> 豆豆(叼豆子):「肉眼看不出谁在攥着,拍片子就看得清清楚楚——**哪类对象最多、被谁一路引用到 GC Root**。」

> **〔4〕** 片子(MAT)在屏幕上摊开,一条刺眼的红线**支配树**直指那颗 `static` 藤蔓:它一个人占了 82% 的堆。
> 豆豆:「找到了。**能被 GC 回收的叫垃圾,不能被回收又没用的,叫泄漏。**」

## 三、本话目标

- 建立"内存泄漏 = 对象该死不死、引用链拴着 GC Root"的心智;
- 掌握内存排障链路:自动 dump / `jmap` 导堆 → `jmap -histo` 速览 → MAT 看支配树与泄漏嫌疑;
- 揪出两个经典泄漏:线程池里 `ThreadLocal` 未 `remove`、静态集合无上限膨胀;
- 分清**内存泄漏(Leak)** 与 **内存溢出(OOM)** 的因果;
- 修好它们,并用测试给缓存和 `ThreadLocal` 上界/上锁。

## 四、排障链路:给堆拍片,再顺引用链断案

```text
第 0 步  启动就挂上保险:-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump
         → OOM 那一刻 JVM 自动导出 .hprof,不用你半夜手忙脚乱

第 1 步  jmap -histo:live <pid>   活对象直方图,速览"哪类对象数量/占用异常多"
第 2 步  jmap -dump:live,format=b,file=heap.hprof <pid>   导出完整堆快照
第 3 步  用 MAT / VisualVM 打开 heap.hprof
第 4 步  看两样东西:
           · Histogram   —— 哪类对象占内存最多
           · Dominator Tree(支配树)—— 谁"独占"着大块内存不放
           · Leak Suspects —— MAT 自动报告的泄漏嫌疑
第 5 步  顺引用链找到 GC Root(常是某个 static 字段 / 线程 ThreadLocalMap)→ 定位代码

心法:OOM 只是"结果",别只盯着"堆不够大就调大 -Xmx"——
      要问"到底是谁攥着一堆对象不放",那才是"因"。
```

> **豆豆锐评 · 别一 OOM 就无脑调大 `-Xmx`**
> 调大堆只是让"爆炸"晚几天到,泄漏还在持续。真泄漏,给多大堆都会满。`-Xmx` 该调的场景是"业务确实需要这么多内存"(容量问题);而"锯齿逐日抬高"是**泄漏**(Bug 问题)——两者的区别,就是这一话要教你分辨的。

## 五、命令:从直方图到支配树

**第 1 步** —— `jmap -histo:live` 速览(`:live` 会先触发一次 GC,只统计活对象,更准):

```text
$ jmap -histo:live 12345 | head -n 8

 num     #instances         #bytes  class name (module)
-------------------------------------------------------
   1:       4821037       193M      com.coffee.model.Order
   2:       4821040        154M      java.util.HashMap$Node
   3:       4821051         115M      java.lang.String
   4:            128          8M      byte[]
   5:           2033          1M      java.lang.Class
```

`Order` 对象竟有 480 万个、占 193M——一个只服务几百顾客的咖啡站,怎么会积了几百万订单在堆里?**数量异常 = 泄漏的第一嗅觉。**

**第 2 步** —— 导出完整堆(OOM 时其实已由 `-XX:+HeapDumpOnOutOfMemoryError` 自动生成):

```text
$ jmap -dump:live,format=b,file=heap.hprof 12345
Dumping heap to /data/dump/heap.hprof ...
Heap dump file created [1284 MB]
```

**第 3~4 步** —— MAT 打开,`Leak Suspects` 报告直接点名:

```text
Problem Suspect 1
  One instance of "com.coffee.OrderCache" loaded by "jdk.internal.loader.ClassLoaders$AppClassLoader"
  occupies 1,061,320,984 bytes (82.34%).
  The memory is accumulated in "java.util.HashMap" —— the field "orders" (a static field).
  Keywords: com.coffee.OrderCache, java.util.HashMap
```

支配树顺着 `OrderCache.orders`(一个 `static HashMap`)一路展开,发现它把每一笔历史订单都塞了进去、**从不删除**。GC Root 是那个 `static` 字段——静态字段的生命周期和类一样长,**类不卸载,它就永远活着**,拴着的 480 万个 `Order` 自然一个都回收不掉。

## 六、故意制造两个 Bug:静态缓存 + ThreadLocal

**Bug 1 · 只进不出的静态缓存**(第五节直方图的元凶):

```java
public class OrderCache {
    // static 生命周期 = 整个应用;只 put 不 evict,等于一个"内存黑洞"
    private static final Map<String, Order> orders = new HashMap<>();

    public static void record(Order o) {
        orders.put(o.id(), o);   // 每笔订单都塞进来,永不清理 → 越堆越多
    }
}
```

**Bug 2 · 线程池里忘了 `remove` 的 ThreadLocal**(和上一话的线程池呼应):

```java
public class UserContext {
    private static final ThreadLocal<User> CURRENT = new ThreadLocal<>();

    public static void set(User u) { CURRENT.set(u); }
    public static User get()       { return CURRENT.get(); }
    // ← 少了 remove()!在线程池里这是灾难
}
```

请求处理时 `UserContext.set(user)`,处理完**没有** `remove()`。放到单次运行的程序里没事(线程结束就回收),可在**线程池**里,工人线程是**长期复用**的——它的 `ThreadLocalMap` 里挂着的 `User` 永远不被清,每处理一个用户就攒一个,越攒越多。

---

## 七、读懂现象 + 修复:给缓存设界,给 ThreadLocal 收尾

**修 Bug 1**——静态缓存必须**有上限 + 淘汰策略**。最小改造用 `LinkedHashMap` 做 LRU:

```java
public class OrderCache {
    // 有界 LRU:超过 1000 条,自动淘汰最久未用的,内存封顶
    private static final Map<String, Order> orders =
        java.util.Collections.synchronizedMap(new LinkedHashMap<>(16, 0.75f, true) {
            @Override protected boolean removeEldestEntry(Map.Entry<String, Order> e) {
                return size() > 1000;   // 关键:让 Map 自己吐出旧数据
            }
        });

    public static void record(Order o) { orders.put(o.id(), o); }
}
```

**修 Bug 2**——`ThreadLocal` 用完必须在 `finally` 里 `remove()`,尤其在线程池:

```java
try {
    UserContext.set(currentUser);
    handleRequest();
} finally {
    UserContext.remove();   // 🔑 归还工人的"小背包",线程复用前清空
}
```

改完连跑三天,堆内存的锯齿最低点**稳定不再抬高**——泄漏止住了。

> **豆豆锐评 · ThreadLocal 在线程池里,不 remove 就是定时炸弹**
> 两层危害:① **内存泄漏**——工人线程常驻,`ThreadLocalMap` 里的 value 一直被强引用,回收不掉;② **数据串味**——线程复用时,上一个请求残留的 `User` 会被下一个请求 `get` 到,轻则数据错乱,重则**用户 A 看到用户 B 的信息**(越权),这比泄漏更可怕。所以铁律:**`ThreadLocal` 谁 `set`,谁在 `finally` 里 `remove`**。

> **🔀 豆豆的多解台 · 缓存怎么才不泄漏?**

| 方案 | 写法 | 适合什么时候 | 坑 |
|---|---|---|---|
| 手写 LRU | `LinkedHashMap` + `removeEldestEntry` | 简单本地缓存,零依赖 | 需自己保证线程安全;功能单薄 |
| `WeakHashMap` | key 弱引用,GC 可回收 | key 是"用完即弃"的对象 | value 仍强引用;回收时机不可控,别当缓存主力 |
| Caffeine | `Caffeine.newBuilder().maximumSize(n)` | **生产本地缓存首选** | 引依赖;但过期/淘汰/统计全给你了 |
| Redis | 缓存放进程外 | 多实例共享、缓存量大 | 网络开销;需运维一套 Redis |

豆豆锐评:**生产本地缓存直接上 Caffeine**(自带容量上限、过期、命中率统计,天然防泄漏);只有"教学演示/极简场景"才手写 `LinkedHashMap`。核心原则就一句——**任何缓存都必须有上限**,无界缓存 = 内存泄漏预定。

> **🎯 面试直击**:有 GC 为什么还会内存泄漏?内存泄漏和内存溢出啥区别?
> **泄漏(Leak)**是"因":对象已经没用了,却仍被一条引用链拴到 **GC Root**(常见 Root:`static` 字段、活线程的 `ThreadLocalMap`、正在用的局部变量),GC 判定它"还有人引用"就不敢回收,于是越积越多。**溢出(OOM)**是"果":泄漏攒到堆装不下,抛 `OutOfMemoryError`。GC 只负责回收"不可达"对象,它**没法判断"可达但你其实不想要了"**——那是程序的逻辑责任。经典泄漏源:未 `remove` 的 `ThreadLocal`、无界的 `static` 集合、忘了关的连接/流、监听器只注册不注销。

## 八、用测试钉死:缓存有界 + ThreadLocal 归零

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class LeakGuardTest {
    @Test
    void cache_is_bounded() {
        for (int i = 0; i < 100_000; i++) {          // 猛塞 10 万条
            OrderCache.record(new Order("id-" + i, "美式", 1));
        }
        assertTrue(OrderCache.size() <= 1000,         // 必须被 LRU 封在 1000 以内
                "缓存必须有上限,否则就是内存泄漏");
    }

    @Test
    void threadlocal_cleared_after_request() {
        UserContext.set(new User("alice"));
        try { /* 处理请求 */ } finally { UserContext.remove(); }
        assertNull(UserContext.get(), "请求结束后 ThreadLocal 必须为空");
    }
}
```

`cache_is_bounded` 是防泄漏的核心断言:塞 10 万条,存活必须 ≤ 1000。回退到无界 `HashMap` 版,这个测试立刻红——**把"内存会不会涨"变成一条能自动跑的红线**。

### 一、选择题(10 道)
1. [基础]内存泄漏(Leak)和内存溢出(OOM)的关系是?
- A) 完全相同　B) 泄漏是"因"(对象不该活着却被 GC Root 拴住),溢出是"果"(堆装不下,抛 OOM)　C) 溢出导致泄漏　D) 无关
> [!答案] **1-B**　泄漏=对象不可达却占内存(引用链拴着),越积越多;溢出=堆满,`OutOfMemoryError`。**举一反三**:调大 `-Xmx` 对付容量问题;对付泄漏调多大堆都会慢慢满——治泄漏才是治本。

2. [进阶]`-XX:+HeapDumpOnOutOfMemoryError` 的作用?
- A) 打印 GC 日志　B) OOM 发生时自动导出 `.hprof` 堆转储文件,用于事后分析　C) 设置最大堆大小　D) 开启 JFR 记录
> [!答案] **2-B**　OOM 瞬间 JVM 自动 dump 堆快照;配合 `-XX:HeapDumpPath=/data/dump` 指定路径。**举一反三**:没有这个参数,OOM 后无法分析——dump 是"案发现场快照",错过了就没了;生产环境**必须配**。

3. [深入]MAT(内存分析工具)的 Dominator Tree(支配树)用来做什么?
- A) 显示类继承关系　B) 计算"每个对象及其独占的内存量"——快速找到谁占了大头内存　C) 显示线程调用栈　D) 查询数据库
> [!答案] **3-B**　支配树按"支配者→被支配者"排列,计算每个对象独占(Retained)的内存量;通常排在第一个的就是"内存大户",顺着引用链找到持有它的 GC Root。**举一反三**:配合 Leak Suspects 报告,MAT 自动列出嫌疑——HashMap 里的静态字段独占 82% 堆,一眼看穿。

4. [基础]GC Root 不包括以下哪一项?
- A) `static` 字段引用的对象　B) 活线程的 `ThreadLocalMap` 中的值　C) 方法局部变量(当前调用栈)　D) 堆中互相引用的普通对象(无 GC Root 可达)
> [!答案] **4-D**　GC Root 包括:静态字段、活线程 ThreadLocalMap、JNI 引用、当前栈帧局部变量等。普通堆对象互相引用但无 Root 可达→不可达→可 GC。**举一反三**:"有引用链到 GC Root"= 可达,GC 不敢回收——即使这对象已经没用了(泄漏的本质)。

5. [进阶]线程池中 `ThreadLocal` 不调用 `remove()` 为什么导致内存泄漏?
- A) ThreadLocal 自动清理　B) 线程池的线程是长期复用的——它的 `ThreadLocalMap` 里挂的 value 永远不会自动清,每处理一个请求攒一个,越攒越多　C) 不影响　D) GC 会自动回收
> [!答案] **5-B**　线程池线程不销毁→ThreadLocalMap 不回收→value 被强引用拴着→GC 不敢动→泄漏。**举一反三**:不仅泄漏——线程复用还会"数据串味":上一个请求残留的 User 对象被下一个请求 get 到,轻则数据错,重则越权。铁律:**谁 set,谁在 finally 里 remove**。

6. [深入]`jmap -histo:live <pid>` 中 `:live` 的含义?
- A) 只显示活着的进程　B) 统计前先触发一次 Full GC,只统计**活对象**,排除垃圾　C) 实时更新　D) 显示线程
> [!答案] **6-B**　`:live` 先 GC 再统计,得到"真正被引用的对象"的直方图——看哪类对象**数量异常多**(如 480 万个 Order),即泄漏的第一嗅觉。**举一反三**:不加 `:live` 会包含垃圾对象,干扰判断;但 `:live` 的 GC 可能耗时,线上慎用。

7. [基础]三种 OOM 类型:堆(`Java heap space`)、元空间(`Metaspace`)、直接内存(`Direct buffer memory`),各自的常见元凶?
- A) 都一样　B) 堆=对象太多,元空间=类定义太多(动态代理/CGLIB),直接内存=NIO ByteBuffer 未释放　C) 全都是因为 `-Xmx` 太小　D) 只与 GC 有关
> [!答案] **7-B**　堆 OOM:查 MAT 找大对象;元空间 OOM:类加载过多(动态代理、Groovy)、`-XX:MaxMetaspaceSize` 太小;直接内存 OOM:NIO `ByteBuffer.allocateDirect()` 未释放、`-XX:MaxDirectMemorySize` 未设。**举一反三**:直接内存 OOM 不体现在堆内存监控中——堆曲线正常但进程内存持续涨,用 `jcmd <pid> VM.native_memory` 定位。

8. [进阶]`LinkedHashMap` 的 `removeEldestEntry()` 可用来做什么?
- A) 加密数据　B) 实现 LRU 缓存——当 `size() > maxSize` 时自动淘汰最久未用的条目,防止无界膨胀　C) 排序　D) 连接数据库
> [!答案] **8-B**　重写 `removeEldestEntry()` 返回 `size() > 1000`,当 Map 超过 1000 条时自动删除最早插入的,实现"有界缓存"。**举一反三**:生产用 Caffeine 更专业(支持过期、容量、统计);手写 LRU 仅适合极小场景。核心原则:**任何缓存都必须有容量上限**。

9. [深入]`WeakHashMap` 和普通 `HashMap` 的区别?
- A) 性能更好　B) key 是弱引用——当 key 对象没有其他强引用时,GC 可回收该条目　C) value 也是弱引用　D) 线程安全
> [!答案] **9-B**　`WeakHashMap` 的 key 被 `WeakReference` 包装,key 无其他强引用时可被 GC 回收;GC 后自动删除对应条目。**举一反三**:不能当缓存主力——回收时机不可控,且 value 仍是强引用(若 value 引用 key 照样泄漏);适合作"用完即弃"的元数据映射。

10. [综合]线上服务堆内存"锯齿逐日抬高"(每次 Full GC 后最低点也在上升),GC 越来越频繁但始终不 OOM。这提示什么?
- A) 服务正常　B) 内存泄漏的**经典前兆**——对象在慢慢攒,GC 回收回来的越来越少,迟早 OOM;应立即 dump 分析　C) 堆太小调大即可　D) 只是 GC 配置问题
> [!答案] **10-B**　锯齿逐日抬高 = 每次 GC 后残留的"顽固对象"越来越多。调大堆只是延缓爆炸;根因是泄漏。`jmap -dump`→MAT 看谁在持续膨胀→定位 GC Root→修复。**举一反三**:用 `-XX:+HeapDumpOnOutOfMemoryError` 只能抓到爆炸瞬间;渐进泄漏在 OOM 前主动 `jmap -dump` 抓快照,和几天前的快照对比,膨胀的对象类一目了然。

### 二、解答题(3 道)
1. [概念]用自己的话解释:"有 GC 为什么还会内存泄漏?"说明 GC 的设计局限和泄漏的本质。
> [!答案] **1**　GC 只能回收"不可达"对象——从 GC Root 出发,没有任何引用链能到达的,视为垃圾。泄漏的本质:**对象已经没用(逻辑上),但仍有一条引用链连到 GC Root**(如 static Map 里的 key),GC 判定"有人引用=还要用",不敢回收。GC 不知道你的"业务意图",它只看"引用链"——这不是 GC 的 bug,是设计的边界:GC 管**可达性**,不管**可用性**。**举一反三**:经典泄漏场景:①静态集合只增不删;②ThreadLocal 不 remove;③Listener 注册后不注销;④连接/流未 close。记住:任何"长生命周期对象持有短生命周期对象引用"的操作,都是泄漏隐患。

2. [场景]线上突然收到 OOM 报警(k8s Pod 重启)。你手边只有 `kubectl` 和 JDK 自带工具。描述从定位到分析的全流程,并指出 OOM 自动 dump 文件该去哪找。
> [!答案] **2**　①确认:查 Pod 重启记录 `kubectl describe pod` 看 Exit Code(137=OOMKilled, 1=OOMError)。②找 dump:如果配了 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump`,dump 文件在容器的 `/data/dump/` 下(或用持久卷)。③复制出来:`kubectl cp <pod>:/data/dump/java_pid.hprof ./dump.hprof`。④MAT 打开:先看 Leak Suspects→定位大对象类→Dominator Tree 找到持有者→Path to GC Roots 看引用链→定位是哪个 static 字段/ThreadLocal/缓存持有了它。⑤代码层面:搜该字段的所有 `put`/`add` 位置,检查是否有对应的 `remove`/清理逻辑。**举一反三**:没配自动 dump 时,用 `jmap -dump:live,format=b,file=dump.hprof <pid>` 手动导(注意 `:live` 会 GC,可能改变现场);容器环境 PID 通常是 1(主进程)。

3. [综合]从"设计阶段预防"和"运行时监控"两个角度,阐述如何建立防内存泄漏的体系。
> [!答案] **3**　①设计预防:缓存用 Caffeine/Redis(天然有容量上限);ThreadLocal 用 `try-finally remove` 模板或用 `AutoCloseable` 封装;静态集合用 `Collections.synchronizedMap(new LinkedHashMap(){removeEldestEntry})` 封顶;连接/流用 try-with-resources;监听器注册配注销。②监控:JVM 指标(Micrometer 暴露堆使用率、GC 频率)→普罗米修斯→Grafana 曲线;"堆锯齿逐日抬高"设告警;`-XX:+HeapDumpOnOutOfMemoryError` 生产必配;定期(如每周)导出 Heap Histogram 对比差异。**举一反三**:测试层面——缓存封顶测试(塞 10 万条,断言 size ≤ 1000)、ThreadLocal 清理测试(request 完断言 get()==null),这些进 CI 门禁,预防回归。

### 三、代码题(2 道)
1. [基础]写一段代码故意触发 `Java heap space` OOM:不断往 ArrayList 加 1MB 的 byte[] 直到堆满。给出 JVM 启动参数(含自动 dump)和预期输出。
> [!答案] **1 验收**:
> ```java
> // 启动参数: -Xmx16m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./heap.hprof
> public class OomDemo {
>     public static void main(String[] args) {
>         var list = new ArrayList<byte[]>();
>         while (true) list.add(new byte[1024*1024]); // 每次 1MB
>     }
> }
> // 输出: java.lang.OutOfMemoryError: Java heap space
> //       Dumping heap to ./heap.hprof ...
> ```
> **举一反三**:拿到 dump 用 MAT → Leak Suspects → 直接指出 `ArrayList`→`byte[]` 占了几乎全部堆——这是最简单的泄漏模型,真实的泄漏链可能多层嵌套。

2. [综合]写两个测试:①缓存有界测试——往 LRU 缓存塞 10 万条记录,断言 size ≤ 1000;②ThreadLocal 清理测试——模拟请求前后 set/remove,断言 remove 后 get() 为 null。将两个测试配上 `@RepeatedTest` 确保稳定性。
> [!答案] **2 验收**:
> ```java
> class LruCache<K,V> extends LinkedHashMap<K,V> {
>     private final int max;
>     LruCache(int max) { super(16,0.75f,true); this.max=max; }
>     @Override protected boolean removeEldestEntry(Map.Entry<K,V> eldest) {
>         return size() > max;
>     }
> }
> 
> @Test void cacheIsBounded() {
>     var cache = new LruCache<String,String>(1000);
>     for (int i=0; i<100_000; i++) cache.put("k"+i, "v"+i);
>     assertTrue(cache.size() <= 1000, "缓存必须封顶,防泄漏");
> }
> 
> static final ThreadLocal<String> CTX = new ThreadLocal<>();
> @Test void threadLocalClearedAfterRequest() {
>     CTX.set("user-data");
>     try { /* 处理请求 */ } finally { CTX.remove(); }
>     assertNull(CTX.get(), "请求结束 ThreadLocal 须清空");
> }
> ```
> **举一反三**:第二个测试模拟的是**同一个线程**先后处理两个请求的场景——如果不清,第二个请求 get 到第一个请求的"user-data",就是"数据串味" + "内存泄漏"双 Bug。
