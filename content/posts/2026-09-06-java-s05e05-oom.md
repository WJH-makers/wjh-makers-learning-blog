# 《从零开始学 Java》44 · OOM 内存事故(线上事故报告)

> 连载特刊 · 第五季「服务器战争」第 5 话 · 线上事故报告 · 基线 Java 25(最新 LTS)
> 承接:上一话扑灭了 CPU 100% 的死循环。可同一台机器又出事——这次不是 CPU 烧,是内存慢慢涨到爆。

---

## 一、事故:内存只涨不落,最后 OOM

> **事故报告 · INC-0931**
> 时间:连续三天 · 现象:coffee-api 堆内存**锯齿逐日抬高**——每次 Full GC 后的最低点也在往上爬,GC 越来越频繁,第三天 02:14 抛出 `OutOfMemoryError: Java heap space`,进程僵死。
> 反常点:重启后一切正常,**跑几天又复现**。典型的"慢性病"。

豆豆:「CPU 那种是急性病,一个 `jstack` 抓现行。内存泄漏是**慢性病**——它不是一次分配了超大对象,而是**有些对象本该被回收,却被人死死攥着不放**,一天天攒,攒到堆装不下。Java 有 GC,可 GC 只回收『没人引用』的对象;**只要还有一根引用链拴着它,GC 就不敢动**。查这种病,靠 `jmap` 把堆『拍张 X 光片』,再用 MAT 看谁在攥着不放。」

## 二、漫画 · 揪住攥着东西不放的手

> **〔1〕** 咖啡站仓库,GC 清洁队推着车来收垃圾。大部分空杯子一收就走,可角落有一堆杯子被一根根**看不见的绳子**拴在墙上,清洁队拽了半天拽不动,只能绕开。
> GC 清洁队长:「这些……还有绳子连着,按规矩我不能收。」

> **〔2〕** 顺着绳子往上看,墙上钉着两颗钉子:一颗是**静态缓存 Map**(`static` 藤蔓),越长越粗,把所有进来的订单全缠住不放;另一颗是 **ThreadLeak 藤蔓**——线程池里的工人干完活走了,却把随身的 `ThreadLocal` 小背包忘在了椅子上,下一个工人坐上来又挂一个。
> 阿零:「工人明明下班了,背包怎么还在?!」

> **〔3〕** 豆豆掏出一台**X 光机**(`jmap`),对着仓库"咔嚓"一拍,导出一张堆快照 `.hprof`。
> 豆豆(叼豆子):「肉眼看不出谁在攥着,拍片子就看得清清楚楚——**哪类对象最多、被谁一路引用到 GC Root**。」

> **〔4〕** 片子(MAT)在屏幕上摊开,一条刺眼的红线**支配树**直指那颗 `static` 藤蔓:它一个人占了 82% 的堆。
> 豆豆:「找到了。**能被 GC 回收的叫垃圾,不能被回收又没用的,叫泄漏。**」

## 三、本话目标

- 建立"内存泄漏 = 对象该死不死、引用链拴着 GC Root"的心智;
- 掌握内存排障链路:自动 dump / `jmap` 导堆 → `jmap -histo` 速览 → MAT 看支配树与泄漏嫌疑;
- 揪出两个经典泄漏:线程池里 `ThreadLocal` 未 `remove`、静态集合无上限膨胀;
- 分清**内存泄漏(Leak)** 与 **内存溢出(OOM)** 的因果;
- 修好它们,并用测试给缓存和 `ThreadLocal` 上界/上锁。

## 四、排障链路:给堆拍片,再顺引用链断案

```text
第 0 步  启动就挂上保险:-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump
         → OOM 那一刻 JVM 自动导出 .hprof,不用你半夜手忙脚乱

第 1 步  jmap -histo:live <pid>   活对象直方图,速览"哪类对象数量/占用异常多"
第 2 步  jmap -dump:live,format=b,file=heap.hprof <pid>   导出完整堆快照
第 3 步  用 MAT / VisualVM 打开 heap.hprof
第 4 步  看两样东西:
           · Histogram   —— 哪类对象占内存最多
           · Dominator Tree(支配树)—— 谁"独占"着大块内存不放
           · Leak Suspects —— MAT 自动报告的泄漏嫌疑
第 5 步  顺引用链找到 GC Root(常是某个 static 字段 / 线程 ThreadLocalMap)→ 定位代码

心法:OOM 只是"结果",别只盯着"堆不够大就调大 -Xmx"——
      要问"到底是谁攥着一堆对象不放",那才是"因"。
```

> **豆豆锐评 · 别一 OOM 就无脑调大 `-Xmx`**
> 调大堆只是让"爆炸"晚几天到,泄漏还在持续。真泄漏,给多大堆都会满。`-Xmx` 该调的场景是"业务确实需要这么多内存"(容量问题);而"锯齿逐日抬高"是**泄漏**(Bug 问题)——两者的区别,就是这一话要教你分辨的。

## 五、命令:从直方图到支配树

**第 1 步** —— `jmap -histo:live` 速览(`:live` 会先触发一次 GC,只统计活对象,更准):

```text
$ jmap -histo:live 12345 | head -n 8

 num     #instances         #bytes  class name (module)
-------------------------------------------------------
   1:       4821037       193M      com.coffee.model.Order
   2:       4821040        154M      java.util.HashMap$Node
   3:       4821051         115M      java.lang.String
   4:            128          8M      byte[]
   5:           2033          1M      java.lang.Class
```

`Order` 对象竟有 480 万个、占 193M——一个只服务几百顾客的咖啡站,怎么会积了几百万订单在堆里?**数量异常 = 泄漏的第一嗅觉。**

**第 2 步** —— 导出完整堆(OOM 时其实已由 `-XX:+HeapDumpOnOutOfMemoryError` 自动生成):

```text
$ jmap -dump:live,format=b,file=heap.hprof 12345
Dumping heap to /data/dump/heap.hprof ...
Heap dump file created [1284 MB]
```

**第 3~4 步** —— MAT 打开,`Leak Suspects` 报告直接点名:

```text
Problem Suspect 1
  One instance of "com.coffee.OrderCache" loaded by "jdk.internal.loader.ClassLoaders$AppClassLoader"
  occupies 1,061,320,984 bytes (82.34%).
  The memory is accumulated in "java.util.HashMap" —— the field "orders" (a static field).
  Keywords: com.coffee.OrderCache, java.util.HashMap
```

支配树顺着 `OrderCache.orders`(一个 `static HashMap`)一路展开,发现它把每一笔历史订单都塞了进去、**从不删除**。GC Root 是那个 `static` 字段——静态字段的生命周期和类一样长,**类不卸载,它就永远活着**,拴着的 480 万个 `Order` 自然一个都回收不掉。

## 六、故意制造两个 Bug:静态缓存 + ThreadLocal

**Bug 1 · 只进不出的静态缓存**(第五节直方图的元凶):

```java
public class OrderCache {
    // static 生命周期 = 整个应用;只 put 不 evict,等于一个"内存黑洞"
    private static final Map<String, Order> orders = new HashMap<>();

    public static void record(Order o) {
        orders.put(o.id(), o);   // 每笔订单都塞进来,永不清理 → 越堆越多
    }
}
```

**Bug 2 · 线程池里忘了 `remove` 的 ThreadLocal**(和上一话的线程池呼应):

```java
public class UserContext {
    private static final ThreadLocal<User> CURRENT = new ThreadLocal<>();

    public static void set(User u) { CURRENT.set(u); }
    public static User get()       { return CURRENT.get(); }
    // ← 少了 remove()!在线程池里这是灾难
}
```

请求处理时 `UserContext.set(user)`,处理完**没有** `remove()`。放到单次运行的程序里没事(线程结束就回收),可在**线程池**里,工人线程是**长期复用**的——它的 `ThreadLocalMap` 里挂着的 `User` 永远不被清,每处理一个用户就攒一个,越攒越多。

---

## 七、读懂现象 + 修复:给缓存设界,给 ThreadLocal 收尾

**修 Bug 1**——静态缓存必须**有上限 + 淘汰策略**。最小改造用 `LinkedHashMap` 做 LRU:

```java
public class OrderCache {
    // 有界 LRU:超过 1000 条,自动淘汰最久未用的,内存封顶
    private static final Map<String, Order> orders =
        java.util.Collections.synchronizedMap(new LinkedHashMap<>(16, 0.75f, true) {
            @Override protected boolean removeEldestEntry(Map.Entry<String, Order> e) {
                return size() > 1000;   // 关键:让 Map 自己吐出旧数据
            }
        });

    public static void record(Order o) { orders.put(o.id(), o); }
}
```

**修 Bug 2**——`ThreadLocal` 用完必须在 `finally` 里 `remove()`,尤其在线程池:

```java
try {
    UserContext.set(currentUser);
    handleRequest();
} finally {
    UserContext.remove();   // 🔑 归还工人的"小背包",线程复用前清空
}
```

改完连跑三天,堆内存的锯齿最低点**稳定不再抬高**——泄漏止住了。

> **豆豆锐评 · ThreadLocal 在线程池里,不 remove 就是定时炸弹**
> 两层危害:① **内存泄漏**——工人线程常驻,`ThreadLocalMap` 里的 value 一直被强引用,回收不掉;② **数据串味**——线程复用时,上一个请求残留的 `User` 会被下一个请求 `get` 到,轻则数据错乱,重则**用户 A 看到用户 B 的信息**(越权),这比泄漏更可怕。所以铁律:**`ThreadLocal` 谁 `set`,谁在 `finally` 里 `remove`**。

> **🔀 豆豆的多解台 · 缓存怎么才不泄漏?**

| 方案 | 写法 | 适合什么时候 | 坑 |
|---|---|---|---|
| 手写 LRU | `LinkedHashMap` + `removeEldestEntry` | 简单本地缓存,零依赖 | 需自己保证线程安全;功能单薄 |
| `WeakHashMap` | key 弱引用,GC 可回收 | key 是"用完即弃"的对象 | value 仍强引用;回收时机不可控,别当缓存主力 |
| Caffeine | `Caffeine.newBuilder().maximumSize(n)` | **生产本地缓存首选** | 引依赖;但过期/淘汰/统计全给你了 |
| Redis | 缓存放进程外 | 多实例共享、缓存量大 | 网络开销;需运维一套 Redis |

豆豆锐评:**生产本地缓存直接上 Caffeine**(自带容量上限、过期、命中率统计,天然防泄漏);只有"教学演示/极简场景"才手写 `LinkedHashMap`。核心原则就一句——**任何缓存都必须有上限**,无界缓存 = 内存泄漏预定。

> **🎯 面试直击**:有 GC 为什么还会内存泄漏?内存泄漏和内存溢出啥区别?
> **泄漏(Leak)**是"因":对象已经没用了,却仍被一条引用链拴到 **GC Root**(常见 Root:`static` 字段、活线程的 `ThreadLocalMap`、正在用的局部变量),GC 判定它"还有人引用"就不敢回收,于是越积越多。**溢出(OOM)**是"果":泄漏攒到堆装不下,抛 `OutOfMemoryError`。GC 只负责回收"不可达"对象,它**没法判断"可达但你其实不想要了"**——那是程序的逻辑责任。经典泄漏源:未 `remove` 的 `ThreadLocal`、无界的 `static` 集合、忘了关的连接/流、监听器只注册不注销。

## 八、用测试钉死:缓存有界 + ThreadLocal 归零

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class LeakGuardTest {
    @Test
    void cache_is_bounded() {
        for (int i = 0; i < 100_000; i++) {          // 猛塞 10 万条
            OrderCache.record(new Order("id-" + i, "美式", 1));
        }
        assertTrue(OrderCache.size() <= 1000,         // 必须被 LRU 封在 1000 以内
                "缓存必须有上限,否则就是内存泄漏");
    }

    @Test
    void threadlocal_cleared_after_request() {
        UserContext.set(new User("alice"));
        try { /* 处理请求 */ } finally { UserContext.remove(); }
        assertNull(UserContext.get(), "请求结束后 ThreadLocal 必须为空");
    }
}
```

`cache_is_bounded` 是防泄漏的核心断言:塞 10 万条,存活必须 ≤ 1000。回退到无界 `HashMap` 版,这个测试立刻红——**把"内存会不会涨"变成一条能自动跑的红线**。

## 🎯 随堂练习

先自己做,再对答案。每道答案都带一句「举一反三」,帮你把这一个点连成一片。

### 选择题(10 道)

1. 内存泄漏(Leak)和内存溢出(OOM)的关系是?
   - A) 同一个东西　B) 泄漏是「因」(对象没用了却仍被引用链拴着 GC Root),溢出是「果」(攒到堆装不下)　C) 溢出导致泄漏　D) 两者无关
2. 有 GC 为什么还会内存泄漏?
   - A) GC 有 bug　B) GC 只回收**不可达**对象,它没法判断「可达但你其实不想要了」　C) GC 太慢　D) 只有老版本 JVM 会
3. 下列**不属于**常见 GC Root 的是?
   - A) `static` 字段　B) 活线程的 `ThreadLocalMap`　C) 正在使用的局部变量　D) 已被置为 null 的成员变量
4. 生产环境应该提前挂上的 OOM 保险是?
   - A) `-Xmx` 调到最大　B) `-XX:+HeapDumpOnOutOfMemoryError` + `-XX:HeapDumpPath`,OOM 那一刻自动导出 `.hprof`　C) 关闭 GC 日志　D) 定时重启
5. `jmap -histo:live` 里 `:live` 的作用是?
   - A) 实时刷新　B) 先触发一次 GC,只统计**活对象**,结果更准　C) 只看大对象　D) 输出到文件
6. MAT 的「支配树(Dominator Tree)」告诉你什么?
   - A) 对象创建顺序　B) 谁「独占」着大块内存不放　C) 类继承关系　D) GC 次数
7. `ThreadLocal` 在线程池里不 `remove`,除了内存泄漏还有什么危害?
   - A) 没有别的　B) **数据串味** —— 线程复用时上个请求残留的值被下个请求读到,可能造成越权　C) 线程无法回收　D) 触发死锁
8. 遇到「堆内存锯齿最低点逐日抬高」,正确的第一反应是?
   - A) 直接把 `-Xmx` 调大　B) 这是**泄漏**信号,该导堆分析找谁攥着对象不放　C) 重启服务　D) 换 GC 收集器
9. 静态缓存 `static Map` 只 put 不清理,问题在于?
   - A) 查询变慢　B) `static` 生命周期和类一样长,拴住的对象一个都回收不掉,等于内存黑洞　C) 线程不安全　D) 占用元空间
10. 关于缓存,本话给出的核心原则是?
    - A) 缓存越大越好　B) **任何缓存都必须有上限**,无界缓存 = 内存泄漏预定　C) 用 `WeakHashMap` 就万无一失　D) 缓存要放在栈上

> [!答案]
> **1-B**　因果要分清才知道该修哪。**举一反三**:所以「OOM 了就调大堆」是治果不治因,泄漏还在持续。
> **2-B**　可达 ≠ 有用。**举一反三**:这是「有 GC 为何还泄漏」的标准答案,也是理解所有泄漏场景的钥匙。
> **3-D**　已置 null 的字段不再是引用来源。**举一反三**:很多「手动置 null」的老技巧,本质就是主动切断到 GC Root 的引用链。
> **4-B**　半夜出事不用手忙脚乱。**举一反三**:这个参数几乎零开销,应该成为生产启动脚本的标配。
> **5-B**　只看活对象才有意义。**举一反三**:不加 `:live` 会把待回收的垃圾也算进去,容易误判。
> **6-B**　它回答「谁在攥着内存」。**举一反三**:配合 Leak Suspects 报告,MAT 往往能直接点名那个 static 字段。
> **7-B**　串味比泄漏更可怕。**举一反三**:用户 A 看到用户 B 的信息 —— 这是真实发生过的线上事故类型,所以 `remove` 是铁律。
> **8-B**　锯齿抬高是泄漏的经典画像。**举一反三**:反过来,「锯齿平稳但整体偏高」通常是容量问题,那才该考虑调 `-Xmx`。
> **9-B**　类不卸载,静态字段就永远活着。**举一反三**:所以往静态集合里放东西之前,先想清楚「什么时候删」。
> **10-B**　无界即泄漏。**举一反三**:生产本地缓存直接上 Caffeine —— 容量上限、过期、命中率统计一次给全。
