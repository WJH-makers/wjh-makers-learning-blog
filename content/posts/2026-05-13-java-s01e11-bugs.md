## 三、本话目标

- 认清三类 Bug 的不同表现:编译期拦 / 结果悄悄错 / 运行期崩;
- 读懂现代 JDK 的「详细空指针」报错;
- **独立**跑完五步排障法,不靠别人给答案;
- 记住:逻辑 Bug 无栈、无报错,唯一防线是**测试 + 边界思考**。

## 四、原理图:三种 Bug 怪的弱点

```text
类型         什么时候发作     谁来抓             致命弱点
─────────────────────────────────────────────────────────
Syntax Bug   编译就过不去     编译官(error:…)   报错带行号,顺藤摸瓜最好抓
Logic  Bug   能跑,结果错     没人报!靠测试+脑   最阴险:无栈无报错,只能想清边界
Null 幽灵    运行到一半崩     JVM(NPE)          现代 JDK 会点名 "xxx" is null
```

五步排障法(阿零这次全程照着念的):

```text
① 观察现象 —— 它到底表现成什么样?崩了?算错了?还是编译不过?
② 收集报错 —— 有报错就读全,行号、异常名、"because…"一个都别漏
③ 提出假设 —— 「我怀疑是 X」
④ 只改一处 —— 一次只动一个变量,否则治好了也不知道是谁的功劳
⑤ 重跑验证 —— 好了?进行下一个。没好?回到 ③ 换假设
```

## 五、代码:一段带三处伤的下单逻辑

```java
public class Cafe {
    static double priceOf(int choice) {
        return switch (choice) {
            case 1 -> 15.0;
            case 2 -> 18.0;
            default -> 20.0;
        };
    }

    public static void main(String[] args) {
        int qty = 3;
        double total = priceOf(1) * qty      // ① 语法:少了分号
        double paid = 40.0;

        if (paid > total) {                  // ② 逻辑:钱刚好等于时也该出杯,应为 >=
            System.out.println("出杯");
        }

        String note = null;
        System.out.println("备注长度:" + note.length());   // ③ Null:对 null 调 length()
    }
}
```

---

## 六、阿零独立排障

**① 语法 Bug**——阿零:「先编译,连门都没进就被拦。观察现象:编译官甩报错;收集报错:」

```text
Cafe.java:13: error: ';' expected
        double total = priceOf(1) * qty
                                      ^
```

「`';' expected`,箭头顶在第 13 行末尾——假设:漏了分号。**只改这一处**,补上 `;`,重跑。过了。下一个。」

**② 逻辑 Bug**——阿零:「这只灰怪不报错,程序跑得好好的,可我付 40、总价 40,它偏不出杯。没有报错能读,那就**自己想边界**:`paid > total`,当 `paid == total`(刚好付够)时是 `false`——顾客付了整钱却被拒。假设:该用 `>=`。改这一处。」这类 Bug **编译和运行都不吭声**,只能靠想清楚边界、或写测试逼它现形。

**③ Null 幽灵**——阿零:「跑到第三步才崩。收集报错:」

```text
Exception in thread "main" java.lang.NullPointerException:
        Cannot invoke "String.length()" because "note" is null
        at Cafe.main(Cafe.java:20)
```

「现代 JDK 太贴心了,它**直接点名**:`because "note" is null`。`note` 是 `null`,对 `null` 调 `.length()` 必崩。假设成立。给它一个有意义的默认值:`String note = "";`」

---

## 七、修复后

```java
double total = priceOf(1) * qty;      // ① 补分号
if (paid >= total) { ... }            // ② 改 >=
String note = "";                     // ③ 不再是 null
```

三处修好,程序正常出杯、打印「备注长度:0」。阿零全程**只改了三处、每处只改一个变量**——这正是五步法第 4 步的纪律。

## 八、用测试守住那只最阴险的

语法和 Null 会「吵着」暴露:一个编译不过、一个当场崩,想漏都难。真正阴险的是 **Logic Bug**——它无栈、无报错、不崩溃,只是安安静静地算错账,可能上线三个月才被财务发现对不上。

> **豆豆锐评**:记死这句——**逻辑 Bug 没有栈、没有报错,你唯一的防线是「测试 + 边界思考」**。报错会自己跳出来找你;逻辑错要你主动出击去逼它。所以「刚好付够」这种边界,必须钉一个测试守住:

```java
static boolean shouldServe(double paid, double total) {
    return paid >= total;   // 关键边界:相等也要出杯
}

@Test
void serve_when_exactly_paid() {
    assertTrue(Cafe.shouldServe(45.0, 45.0));   // 若手滑写成 >,这行立刻变红
}
```

这个测试就是那只灰怪的「防复发疫苗」:哪天有人手滑把 `>=` 改回 `>`,红灯当场亮起——比等财务对账早三个月。JUnit 质检员的口头禅又对上了:「**证据呢?**」

> **🎯 面试直击**:NullPointerException 是怎么来的,怎么防?
> **对一个 `null` 引用调用方法或访问字段**就抛 NPE。防线:① 变量给合理默认值(如空串、空集合)而非 null;② 用 `Objects.requireNonNull` 在入口尽早拦;③ 用 `equals` 时把已知非 null 的常量写前面。追问点:`Optional` 是更系统的「可能没有值」的表达(第二季讲)。现代 JDK 的**详细 NPE 报错**会点名是哪个变量为 null,排查快很多。

## 🎯 随堂练习

先自己做,再对答案。每道答案都带一句「举一反三」,帮你把这一个点连成一片。

### 选择题(10 道)

1. 三类 Bug 的发作时机,正确的对应是?
   - A) Syntax 运行期 / Logic 编译期 / Null 运行期　B) Syntax 编译期 / Logic 能跑但结果错 / Null 运行期崩　C) 三者都在运行期　D) 三者都能被编译器拦下
2. 五步排障法的正确顺序是?
   - A) 提出假设 → 观察现象 → 改代码 → 重跑 → 收集报错　B) 观察现象 → 收集报错 → 提出假设 → 只改一处 → 重跑验证　C) 重跑 → 观察 → 全改一遍 → 收集报错 → 假设　D) 收集报错 → 全部一起改 → 重跑
3. 第 4 步「只改一处」的理由是?
   - A) 改多了编译慢　B) 一次只动一个变量,否则治好了也不知道是谁的功劳　C) IDE 只支持单处修改　D) 避免冲突
4. `Cannot invoke "String.length()" because "note" is null` 这条报错的价值在于?
   - A) 告诉你哪一行崩了　B) 现代 JDK 直接**点名**是哪个变量为 null,不用再逐个排查　C) 提示该加 try-catch　D) 说明 JVM 出了故障
5. `if (paid > total)` 这个逻辑 Bug 的表现是?
   - A) 编译不过　B) 抛异常　C) 顾客刚好付够(`paid == total`)时被拒绝出杯　D) 多找了钱
6. 为什么说 Logic Bug 最阴险?
   - A) 它会让程序崩溃　B) 它无栈、无报错、不崩溃,可能上线三个月才被财务发现　C) 它只在生产环境出现　D) 它会传染给别的模块
7. 对付逻辑 Bug 唯一的防线是?
   - A) 更严格的编译器　B) 测试 + 边界思考　C) 多写 try-catch　D) 加日志
8. `';' expected` 属于哪一类 Bug?
   - A) Syntax Bug,编译期就被拦下　B) Logic Bug　C) 运行期异常　D) 环境问题
9. 防 NPE 的做法中,**不属于**本话给出的是?
   - A) 变量给合理默认值(空串、空集合)而非 null　B) 用 `Objects.requireNonNull` 在入口尽早拦　C) 用 `equals` 时把已知非 null 的常量写前面　D) 把所有代码用 `try-catch(Exception)` 包起来
10. `assertTrue(Cafe.shouldServe(45.0, 45.0));` 这个测试的作用是?
    - A) 提高覆盖率好看　B) 当「防复发疫苗」:哪天有人把 `>=` 手滑改回 `>`,红灯当场亮　C) 让程序跑更快　D) 替代边界思考

> [!答案]
> **1-B**　编译期拦 / 悄悄算错 / 运行期崩,三种发作方式对应三种抓法。**举一反三**:拿到问题先归类,再选工具 —— 归错类就会一路查错方向。
> **2-B**　观察 → 收集 → 假设 → 只改一处 → 重跑。**举一反三**:这套框架也是面试「你怎么定位一个线上问题」的标准答题结构。
> **3-B**　一次动多处,治好了也不知道是哪一步起的作用。**举一反三**:这也是科学实验的控制变量法,排障和做实验本质相同。
> **4-B**　详细 NPE 会点名变量,排查速度天差地别。**举一反三**:这是 JDK 14 引入(JEP 358)、后续默认开启的能力,老 JDK 只会甩你一行光秃秃的 NPE。
> **5-C**　`>` 把「刚好付够」判成不够。**举一反三**:所有 `>` / `>=`、`<` / `<=` 的边界都值得单独写一个测试钉死。
> **6-B**　它安安静静地算错账,没有任何东西提醒你。**举一反三**:报错会自己跳出来找你,逻辑错要你主动出击去逼它现形。
> **7-B**　编译官和 JVM 都指望不上,只能靠测试和边界思考。**举一反三**:所以「写完代码顺手补一个边界测试」的收益,远高于事后调试。
> **8-A**　连编译都过不去,报错还带行号。**举一反三**:语法错误是最好抓的一类 —— 顺着行号和箭头就能到现场。
> **9-D**　用 `catch(Exception)` 兜住一切只会掩盖问题,不是防线。**举一反三**:吞异常是工程大忌,第三季会专门讲「异常该抛该catch的边界在哪」。
> **10-B**　它是那只灰怪的防复发疫苗,比等财务对账早三个月。**举一反三**:每修一个 Bug 都补一个测试,你的测试集会慢慢长成一张「历史事故地图」。
