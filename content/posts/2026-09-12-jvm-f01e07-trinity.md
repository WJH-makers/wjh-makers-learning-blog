## 🔑 核心设计：三件套分工

| 件套 | 职责 | 语言特性 |
|---|---|---|
| sealed interface | **封闭类型空间**：只有白名单里的类型合法 | `sealed` + `permits`（JDK 17） |
| record 子类型 | **携带数据**：每种规则的参数声明即规格，不可变 | `record`（JDK 16） |
| 穷尽 switch | **处理逻辑**：一张决策表，新类型漏处理编译失败 | switch 模式匹配（JDK 21） |

三件套的设计哲学被称为**数据导向编程（Data-Oriented Programming）**：
- 数据（record）与行为（switch 函数）分离，不强耦合到类层次
- 新增类型 = 打开白名单 + 补 switch 分支，影响面明确、可追踪
- 与 OOP 的"行为封装进类"形成互补，各有适用场景

## ⚙️ 代码实录：促销引擎完整实现

```java
// javac -encoding UTF-8 --release 25 PromoEngine.java
// ─── 数据模型层 ────────────────────────────────────────
sealed interface DiscountRule permits FixedOff, PercentOff, FreeItem, BuyXGetY {}
record FixedOff(int cents)               implements DiscountRule {}  // 直减 N 分
record PercentOff(int percent)           implements DiscountRule {}  // 打折 N%（1-100）
record FreeItem(String name)             implements DiscountRule {}  // 赠品，价格不变
record BuyXGetY(int buyQty, int freeQty) implements DiscountRule {}  // 买 X 赠 Y

sealed interface MenuItem permits CoffeeItem, TeaItem {}
record CoffeeItem(String name, int cents) implements MenuItem {}
record TeaItem(String name, int cents)    implements MenuItem {}

// ─── 促销引擎 ─────────────────────────────────────────
class PromoEngine {
    // 返回最终应付分（1元=100分）
    static int finalPrice(MenuItem item, DiscountRule rule) {
        // 从 MenuItem 解构出基础价格（穷尽，不需要 default）
        int base = switch (item) {
            case CoffeeItem c -> c.cents();
            case TeaItem t    -> t.cents();
        };
        // 根据促销规则计算（穷尽，漏掉任何一种 → 编译报错）
        return switch (rule) {
            case FixedOff(int off)               -> Math.max(0, base - off);
            case PercentOff(int pct)             -> base * pct / 100;
            case FreeItem(String _)              -> base;         // 价格不变，赠品另算
            case BuyXGetY(int buy, int free)
                when buy > 0 && free > 0         -> base * buy / (buy + free);
            case BuyXGetY(_, _)                  -> base;         // 参数非法时原价
        };
    }

    public static void main(String[] args) {
        var latte = new CoffeeItem("拿铁", 2800);    // 28.00 元
        System.out.println("直减200: "  + finalPrice(latte, new FixedOff(200)));    // 2600
        System.out.println("8折: "      + finalPrice(latte, new PercentOff(80)));   // 2240
        System.out.println("赠品杯: "    + finalPrice(latte, new FreeItem("小杯"))); // 2800
        System.out.println("买2赠1: "   + finalPrice(latte, new BuyXGetY(2, 1)));   // 1866
    }
}
```

**实测输出**（GraalVM 25.0.4）：

```
直减200: 2600
8折: 2240
赠品杯: 2800
买2赠1: 1866
```

## 🚨 三件套的三道守卫

### 守卫 1：sealed 拦截非法子类

```java
// 促销主管想偷加「买咖啡赠保险」
record InsuranceOffer(String plan) implements DiscountRule { ... }
```

```
error: 类不得扩展密封类：DiscountRule（因为它未列在其 'permits' 子句中）
```

### 守卫 2：穷尽 switch 拦截遗漏分支

新增 `FlashSale` 到 permits 白名单，但促销引擎 switch 没跟上：

```java
sealed interface DiscountRule permits FixedOff, PercentOff, FreeItem, BuyXGetY, FlashSale {}
record FlashSale(int durationSecs) implements DiscountRule {}
// 上面的 finalPrice 的 switch 里没有 FlashSale 分支
```

```
error: switch 表达式不包含所有可能的输入值
        return switch (rule) {
               ^
```

### 守卫 3：record 解构支配性检查

带 `when` 守卫的窄分支必须在宽分支之前：

```java
case BuyXGetY(_, _)                  -> base;         // 宽：放前面会支配下一行
case BuyXGetY(int b, int f) when b>0 -> ...;          // 窄：编译报支配性错误
```

```
error: 此 case 标签由前一个 case 标签支配
```

## 📊 旧写法 vs 三件套对比

| 场景 | 旧：普通接口 + instanceof 链 | 新：三件套 |
|---|---|---|
| 新增活动类型 | 开发人员手动找所有 if-else，靠记忆补充 | 编译器自动点名所有遗漏的 switch |
| 非法子类 | 运行时才发现，ClassCastException | 编译时拦截 |
| 规则数据 | 字段散落在实现类中，可变 | record 自带参数，不可变 |
| 代码结构 | 行为与数据混合在类里 | 数据（record）与行为（switch）分离 |
| 适用场景 | 行为多态（不同子类有不同行为实现） | **数据多态（类型不同但处理函数集中）** |

> 焰焰对着 `DiscountRule.class` 和 `PromoEngine.class` 说：「看一眼新旧两个关键字节码结构。」

```bash
# 统一编译
javac -encoding UTF-8 --release 25 PromoEngine.java

# sealed interface 的 PermittedSubclasses 属性
javap -verbose DiscountRule.class

# record 分量（组件）方法列表
javap -p BuyXGetY.class

# 促销引擎方法字节码（switch 模式匹配底层）
javap -c PromoEngine.class
```

**实测 `javap -p BuyXGetY.class`**：

```
final class BuyXGetY extends java.lang.Record implements DiscountRule {
  private final int buyQty;
  private final int freeQty;
  BuyXGetY(int, int);
  public final java.lang.String toString();
  public final int hashCode();
  public final boolean equals(java.lang.Object);
  public int buyQty();     ← record 解构 case BuyXGetY(int buy, int free) 调用此方法
  public int freeQty();    ← 同上
}
```

**`javap -verbose DiscountRule.class` 关键节选**：

```
PermittedSubclasses:
  FixedOff
  PercentOff
  FreeItem
  BuyXGetY
```

**`javap -c PromoEngine.class`，`finalPrice` 方法关键结构**：

```
static int finalPrice(MenuItem, DiscountRule);
  Code:
     ...
     // 第一个 switch（MenuItem）
     invokestatic  typeSwitch    // invokedynamic 引导 sealed MenuItem
     // CoffeeItem/TeaItem 两分支
     ...
     // 第二个 switch（DiscountRule）
     invokestatic  typeSwitch    // invokedynamic 引导 sealed DiscountRule
     // FixedOff/PercentOff/FreeItem/BuyXGetY 分支 + when 守卫跳转
     ...
```

关键观测点：
- 两个 switch 分别用 `invokedynamic typeSwitch` 分发——JVM 在运行时记住类型索引，热身后直接跳转
- `BuyXGetY(int buy, int free)` 解构：编译器生成 `invokevirtual BuyXGetY.buyQty()` + `invokevirtual BuyXGetY.freeQty()` 取值
- `_` 忽略的字段（`FreeItem(String _)` 的 `name`）**不产生 accessor 调用**，字节码里完全消失
- 穷尽性检查：字节码末尾有一个 `athrow MatchException` 的隐式兜底——但只要 sealed 合同不被破坏，这行代码永不执行

## 🗺️ 数据导向编程：什么时候用三件套？

决策树：

- **类型集合固定（或变化可控）？**
  - **否** → 普通接口 / 抽象类
  - **是** → 行为分散到各子类？
    - **是** → OOP 多态（行为封装进类）✅
    - **否** → **三件套** ✅

- **适合三件套**：促销规则、AST 节点、HTTP 响应体、状态机的状态——类型有限、处理函数集中
- **适合 OOP**：UI 组件、插件体系——类型开放、每种类型行为复杂且独立

---

> [!答案]
>
> **Q1. JDK 21。**record（JDK 16 GA）、sealed（JDK 17 GA）、switch 模式匹配 + record 解构（JDK 21 GA）——三件套完整组合的最低版本是 JDK 21。未命名变量 `_` 需 JDK 22。
>
> **Q2. B — HTTP 状态码响应体。**`200 OK / 404 Not Found / 500 Error` 是固定类型集合，处理函数集中（日志、解析、重试策略），适合三件套。其他选项类型开放或行为高度独立，适合 OOP。
>
> **Q3. 区别：`_` 明确声明"name 字段被有意忽略"，`f` 则声明了一个未被使用的变量（编译器可能给 unused 警告）。`_` 更能表达意图——「我知道这里有 name，但不需要它」。**
>
> **Q4. 最小集合：① 在 `permits` 子句加 `FlashSale`；② 新建 `record FlashSale(int durationSecs) implements DiscountRule {}`；③ 在所有穷尽 switch 里补 `case FlashSale(int d) -> ...` 分支。**（缺 ③ 编译即报错，不会漏单）
>
> **Q5. B 正确。**带 `when` 的窄分支必须放在宽分支之前；A 写法中宽分支放在前面，支配了带 `when` 的行，编译报"支配性"错误。
>
> **Q6. `PermittedSubclasses` 属性（JVMS §4.7.31）。**运行时读取：`DiscountRule.class.permittedSubclasses()` 返回 `Class<?>[]`，包含所有许可子类型的 Class 对象。
>
> **Q7. 最大区别：新增类型时的影响范围可追踪性。**传统策略模式新增实现类，调用方 if-else / instanceof 链不会自动报错；三件套新增 record 类型，所有穷尽 switch 立刻编译失败——错误不可能被忽视。
>
> **Q8. `case BuyXGetY(_, _) -> base` 用 `_` 忽略两个字段，匹配任何 `BuyXGetY` 实例（当 when 守卫不满足时兜底）。如果 `BuyXGetY` 新增字段（例如 `record BuyXGetY(int b, int f, String desc)`），`(_, _)` 会编译报错"分量数量不匹配"——强制开发人员更新处理逻辑，不会悄悄漏掉。**
>
> **Q9. `Math.max(0, base - off)` 防止 `off > base` 时返回负数价格。**去掉后如果 `FixedOff(cents=5000)` 应用到 2800 分的商品，会返回 `-2200`——用户反向被充值，是严重的业务 bug。
>
> **Q10. 可以不写 `default`。**`MenuItem` 是 sealed interface，只有 `CoffeeItem` 和 `TeaItem` 两种许可子类，编译器知道穷尽性已满足，无需 `default`。如果将来 sealed 合同新增类型，此 switch 也会立刻报"不包含所有可能的输入值"。

## 🔮 卷二预告：F2E1《两个世界的时间》

卷一走完语法进化——卷二开始清偿类库欠下的债。

第一笔债：**时间**。

`Date`、`Calendar`、`SimpleDateFormat`——这三位"老住户"在附录 D 里堆了三十年的坑。下一卷开门话，焰焰展示 `java.time` 的两块表：机器时间（`Instant` 纳秒精度时间戳）与人类日历（`LocalDateTime` 没有时区的挂钟时间），以及它们之间的换算桥梁——让 `Date` 的残影永远留在琥珀展览里。
