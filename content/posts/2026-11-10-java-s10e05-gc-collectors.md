## 四、原理图:三板斧、分代与家族史

```text
回收算法三板斧(分代假说回看 #45):
  标记-清除   标出活的,清走死的 —— 不搬家,留一地碎片
  复制        活的整体搬去空地,旧地推平 —— 无碎片,代价是留一块空地
  标记-整理   活的统一往一端挪 —— 无碎片不浪费,但搬家慢

分代假说:绝大多数对象朝生夕死 → 新生代用「复制」薄利多销;
熬过多轮晋升老年代 → 用「整理/清除」伺候。

家族史(版本事实,一个不许编):
  Serial     单人清扫,全程 STW —— 单核小堆容器仍合理
  Parallel   多人齐扫,全程 STW —— 吞吐优先,JDK 8 时代的默认
  CMS        首个并发收集器 —— JDK 9 弃用,JDK 14 移除(JEP 363)
  G1         JDK 9 起默认(JEP 248)—— Region 化 + 停顿目标 + Mixed GC
  ZGC        JDK 15 转正 —— 着色指针;JDK 21 分代(JEP 439),
             JDK 23 起分代为默认,JDK 24 移除非分代模式
  Shenandoah 另一支低延迟流派,路数不同,知道名字即可
```

**三色标记一分钟直觉**:并发收集 = 清洁队与顾客同场。对象染三色:白(没查)、灰(自己查了邻居没查完)、黑(查完)。若用户线程把白对象挂到**黑**对象名下、又剪断它与灰对象的旧连接,这个活对象就会被漏标误删。补救靠**写屏障**:引用一变动就记账,收尾照账补扫——G1 与 ZGC 的并发底气全押在这。

**选型决策表**(按服务画像查):

| 服务画像 | 选择 | 一句话理由 |
|---|---|---|
| 小堆(百 MB 级)/ 单核容器 | Serial | 没多核可用,省掉协调开销最划算 |
| 批处理 / 报表:吞吐第一,不在乎单次停顿 | Parallel | 用整段 STW 换最高吞吐 |
| 通用后端,堆几 G 到几十 G | G1(默认) | 停顿目标可调,吞吐延迟两头兼顾 |
| 大堆 + 延迟敏感,P99 按毫秒考核 | 分代 ZGC | 停顿亚毫秒级,基本不随堆变大而变长 |

```text
参数速查:
-Xms4g -Xmx4g              初始堆=最大堆,避免运行中伸缩抖动
-XX:+UseSerialGC / +UseParallelGC / +UseG1GC / +UseZGC   指定收集器
-XX:MaxGCPauseMillis=50    G1 停顿目标(软目标,不是合同)
-Xlog:gc*                  统一 GC 日志,排障第一现场
```

> **⏳ 版本时光机 · 默认收集器怎么换的班**

| JDK 版本 | 默认/大事 | 关键变化 |
|---|---|---|
| JDK 8 | Parallel 默认 | 吞吐优先时代;CMS 是低延迟的少数派 |
| JDK 9 | G1 上位默认(JEP 248) | 「可预测停顿」成主流;CMS 同版弃用,JDK 14 移除 |
| JDK 15 → 21 → 23 | ZGC 转正 → 分代 ZGC(JEP 439)→ 分代为默认 | 停顿进入亚毫秒;JDK 24 移除非分代模式 |

一句演进小结:默认收集器的换班史,就是从「吞吐最大」滑向「停顿可控」的历史。

## 五、从上一话继续改代码

上一话给下单服务配好了 JIT 观测;今天在同一套启动脚本前,先把决策表写成一个「选型器」:

```java
/** 咖啡站 v10.5:服务画像 → GC 参数 */
enum ServiceProfile { TINY_CONTAINER, THROUGHPUT_BATCH, LATENCY_SENSITIVE, HUGE_HEAP_LOW_LATENCY }

public class GcAdvisor {
    public static String advise(ServiceProfile p) {
        return switch (p) {   // 现代 switch:穷尽性检查,漏一档编译不过
            case TINY_CONTAINER        -> "-XX:+UseSerialGC";
            case THROUGHPUT_BATCH      -> "-XX:+UseParallelGC";
            case LATENCY_SENSITIVE     -> "-XX:+UseG1GC -XX:MaxGCPauseMillis=50";
            case HUGE_HEAP_LOW_LATENCY -> "-XX:+UseZGC";   // JDK 23 起即分代
        };
    }
}
```

## 七、观察真实现象:GC 日志抓现行

晚高峰,监控 P99 从 80ms 飙到 400ms,毛刺每几秒一根。翻 `-Xlog:gc*`:

```text
[0.003s][info][gc] Using Parallel
[312.518s][info][gc] GC(96) Pause Young (Allocation Failure) 2214M->186M(3925M) 236.512ms
```

毛刺周期和 `GC(n)` 严丝合缝:Parallel 的「快」是吞吐的快——攒满 2G 新生代再全场 STW 大扫除,**单次停顿和新生代大小正相关**。报表夜里停 240ms 没人知道;下单接口停 240ms,顾客已经在骂街。

> **豆豆锐评**:参数不看服务画像就复制,等于把货车发动机装进跑车——马力没错,错的是用途。

> **🎯 面试直击**:G1 凭什么做到「可预测停顿」?
> 堆切成等大 Region 而非物理连续两代,持续统计每格回收价值;每次按 `MaxGCPauseMillis` 预算,优先挑「垃圾最多、性价比最高」的一批 Region 回收(Mixed GC 连老年代格子一起挑)——Garbage First 由此得名。追问点:这是**软目标**,预算压到 1ms 做不到,只会缩小单次回收量、推高频率。

## 八、修复,并用测试证明

按画像换 G1,给出停顿预算:

```text
# order-service 启动参数(修复:延迟敏感 → G1 + 停顿目标)
java -XX:+UseG1GC -XX:MaxGCPauseMillis=50 -Xms4g -Xmx4g -Xlog:gc* -jar order-service.jar
```

```text
[0.004s][info][gc] Using G1
[295.410s][info][gc] GC(83) Pause Young (Normal) (G1 Evacuation Pause) 812M->146M(4096M) 11.437ms
```

停顿从 240ms 级掉到 12ms 级,P99 回到 90ms 以内。JUnit 把选型固化成纪律:

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class GcAdvisorTest {
    @Test
    void latency_sensitive_service_must_not_use_parallel() {
        String flags = GcAdvisor.advise(ServiceProfile.LATENCY_SENSITIVE);
        assertTrue(flags.contains("UseG1GC"));
        assertTrue(flags.contains("MaxGCPauseMillis"));
        assertFalse(flags.contains("UseParallelGC"));   // 再有人抄报表参数,这里先红
    }

    @Test
    void batch_job_prefers_throughput() {
        assertEquals("-XX:+UseParallelGC", GcAdvisor.advise(ServiceProfile.THROUGHPUT_BATCH));
    }
}
```

### 解答题(5 道)

**Q1(概念)** 画出 GC 回收算法三板斧(标记-清除 / 复制 / 标记-整理)的示意图,并说明每种算法最适合哪一代。

**Q2(解释)** G1 的 `MaxGCPauseMillis` 是硬指标还是软目标?如果设为 1ms 会发生什么?

**Q3(场景)** 你的服务堆 16G,白天 P99 稳定 30ms,凌晨批处理报表任务跑完后发现堆区碎片严重、Full GC 频繁。请分析可能原因并给出选型调整建议。

**Q4(分析)** 分析三色标记中「漏标」产生的精确条件:为什么必须是「黑色对象引用白对象」+「灰色对象到白对象的引用被切断」同时发生?写屏障如何补救?

**Q5(设计)** 你需要为团队制定「JVM GC 参数管理规范」,涵盖不同服务画像的参数模板。请至少设计 3 种画像(Small / Batch / Latency-Sensitive),并为每种给出关键参数及理由。

> [!答案]
> **选择题**
> 1-B。标记-清除只标活对象后清走死的,不搬动存活对象,留下碎片。★举一反三:碎片会导致「有足够的空闲总内存,但找不到连续的」,触发 Full GC。
>
> 2-B。分代假说:绝大多数对象朝生夕死(适合新生代用复制——少量存活,搬得快);少数熬过的对象存活久(老年代用标记-整理/清除)。★举一反三:这个经验假设不是定理,但二十多年的生产数据一直支撑它。
>
> 3-D。JDK 9 JEP 248 将 G1 设为默认。★举一反三:JDK 8 默认 Parallel(吞吐优先)→ JDK 9 G1(停顿可控)→ 未来 ZGC 可能接棒。
>
> 4-B。G1 把堆切成等大的 Region(默认 2048 个),每个 Region 可动态扮演 Eden/Survivor/Old/Humongous。★举一反三:Region 化是 G1 实现「可预测停顿」的基础——只挑垃圾最多的 Region 收。
>
> 5-B。CMS 是首个并发收集器(JDK 1.4),因碎片和 Concurrent Mode Failure 问题,JDK 9 弃用,JDK 14(JEP 363)正式移除。★举一反三:面试中如果有人从「CMS」切换到「ZGC」中间跳了两代——提醒对方先补 G1。
>
> 6-B。G1 在每次回收时,根据统计数据挑「垃圾最多、回收收益最大」的 Region 集合,在停顿预算内回收——Garbage First。★举一反三:从 G1 开始,GC 从「全堆打扫」转向「按需选择性打扫」。
>
> 7-B。Parallel 是「整段 STW 换吞吐」,停顿时间随新生代大小线性增长。报表机夜里停 240ms 无所谓,下单接口停 240ms 顾客骂街。★举一反三:参数不看「服务画像」就复制,是 P99 毛刺的首要原因。
>
> 8-B。并发标记期间,用户线程同时改引用,可能把白对象挂到已检查完的黑对象下、剪断灰色到白的链接——漏标。写屏障在引用变更时记录,收尾阶段补扫。★举一反三:CMS 的写屏障策略和 G1/ZGC 不同,但目的相同——不漏活对象。
>
> 9-B。ZGC 用着色指针(指针本身编码 GC 状态信息)+ 读屏障(读取对象时检查并顺带修正)——大部分 GC 工作与业务线程并发。★举一反三:JDK 21 分代 ZGC(JEP 439)后,ZGC 也走向分代,进一步减少内存开销。
>
> 10-C(精判 D 亦可)。8G 在 G1 的舒适区内,默认 G1 + 合理的 MaxGCPauseMillis 即可;若延迟要求极端(如高频交易),才上 ZGC。★举一反三:不要过度设计——不是所有服务都需要 ZGC,很多 8G 堆的在线服务 G1 调优就够了。
>
> **解答题**
>
> **Q1** 标记-清除:标出活对象→清除死对象→留下碎片;最适合老年代(存活多,搬不动)。复制:活对象整体搬到空地→旧地整块回收→无碎片,代价是预留一半空地;最适合新生代(存活少,搬得快)。标记-整理:标活→活对象统一移到一端整理→无碎片不浪费→但搬迁开销大;适合老年代的碎片整理阶段。★举一反三:三种算法没有「最优」,只有「最对某一代」——分代假说正是用这种分工组合取长补短。
>
> **Q2** `MaxGCPauseMillis` 是**软目标**(soft goal),不是硬合同。G1 会尽力使停顿不超过此值,但无法保证每轮都达标。如果设为 1ms,结果不是「每轮 1ms 内完成」,而是「每轮回收量极小、GC 频率暴增、吞吐暴跌」——G1 会缩小单次回收的 Region 数来逼近目标,但 GC 本身有最低开销,1ms 远低于这个底限。★举一反三:合理目标通常是 50~200ms,视业务可接受的抖动而定;别用不合理的 GC 目标把吞吐压死。
>
> **Q3** 可能原因:报表任务产生大量长生命周期对象,或使用 Parallel GC 产生碎片 → 老年代碎片化 → 即使总空闲够,但无连续空间分配给大对象 → 触发 Full GC。调整建议:①确认是否在用 Parallel(如果是,换成 G1——Region 化显著减少碎片);②如果是 G1,调大 `-XX:InitiatingHeapOccupancyPercent`(默认 45,适当调高减少 Mixed GC 频率)或增大堆;③检查是否有「大对象直接进老年代」的情况(如大数组),用 `-XX:G1HeapRegionSize` 调整 Humongous 阈值。★举一反三:碎片问题在早期的 CMS 和 Parallel 上特别严重,G1/ZGC 通过 Region 化基本解决了这个痛点。
>
> **Q4** 漏标的精确条件(两个条件缺一不可):①写屏障执行前,用户线程新建了一条从**黑色**对象到**白色**对象的引用;②同时,该白色对象原本通过一个**灰色**对象可达,但从灰对象到白对象的**唯一**引用被剪断了。结果:白色对象被黑色(已标记完成不再扫)持有,又失去了从灰色(待扫队列中的)出发的路径,最终被判定为垃圾误删。写屏障补救:在引用变更时(如 `A.field = B`),若 A 是黑色、B 是白色,则把 B 标记为灰色——即把「被黑色对象引用的白色对象」重新加入扫描队列。★举一反三:G1 用 SATB(Snapshot At the Beginning)写屏障,在赋值前记下旧引用快照;ZGC 用读屏障;CMS 用增量更新——手段不同,目标一致。
>
> **Q5** 三种画像参数模板:①**Small(百 MB 堆/单核容器)**:`-XX:+UseSerialGC -Xms256m -Xmx256m`;理由——没多核可用,串行 GC 省掉协调开销,单线程清场最划算。②**Batch(批处理/报表,吞吐第一)**:`-XX:+UseParallelGC -Xms8g -Xmx8g`;理由——全 STW 清扫,停顿多久无所谓,吞吐最大化。③**Latency-Sensitive(在线服务,8~32G)**:`-XX:+UseG1GC -XX:MaxGCPauseMillis=100 -Xms16g -Xmx16g`;理由——Region 化 + 软停顿目标,兼顾吞吐与延迟。所有模板加 `-Xlog:gc*:file=gc.log`(GC 日志常开,排障第一现场)。★举一反三:参数模板只是最低基准,上线后必须结合 GC 日志和监控调整;特别是 `MaxGCPauseMillis`,需要根据实际 P99 数据反推合理值。
>
