# 《从零开始学 Java》30 · JUnit 质检员

> 连载特刊 · 第三季「工程时代」第 6 话 · 基线 Java 25(最新 LTS)
> 承接:上一话 `mvn test` 能自动跑测试了,可阿零写的测试还很潦草。

## 一、需求:测试也要写得专业

`mvn test` 跑得欢,但阿零的测试来来回回就一句 `assertEquals`。遇到"一批越界值都要测""这里就该抛异常""每个测试都得先备一套干净库存",他就抓瞎。豆豆:「测试不是走过场。质检员要来了——她只信**证据**。」

从第一话起就露过面的 JUnit 质检员,这一话正式收阿零为徒。

---

## 二、漫画 · 质检员的规矩

> **〔1〕** 一位戴老花镜的质检员举着放大镜,逐杯检查,口头禅刻在牌子上:「证据呢?」
> 豆豆:「`assertEquals`/`assertThrows`/`assertTrue`——这些**断言**就是她的检验标准,不达标当场打回。」

> **〔2〕** 每检一杯前,她都换一副干净手套、重备一套样品。
> 豆豆:「`@BeforeEach`——**每个测试跑之前**都重新备一份干净数据,谁也不许用上一轮的剩货。」

> **〔3〕** 她端来一整盘样本 `{6, 10, 999}` 一次性过检。
> 豆豆:「`@ParameterizedTest` + `@ValueSource`——**一批数据喂进同一个测试**,逐个验,不用复制粘贴三遍。」

> **〔4〕** 阿零图省事,两个测试**共用同一杯咖啡**。第一个测试喝掉半杯,第二个测试拿起来一看:量不对,红牌。
> 质检员(敲桌):「样品被上一轮**污染**了!你的测试**互相依赖**,这检验作废。」
> 豆豆(叼豆子):「经典翻车——测试之间共享可变状态,结果时绿时红,全看谁先跑。」

## 三、本话目标

- 掌握常用断言:`assertEquals` / `assertThrows` / `assertAll` / `assertDoesNotThrow`;
- 用 `@BeforeEach` 给每个测试备一份干净夹具(fixture);
- 用 `@ParameterizedTest` 一次测一批数据;
- 踩一次"测试共享状态互相污染"的坑,理解**测试隔离**;
- 建立"测试必须独立、可重复"的意识。

---

## 四、原理图:一个测试类的骨架

```text
@BeforeEach   每个 @Test 前都跑一次 —— 备干净数据(隔离的关键)
@Test         一个独立的检验用例
@DisplayName  给用例起人话名字,报告里好读
断言:
  assertEquals(期望, 实际)         值相等
  assertThrows(异常.class, () -> …) 断言"必须抛这个异常",并返回异常对象
  assertAll(…, …, …)               一次验多个点,全报告而非遇错即停
  assertDoesNotThrow(() -> …)      断言"不该抛"
@ParameterizedTest + @ValueSource  同一逻辑喂一批输入
```

## 五、代码:给 CoffeeShop 写体系化测试

被测对象是第 1、2 话的 `CoffeeShop`(美式库存 1、拿铁 5)与业务异常 `OutOfStockException`:

```java
import org.junit.jupiter.api.*;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;
import static org.junit.jupiter.api.Assertions.*;

class CoffeeShopTest {
    private CoffeeShop shop;

    @BeforeEach
    void freshShop() {              // ★ 每个测试前重建,拿一套干净库存
        shop = new CoffeeShop();
    }

    @Test
    @DisplayName("库存足够时正常出杯")
    void serves_when_enough() {
        assertDoesNotThrow(() -> shop.order("拿铁", 3));
    }

    @Test
    @DisplayName("缺货时抛业务异常,且带对缺口")
    void rejects_when_not_enough() {
        OutOfStockException e = assertThrows(
            OutOfStockException.class, () -> shop.order("美式", 5));
        assertAll(
            () -> assertEquals("美式", e.item()),
            () -> assertEquals(4, e.shortfall()));   // 要 5 剩 1,缺 4
    }

    @ParameterizedTest
    @ValueSource(ints = {6, 10, 999})               // 一批越界值,逐个过检
    void rejects_any_over_stock(int qty) {
        assertThrows(OutOfStockException.class, () -> shop.order("拿铁", qty));
    }
}
```

`assertAll` 会把里面每个断言**都执行完再汇总报告**,而不是第一个失败就停——一次看清所有问题。

## 六、故意制造一个 Bug:测试互相污染

把 `@BeforeEach` 删掉,改成只在字段处 `new` 一次,让所有测试**共用同一个 shop**:

```java
private CoffeeShop shop = new CoffeeShop();   // ← 故意:只建一次,全类共享

@Test void a_buy() { shop.order("拿铁", 5); }              // 把拿铁买空
@Test void b_still_has_latte() {
    assertDoesNotThrow(() -> shop.order("拿铁", 1));        // 期望还能买
}
```

---

## 七、读懂现象:时绿时红的"幽灵测试"

有时全绿,有时 `b_still_has_latte` 红着报 `OutOfStockException`。根因:JUnit **不保证测试执行顺序**;`a_buy` 一旦先跑,就把共享的拿铁买空了,`b` 再买必然缺货。这种"结果取决于谁先跑"的测试叫 **flaky test(不稳定测试)**,是团队里最招人恨的一类——它让 CI 时红时绿,谁也不敢信。

根治就一句话:**每个测试必须从干净状态开始**。`@BeforeEach` 每次重建 `shop`,测试之间就再无瓜葛。

> **⏳ 版本时光机 · JUnit 4 → JUnit 5 的注解换血**

| 用途 | JUnit 4 | JUnit 5(现在用这套) |
|---|---|---|
| 每个测试前 | `@Before` | `@BeforeEach` |
| 全部测试前一次 | `@BeforeClass`(须 static) | `@BeforeAll` |
| 断言异常 | `@Test(expected = X.class)` | `assertThrows(X.class, …)`(更精准,能断言消息) |
| 扩展机制 | `@RunWith` | `@ExtendWith` |

老项目还常见 JUnit 4,新项目一律 JUnit 5(Jupiter)。

> **🎯 面试直击**:一个好的单元测试应该满足什么?
> 记 **FIRST**:Fast(快)、Independent(相互独立、无顺序依赖)、Repeatable(任何环境可重复)、Self-validating(用断言自动判定成败,不靠人眼看输出)、Timely(及时,最好和代码一起写)。本话那个 flaky Bug 违反的正是 **Independent**。

### 一、选择题（10 道）

1. [基础] JUnit 5 中标记测试方法的注解是？
- A) `@Test`　B) `@TestMethod`　C) `@UnitTest`　D) `@RunTest`

2. [基础] `assertEquals(expected, actual)` 和 `assertTrue(condition)` 的核心区别是？
- A) 完全相同　B) 前者比预期，后者**判断布尔条件**　C) 前者只能用于数值　D) 后者更精确

3. [基础] `@BeforeEach` 的生命周期是什么？
- A) 整个测试类只执行一次　B) **每个 `@Test` 方法之前**都执行一次　C) 所有测试方法之后执行　D) 编译前执行

4. [进阶] 测试"某个方法必须抛出指定异常"应该用？
- A) `assertEquals`　B) `assertThrows(异常类.class, () -> 被测代码)`　C) `try-catch` 手动判断　D) `assertTrue`

5. [进阶] `assertAll` 相比多个独立的 `assertEquals` 的优势是？
- A) 更漂亮　B) 所有断言**都执行后才汇总报告**，而非第一个失败就停　C) 性能更好　D) 不需要写测试方法

6. [进阶] `@ParameterizedTest` + `@ValueSource(ints = {1, 2, 3})` 的作用是？
- A) 并行执行 3 个测试　B) 用 3 个不同输入**同一逻辑各跑一次**　C) 随机选一个值跑　D) 只跑第一个值

7. [进阶] 删除 `@BeforeEach` 让所有测试共享同一个对象，可能导致？
- A) 编译错误　B) **flaky test**（时绿时红的幽灵测试）　C) 测试无法运行　D) 测试速度变快

8. [综合] `assertThrows` 的返回值可以用来做什么？
- A) 不能使用返回值　B) **进一步断言异常对象**的消息、字段等　C) 替代异常对象　D) 自动修复异常

9. [综合] 一个好的单元测试应该满足 FIRST 原则中的 "I" 代表？
- A) Integration　B) **Independent**（测试之间相互独立）　C) Interactive　D) Inclusive

10. [综合] `@BeforeAll` 和 `@BeforeEach` 的区别是？
- A) 完全相同　B) `@BeforeAll` 在所有测试**之前执行一次**（须 static），`@BeforeEach` 每个测试前执行　C) `@BeforeAll` 只用于参数化测试　D) `@BeforeEach` 更高级

> [!答案] **1-A** `@Test`（`org.junit.jupiter.api.Test`）是核心注解。**举一反三**：JUnit 4 也是 `@Test`，但包名不同（`org.junit.Test`）——注意导入。
> [!答案] **2-B** `assertEquals` 适合有明确预期值；`assertTrue` 适合验证"结果应满足某性质"但无法写死具体值。**举一反三**：能用 `assertEquals` 就别用 `assertTrue(actual == expected)`——前者失败时会打印两个值，后者只告诉你 true/false。
> [!答案] **3-B** `@BeforeEach` 在每个 `@Test` 前执行，用于准备**干净**测试数据（夹具）。**举一反三**：JUnit 4 的对应注解是 `@Before`；JUnit 5 还增加了 `@AfterEach`。
> [!答案] **4-B** `assertThrows` 是 JUnit 5 的推荐方式——不仅断言抛了，还能拿到异常对象深入验证。JUnit 4 的方式是 `@Test(expected = X.class)`，但无法断言异常消息。**举一反三**：反过来验证"不应该抛异常"用 `assertDoesNotThrow`。
> [!答案] **5-B** `assertAll` 会把里面的每个断言都跑完，然后一次性报告所有失败。单独的 `assertEquals` 遇到第一个失败就停，修完一个才能看到下一个问题。**举一反三**：`assertAll` 适合一次验证一个操作产出的多个属性——如一个订单对象同时有 item、qty、amount。
> [!答案] **6-B** 参数化测试让同一个测试逻辑喂入一批不同的输入，每个输入都独立跑一次。写一个方法，覆盖多种情况。**举一反三**：`@CsvSource` 可以传多参数组合；`@MethodSource` 可从方法获取复杂测试数据。
> [!答案] **7-B** 测试共享可变状态时，执行顺序会影响结果——JUnit 不保证顺序，于是结果时绿时红，严重时导致对 CI 失去信任。**举一反三**：根治方案——`@BeforeEach` 每个测试前重建对象，保证隔离。
> [!答案] **8-B** `assertThrows` 返回捕获的异常对象，可以继续 `assertEquals("预期消息", e.getMessage())` 或断言自定义字段。**举一反三**：这是测试自定义异常（如 `OutOfStockException.shortfall()`）的标准手法。
> [!答案] **9-B** FIRST = Fast / Independent / Repeatable / Self-validating / Timely。I 是 Independent——测试之间无顺序依赖，不共享状态。**举一反三**：违反 I 的就是本话的 flaky test——CI 时红时绿，谁也不敢信。
> [!答案] **10-B** `@BeforeAll` 整个类只跑一次（适合初始化数据库连接等昂贵资源），方法必须 `static`；`@BeforeEach` 每个测试跑一次（适合重置测试数据）。**举一反三**：JUnit 4 对应关系：`@BeforeAll` → `@BeforeClass`，`@BeforeEach` → `@Before`。

### 二、解答题（3 道）

1. [概念] 什么是 flaky test（不稳定测试）？产生 flaky test 的常见原因有哪些？如何通过 `@BeforeEach` 和测试隔离来根治？

2. [场景] 为 `CoffeeShop` 的两个场景设计测试：①正常下单后库存扣减正确；②库存不足抛异常，且异常带缺口信息。用 JUnit 5 写出测试骨架（含注解和关键断言）。

3. [综合] FIRST 原则中每一条的具体含义和反面例子是什么？你所在的团队 CI 时红时绿——你怀疑是 flaky test，请给出排查步骤和修复策略。

> [!答案] **1** flaky test 是"同一份代码，不修改任何东西，多次运行结果可能不同"的测试。常见原因：①测试共享可变状态（本话例子）；②依赖外部资源（网络、文件、时间）；③依赖执行顺序；④未处理的并发竞态。根治：`@BeforeEach` 每次重建测试对象 + 每个测试只用自己创建的数据 + 不依赖外部状态。**举一反三**：可以用 `@TempDir` 隔离文件操作；用 Mock 隔离外部依赖（第四季讲）。
> [!答案] **2** 测试骨架：
> ```java
> class CoffeeShopTest {
>     CoffeeShop shop;
>     @BeforeEach void setUp() { shop = new CoffeeShop(); }
>     @Test void order_reduces_stock() {
>         shop.order("拿铁", 3);
>         OutOfStockException e = assertThrows(OutOfStockException.class, () -> shop.order("拿铁", 3));
>         assertEquals(4, e.shortfall()); // 原来5杯,买3剩2,再要3差1...不对,应该是1
>     }
>     @Test void rejects_with_shortfall() {
>         OutOfStockException e = assertThrows(OutOfStockException.class, () -> shop.order("美式", 5));
>         assertAll(
>             () -> assertEquals("美式", e.item()),
>             () -> assertEquals(4, e.shortfall())  // 库存1,要5,缺口4
>         );
>     }
> }
> ```
> **举一反三**：测试方法命名遵循 `动作_条件_结果` 模式，如 `order_whenShortStock_rejects`，可读性强。
> [!答案] **3** 逐条：F-快（测试要在秒级完成，反面：每个测试启动 Spring 容器）；I-独立（反面：测试 B 依赖测试 A 留下的数据）；R-可重复（反面：依赖当前日期、随机数，不同时间结果不同）；S-自验证（反面：靠人眼看 System.out 判断成败）；T-及时（反面：发布前一天才写测试）。排查 flaky：①在 CI 上反复重跑 10 次，找出失败规律；②检查是否有共享状态（字段 static、单例）；③打日志记录测试执行顺序和状态。**举一反三**：Maven Surefire 支持 `-Dtest=XXXTest#methodName` 单独跑可疑测试。

### 三、代码题（2 道）

1. [基础] 用 JUnit 5 为 `Math.max(a, b)` 写参数化测试：用 `@CsvSource` 传入三组数据：`(3, 5, 5)`、`(7, 7, 7)`、`(-1, 0, 0)`（前两个是入参，第三个是预期结果）。再加一个 `@BeforeEach` 打印"开始测试"。确保测试能跑出 3 次结果。

2. [综合] 为 `StringUtils.isEmpty(String s)` 写完整测试套件：①null → true；②"" → true；③"  " → false；④"hello" → false。用 `@ParameterizedTest` + `@NullAndEmptySource` 覆盖 null 和空串；再加一个 `@ParameterizedTest` + `@ValueSource` 覆盖非空场景。同时加 `@BeforeEach` 初始化一个计数器，用 `@AfterEach` 打印当前测试名称。

> [!答案] **1 验收**：
> ```java
> import org.junit.jupiter.api.*;
> import org.junit.jupiter.params.ParameterizedTest;
> import org.junit.jupiter.params.provider.CsvSource;
> import static org.junit.jupiter.api.Assertions.*;
> 
> class MathTest {
>     @BeforeEach void setUp() { System.out.println("开始测试"); }
>     
>     @ParameterizedTest
>     @CsvSource({"3, 5, 5", "7, 7, 7", "-1, 0, 0"})
>     void max_returns_larger(int a, int b, int expected) {
>         assertEquals(expected, Math.max(a, b));
>     }
> }
> // 输出: 开始测试 \n (结果) \n 开始测试 \n (结果) \n 开始测试 \n (结果)
> // 每个参数组合都会触发一次 @BeforeEach
> ```
> **举一反三**：`@CsvSource` 比 `@ValueSource` 灵活——可以传多个参数；用 `@MethodSource` 可以返回更复杂的参数对象。
> [!答案] **2 验收**：
> ```java
> import org.junit.jupiter.api.*;
> import org.junit.jupiter.params.ParameterizedTest;
> import org.junit.jupiter.params.provider.*;
> import static org.junit.jupiter.api.Assertions.*;
> 
> class StringUtilsTest {
>     private int testCount;
>     
>     @BeforeEach void init() { testCount = 0; }
>     @AfterEach void report(TestInfo info) {
>         System.out.println("[" + info.getDisplayName() + "] 执行完毕");
>     }
> 
>     @ParameterizedTest
>     @NullAndEmptySource                    // 自动传 null 和 ""
>     void isEmpty_nullOrEmpty(String s) {
>         assertTrue(StringUtils.isEmpty(s));
>     }
> 
>     @ParameterizedTest
>     @ValueSource(strings = {"  ", "hello", "a"})
>     void isEmpty_nonEmpty(String s) {
>         assertFalse(StringUtils.isEmpty(s));
>     }
> }
> // 假设 StringUtils.isEmpty(s) 的实现:
> // return s == null || s.isEmpty();
> ```
> **举一反三**：`@NullAndEmptySource` 自动覆盖两个边界；`TestInfo` 可以拿到当前测试的展示名、方法名等元信息——测试报告和日志的好帮手。
