## 二、漫画 · JIT 加速工厂参观记

> **〔1〕** 类加载站出口,盖好戳的字节码卷轴顺传送带滑进一座大厅,门口挂牌「执行引擎」。一排小窗口后,解释器职员逐条念指令。
> JVM 城主:「CPU 听不懂字节码,解释器一句句现场口译——算 15+3 也要老老实实:压栈、压栈、弹出来相加。这就是**栈式虚拟机**。」

> **〔2〕** 阿零发现每条传送带旁都有一只咔咔跳数的计数器,其中一只突然爆红报警:「HOT!」
> 豆豆:「方法每被调用一次、循环每绕一圈(回边),计数器 +1。攒过阈值,这段代码就是**热点**——值得花真金白银去编译。」

> **〔3〕** 热点卷轴被叉车分送两间车间:C1 车间灯亮手快,三下五除二产出机器码;C2 车间门口排队,里面全是精密仪器。
> JVM 城主:「C1 编得快、优化浅,先顶上;一直热的常客再送 C2,编得慢但下狠手。**分层编译**,冷热分治。」

> **〔4〕** C2 车间内:机械臂把 `price()` 的小卷轴直接焊进调用它的大卷轴,进出方法的旋转门被整个拆走。
> 豆豆:「**方法内联**——调用开销连同旋转门一起消失。所以小方法不吃亏,别为了『省一次调用』写巨无霸方法。」

> **〔5〕** 另一条产线:一个从没离开车间的对象被拆成零件摆上工作台;旁边一把没人抢的锁被机械臂「咔」地卸掉。
> 豆豆:「**逃逸分析**:对象逃不出方法,就不进堆;锁只被一个线程摸,直接抹掉——第 72 话那句『工厂内幕』,今天兑现。」

> **〔6〕** 阿零掏出手机秒表:「我来实测内联!」两段循环一跑,他举着屏幕大喊:「方法调用比直接算慢 100 倍!内联是骗人的!」
> 豆豆(叼着豆子叉腰):「引擎还没热就踩油门量油耗,量出来的是冷车,外加一段被工厂连根拔掉的死代码。回去,重测。」

## 四、原理图:执行引擎流水线

```text
.class 字节码 ──类加载站(上一话)──▶ 执行引擎
                                      │
             ┌────────────────────────┤
             ▼                        ▼
        解释器(逐条口译)      热点计数器(方法调用 + 循环回边)
             │                        │ 超过阈值 → 热点
             │                        ▼
             │            C1 编译器:编得快、优化浅,先顶上
             │                        │ 持续热
             │                        ▼
             │            C2 编译器:编得狠 —— 内联、逃逸分析、投机优化
             └── 冷代码一直解释也无妨;热代码逐层升级 → 越跑越快
```

C2 的两记狠手,记牢:

- **方法内联**:把小方法的字节码直接抄进调用处,消灭调用开销,也给后续优化腾出视野;
- **逃逸分析三件套**:对象逃不出方法/线程,就 ① **栈上分配**(不进堆,返回即蒸发,GC 全程不知情);② **标量替换**(拆成零散字段放栈和寄存器);③ **锁消除**(同步省略:没人抢的 `synchronized` 直接抹掉)。

> **⏳ 版本时光机 · 执行引擎怎么一路变快**

| 阶段 | 执行方式 | 关键变化 |
|---|---|---|
| 远古 JVM | 纯解释执行 | 简单、启动即跑,但热代码也永远在「现场口译」 |
| HotSpot 时代(至今) | 解释器 + C1/C2 分层编译 | 热点探测、冷热分治:越跑越快,代价是预热 |
| Java 25 | AOT 方法画像(JEP 515) | 上次运行攒下的「谁是热点」画像随 AOT 缓存带走,下次启动少交预热学费 |

一句演进小结:从「全靠口译」到「热点精译」,再到「带着上次的笔记开工」——始终在把预热的学费越交越少。

## 五、代码:用 javap 给字节码拍 X 光

本话不动咖啡站业务代码,只做透视。新增一个演示类(整数演示价,不替换第 60 话的 BigDecimal 计价):

```java
public class HotPath {
    static int price(int cups) {   // 单价 15,整单杯套费 +3(演示用)
        int unit = 15;
        return unit * cups + 3;
    }

    int nameLen(String name) {
        return name.length();
    }
}
```

`javac HotPath.java` 之后,X 光机开机:

```text
$ javap -c HotPath
Compiled from "HotPath.java"
public class HotPath {
  public HotPath();
    Code:
       0: aload_0
       1: invokespecial #1                  // Method java/lang/Object."<init>":()V
       4: return

  static int price(int);
    Code:
       0: bipush        15
       2: istore_1
       3: iload_1
       4: iload_0
       5: imul
       6: iconst_3
       7: iadd
       8: ireturn

  int nameLen(java.lang.String);
    Code:
       0: aload_1
       1: invokevirtual #7                  // Method java/lang/String.length:()I
       4: ireturn
}
```

逐行读 `price`,栈式虚拟机的直觉就有了:`bipush 15` 把 15 压栈,`istore_1` 存进局部变量表 1 号槽(`unit`);`iload_1`/`iload_0` 把 `unit` 和参数 `cups` 依次压栈,`imul` 弹出两个相乘再压回;`iconst_3` 压个 3,`iadd` 弹出相加,`ireturn` 带着栈顶结果走人。**一切运算都绕着操作数栈转**。

`nameLen` 里那条 `invokevirtual`,则是多态在字节码层的样子:按对象**运行时的实际类型**去找方法。顺带一眼:类里若有 Lambda,`javap` 会多一条 `invokedynamic`——Lambda 不是编译成匿名内部类,而是运行时动态搭桥(回看第 68 话)。

> **豆豆旁白**:字节码是给 JVM 而非 CPU 看的中间语言。隔了这一层,同一份 `.class` 才能到处跑,也才轮得到 JIT 运行期看菜下饭。

## 六、故意制造一个 Bug:秒表裸测微基准

阿零不服漫画第 6 格的吐槽,把「实测」写成了代码——用 `System.currentTimeMillis()` 对比「直接算」和「方法调用」:

```java
public class ColdBench {
    public static void main(String[] args) {
        long t0 = System.currentTimeMillis();
        long a = 0;
        for (int i = 0; i < 200_000_000; i++) a += 15 * i + 3;        // 手写「内联」版
        long t1 = System.currentTimeMillis();

        long b = 0;
        for (int i = 0; i < 200_000_000; i++) b += HotPath.price(i);  // 方法调用版
        long t2 = System.currentTimeMillis();

        System.out.println("直接算  : " + (t1 - t0) + " ms");          // a 从头到尾没人用
        System.out.println("方法调用: " + (t2 - t1) + " ms,校验 b=" + b);
    }
}
```

## 七、观察离谱现象,并拆穿它

```text
直接算  : 2 ms
方法调用: 207 ms,校验 b=299999999100000000
```

阿零:「看!慢 100 倍!」豆豆:「你这份测评,两宗罪。」

- **罪一 · 死代码消除**:`a` 算完没人用,C2 顺着数据流一看整条循环白干,**连根拔掉**——「2 ms」不是直接算快,是**根本没算**。
- **罪二 · 没预热**:`b` 真跑了两亿次,但从解释器起步、边跑边换编译版,单次计时把「冷车 + 换挡」全算进去,离稳态十万八千里。

证据不用猜,让工厂自己交代——加 `-XX:+PrintCompilation` 重跑,能看到编译日志(节选):

```text
     76   19 %     3       ColdBench::main @ 10 (89 bytes)
     82   23       3       HotPath::price (9 bytes)
     95   27 %     4       ColdBench::main @ 10 (89 bytes)
```

`%` 是 OSR(循环半路被当场换成编译版),数字是层级(3 = C1 带画像,4 = C2)——你的循环在计时途中被反复换了引擎。

> **🎯 面试直击**:Java 是解释执行还是编译执行?逃逸分析能带来哪三种优化?
> 都有:javac 先编成字节码,运行期解释器与 JIT **混合执行**——冷代码解释,热点分层编译(C1→C2),所以「越跑越快」。逃逸分析三件套:**栈上分配、标量替换、锁消除(同步省略)**。追问点:为什么不干脆全部提前编译?——哪条分支热、对象实际是什么类型,只有跑起来才知道;JIT 靠运行期画像做激进的投机优化,赌错了还能退回解释器(去优化)。

## 八、修复:预热、消费结果,以及 JMH 存在的意义

微基准三条军规:**① 先预热再计时,只看稳态;② 结果必须被消费,不给死代码消除留缝;③ 多轮取样,别信单次**。照军规重写:

```java
import java.util.function.IntToLongFunction;

public class WarmBench {
    static long run(IntToLongFunction f) {
        long sink = 0;
        for (int i = 0; i < 200_000_000; i++) sink += f.applyAsLong(i);
        return sink;                                    // 军规②:结果被消费
    }

    public static void main(String[] args) {
        IntToLongFunction call = i -> HotPath.price(i);
        for (int round = 1; round <= 5; round++) {      // 军规①③:前几轮是预热,看后几轮
            long t0 = System.nanoTime();
            long sink = run(call);
            System.out.println("第 " + round + " 轮: "
                    + (System.nanoTime() - t0) / 1_000_000 + " ms(sink=" + sink + ")");
        }
    }
}
```

再跑:第 1 轮 213 ms、第 2 轮 96 ms、第 3~5 轮稳在 62 ms 上下——**稳态下方法调用与手写内联打平**,C2 早把 `price` 焊了进去。三条军规的工业级形态就是官方微基准框架 **JMH**:fork 独立 JVM、自动预热轮、Blackhole 吞结果防消除、自带统计误差。概念立住即可,依赖细节不展开。

语义没变,才轮得到谈快慢——JUnit 质检员:「证据呢?」

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class HotPathTest {
    @Test
    void inline_math_and_method_call_agree() {
        for (int i = 0; i < 10_000; i++) {
            assertEquals(15 * i + 3, HotPath.price(i));  // 手写式与方法调用语义一致
        }
    }
}
```

```text
HotPathTest > inline_math_and_method_call_agree() PASSED
```

> **豆豆锐评**:JIT 的一切优化都以「语义不变」为底线,你的一切性能结论都以「测法正确」为底线。顺带展望:JDK 25 的 **AOT 方法画像(JEP 515)** 能把上次运行的热点画像存进 AOT 缓存,下次启动照单加速——开头那条「重启后慢几分钟」的曲线会越来越平。

### 解答题(5 道)

**Q1(概念)** 用 `javap -c` 反编译一段简单的方法(如 `int add(int a, int b) { return a + b; }`),逐行解释每条字节码指令在操作数栈上的动作。

**Q2(解释)** 为什么 Java 被称为「解释与编译混合执行」?请从解释器和 JIT 协作的角度解释。

**Q3(场景)** 你负责的订单服务每次重启后 RT 偏高,5 分钟后自动回落到正常水平。请分析原因,并给出至少两种减少预热的方案。

**Q4(分析)** 本话提到逃逸分析三件套:栈上分配、标量替换、锁消除。请分析一段使用了局部 `StringBuilder` 和局部 `synchronized` 的代码,说明 C2 如何优化它,以及优化的前提条件。

**Q5(设计)** 你需要为团队设计一套微基准测试规范(用于验证某个工具方法的性能是否退化)。请写出规范的核心要素(至少 5 条),并说明为什么不能用 `System.currentTimeMillis()` 的简单循环来做。

> [!答案]
> **选择题**
> 1-B。JVM 是栈式虚拟机,字节码指令围绕操作数栈工作。★举一反三:Android 的 Dalvik/ART 是寄存器式,指令集不同但思想相通。
>
> 2-B。`imul` 弹出两个 int,相乘,结果压回。对应的源码是 `*` 运算符。★举一反三:`iadd`(加)、`isub`(减)、`idiv`(除)同理。
>
> 3-B。C1(client compiler):编得快、优化浅,先顶上;一直热的代码再升级到 C2(server compiler):编得慢但下狠手(内联、逃逸分析等)。★举一反三:C2 的「狠」体现在:宁愿多花编译时间,也要在运行时把代码跑到极致。
>
> 4-D。「死代码消除」是独立优化(无关逃逸分析),C2 在数据流分析中发现某段代码结果没人用就消除——但逃逸分析专指「分析对象的可见范围」。★举一反三:前三个选项 + 死代码消除,四点都可能在同一个方法上同时发生。
>
> 5-B。内联是把小方法体直接嵌进调用处——最常见:C2 把 getter/setter 和短工具方法内联掉。★举一反三:内联的收益不只是省一次调用,它把更大范围的代码暴露给后续优化,连锁效应远超调用本身。
>
> 6-B。计算结果 `a` 从头到尾没人用(没打印、没返回、没传给外部),C2 顺着数据流判定整段循环无副作用,连根拔掉——不是性能好,是根本没算。★举一反三:这就是为什么微基准测试必须「消费结果」——Blackhole 或 return 给外部。
>
> 7-B。计数器有两种:方法调用计数器(方法被调一次 +1)和回边计数器(循环绕一圈 +1)。热点探测贯穿运行全过程。★举一反三:还有 OSR(On-Stack Replacement):循环跑到一半,C1 编译完了,当场把解释器版本的栈换成编译版本。
>
> 8-B。JIT 的激进优化基于运行期收集的类型画像。若假设「某个引用总是 String」做了内联,后来传入 Integer,就必须「去优化」——退回解释器状态,丢掉错误的编译版本。★举一反三:这解释了「Java 为什么不干脆全部 AOT」——运行期的信息是编译期拿不到的。
>
> 9-D。JMH 专精微基准测试(单个方法的吞吐/延迟),不能替代端到端的集成测试。★举一反三:JMH 测的是「这个工具方法的极限吞吐」,不是「用户从下单到支付的全链路耗时」。
>
> 10-B。JEP 515 把 JIT 运行期收集的方法画像(热点、内联决策等)持久化,下次启动读画像直接加速,少交预热费。★举一反三:这类似「带着上次的笔记开工」,但仍是 JIT 主导,AOT 只是辅助。
>
> **解答题**
>
> **Q1** `javap -c` 输出:
> ```
> 0: iload_0    // 将局部变量表 0 号槽(a)压入栈
> 1: iload_1    // 将局部变量表 1 号槽(b)压入栈
> 2: iadd       // 弹出栈顶两个 int 相加,结果压回
> 3: ireturn    // 弹出栈顶 int,作为方法返回值
> ```
> 栈变化:`[] → [a] → [a,b] → [a+b] → []`。★举一反三:所有字节码指令都以「弹出操作数→运算→压回结果」的栈模式执行,这与 x86 的寄存器模式完全不同的思维范式。
>
> **Q2** java 编译成字节码 → JVM 启动时解释器逐条执行(冷代码);同时热点探测器统计方法调用和循环回边 → 超过阈值触发 JIT 编译(C1→C2)→ 后续调用直接执行编译后的本地代码。所以「解释执行」负责快速启动和冷代码,「编译执行」负责热代码加速。★举一反三:这个协作模型的精髓在于:C2 只在「值得花编译时间」的热点上工作,不把编译时间浪费在只跑一两次的代码上。
>
> **Q3** 原因:重启后所有代码从解释器起步,JIT 需要跑过足够多次调用/循环才能识别热点并编译,这期间的代码都是「冷」的。方案:①**预热脚本**——启动后自动跑一遍核心接口,触发热点编译;②**AOT 缓存**(JDK 25 JEP 515)——把上次的热点画像带走,下次启动直接编译;③**增大 JIT 阈值**(`-XX:CompileThreshold`)适当调低,让热点更快被编译;④**分层编译**默认已开,确认没有因参数被关闭。★举一反三:这个问题在大促压测时常见——冷 JVM 跑出来的性能数据没有参考价值,必须先预热。
>
> **Q4** 分析一段典型代码:
> ```java
> StringBuilder sb = new StringBuilder();
> sb.append("Hello").append(name);
> String result = sb.toString();
> ```
> `sb` 对象全程未离开该方法(未赋给字段、未当返回值、未当参数传给外部方法)。逃逸分析判定「无逃逸」后:①**标量替换**:不分配 `StringBuilder` 对象,直接把它拆成内部的 `char[]` 数组和 `count` 字段,放到栈上;②**栈上分配**(若未完全标量替换):`StringBuilder` 对象直接分配在栈帧而非堆上,方法返回即回收,GC 全程不知情。锁消除同理:
> ```java
> synchronized (new Object()) { doSomething(); }
> ```
> 锁对象是局部新建的,不可能被其他线程引用到——锁消除直接把 `synchronized` 抹掉。★举一反三:前提是对象真的没有逃逸——一旦赋值给静态字段/作为返回值/传入外部方法,逃逸分析就宣告失败,所有优化撤回。
>
> **Q5** 微基准测试规范核心要素:①**预热**:正式计时前先跑足够轮次让 JIT 编译完成,只看稳态;②**消费结果**:计算结果必须被返回/写入 Blackhole/打印,防死代码消除;③**多轮取样 + 统计**:至少 5~10 轮,记录均值/标准差,不信单次;④**fork 独立 JVM**:每轮测试 fork 新 VM,避免前置测试影响后置;⑤**控制变量**:每次只改一个变量,对比组在同样环境下跑;⑥**批量而非单次**:一次调用开销太小,至少循环万次以上才有一段时间。不能用简单循环的原因:没预热(冷 JVM)/死代码消除(结果未被消费)/单次波动大(GC 恰好发生)/没统计(无法判断差异是否显著)。★举一反三:JMH 就是把这套规范做成框架——`@Benchmark` + `@Warmup` + `@Measurement` + `@Fork` + `Blackhole`。
>
