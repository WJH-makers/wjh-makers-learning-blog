# 《从零开始当工程师》03 · 苍穹外卖：用一条业务链证明基本功

> 连载特刊 · 第四部《从零开始当工程师》第一卷「把能力变成证据」第 3 话
> 长期项目：阿零从只会写代码，到带着咖啡站团队把事做成。

> 课程项目的价值不在于“我看过视频”，而在于你能从 HTTP 请求讲到数据落库，再讲到失败如何处理。

## 一、「这个项目我做过」

上一话结尾领姐问阿零：你能从一个 HTTP 请求，一路讲到数据落库吗？

阿零说能。他把跟课做完的外卖项目打开，准备讲。

> **〔1〕** 阿零把架构图投在墙上，图上十几个方框连成一片。
> 阿零（自信）：「这是我做的外卖系统。用户端、商家端、后台管理，一共四十多个接口。」
> 领姐：「挑一个。从用户点『提交订单』那一下开始，讲到数据库里多了一行。」
> 阿零：「呃……那是 `OrderController` 里的 `submit` 方法……」（停顿）「……然后它调 service……」

> **〔2〕** 阿零翻代码找了半分钟。
> 阿零：「找到了！这里，`orderService.submitOrder()`。它里面……」（往下滚，滚了很久）「……它里面有一百二十行。」
> 豆豆：「一百二十行你自己写的？」
> 阿零（诚实）：「……跟着敲的。」
> 豆豆：「跟着敲的和自己写的，区别就在你刚才那半分钟。」

> **〔3〕** 领姐没打断，等他滚完。
> 领姐：「我不问你写没写。我问你——**这一百二十行里，事务边界在哪一行开始？**」
> 阿零（找 `@Transactional`）：「……在方法上面。」
> 领姐：「那如果里面调了另一个类的方法，那个方法自己也标了 `@Transactional`，会开新事务还是用原来的？」
> 阿零：「……应该是……用原来的？」
> 领姐：「『应该是』。这三个字面试官一听就知道你没验证过。」

> **〔4〕** 豆豆插嘴：「让他现场试。改一行，跑一遍，看日志。」
> 阿零去试了。他故意让内层方法抛异常，想看外层会不会回滚。
> 结果：**没回滚**。订单表留了一行，库存却没扣。
> 阿零（傻了）：「……为什么？我 catch 住了啊，我 catch 完还打了日志……」
> 豆豆：「对啊。你 catch 住了。所以 Spring 觉得——**没出事**。」

> **〔5〕** 领姐把翅膀上的路线图翻到一页，上面画了一条线，线上有六个点。
> 领姐：「四十个接口，你一个都讲不透。一条链路讲透，你就有了四十个接口都通用的一套话。」
> 领姐：「**选一条，走到底。** 剩下三十九个，等你把这条讲明白，自然也就明白了。」

> [!吐槽] 豆豆：「四十个接口，听着像四十个成果。实际是同一件事没学会，重复了四十遍。」

## 二、本话目标

- 尊重项目的真实版本，不为"最新"强行升级。
- 锁定一条主链路，从入口讲到落库。
- 亲手改三处能产生解释的地方。
- 验证事务边界与异常回滚的真实行为。
- 备好五类随机追问的证据。

## 三、先尊重项目的真实版本

若课程项目的基线是 JDK 17 与 Spring Boot 2.7，就用它完成构建、测试和演示。Java 25 是本站技术文章的审计参考，不是把旧项目强行升级到新框架的理由。

开始前记录：

```text
java --version
./mvnw -v 或 mvn -v
数据库版本与初始化步骤
前端运行命令（若项目含前端）
```

版本对不上时先解决兼容问题；不要为了“技术栈最新”把 `javax`/`jakarta`、依赖版本和课程代码混在一起，再无法解释故障来源。

## 四、只挑一条主链路讲透

建议先锁定这一条：

```text
登录 → 身份校验 → 浏览商品 → 加购物车 → 提交订单 → 扣减/状态落库 → 返回订单结果
```

对每一步都能回答：入口控制器是谁？参数在哪里校验？身份如何传递？事务边界在哪？涉及哪些表？异常返回什么？

把这些答案画成一页图，比堆十张页面截图更有价值。

## 五、三个必须亲手改过的点

不要从功能列表里挑；挑能产生解释的改动：

1. **参数校验与错误响应**：非法数量、缺字段、无权限时不能默默成功。
2. **订单事务**：任一步失败后，订单状态与相关数据不能留下半成品。
3. **查询与索引**：为一个真实列表或订单查询看 `EXPLAIN`，再说明索引为何这样建。

每项改动保留“原问题 → 修改 → 验证 → 边界”四行记录。不能复现的改动不写进简历。

## 六、一次真实翻车：被 `catch` 吃掉的回滚

阿零那次现场试验，暴露的是一个课程项目里极常见的组合错误。他的代码大致是这样：

```java
@Transactional
public void submitOrder(OrderDTO dto) {
    orderMapper.insert(order);
    try {
        stockService.deduct(dto.getSkuId());   // 这里会抛
    } catch (Exception e) {
        log.error("扣库存失败", e);            // 吞了
    }
}
```

他的想法很朴素："扣库存失败了我记个日志，别让整个请求 500。"

问题是 Spring 的事务回滚是**靠异常传播出来**才触发的。异常被 `catch` 住没往外抛，事务管理器什么都没看见，于是正常提交——订单留下了，库存没扣。

这个坑还有个更隐蔽的变体：就算他不 `catch`，如果 `stockService.deduct` 是通过 `this.deduct()` 在同类内部调用的，`@Transactional` 也不生效，因为它走的是代理。这就是领姐问"事务边界在哪一行开始"的原因——**注解写在哪不等于事务从哪开始。**

> [!坑] 记住两条：异常被吞 = 不回滚；同类内部自调用 = 注解失效。这两条几乎是 Spring 事务面试的固定考点，也是课程项目最容易埋的雷。

## 七、复盘出根因

| 层次 | 内容 |
|---|---|
| 表象 | 订单表有数据，库存没扣，没人报错 |
| 直接原因 | `catch` 吞掉异常，事务管理器收不到回滚信号 |
| 根因 | 以为"处理了错误"等于"保住了一致性"，没区分**记录错误**和**中止操作** |
| 本可以怎样 | 要么让异常传播出去，要么显式 `setRollbackOnly()`，要么这一步根本不该放在同一事务里 |

引申出一条可复用的判断：**每次写 `catch`，问自己一句"吞掉之后，调用方会不会以为成功了"。** 如果会，那就不能只记日志。

> **💬 沟通拆解 · 课程项目怎么讲才不显得是跟做的**
>
> | 场景 | 常见说法（反面） | 问题出在哪 | 改写后 |
> |---|---|---|---|
> | 介绍项目 | 「我做了一个外卖系统，有四十多个接口。」 | 接口数量不证明理解，反而邀请随机抽查 | 「我以下单这条链路为主：从 Controller 参数校验、到事务边界、到库存扣减和异常回滚。这条我能逐行解释，其余模块是同一套模式。」 |
> | 被问细节卡住 | 「这块记不太清了，应该是……」 | "应该是"直接暴露没验证过 | 「这块我当时没深究。我的理解是走代理所以自调用会失效，但我没实测过——如果需要我可以现在写个例子验证。」 |
> | 讲改动 | 「我优化了订单模块。」 | 无从追问，也无从相信 | 「我改了三处：一是补了非法数量的参数校验，二是修了一个 catch 吞异常导致不回滚的 bug，三是给订单查询看了 EXPLAIN 后加了联合索引。每处都有改前改后的验证记录。」 |
>
> 一句套路小结：**用"我能讲透的一条链路"替代"我做过的四十个接口"，用"我修过的具体 bug"替代"我优化了某模块"。**

## 八、随机追问演练

| 追问 | 你必须落到的证据 |
|---|---|
| `@Transactional` 为什么生效/失效？ | 调用路径、代理边界、回滚规则 |
| 重复提交订单怎么办？ | 幂等键、唯一约束或状态机 |
| 慢查询怎么处理？ | SQL、执行计划、索引取舍 |
| 接口被滥用怎么办？ | 鉴权、参数校验、限流边界 |
| 订单创建后通知失败怎么办？ | 当前保证什么、暂不保证什么 |

不确定时先说当前实现的边界，再说明下一步验证方案。不要把单体课程项目说成已经具备分布式一致性。

## 九、交付清单

- `README`：环境、初始化、启动、演示账号/测试数据的安全处理方式。
- `ARCHITECTURE.md`：一条主链路和表关系。
- `PROJECT_EVIDENCE.md`：三次亲手改动、验证和边界。
- 一段五分钟录屏或现场演示路径。

做到这些，苍穹外卖就是合格的后端主项目；上一话的秒杀项目负责补并发与库存场景，下一话的 RSVQA 负责展示你的 AI 工程差异化。

> **🧭 路线台 · 这周你可以做的三件事**
>
> 1. 挑你项目里最长的那个 service 方法，画出它的事务边界：哪一行进入事务、哪些调用在同一事务里、哪一步失败会回滚到哪。画不出来就去实测——故意抛异常，看数据留没留。
> 2. 全局搜一遍 `catch (Exception`，逐个问"吞掉之后调用方会不会以为成功了"。至少找出一个会的，修掉，记下改前改后。
> 3. 下周自检一句：把下单这条链路讲给同学听，他能在中途插进来问"那这一步失败了会怎样"，而你每次都答得上来吗？
>
> 领姐结语：技术是船，方向是舵——先校准方向，再谈速度。

## 十、项目检查点

外卖项目此刻的状态：

- **已具备**：一条能从入口讲到落库的主链路；三处可解释的亲手改动；对事务边界与回滚的实测认知；版本环境固定可复现。
- **还没有**：分布式一致性（也不该声称）；缓存与索引的压测口径；通知失败的补偿机制。

阿零的变化：他不再用接口数量介绍项目。他开始说"我以这条链路为主"——从铺开炫耀，转向纵深证明。
