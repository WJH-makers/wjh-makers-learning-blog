## 一、需求:换台机器,一条命令把全家桶拉起来

咖啡平台现在是一群进程:下单、菜单、制作三个服务,外加 Nacos、Redis、Kafka、MySQL。阿零想在同事机器上演示,结果对方 JDK 版本不对、8080 端口被占、连不上 Redis——经典的"**在我电脑上是好的**"。

豆豆:「病根是**环境不可复现**。解法叫**容器**:把应用 + 它需要的运行时(JDK、依赖、配置)一起塞进一个**集装箱(镜像)**,箱子到哪台机器打开都一模一样。再用一份 `docker-compose.yml` 编排七八个箱子——换机器?**一条 `docker compose up`,全平台原地复活。** 这是第六季最后一块拼图。」

## 二、漫画 · 把整条街装进集装箱

> **〔1〕** 阿零拎着 U 盘挨家挨户拷代码装环境,装到第三台就崩溃:「JDK 25 呢?Redis 呢?端口又冲突了!」
> 豆豆(叼豆子):「你在手工搬家具。**该搬的是集装箱,不是散装家具。**」

> **〔2〕** 豆豆把每个服务连同 JDK、依赖、配置一起压进一个标准集装箱,贴上标签(镜像名 + 版本 tag)。
> 豆豆:「镜像是**只读模板**,容器是**跑起来的实例**——同一个镜像能开出一百个一样的容器。这就是'一次构建,处处运行',比字节码更彻底:连操作系统依赖都一起打包了。」

> **〔3〕** 阿零第一次构建,镜像**足足 900MB**——把整套 JDK、Maven、源码、构建缓存全塞进去了。
> 豆豆:「臃肿!用**多阶段构建**:第一阶段用带 Maven 的大箱子编译,第二阶段只把编好的 jar 拷进一个瘦小的 JRE 箱子,构建工具全扔掉。」

> **〔4〕** compose 一拉,七个容器同时亮灯……下单容器却连不上 Redis,红着脸报错。
> 阿零:「我明明写了 `localhost:6379`!」豆豆:「**在容器里,`localhost` 是它自己!** 容器之间要用**服务名**互相找。最后一个坑,踩完就毕业。」

- 用 **docker-compose** 一键编排全平台(应用 + 中间件);

## 四、原理图:多阶段构建 + Compose 编排

```text
【多阶段构建 · 一个服务】
  阶段1 build(大)         阶段2 runtime(小)
  ┌─────────────────┐     ┌──────────────────┐
  │ maven + JDK25    │     │ 只有 JRE25       │
  │ 拉依赖 → 编译打 jar│──▶ │ + 上一阶段的 app.jar│ ← 最终镜像只留这层
  └─────────────────┘     └──────────────────┘
      构建工具全丢弃            镜像从 ~900MB 瘦到 ~200MB

【Compose 编排 · 全平台】
  docker-compose.yml
    ├ mysql      ┐
    ├ redis      │  同一个自定义网络,彼此用"服务名"当主机名互访
    ├ kafka      │  (order-service 连 redis:6379,不是 localhost)
    ├ nacos      │
    ├ order-service ┘
    └ ...        →  一条 `docker compose up -d` 全部拉起
```

## 五、代码:多阶段 Dockerfile + compose

**① 每个服务的 `Dockerfile`(多阶段)**:

```dockerfile
# ---- 阶段 1:构建(用带 JDK + Maven 的大镜像编译) ----
FROM maven:3-eclipse-temurin-25 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn -q dependency:go-offline        # 先拉依赖:pom 没变时这层走缓存,构建飞快
COPY src ./src
RUN mvn -q clean package -DskipTests     # 打出 target/app.jar

# ---- 阶段 2:运行(只要一个瘦 JRE + 那个 jar) ----
FROM eclipse-temurin:25-jre
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar   # 只从上一阶段拷 jar,构建工具统统不要
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**② `docker-compose.yml`(编排全家桶,片段)**:

```yaml
services:
  redis:
    image: redis:7
    ports: ["6379:6379"]
  mysql:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: coffee
  order-service:
    build: ./order-service           # 用上面的 Dockerfile 构建
    depends_on: [redis, mysql, kafka, nacos]
    environment:
      SPRING_DATA_REDIS_HOST: redis   # ← 关键:主机名 = 服务名"redis",不是 localhost
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/coffee
    ports: ["8080:8080"]
```

一条命令拉起整个分布式咖啡平台:

```bash
docker compose up -d --build
```

## 六、故意制造一个 Bug:容器里的 localhost 指自己

沿用上一话本地开发的配置——`SPRING_DATA_REDIS_HOST: localhost`,直接搬进 compose:

```yaml
order-service:
  environment:
    SPRING_DATA_REDIS_HOST: localhost   # ← 本地能跑,一进容器就废
```

## 七、读懂真实报错:连接被拒

`order-service` 容器启动即崩,日志:

```text
org.springframework.data.redis.RedisConnectionFailureException:
  Unable to connect to Redis
Caused by: io.lettuce.core.RedisConnectionException:
  Unable to connect to localhost/127.0.0.1:6379
Caused by: java.net.ConnectException: Connection refused: localhost/127.0.0.1:6379
```

**根因:每个容器有自己独立的网络命名空间,容器里的 `localhost` = 这个容器自己**,而 Redis 跑在**另一个容器**里,当然连不上。Compose 会为所有服务建一个共享网络,并用**服务名**当 DNS 主机名——所以要连的是 `redis:6379`,不是 `localhost:6379`。把 `localhost` 改成 `redis`,重启即通。

> **豆豆锐评 · 容器网络的第一课**
> 三条铁律:① 容器内 `localhost` 只指自己,跨容器一律用**服务名**;② 宿主机访问容器靠 `ports` 端口映射(`8080:8080`);③ `depends_on` 只保证**启动顺序**,不保证依赖**已就绪**——生产要配**健康检查 + 重试**。第①条是新手进容器的头号坑,今天你踩平了。

## 八、验证:一键起平台,冒烟测试全绿

`docker compose up` 后,`docker ps` 应看到七个容器都在 `Up`。跑一个端到端冒烟测试打通全链路(下单 → 扣库存 → 发消息 → 制作),证明整套平台在容器里活着:

```java
@Test
void smoke_place_order_end_to_end() throws Exception {
    var client = HttpClient.newHttpClient();
    var req = HttpRequest.newBuilder()
        .uri(URI.create("http://localhost:8080/api/orders"))
        .header("Content-Type", "application/json")
        .POST(BodyPublishers.ofString("{\"name\":\"拿铁\",\"qty\":1}"))
        .build();
    var resp = client.send(req, BodyHandlers.ofString());
    assertEquals(200, resp.statusCode());        // 网关→下单→扣库存→发消息,全链路通
    assertTrue(resp.body().contains("orderId"));
}
```

> **豆豆旁白**:更工业的做法是 **Testcontainers**——测试里用 Docker 拉起真实 Redis/Kafka/MySQL 跑集成测试,测完自动销毁,第七季 CI 里还会见到它。

> **🔀 豆豆的多解台 · 让 Java 镜像又小又快,几条路?**

| 方案 | 做法 | 适合 | 代价 / 坑 |
|---|---|---|---|
| **多阶段构建**(本话) | build 阶段编译,runtime 阶段只留 JRE + jar | 几乎所有项目的默认起点 | 需合理分层利用缓存 |
| **分层 jar(layered)** | 把依赖层/应用层拆开 COPY,依赖不变时复用缓存 | 迭代频繁、想加速构建与推送 | Dockerfile 稍复杂 |
| **jlink 定制运行时** | 用 `jlink` 裁出只含所需模块的精简 JRE | 想再压一截镜像体积 | 要理清模块依赖 |
| **GraalVM Native Image** | 编成本地可执行文件,秒级启动、内存小 | Serverless / 快速弹性扩缩 | 构建慢、反射需配置、生态有坑 |

豆豆锐评:**默认就上"多阶段 + 分层 jar"**,性价比最高、几乎无副作用。追求极致启动速度和密度(如函数计算)再考虑 GraalVM native——但它的构建复杂度和反射坑,别在没需求时提前背。

> **🎯 面试直击**:容器和虚拟机有什么区别?
> **虚拟机**虚拟的是**硬件**,每台跑一个完整客户机操作系统,重、启动慢(分钟级)、隔离最强。**容器**共享宿主机内核,只隔离**进程/文件系统/网络**,轻、秒级启动、镜像小、密度高;隔离性弱于 VM。所以容器"接近裸机的性能 + 一致的环境",成了微服务和云原生的默认交付单元。追问镜像与容器:**镜像是只读模板(分层),容器是镜像跑起来的可写实例**——一个镜像可开多个容器。

### 一、选择题（10 道）

**1.** Dockerfile 中 `RUN` 指令的执行时机是什么？
- A) 容器启动时　B) 每次容器运行时　C) 镜像构建时（`docker build` 过程中）　D) 容器停止时

**2.** Dockerfile 中 `CMD` 和 `ENTRYPOINT` 的主要区别是什么？
- A) `CMD` 在构建时执行，`ENTRYPOINT` 在启动时执行　B) `CMD` 设置默认命令（可被 `docker run` 后的参数覆盖），`ENTRYPOINT` 设置固定入口（参数作为其附加）　C) 两者完全相同　D) `CMD` 只能用于前台进程，`ENTRYPOINT` 只能用于后台进程

**3.** 多阶段构建（multi-stage build）的主要优势是什么？
- A) 让 Dockerfile 看起来更专业　B) 构建阶段包含完整工具链（Maven/JDK），运行阶段只留 JRE + jar，大幅缩小最终镜像　C) 让镜像支持多个操作系统　D) 同时构建多个服务的镜像

**4.** Docker 镜像的"分层"机制带来了什么好处？
- A) 构建缓存复用——未变化的层走缓存，只重建变化的层　B) 多个镜像共享相同基础层节省磁盘　C) 推送时只上传变化的层　D) 以上都是

**5.** `docker-compose.yml` 中 `depends_on` 的作用是什么？
- A) 保证依赖服务已初始化完毕可接受请求　B) 控制服务启动顺序　C) 为服务分配固定 IP　D) 监控服务健康状态

**6.** 在 Docker Compose 编排中，容器内 `localhost` 指向什么？跨容器通信应该用什么？
- A) localhost 指向宿主机，跨容器用 IP　B) localhost 指向容器自己，跨容器用服务名（如 `redis`）　C) localhost 指向 Docker 网桥　D) 容器内没有 localhost 概念

**7.** Dockerfile 中 `EXPOSE 8080` 的作用是什么？
- A) 将容器的 8080 映射到宿主机　B) 声明该容器运行时监听 8080 端口（文档性质，不实际发布）　C) 限制容器只能使用 8080 端口　D) 关闭 8080 以外的所有端口

**8.** 多阶段构建中 `COPY --from=build /app/target/*.jar app.jar` 的含义是什么？
- A) 从宿主机复制 jar 到容器　B) 从名为 `build` 的构建阶段复制文件到当前阶段的镜像中　C) 从远程仓库下载依赖　D) 将 jar 拷贝为构建缓存

**9.** 以下哪个**不是** Dockerfile 的合法指令？
- A) `FROM`　B) `COPY`　C) `DEPLOY`　D) `ENV`

**10.** Docker 容器和虚拟机（VM）的本质区别是什么？
- A) 容器有完整独立操作系统内核，虚拟机共享宿主机内核　B) 虚拟机虚拟硬件（每个跑完整操作系统），容器共享宿主机内核只隔离进程/文件系统/网络，更轻量　C) 两者没有区别　D) 虚拟机比容器启动更快

> [!答案]
> **1-C**　`RUN` 在镜像构建阶段（`docker build`）执行，用于安装软件包、编译代码等。每条 `RUN` 产生一个新镜像层。启动时默认命令由 `CMD`/`ENTRYPOINT` 指定。　举一反三：容器启动时执行的脚本应用 `CMD`/`ENTRYPOINT`，非 `RUN`——`RUN` 只在构建时一次，结果固化在镜像里。
> 
> **2-B**　`CMD` 是可被覆盖的默认命令；`ENTRYPOINT` 是固定入口，`docker run` 参数会追加到其后。最佳实践：`ENTRYPOINT ["java", "-jar", "app.jar"]` + `CMD ["--spring.profiles.active=dev"]`。　举一反三：这样用户可 `docker run myimage --spring.profiles.active=prod` 只覆盖参数不改入口。
> 
> **3-B**　从 ~900MB（带 Maven+源码+构建缓存）瘦到 ~200MB（只有 JRE+app.jar）。第一阶段用完整 JDK+Maven 的大镜像编译，第二阶段 `COPY --from=build` 只拷产物到瘦小 JRE 镜像中。　举一反三：多阶段构建还缩小了攻击面——运行镜像里无编译器，即使被攻破也做不了太多事（最小化原则）。
> 
> **4-D**　分层三大利好：① 构建缓存复用——变频率低的层放前面（先 COPY pom.xml 拉依赖），改代码只重建编译层；② 存储共享——多镜像共享同一基础层（如都基于 `eclipse-temurin:25-jre`）；③ 增量推送——只推送变化的层。　举一反三：合理排层是 Dockerfile 优化的关键——把变化少的指令放前面最大化缓存命中。
> 
> **5-B**　`depends_on` 只控制容器启动的先后顺序，不保证依赖服务"已就绪"。MySQL 容器启动了不等于进程已能接受连接（初始化可能还要几秒）。　举一反三：Spring Boot 可用 `initialization-fail-timeout: -1`（一直重试），或 Docker Compose v3.9+ 用 `healthcheck` + `condition: service_healthy` 解决启动时序。
> 
> **6-B**　每个容器有独立网络命名空间，容器内 `localhost` = 容器自己。本话 Bug 就是本地开发写了 `localhost:6379`，搬进 Compose 后连 Redis 被拒——Redis 在另一个容器里。Compose 创建共享网络用服务名做 DNS，所以写 `redis:6379`。　举一反三：三条铁律——① 跨容器用服务名；② 宿主机访问容器用端口映射；③ `depends_on` 不等同于就绪。
> 
> **7-B**　`EXPOSE` 是声明性指令——告诉使用者"这个镜像的应用监听 8080"，本身不做端口映射。真正映射靠 `docker run -p 8080:8080` 或 Compose 的 `ports`。　举一反三：`EXPOSE` 虽看似"没啥用"，但 Dockerfile 最佳实践推荐加上——它是镜像的"文档"，让使用者一眼知道暴露哪些端口。
> 
> **8-B**　`--from=build` 引用前面 `FROM ... AS build` 定义的构建阶段。只把编译好的 jar 拷到运行阶段，Maven、源码、构建缓存全不带走。　举一反三：`--from` 也可引用外部镜像，如 `COPY --from=nginx:latest /etc/nginx/nginx.conf /`，从任意镜像拷贝文件。
> 
> **9-C**　`DEPLOY` 不是 Dockerfile 指令。合法指令：`FROM`、`COPY`、`RUN`、`CMD`、`ENTRYPOINT`、`ENV`、`EXPOSE`、`WORKDIR`、`ADD`、`ARG` 等。　举一反三：不混淆 Dockerfile 指令和 compose 关键字——`deploy` 存在于 compose 文件中（Swarm 模式），不是 Dockerfile 指令。
> 
> **10-B**　VM 虚拟硬件层，每个 VM 跑完整客户操作系统（含内核），重、分钟级启动、隔离最强。容器共享宿主机内核，只做进程/文件系统/网络命名空间隔离，轻、秒级启动、密度高、接近裸机性能——隔离性弱于 VM。　举一反三：容器"一次构建处处运行"——镜像包含应用+运行时（JDK、lib、配置），不依赖宿主机环境。

### 二、解答题（3 道）

**1.** 解释 Docker 镜像的"分层"机制，以及它对构建缓存和存储的具体好处。

**2.** 描述容器和虚拟机的本质区别，以及为什么容器成为云原生和微服务的默认交付单元。

**3.** 在 Docker Compose 中，为什么容器内用 `localhost` 连不到另一个容器里的服务？跨容器通信的正确方式是什么？

> [!答案]
> **1**　Docker 镜像由多个只读层堆叠而成，每条指令（`RUN`、`COPY`、`ADD`）创建一个新层，容器启动时在最上层加可写层。分层好处：① 构建缓存——某层输入没变（如 `COPY pom.xml` 后 pom.xml 没改），Docker 直接复用缓存跳过该层及以下重建，构建大幅提速；② 存储共享——多个镜像使用相同基础层，主机上只存一份节省磁盘；③ 增量推送——只上传变化的层。Dockerfile 优化技巧：先 `COPY pom.xml`→拉依赖→再 `COPY src`→编译——改代码只重建编译层。　举一反三：合理排层（变频率低的放前面、高的放后面）能最大化缓存命中率。
> 
> **2**　本质区别：VM 虚拟硬件，每台 VM 跑完整客户操作系统（含独立内核），隔离性强但重（GB 级镜像、分钟级启动）；容器共享宿主机内核只隔离进程/文件系统/网络，轻量（MB 级镜像、秒级启动、高密度）但隔离性弱。容器成为云原生默认交付单元的原因：① 环境一致性——"一次构建处处运行"消除环境差异；② 快速弹性——秒级启动适合自动扩缩和滚动发布；③ 资源利用率高——一台物理机可跑几十上百个容器远多于 VM；④ 编排友好——Kubernetes 等以容器为最小调度单元。　举一反三：安全隔离要求极高场景（如多租户公有云）仍用 VM——容器共享内核的隔离性不足以满足严格安全边界。
> 
> **3**　每个容器有独立网络命名空间（Network Namespace），容器 A 里的 `localhost` 指向 A 自己的环回接口——只和 A 内部进程通信，无法访问其他容器的网络栈。Compose 将所有服务放在同一自定义网络并用服务名作为 DNS 主机名。正确方式：写服务名（如 `redis:6379`），Docker 内置 DNS 把服务名解析为对应容器的内部 IP。宿主机访问容器用 `ports` 做端口映射。　举一反三：三条铁律——① 容器内 localhost=自己；② 跨容器用服务名；③ 宿主机用端口映射。这是容器网络入门第一课。

### 三、代码题（2 道）

**1.** 为 Spring Boot 应用写一个多阶段构建的 Dockerfile：第一阶段用 `maven:3-eclipse-temurin-25` 编译，第二阶段用 `eclipse-temurin:25-jre` 运行，合理利用分层缓存。

**2.** 写一个 `docker-compose.yml`，编排一个 Spring Boot 应用（用当前目录 Dockerfile 构建）和一个 MySQL（`mysql:8`）服务，应用通过服务名 `db` 连接 MySQL，MySQL 设置 root 密码和数据库名。

> [!答案]
> **1 验收**　```dockerfile
> # ---- 阶段 1：构建 ----
> FROM maven:3-eclipse-temurin-25 AS build
> WORKDIR /app
> COPY pom.xml .
> RUN mvn -q dependency:go-offline         # 先拉依赖，pom不变走缓存
> COPY src ./src
> RUN mvn -q clean package -DskipTests     # 改代码只重建这层
> 
> # ---- 阶段 2：运行 ----
> FROM eclipse-temurin:25-jre
> WORKDIR /app
> COPY --from=build /app/target/*.jar app.jar  # 只拷jar，构建工具全丢
> EXPOSE 8080
> ENTRYPOINT ["java", "-jar", "app.jar"]
> ```　举一反三：进阶瘦身——用 `jlink` 定制 JRE 只含用到的模块，或用 GraalVM Native Image 编译成本地可执行文件。多数项目多阶段构建足够。
> 
> **2 验收**　```yaml
> services:
>   app:
>     build: .
>     ports: ["8080:8080"]
>     environment:
>       SPRING_DATASOURCE_URL: jdbc:mysql://db:3306/coffee  # 服务名db，非localhost
>       SPRING_DATASOURCE_USERNAME: root
>       SPRING_DATASOURCE_PASSWORD: root123
>     depends_on: [db]
>   db:
>     image: mysql:8
>     environment:
>       MYSQL_ROOT_PASSWORD: root123
>       MYSQL_DATABASE: coffee
>     volumes:
>       - mysql-data:/var/lib/mysql   # 数据持久化
> volumes:
>   mysql-data:
> ```　举一反三：`depends_on` 不保证就绪——生产需加 `healthcheck` 或在应用端配置连接重试。一行命令 `docker compose up -d --build` 拉起全家桶。
