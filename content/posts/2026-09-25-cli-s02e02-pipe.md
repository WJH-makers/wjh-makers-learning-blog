## 一、需求:别再来回搬水桶了

上一话阿零学会用 grep 照出所有访问记录。可豆豆的新要求是:**只留 IP → 去重 → 数出谁访问最多**。阿零的做法是——先把 grep 结果存进 `tmp1.txt`,打开它 cut 出 IP 存进 `tmp2.txt`,再打开排序去重……**来回搬了三趟中转文件**,桌面堆满 `tmp` 垃圾。

特米看不下去了:「你每一步都在**把水舀进桶、搬过去、再倒出来**。Unix 六十年前就解决了这事——**让水自己顺着管子流**。」话音未落,一个戴安全帽、扛着一根竖管的角色从终端里冒出来。

---

## 二、漫画 · 管道工登场

> **〔1〕** 阿零面前摆着三个中转文件 `tmp1 tmp2 tmp3`,他正手忙脚乱地 `cat` 完一个再喂下一个。
> 阿零:「先存起来,再打开,再处理……怎么这么累?」

> **〔2〕** 一个扛着竖管、戴黄色安全帽的机器人「哐」地落地,管身上刻着一道竖线 `|`。
> 管道工:「我是**管道工**。你那些中转桶,全扔了。看好——」他把竖管往两个命令中间一插。

> **〔3〕** 管道工敲下 `cut -d' ' -f1 access.log | sort | uniq -c | sort -rn`。四个命令像四节水管接上,水一路流到底,直接吐出排名。
> 阿零:「没有一个中转文件?!」管道工:「`|` 就是**把左边的嘴接到右边的耳朵**。一个命令的输出,是下一个的输入。」

> **〔4〕** 特米在旁补刀:「这就是 **Unix 哲学**——每个小工具只干一件事、干到极致,`|` 负责把它们串成流水线。`cut` 只会切,`sort` 只会排,`uniq` 只会去重。**它们不认识彼此,管道让它们协作。**」

> **〔5〕** 阿零想把结果存下来,敲 `... > report.txt`,存成功了。可他手一抖,想再追加一行统计时又敲了一次 `> report.txt`,回车——一整天攒的报表**瞬间只剩最后一行**。
> 阿零(脸白):「我的报表!」管道工(扶额):「`>` 是**推土机**,进门先铲平。你要的是 `>>`,**接在后面**。」

> **〔6〕** 特米指着屏幕角落一行没进文件的红字报错:「还有,错误信息走的是**另一根管子**(stderr)。想把它也收进文件,得喊 `2>&1`——把 2 号管接到 1 号管上。」

> **〔7〕** 阿零把命令改成 `... >> report.txt 2>&1`,正常输出和错误一起乖乖进了文件。
> 管道工扛起竖管:「记住三样:`|` 串流水线、`>`/`>>` 落文件、`2>&1` 连错误。**这三样,是终端从玩具变成生产力的分水岭。**」

## 三、本话目标

- 理解 `|`:把左命令的**标准输出**直接接到右命令的**标准输入**,串成流水线;
- 掌握重定向:`>` 覆盖写、`>>` 追加写,把「屏幕」改道到「文件」;
- 认清三根管子:stdin(0)、stdout(1)、stderr(2),会用 `2>&1` 合并;
- 踩一个致命坑:`>` 覆盖 vs `>>` 追加,一字之差、数据全丢;
- 内化 **Unix 哲学**:小工具各司其职,管道负责组合。

---

## 四、原理图:三根管子与一竖管

```text
每个命令天生长着三个口(文件描述符):
   0  stdin   标准输入   ← 从这里读
   1  stdout  标准输出   → 正常结果从这里出
   2  stderr  标准错误   → 报错从这里出(独立的一根!)

管道 |  ：把左边的 1 号口,接到右边的 0 号口
   命令A ──stdout(1)──▶│──stdin(0)──▶ 命令B

重定向 ：把某根管子引到文件,而不是屏幕
   命令 > file     1号口 → 覆盖写入 file(先清空!)
   命令 >> file    1号口 → 追加到 file 末尾
   命令 2> file    2号口(错误) → 写入 file
   命令 > file 2>&1  先把1号引到file,再让2号"跟着1号走"
```

一句话:**`|` 在命令之间接管子,`>`/`>>` 把管子引到文件,`2>&1` 把错误管并进正常管。**

## 五、上手:把三趟搬运压成一条流水线

阿零那个「谁访问最多」的需求,一行搞定:

```bash
$ cut -d' ' -f1 logs/access.log | sort | uniq -c | sort -rn
      3 192.168.1.11
      3 192.168.1.10
      2 192.168.1.12
      1 192.168.1.14
      1 192.168.1.13
```

拆开看这条流水线的四个工位(下一话专门练):`cut` 切出第 1 列 IP → `sort` 排好(让相同的挨一起)→ `uniq -c` 去重并计数 → `sort -rn` 按数字倒序。**没有一个中转文件。**

把结果落地:

```bash
$ cut -d' ' -f1 logs/access.log | sort | uniq -c | sort -rn > top-ip.txt   # 落成报表
$ cat top-ip.txt          # 复查
      3 192.168.1.11
      ...
$ date >> top-ip.txt      # 追加一行时间戳,>> 不会铲平已有内容
```

> **特米旁白**:`|` 传的是**文本流**,一行一行往下淌。所以流水线上每个工具都设计成「读一行、处理一行、吐一行」——这才是它们能无限串接的底层原因。

## 六、故意制造一个 Bug:用 > 追加

阿零攒了一天的报表在 `report.txt` 里,他想再补一段统计,凭感觉又敲了一次单箭头:

```bash
$ echo "line1" > report.txt
$ echo "line2" > report.txt      # 本想追加,结果又覆盖了一次
```

## 七、读懂真实报错

这个坑**不报错**——这才是它最阴险的地方。文件安安静静地只剩最后一次写入的内容:

```bash
$ cat report.txt
line2
```

`line1` 无声无息地没了。根因:`>` 每次都**先把文件清空(truncate)再写**,它是推土机不是订书机。终端不会拦你,`echo $?` 也返回 0——**一切"成功",数据却没了**。这类「静默数据丢失」比报错难查十倍。修法只有一个字的差别,把覆盖改成追加:

```bash
$ echo "line1" > report.txt      # 第一次建文件,用 > 开个头
$ echo "line3" >> report.txt     # 之后一律用 >> 追加
$ cat report.txt
line1
line3
```

**口诀:开头一次 `>`,之后全 `>>`。** 尤其对日志、报表这种「只增不减」的文件,手一滑打成 `>` 就是一场事故。

再看 `2>&1` 的必要性——只用 `>` 时,错误根本进不了文件:

```bash
$ ls /tmp/nope.txt > only-stdout.log        # 文件不存在
ls: cannot access '/tmp/nope.txt': No such file or directory   ← 错误漏到了屏幕
$ cat only-stdout.log
                                             ← 文件是空的!错误走的是 2 号管
$ ls /tmp/nope.txt > merged.log 2>&1         # 把 2 号并进 1 号
$ cat merged.log
ls: cannot access '/tmp/nope.txt': No such file or directory   ← 这下收进来了
```

> **🪟 双系统对照 · bash 文本管道 ↔ PowerShell 对象管道(本线最精彩的一处)**

这是两个系统**世界观级别**的差异,值得单独讲透:

| 维度 | Linux (bash) | PowerShell 7 |
|---|---|---|
| 管道里流的是 | **纯文本**,一行一行 | **对象**(带属性和方法) |
| 取「第一列」 | `cut -d' ' -f1`(靠切字符) | `Select-Object -First 1` 或 `$_.Name`(靠属性名) |
| 排序 | `sort`(按字符串,数字要 `-n`) | `Sort-Object CPU`(按对象属性,类型自动对) |
| 落文件 | `> file` / `>> file` | `> file` / `>> file`(同款语法!)或 `Out-File` |
| 合并错误 | `2>&1` | `2>&1`(PS 也支持) |

对比同一个需求「找占 CPU 最高的进程」:

```bash
# bash:进程信息是文本,得靠列号切
ps aux | sort -rnk3 | head -3
```

```powershell
# PowerShell:进程是对象,直接点属性名,不用数第几列
Get-Process | Sort-Object CPU -Descending | Select-Object -First 3
```

bash 里你在**切字符串**,列一变就崩;PowerShell 里你在**筛对象属性**,不怕列错位——代价是它更重、跨机器不一定有。**服务器上是 bash 文本流的天下,这套「切列」的手感必须练熟。**

> **🎯 面试直击**:说说 Unix 的管道哲学 / `|` 和 `>` 有什么区别?
> `|` 把上一个命令的输出接到下一个命令的**输入**(命令→命令);`>` 把输出写到**文件**(命令→文件)。背后是 Unix 哲学:每个程序只做好一件事,用管道把小工具组合成复杂流水线,而不是造一个大而全的程序。追问:`2>&1` 顺序为何不能写成 `2>&1 > file`?因为重定向从左到右生效,那样 2 号会先跟到「还没改道的屏幕」,错误就漏了。

## 八、用命令验证:水真的流到位了吗

```bash
$ cut -d' ' -f1 logs/access.log | sort | uniq -c | sort -rn | wc -l   # 有几个不同 IP
5
$ echo $?          # 管道的退出码 = 最后一个命令的退出码
0
$ ls /tmp/clilab | wc -l    # 经典组合:列目录 | 数行数 = 数文件个数
6
```

> **特米旁白**:`echo $?` 在管道里看的是**最后一节**的成败。前面某节挂了、最后一节成功,`$?` 仍是 0——想逐节把关是后面 `set -o pipefail` 的事,先记住这个默认脾气。
