## 一、需求:别再来回搬水桶了

上一话阿零学会用 grep 照出所有访问记录。可豆豆的新要求是:**只留 IP → 去重 → 数出谁访问最多**。阿零的做法是——先把 grep 结果存进 `tmp1.txt`,打开它 cut 出 IP 存进 `tmp2.txt`,再打开排序去重……**来回搬了三趟中转文件**,桌面堆满 `tmp` 垃圾。

特米看不下去了:「你每一步都在**把水舀进桶、搬过去、再倒出来**。Unix 六十年前就解决了这事——**让水自己顺着管子流**。」话音未落,一个戴安全帽、扛着一根竖管的角色从终端里冒出来。

## 二、漫画 · 管道工登场

> **〔1〕** 阿零面前摆着三个中转文件 `tmp1 tmp2 tmp3`,他正手忙脚乱地 `cat` 完一个再喂下一个。
> 阿零:「先存起来,再打开,再处理……怎么这么累?」

> **〔2〕** 一个扛着竖管、戴黄色安全帽的机器人「哐」地落地,管身上刻着一道竖线 `|`。
> 管道工:「我是**管道工**。你那些中转桶,全扔了。看好——」他把竖管往两个命令中间一插。

> **〔3〕** 管道工敲下 `cut -d' ' -f1 access.log | sort | uniq -c | sort -rn`。四个命令像四节水管接上,水一路流到底,直接吐出排名。
> 阿零:「没有一个中转文件?!」管道工:「`|` 就是**把左边的嘴接到右边的耳朵**。一个命令的输出,是下一个的输入。」

> **〔4〕** 特米在旁补刀:「这就是 **Unix 哲学**——每个小工具只干一件事、干到极致,`|` 负责把它们串成流水线。`cut` 只会切,`sort` 只会排,`uniq` 只会去重。**它们不认识彼此,管道让它们协作。**」

> **〔5〕** 阿零想把结果存下来,敲 `... > report.txt`,存成功了。可他手一抖,想再追加一行统计时又敲了一次 `> report.txt`,回车——一整天攒的报表**瞬间只剩最后一行**。
> 阿零(脸白):「我的报表!」管道工(扶额):「`>` 是**推土机**,进门先铲平。你要的是 `>>`,**接在后面**。」

> **〔6〕** 特米指着屏幕角落一行没进文件的红字报错:「还有,错误信息走的是**另一根管子**(stderr)。想把它也收进文件,得喊 `2>&1`——把 2 号管接到 1 号管上。」

> **〔7〕** 阿零把命令改成 `... >> report.txt 2>&1`,正常输出和错误一起乖乖进了文件。
> 管道工扛起竖管:「记住三样:`|` 串流水线、`>`/`>>` 落文件、`2>&1` 连错误。**这三样,是终端从玩具变成生产力的分水岭。**」

## 三、本话目标

- 理解 `|`:把左命令的**标准输出**直接接到右命令的**标准输入**,串成流水线;
- 掌握重定向:`>` 覆盖写、`>>` 追加写,把「屏幕」改道到「文件」;
- 认清三根管子:stdin(0)、stdout(1)、stderr(2),会用 `2>&1` 合并;
- 踩一个致命坑:`>` 覆盖 vs `>>` 追加,一字之差、数据全丢;
- 内化 **Unix 哲学**:小工具各司其职,管道负责组合。

## 四、原理图:三根管子与一竖管

```text
每个命令天生长着三个口(文件描述符):
   0  stdin   标准输入   ← 从这里读
   1  stdout  标准输出   → 正常结果从这里出
   2  stderr  标准错误   → 报错从这里出(独立的一根!)

管道 |  ：把左边的 1 号口,接到右边的 0 号口
   命令A ──stdout(1)──▶│──stdin(0)──▶ 命令B

重定向 ：把某根管子引到文件,而不是屏幕
   命令 > file     1号口 → 覆盖写入 file(先清空!)
   命令 >> file    1号口 → 追加到 file 末尾
   命令 2> file    2号口(错误) → 写入 file
   命令 > file 2>&1  先把1号引到file,再让2号"跟着1号走"
```

一句话:**`|` 在命令之间接管子,`>`/`>>` 把管子引到文件,`2>&1` 把错误管并进正常管。**

## 五、上手:把三趟搬运压成一条流水线

阿零那个「谁访问最多」的需求,一行搞定:

```bash
$ cut -d' ' -f1 logs/access.log | sort | uniq -c | sort -rn
      3 192.168.1.11
      3 192.168.1.10
      2 192.168.1.12
      1 192.168.1.14
      1 192.168.1.13
```

拆开看这条流水线的四个工位(下一话专门练):`cut` 切出第 1 列 IP → `sort` 排好(让相同的挨一起)→ `uniq -c` 去重并计数 → `sort -rn` 按数字倒序。**没有一个中转文件。**

把结果落地:

```bash
$ cut -d' ' -f1 logs/access.log | sort | uniq -c | sort -rn > top-ip.txt   # 落成报表
$ cat top-ip.txt          # 复查
      3 192.168.1.11
      ...
$ date >> top-ip.txt      # 追加一行时间戳,>> 不会铲平已有内容
```

> **特米旁白**:`|` 传的是**文本流**,一行一行往下淌。所以流水线上每个工具都设计成「读一行、处理一行、吐一行」——这才是它们能无限串接的底层原因。

## 七、读懂真实报错

这个坑**不报错**——这才是它最阴险的地方。文件安安静静地只剩最后一次写入的内容:

```bash
$ cat report.txt
line2
```

`line1` 无声无息地没了。根因:`>` 每次都**先把文件清空(truncate)再写**,它是推土机不是订书机。终端不会拦你,`echo $?` 也返回 0——**一切"成功",数据却没了**。这类「静默数据丢失」比报错难查十倍。修法只有一个字的差别,把覆盖改成追加:

```bash
$ echo "line1" > report.txt      # 第一次建文件,用 > 开个头
$ echo "line3" >> report.txt     # 之后一律用 >> 追加
$ cat report.txt
line1
line3
```

**口诀:开头一次 `>`,之后全 `>>`。** 尤其对日志、报表这种「只增不减」的文件,手一滑打成 `>` 就是一场事故。

再看 `2>&1` 的必要性——只用 `>` 时,错误根本进不了文件:

```bash
$ ls /tmp/nope.txt > only-stdout.log        # 文件不存在
ls: cannot access '/tmp/nope.txt': No such file or directory   ← 错误漏到了屏幕
$ cat only-stdout.log
                                             ← 文件是空的!错误走的是 2 号管
$ ls /tmp/nope.txt > merged.log 2>&1         # 把 2 号并进 1 号
$ cat merged.log
ls: cannot access '/tmp/nope.txt': No such file or directory   ← 这下收进来了
```

> **🪟 双系统对照 · bash 文本管道 ↔ PowerShell 对象管道(本线最精彩的一处)**

这是两个系统**世界观级别**的差异,值得单独讲透:

| 维度 | Linux (bash) | PowerShell 7 |
|---|---|---|
| 管道里流的是 | **纯文本**,一行一行 | **对象**(带属性和方法) |
| 取「第一列」 | `cut -d' ' -f1`(靠切字符) | `Select-Object -First 1` 或 `$_.Name`(靠属性名) |
| 排序 | `sort`(按字符串,数字要 `-n`) | `Sort-Object CPU`(按对象属性,类型自动对) |
| 落文件 | `> file` / `>> file` | `> file` / `>> file`(同款语法!)或 `Out-File` |
| 合并错误 | `2>&1` | `2>&1`(PS 也支持) |

对比同一个需求「找占 CPU 最高的进程」:

```bash
# bash:进程信息是文本,得靠列号切
ps aux | sort -rnk3 | head -3
```

```powershell
# PowerShell:进程是对象,直接点属性名,不用数第几列
Get-Process | Sort-Object CPU -Descending | Select-Object -First 3
```

bash 里你在**切字符串**,列一变就崩;PowerShell 里你在**筛对象属性**,不怕列错位——代价是它更重、跨机器不一定有。**服务器上是 bash 文本流的天下,这套「切列」的手感必须练熟。**

> **🎯 面试直击**:说说 Unix 的管道哲学 / `|` 和 `>` 有什么区别?
> `|` 把上一个命令的输出接到下一个命令的**输入**(命令→命令);`>` 把输出写到**文件**(命令→文件)。背后是 Unix 哲学:每个程序只做好一件事,用管道把小工具组合成复杂流水线,而不是造一个大而全的程序。追问:`2>&1` 顺序为何不能写成 `2>&1 > file`?因为重定向从左到右生效,那样 2 号会先跟到「还没改道的屏幕」,错误就漏了。

## 八、用命令验证:水真的流到位了吗

```bash
$ cut -d' ' -f1 logs/access.log | sort | uniq -c | sort -rn | wc -l   # 有几个不同 IP
5
$ echo $?          # 管道的退出码 = 最后一个命令的退出码
0
$ ls /tmp/clilab | wc -l    # 经典组合:列目录 | 数行数 = 数文件个数
6
```

> **特米旁白**:`echo $?` 在管道里看的是**最后一节**的成败。前面某节挂了、最后一节成功,`$?` 仍是 0——想逐节把关是后面 `set -o pipefail` 的事,先记住这个默认脾气。

### 解答题(5 道)

**Q1 概念:** 简述 stdin(0)、stdout(1)、stderr(2) 三者各自的作用和默认目标。

**Q2 解释:** 为什么 `cmd > file 2>&1` 的重定向顺序重要?如果把 `2>&1` 放在 `> file` 前面会发生什么?

**Q3 操作:** 写出将当前目录下所有 `.log` 文件的行数统计(文件名+行数)输出到 `report.txt`,同时在终端也能看到的命令。

> [!答案]
> **1-A** `|` 将前一个命令的标准输出(stdout)连接到后一个命令的标准输入(stdin)。**举一反三:**`|` 是 Unix 最核心的发明之一,让简单命令可以像乐高积木一样组合。🪟 PowerShell 同样支持 `|`。
>
> **2-C** 文件描述符:0=stdin(标准输入),1=stdout(标准输出),2=stderr(标准错误输出)。**举一反三:**`cmd 2>&1` 读作"把 fd 2(stderr)重定向到 fd 1(stdout)的当前位置"。
>
> **3-B** `>` 默认重定向 stdout。**举一反三:**`> file` 是 `1> file` 的简写;`2> file` 重定向 stderr;`&> file` 同时重定向 stdout 和 stderr(Bash 特有)。
>
> **4-B** `>&` 是重定向到文件描述符的语法(后跟 fd 编号);`>` 后跟文件名表示重定向到文件。所以 `2>1` 创建/覆盖名为 `1` 的文件。**举一反三:**`>&` 中 `&` 的作用是区分"文件描述符编号"和"普通文件名"——`2>1`(写到文件 1) vs `2>&1`(重定向到 fd 1)。
>
> **5-B** `2> error.log` 只重定向 stderr,stdout 仍走默认路径(终端)。**举一反三:**`cmd 2> /dev/null` 静默错误(忽略错误信息),常用于脚本。🪟 PowerShell 等价:`cmd 2> error.log` 需要在参数中指定 `-ErrorVariable` 或 redirect。
>
> **6-B** 数据从左向右流过管道:`cat file.txt`→`sort`(排序)→`uniq`(去重)。**举一反三:**管道是串行处理,前一个命令的输出成为后一个命令的输入,每个命令处理完自己的部分后数据才流向下一个。这与多线程并行完全不同。
>
> **7-B** Unix 哲学:每个工具只做好一件事,通过管道(pipe)组合完成复杂任务。**举一反三:**"小即美"(Small is beautiful)是 Doug McIlroy 提出的 Unix 理念。`sort | uniq -c | sort -rn | head` 这种"数据流管线"就是这种哲学的典型体现。
>
> **8-B** 顺序至关重要。`cmd > file.log 2>&1`:先把 stdout 指向 file.log,再把 stderr 指向 stdout(此时 stdout 已指向 file.log)→结果:两者都进 file.log。`cmd 2>&1 > file.log`:先把 stderr 指向"当前 stdout"(即终端),再把 stdout 指向 file.log→结果:只有 stdout 进 file.log,stderr 仍在终端。**举一反三:**重定向顺序可以理解为"快照"——`2>&1` 复制的是当时 stdout 指向的目标。
>
> **9-D** `&> /dev/null` 是 Bash 中同时重定向 stdout+stderr 的简洁写法。**举一反三:**`/dev/null` 是 Linux 的"黑洞",任何写入的数据都会被丢弃。C 选项 `> /dev/null 2>&1` 效果相同,更兼容 POSIX。🪟 Windows 中 `/dev/null` 等价物是 `$null`。
>
> **10-D** `tee` 可以将输出同时写入文件和终端。A:`2>&1` 先将 stderr 合并到 stdout,然后 tee 同时写入文件和终端。B:`| tee` 只能处理管道传来的 stdout,stderr 没有被合并到管道,所以错误信息在终端能看到但 tee 捕获不到。B 无法实现"把错误也记录到文件"。**举一反三:**想全面记录且终端可见,推荐用 `script` 或用 `cmd 2>&1 | tee file.log`。
>
> **Q1** stdin(0):命令的标准输入源,默认来自键盘;可被 `<` 或管道重定向。stdout(1):命令的正常输出目标,默认显示在终端;可被 `>` `>>` 或管道重定向。stderr(2):命令的错误输出目标,默认也显示在终端(与 stdout 混在一起);可被 `2>`单独重定向。**三者分离**的设计让你可以把正常数据和错误信息分流处理。
>
> **Q2** 重定向顺序决定"复制点"。`> file`重定向 stdout 到文件;`2>&1` 让 stderr 指向"stdout 的当前目标"。先 `> file` 再 `2>&1`:都进文件。先 `2>&1` 再 `> file`:stderr 锁死在终端,stdout 被重定向到文件。**口诀:**先改目标,再跟风。**记忆方法:**把 `2>&1` 理解为"stderr,你跟 stdout 走",此时 stdout 去哪它就跟着去哪。
>
> **Q3** 命令:`wc -l *.log | tee report.txt`。`wc -l *.log` 统计行数;`tee report.txt` 同时输出到终端和文件。**举一反三:**`tee -a` 追加而非覆盖;`tee` 在脚本调试中非常有用——把中间结果记录下来同时还能看到。
>
> **Q4** 原因:顺序错了。`2>&1` 先执行,stderr 被复制到"当时的 stdout"(终端);然后 `> results.txt` 改变 stdout 的目标,但 stderr 已经锁死在终端。**修正:**`find / -name "*.conf" > results.txt 2>&1`。这样先让 stdout 进 results.txt,再让 stderr 跟随 stdout。**举一反三:**对于 `find`,更优雅的做法是用 `2> /dev/null` 直接丢弃错误,因为 "Permission denied" 是预期行为而非真正的错误。
>
> **Q5** 命令:`grep -r "ERROR" /var/log/ --include="*.log" | grep -v "DEBUG" | cut -d: -f1 | sort | uniq -c | sort -rn | head -n 5 | tee top_errors.txt`。解析:①递归搜索 ERROR ②`-v` 排除 DEBUG ③`cut -d: -f1` 提取文件名(grep 默认输出 `filename:line`) ④`sort|uniq -c` 统计每个文件出现次数 ⑤`sort -rn|head -5` 取 Top 5 ⑥`tee` 同时保存。**举一反三:**这是 "管道编程" 的经典模式——每一步只做一个简单操作,串联起来完成复杂分析。
