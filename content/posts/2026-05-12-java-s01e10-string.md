## 三、本话目标

- 理解 String **不可变**,以及「每次修改都是新建对象」;
- 分清 `==`(比引用/同一只罐子)与 `equals`(比内容);
- 破除迷信:搞清 `+` 拼接在现代 JDK 到底慢不慢、`StringBuilder` 该用在哪;
- 用文本块 `"""..."""` 排版多行小票;
- 踩一次用 `==` 比较字符串内容的逻辑坑。

## 四、原理图:一次「修改」发生了什么

```text
String s = "美式";
s = s + "少冰";

 堆内存里:
   ["美式"]      ← 旧对象,没人指了 → 等 GC 回收
   ["少冰"]      ← 字面量
   ["美式少冰"]  ← 新建的第三个对象   ┐
                                      s ┘  变量 s 现在指向它

结论:s 变了,但没有任何一个字符串对象「被改」过。变的是「s 指向谁」。

==      比较引用(两个变量是不是指同一个对象)
equals  比较内容(字符是否逐个相同)   ← 比字符串内容,一律用它
```

为什么 Java 要把 String 设计成不可变?因为它太常用了——做 Map 的 key、做常量、在多线程间传递……不可变意味着**它绝不会被人偷偷改掉**,可以安全共享、可以缓存 hash、可以放进「字符串常量池」复用。安全和性能,都建立在「改不动」这个前提上。

## 五、代码:拼一张小票

```java
public class Cafe {
    static String receipt(String customer, String coffee, String note, double price) {
        // 文本块:多行小票原样排版,不用满屏 + "\n"
        return """
               —— 豆豆咖啡站 ——
               顾客:%s
               咖啡:%s(%s)
               应付:¥%.2f
               ——————————————
               """.formatted(customer, coffee, note, price);
    }

    public static void main(String[] args) {
        String note = "少冰";
        String order = "美式" + " / " + note;     // 单次拼接,大方用 +,一点不慢
        System.out.println(order);
        System.out.print(receipt("张三", "美式", note, 15.0));
    }
}
```

注意 `order` 这行:三段字符串,直接 `+` 拼,清清爽爽——**别听人忽悠说「+ 拼接慢就得换 StringBuilder」**,下面第七节后面专门破这个迷信。

## 六、故意制造一个 Bug

判断「这位顾客是不是会员『张三』」时,顺手用了 `==`:

```java
String input = new String("张三");     // 用 new 运行时新建,和字面量不是同一只罐子
if (input == "张三") {                 // ← 故意:比的是引用
    System.out.println("欢迎会员张三");
} else {
    System.out.println("查无此会员");   // 实际走这里
}
```

---

## 七、读懂现象(Logic Bug)

**不报错**,但明明输入了「张三」,却打印「查无此会员」。因为 `new String("张三")` 在堆里**新建了一只罐子**,和字面量 `"张三"`(常量池里的那只)是**两个不同对象**;`==` 比引用 → 两只手指没指同一只罐子 → `false`。

> **🎯 面试直击**:`==` 和 `equals` 有什么区别?String 为什么用 `equals` 比?
> `==` 比**引用**(是不是同一个对象),`equals` 比**内容**。基本类型没有 equals,`==` 比值;引用类型比内容一律用 `equals`。追问点:`Object.equals` 默认也是比引用,是 `String` **重写**了它才变成比内容;所以你自己写的类要比内容,也得重写 `equals`(第二季讲)。

现在破除那个流传最广的性能迷信:

> **豆豆锐评 · 「+ 拼接慢」是老黄历**
> 单次(或几次)`+` 拼接,现代 JDK 编译时会走 **`invokedynamic` + `StringConcatFactory`** 动态生成一条高效的拼接逻辑,**一点不慢**,可读性还最好。真正的性能杀手是**在循环里反复 `+`**:那样每转一圈就新建一个中间字符串,几千次循环就是几千个垃圾对象。`StringBuilder` 的价值,**只在循环拼接**这一个场景——它用一块可变缓冲,全程只造一个对象。

> **🔀 豆豆的多解台 · 拼字符串,到底用哪种?**

| 方案 | 写法 | 适合什么时候 | 说明 |
|---|---|---|---|
| `+` | `a + b + c` | **单次/少量拼接**(绝大多数场景) | 现代 JDK 编译成 `invokedynamic`,快且最好读 |
| `StringBuilder` | `sb.append(x)` 循环后 `toString()` | **循环里反复拼接** | 唯一真正需要它的场景,避免造一堆临时对象 |
| `String.join` | `String.join(" / ", a, b, c)` | 用**固定分隔符**连一串 | 拼列表/路径最省心,免得手写分隔符 |
| 文本块 `"""..."""` | 多行原样写 | **多行模板**(小票、SQL、JSON) | 所见即所得,免掉满屏 `\n` |
| `formatted` | `"¥%.2f".formatted(p)` | 需要**格式化**(补零、对齐、精度) | 配文本块拼小票的黄金搭档 |

> 豆豆锐评:**默认用 `+`,循环才换 `StringBuilder`,多行用文本块**。记住这一句,你已经超过一半张口就说「+ 慢」的人。

## 八、修复,并用测试证明

```java
static boolean isMember(String input, String member) {
    return member.equals(input);   // 常量写在前:input 万一是 null 也不会 NPE
}
```

```java
@Test
void member_matched_by_content() {
    assertTrue(Cafe.isMember(new String("张三"), "张三"));  // 内容相同即会员,不管是不是同一只罐子
    assertFalse(Cafe.isMember("李四", "张三"));
}
```

`member.equals(input)` 而不是 `input.equals(member)`——把已知非 null 的常量放前面,天然躲开「input 为 null 时调 `.equals` 崩掉」的坑。这是一个能白拿的好习惯。

## 🎯 随堂练习

先自己做,再对答案。每道答案都带一句「举一反三」,帮你把这一个点连成一片。

### 选择题(10 道)

1. `String s = "美式"; s = s + "少冰";` 之后,内存里发生了什么?
   - A) 原来那只罐子里的字被改了　B) 新建了一个字符串对象,变量 `s` 改指向它,旧对象等 GC　C) 两个字符串合并成一个可变缓冲　D) 编译报错,String 不可修改
2. `==` 和 `equals` 的区别是?
   - A) `==` 比内容,`equals` 比引用　B) `==` 比引用(是不是同一只罐子),`equals` 比内容　C) 两者对 String 完全等价　D) `equals` 只能比数字
3. `String input = new String("张三"); input == "张三"` 的结果是?
   - A) `true`　B) `false`,`new` 出来的是堆里另一只罐子　C) 编译报错　D) 运行期抛异常
4. `Object.equals` 默认比的是什么?String 为什么能比内容?
   - A) 默认比内容,String 没做特殊处理　B) 默认比引用,是 String **重写**了 `equals`　C) 默认比 hashCode　D) 由 JVM 自动优化
5. Java 把 String 设计成不可变,最主要的收益是?
   - A) 节省内存　B) 可安全共享、能做 Map 的 key、能缓存 hash、能进常量池　C) 让代码更短　D) 支持中文
6. 关于「`+` 拼接慢」,正确的说法是?
   - A) 任何 `+` 拼接都慢,一律换 `StringBuilder`　B) 单次/少量 `+` 一点不慢,现代 JDK 编译成 `invokedynamic` + `StringConcatFactory`　C) `+` 只在拼中文时慢　D) `+` 会导致内存泄漏
7. `StringBuilder` 真正不可替代的场景是?
   - A) 任何拼接　B) **循环里反复拼接**　C) 拼接超过 3 段时　D) 多线程拼接
8. 为什么写 `member.equals(input)` 而不是 `input.equals(member)`?
   - A) 前者更快　B) 把已知非 null 的常量放前面,`input` 为 null 时也不会 NPE　C) 后者编译不过　D) 两者结果不同
9. 文本块 `"""..."""` 最适合用来?
   - A) 拼接两个短字符串　B) 写多行模板:小票、SQL、JSON　C) 替代 `StringBuilder`　D) 存储二进制数据
10. 用固定分隔符连一串字符串,最省心的是?
    - A) 循环里手写 `+ " / "`　B) `String.join(" / ", a, b, c)`　C) `StringBuilder` 手动 append 分隔符　D) `formatted`

> [!答案]
> **1-B**　你没「改」,你是造了新罐子再把标签贴过去。**举一反三**:所以在循环里反复 `+`,就是在批量造垃圾对象 —— 这才是性能问题真正的来源。
> **2-B**　一个比「是不是同一个」,一个比「内容一不一样」。**举一反三**:比字符串内容一律用 `equals`,这行代码你要写一辈子。
> **3-B**　`new String(...)` 强制在堆里新建对象,和常量池里的字面量不是同一只罐子。**举一反三**:正因为 `==` 有时「碰巧为 true」(字面量复用常量池),才更危险 —— 测试时可能通过,上线就翻车。
> **4-B**　`Object.equals` 默认也是比引用,String 重写后才比内容。**举一反三**:所以你自己写的类要比内容,也必须重写 `equals`(还要一起重写 `hashCode`,第二季讲)。
> **5-B**　安全和性能都建立在「改不动」这个前提上。**举一反三**:「String 为什么适合做 HashMap 的 key」= 不可变 → hash 不会变 → 桶位不会错乱。
> **6-B**　「+ 慢」是老黄历。**举一反三**:能说清 `invokedynamic` 这一层,就把背题党和真懂的人分开了。
> **7-B**　只有循环拼接才需要它 —— 一块可变缓冲,全程只造一个对象。**举一反三**:默认用 `+`,循环才换 `StringBuilder`,多行用文本块,记住这一句就够。
> **8-B**　常量写前面,天然躲开 null 调方法崩掉的坑。**举一反三**:这是白拿的好习惯,同类还有 `Objects.equals(a, b)`,两边都可为 null。
> **9-B**　所见即所得,免掉满屏 `\n`。**举一反三**:配 `formatted` 是拼小票、拼 SQL 的黄金搭档。
> **10-B**　`String.join` 专治「连一串」。**举一反三**:它还能直接接 `List`,拼路径、拼 CSV 一行搞定,省掉「最后多一个分隔符」的老毛病。
