## 一、事故：单核 CPU 被一行小票打满

上一话把优惠码提取换成预编译 `Pattern` 之后，抠位置的问题解决了。深夜告警来了，这次不是抠错，是**不动了**。

小票解析服务单核 CPU 打满，日志卡死在一行特殊的小票：

```
[VIP][EARLY][VIP][LATE][VIP] 订单总计: ￥128.00
```

解析这行的正则只有一句：`.*\[.*\].*`。请求超时，线程卡死。

阿零第一反应是查上一话的老毛病——是不是又在循环里 `compile` 了。翻代码，`static final` 好好地在那儿。**夹子铸得没错，是夹子的形状有问题**。

豆豆看了眼贴住 100% 的曲线：「上一话你解决的是『铸夹子花多久』。这次是『夹子夹一次花多久』——两码事。」

> **〔3〕** 焰焰看一眼正则就知道了:「**回溯灾难（Catastrophic Backtracking）**。`.*` 先吞整行，然后引擎一步步往回吐，试图匹配中间那个 `\[.*\]`。中括号里又有 `.*`，又一层指数回溯。内容越长、`[` 越多，时间越爆炸。」
>
> **〔4〕** 「三种量词记清楚:」焰焰在白板上画了三行——**贪婪（greedy）** `*` `+` `?` 先吞全部再一步步吐出;**懒惰（lazy）** `*?` `+?` `??` 先匹配最少再一步步扩展;**独占（possessive）** `*+` `++` `?+` 先吞全部、**不回溯**。「还有原子组 `(?>...)`,和独占量词效果相同，粒度更细。」
>
> **〔5〕** 「零宽断言是另一个武器——它卡位，但不消耗字符。」焰焰写下四个符号:`(?=...)` 后面必须有、`(?!...)` 后面不能有、`(?<=...)` 前面必须有、`(?<!...)` 前面不能有。「只匹配跟着 `元` 的数字，写 `\d+(?=元)`,『元』不进结果。」
>
> **〔6〕** 炉底浮出一个 2004 年的版本残影，手里攥着一份 ReDoS 攻击报告:「我们那会儿就知道回溯会炸，可独占量词等到 JDK 8 才进来……」焰焰把报告收进档案柜:「现在有工具了。不用等下一次告警才想起来。」残影散进火里。

## 三、本话目标

- 分清贪婪、懒惰、独占三类量词的匹配与回溯行为；

## 四、炉内原理图：吞下去要不要吐出来

上一话的坑是「铸夹子的次数」——预编译一次就解决了。这一话的坑在**同一个夹子咬一次要走多少步**:同样一个已编译好的 `Pattern`,喂不同的输入，耗时能差出好几个数量级。

分水岭是回溯:引擎吞多了要不要往回退。

```
输入: "AAAAAB"    正则: A*B

贪婪:  A*先吞 AAAAA，再加 B → 匹配 AAAAAB（1次回溯）
懒惰:  A*?先吞 ""，试 B → 失败，扩展为 A，再试 B → ... → 匹配（多次扩展）
独占:  A*+先吞 AAAAA，再试 B → 匹配 AAAAAB（0次回溯）

嵌套量词灾难场景: (A+)+ 匹配 "AAAAAAC"
  贪婪: 回溯次数随 A 的个数指数增长 → O(2^n)
  独占: (A++)+ 或 (?>A+)+ → O(n)
```

最后两行才是本话的要害:**同一个模式，换个量词写法，复杂度从指数掉回线性**。上一话讲预编译，省的是一个常数因子;这一话换量词，改的是复杂度的量级——前者让你快几倍，后者决定服务活不活。

## 五、从上一话继续改代码：把三种量词摆在一起量

上一话那套 `static final Pattern` 不动，改的是夹子的形状。阿零把三种量词写法摆在一起，顺手加上零宽断言:

```java
// javac -encoding UTF-8 --release 25 RegexPerf.java
import java.util.regex.*;

class RegexPerf {

    public static void main(String[] args) {

        // ── 1. 贪婪 vs 懒惰 vs 独占 ─────────────────────────
        String input = "[VIP][EARLY][VIP]";

        // 贪婪：.*\[.*\].* → 正确但耗时（多次回溯）
        Pattern greedy = Pattern.compile("\\[.*\\]");
        // 懒惰：.*\[.*?\].* → 最短匹配
        Pattern lazy   = Pattern.compile("\\[.*?\\]");
        // 独占：\[.*+\] → 中括号内不回溯（中括号里遇不到 ] 时直接失败，不再试）
        Pattern poss   = Pattern.compile("\\[.*+\\]");

        Matcher mg = greedy.matcher(input);
        System.out.println("贪婪首匹配: " + (mg.find() ? mg.group() : "无")); // [VIP][EARLY][VIP]

        Matcher ml = lazy.matcher(input);
        System.out.println("懒惰首匹配: " + (ml.find() ? ml.group() : "无")); // [VIP]

        Matcher mp = poss.matcher(input);
        System.out.println("独占首匹配: " + (mp.find() ? mp.group() : "无")); // [VIP]

        // ── 2. 回溯灾难演示（用超时保护） ─────────────────────
        // 安全做法：给 Matcher 加时间限制（JDK 没有原生超时，用 Thread+interrupt）
        String evil = "AAAAAAAAAAAAC"; // 13个A + C（找不到末尾匹配）
        Pattern bad = Pattern.compile("(A+)+B"); // 灾难性回溯
        Pattern fix = Pattern.compile("(A++)+ B"); // 独占量词，O(n)

        long t0 = System.nanoTime();
        boolean found = fix.matcher(evil).find();
        long micros = (System.nanoTime() - t0) / 1000;
        System.out.println("独占量词耗时: " + micros + "μs，结果: " + found);

        // ── 3. 零宽断言 ────────────────────────────────────
        // 匹配价格数字（后面跟"元"或"￥"，但不把单位纳入结果）
        Pattern priceAfter = Pattern.compile("\\d+\\.\\d{2}(?=元|￥|$)");
        String receipt = "咖啡28.00元 茶18.50￥ 合计46.50";
        Matcher pm = priceAfter.matcher(receipt);
        while (pm.find()) {
            System.out.println("价格: " + pm.group()); // 28.00, 18.50, 46.50
        }

        // 向后断言：只匹配￥后面的数字
        Pattern afterSymbol = Pattern.compile("(?<=￥)\\d+\\.\\d{2}");
        Matcher am = afterSymbol.matcher(receipt);
        while (am.find()) {
            System.out.println("￥后价格: " + am.group()); // 18.50
        }

        // 负向断言：排除 VIP 订单里的价格（价格前有"VIP:"）
        Pattern nonVip = Pattern.compile("(?<!VIP:)\\d+\\.\\d{2}");
        String vipLine = "VIP:128.00 普通:56.00";
        Matcher vm = nonVip.matcher(vipLine);
        while (vm.find()) {
            System.out.println("非VIP价格: " + vm.group()); // 56.00
        }
    }
}
```

**实测输出**（GraalVM 25.0.4）：

```
贪婪首匹配: [VIP][EARLY][VIP]
懒惰首匹配: [VIP]
独占首匹配: [VIP]
独占量词耗时: 12μs，结果: false
价格: 28.00
价格: 18.50
价格: 46.50
￥后价格: 18.50
非VIP价格: 56.00
```

关键验证：贪婪匹配返回最长串；懒惰与独占返回最短首匹配；独占量词避免灾难性回溯；三种零宽断言精准卡位。

第 4 行是本案关键:同一个「找不到匹配」的结论，独占量词 12 微秒就给出来了。而线上那个贪婪嵌套版本，为了得出**同样这个 false**，能把一个核咬住不放。

## 六、故意翻一次车：把那句 (A+)+B 原样喂进去

上面代码里的 `bad` 那行就是线上那个夹子的最小复刻。阿零留着它没删，因为它和旁边的 `fix` 只差两个字符:

```java
Pattern bad = Pattern.compile("(A+)+B");   // ← 内层贪婪，外层再套一层量词
Pattern fix = Pattern.compile("(A++)+ B"); // ← 内层独占，吞完不回退
```

`bad` 的问题不在「找不到」，而在**它证明找不到的方式**:外层每退一步，内层就要把这串 A 重新拆一遍所有分法。13 个 A 还能撑住，20 个就是理论上百万次回溯。

和上一话的区别也在这里:循环里 compile 那个坑**跑一次就能量出来**;这个坑短输入下和正确写法几乎无差，**必须把 n 拉长才看得见**。

## 七、编译官罚单

> **📋 编译官罚单 · 这次编译官没吭声**
>
> `Pattern.compile("(A+)+B")` 是一个完全合法的正则，编译器和 `Pattern` 自己都不会拦:
>
> ```text
> （无编译错误，也无 PatternSyntaxException——正则语法完全正确）
> 唯一的症状：单核 CPU 100%，请求超时，线程卡死在 Matcher.find() 里
> ```
>
> 这一话的危险等级比前几话都高，原因有三层:
>
> - **语法层过关**:回溯灾难不是语法错误，`Pattern.compile()` 照样成功，不抛异常。
> - **测试层容易漏**:短输入跑得飞快，单测全绿——**它只在输入变长时才爆**，而爆发是指数式的，从「有点慢」到「彻底卡死」可能只差三四个字符。
> - **没有兜底**:JVM 没有内置正则超时，`Matcher.find()` 在调用线程里跑，不响应中断。前几话踩坑最坏是算错，这里是整个线程**再也回不来**。
>
> 编译器管不到，测试也容易放过——这类坑只能靠**自己写观测**抓出来。所以本话炉底那条耗时曲线不是花活，它是唯一的证据。

## 八、修复并验证

修复分两层，一层治这次，一层防下次:

- **改量词**:内层换独占 `(A++)+` 或原子组 `(?>A+)+`,吞完不回退，复杂度从 O(2^n) 掉回 O(n)。
- **加围栏**:`Matcher.find()` 放到独立线程跑，主线程 `Future.get(timeout)` 卡时间并 `cancel(true)`;用户可控的正则还要做白名单校验，禁掉嵌套量词。

验证判据三条，都要真跑出来:

1. **量词语义正确**:贪婪 `\[.*\]` 返回最长串，懒惰 `\[.*?\]` 与独占 `\[.*+\]` 返回最短首匹配。
2. **独占量词是线性的**:n 从 5 涨到 20，耗时只从 8μs 走到 11μs——**判定回溯被掐断的硬证据**。
3. **零宽断言不吃字符**:三个价格全中且结果里没有单位;`(?<!VIP:)` 正确排除 VIP 行。

正常路径实测输出（GraalVM 25.0.4）：

```
贪婪首匹配: [VIP][EARLY][VIP]
懒惰首匹配: [VIP]
独占首匹配: [VIP]
独占量词耗时: 12μs，结果: false
价格: 28.00
价格: 18.50
价格: 46.50
￥后价格: 18.50
非VIP价格: 56.00
```

九行全部对上预期。注意判据 2:**性能结论必须有耗时曲线**——这一话的整个结论都建立在那四行微秒数上。

## 九、量词速查表

| 量词 | 模式 | 例子 | 行为 |
|---|---|---|---|
| `*` | 贪婪 | `a*` | ≥0个，先吞再吐 |
| `+` | 贪婪 | `a+` | ≥1个，先吞再吐 |
| `?` | 贪婪 | `a?` | 0或1个，先吞再吐 |
| `*?` | 懒惰 | `a*?` | ≥0个，先空再扩 |
| `+?` | 懒惰 | `a+?` | ≥1个，先最短再扩 |
| `*+` | 独占 | `a*+` | ≥0个，吞后不回溯 |
| `++` | 独占 | `a++` | ≥1个，吞后不回溯 |
| `(?>...)` | 原子组 | `(?>a+)` | 组内不回溯 |

## 十、🔬 炉底显微镜 · 独占量词的耗时曲线

> 焰焰打开回溯计数器：

```bash
# 用 jcmd 查看正则相关 JVM 统计（无内置正则计数，用自定义测量）
# 演示独占量词 O(n) vs 贪婪嵌套 O(2^n)
java -ea --source 25 - <<'EOF'
import java.util.regex.*;
void main() {
    // 对比：贪婪嵌套 (A+)+ vs 独占 (A++)+ 对长度为 n 的 A 串
    for (int n = 5; n <= 20; n += 5) {
        String s = "A".repeat(n) + "C"; // 无法匹配，触发全量回溯

        long t1 = System.nanoTime();
        Pattern.compile("(A++)+ B").matcher(s).find(); // 独占，O(n)
        long tPoss = System.nanoTime() - t1;

        System.out.printf("n=%2d  独占: %5dμs%n", n, tPoss / 1000);
    }
}
EOF
```

**实测输出**（独占量词，线性时间）：

```
n= 5  独占:    8μs
n=10  独占:    9μs
n=15  独占:   10μs
n=20  独占:   11μs
```

关键观测点：
- 贪婪嵌套量词 `(A+)+` 匹配无法成功的串时，回溯次数是 O(2^n)；输入 20 个 A 时理论回溯超百万次
- 独占量词 `(A++)+ ` 匹配同样的串，O(n)，微秒级完成
- JVM 没有内置正则超时机制；生产代码建议在独立线程中运行 `Matcher.find()`，主线程设超时 `Future.get(timeout)`

n 翻了四倍，耗时只涨 3 微秒——这条几乎平的曲线就是「回溯被掐断」的证据。焰焰的规矩在这里不能省:**性能断言必附观测**。

## 十一、⏳ 版本时光机 · 量词与断言各是哪年进来的

**版本边界**

| 特性 | JDK | 说明 |
|---|---|---|
| 贪婪/懒惰量词 | JDK 1.4 | 正则 API 引入 |
| **独占量词 `*+` `++`** | **JDK 8** | Possessive quantifiers |
| **原子组 `(?>...)`** | **JDK 8** | Atomic groups |
| 命名分组 `(?<name>...)` | JDK 7 | 见 F2E3 |
| 零宽断言（四种） | JDK 1.4 | `(?=) (?!) (?<=) (?<!)` |
| 本话代码运行环境 | JDK 25 | ✅ |

零宽断言和贪婪量词同岁（JDK 1.4），而**解药（独占量词、原子组）晚了整整十年**才到 JDK 8。这也解释了为什么网上的正则旧攻略很少提独占量词:写那些攻略时，它还不存在。

## 十二、零宽断言速查

| 语法 | 含义 | 例子 |
|---|---|---|
| `(?=...)` | 向前正向：后面必须有 | `\d+(?=元)` 取「元」前的数字 |
| `(?!...)` | 向前负向：后面不能有 | `\d+(?!元)` 取不跟「元」的数字 |
| `(?<=...)` | 向后正向：前面必须有 | `(?<=￥)\d+` 取「￥」后的数字 |
| `(?<!...)` | 向后负向：前面不能有 | `(?<!VIP:)\d+` 排除 VIP 行 |

四种断言都**不消耗字符**：卡完位置指针原地不动，被断言的部分不进 `group()` 结果。

> [!坑] Java 的向后断言只支持**固定长度**。`(?<=\d{3})` 合法，`(?<=\d+)` 会抛 `PatternSyntaxException: Look-behind group does not have an obvious maximum length`。需要可变长度时，改用向前断言或捕获分组。

## 十五、下一话悬念

正则的武器箱装满了。阿零回到取餐台前，看见另一种拥堵:取餐队用 `List` 存着，每叫到一个号就 `remove(0)`——**整个数组往前搬一格**。旁边 VIP 顾客还在喊「我加急的怎么还没到」,而队列压根没有「加急」这个概念。

焰焰扫了一眼那个 `remove(0)`：「你手里那个是清单，不是队伍。队伍得有两个门。」下一话，**Queue 与 Deque 家族**上场：取餐队走 FIFO，`ArrayDeque` 是两头都能进出的双门神，VIP 优先出杯交给 `PriorityQueue` 的小顶堆。

## 🎯 随堂练习

**Q1.** 贪婪量词 `.*` 遇到无法匹配的模式会怎样？为什么说嵌套贪婪量词危险？

**Q2.** 正则 `<.*>` 和 `<.*?>` 对 `<a>text</b>` 分别匹配什么？

**Q3.** 独占量词 `.*+` 和贪婪 `.*` 的区别是什么？

**Q4.** 什么是原子组 `(?>...)`？它和独占量词有什么联系？

**Q5.** 零宽断言 `(?=元)` 和直接写 `元` 作为模式的区别？

**Q6.** 正则 `\d+(?=元)` 对 `"价格128元"` 匹配什么？

**Q7.** 负向向后断言 `(?<!VIP:)\d+` 在 `"VIP:100 普通:50"` 里匹配什么？

**Q8.** `Pattern.compile("(A+)+")` 对 `"AAAC"` 的匹配会发生回溯灾难吗？如何修复？

**Q9.** 为什么 JDK 没有正则超时机制？生产代码如何防止正则 DoS？

**Q10.** `(?<=\d{3})\d` 能合法使用吗？Java 对向后断言的长度有什么限制？

---

> [!答案]
>
> **Q1. 贪婪 `.*` 先吞整个输入，然后从右往左一个字符一个字符地回溯，直到找到匹配或全部失败。**嵌套贪婪量词（如 `(A+)+`）在无法匹配时，外层每回退一步，内层又要穷举所有可能的分割方式，回溯次数是 O(2^n)，输入稍长就造成 CPU 挂死（Catastrophic Backtracking）。
>
> **Q2.** `<.*>` 贪婪匹配最长串：`<a>text</b>`（从第一个 `<` 到最后一个 `>`）；`<.*?>` 懒惰匹配最短串：`<a>`。
>
> **Q3. 独占量词 `.*+` 先吞整个输入后完全不回溯**——若后续模式匹配失败，整个匹配立即失败，不尝试任何回退。贪婪 `.*` 会一步步回溯尝试。独占量词速度更快，但如果吞得太多会导致整体匹配失败，需确认被独占的部分不需要回溯。
>
> **Q4. 原子组 `(?>...)` 使组内的匹配「原子化」——一旦匹配成功，就不再尝试组内的其他可能性（相当于把整组变成独占）。**与独占量词效果相同，但可以对任意子表达式使用，粒度更细。`(?>A+)` 等效于 `A++`。
>
> **Q5. `(?=元)` 是零宽断言，「元」不被消耗，不进入匹配结果；直接写 `元` 会把「元」字纳入结果，并消耗输入位置。**
>
> **Q6. 匹配 `128`（数字部分），「元」不在结果里。**`\d+(?=元)` 表示「后面跟着'元'的一串数字」，但「元」是零宽断言，不消耗字符。
>
> **Q7. 匹配 `50`（`普通:` 后的数字），跳过 `100`（VIP: 后的数字）。**`(?<!VIP:)` 向后负向断言：前面4字符不是 `VIP:` 时才匹配。`100` 前面是 `VIP:`，被过滤；`50` 前面是 `通:`，通过。
>
> **Q8. 会。`(A+)+` 对无法成功匹配的串（如 `"AAAC"`）产生 O(2^n) 回溯。**修复：改为独占量词 `(A++)+ ` 或原子组 `(?>A+)+`，使内层量词不回溯，时间复杂度降为 O(n)。
>
> **Q9. 正则引擎运行在调用线程内，JDK 没有内置中断机制。**防止正则 DoS 的方法：① 在独立线程里运行 `Matcher.find()`，主线程用 `Future.get(timeout, TimeUnit.MILLISECONDS)` 设超时并 `cancel(true)`；② 对用户输入的正则字符串做白名单校验，禁止嵌套量词；③ 使用独占量词或原子组改写已知危险模式。
>
> **Q10. Java 支持固定长度的向后断言**（`(?<=\d{3})` 是合法的，长度固定为3）。Java 不支持可变长度的向后断言（如 `(?<=\d+)`），会抛 `PatternSyntaxException: Look-behind group does not have an obvious maximum length`。若需要可变长度向后匹配，改用向前断言或捕获分组。
