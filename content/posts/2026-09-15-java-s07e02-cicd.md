# 《从零开始学 Java》53 · CI/CD 自动质检与发布

> 连载特刊 · 第七季「云端世界」第 2 话 · 基线 Java 25(最新 LTS) · 章节类型:实验手册。
> 承接:上一话咖啡站上了 K8s,可**上线三步全靠人肉**——`docker build`、`docker push`、`kubectl apply`,一步都不能漏。

---

## 一、事故:推错了一个镜像标签

阿零改完一个价格 bug,熟练地敲 `docker build`、`push`、`apply`。上线后测试同学炸了:「怎么还是老价格?」阿零一查——他 build 的是新代码,push 上去的镜像标签却手滑打成了上一版,K8s 拉的还是旧镜像。

豆豆:「人肉三步,重复十遍,第十一遍必翻车——这不是你菜,这是**流程的错**。凡是『每次都一样、还不能出错』的活,就该交给机器。今天给你的仓库装一条**流水线**:你只管 `git push`,它自动帮你跑测试、打镜像、上线。测试没过?它**不让你上**。」

本话目标只有一个:**让「提交代码」这个动作,自动触发「测试 → 构建 → 部署」**。

## 二、漫画 · 提交即发布

> **〔1〕** 阿零抱着一摞写着 build / push / apply 的牌子,在三个窗口间来回跑,满头大汗,还漏掉了一张牌子掉在地上。
> 阿零:「我发誓我上次记得推镜像的……大概……」

> **〔2〕** 豆豆掀开一块地板,底下是一条闪着灯的**自动流水线**,入口写着 `git push`,出口写着 `已上线`。
> 豆豆:「你只要把代码丢进这个入口。剩下的,传送带自己走。」

> **〔3〕** 传送带第一关是一道**闸机**,上面挂着 JUnit 质检员的牌子「证据呢?」。一个带着 bug 的提交滑过来,测试红了,闸机"哐"地落下,把它挡在门外,亮起红灯。
> JUnit 质检员:「没通过测试的代码,**休想上线**。这是门禁,不是建议。」

> **〔4〕** 一个测试全绿的提交顺利通过闸机,被自动打成镜像、贴上和 commit 一致的标签,送上 K8s 甲板。全程没有阿零的手。
> 阿零:「所以……我以后上线,就是 `git push`?」豆豆(叼着豆子):「对。你昨晚漏的那一步,机器永远不会漏。」

> **〔5〕** 阿零看着流水线尽头的绿灯,长舒一口气。
> 豆豆:「记住:**CI 是把代码持续合到一起还保证不坏,CD 是把它持续送上线。** 你今天两样都要。」

## 三、本话目标

- 分清 **CI(持续集成)** 与 **CD(持续交付/部署)**;
- 用 **GitHub Actions** 写一条 `push` 触发的流水线;
- 让流水线自动**跑测试 → 构建镜像 → 部署到 K8s**;
- 理解「测试失败 = 流水线失败 = 拦住发布」这条**门禁**;
- 撞一次「测试挂了流水线却绿灯」的配置坑,并修好它。

---

## 四、原理图:一条流水线的四道关

```text
 开发者 ──git push──▶ GitHub 仓库
                         │ 触发 workflow(on: push)
                         ▼
   ┌─────────────────── GitHub Actions Runner ───────────────────┐
   │  [1] checkout 代码 + 装 JDK 25                                │
   │        ▼                                                     │
   │  [2] mvn verify  ← CI 门禁:测试没过,整条流水线红,就此打住   │
   │        ▼(绿了才继续)                                        │
   │  [3] docker build + push(标签 = commit SHA,绝不重复)        │
   │        ▼                                                     │
   │  [4] kubectl set image ... ──▶ 滚动更新 K8s 上的 Deployment   │
   └─────────────────────────────────────────────────────────────┘
      └──── CI(集成+质检) ────┘└──────── CD(交付上线) ────────┘
```

关键在**顺序和门禁**:测试(第 2 关)必须在构建部署(第 3、4 关)**之前**,而且测试一红,后面的步骤**根本不会执行**。这样「坏代码」在被打成镜像之前就被拦下了——这就是 CI 的核心价值:**不是自动化了多少,而是自动拦住了多少**。

## 五、代码:写一条 GitHub Actions 流水线

在仓库根目录建 `.github/workflows/deploy.yml`。注意路径和文件名是 GitHub 约定死的,放错地方它不认:

```yaml
name: 咖啡站 CI/CD

on:
  push:
    branches: [ main ]            # 只有推到 main 才触发上线

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: 拉取代码
        uses: actions/checkout@v4

      - name: 装 JDK 25(与线上基线一致)
        uses: actions/setup-java@v4
        with:
          distribution: 'temurin'
          java-version: '25'
          cache: maven            # 缓存 ~/.m2,第二次跑快很多

      - name: 跑测试 + 打包(CI 门禁)
        run: mvn -B verify        # verify 会执行 test 阶段;任一测试失败,这一步非 0 退出

      - name: 登录镜像仓库
        run: echo "${{ secrets.REGISTRY_TOKEN }}" | docker login -u ci --password-stdin registry.example.com

      - name: 构建并推送镜像(标签 = 本次 commit)
        run: |
          IMG=registry.example.com/coffee-order:${{ github.sha }}
          docker build -t "$IMG" .
          docker push "$IMG"

      - name: 部署到 K8s(滚动更新)
        run: |
          kubectl set image deployment/coffee-order \
            order=registry.example.com/coffee-order:${{ github.sha }}
          kubectl rollout status deployment/coffee-order
```

三个要点:

- **镜像标签用 `github.sha`**——每次 commit 一个唯一标签,彻底根治阿零昨晚「推错标签」的问题,还能一眼追溯「线上跑的是哪次提交」;
- **`secrets.REGISTRY_TOKEN`** 是在 GitHub 仓库 Settings → Secrets 里配的密码,**绝不写进 YAML**(第四季讲过:凭证不进代码库);
- 最后一步 `kubectl set image` 触发的正是上一话 Deployment 的**滚动更新**——旧 Pod 一个个换成新镜像,不中断服务。

## 六、故意制造一个 Bug:让测试「挂了也放行」

阿零嫌 `mvn verify` 有个用例偶尔慢,自作聪明加了个参数**跳过测试失败**:

```yaml
      - name: 跑测试 + 打包
        run: mvn -B verify -Dmaven.test.failure.ignore=true   # ← 埋雷:忽略测试失败
```

然后他提交了一段有 bug 的价格计算代码(单价算错),`git push`。

## 七、读懂现象:绿灯放行了坏代码

流水线**全绿**,坏代码顺利上线。可 Actions 日志里,测试其实早就红了:

```text
[ERROR] Tests run: 12, Failures: 1, Errors: 0, Skipped: 0
[ERROR] PriceServiceTest.latte_price_should_be_correct:31
        expected: <32> but was: <23>
...
[INFO] BUILD SUCCESS      ← 注意:测试失败了,构建却「成功」
```

问题就出在 `-Dmaven.test.failure.ignore=true`:它让 Maven **看到失败也当没看见**,以 0 退出码收场。GitHub Actions 只认**退出码**——一步的命令返回 0 就算「绿」,于是这个「假绿」一路放行,把坏镜像推上了线。**门禁被自己拆了。**

这是 CI 最危险的反模式:**流水线跑得再全,只要门禁形同虚设,它就退化成一条「更快地把 bug 送上线」的传送带**。去掉那个参数,让测试失败**真的**把流水线弄红:

```yaml
      - name: 跑测试 + 打包(CI 门禁)
        run: mvn -B verify        # 一个用例挂,退出码非 0,后续步骤全部跳过
```

重新推,日志变成:

```text
[ERROR] PriceServiceTest.latte_price_should_be_correct:31
        expected: <32> but was: <23>
[ERROR] BUILD FAILURE
Error: Process completed with exit code 1.
```

后面的 build、push、deploy **全部没执行**——坏代码被挡在了镜像仓库之外。这才是门禁该有的样子。

> **豆豆锐评 · CI 的价值在「红」,不在「绿」**
> 新手常把 CI 当成「自动部署工具」,于是想方设法让它别报错、别挡路。搞反了:**CI 存在的意义,恰恰是在该红的时候红给你看。** 一条从不失败的流水线,要么你代码是神,要么你的门禁是摆设——后者的概率高得多。任何「忽略失败 / 跳过测试 / `|| true`」的写法,都是在偷偷拆掉安全网。

> **🎯 面试直击**:CI 和 CD 到底有什么区别?
> **CI(持续集成)**:每次提交都自动合并、构建、跑测试,尽早发现「合不到一起」或「合坏了」——重点是**质量门禁**。**CD** 有两层:**持续交付**(Continuous Delivery)是自动把通过测试的产物准备到「随时可上线」,但**上线按钮由人点**;**持续部署**(Continuous Deployment)更进一步,连按钮都省了,过了门禁**自动上生产**。追问点:多数团队生产环境用「持续交付」(留一道人工确认),测试环境才敢「持续部署」;而无论哪种,**前提都是有一套可信的自动化测试**——测试不可信,CD 就是自动化的车祸。

## 八、验证:让流水线自己证明门禁有效

与其等下次事故,不如**主动写一个「坏提交」测门禁**。在一个分支上故意留一个必失败的断言:

```java
@Test
void ci_gate_must_block_bad_code() {
    // 这个断言故意为假:用来验证「测试挂 → 流水线必须红」
    // 确认流水线拦住后,再把这段删掉
    assertEquals(32, PriceService.price("latte"));   // 若价格逻辑被改坏,这里会失败
}
```

推上去,到 GitHub 的 Actions 页面确认这次 run 是**红叉**、且「构建镜像」以后的步骤显示 `skipped`。看到它被拦住,你才敢信任它——**没验证过会失败的门禁,等于没有门禁**。确认无误后删掉这个临时用例。

日常真正跑的,是各层已有的单元 / 集成测试(第三季 JUnit、第四季 `@SpringBootTest`),它们现在每次 `push` 都自动执行,成了发布的第一道关。

### 一、选择题（10 道）

**1.** CI/CD 中"CI"（持续集成）的核心目标是什么？
- A) 自动部署到生产环境　B) 每次提交自动构建、跑测试，尽早发现集成问题　C) 替代人工写代码　D) 监控线上服务状态

**2.** GitHub Actions 工作流文件必须放在仓库的哪个目录下？
- A) `.github/actions/`　B) `.github/scripts/`　C) `.github/workflows/`　D) `根目录/ci/`

**3.** 流水线中测试失败时，正确的行为是什么？
- A) 跳过失败继续构建　B) 打印警告但标记为成功　C) 流水线变红，后续步骤全部跳过　D) 自动回滚到上一个版本

**4.** 蓝绿部署（Blue-Green Deployment）的关键特征是？
- A) 一台一台替换旧版本 Pod　B) 先放 5% 流量给新版本　C) 同时维护两套完整环境，流量一次性切换　D) 按用户 ID 哈希分配版本

**5.** 金丝雀发布（Canary Release）的核心思想是什么？
- A) 全部流量瞬间切到新版本　B) 先放一小部分流量到新版本，观察后逐步放量　C) 每次只部署一个 Pod　D) 仅在测试环境验证新版本

**6.** CI 中"门禁"（Quality Gate）的正确理解是？
- A) 一个检查代码风格的插件　B) 测试不通过则阻止代码进入后续阶段（构建/部署）的机制　C) 限制谁可以提交代码的权限　D) 部署前的数据库备份

**7.** 流水线中镜像仓库的登录密码应该存储在哪里？
- A) 直接写在 workflow YAML 文件中　B) 写在项目 README 中　C) 写在 application.properties 中　D) GitHub 仓库的 Settings → Secrets 中，通过 `${{ secrets.XXX }}` 引用

**8.** 镜像标签使用 `${{ github.sha }}`（commit SHA）的主要好处是什么？
- A) 镜像名更短　B) 每次构建唯一标签，可追溯到具体 commit，根治"推错标签"问题　C) 镜像体积更小　D) 不需要登录镜像仓库

**9.** `mvn verify -Dmaven.test.failure.ignore=true` 这条命令的风险是什么？
- A) 构建变慢　B) 测试失败但 Maven 仍以 0 退出码结束，流水线误判为"成功"　C) 跳过编译阶段　D) 生成的镜像体积变大

**10.** "持续交付"（Continuous Delivery）和"持续部署"（Continuous Deployment）的区别是？
- A) 没有区别　B) 持续交付自动上线到生产，持续部署需手动确认　C) 持续交付产物随时可上线但需人工点击发布，持续部署过门禁后全自动上线　D) 持续交付只用于前端

> [!答案]
> **1-B**　CI 核心是「频繁将代码合并到主干并自动验证」——每次 commit 触发构建+测试，确保新代码不 break 主线，缩短反馈周期。　举一反三：CI 的频率直接影响代码质量——一天合一次 vs 一周合一次，冲突量和修复成本差一个数量级。
> 
> **2-C**　GitHub Actions 约定工作流 YAML 文件必须放在 `.github/workflows/` 目录，文件名任意但扩展名必须是 `.yml` 或 `.yaml`。　举一反三：一个仓库可有多个 workflow 文件，各自定义不同触发条件（push、pull_request、schedule 定时任务等），互不干扰。
> 
> **3-C**　测试步骤退出码非 0 导致整个 job 失败，后续步骤不会执行——这是 CI 门禁的核心机制：坏代码在打包部署之前被拦下。　举一反三：任何 `-Dmaven.test.failure.ignore=true`、`|| true`、`continue-on-error: true` 都是在拆掉这道门禁。
> 
> **4-C**　蓝绿部署同时维护蓝（当前生产）和绿（新版本）两套完整环境，验证通过后一次性将流量从蓝切到绿。回滚也是瞬间完成——切回蓝即可。　举一反三：蓝绿代价是双倍资源。资源紧张的团队可用金丝雀作为折中——只多跑一小撮新版本 Pod。
> 
> **5-B**　金丝雀（矿工先放金丝雀测毒气）——新版本先只给一小部分真实用户（如 5%），盯它的错误率和延迟，没问题逐步放量（20%→50%→100%）。　举一反三：金丝雀「爆炸半径」最小——即使新版本有问题只影响 5% 用户。大促、高风险变更首选。日常改文案走滚动更新就够了。
> 
> **6-B**　门禁是流水线中的一道关卡——测试、lint、安全扫描等检查不通过，后续构建、部署步骤不会执行，把坏代码挡在交付链最前端。　举一反三：除测试外常见门禁还包括 SonarQube 质量门、Dependency Check 等。门禁越多越安全但也越慢——需在安全与速度间平衡。
> 
> **7-D**　凭证必须存在 Secrets 中，在 YAML 中用 `${{ secrets.XXX }}` 引用。Actions 日志中 Secrets 自动脱敏（显示为 `***`）。　举一反三：Secrets 不会传递给 fork 仓库的 PR，防止恶意 PR 窃取凭证。绝对不要通过 `echo`、`printenv` 打印。
> 
> **8-B**　git commit SHA 全局唯一，每次 push 产生新标签，`kubectl describe pod` 看到的镜像标签就是 commit SHA，能直接对应 Git 历史。　举一反三：生产别用 `latest` 标签——不可追溯，且 K8s 默认对 `latest` 的拉取策略是 `Always`，可能导致节点镜像版本不一致。生产必须用唯一标签。
> 
> **9-B**　`maven.test.failure.ignore=true` 让 Maven 即使测试失败也返回 0 退出码。GitHub Actions 只看退出码——0=成功→后续全部继续执行，坏代码被"绿灯"放上线。　举一反三：CI 最危险的反模式就是「把门禁搞绿」。验证门禁有效的最好方法是主动提交必败的测试，确认流水线确实变红。
> 
> **10-C**　持续交付（Delivery）= 通过 CI 后自动打包、部署到预发环境，产物"随时可上线"但上线按钮由人点。持续部署（Deployment）= 连按钮都省了，通过门禁后自动上生产。　举一反三：多数团队生产环境用持续交付（留人工确认防手滑），测试环境才敢用持续部署。前提是有可信的自动化测试。

### 二、解答题（3 道）

**11.** CI 和 CD 各自解决什么问题？为什么 CI 是 CD 的前提？

**12.** 对比蓝绿部署和金丝雀发布——各自的成本是什么？大促场景下该选哪个，为什么？

**13.** 有人说「CI 的价值在红不在绿」——你怎么理解这句话？

> [!答案]
> **11**　CI 解决「代码能不能合到一起、合完后有没有坏」——每次提交自动构建+测试，缩短反馈周期、减少合并冲突。CD 解决「通过验证的代码怎么安全快速地送到用户手里」——自动化部署减少人肉失误。CI 是 CD 的前提：如果连代码质量都无法自动验证，自动部署就是把未经检验的代码直接推上线，风险极大。只有 CI 门禁够硬（测试覆盖率够、门禁够严），CD 才有意义。　举一反三：CI 门禁程度决定 CD 能多大程度自动化——如果测试只覆盖 20%，就乖乖用持续交付（人工确认），别上持续部署。
> 
> **12**　蓝绿部署成本是资源翻倍（两套完整环境同时跑），但切换和回滚瞬间完成（秒级）。金丝雀资源增量较小（只需多跑一小撮新 Pod），但发布周期较长（逐步放量、持续观察），需配套监控。大促选金丝雀——原因：① 资源可控（大促本身就要扩容）；② 爆炸半径最小（即使有 bug 只影响 5%）；③ 用真实流量做最有效验证（压测只是模拟）。　举一反三：三者可组合——金丝雀验证通过后底层用滚动更新全量铺开；也可蓝绿切换后保留旧环境 24h 作为快速回滚后备。
> 
> **13**　CI 的真正价值不是「自动化了多少」，而是「自动拦住了多少」。一条从不失败的流水线，要么团队代码质量神级（几乎不可能），要么门禁形同虚设（大概率）。CI 的价值恰恰体现在"该红的时候会红"——当有人提交问题代码，测试变红、流水线拦住、坏代码上不了线，这才是 CI 在发挥作用。永远绿灯的流水线就像永远不响的烟雾报警器——它没火灾，是坏了。　举一反三：验证门禁有效性的标准做法——主动提交必败的测试，确认流水线变红且后续步骤被跳过。这就是"哨兵测试"模式。

### 三、代码题（2 道）

**14.** 写一份完整的 GitHub Actions 流水线 YAML：在 push 到 `main` 分支时触发，(1) 拉取代码 + 安装 JDK 21，(2) 跑 Maven 测试（必须让失败阻止后续步骤），(3) 测试通过后构建 Docker 镜像（标签为 git commit SHA），(4) 推送到 Docker Hub，(5) 通过 `kubectl set image` 滚动更新 K8s Deployment。

**15.** 写一个 JUnit 测试，专门验证「CI 门禁会拦截坏代码」——即故意写一个必失败的断言，确认流水线会因为测试失败而变红。

> [!答案]
> **14 验收**　```yaml
> name: 咖啡站 CI/CD
> on:
>   push:
>     branches: [ main ]
> jobs:
>   build-and-deploy:
>     runs-on: ubuntu-latest
>     steps:
>       - name: 拉取代码
>         uses: actions/checkout@v4
>       - name: 安装 JDK 21
>         uses: actions/setup-java@v4
>         with: { distribution: 'temurin', java-version: '21', cache: maven }
>       - name: 跑测试（CI 门禁——失败则后续全部跳过）
>         run: mvn -B verify
>       - name: 构建 Docker 镜像
>         run: docker build -t docker.io/myorg/coffee-order:${{ github.sha }} .
>       - name: 登录 Docker Hub
>         run: echo "${{ secrets.DOCKERHUB_TOKEN }}" | docker login -u myorg --password-stdin
>       - name: 推送镜像
>         run: docker push docker.io/myorg/coffee-order:${{ github.sha }}
>       - name: 部署到 K8s
>         run: |
>           kubectl set image deployment/coffee-order \
>             order=docker.io/myorg/coffee-order:${{ github.sha }}
>           kubectl rollout status deployment/coffee-order --timeout=120s
> ```　举一反三：`rollout status` 等待滚动更新完成，超时则退出码非 0→流水线变红。生产级应加：部署前备份 Deployment YAML；部署后跑冒烟测试；`if: failure()` 自动触发回滚。
> 
> **15 验收**　```java
> class CiGateValidationTest {
>     @Test
>     void ciMustBlockFailingTest() {
>         assertEquals(4, 5, "如果 CI 门禁有效，这个断言失败应该让流水线变红");
>     }
>     @Test
>     void ciMustBlockException() {
>         throw new RuntimeException("如果 CI 门禁有效，这个异常应该让流水线变红");
>     }
>     @Test
>     void ciMustBlockTimeout() {
>         assertTimeoutPreemptively(Duration.ofSeconds(1), () -> Thread.sleep(5000),
>             "如果 CI 门禁有效，超时应该让流水线变红");
>     }
> }
> ```　举一反三：这个门禁健康检查适合放不常 push 的分支上定期跑，或集成到 CI 本身——schedule 触发自动提交坏测试、等红了再自动 revert。
