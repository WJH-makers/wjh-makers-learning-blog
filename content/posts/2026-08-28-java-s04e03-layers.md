# 《从零开始学 Java》35 · Controller / Service / Repository

> 连载特刊 · 第四季「咖啡帝国」第 3 话 · 基线 Java 25 · Spring Boot 4.x
> 承接:上一话 `/hello` 通了,但如果把所有业务都塞进一个 Controller,又会回到"巨型方法"的老路。

---

## 一、需求:各司其职,别挤在一层

查菜单、下单、扣库存、将来还要连数据库——全写进一个 Controller,它很快就臃肿到没法维护、没法测试。豆豆:「一家咖啡店,收银、后厨、仓库是分开的。代码也一样:**Controller 管收发,Service 管业务,Repository 管数据。** 各守一层,谁也别越界。」

更重要的是,这一话你会第一次看清 Spring 最核心的魔术——**这些对象到底是谁创建的、又怎么被凑到一起的**。

---

## 二、漫画 · 三层楼与管家的名册

> **〔1〕** 一栋三层小楼:顶层 `Controller`(前台收发)、中层 `Service`(后厨业务)、底层 `Repository`(仓库数据)。请求从顶层进,一层层往下调。
> 豆豆:「请求只跟前台打交道;前台把活交给后厨,后厨找仓库要数据。**依赖从上往下,单向。**」

> **〔2〕** Spring 管家掏出一本名册,挨个登记贴了 `@Service`/`@Repository`/`@RestController` 标签的类,给每个**造一个实例、收进库房**。
> 豆豆:「这库房就是 **IoC 容器**。对象不再由你 `new`,而是**管家统一创建、统一保管**——这叫『控制反转』。」

> **〔3〕** 管家造前台 `CoffeeController` 时,发现它"点名要"一个 `CoffeeService`,便从库房取出来塞给它。
> 豆豆:「这一塞,就是**依赖注入(DI)**。你在构造器上写要什么,管家就从库房找来给你——不用自己 new。」

> **〔4〕** 阿零忘了给 `CoffeeService` 贴 `@Service` 标签。管家名册里查无此人,造前台时两手一摊:「你要的 `CoffeeService`,库房里没有啊。」启动当场失败。
> 豆豆(叼豆子):「没登记,就进不了库房;进不了库房,就没法被注入。经典翻车。」

## 四、原理图:三层与依赖注入

```text
GET /api/menu ─▶ CoffeeController(@RestController) 收发
                      │ 构造器注入
                      ▼
                 CoffeeService(@Service) 业务:下单、扣库存、抛缺货异常
                      │ 构造器注入
                      ▼
                 MenuRepository(@Repository) 数据:存取菜单

IoC 容器启动:扫描 @RestController/@Service/@Repository
  → 各造一个单例 Bean 收进容器
  → 造 Controller 时,发现构造器要 Service → 从容器取来注入
  → 造 Service 时,发现要 Repository → 从容器取来注入
```

## 五、代码:三层各就各位

数据载体沿用第二季的 `record`:

```java
public record Coffee(String name, double price, int stock) {}
```

**Repository 层**——只管数据存取:

```java
import org.springframework.stereotype.Repository;
import java.util.*;

@Repository
public class MenuRepository {
    private final Map<String, Coffee> menu = new LinkedHashMap<>();

    public MenuRepository() {                          // 先用内存,下一话换 MySQL
        save(new Coffee("美式", 15.0, 3));
        save(new Coffee("拿铁", 18.0, 5));
    }
    public void save(Coffee c) { menu.put(c.name(), c); }
    public Optional<Coffee> findByName(String name) { return Optional.ofNullable(menu.get(name)); }
    public List<Coffee> findAll() { return List.copyOf(menu.values()); }
}
```

**Service 层**——只管业务规则(复用第三季的 `OutOfStockException`):

```java
import org.springframework.stereotype.Service;
import java.util.List;

@Service
public class CoffeeService {
    private final MenuRepository repo;

    public CoffeeService(MenuRepository repo) {        // 构造器注入:依赖 final、不可变
        this.repo = repo;
    }

    public List<Coffee> menu() { return repo.findAll(); }

    public Coffee order(String name, int qty) {
        Coffee c = repo.findByName(name)
            .orElseThrow(() -> new IllegalArgumentException("菜单里没有:" + name));
        if (qty > c.stock())
            throw new OutOfStockException(name, qty, c.stock());
        Coffee updated = new Coffee(c.name(), c.price(), c.stock() - qty);
        repo.save(updated);
        return updated;
    }
}
```

**Controller 层**——只管 HTTP 收发:

```java
import org.springframework.web.bind.annotation.*;
import java.util.List;

@RestController
@RequestMapping("/api")
public class CoffeeController {
    private final CoffeeService service;

    public CoffeeController(CoffeeService service) {   // 构造器注入
        this.service = service;
    }

    @GetMapping("/menu")
    public List<Coffee> menu() { return service.menu(); }

    @PostMapping("/orders")
    public Coffee order(@RequestParam String name, @RequestParam int qty) {
        return service.order(name, qty);
    }
}
```

访问 `GET /api/menu` 返回菜单 JSON,`POST /api/orders?name=美式&qty=2` 下单并返回扣减后的库存。

## 七、读懂真实报错:找不到要注入的 Bean

启动直接失败:

```text
Parameter 0 of constructor in CoffeeController required a bean of type
'CoffeeService' that could not be found.

Action: Consider defining a bean of type 'CoffeeService' in your configuration.
```

Spring 说得很清楚:造 `CoffeeController` 需要一个 `CoffeeService` 类型的 Bean,但**容器里没有**——因为没 `@Service`,它压根没被登记进容器。Spring 甚至贴心给了 Action 提示。补回 `@Service` 即解决。这正是漫画里"没登记就进不了库房"。

> **⏳ 版本时光机 · 依赖注入的写法演进**

| 时期 | 写法 | 问题 |
|---|---|---|
| 早期 | 字段注入 `@Autowired private CoffeeService s;` | 依赖被隐藏、不能 final、难写单测、纵容循环依赖 |
| **现代推荐** | **构造器注入**(单构造器可省略 `@Autowired`) | 依赖 `final` 不可变、启动即暴露缺失、`new` 传 mock 就能测 |

> **🎯 面试直击**:什么是 IoC 和 DI?
> **IoC(控制反转)**:对象的创建与组装权从你手里"反转"给容器——你不再 `new`,由 Spring 统一造、统一管。**DI(依赖注入)**是 IoC 的落地方式:容器在创建一个对象时,把它声明需要的依赖"注入"进去。追问:为什么推荐构造器注入?① 依赖可声明为 `final`,对象一建好就完整、不可变;② 缺依赖在**启动时**就报错,而非运行到某行才 NPE;③ 脱离 Spring 也能 `new CoffeeService(mockRepo)` 直接单测。

## 八、用测试证明:三层链路通

```java
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.test.web.servlet.MockMvc;
import org.junit.jupiter.api.Test;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@SpringBootTest
@AutoConfigureMockMvc
class CoffeeControllerTest {
    @Autowired MockMvc mvc;

    @Test
    void menu_lists_coffees() throws Exception {
        mvc.perform(get("/api/menu"))
           .andExpect(status().isOk())
           .andExpect(jsonPath("$[0].name").value("美式"));
    }

    @Test
    void order_reduces_stock() throws Exception {
        mvc.perform(post("/api/orders").param("name", "拿铁").param("qty", "2"))
           .andExpect(status().isOk())
           .andExpect(jsonPath("$.stock").value(3));   // 5 - 2
    }
}
```

### 一、选择题(10 道)
1. [基础]IoC(控制反转)的核心思想是什么?
- A) 让每个类自己 `new` 依赖对象　B) 对象的创建与组装权反转给容器,由容器统一管理　C) 反转 HTTP 请求的方向　D) 让数据库控制业务逻辑
> [!答案] **1-B**　IoC = 对象的"控制权"从开发者手里反转给 Spring 容器;开发者不再 `new`,由容器统一创建、装配、管理生命周期。**举一反三**:IoC 是思想,DI(依赖注入)是 IoC 的具体实现方式——构造器注入、Setter 注入等。

2. [进阶]Spring 中构造器注入优于字段注入的主要原因?
- A) 代码更短　B) 依赖可声明为 final 不可变,且单测可直接 new 传 mock　C) 性能更好　D) 不需要写构造函数
> [!答案] **2-B**　字段 `@Autowired` 让依赖可变、难测、可能 NPE;构造器注入:依赖 `final` 不可变、启动即暴露缺失、`new Controller(mockService)` 就能单测。**举一反三**:Spring 4.3+ 单构造器可省略 `@Autowired`;Lombok `@RequiredArgsConstructor` 自动生成构造器注入代码。

3. [深入]Service 层被标记 `@Service` 后,Spring 做了哪两件事?
- A) 自动生成 SQL 并连接数据库　B) 组件扫描发现它→创建单例 Bean→收进 IoC 容器,等待注入　C) 编译时优化性能　D) 自动实现所有接口
> [!答案] **3-B**　`@ComponentScan` 扫描到 `@Service` → 创建一个实例(默认单例)放进容器 → 其他类需要时通过 DI 拿到。**举一反三**:`@Service`/`@Repository`/`@RestController` 都是 `@Component` 的语义化别名,本质相同但表意更清晰。

4. [基础]三层架构中,Repository 层的职责是?
- A) 接收 HTTP 请求并返回响应　B) 处理业务逻辑和事务　C) 负责数据持久化——从数据库存取数据　D) 渲染 HTML 页面
> [!答案] **4-C**　Repository = 数据访问层,只管"把数据存进去、取出来",不关心业务规则。**举一反三**:依赖方向是 Controller→Service→Repository,单向;Service 不依赖 Controller,Repository 不依赖 Service。

5. [进阶]如果忘记给 Service 类加 `@Service` 注解,会发生什么?
- A) 编译报错　B) 启动报错——Controller 的构造器需要该类型的 Bean 但容器里没有　C) 运行时功能正常但慢　D) 自动降级为普通对象
> [!答案] **5-B**　没有 `@Service`,该类不会被扫描和注册为 Bean;Controller 构造器要注入它时,Spring 找不到匹配 Bean,启动直接报 `NoSuchBeanDefinitionException`。**举一反三**:这是"快速失败"的设计——启动时暴露,而不是上线后 NPE。

6. [深入]Bean 的默认作用域(Scope)是什么?
- A) prototype(每次获取新建)　B) singleton(整个容器只有一个实例)　C) request(每个 HTTP 请求新建)　D) session(每个会话新建)
> [!答案] **6-B**　Spring 默认 singleton,即整个容器中该类型的 Bean 只有**一个实例**。**举一反三**:需要每次新建时用 `@Scope("prototype")`,但绝大多数场景 singleton 就够——`@RestController`/`@Service`/`@Repository` 通常是**无状态**的。

7. [基础]`@Autowired` 可以放在哪些位置?
- A) 只能放在字段上　B) 只能放在构造器上　C) 构造器、Setter 方法、字段上都可以　D) 只能放在方法参数上
> [!答案] **7-C**　`@Autowired` 可标注在构造器、Setter、字段;现代推荐**构造器注入**(单构造器时可省略 `@Autowired`)。**举一反三**:字段注入在测试中需要反射或 `@SpringBootTest` 才能注入 mock,而构造器注入一行 `new` 就搞定。

8. [进阶]如果有两个同类型的 Bean,如何指定注入哪一个?
- A) 随机选　B) 用 `@Primary` 标记首选,或用 `@Qualifier("beanName")` 指定　C) 启动报错无法解决　D) 修改类型名
> [!答案] **8-B**　`@Primary` 给一个默认首选;`@Qualifier("具体的 bean 名")` 精确指定。**举一反三**:默认 bean 名是类名首字母小写(`coffeeService`);`@Qualifier` 和 `@Primary` 同时存在时 `@Qualifier` 优先。

9. [深入]Spring 中的"循环依赖"指什么?
- A) ServiceA 依赖 ServiceB,ServiceB 又依赖 ServiceA,形成闭环　B) 一个类实现了多个接口　C) 多个 Controller 共用一个 Service　D) pom.xml 中依赖重复
> [!答案] **9-A**　循环依赖 = A→B→A,构造器注入下 Spring 无法创建(谁先 new?)。**举一反三**:构造器注入天然**禁止循环依赖**(启动即报错),这其实是好事——循环依赖通常是**设计问题**(职责拆分不清),应重构而非绕过。

10. [综合]Controller 调用 Service,Service 调用 Repository——这种分层设计的最大收益是?
- A) 代码行数更少　B) 每一层可独立测试、可独立替换实现,修改一层不影响其他层　C) 运行速度更快　D) 不需要写注释
> [!答案] **10-B**　分层之后:Repository 换数据库(MySQL→PostgreSQL),Service 一行不改;Service 换业务规则,Controller 不受影响;单元测试可 mock Service 测 Controller、mock Repository 测 Service。**举一反三**:这是**单一职责原则**和**依赖倒置**的体现——每一层只做自己的事,依赖抽象而非具体实现。

### 二、解答题(3 道)
1. [概念]用咖啡店的收银、后厨、仓库作类比,解释 IoC 容器和依赖注入的关系。为什么说"容器是仓库,DI 是管家送人上门"?
> [!答案] **1**　IoC 容器就像一个**员工名册 + 仓库**:所有贴了标签的类(`@Service`/`@Repository`)被扫描后,容器给每个造一个实例"存进仓库"。DI 就像**管家上门送人**:Controller 声明"我需要一个 CoffeeService",管家(IoC 容器)去仓库找,找到就送过去,找不到就报错。开发者不再 `new`——**创建权交容器,组装权交 DI**。**举一反三**:IoC 的"反转"是相对于传统 `new` 模式的反转——以前你自己 new,现在容器替你 new。

2. [场景]一个 Controller 有 5 个方法分别处理下单、查单、退款、加积分、发优惠券。如何判断哪些逻辑应该在 Service 层、哪些可以留在 Controller?
> [!答案] **2**　判断标准:**可复用 + 可独立测试**。下单、退款(核心业务)放 Service;加积分、发优惠券(可被多个接口复用)更应放 Service;Controller 只做:①解析请求参数;②调用 Service;③包装响应。简单判断:**把 Controller 关了,这个逻辑还应该能跑**——如果能,说明放对了层。**举一反三**:Controller 越薄越好,永远不要包含 `if (stock>0) { save(); sendMQ(); }` 这样的业务判断——那是 Service 的活。

3. [综合]从"启动→扫描→创建→注入"四个阶段,描述 Spring Boot 启动时如何将 Controller/Service/Repository 组装成可运行的调用链。
> [!答案] **3**　①`@ComponentScan` 扫描启动类所在包及子包,找到所有 `@RestController`/`@Service`/`@Repository` 标记的类;②按依赖关系排序(无依赖的先创建),为每个类创建一个**单例** Bean;③创建 Controller 时,发现构造器需要 Service →去容器找类型匹配的 Bean,找到就注入;④创建 Service 时,同理注入 Repository。最终 IoC 容器里形成一条"Controller 持 Service、Service 持 Repository"的引用链,请求来时直接调用。**举一反三**:如果某一步找不到 Bean,启动即报错(fail-fast),不会等到运行时。

### 三、代码题(2 道)
1. [基础]定义一个 `Product` record(id, name, price),并写出完整的三层架构:ProductController(`GET /api/products` 返回列表 + `POST /api/products` 新增),ProductService(带基本的非空校验),ProductRepository(内存 Map 实现)。全部用构造器注入。
> [!答案] **1 验收**:
> ```java
> record Product(Long id, String name, double price) {}
> 
> @Repository
> class ProductRepository {
>     private final Map<Long,Product> store = new HashMap<>();
>     public Product save(Product p) { store.put(p.id(),p); return p; }
>     public List<Product> findAll() { return List.copyOf(store.values()); }
> }
> 
> @Service
> class ProductService {
>     private final ProductRepository repo;
>     public ProductService(ProductRepository repo) { this.repo = repo; }
>     public Product add(Product p) {
>         if (p.name() == null || p.name().isBlank()) throw new IllegalArgumentException("名称必填");
>         return repo.save(p);
>     }
>     public List<Product> list() { return repo.findAll(); }
> }
> 
> @RestController
> @RequestMapping("/api/products")
> class ProductController {
>     private final ProductService svc;
>     public ProductController(ProductService svc) { this.svc = svc; }
>     @GetMapping List<Product> list() { return svc.list(); }
>     @PostMapping Product add(@RequestBody Product p) { return svc.add(p); }
> }
> ```
> **举一反三**:所有注入通过构造器、依赖声明为 final——这就是"Spring 推荐的最佳实践"的落地代码。

2. [综合]写一个 `@WebMvcTest(ProductController.class)` 测试,用 `@MockBean` mock ProductService,验证:①`GET /api/products` 返回 200 + JSON 数组;②`POST /api/products` 传非法数据时返回 400。边界:mock 应只被调用一次。
> [!答案] **2 验收**:
> ```java
> @WebMvcTest(ProductController.class)
> class ProductControllerTest {
>     @Autowired MockMvc mvc;
>     @MockBean ProductService svc;
> 
>     @Test
>     void list_returns_200() throws Exception {
>         when(svc.list()).thenReturn(List.of(new Product(1L, "美式", 15.0)));
>         mvc.perform(get("/api/products"))
>            .andExpect(status().isOk())
>            .andExpect(jsonPath("$[0].name").value("美式"));
>         verify(svc, times(1)).list();
>     }
> 
>     @Test
>     void add_invalid_returns_400() throws Exception {
>         when(svc.add(any())).thenThrow(new IllegalArgumentException("名称必填"));
>         mvc.perform(post("/api/products")
>                 .contentType(MediaType.APPLICATION_JSON)
>                 .content("{\"id\":1,\"name\":\"\",\"price\":0}"))
>            .andExpect(status().isBadRequest())
>            .andExpect(jsonPath("$.error").exists());
>     }
> }
> ```
> **举一反三**:`@WebMvcTest` 只加载 Controller 层,不启动完整 Spring 上下文——比 `@SpringBootTest` 快很多,适合 Controller 层的单元测试。
