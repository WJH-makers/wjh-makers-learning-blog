# 《从零开始学 Java》35 · Controller / Service / Repository

> 连载特刊 · 第四季「咖啡帝国」第 3 话 · 基线 Java 25 · Spring Boot 4.x
> 承接:上一话 `/hello` 通了,但如果把所有业务都塞进一个 Controller,又会回到"巨型方法"的老路。

---

## 一、需求:各司其职,别挤在一层

查菜单、下单、扣库存、将来还要连数据库——全写进一个 Controller,它很快就臃肿到没法维护、没法测试。豆豆:「一家咖啡店,收银、后厨、仓库是分开的。代码也一样:**Controller 管收发,Service 管业务,Repository 管数据。** 各守一层,谁也别越界。」

更重要的是,这一话你会第一次看清 Spring 最核心的魔术——**这些对象到底是谁创建的、又怎么被凑到一起的**。

---

## 二、漫画 · 三层楼与管家的名册

> **〔1〕** 一栋三层小楼:顶层 `Controller`(前台收发)、中层 `Service`(后厨业务)、底层 `Repository`(仓库数据)。请求从顶层进,一层层往下调。
> 豆豆:「请求只跟前台打交道;前台把活交给后厨,后厨找仓库要数据。**依赖从上往下,单向。**」

> **〔2〕** Spring 管家掏出一本名册,挨个登记贴了 `@Service`/`@Repository`/`@RestController` 标签的类,给每个**造一个实例、收进库房**。
> 豆豆:「这库房就是 **IoC 容器**。对象不再由你 `new`,而是**管家统一创建、统一保管**——这叫『控制反转』。」

> **〔3〕** 管家造前台 `CoffeeController` 时,发现它"点名要"一个 `CoffeeService`,便从库房取出来塞给它。
> 豆豆:「这一塞,就是**依赖注入(DI)**。你在构造器上写要什么,管家就从库房找来给你——不用自己 new。」

> **〔4〕** 阿零忘了给 `CoffeeService` 贴 `@Service` 标签。管家名册里查无此人,造前台时两手一摊:「你要的 `CoffeeService`,库房里没有啊。」启动当场失败。
> 豆豆(叼豆子):「没登记,就进不了库房;进不了库房,就没法被注入。经典翻车。」

## 三、本话目标

- 把咖啡站拆成 Controller / Service / Repository 三层,依赖单向向下;
- 理解 **IoC 容器**(谁创建对象)与**依赖注入 DI**(怎么送到一起);
- 用**构造器注入**组装三层;
- 踩一次"忘贴 `@Service` 导致注入失败"的坑;
- 用 `MockMvc` 测通整条链路。

## 四、原理图:三层与依赖注入

```text
GET /api/menu ─▶ CoffeeController(@RestController) 收发
                      │ 构造器注入
                      ▼
                 CoffeeService(@Service) 业务:下单、扣库存、抛缺货异常
                      │ 构造器注入
                      ▼
                 MenuRepository(@Repository) 数据:存取菜单

IoC 容器启动:扫描 @RestController/@Service/@Repository
  → 各造一个单例 Bean 收进容器
  → 造 Controller 时,发现构造器要 Service → 从容器取来注入
  → 造 Service 时,发现要 Repository → 从容器取来注入
```

## 五、代码:三层各就各位

数据载体沿用第二季的 `record`:

```java
public record Coffee(String name, double price, int stock) {}
```

**Repository 层**——只管数据存取:

```java
import org.springframework.stereotype.Repository;
import java.util.*;

@Repository
public class MenuRepository {
    private final Map<String, Coffee> menu = new LinkedHashMap<>();

    public MenuRepository() {                          // 先用内存,下一话换 MySQL
        save(new Coffee("美式", 15.0, 3));
        save(new Coffee("拿铁", 18.0, 5));
    }
    public void save(Coffee c) { menu.put(c.name(), c); }
    public Optional<Coffee> findByName(String name) { return Optional.ofNullable(menu.get(name)); }
    public List<Coffee> findAll() { return List.copyOf(menu.values()); }
}
```

**Service 层**——只管业务规则(复用第三季的 `OutOfStockException`):

```java
import org.springframework.stereotype.Service;
import java.util.List;

@Service
public class CoffeeService {
    private final MenuRepository repo;

    public CoffeeService(MenuRepository repo) {        // 构造器注入:依赖 final、不可变
        this.repo = repo;
    }

    public List<Coffee> menu() { return repo.findAll(); }

    public Coffee order(String name, int qty) {
        Coffee c = repo.findByName(name)
            .orElseThrow(() -> new IllegalArgumentException("菜单里没有:" + name));
        if (qty > c.stock())
            throw new OutOfStockException(name, qty, c.stock());
        Coffee updated = new Coffee(c.name(), c.price(), c.stock() - qty);
        repo.save(updated);
        return updated;
    }
}
```

**Controller 层**——只管 HTTP 收发:

```java
import org.springframework.web.bind.annotation.*;
import java.util.List;

@RestController
@RequestMapping("/api")
public class CoffeeController {
    private final CoffeeService service;

    public CoffeeController(CoffeeService service) {   // 构造器注入
        this.service = service;
    }

    @GetMapping("/menu")
    public List<Coffee> menu() { return service.menu(); }

    @PostMapping("/orders")
    public Coffee order(@RequestParam String name, @RequestParam int qty) {
        return service.order(name, qty);
    }
}
```

访问 `GET /api/menu` 返回菜单 JSON,`POST /api/orders?name=美式&qty=2` 下单并返回扣减后的库存。

## 七、读懂真实报错:找不到要注入的 Bean

启动直接失败:

```text
Parameter 0 of constructor in CoffeeController required a bean of type
'CoffeeService' that could not be found.

Action: Consider defining a bean of type 'CoffeeService' in your configuration.
```

Spring 说得很清楚:造 `CoffeeController` 需要一个 `CoffeeService` 类型的 Bean,但**容器里没有**——因为没 `@Service`,它压根没被登记进容器。Spring 甚至贴心给了 Action 提示。补回 `@Service` 即解决。这正是漫画里"没登记就进不了库房"。

> **⏳ 版本时光机 · 依赖注入的写法演进**

| 时期 | 写法 | 问题 |
|---|---|---|
| 早期 | 字段注入 `@Autowired private CoffeeService s;` | 依赖被隐藏、不能 final、难写单测、纵容循环依赖 |
| **现代推荐** | **构造器注入**(单构造器可省略 `@Autowired`) | 依赖 `final` 不可变、启动即暴露缺失、`new` 传 mock 就能测 |

> **🎯 面试直击**:什么是 IoC 和 DI?
> **IoC(控制反转)**:对象的创建与组装权从你手里"反转"给容器——你不再 `new`,由 Spring 统一造、统一管。**DI(依赖注入)**是 IoC 的落地方式:容器在创建一个对象时,把它声明需要的依赖"注入"进去。追问:为什么推荐构造器注入?① 依赖可声明为 `final`,对象一建好就完整、不可变;② 缺依赖在**启动时**就报错,而非运行到某行才 NPE;③ 脱离 Spring 也能 `new CoffeeService(mockRepo)` 直接单测。

## 八、用测试证明:三层链路通

```java
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.test.web.servlet.MockMvc;
import org.junit.jupiter.api.Test;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@SpringBootTest
@AutoConfigureMockMvc
class CoffeeControllerTest {
    @Autowired MockMvc mvc;

    @Test
    void menu_lists_coffees() throws Exception {
        mvc.perform(get("/api/menu"))
           .andExpect(status().isOk())
           .andExpect(jsonPath("$[0].name").value("美式"));
    }

    @Test
    void order_reduces_stock() throws Exception {
        mvc.perform(post("/api/orders").param("name", "拿铁").param("qty", "2"))
           .andExpect(status().isOk())
           .andExpect(jsonPath("$.stock").value(3));   // 5 - 2
    }
}
```

## 🎯 随堂练习

先自己做,再对答案。每道答案都带一句「举一反三」,帮你把这一个点连成一片。

### 选择题(10 道)

1. 三层的职责划分是?
   - A) Controller 管业务、Service 管收发、Repository 管日志　B) Controller 管 HTTP 收发、Service 管业务规则、Repository 管数据存取　C) 三层都能写业务　D) Controller 直接访问数据库
2. **IoC(控制反转)**指的是?
   - A) 控制流程反过来执行　B) 对象的创建与组装权从你手里反转给容器,你不再 `new`　C) 依赖方向反转　D) 请求处理顺序反转
3. **DI(依赖注入)**与 IoC 的关系是?
   - A) 两者无关　B) DI 是 IoC 的落地方式:容器创建对象时把它声明的依赖注入进去　C) DI 是 IoC 的替代品　D) IoC 是 DI 的一种
4. 删掉 `CoffeeService` 上的 `@Service` 后,应用会?
   - A) 正常运行,运行到该方法才 NPE　B) **启动就失败**:`required a bean of type 'CoffeeService' that could not be found`　C) 编译报错　D) 自动创建一个默认实例
5. 现代推荐的注入方式是?
   - A) 字段注入 `@Autowired private ...`　B) **构造器注入**　C) setter 注入　D) 静态工厂
6. 构造器注入的优点**不包括**?
   - A) 依赖可声明为 `final`,对象一建好就完整　B) 缺依赖在启动时就报错　C) 脱离 Spring 也能 `new Service(mockRepo)` 单测　D) 运行时可以随时替换依赖
7. 字段注入被诟病的原因是?
   - A) 性能差　B) 依赖被隐藏、不能 `final`、难写单测、纵容循环依赖　C) 不支持接口　D) 需要额外配置
8. `repo.findByName(name).orElseThrow(...)` 用的是?
   - A) `Optional`,把「可能没有」显式表达并在缺失时抛出　B) 一个自定义集合　C) Stream 终端操作　D) 异常链
9. `Coffee` 是 record,扣库存时的写法是?
   - A) `c.setStock(...)`　B) 用新库存造一个新 `Coffee` 再 `save` 回去　C) 直接改字段　D) 用反射修改
10. 三层之间的依赖方向应该是?
    - A) 双向　B) Controller → Service → Repository,单向向下　C) Repository → Service → Controller　D) 任意

> [!答案]
> **1-B**　各司其职,一家咖啡店也是收银、后厨、库房分工。**举一反三**:业务逻辑爬进 Controller 是最常见的腐化路径 —— CR 时重点盯这个。
> **2-B**　创建权交给容器。**举一反三**:所以你几乎不再在业务代码里看到 `new`,对象生命周期由容器统一管理。
> **3-B**　DI 是 IoC 的具体实现手段。**举一反三**:除了注入,IoC 还体现在模板方法、事件回调等「别调我,我会调你」的场景。
> **4-B**　容器里没有这个 Bean,启动即失败。**举一反三**:「启动时暴露」远好过「运行到某行才 NPE」—— 这正是构造器注入的核心优势。
> **5-B**　构造器注入是现代默认。**举一反三**:单构造器时可以省略 `@Autowired`,Spring 4.3 起就支持了。
> **6-D**　依赖注入后不可变才是优点,「随时替换」恰恰是缺点。**举一反三**:不可变意味着对象状态可预测,这和第二季 record 的思路一脉相承。
> **7-B**　它把依赖藏起来了。**举一反三**:一个类字段注入了十个依赖也看不出来「它有多重」,构造器注入则会让参数列表长得刺眼 —— 这种「难看」是有价值的信号。
> **8-A**　`Optional` 强迫调用方面对「可能没有」。**举一反三**:别用 `Optional.get()` 直接取值,那等于把它退化回 null;`orElseThrow` / `orElse` / `map` 才是正确用法。
> **9-B**　不可变对象只能整个替换。**举一反三**:这也让「谁改了这个对象」这个问题永远不会出现 —— 状态变化只发生在你显式 save 的那一刻。
> **10-B**　单向向下。**举一反三**:和第三季多模块的 app→core 是同一条纪律,只是从模块粒度落到了类粒度。
