# 《从零开始学 Java》31 · Git 版本时间机

> 连载特刊 · 第三季「工程时代」第 7 话(实验手册)· 基线 Java 25(最新 LTS)

## 一、需求:给代码装一台时间机

阿零昨天重构手滑删了半个类,今天想找回昨天的版本——发现根本没存档。更别说和同学并行开发同一个项目:两人改同一个文件,互相覆盖。豆豆:「你需要一台**时间机**:随时存档、随时回退、还能开平行时间线各干各的,最后再汇到一起。」

这一话不改业务逻辑,而是把项目纳入 **Git** 版本控制——它是团队协作与持续交付的地基。

## 二、漫画 · 时间机

> **〔1〕** 阿零对着删坏的代码欲哭无泪:「昨天还好好的……」
> 豆豆:「因为你从没**存档**。来,开时间机。」

> **〔2〕** 一台写着 `Git` 的机器亮起,面板三个格子:**工作区** → `add` → **暂存区** → `commit` → **仓库(存档点)**。
> 豆豆:「`commit` 就是一个存档点,盖上时间戳和说明。想回哪个存档,随时跳。」

> **〔3〕** 机器分出一条平行光轨 `feature` 分支。
> 豆豆:「`branch` 是**平行时间线**。你在支线上大胆试验,炸了也不影响主线 `main`;成了再 `merge` 汇回去。」

> **〔4〕** 阿零一句 `git add .` 把 `target/` 里一堆 `.class` 也塞进了暂存区,仓库瞬间臃肿。
> 豆豆(叼豆子):「编译产物凭什么进仓库?写张 **`.gitignore`** 黑名单,把它们挡在门外——只存**源码**,别存能重新生成的东西。」

## 三、本话目标

- 理解 Git 三个区:工作区 / 暂存区(add)/ 本地仓库(commit);
- 用 `init / add / commit / log` 给项目建立版本历史;
- 用 `branch / merge` 开平行时间线并汇流;
- 用 `.gitignore` 把 `target/`、`.class`、IDE 配置挡在仓库外;
- 踩一次"把编译产物提交进去"的坑并清理。

---

## 四、原理图:三个区与分支

```text
工作区(你编辑的文件)
   │  git add
   ▼
暂存区(准备提交的快照)
   │  git commit -m "..."
   ▼
本地仓库(一串带时间戳的存档点 = commit)

main    ●──●──●──────●   ← 汇流(merge)
             \       /
feature       ●──●──         平行时间线,试验不惊动主线
```

## 五、实验:把咖啡站纳入 Git

先写 `.gitignore`(放项目根目录),再初始化:

```gitignore
# 编译产物 / 构建输出
target/
*.class
# IDE / 系统
.idea/
*.iml
.DS_Store
```

```bash
git init                       # 初始化仓库
git add .                      # 暂存(.gitignore 里的会被自动跳过)
git commit -m "feat: 咖啡站 v2.6,含异常/文件/Stream/测试"

git switch -c feature/discount # 开一条平行时间线做"会员折扣"
# ...改代码...
git commit -m "feat: 加入会员折扣"
git switch main                # 回主线
git merge feature/discount     # 把折扣成果汇回主线
git log --oneline              # 看存档历史
```

## 七、读懂现象:仓库被编译产物淹没

```text
Changes to be committed:
	new file:   target/classes/CoffeeShop.class
	new file:   target/classes/MenuStore.class
	new file:   target/coffee-shop-1.0.0.jar
	... (几十个 .class)
```

一堆 `.class` 和 jar 混进了暂存区。后果:仓库臃肿、每次编译都产生"假改动"、多人合并时 `.class` 疯狂冲突。补救:

```bash
# 补上 .gitignore 后,把已误入的产物从版本控制里移除(保留本地文件)
git rm -r --cached target
git commit -m "chore: 忽略 target/ 编译产物"
```

原则一句话:**只提交源码和不可再生的东西;凡是能由构建重新生成的(target/、node_modules/、.class),一律 ignore。**

> **⏳ 版本时光机 · 从集中式到分布式**

| 时代 | 代表 | 特点 |
|---|---|---|
| 集中式 | SVN / CVS | 只有一个中央仓库,断网就没法提交、看历史 |
| 分布式 | **Git** | 每个人本地都有完整历史,离线可提交/切分支,中央仓库只是"约定的同步点" |

> **🎯 面试直击**:`git merge` 和 `git rebase`有什么区别?
> `merge` 把两条分支的历史**合并出一个新的合并提交**,保留真实的分叉形状;`rebase` 把你的提交**"搬"到目标分支最新提交之后**,历史变成一条直线、更干净,但**改写了提交哈希**。经验:公共分支(别人也在用的)别 rebase,以免打乱他人历史;自己的本地分支可以 rebase 让历史整洁。追问点:三个区(工作区/暂存区/仓库)与 `reset --soft/--mixed/--hard` 各退到哪个区。

### 一、选择题（10 道）

1. [基础] `git add` 的作用是？
- A) 将文件从仓库提交到远端　B) 将工作区修改添加到**暂存区**　C) 将暂存区提交到仓库　D) 初始化仓库

2. [基础] `git commit` 的作用是？
- A) 将工作区修改保存到仓库　B) 将暂存区内容保存为一个**版本快照**　C) 同步到远端仓库　D) 回退修改

3. [基础] Git 三区模型中，正确的流转顺序是？
- A) 仓库 → 暂存区 → 工作区　B) 暂存区 → 仓库 → 工作区　C) 工作区 → `add` → 暂存区 → `commit` → 仓库　D) 仓库 → `commit` → 工作区

4. [进阶] `.gitignore` 文件的作用是？
- A) 标记重要文件　B) **排除**指定文件/目录，不让它们进入版本控制　C) 加速 Git 性能　D) 定义分支规则

5. [进阶] `git branch feature` + `git switch feature` 的可合并简写是？
- A) `git new feature`　B) `git switch -c feature`　C) `git checkout feature`　D) `git create feature`

6. [进阶] `git merge` 和 `git rebase` 的核心区别是？
- A) 完全相同　B) merge 保留分支历史（产生合并提交），rebase 将提交"搬"到目标分支顶部（历史呈直线）　C) rebase 更安全　D) merge 会丢失历史

7. [进阶] `git rm --cached target` 的作用是？
- A) 删除 target 目录　B) 将 target 目录标记为未追踪　C) 从 Git 跟踪中移除但**保留本地文件**　D) 恢复已删除的文件

8. [综合] 不写 `.gitignore` 就 `git add .`，可能有以下哪个后果？
- A) 仓库更安全　B) `target/`、`.class` 等编译产物被提交，**仓库臃肿且多人协作时疯狂冲突**　C) 自动排除编译产物　D) 不会产生任何影响

9. [综合] Maven 项目的 `.gitignore` 中最应该排除的三个目录/文件是？
- A) src/、pom.xml、README　B) target/、*.class、.idea/　C) main/、test/、resources/　D) .git/、*.java、*.xml

10. [综合] 下列说法**正确**的是？
- A) `git commit` 会自动 push 到远端　B) Git 是集中式版本控制工具　C) 已推到远端的公共分支**不应该**做 rebase（会改写历史）　D) `git add` 等于 `git commit`

> [!答案] **1-B** `git add` = 工作区 → 暂存区；`git commit` = 暂存区 → 仓库。**举一反三**：`git commit -a` 跳过 add（只对已追踪文件），新文件仍需先 add。
> [!答案] **2-B** `commit` 把暂存区的快照永久保存到本地仓库，带时间戳和消息。**举一反三**：commit 只保存在本地——`git push` 才会同步到远端。
> [!答案] **3-C** 编辑文件（工作区）→ `git add`（暂存区）→ `git commit`（仓库）。三步组成一个完整的存档动作。**举一反三**：`git status` 可以查看三个区的差异。
> [!答案] **4-B** `.gitignore` 是黑名单，匹配到的文件/目录不会被 `git add` 包含。**举一反三**：原则——只提交源码，能由构建重新生成的（target/、node_modules/、.class）一律 ignore。
> [!答案] **5-B** `git switch -c feature` = 创建并切换到 feature 分支。`git checkout -b feature` 是旧写法，效果相同。**举一反三**：`git switch` 是 Git 2.23+ 引入的更清晰的分支切换命令，替代 `git checkout`。
> [!答案] **6-B** merge 保留完整分叉历史，rebase 把提交搬成一条直线。**举一反三**：公共分支禁止 rebase（会改写他人依赖的提交哈希）；自己的本地分支可 rebase 保持整洁。
> [!答案] **7-C** `--cached` 表示只从 Git 的跟踪中移除（不再纳入版本控制），但不删除磁盘上的实际文件。**举一反三**：这是补救"已经把 target/ 提交进去"的标准操作——先写 `.gitignore`，再 `git rm -r --cached target`。
> [!答案] **8-B** 编译产物每次构建都会变化，提交进仓库会导致：①仓库体积暴增；②每次编译产生无意义的 diff；③多人 merge 时 .class 疯狂冲突。**举一反三**：在项目初始化时就创建 `.gitignore`，不要等到第一个 commit 后补救。
> [!答案] **9-B** `target/`（Maven 构建输出）、`*.class`（编译产物）、`.idea/`（IDE 配置）。**举一反三**：还有 `*.iml`（IDEA 模块文件）、`.DS_Store`（macOS）、`*.log` 等。
> [!答案] **10-C** rebase 改写 commit 哈希——已推送的分支被 rebase 后，队友本地基于旧哈希的历史就"对不上"了，需要 force push 才能同步，严重影响协作。**举一反三**：Git 是分布式的，每个人的本地仓库都有完整历史。

### 二、解答题（3 道）

1. [概念] Git 的三个区（工作区、暂存区、仓库）分别存放什么内容？`git status` 如何体现三个区的差异？

2. [场景] 你和同学都在开发咖啡站项目。你在 `feature/discount` 分支上加了会员折扣功能，同学在 `main` 分支修了一个库存 Bug。请描述如何把你的折扣功能安全地合入 main（含处理潜在冲突的步骤），以及在合并前为什么应该先 `git pull` 拉取同学修的那部分。

3. [综合] 你的项目被人发现 `target/` 目录记录在了 Git 历史中（第 3 个 commit 开始就有）。请给出完整的补救方案：①如何清理当前工作区；②如何停止追踪；③历史里的哪些不需要清理（为什么）；④如何防止未来再犯。

> [!答案] **1** 工作区：你正在编辑的文件（未暂存的改动 → `modified`）；暂存区：`git add` 后等待提交的文件（`Changes to be committed`）；仓库：`git commit` 后的永久快照（`nothing to commit`）。`git status` 明确区分：红色文件名 = 工作区修改未暂存；绿色文件名 = 已暂存待提交；干净状态 = 三个区一致。**举一反三**：`git diff` 看工作区 vs 暂存区的差异；`git diff --staged` 看暂存区 vs 仓库的差异。
> [!答案] **2** 流程：①在 `feature/discount` 分支上 commit 所有改动；②`git switch main` → `git pull`（拉取同学的 Bug 修复）；③`git merge feature/discount`（合并你的折扣功能）；④如有冲突——Git 会标记冲突文件，手动编辑解决后 `git add` + `git commit`；⑤最后视情况 `git push`。先 pull 的原因：确保 main 是最新的，在本地先解决冲突再推送，避免直接把冲突推到远端。**举一反三**：`git merge --abort` 可在解决到一半时放弃合并。
> [!答案] **3** 补救：①当前工作区——新建/补充 `.gitignore`（写入 `target/`、`*.class`）；②停止追踪——`git rm -r --cached target/` + commit；③历史——**不需要清理**。理由：重写历史（`git filter-branch`/`BFG Repo-Cleaner`）会改变所有 commit 哈希，如果已推送，所有协作者都需要重新 clone，代价远大于收益。只清理当前和未来即可；④防再犯——`.gitignore` 在项目初始化时就创建并提交 + 在 CI 中加检查步骤（如 `git status --porcelain` 不应有未追踪的构建产物）。**举一反三**：可安装 pre-commit hook 自动检查。

### 三、代码题（2 道）

1. [基础] 用命令（文字）描述一次完整 Git 工作流：初始化仓库、创建 `.gitignore`（忽略 `target/` 和 `*.class`）、创建 `Main.java`、提交首次 commit、基于当前状态创建 `feature/logging` 分支、在该分支上修改文件并提交、切回 `main` 分支并 merge。用命令序列写出。

2. [综合] 模拟一个"合并冲突"的场景并描述解决过程：①在 `main` 分支创建 `Price.java`（price=20）；②创建 `feature/discount` 分支，修改 price=18 并 commit；③切回 `main`，修改 price=22 并 commit；④尝试 merge `feature/discount` 到 `main`；⑤写出冲突时 Git 标记的样子；⑥写出解决冲突后的最终代码（取两者中的较小值）和完成合并的命令。

> [!答案] **1 验收**：
> ```bash
> git init
> echo "target/" > .gitignore
> echo "*.class" >> .gitignore
> git add .gitignore
> git commit -m "chore: 初始化仓库，添加 .gitignore"
> echo 'public class Main { public static void main(String[] a) { } }' > Main.java
> git add Main.java
> git commit -m "feat: 创建程序入口 Main"
> git switch -c feature/logging
> # 编辑 Main.java，添加日志代码...
> git add Main.java
> git commit -m "feat: 添加日志功能"
> git switch main
> git merge feature/logging
> ```
> **举一反三**：`git log --oneline --graph` 可视化分支历史；`git branch -d feature/logging` 删除已合并的分支。
> [!答案] **2 验收**：
> ```bash
> # ① main 分支创建 Price.java (price=20)
> echo 'int price = 20;' > Price.java
> git add Price.java && git commit -m "feat: 基础定价 20 元"
> # ② 创建 feature/discount，改 price=18
> git switch -c feature/discount
> echo 'int price = 18;' > Price.java
> git add Price.java && git commit -m "feat: 会员折扣 18 元"
> # ③ 切回 main，改 price=22
> git switch main
> echo 'int price = 22;' > Price.java
> git add Price.java && git commit -m "chore: 调价至 22 元"
> # ④ merge → 冲突！
> git merge feature/discount
> # 输出: CONFLICT (content): Merge conflict in Price.java
> ```
> ⑤ Git 冲突标记的样子：
> ```
> <<<<<<< HEAD
> int price = 22;
> =======
> int price = 18;
> >>>>>>> feature/discount
> ```
> ⑥ 解决冲突（取较小值 18）+ 完成合并：
> ```bash
> # 手动编辑 Price.java，删除标记，改为 int price = 18;
> echo 'int price = 18;' > Price.java
> git add Price.java
> git commit -m "merge: 合并会员折扣，取最低价 18 元"
> ```
> **举一反三**：`<<<<<<< HEAD` 和 `=======` 之间是当前分支的内容（22），`=======` 和 `>>>>>>>` 之间是合并过来的分支的内容（18）。冲突的本质是——Git 不知道你要哪一个，你手动决定。
