# 《从零开始学 Java》31 · Git 版本时间机

> 连载特刊 · 第三季「工程时代」第 7 话(实验手册)· 基线 Java 25(最新 LTS)
> 承接:上一话代码有了体系化测试,但没有任何版本存档,改坏了只能干瞪眼。

---

## 一、需求:给代码装一台时间机

阿零昨天重构手滑删了半个类,今天想找回昨天的版本——发现根本没存档。更别说和同学并行开发同一个项目:两人改同一个文件,互相覆盖。豆豆:「你需要一台**时间机**:随时存档、随时回退、还能开平行时间线各干各的,最后再汇到一起。」

这一话不改业务逻辑,而是把项目纳入 **Git** 版本控制——它是团队协作与持续交付的地基。

---

## 二、漫画 · 时间机

> **〔1〕** 阿零对着删坏的代码欲哭无泪:「昨天还好好的……」
> 豆豆:「因为你从没**存档**。来,开时间机。」

> **〔2〕** 一台写着 `Git` 的机器亮起,面板三个格子:**工作区** → `add` → **暂存区** → `commit` → **仓库(存档点)**。
> 豆豆:「`commit` 就是一个存档点,盖上时间戳和说明。想回哪个存档,随时跳。」

> **〔3〕** 机器分出一条平行光轨 `feature` 分支。
> 豆豆:「`branch` 是**平行时间线**。你在支线上大胆试验,炸了也不影响主线 `main`;成了再 `merge` 汇回去。」

> **〔4〕** 阿零一句 `git add .` 把 `target/` 里一堆 `.class` 也塞进了暂存区,仓库瞬间臃肿。
> 豆豆(叼豆子):「编译产物凭什么进仓库?写张 **`.gitignore`** 黑名单,把它们挡在门外——只存**源码**,别存能重新生成的东西。」

---

## 三、本话目标

- 理解 Git 三个区:工作区 / 暂存区(add)/ 本地仓库(commit);
- 用 `init / add / commit / log` 给项目建立版本历史;
- 用 `branch / merge` 开平行时间线并汇流;
- 用 `.gitignore` 把 `target/`、`.class`、IDE 配置挡在仓库外;
- 踩一次"把编译产物提交进去"的坑并清理。

---

## 四、原理图:三个区与分支

```text
工作区(你编辑的文件)
   │  git add
   ▼
暂存区(准备提交的快照)
   │  git commit -m "..."
   ▼
本地仓库(一串带时间戳的存档点 = commit)

main    ●──●──●──────●   ← 汇流(merge)
             \       /
feature       ●──●──         平行时间线,试验不惊动主线
```

## 五、实验:把咖啡站纳入 Git

先写 `.gitignore`(放项目根目录),再初始化:

```gitignore
# 编译产物 / 构建输出
target/
*.class
# IDE / 系统
.idea/
*.iml
.DS_Store
```

```bash
git init                       # 初始化仓库
git add .                      # 暂存(.gitignore 里的会被自动跳过)
git commit -m "feat: 咖啡站 v2.6,含异常/文件/Stream/测试"

git switch -c feature/discount # 开一条平行时间线做"会员折扣"
# ...改代码...
git commit -m "feat: 加入会员折扣"
git switch main                # 回主线
git merge feature/discount     # 把折扣成果汇回主线
git log --oneline              # 看存档历史
```

## 七、读懂现象:仓库被编译产物淹没

```text
Changes to be committed:
	new file:   target/classes/CoffeeShop.class
	new file:   target/classes/MenuStore.class
	new file:   target/coffee-shop-1.0.0.jar
	... (几十个 .class)
```

一堆 `.class` 和 jar 混进了暂存区。后果:仓库臃肿、每次编译都产生"假改动"、多人合并时 `.class` 疯狂冲突。补救:

```bash
# 补上 .gitignore 后,把已误入的产物从版本控制里移除(保留本地文件)
git rm -r --cached target
git commit -m "chore: 忽略 target/ 编译产物"
```

原则一句话:**只提交源码和不可再生的东西;凡是能由构建重新生成的(target/、node_modules/、.class),一律 ignore。**

> **⏳ 版本时光机 · 从集中式到分布式**

| 时代 | 代表 | 特点 |
|---|---|---|
| 集中式 | SVN / CVS | 只有一个中央仓库,断网就没法提交、看历史 |
| 分布式 | **Git** | 每个人本地都有完整历史,离线可提交/切分支,中央仓库只是"约定的同步点" |

> **🎯 面试直击**:`git merge` 和 `git rebase`有什么区别?
> `merge` 把两条分支的历史**合并出一个新的合并提交**,保留真实的分叉形状;`rebase` 把你的提交**"搬"到目标分支最新提交之后**,历史变成一条直线、更干净,但**改写了提交哈希**。经验:公共分支(别人也在用的)别 rebase,以免打乱他人历史;自己的本地分支可以 rebase 让历史整洁。追问点:三个区(工作区/暂存区/仓库)与 `reset --soft/--mixed/--hard` 各退到哪个区。

## 🎯 随堂练习

先自己做,再对答案。每道答案都带一句「举一反三」,帮你把这一个点连成一片。

### 选择题(10 道)

1. Git 的三个区依次是?
   - A) 本地 / 远程 / 备份　B) 工作区 → 暂存区(add)→ 本地仓库(commit)　C) 分支 / 标签 / 提交　D) 源码 / 产物 / 配置
2. 一个 commit 本质上是?
   - A) 一次文件保存　B) 一个带时间戳的存档点(快照)　C) 一条分支　D) 一次远程推送
3. `.gitignore` 的取舍原则是?
   - A) 忽略所有大文件　B) 只提交源码和不可再生的东西;凡是构建能重新生成的(`target/`、`.class`)一律忽略　C) 忽略所有二进制　D) 由 IDE 自动决定
4. 不写 `.gitignore` 就 `git add .`,后果是?
   - A) 仓库臃肿、每次编译产生「假改动」、多人合并时 `.class` 疯狂冲突　B) 提交失败　C) Git 自动跳过产物　D) 只是占点空间,没有别的影响
5. 已经误提交了 `target/`,补救命令是?
   - A) `git rm -r target`　B) `git rm -r --cached target`(从版本控制移除但保留本地文件)　C) `git reset --hard`　D) 删掉仓库重建
6. `git switch -c feature/discount` 做了什么?
   - A) 切到已有分支　B) 新建并切换到一条平行时间线　C) 合并分支　D) 删除分支
7. `merge` 和 `rebase` 的核心区别是?
   - A) 速度不同　B) `merge` 产生合并提交、保留真实分叉;`rebase` 把提交搬到目标分支之后,历史成一条直线但**改写了提交哈希**　C) `rebase` 会丢代码　D) `merge` 只能用于主分支
8. 关于 rebase 的经验法则是?
   - A) 任何分支都该 rebase 保持整洁　B) **公共分支(别人也在用的)别 rebase**,自己的本地分支可以　C) 只有主分支能 rebase　D) rebase 已过时,别用
9. Git 相对 SVN 这类集中式版本控制的关键优势是?
   - A) 界面更好　B) 分布式:每个人本地都有完整历史,离线可提交/切分支　C) 文件体积更小　D) 不需要合并
10. 提交前想确认「暂存区里到底有什么」,该用?
    - A) `git log`　B) `git status`　C) `git branch`　D) `git merge`

> [!答案]
> **1-B**　编辑 → add → commit,三步三个区。**举一反三**:理解三个区,`reset --soft/--mixed/--hard` 各退到哪一层就一目了然了。
> **2-B**　commit 是快照不是差异。**举一反三**:正因为是快照,Git 切分支才那么快 —— 它不需要「重放」历史。
> **3-B**　只存不可再生的东西。**举一反三**:同理 `node_modules/`、`build/`、`*.log` 都该忽略;而锁文件(`package-lock.json`)反而要提交,因为它不可再生。
> **4-A**　产物混进仓库是低级但常见的失误。**举一反三**:代码评审时看一眼 diff 里有没有 `.class`/`.jar`,是最便宜的质量检查。
> **5-B**　`--cached` 只从索引移除,不删你本地文件。**举一反三**:漏掉 `--cached` 会把本地文件也删掉 —— 这个参数值得记牢。
> **6-B**　`-c` = create。**举一反三**:`git switch` 是新命令,语义比老的 `git checkout`(既切分支又还原文件)清晰得多。
> **7-B**　一个保留分叉,一个改写历史。**举一反三**:改写哈希意味着别人基于旧哈希的工作会对不上,这就是下一题那条法则的由来。
> **8-B**　公共分支 rebase 会打乱他人历史。**举一反三**:一句口诀 ——「rebase 私有,merge 公有」。
> **9-B**　完整历史在本地,断网照样干活。**举一反三**:所以「中央仓库」在 Git 里只是约定的同步点,技术上并不特殊。
> **10-B**　`git status` 会分区列出改动。**举一反三**:配合 `git diff --staged` 能看清暂存区的具体内容,提交前扫一眼是好习惯。
