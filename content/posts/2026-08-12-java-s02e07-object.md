## 一、需求:两个「张三」应该算同一个会员

会员卡上线,阿零用对象表示每位会员。他 `new Member("m01")` 建了两次同一个人,写下 `new Member("m01").equals(new Member("m01"))`,满以为 `true`,结果是 `false`,程序一口咬定这是**两个人**。

豆豆点破:「默认的 `equals` 比的是**『是不是同一个对象』**(内存地址),不是**『内容一不一样』**。两次 `new`,地址天生不同,所以判不相等。」这个坑不修好,下一步做「会员去重」会全线崩盘。

## 三、本话目标

- 理解 `Object` 是所有类的根,默认 `equals` 比引用、默认 `toString` 是乱码;
- 手写重写 `equals` + `hashCode`(**成对出现**)与 `toString`,吃透契约;
- 认识 `record`,把 Coffee 正式升级为 `record Coffee(String name, double price, int stock)`;
- **故意只写 equals、不写 hashCode**,亲手埋下一颗要到两话后才引爆的雷。

## 四、原理图:Object 的三条契约

```text
Object 默认给的:
  equals  → 比引用(是不是同一个对象)
  hashCode→ 由对象地址算出,同一对象每次相同,不同对象几乎必不同
  toString→ "类名@十六进制哈希",给人看约等于乱码

重写 equals 时必须守的契约:
  a.equals(b) 为真  ⇒  a.hashCode() == b.hashCode()   （相等则哈希必相等）
  反之不要求：哈希相等，未必 equals（那叫哈希碰撞，允许）

现代捷径:record Coffee(String name, double price, int stock) { }
          编译器自动生成 equals / hashCode / toString / 构造器 / 三个访问器
```

一句话记牢:**`equals` 和 `hashCode` 是一对连体婴,动一个必须动另一个**——否则对象进 `HashSet`/`HashMap` 后,去重和查找会诡异地失灵。

## 五、代码:手写契约 vs record 自动生成

**手写版**(为了理解契约,先吃一次苦):

```java
import java.util.Objects;

class Member {
    private final String id;
    Member(String id) { this.id = id; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;                 // 同一对象,快路径
        if (!(o instanceof Member m)) return false; // 模式匹配 instanceof,顺带强转成 m
        return Objects.equals(id, m.id);            // 按 id 判等(null 安全)
    }
    @Override public int hashCode() { return Objects.hash(id); }  // 必须和 equals 用同一批字段
    @Override public String toString() { return "Member(" + id + ")"; }
}
```

**现代版**——把项目里的 Coffee 从普通 class **正式升级为 `record`**,三件套一行全自动:
```java
// 全季统一:纯数据的 Coffee 固定三字段(含库存 stock),往后各话一律沿用这一个
record Coffee(String name, double price, int stock) {}

var a = new Coffee("拿铁", 18.0, 10);
var b = new Coffee("拿铁", 18.0, 10);
System.out.println(a.equals(b));  // true —— record 按全部字段逐个比
System.out.println(a);            // Coffee[name=拿铁, price=18.0, stock=10] —— toString 自动可读
```

> **豆豆锐评**:`Objects.hash(id, name)` 写着爽,但它是**可变参数**——每次调用都悄悄 `new` 一个 `Object[]` 装参数、还给 `double`/`int` 装箱。绝大多数场景无所谓;但若这段哈希在**热点路径**上每秒被调几百万次,就手写 IDE 那套 `int result = f1.hashCode(); result = 31 * result + Double.hashCode(price);`,省掉数组分配。知道有这回事,调优时才不露怯。

> **⏳ 版本时光机 · 数据载体怎么从一坨瘦成一行**

| JDK 版本 | 写一个「值对象」要写什么 | 关键变化 |
|---|---|---|
| Java 8~15 | 字段 + 构造器 + 每个字段 getter + 手写 `equals`/`hashCode`/`toString`,动辄五六十行 | 全靠手写或 IDE 生成,改字段要同步改一堆,极易漏 `hashCode` |
| Java 16 | `record Coffee(String name, double price, int stock) {}` 一行 | JEP 395 `record` 转正,编译器按字段自动生成全套方法 |
| Java 25 | 同上,并可配合**记录模式**解构:`if (c instanceof Coffee(var n, var p, var s))` | record 已是值对象事实标准,还能被模式匹配一把拆开 |

一句演进小结:从「手写五十行还易漏 `hashCode`」到「一行且天生守约」——`record` 不只少打字,更是**把最易犯的错从源头消灭**。

## 六、故意制造一个 Bug:只写 equals,不写 hashCode

阿零嫌 `hashCode` 麻烦,决定「只重写 `equals` 就够了」:

```java
class Member {
    private final String id;
    Member(String id) { this.id = id; }
    @Override public boolean equals(Object o) {
        return o instanceof Member m && Objects.equals(id, m.id);
    }
    // 没有 hashCode —— 编译能过,运行不报错,但契约已经被违反
}
```

---

## 七、读懂现象:不报错,却已经违约

编译、运行**全都不报错**——这正是它阴险的地方。可你一测就露馅:两个 `new Member("m01")`,`a.equals(b)` 是 `true`(内容相等),`a.hashCode() == b.hashCode()` 却是 `false`(默认 `hashCode` 按地址算)。**「相等则哈希必相等」的契约被撕破了**,而编译官不管这条语义约束,JVM 也不吭声,它就安静地躺在你代码里。

> **豆豆锐评**:这类 Bug 比报错的更可怕——它**不吭声**,直到你把对象丢进「用 `hashCode` 找桶、用 `equals` 确认」的容器才突然翻脸。这颗雷我们**故意留着不当场修**,让你两话后亲眼看它在 `Set` 里爆。

> **🎯 面试直击**:为什么重写 `equals` 必须重写 `hashCode`?
> 因为 `HashSet`/`HashMap` 先用 `hashCode` 定位「桶」,再在桶内用 `equals` 逐个确认。若两个 `equals` 相等的对象 `hashCode` 不同,会被分到不同桶,永远碰不到一起做 `equals`——去重、查找、去键全部失灵。追问点:`hashCode` 相等而 `equals` 不等允许吗?允许,那叫哈希碰撞,靠桶内 `equals` 兜底。

## 八、修复,并用测试证明

修法只有两条:**补上 `hashCode`**,或**干脆用 `record`**(记不住契约就让编译器替你守)。给 Coffee 补一个把契约钉死的测试:

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class CoffeeTest {
    @Test
    void equal_coffees_share_hashcode() {
        var a = new Coffee("拿铁", 18.0, 10);
        var b = new Coffee("拿铁", 18.0, 10);
        assertEquals(a, b);                          // 内容相等
        assertEquals(a.hashCode(), b.hashCode());    // 且哈希相等 —— 契约成立
        assertNotSame(a, b);                         // 但确实是两个对象
    }
}
```

测试一通过,Coffee 就能**安全地**进 `Set`/`Map` 去重和索引了。而阿零那个偷懒的 `Member`,还在等着爆。

Coffee 学会了认人,可订单还没处理——顾客一多,固定长度的数组开小了装不下、开大了空浪费。

### 一、选择题（10 道）

3. [基础] `Object` 类中 `equals()` 的默认实现是比较什么？- A) 字段内容　B) 引用地址（`==`）　C) 哈希码　D) 类名
4. [进阶] 为什么覆写 `equals()` 就必须覆写 `hashCode()`？- A) 编译器强制　B) 契约：相等的对象必须有相等的哈希码　C) 为了性能　D) 其实不是必须的
5. [进阶] `equals()` 方法的参数类型是什么？- A) `Object`　B) `泛型 T`　C) 当前类的类型　D) `String`
6. [进阶] 下面覆写 `equals` 哪个是正确的签名？- A) `public boolean equals(MyClass o)`　B) `@Override public boolean equals(Object o)`　C) `public boolean equals(Object o, MyClass o2)`　D) `public void equals(Object o)`
7. [进阶] `Objects.equals(a, b)` 与 `a.equals(b)` 相比，好处是什么？- A) 更快　B) `a` 为 `null` 时不会抛 NPE　C) 更短　D) 功能完全一样
8. [综合] `hashCode()` 的契约是什么？- A) 相等的对象可有不同哈希码　B) 相等的对象必须有相同哈希码，但哈希码相同不必相等　C) 哈希码必须唯一　D) 哈希码随时间变化
9. [综合] 如果只覆写 `equals` 不覆写 `hashCode`，把对象放入 `HashSet` 会有什么后果？- A) 正常工作　B) 两个 `equals()` 相等的对象可能被当作不同元素保留　C) 编译错误　D) 自动补充 hashCode
10. [综合] `record Coffee(String name, double price, int stock) {}` 自动提供了什么？- A) 只有 getter　B) 构造器 + getter + `equals`/`hashCode`/`toString` 全自动生成　C) 只有 toString　D) 什么都没提供

> [!答案] **1-C**　`java.lang.Object` 是 Java 类层次结构的根。**2-B**　默认 `toString()` = `类名@hashcode`（如 `Coffee@1a2b3c`）。**3-B**　`Object.equals()` 默认就是 `==`，比较两个引用是否指向同一块内存。**4-B**　`equals`/`hashCode` 契约：`a.equals(b) == true → a.hashCode() == b.hashCode()`。违反它 = 集合类（HashSet/HashMap）行为不可预期。**5-A**　`public boolean equals(Object o)`——参数必须是 `Object`，否则是重载而非覆写。**6-B**　必须加 `@Override` + 参数类型为 `Object`——写成 `equals(MyClass o)` 是重载，不是覆写，编译器不会帮你发现。**7-B**　`Objects.equals(a, b)` 内部先判空：`(a == b) || (a != null && a.equals(b))`——a 为 null 时不炸。**8-B**　核心契约：equals → hashCode 一致；但 hashCode 一致 ↛ equals（哈希冲突）。**9-B**　去重失效——两个 "张三" 的 hashCode 不同（Object 默认用内存地址），被分到不同桶，HashSet 认为它们不同。**10-B**　`record` 自动生成：全参构造器 + getter（方法名即字段名）+ `equals`/`hashCode`/`toString`。
**举一反三**：第 4、8、9 题是面试连环套——从"为什么要一起覆写"到"不覆写会怎样"到"record 怎么解决"，一口气串起 Object 三大方法。

### 二、解答题（3 道）

1. [概念] 为什么 `equals` 参数类型必须是 `Object` 而不是当前类的类型？如果写成 `equals(MyClass o)` 会发生什么？
2. [场景] 咖啡站会员系统：两个 `new Member("张三")` 应该算同一个人。请说明需要覆写哪些 Object 方法、覆写的完整契约是什么、如果漏掉 `hashCode` 在哪种容器里才会暴露问题（而在 List 里为什么没事）。
3. [综合] 自反性、对称性、传递性、一致性、非空性——`equals` 方法的五条约定。举一个违反其中某一条的实际代码例子，说明会导致什么 bug。

> [!答案] **1**　参数必须是 `Object` 因为这是覆写（Override）父类 `Object.equals(Object)`。如果写成 `equals(MyClass o)`，那是在类里新增了一个**重载（Overload）**方法，而不是覆写。后果：`Object o = new MyClass(); o.equals(another)` 走的是 `Object.equals`（比较引用），不会调用你写的重载版本——静默 bug。`@Override` 注解能立刻暴露这个问题（编译器报错"Method does not override"）。**举一反三**：这就是为什么 `@Override` 是"防御性注解"——不写也能编译通过，但拼错签名时会悄悄地产生一个没人调的重载方法。**2**　需要覆写 `equals()` 和 `hashCode()`。合约：①`equals` 按 name 判等（同 name = 同一人）；②`hashCode` 基于 name 计算（`Objects.hash(name)`），保证 equals 相等的对象 hashCode 一致。在 `List` 里不暴露问题——List 的 `contains()` 只看 `equals`，不调用 `hashCode`。但在 `HashSet`/`HashMap` 里会暴露——先去错桶，`equals` 都轮不到用，"张三" 1 号和 2 号擦肩而过。**举一反三**：这就是第 19 话（S02E07）埋的雷，在第 21 话（S02E09 Set）才炸——List 无视 hashCode，Set 依赖 hashCode，跨容器行为不一致是初学者最困惑的点。**3**　常见违反是在 `equals` 中混入"子类比较"。例如：
> ```java
> class Parent {
>     @Override public boolean equals(Object o) {
>         if (!(o instanceof Parent)) return false;
>         return xxx.equals(((Parent) o).xxx);
>     }
> }
> class Child extends Parent { ... }
> Parent p = new Parent();
> Child c = new Child();
> p.equals(c); // true (c instanceof Parent)
> c.equals(p); // false (p not instanceof Child) → 违反对称性!
> ```
> 对称性被打破后，`Set<Parent>` 中可能同时存在"父子对"——去重行为变得不可靠。解：用 `getClass()` 替代 `instanceof`（但破坏里氏替换），或把值对象设计成 `final` 类/`record`。**举一反三**：`equals` 五条约定是 Java 集合框架的基石——违反任何一条都可能让 HashMap.contains() 的 O(1) 查询悄无声息地出错。

### 三、代码题（2 道）

1. [基础] 写 `Member` 类（字段 `String id, String name`），覆写 `toString()` 返回 `"Member{id, name}"` 格式，覆写 `equals` 和 `hashCode` 使 `id` 相同即判为同一人。用 `HashSet` 验证去重（添加两个同 id 的 Member，size=1），打印 set 确认 `toString` 可读。
2. [综合] 将上面的 `Member` 改写为 `record Member(String id, String name) {}`，一行代码替代之前的四五十行。对比验证：创建两个相同 id 的 record 实例，测试 `equals()` 为 true、`hashCode()` 相同、`toString()` 可读。最后用 `record` 重写 `Coffee`（`String name, double price, int stock`），验证自动生成的 `equals`/`hashCode` 让两个相同字段的 Coffee 判等。

> [!答案] **1 验收**：
> ```java
> import java.util.Objects;
> class Member {
>     String id;
>     String name;
>     Member(String id, String name) { this.id = id; this.name = name; }
>     @Override public String toString() {
>         return "Member{" + id + ", " + name + "}";
>     }
>     @Override public boolean equals(Object o) {
>         if (this == o) return true;
>         if (!(o instanceof Member m)) return false;  // Java 16+ pattern matching
>         return Objects.equals(id, m.id);
>     }
>     @Override public int hashCode() {
>         return Objects.hash(id);
>     }
> }
> java.util.HashSet<Member> set = new java.util.HashSet<>();
> set.add(new Member("M01", "张三"));
> set.add(new Member("M01", "张三"));   // 同 id → 判定重复
> System.out.println(set.size());        // 1
> System.out.println(set);               // [Member{M01, 张三}]
> ```
> **举一反三**：注意 `equals` 里只比较 `id` 不比较 `name`——这意味着"同 id 不同名"也会被判等。这是业务设计决策，Java 不管。**2 验收**：
> ```java
> record Member(String id, String name) {}
> // 对比验证:
> Member m1 = new Member("M01", "张三");
> Member m2 = new Member("M01", "张三");
> System.out.println(m1.equals(m2));   // true
> System.out.println(m1.hashCode() == m2.hashCode()); // true
> System.out.println(m1);              // Member[id=M01, name=张三]
> // record Coffee:
> record Coffee(String name, double price, int stock) {}
> Coffee c1 = new Coffee("美式", 15.0, 10);
> Coffee c2 = new Coffee("美式", 15.0, 10);
> System.out.println(c1.equals(c2));   // true —— 字段全相同即相等
> ```
> **举一反三**：`record` 的 `equals`/`hashCode` 基于**所有组件字段**（全部参与比较），和上面手写的"只比 id"不同。如果需要只比 id，还是得手写类。但值对象（Value Object）场景——字段全相同就该判等——record 一行搞定。
