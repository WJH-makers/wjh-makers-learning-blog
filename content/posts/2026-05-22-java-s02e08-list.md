## 一、需求:一个能自动伸缩的订单容器

早高峰订单雪片一样来,晚上又冷清。阿零想用数组存订单,却卡在第一步:数组长度**一次定死**——开 `new String[10]` 高峰装不下,开 `new String[1000]` 平时全是空位白占内存。

豆豆:「你要的不是数组,是一个**能随订单增减自动伸缩**的容器——`List`。它底层还是数组,但满了会自己搬家换个更大的,你不用操心长度。」

## 二、漫画 · 会翻脸的传送带

> **〔1〕** 一条能自己接长的传送带,侧面刻着 `ArrayList`。订单一多,它「咔」地自动延长一截。

> 豆豆:「`LinkedList` 两端增删快,但**随机访问是 O(n)**——按下标取值它得从头走,别拿它当数组使。」

> **〔3〕** 阿零嫌麻烦,一边用 for-each 遍历订单、一边顺手把「美式」的杯子往外扔。
> 阿零:「反正边看边删,一趟搞定!」

> **〔4〕** 传送带突然「哐当」卡死、红灯狂闪,吐出一张报警条 `ConcurrentModificationException`。
> 豆豆:「一边遍历一边改结构,集合**当场翻脸**。它记着自己被改了几次,发现你绕过它偷偷动手,立刻掀桌。」

> **〔5〕** 阿零缩手:「那我少删一个、留倒数第二个不删呢?刚才那次它咋没报?」
> 豆豆(叼着豆子叉腰):「问到点子上了——这异常是**尽力而为**,不是每次都抛。别把『它没报』当成『我写对了』,那是运气,不是本事。」

## 三、本话目标

- 用 `List<T>` / `ArrayList` 做增删改查与遍历;
- 说清 `ArrayList`(数组,默认扩容 1.5 倍)与 `LinkedList`(链表,随机访问 O(n))的取舍;
- 踩一次遍历中删除触发的 `ConcurrentModificationException`;
- 想通它是 **fail-fast 尽力而为、不保证一定抛**,并学会用 `removeIf` / 迭代器安全删除。

## 四、原理图:List 的两种底盘

```text
List<String> orders = new ArrayList<>();
orders.add("美式");  orders.get(0);  orders.size();  orders.remove("美式");

ArrayList   底层=可扩容数组   随机访问 O(1)  中间增删要挪后面所有元素
            装满时:新建 1.5 倍大的数组,旧元素整体拷过去(所以别频繁扩)
LinkedList  底层=双向链表     随机访问 O(n)  两端增删 O(1)

遍历中改结构  → 迭代器发现 modCount 变了 → ConcurrentModificationException
安全删除     → removeIf(条件)  或  迭代器 it.remove()
```

## 五、代码:订单队列

```java
import java.util.ArrayList;
import java.util.List;

public class Orders {
    public static void main(String[] args) {
        List<String> orders = new ArrayList<>();
        orders.add("美式");
        orders.add("拿铁");
        orders.add("美式");

        System.out.println("共 " + orders.size() + " 单");
        for (String o : orders) System.out.println("制作 " + o);
    }
}
```

> **豆豆旁白**:`ArrayList` 默认初始容量为空,第一次 `add` 才分配。如果你已经知道大概要装多少,直接 `new ArrayList<>(1000)` 一次给够,能省掉中途一次次「搬家扩容」的开销——这在批量导入时是实打实的提速。

## 六、故意制造一个 Bug:遍历中删除

想在遍历时把所有「美式」取消掉:

```java
for (String o : orders) {
    if (o.equals("美式")) orders.remove(o);   // ← 故意:for-each 中直接改结构
}
```

## 七、读懂真实报错

```text
Exception in thread "main" java.util.ConcurrentModificationException
        at java.base/java.util.ArrayList$Itr.checkForComodification(ArrayList.java:1095)
        at java.base/java.util.ArrayList$Itr.next(ArrayList.java:1049)
        at Orders.main(Orders.java:12)
```

`ConcurrentModificationException`(并发修改异常,但**单线程也会抛**)。for-each 底层其实是个**迭代器**,它出生时记下集合的「修改次数」`modCount`;你绕过迭代器直接 `orders.remove(o)`,`modCount` 变了,迭代器下次 `next()` 一对账发现数字对不上,立刻抛异常——**防止你在一个不一致的状态上继续瞎跑**。

> **豆豆锐评**:注意它叫 **fail-fast(快速失败)**,不叫 **fail-safe**。它是**尽力而为**地帮你早发现,**不保证每次都抛**。经典反例:你删的是**倒数第二个**元素——删完后集合 `size` 少 1,迭代器的游标刚好等于新 `size`,`hasNext()` 直接返回 false、循环正常结束,`next()` 压根没再被调,那次对账就没发生,**异常也就没抛**。所以「这回没报」绝不等于「这么写是对的」。**永远别依赖它,该用安全删除就用安全删除。**

> **🔀 豆豆的多解台 · 遍历中删除元素,怎么删才安全?**

| 解法 | 代码要点 | 适合什么时候 | 坑 |
|---|---|---|---|
| 迭代器 `it.remove()` | `var it = list.iterator(); while(it.hasNext()){ if(...) it.remove(); }` | 删除逻辑复杂、需要在循环里干别的事 | 只能删「刚 `next()` 出来的那个」,别调错对象 |
| `Collection.removeIf` | `list.removeIf(o -> o.equals("美式"))` | **纯按条件批量删**(最常见) | 条件里别有副作用;一行搞定,首选 |
| 倒序索引 for | `for(int i=list.size()-1;i>=0;i--) if(...) list.remove(i);` | 需要按下标操作、或删除时还要看位置 | 必须**倒着删**,正序删会漏元素(删一个后面全前移) |

豆豆锐评:**默认用 `removeIf`**——它专为「按条件删」设计,内部走安全路径,一行、可读、不会踩 CME。只有当删除逻辑复杂到 `removeIf` 的一个 lambda 表达不清时,才退回迭代器。

## 八、修复,并用测试证明

用 `removeIf`,一行安全删除:

```java
static int cancelAll(List<String> orders, String name) {
    int before = orders.size();
    orders.removeIf(o -> o.equals(name));   // 内部走安全路径,不触发 CME
    return before - orders.size();          // 返回取消了几单
}
```

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class OrdersTest {
    @Test
    void cancel_all_americano() {
        var orders = new ArrayList<>(List.of("美式", "拿铁", "美式"));
        assertEquals(2, Orders.cancelAll(orders, "美式"));  // 取消 2 单
        assertEquals(1, orders.size());                     // 只剩拿铁
    }
}
```

## 🎯 随堂练习

先自己做,再对答案。每道答案都带一句「举一反三」,帮你把这一个点连成一片。

### 选择题(10 道)

1. `ArrayList` 装满后默认扩容成原来的多少倍?
   - A) 2 倍　B) 1.5 倍　C) 每次加 10　D) 不扩容,直接报错
2. `LinkedList` 的短板是?
   - A) 两端增删慢　B) 随机访问 O(n),按下标取值要从头一节节数　C) 不能存 null　D) 不能遍历
3. `for (String o : orders) { if (...) orders.remove(o); }` 会?
   - A) 正常删除　B) 抛 `ConcurrentModificationException`　C) 编译报错　D) 死循环
4. 上题异常的触发机制是?
   - A) 多线程冲突　B) 迭代器记着出生时的 `modCount`,发现集合被绕过它修改就掀桌　C) 数组越界检查　D) GC 触发
5. 关于 `ConcurrentModificationException`,正确的说法是?
   - A) 只有多线程才会抛　B) 单线程也会抛,而且它是 **fail-fast 尽力而为**,不保证每次都抛　C) 一定会抛,可以当检测手段　D) 抛出后集合会自动回滚
6. 经典的「没抛出来」反例是删掉哪个元素?
   - A) 第一个　B) 中间任意一个　C) **倒数第二个** —— 删完游标刚好等于新 size,`hasNext()` 直接为 false　D) 最后一个
7. 「按条件批量删除」的首选写法是?
   - A) for-each 里 remove　B) `list.removeIf(o -> ...)`　C) 正序索引 for 删除　D) 先复制再清空
8. 用正序索引 `for` 删除元素会?
   - A) 完全正确　B) 漏掉元素 —— 删一个后面全部前移,必须**倒着删**　C) 抛 CME　D) 死循环
9. 已知大概要装 1000 条,`new ArrayList<>(1000)` 的收益是?
   - A) 元素访问更快　B) 省掉中途一次次「搬家扩容」的拷贝开销　C) 自动去重　D) 线程安全
10. `for-each` 遍历集合时,底层实际用的是?
    - A) 下标循环　B) 迭代器(Iterator)　C) 递归　D) Stream

> [!答案]
> **1-B**　满了就新建 1.5 倍大的数组、整体搬过去。**举一反三**:所以「频繁扩容」的代价是反复拷贝,批量导入前先给够容量最划算。
> **2-B**　链表按下标取值必须从头走。**举一反三**:实际工程里 `ArrayList` 几乎总是更优 —— `LinkedList` 只有在「两端频繁增删且不随机访问」时才值得考虑。
> **3-B**　绕过迭代器改结构,当场翻脸。**举一反三**:同理在 for-each 里 `add` 也会触发,不只是删。
> **4-B**　`modCount` 对账不上就抛。**举一反三**:这套「记修改次数」的机制在 `HashMap` 的迭代器里也一样存在。
> **5-B**　单线程照样抛,而且不保证每次都抛。**举一反三**:「这回没报」不等于「写对了」,那是运气不是本事。
> **6-C**　删倒数第二个时,`next()` 压根没再被调,对账没发生。**举一反三**:凡是「靠异常提醒我写错了」的依赖都不可靠 —— 检测机制不是正确性保证。
> **7-B**　`removeIf` 内部走安全路径,一行搞定。**举一反三**:条件里别写有副作用的代码 —— 它可能被调用的次数和你想的不一样。
> **8-B**　正序删会漏,倒序才安全。**举一反三**:根因还是 off-by-one 家族 —— 元素前移导致下标错位。
> **9-B**　一次给够,省掉搬家。**举一反三**:`HashMap` 同理,`new HashMap<>(预期容量)` 能减少 rehash。
> **10-B**　`for-each` 是迭代器的语法糖。**举一反三**:所以想在遍历中安全删除,直接用迭代器的 `it.remove()` 就名正言顺。
